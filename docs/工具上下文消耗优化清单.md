# 工具上下文消耗优化清单

> 状态：待实施清单，依据当前代码审查整理。已完成项不再重复列入待办。
> 目标：降低后续模型请求中的真实输入消耗，同时保留任务所需证据、错误诊断和按需恢复能力。不能只缩短前端展示，也不能把全局截断当作完成。

## 1. 已完成的直接收益项

- `write_file`：移除正文与 diff 回显，也不再为返回 diff 读取旧文件。
- `execute_command`：小输出保留原文，大输出只给摘要；已接受的有界结果可通过 `tool-result:` 恢复。
- `read_file`：默认 500 行、16 KiB；普通读取返回裸行；补充实际 `read_lines/total_lines/returned_bytes`；支持 `outline` 和单文件 `pattern` 定位读取。
- 写入、编辑、状态、目录、浏览器、MCP 等已有部分语义投影；模型观察与事件/审计载荷已分离。
- 工具规格已有 full/compact/tiny、固定 profile、schema 引用；线程 system prompt 与初始化记忆已冻结。
- 计划面板只返回状态，问询面板只返回等待输入标记，无需再按“完整计划/问题回显”立项。

## 2. P0：优先实施，收益最明确

### P0-1 在压缩检查点处理历史工具调用参数

- [ ] 在压力下为旧的、已成功完成的 `write_file`、`apply_patch` 调用参数生成 `{path, bytes, content_omitted, status}` 等短摘要；保留 tool call 与 tool result 配对。
- [ ] 不得直接改写当前稳定前缀中的参数。只能在压缩检查点生成新的模型上下文快照：检查点前的稳定前缀保持不变，旧的大参数在检查点摘要中收敛，最近消息原样接在摘要后。
- [ ] 新快照持久化后再用于后续轮次，让后续请求复用新的稳定前缀；转换时的一次性后缀缓存重建必须单独计量，不能宣称缓存不受影响。
- [ ] 如果当前链路无法建立并持久化检查点，就不压缩参数，退化为保留原文。
- [ ] 当前轮、最近若干轮、失败调用和仍需精确补丁上下文的调用不得压缩；原参数继续留在审计/持久历史中，后续需要正文时优先重读当前文件。

**原因**：工具结果已不再回显，但 assistant 的 tool call 参数仍会在每次后续请求中重复发送。直接修改旧参数会从首个变更点使 provider 的前缀缓存失效；持久历史 append-only 只保证可重放，并不能避免这种失效。

**位置**：模型历史派生、压缩检查点与 `orchestrator/microcompaction.rs` 相关链路。

### P0-2 限制会话历史的默认读取量与扇出

- [ ] 将 `sessions_history` 默认 200 条改为小窗口，并增加游标、时间范围和单条正文预算。
- [ ] 默认排除工具正文；`include_tools=true` 时使用单独、更小的预算。
- [ ] `sessions_list(message_limit>0)` 防止“50 个会话 × 每会话 50 条消息”的扇出，增加整次调用总消息/总字节上限。
- [ ] 列表默认只给 session 摘要；历史详情按 session 单独读取。

**位置**：`services/tools/session_tool.rs`、`session_tool_args.rs`。

### P0-3 消除知识库多查询的重复正文

- [ ] 多查询结果只保留一种主形态：扁平去重文档列表，或按 query 分组，不能同时返回 `documents` 与 `queries[*].documents` 两份正文。
- [ ] 每条命中只保留一个文档名称字段；当前 `document` 与 `name` 重复。
- [ ] 默认返回有界 snippet，`doc_id/chunk_id` 用于按需二读；完整 `content` 仅在显式详情请求中返回。
- [ ] 多查询按全局 top_k 限量，而不是每个 query 各自 top_k 后无界叠加。

**位置**：`services/tools/knowledge_tool.rs:162-240`、`379-425`、`462-547`。

### P0-4 让旧读取结果真正可压缩

- [ ] 区分“可以继续读源文件”与“必须永久保留当前观察”，不要让 `continuation_required` 自动排除所有 microcompaction。
- [ ] 对可重读的普通文件，旧观察缩成路径、范围、总行数和短预览；需要时通过 `pattern/outline/range` 重读。
- [ ] 对 `tool-result:` 句柄按 TTL 和可恢复状态判断，句柄过期前也不能假装永久可恢复。
- [ ] 与 P0-1 相同，只在压缩检查点切换模型上下文，不能把 hidden marker 的 append-only 存储误认为 provider 缓存仍然命中。
- [ ] 保留失败结果、非可复现外部结果和必要游标，不为省 token 丢失错误证据。

**原因**：默认读取超过 500 行的文件会产生 continuation 信号，当前 `protected_payload` 会让这类旧读取长期保持完整，长会话收益被抵消。

**位置**：`orchestrator/microcompaction.rs:16-120`。

### P0-5 降低技能首次加载的默认预算

- [ ] 评估将首次 `load` 从 48 KiB/800 行降为 manifest + 当前所需章节；保留显式扩大窗口的能力。
- [ ] 将技能观察预算与当前 16k token 特例解耦，避免一个技能挤占整轮工具观察预算。
- [ ] 资源索引只给相关资源，不给完整资源树；正文按 `section/path/cursor` 读取。
- [ ] 记录技能首次调用后的任务成功率，防止过度压缩导致反复补读。

**位置**：`services/tools/skill_call.rs:17-26`、`orchestrator/tool_result_payload.rs:575`。

### P0-6 浏览器默认只返回一种页面视图

- [ ] 避免同一结果同时携带 snapshot、text、refs 和重复 URL/title。
- [ ] 默认优先可操作 refs；正文阅读显式选择 `observe_text`，全文与无障碍树不要同时内联。
- [ ] refs 默认聚焦可见、可交互元素；当前 32 条上限应按任务实测继续收紧。
- [ ] batch 只返回最终必要状态和失败步骤，不重复每一步页面快照。
- [ ] 大正文继续使用绑定页面世代的 cursor，不将整页内容反复放入后续轮次。

**位置**：`orchestrator/tool_result_payload.rs:596-599`、`1611-1803`。

## 3. P1：第二批，统一高频工具协议

| 编号 | 工具或位置 | 当前消耗点 | 建议 |
| --- | --- | --- | --- |
| P1-1 | 工具 schema / profile | 默认 authorized 可能让大量无关工具定义进入每次请求；动态 schema 还可含长描述 | 默认从最小工具面开始，按任务升级；共享 `$defs`；长示例留在 full，不进 compact |
| P1-2 | 子智能体控制 | spawn task、report、history、卡片摘要可能与父线程已有内容重复；history 可返回多条消息 | list/status/wait 只回状态和增量；history 游标化；相同 report 不重复注入父上下文 |
| P1-3 | 命令会话 | 高频 poll 仍可能反复返回较大增量与状态字段 | 小增量原文、大增量摘要；退出时优先错误尾部；stdout/stderr 各只出现一次 |
| P1-4 | `web_fetch` / `web_search` | fetch 可保留约 12k 字符正文；搜索开启 scrape 后正文与 snippet 重叠 | 默认链接+snippet；正文按 max_chars/cursor；query/effective_query、provider/cache 等只留审计 |
| P1-5 | 记忆管理 | list/search 可含多条长正文；与初始化记忆或后续 recall 可能重复 | list/search 只回 id/title/tag/snippet；get 才给正文；写操作只回 id 和状态 |
| P1-6 | MCP package / 用户工具 | 通用 structured JSON 和 content blocks 字段多，未知结果可能退化为带转义的 JSON 字符串预览 | 优先结构化白名单和表格采样；资源只给引用；schema 按需 get；禁止 base64/raw blob |
| P1-7 | `search_content` | 命中行、segments、before/after、summary 中存在重复文本；多条命中可能重复同一上下文 | 合并相邻命中与重叠上下文；模型只保留 path/line/text；需要大上下文时引导 `read_file(pattern=...)` |
| P1-8 | 通用观察预算 | 默认单结果 4k token、整轮目标 16k/软限 20k，在并行工具调用时仍偏大 | 按工具语义进一步分档；并行时优先完整保留少量关键结果，其余摘要；不能把协议预留当正文配额 |
| P1-9 | `list_files` / `glob` | 大目录可返回数百条路径，公共前缀重复 | 小默认页；只给相对路径和 cursor；必要时按顶层目录采样并报告 omitted |
| P1-10 | 历史 reasoning / 长 assistant 内容 | 旧推理和长解释可能与最终答案、工具参数重复 | 只在压缩检查点生成新稳定上下文，保留最终结论、未完成决策和工具配对；不得影响最近推理链或原地改写稳定前缀 |
| P1-11 | 声转文与长媒体结果 | 转写正文、分段和元数据可能一次进入上下文 | 默认正文窗口 + segment cursor；生成类只回 artifact 引用和状态，不回完整 provider 响应 |

## 4. P2：协议与诊断体验完善

- [ ] **纯文本结果载体**：命令 stdout/stderr 可增加纯文本流式落盘，避免 `tool-result:` JSON 序列化和转义造成二次膨胀；仍需保留所有权、TTL、容量和有界读取。
- [ ] **失败结果恢复**：大输出失败目前主要保留短错误摘要；在不放大错误正文的前提下，补充与成功结果一致的按需恢复入口。
- [ ] **去重提示字段**：`patch_usage_hint`、后台 next_step、重复 continuation 文案改为稳定短代码，详细解释留在工具描述。
- [ ] **结构化错误**：统一错误码、失败位置、相关行和 retryable；避免 message、detail、stderr 重复表达同一错误。
- [ ] **媒体附件**：继续只传受控 artifact，不新增 base64、重复 URL、绝对路径或相同图片的多帧冗余。

## 5. 不建议优先投入的方向

- **继续削减小状态工具**：计划、问询、写入确认、桌面动作确认已经接近最小结果，收益很低。
- **只调整前端预览**：`tool_result_display` 和聊天列表预览不决定模型输入，不能作为 token 优化完成证据。
- **再次压缩 apply_patch 成功 diff**：成功模型投影已经是变更计数；审计 diff 不应被误删。
- **全局统一截断**：会破坏列表结构、游标、错误尾部和任务证据。应优先语义投影、分页、去重和旧参数压缩。
- **反复改写 system prompt 或初始化记忆**：会破坏前缀缓存；优化应发生在历史派生层，不违反线程初始化冻结约束。

## 6. 推荐实施顺序

1. **第一批**：P0-1 参数压缩检查点、P0-2 会话历史、P0-3 知识库去重。改动边界清晰，收益可直接测量。
2. **第二批**：P0-4 旧观察压缩、P0-5 技能、P0-6 浏览器。需要真实任务验证恢复率，不能只看字节下降。
3. **第三批**：P1 高频工具语义统一，最后处理 P2 的纯文本载体和协议细节。

## 7. 每项改造的验收清单

- [ ] 分别记录工具执行原始载荷、模型观察载荷、下一次完整请求的输入 token；不能用前端字符数替代。
- [ ] 分别记录检查点切换时的一次性后缀重建成本和后续请求的 cached/uncached input，确认新稳定前缀能够命中缓存；不得把 append-only 持久化当作缓存未失效的证据。
- [ ] 覆盖“单个大结果”和“多个并行小结果”，防止只优化单条预算而整轮仍膨胀。
- [ ] 覆盖长会话：大文件写入、长脚本、200 条以上历史、连续读取、技能加载、浏览器多步操作。
- [ ] 验证任务成功率、平均工具调用次数和补读次数；如果 token 降低但调用次数明显上升，不算有效优化。
- [ ] 验证错误尾部、退出码、路径、范围、游标和权限边界不丢失。
- [ ] 验证按需恢复：源文件可重读、句柄可读、TTL/容量失败有明确提示，不能承诺恢复生产者早已丢弃的流。
- [ ] 验证模型观察与事件/审计分离，前端完整展示和回放不需要被迫同步缩小。

## 8. 建议跟踪指标

| 指标 | 用途 |
| --- | --- |
| 单次工具观察近似 token / provider 实际 input token | 判断结果投影是否真正减少模型输入 |
| 下一请求总输入与新增输入 | 识别历史参数、重复正文和并行结果放大 |
| 每任务工具调用数、补读数、重跑数 | 防止以效率下降换取表面压缩 |
| 大结果恢复成功率 | 验证摘要之后仍能取得必要证据 |
| 压缩前后任务成功率 | 作为是否允许合入的最终门槛之一 |
| cached input 比例 | 防止动态改写破坏前缀缓存 |

相关方案与历史基线见 [工具与上下文提效方案](提效上下文方案.md)。本文只列当前剩余待办；实施完成后应更新对应条目和验收数据。
