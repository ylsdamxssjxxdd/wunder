# 工具结果裁剪与观测链路

> 排障中的一类分歧来自两条独立通道：「模型看到的内容」与「前端/监控展示的内容」。把展示截断误判成模型丢数据，或把模型输入压缩误判成前端 bug，是两类常见误判。§6 判据表用于判断症状属于哪条通道。

## 1. 两条通道总览

一次工具调用的结果会分叉成两条互不改写的路径：

```
工具执行（services/tools/dispatch.rs）
  → ToolResultPayload 统一载荷（orchestrator/tool_result_payload.rs）
  → normalize_tool_result_payload 业务失败识别（orchestrator/result_normalizer.rs）
  → finalize_tool_result 编排层裁剪（orchestrator/execute_tools.rs:741 → tool_exec.rs:337）
  ├── 展示通道：tool_result 事件 + tool_result_display 预览 + 写时视图投影 → 客户端
  └── 模型输入通道：build_tool_observation → "tool_response: " 前缀观测写入模型上下文
                     → microcompaction / compaction 在后续轮次继续压缩该上下文
```

| 通道 | 谁消费 | 裁剪发生地 | 是否影响模型推理 |
| --- | --- | --- | --- |
| 展示通道 | 蛹 / 蜂巢 / 舰桥等客户端 | `services/tool_result_display.rs`、`storage/thread_view_projection.rs` | 否 |
| 模型输入通道 | 下一轮模型调用 | `orchestrator/constants.rs` 裁剪、`microcompaction.rs`、`compaction_policy.rs` | 是 |

同一个 `tool_result` 事件负载里同时携带展示用字段与 `model_observation` 字段（`orchestrator/execute.rs:1446`），排障时可在一条事件里对照两路各看到了什么。

## 2. 展示通道：只影响客户端

### 2.1 事件预览：`tool_result_display`

`crates/wunder-runtime/src/services/tool_result_display.rs` 为原生客户端生成有界工具展示文本：

- `preview()` 单段限 **2400 字符 / 16 行**，超限追加 `…`。
- 按工具类型组装（执行类取前 3 条记录的 stdout/stderr、补丁取前 6 文件、网页搜索取前 8 条来源等），全部行合并后再过一遍 `preview()`。
- 传输/调试字段（如 `query_handle`、`cursor`、provider 名）**不作为 UI 内容输出**；运行中/失败状态由事件生命周期供给，缺失输出不等于成功。

### 2.2 写时视图投影：聊天行与线程轨迹

线程轨迹与聊天行里的工具条目**不是实时算出来的，而是写入时投影**（`crates/wunder-runtime/src/storage/thread_view_projection.rs`，头注释 「Write-time display projection, shared by both transactional stores」）：

| 投影字段 | 截断 | 位置 |
| --- | --- | --- |
| 消息正文预览 `content` | 2048 字符 | `message()`，projection.rs:12 |
| 推理摘要 `reasoning` | 2048 字符 | `set_reasoning()`，:27 |
| 轨迹行 `summary` | 256 字符 | `trajectory()`，:93 |
| 轨迹行 `tool_name` | 96 字符 | :94 |
| 子智能体卡片字段 | 256 字符；行内 ID 96 字符 | :151,175 |
| 单行子智能体卡片数 | `MAX_ROW_SUBAGENTS = 8` | :144 |

### 2.3 正文按块存储：完整内容仍可取回

预览截断不丢正文。正文以块存：`BODY_CHUNK_BYTES = 8192`（`crates/wunder-core/src/thread_view.rs:9`），落在 `thread_body_manifests` / `thread_body_chunks` 表（建表见 `storage/thread_view_store.rs:37-41`，SQLite 与 Postgres 双实现同名）。客户端取全文走 body 分块读取（`LIMIT 9` 块起读、游标续取，`storage/sqlite/thread_view_store.rs:751`）；FTS 搜索命中摘要再按 256 字符预览。

前端「看不到全」是 2.1/2.2 的预览在起作用；正文与原始 item 完整保留，按 2.3 取回。

## 3. 模型输入通道：真正影响模型看到什么

### 3.1 统一载荷与业务失败识别

- 工具返回值统一收敛为 `ToolResultPayload{ok, data, error, sandbox, meta}`（`orchestrator/tool_result_payload.rs:3`）。
- `normalize_tool_result_payload`（`orchestrator/result_normalizer.rs:20`）在传输 `ok` 之上做 `detect_business_failure`：传输成功但载荷表达业务失败的，翻转为 `ok=false` 并补错误消息与错误码。模型收到的是失败语义，而不是「看起来成功」的空结果。

### 3.2 编排层全局裁剪：`finalize_tool_result`

`execute_tools.rs:741` 调用 `finalize_tool_result`（实现在 `tool_exec.rs:337`），对将进入模型上下文的数据做裁剪，常量在 `orchestrator/constants.rs:41-50`：

| 常量 | 值 | 语义 |
| --- | --- | --- |
| `TOOL_RESULT_HEAD_CHARS` / `TOOL_RESULT_TAIL_CHARS` | 各 10000 字符 | 字符串按头 + 尾保留，中间插 `...(truncated)...` |
| `TOOL_RESULT_MAX_ARRAY_ITEMS` | 128（头 48 + 尾 16） | 普通数组限量 |
| `TOOL_RESULT_PAGINATED_MAX_ARRAY_ITEMS` | 500（头 180 + 尾 60） | 可分页结果放宽 |

部分工具经 `should_skip_event_payload_truncation` 跳过裁剪；裁剪事实记入 `truncated` 与截断原因随事件负载下发。更早还有工具自身的输出预算裁剪（读取字节上限、命令输出 head+tail、分页游标等），在 `services/tools/` 各工具内，见第 5 章。

### 3.3 观测写入：`tool_response:` 前缀

裁剪后的载荷经 `build_tool_observation`（`tool_exec.rs:260`）由 `to_compact_payload` 序列化为紧凑 JSON 观测串，以 `OBSERVATION_PREFIX = "tool_response: "`（`constants.rs:2`）为前缀写入模型上下文。历史里缺失配对结果的孤儿工具消息由 `orchestrator/context.rs` 的 `convert_orphan_tool_message_to_observation` / `build_missing_tool_observation` 做确定性补齐，保证上下文可重放。

### 3.4 microcompaction：旧观测瘦身（不是删除）

`orchestrator/microcompaction.rs` 在压力下把**旧的、可复现的**观测缩成 **768 字节**预览（`PREVIEW_BYTES`，:8），条件与边界：

- 保留最近 **5 组**（`KEEP_RECENT_GROUPS`，:6）不动。
- 只有至少能省 **256 token**（`MIN_SAVINGS`，:7）才执行。
- 受保护载荷不缩：业务失败（`ok=false` / `isError`）、带续读信号（`has_more`、`continuation_required`）、多模态内容、各类 `next_*` 游标字段（`protected_payload`，:16-40）。
- 替换历史以 **hidden marker 行**持久化：meta 携带 `type=microcompaction` 与 `replacement_history`（键名 `COMPACTION_REPLACEMENT_HISTORY_META_KEY`，`constants.rs:4`；写入与落库校验在 microcompaction.rs:204-267），模型输入派生时从该行重放，历史保持 append-only。

被缩掉的观测对模型只剩 768B 预览；模型需要完整内容时重新执行该工具（重读文件/重跑命令），这是「可复现」判据的含义。

### 3.5 压缩三触发

摘要压缩由 `orchestrator/compaction_policy.rs` 决策，三个触发面（`CompactionDecision`，:5-28）：

| 触发 | 条件 | 出处 |
| --- | --- | --- |
| `history` | 投影 token ≥ 0.9 × max_context（`COMPACTION_HISTORY_RATIO = 0.9`） | `constants.rs:7` |
| `overflow` | 投影 token ≥ limit | compaction_policy.rs:60 |
| `pre_sampling` | 占用 ≥ 0.9，或 ≥ `limit − clamp(limit/8, 256, 8192)` 的自适应留白 | :1-3,31-42 |

token 占用**只信任 provider 观测到的 input**（`execute.rs:410-412`），不做本地估算；压缩窗口保护当前用户消息（`memory_compaction_window.rs`）。压缩与缓存的完整链路见第 3 章。

## 4. 为什么两条通道必须分开设计

1. **prompt 缓存前缀稳定**：system prompt 首次确定后冻结，历史保持 append-only，才能复用大模型 API 的前缀缓存。若展示层按需改写历史条目，缓存即失效——所以展示裁剪只能发生在「投影」上，不能碰持久 item。
2. **append-only 历史**：microcompaction 不删行，而是追加 hidden marker 记录替换结果；摘要压缩同理。任何时刻都能从持久行重放出模型输入。
3. **补水可重放**：客户端断线重连后按 `change_seq`/`view_seq`/`event_seq` 游标补水（见第 4 章）。前提是 durable 数据完整、展示投影可重建——「原始内容必须完整保留、降级只影响展示」这条不变量正是由**持久 item/block（`thread_items`、`thread_body_chunks`）与展示投影行分离**兑现的：投影可随时重算，durable 表不因展示而变。

## 5. 观测面：数据到监控与客户端的链路

| 组件 | 角色 | 位置 |
| --- | --- | --- |
| `ThreadLogCommitter` | **durable 写唯一出口**：每会话 gate 串行提交 → 单事务落库 → 事务成功才发布游标；幂等空操作不发变更，失败提交不发游标 | `orchestrator/thread_log_committer.rs:9-21` |
| `EventEmitter` | emit 路径持锁，**同步 commit 到 durable** 再入队，保证游标序 == 队列序 == 线上序 | `orchestrator/event_stream.rs:36-38,160-162` |
| `ThreadChangeHub` | 只是**唤醒信号**，不是数据源 | `orchestrator/thread_change_hub.rs` |
| `thread_change_feeder` | 消费侧共享层，durable 帧每页 `FEEDER_PAGE_SIZE = 200`，内部通道容量 256，轮询兜底跨实例正确性 | `services/thread_change_feeder.rs:20-22` |
| WS 背压 | 写队列 `STREAM_EVENT_QUEUE_SIZE = 256`；剩余容量 ≤ 水位 `2` 时发 `slow_client` 告警（≥3s 一次），溢出发 `stream_overflow` + `resume_recommended` 再断该订阅 | `constants.rs:26,32-33`、`api/ws_helpers.rs:219-232,511-517` |
| 错误包络 | HTTP 错误响应带 `x-error-code` 头（`ERROR_CODE_HEADER`），经 `error_response_with_detail` 输出 | `api/errors.rs:10,132` |
| 监控记录 | monitor 记录携带 `trace_id`（缺失时 `build_monitor_trace_id` 补齐），时间线可按其串联 | `ops/monitor.rs:183,384-390,2464-2469` |
| `runtime_metrics` | blocking / queues / long_tasks / loop_ticks 指标族 + alerts + thresholds | `core/runtime_metrics.rs` |
| 渠道运行日志 | 内存环形 **300 条** + **20s** 洪泛去重窗；用户面 `/wunder/channels/runtime_logs[/probe]`，管理面 `/wunder/admin/channels/runtime_logs[/probe]` | `channels/service.rs:78-79,211-214` |

WS 事件名无集中枚举、散在发送处，与本章相关的有：`tool_call` / `tool_result` / `thread_item_tail` / `thread_item_delta` / `thread_view_change` / `slow_client` / `stream_overflow` / `resume_recommended`。

## 6. 判据表：症状 → 通道 → 位置

| 症状 | 属于哪条通道 | 该看的位置 |
| --- | --- | --- |
| 工具输出在前端只显示几行 / 带 `…` | 展示 | `services/tool_result_display.rs`（2400 字符/16 行）；轨迹行摘要 256 字符（`thread_view_projection.rs:93`）。全文按 body 块取回（`thread_body_chunks`，8192B/块） |
| 模型说「没看到文件内容」 | 模型输入 | 该条 `tool_result` 事件的 `model_observation` 字段（`execute.rs:1446`）；若被 `finalize_tool_result` 裁到 10000+10000 字符，模型确实只有头尾；业务失败翻转看 `result_normalizer.rs` |
| 长会话后模型「忘记」早期工具结果 | 模型输入 | microcompaction 把旧观测缩成 768B 预览（`microcompaction.rs:8`），或触发摘要压缩（`compaction_policy.rs` 三触发）。替换历史看 hidden marker 行的 `replacement_history`，原始行并未删除 |
| 刷新后条目丢失 / 顺序错乱 | 观测面 | 投影未就绪 ≠ 数据缺失：先确认 durable 侧 `thread_items` 有行（`ThreadLogCommitter` 是唯一写出口），再看 feeder 页消费（200/页）与补水游标 `change_seq`/`view_seq` 是否落后（`services/thread_change_feeder.rs`、第 4 章） |
| 客户端频繁断开 | 观测面 | `slow_client` / `stream_overflow` 事件与队列水位 2（`api/ws_helpers.rs`）；这是背压保护，不是服务故障 |

## 7. 常见误判清单

| 误判 | 事实 |
| --- | --- |
| 前端只显示 16 行 = 数据被截断丢了 | 展示预览（2400/16）与写时投影（2048/256/96）只影响客户端，正文按块完整可取 |
| 模型上下文里旧工具结果变成短预览 = 历史被删 | microcompaction 只替换模型输入派生，原始行 append-only 保留，替换记录在 hidden marker 的 `replacement_history` |
| WS 报 `slow_client`/`stream_overflow` 后断开 = 服务挂了 | 队列 256、水位 2 的有界背压按设计先告警再断订阅，重连带游标 resume 即可恢复 |
| 聊天列表某条目暂时缺失 = 后端丢数据 | 条目来自写时投影，投影滞后或补水未追平时 durable 表里已有行；先查 `thread_items` 再查视图表 |
| 工具「成功返回但模型当失败处理」 = 模型幻觉 | `result_normalizer.rs` 做业务失败识别，传输 ok 不等于业务 ok，模型收到的是翻转后的失败语义 |
| 监控时间线与模型输入内容不一致 | 二者本就不是同一份数据：监控走事件负载与 `trace_id`，模型走 `model_observation` 压缩后的观测 |
