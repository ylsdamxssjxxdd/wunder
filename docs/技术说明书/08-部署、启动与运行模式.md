# 部署、启动与运行模式

## 1. 三种运行形态

| 形态 | 入口 | 说明 |
| --- | --- | --- |
| Server | `wunder-server` | 组织级核心，多租户、多用户、多渠道 |
| Desktop | `wunder-desktop` + bridge | 个人用户主推，本地即用 |
| CLI | `wunder-cli` | 脚本化、批处理、自动化 |

另有 `sandbox` 模式：`WUNDER_SERVER_MODE=sandbox`。

## 2. 入口文件

| 形态 | 入口 |
| --- | --- |
| Server | `crates/wunder-server/src/main.rs` |
| CLI | `crates/wunder-cli/main.rs` |
| Desktop | `crates/wunder-desktop/main.rs` |
| Desktop Bridge | `crates/wunder-desktop/bridge_main.rs` |

所有形态共用 `wunder-runtime` crate，通过独立入口 crate 和 `AppRuntimeProfile` 区分。

## 3. 配置路径

| 配置 | 路径 |
| --- | --- |
| 默认配置 | `config/wunder.yaml` |
| 示例配置 | `config/wunder-example.yaml` |
| MCP 配置 | `config/mcp_config.json` |
| 自定义路径 | `WUNDER_CONFIG_PATH` 环境变量覆盖 |

## 4. Server 启动

```bash
# 编译并运行
cargo run --release -p wunder-server --bin wunder-server

# 覆盖地址和模式
WUNDER_HOST=0.0.0.0 WUNDER_PORT=18000 WUNDER_SERVER_MODE=api \
  cargo run --release -p wunder-server --bin wunder-server
```

默认 HTTP 端口以 `config/wunder.yaml` 为准，默认样例 `18000`。

## 5. 前端开发

```bash
# 用户侧前端开发
npm run dev --workspace wunder-frontend
# 默认端口 18001，代理 http://127.0.0.1:18000

# 生产构建
npm run build --workspace wunder-frontend
```

## 6. CLI 启动

```bash
cargo run --release -p wunder-cli --bin wunder-cli
```

CLI 启动时自动：
- 解析 repo root
- 生成本地运行配置副本
- 设置 `WUNDER_HOME`、`WUNDER_USER_TOOLS_ROOT` 等变量
- 将 `config.server.mode` 调整为 `cli`

## 7. Desktop 启动

```bash
# 开发运行
cargo run --release -p wunder-desktop --features desktop --bin wunder-desktop

# Bridge 单独运行
cargo run --release -p wunder-desktop --bin wunder-desktop-bridge
```

Desktop 启动时自动生成运行配置，模式设置为 `desktop`。

桌面 GUI 使用两阶段启动：先显示轻量启动页，首帧后至少留出 10ms，再初始化本地服务。Electron 以 `ready-to-show` 为首帧门槛，`desktop/electron/src/startupFrame.js` 负责计时、关闭取消和 15 秒无首帧超时；窗口显示不再等待 bridge。更新模块只在用户检查更新时加载。原 `WUNDER_LOADING_SHELL_DELAY_MS` 诊断开关已移除，启动页始终立即加载。

Tauri 先加载内嵌 `startup.html`，页面收到 first-contentful-paint 后等待至少 10ms（不支持 Paint Timing 时回退到两次 animation frame），再调用本地 `desktop_startup_ready`；`startup.rs` 在 Tauri 异步运行时中初始化同一 DesktopBridge，完成后导航到本地服务。失败可重试，重复调用不创建第二个运行时；`--bridge-only` 无 GUI，因此保持原启动方式。

前端入口 `frontend/src/bootstrap.ts` 无应用静态依赖：桌面启动页收到 first-contentful-paint 并再等待至少 10ms 后，才动态导入 `main.ts`（Vue、路由、组件库和业务样式）。入口资源加载失败显示重载按钮。隐藏页面等到恢复绘制后继续，不用超时抢跑。窗口创建、图形兼容配置和必要的权限守卫仍是首帧必需工作；10ms 是首帧后的最小延后间隔，不是进程启动时间承诺。

使用 `desktop/electron/scripts/benchmark-startup.ps1 -Runs 3 -WarmupRuns 1` 采样，分别观察 `window_ready_to_show_ms`、`post_first_frame_ms`、`frontend_post_first_frame_ms` 和 `messenger_conversation_ready_ms`。计时从主进程模块加载前开始；缺失阶段保留 null。窗口首帧和会话可用是两个指标，不以启动页显示推断会话已经可用。

## 8. 构建与分发

```bash
# 前端构建
npm run build --workspace wunder-frontend

# 桌面资源准备
npm run prepare:desktop:resources

# Electron 打包
npm run build --workspace wunder-desktop-electron

# Linux 桌面打包
npm run build:desktop:linux:x64
```

## 9. 启动前检查清单

- 配置文件路径正确
- 数据库可用（server: PostgreSQL；desktop/CLI: SQLite）
- `workspace.root`、浏览器数据目录、导出目录可写
- LLM 配置可达（endpoint + API key）
- MCP 配置文件中 endpoint 与鉴权配置正确
- 前端 dev 代理目标与服务端地址一致
