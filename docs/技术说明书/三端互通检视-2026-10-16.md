# 三端互通可用性检视（2026-10-16）

> 本文是 2026-10-16 重构前的历史基线，保留原始问题证据。当前实现与验收结果见：[三端互通重构与验收](三端互通重构与验收-2026-10-16.md)。

## 结论与范围（历史基线）

蛹作为本地 AI 工作台，可以登录舰体并使用部分云端能力；当前还不能把“登录成功”理解为“跨端工作区与智能体线程均可稳定操作”。本次结论是：**底层互通基础已存在，用户要求的完整互通尚未达到可用、好用的验收标准。**

检视对象为舰桥 `web/`、蜂巢 `frontend/src/`、蛹 `frontend-slint/` 与 `crates/wunder-desktop/`、舵机 `crates/wunder-cli/`，以及共享的 `wunder-runtime` / `wunder-core`。未把停止维护的 Electron/Tauri 壳作为蛹的能力依据。

这是重构前检视报告；下文“已复现”指当时的隔离路由测试、真实回环隧道或前端函数复现。行号可能随后续开发漂移。

| 用户期待 | 当前能力 | 判断 |
| --- | --- | --- |
| 舰桥查看蜂巢、蛹、舵机在线情况 | 用户表有三个在线列，浏览器连接和本地隧道接入 presence | 基础监控存在；在线不等于登录凭证有效，也不等于设备可操作 |
| 舰桥统一下线、撤销设备 | 有账号强制下线和设备撤销接口 | 存在撤销范围缺口，尚不能作为完整管理保证 |
| 蜂巢看到本地设备工作区 | 有节点目录、影子投影与侧栏工作区行 | 默认共享级别、能力判定、结果解析均有阻断 |
| 蜂巢读写本地文件 | 有目录/预览接线，后端有写操作与审批机制 | 当前界面强制只读；读取链路也有缺陷 |
| 蜂巢操作本地智能体线程 | 后端支持线程查询、消息、取消、审批与远程事件中继 | 当前蜂巢未形成用户操作闭环 |
| 蛹操作云端工作区 | 强类型 façade 已有列目录、拉取、写入、重命名、删除等 | 部分接入；界面错误依赖反向隧道在线 |
| 蛹控制云端智能体线程 | 本地线程和云模型可用 | 未发现云端线程的列出、选择、发送、旁观、取消完整接线 |
| 舵机控制云端线程 | 有 `cloud threads`、`thread show`、`send --attach`、`watch`、`approve` | 完成度最高，但会话续期、审批提示、控制命令仍有缺口 |

## 优先问题

优先级中，P1 表示直接破坏管理边界、连接稳定性或主要使用路径；P2 表示操作闭环与说明尚不完整。各问题不能仅通过修改界面文案解决。

### F01 · P1 · 舰桥强制下线未覆盖蛹和舵机（已复现）

`crates/wunder-runtime/src/api/admin/identity_admin.rs:1112` 只处理 `user_web` 和 `default`，返回的 `session_scopes` 也仅包含二者。随后 `presence.force_user_offline` 清空在线展示，但 `local_desktop` / `local_cli` 的访问凭证仍有效。

隔离测试调用管理员下线接口后，再用原凭证访问 `/wunder/auth/me`：蜂巢返回 401，蛹和舵机均返回 200。因此界面显示离线不能证明已切断访问。舰桥按钮及确认提示见 `web/modules/user-accounts.js:593`。

建议从服务端统一定义“账号全部下线”与“指定设备下线”：覆盖访问令牌、刷新令牌族、已有隧道和订阅，并在完成后更新 presence。仅添加两个 scope 或清空在线标记不足以完成治理。

### F02 · P1 · 撤销设备未阻断该凭证的云端互通请求（已复现）

`crates/wunder-runtime/src/api/cloud.rs:1527` 撤销设备后，会关隧道、关闭观察者、清影子并终结针对设备的命令；这部分已存在。但 `api/interlink.rs:809` 仅通过 `resolve_user` 校验账号，`to: cloud` 分支没有验证来源设备是否撤销。`api/user_context.rs:18` 也不承担设备校验。

隔离测试用同一个本地凭证验证：撤销后 `/wunder/cloud/account` 携设备头返回 401 `DEVICE_REVOKED`；随后向 `/wunder/interlink/commands` 提交 `to: cloud`、`kind: node.summary` 仍返回 200。实际本地互通调用也未统一携带设备身份，见 `services/cloud/service.rs:1126` 和 `crates/wunder-cli/cloud_interlink.rs:135`。

这证明撤销边界不一致；该测试未穷举所有写命令。建议将本地会话与来源设备在服务端绑定，统一覆盖 HTTP、WS 与续期鉴权，避免依赖可省略或可自行填写的来源字段。

### F03 · P1 · 蛹与舵机共享登录文件也共享设备身份（代码确认，附回环实验）

`services/cloud/session.rs:243` 的 `path_for(base_dir, _client)` 忽略客户端类型。共享文件同时保存令牌、scope、`device_id`、`client` 与节点密钥。隧道从共享 CloudService 读取该文件，节点类型取自文件中的 `session.client`，见 `services/interlink/client/mod.rs:440`、`:596`。

服务端 `services/interlink/mod.rs:134` 用 `device_id` 作为唯一活动通道键；`api/interlink_ws.rs:461` 明确让新通道替换旧通道。旧客户端收到 superseded 后仍重试，见 `client/handshake.rs:162`。当蛹、舵机在同一共享目录下同时常驻时，存在争用同一通道、客户端分类沿用最后登录者的问题。

回环实验将两个客户端的 watchdog 延长至 180 秒，排除 F05 的固定超时干扰后，共用设备会话的两个真实客户端仍在 10 秒内连续出现三条不同通道。该实验是同进程模拟，未做两个独立可执行程序的界面验收。建议保留共享账号登录体验，同时分离账号凭证、物理设备身份、运行形态和进程连接身份，明确同一设备多形态的接入与命令路由规则。

### F04 · P1 · 同账号另一台同类设备登录会使原登录失效（已复现）

`services/user_store.rs:776` 的 `login_local_with_refresh_token` 在新登录时按“用户 + scope”撤销此前全部刷新令牌族（`:793`），没有设备维度。

隔离测试连续执行两次 `local_desktop` 登录：第二次有效，第一次访问令牌失效、刷新令牌被撤销。这是当前明确实现的单 scope 替换策略，与“同账号多台本地设备持续互通”不匹配。已有隧道的生命周期又未在此处同步终止，可能出现设备仍在线而访问凭证已失效的状态。

建议将令牌族绑定到具体设备会话；如产品选择限制同类设备同时登录，应提供明确限制、替换提示及完整断开行为。

### F05 · P1 · 正常心跳不能延长客户端存活期限（已复现）

`services/interlink/client/mod.rs:1170` 建立三倍心跳周期的 watchdog，接收帧的循环没有重置计时器；到 `:1220` 无条件以 Timeout 结束。服务端仍在正常发送心跳，见 `api/interlink_ws.rs:546`。客户端还使用本地配置计算超时，没有以服务端协商值作为统一依据。

将服务端和客户端心跳周期设为 1 秒后，真实回环隧道在 7 秒观察窗内出现两条不同通道，证明健康连接发生重连。默认配置 `config/wunder.yaml:875` 为 25 秒，当前逻辑对应约 75 秒后主动断开。断线还会清理审批和活动执行，因此影响不止是状态闪烁。

建议使用最后一次有效接收时间驱动可重置的存活期限，统一协商心跳，并区分连接代次。现有忽略执行的 idle 测试默认只观察 60 秒，见 `tests/interlink_loopback.rs:1599`，不足以覆盖默认 75 秒问题。

### F06 · P1 · 默认新设备不会形成蜂巢工作区入口（代码确认、前端函数复现）

`crates/wunder-core/src/interlink.rs:75` 默认能力为 `shadow:minimal`、`query.basic`、`thread.drive`。`services/interlink/client/shadow.rs:837` 在 minimal 模式仅返回 summary，不包含工作区元数据；`api/interlink.rs:352` 的工作区目录依赖影子。蜂巢 `interlinkNodeModel.ts:102` 仅为具有实际 workspace_id 的节点生成工作区行，因此默认节点产生零行。

后端存在授予 full 投影的策略能力，但当前舰桥未发现对应业务管理入口。已有回环测试主动授予 `shadow:full`，不能据此判定默认首次登录流程可用。

建议提供清楚的本地共享授权与舰桥管理入口，并将“设备已登录”“设备在线”“尚未共享工作区”分别展示。不能通过默默提高默认授权或自动上传全部目录来消除空列表。

### F07 · P1 · 蜂巢不认识服务端的能力分组（已复现）

`frontend/src/views/messenger/interlink/interlinkNodeModel.ts:129` 只识别精确命令名、星号和命名空间。服务端实际用 `query.basic` 授权目录/文件/线程查询，用 `thread.drive` 授权线程控制，映射见 `crates/wunder-core/src/interlink.rs:227`。

执行实际前端判定函数，传入在线且具有这些服务端能力的节点后，`workspace.list`、`workspace.read`、`threads.list`、`thread.message` 全部被判定为缺少能力；文件面板通过该结果阻止预览。

建议由核心契约生成或统一提供“能力到命令”的映射，界面禁用判断与服务端授权规则保持同源。

### F08 · P1 · 蜂巢将成功目录结果解析为空（已复现）

`services/interlink/commands.rs:998` 保存的设备结果为 `{status, result: {entries, total}, ...}`，接口又把它放入 `data.result`。`frontend/src/api/interlink.ts` 的 `fetchInterlinkCommand` 原样传出此 result；`interlinkCommandRunner.ts:312` 却直接读取 `outcome.result.entries`。云端执行经 `api/interlink_cloud_exec.rs` 和 `commands::finish_local` 还存在额外包装差异。

隔离前端测试使用实际 `listRemoteDirectory`、模拟符合设备返回结构的一条文件记录，结果为 `{entries: [], total: 0, failure: ''}`。用户看到空目录且没有错误。

建议在源头固定命令结果 DTO，统一设备执行和云端执行的输出层级，由各客户端共享类型及契约用例。避免各界面自行猜测多层 result。文件内容的 blob 兜底在后端已有实现，本结论不等于所有文件传输均未实现。

### F09 · P1 · 蜂巢文件预览丢失所选工作区（代码确认）

`frontend/src/views/messenger/workspace/WorkspaceFilesPanel.vue:356` 列目录时传入 `workspaceId`，但 `:1209` 调用 `readRemoteFile` 时仅传目标、路径和 signal，遗漏工作区。命令函数本身支持该参数，后端 `services/interlink/client/execute.rs:504` 在缺少参数时回到默认工作区。

因此命名工作区中列出的文件，预览时可能读不到，或读到默认工作区同名相对路径的另一份文件。建议将设备与工作区作为不可拆分的目标上下文贯穿查询、预览与写操作，增加两个工作区存在同名文件的契约验收。

## 操作体验与未完成闭环

### F10 · P2 · 蜂巢本地目标当前为只读，未接通本地线程控制

`WorkspaceFilesPanel.vue:51` 明确使用 `:read-only="remoteInterlinkActive"`，远端预览也设为不可编辑，上传、保存、删除等路径均有保护分支。因此“蜂巢进行操作”目前不能按完整文件管理理解。

后端已有 `thread.message`、取消、审批及 `/wunder/interlink/remote_ws`，但在当前蜂巢生产调用中未发现相应线程操作及事件订阅接入。`frontend/src/views/messenger/sections/MessengerSidebar.vue:350` 的设备行只改变文件目标，打开线程又切回云端上下文。

应先明确首批支持的远端操作，再沿已有后端命令、审批与审计链路接入，覆盖执行中、等待审批、失败、取消、离线的可见反馈。

### F11 · P2 · 蛹有云端文件操作，缺少云端线程控制入口

`crates/wunder-desktop/native_interlink.rs:217` 起的 façade 覆盖云端工作区读写操作；`frontend-slint/src/native_interlink.rs` 接入了状态轮询、文件面板刷新和本地审批。未发现云端线程列出、选择、发送、观察、取消所需的完整 façade 与页面接线。`frontend-slint/src/native_chat.rs` 当前仍以本地线程执行为主。

选择云模型表示本地智能体使用舰体提供的模型能力，不能作为“正在控制舰体上的智能体线程”的证据；本地线程来源徽标也不代表云端线程界面已经完成。后续应先建立具有云端线程身份的强类型 Rust façade，再以线程隔离、增量事件与恢复机制接入 Slint。

另有一个独立阻断：`frontend-slint/src/workspace_files.rs:837` 以本地反向隧道的 connected 状态决定云端文件面板能否加载。但云端目录/命令通过 CloudService 的 HTTP 请求执行，不需要本地被远程控制的反向隧道。关闭本地入站互通不应使已登录账号失去主动访问云端文件的能力。

### F12 · P2 · 舵机已有云端线程主路径，续期与审批体验仍不完整

`crates/wunder-cli/args.rs:290` 起提供 devices、ws、threads、thread show、send、watch、audit、approve。`cloud_interlink.rs:1317` 的 send 可投递到既有或新云端线程，并通过 attach 回显输出。该端的主路径接线比蛹完整。

仍有以下缺口（代码确认）：

- `cloud_interlink.rs:135`、`:167` 的 HTTP helper 和事件订阅直接使用取得的 session.token，没有复用 CloudService 的鉴权重试/续期请求机制。长时间旁观或轮询跨越凭证轮换时可能失败，本次未做续期端到端复现。
- `:273` 的 `print_command_outcome` 先判断 issued/queued/running，再判断 pending 审批；服务器等待审批仍可为 issued，导致应显示的审批指引被“仍在执行”遮盖。`:2657` 的 approve 只报告审批状态，不接续原 send 的输出。
- 命令定义中没有线程 cancel、answer、云端智能体选择等完整控制入口。不能把对默认云端线程发消息扩大描述为全部云端智能体管理。
- 本地隧道在常驻 TUI 生命周期启动，见 `tui/mod.rs:65`；一次性 `cloud login` 退出后，不会留下舵机后台进程。登录成功、账号凭证有效和本地设备持续在线需要明确区分。

### F13 · P2 · 使用说明超前于实际接线

`docs/使用说明书/zh-CN/capabilities/interlink.md` 把蜂巢线程控制、写操作及蛹云端线程描述为完整能力，并列出蛹设置页“设备互通”入口。当前 `frontend-slint/src/native_interlink.rs:1` 已明确该设置页移除，文件能力迁至工作目录面板。

应在实际修复验收后按形态重新校准说明，展示清楚“当前可操作项、需要授权项、尚未开放项”，不能用设计目标或后端接口列表代替用户可用性。

## 建议修复顺序与验收

1. **先统一账号与设备生命周期**：处理 F01–F04。鉴权应绑定来源设备，账号全部下线、单设备下线、注销、撤销、刷新轮换形成一致边界；同账号多设备、多形态不互相误伤。
2. **修复连接存活与恢复**：处理 F05，并验证新旧连接代次隔离。状态切换不能清掉仍有效的授权或错误路由新命令。
3. **固定互通契约与工作区上下文**：处理 F06–F09。能力映射、结果 DTO、目标工作区在核心/服务端定义；共享授权需要用户能理解和管理。
4. **完成用户操作闭环**：处理 F10–F12。优先保证可选定目标线程、发消息、实时查看、取消及审批恢复，再补其他管理能力；最后同步说明文档 F13。

建议以以下场景作为“可用、好用”的验收门槛：

| 场景 | 期望 |
| --- | --- |
