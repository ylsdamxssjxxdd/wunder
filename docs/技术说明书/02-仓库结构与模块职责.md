# 仓库结构与模块职责

这页回答「东西在哪、改动该落哪一层」。先按顶层目录定位 crate 或前端，再按模块表定位文件；「常见改动落点」表和「改代码前的判断顺序」放在最后，改之前先看那两节。

## 1. 顶层目录

```
wunder/
├── Cargo.toml            纯 workspace manifest；default-members = crates/wunder-server
├── crates/               五个 Rust crate：core、runtime、server、desktop、cli
├── frontend/             蜂巢（Vue 3 + TypeScript）；dist 由 nginx 容器对外提供，不由舰体托管
├── frontend-slint/       蜂窝默认前端（Rust + Slint）：ui/ 界面、src/ 接入与投影、vendor/ 本地补丁
├── web/                  舰桥（原生 HTML + JS 模块，无构建步骤），随舰体挂载在 /
├── builders/             构建、交叉编译与打包统一入口（Win7 / Ubuntu 18.04 离线链）
├── packaging/            分发附加资源：Dockerfile.*、win7/linux 补充包、python requirements
├── config/               运行配置与内置资源（prompts、skills、fonts、ppt_templates、data 等）
├── extra_mcp/            独立 Python FastMCP 服务（/mcp，配置 config/mcp_config.json）
├── scripts/              仓库脚本（功能迭代记录、文档站点、基准、诊断、修复工具）
├── tests/                非 Rust 测试夹具与脚本；Rust 集成测试在 crates/wunder-runtime/tests/
├── docs/                 设计文档、技术说明书、使用说明书、API 文档、方案、性能基线
├── patches/              依赖与兼容性补丁资源
├── images/               共享图片资源
├── Dockerfile            rust:1.92-slim 构建/开发镜像（CMD 为 bash，不是运行镜像）
├── docker-compose-x86.yml / docker-compose-arm.yml   整套服务编排
└── build.bat / build.sh  构建入口，转发到 builders/
```

`frontend-slint/target/`、`target/`、`node_modules*`、`temp_dir/`、`.temp/` 是产物或工作目录，不是代码事实来源。

## 2. 五个 crate

| crate | 产物 | 职责 | 不该放 |
| --- | --- | --- | --- |
| `wunder-core` | 仅 lib | 跨形态低依赖基础能力：`config`、`auth`、`approval`、`exec_policy`、`path_utils`、`storage_backend`（存储契约 trait）、`storage_records`（记录类型）、`storage_constants`、`thread_view`（展示读模型契约）、`i18n`、`schemas`、`tool_args`、`interlink`、`virtual_model`、`request_limits` | 执行链路、外部协议、任何依赖 tokio/axum 的东西 |
| `wunder-runtime` | lib（**lib 名 `wunder_server`**，`crates/wunder-runtime/Cargo.toml:7-9`）+ 可选 bin `backend_sim`（需 `sim-bins`） | 引擎：接入路由、编排执行、线程运行时、工具、渠道、网关、互通、存储实现、观测 | 只属于某个形态的展示逻辑 |
| `wunder-server` | bin `wunder-server` | **只有 `src/main.rs`**：feature 转发组装、运行时线程调优、日志初始化、路由与静态资源挂载、中间件层接线、优雅停机 | 业务逻辑（全在引擎）、路由实现（`runtime/src/api`） |
| `wunder-desktop` | lib（根 `lib.rs`）+ bin `wunder-desktop-bridge`（`bridge_main.rs`） | 本地运行时与强类型 Rust façade：`DesktopRuntime`、`NativeDesktop`、`native_*`；bridge 仅为既有兼容客户端保留 | 只服务于 Slint 展示的取数逻辑（放 `frontend-slint/`） |
| `wunder-cli` | bin `wunder-cli`（根 `main.rs`，**无 lib.rs**） | 舵机：参数解析、TUI、一次性 exec、slash 命令、本地 doctor/stress | 另起一套执行链路（复用引擎 `AppState` 与 orchestrator） |

引用规则：外部 crate 通过 `wunder_server::` 使用引擎（例如 `crates/wunder-desktop/native.rs`、`crates/wunder-cli/main.rs`），不是 `wunder_runtime::`。看到 `wunder_server::` 不要当成旧名残留。

## 7. `storage/`

```
crates/wunder-runtime/src/storage/
├── mod.rs              模块声明与特性门控
├── backend.rs          仅 re-export wunder_core::storage_backend（契约在核心）
├── factory.rs:8-17     选型：配置为空 → sqlite；postgres|postgresql|pg|auto → PostgreSQL
│                       未启用对应 feature 时返回明确错误（:21-45）
├── records.rs          记录类型 re-export
├── constants.rs        tool_logs 列预算（头尾各 2000 字符）等落库截断常量
├── thread_view_store.rs     投影表读写（heads/chat_rows/trajectory_rows/body_*/tiles）
├── thread_view_projection.rs 写时投影与预览截断
├── thread_view_source.rs      投影未就绪时的有界窗口读
├── session_cleanup/    空会话清扫 SQL
├── sqlite/  └── postgres/   同名分域 store 文件两侧成对出现 + schema.rs + backend_impl.rs
```

要点：

- **没有 schema 版本表、没有迁移脚本目录**。`schema.rs` 用幂等 `CREATE TABLE IF NOT EXISTS`，加列走列探测式 `ensure_*` ALTER。新增列就写 `ensure_*`，不要造版本号迁移。
- 聊天真相表：`thread_turns` / `thread_items` / `tool_logs` / `thread_log_changes`（`storage/sqlite/schema.rs:607/626/652/694`）。
- 每个分域 store 在 SQLite 与 PostgreSQL 两侧**同名成对**，加方法必须两边都实现。

## 9. 本地形态 crate 结构

`crates/wunder-desktop/`（扁平，无 `src/`）：`lib.rs`（导出面 `:6-24`）、`args.rs`、`native.rs`（`NativeDesktop::start` → `native_defaults()`，同进程，不起本机 HTTP）、`runtime.rs`、`bridge.rs` + `bridge_main.rs`（仅兼容客户端），其余 `native_*.rs` 是按页面划分的强类型 façade。Slint 侧只认 `None | --native → native_runtime::install`（`frontend-slint/src/main.rs:123`），其它 bridge 参数直接报错。

`crates/wunder-cli/`（扁平，无 `src/`）：`main.rs`（TTY 判定 → TUI 或一次性 exec）、`args.rs`（子命令 exec/resume/tool/mcp/skills/config/stress-thread/doctor/cloud/completion）、`runtime.rs`（`CliRuntime.state: Arc<AppState>`，直连引擎）、`slash_command.rs`、`tui/`（ratatui + crossterm，Inline 视口）。数据目录 `WUNDER_HOME` → `~/.wunder`。

| 新增存储方法 | 契约在 `wunder-core/src/storage_backend.rs`，实现在 `storage/sqlite/<域>_store.rs` **和** `storage/postgres/<域>_store.rs`，DDL 走幂等 + `ensure_*` | 只实现一侧；新建版本化迁移脚本 |
| 新增实时事件 | `orchestrator/event_stream.rs` 发射（内部同步 commit）+ `services/thread_change_feeder.rs` 读侧 + `api/*_ws.rs` 接线 | 在单个 WS 路由里私造状态机；绕过 `thread_log_committer.rs` 写库 |
| 新增渠道 | `channels/<name>.rs` 实现 `ChannelAdapter` + `registry.rs` 注册 + `config/wunder.yaml` 配置 | 在 `api/channel.rs` 里写收发细节 |
| 新增展示字段（蜂巢/蜂窝列表） | `wunder-core/src/thread_view.rs` 契约 + `storage/thread_view_projection.rs` 写时投影 + 前端消费 | 在接口里现算全量历史、把执行快照当分页契约 |
| 新增舰桥能力 | `web/modules/*` | 在 `web/app.js` 写耦合逻辑 |
| 新增蜂窝能力 | `crates/wunder-desktop/native_*.rs` 强类型 façade + `frontend-slint/` | 独立 WebView 前端壳、Electron/Tauri |
| 新增舵机/TUI 能力 | `crates/wunder-cli/*` | 另起一套执行链路或存储 |

## 11. 改代码前的判断顺序

1. 这是接入层、运行时、投影、业务服务还是基础设施问题？先按 §3 定层。
2. 这段逻辑是核心执行语义（进 `orchestrator`）还是领域服务（进 `services`）还是跨形态类型（进 `wunder-core`）？
3. 我操作的是 durable 状态（必须走 `thread_log_committer.rs`）、展示读模型（必须走 `thread_view`）、执行快照（`runtime_snapshot` / `chat_runtime_projection`）还是进程内临时状态？三者不能互相替代。
4. 涉及列表/日志/面板：有没有分页、有没有上限、有没有全量重算？见 §5 与 09 章性能红线。
5. 需要同步哪几层文档：`docs/API文档.md`、`docs/设计文档/`、本说明书、`docs/功能迭代.md`？
