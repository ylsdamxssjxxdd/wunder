# 数据存储、工作区与配置

## 1. 四类数据

| 类型 | 特征 | 举例 |
| --- | --- | --- |
| 数据库存储 | Durable，跨进程持久 | 用户、agent、hive、session、stream events |
| 文件现实 | 智能体真实读写的文件和目录 | 工作区、下载、导出、浏览器数据 |
| 配置文件 | 启动时加载，运行时只读为主 | `config/wunder.yaml` |
| 进程内状态 | 可丢失、可重建 | watch、presence、热缓存、临时目录 |

## 2. 数据库

| 运行形态 | 后端 |
| --- | --- |
| `wunder-server` | PostgreSQL |
| `wunder-desktop` | SQLite |
| `wunder-cli` | 本地 SQLite |

统一抽象位于 `crates/wunder-runtime/src/storage/`。具体实现在 `crates/wunder-runtime/src/storage/postgres.rs` 和 `crates/wunder-runtime/src/storage/sqlite.rs`（ThreadLog 存储分别落在 `postgres/thread_log_store.rs` 与 `sqlite/thread_log_store.rs`）。

### 关键 durable 对象

- 用户、组织、权限、令牌、额度账户
- agent 预设、agent 配置、工具授权
- team run、team task
- 会话、ThreadLog 持久条目（Turn / Item / 内容块）、stream_events
- 记忆记录、知识元信息
- channel / gateway 绑定
- 工具日志、附件日志

`thread_log_changes`（durable change 游标与帧）是聊天会话断线恢复的唯一真相，默认永久保留；`chat_history` 表已在 ThreadLog 收口后整体 DROP，不再存在；`stream_events` 按 `observability.stream_event_retention_hours`（默认 168 小时，0 表示禁用）由每小时保留期清扫任务删除过期事件，轮次成功完成后还会折叠删除该 `(session_id, user_round)` 的 `llm_output_delta` 类事件；`monitor_sessions`、`tool_logs`、`artifact_logs` 仍默认永久保留，删除由管理员调用日志清理接口并提供明确时间范围完成。用户删除会话先写 `deleted_session_log_grace` 墓碑，`observability.deleted_session_log_grace_hours`（默认 24 小时，<=0 表示立即清理）到期后由清扫任务物理删除其日志；管理端删除会话仍立即物删。SQLite 打开时启用 `auto_vacuum=INCREMENTAL`（既有库启动一次性 VACUUM），清理删除行后执行 `incremental_vacuum` + `wal_checkpoint(TRUNCATE)` 回收空间。服务端文件日志同样默认不自动清理，管理员应根据磁盘容量制定维护计划。

## 3. 工作区

工作区是智能体读写真实文件的现实层，不是附件桶。

能力包括：文件读写、附件存储与转换、导出路径、目录路由与 fence、与工具/浏览器/桌面系统联动。

**禁止**：
- 把长期业务文件写进 `data/` 或 `temp_dir/`
- 把 `temp_dir/` 当长期业务目录

## 4. 记忆与知识

| 子系统 | 说明 |
| --- | --- |
| 长期记忆 | 跨线程的用户/agent 记忆，通过 `memory.rs` + `memory_fragments.rs` 管理 |
| 知识库 | 文档解析、切分、缓存和检索（`knowledge.rs`） |
| 向量知识 | 向量化检索的补充能力（`vector_knowledge.rs`），不是唯一知识入口 |

## 5. 配置文件

默认路径：`config/wunder.yaml`。示例：`config/wunder-example.yaml`。可通过 `WUNDER_CONFIG_PATH` 覆盖。

配置结构定义：`crates/wunder-runtime/src/core/config.rs`。

### 关键配置段

| 配置段 | 作用 |
| --- | --- |
| `security` | API key、执行策略、允许路径与命令 |
| `server` | host、port、mode、流式通道 |
| `llm` | 默认模型、提供方和超时参数 |
| `tools` | 内置工具、web fetch、browser、desktop controller |
| `browser` | 浏览器运行时与 docker/headless 参数 |
| `cron` | 定时任务运行参数 |
| `workspace` | 工作区根目录和历史条数上限 |
| `observability` | 日志级别、监控字段裁剪、stream_events 保留与删会话宽限期 |
| `mcp` | MCP 服务器列表和超时 |
| `storage` | 存储后端设置 |
| `channels` | 渠道配置 |

`observability.monitor_event_limit` 与 `monitor_drop_event_types` 仅为旧配置兼容保留，不再造成线程日志丢失；`monitor_payload_max_chars` 设为 `0` 可保留完整事件内容。`observability.stream_event_retention_hours`（默认 168 小时，0 表示禁用）控制 `stream_events` 自动清理；`observability.deleted_session_log_grace_hours`（默认 24 小时，<=0 表示立即清理）控制用户删除会话后的日志宽限期。debug 模式已移除：外部请求 `debug_payload` 字段保留解析但忽略，`llm_request` 事件恒定 `payload_omitted` 摘要，`tool_logs` 的 payload 列恒为 `{}`、args/data 头尾各截断 2000 字符，监控每会话事件队列上限 500 条。

### 环境变量

| 变量 | 作用 |
| --- | --- |
| `WUNDER_CONFIG_PATH` | 指定配置文件路径 |
| `WUNDER_HOST` | 覆盖绑定主机 |
| `WUNDER_PORT` | 覆盖绑定端口 |
| `WUNDER_SERVER_MODE` | 覆盖运行模式 |
| `WUNDER_HOME` | CLI / 本地运行时 home |
| `WUNDER_USER_TOOLS_ROOT` | 用户工具目录 |

CLI 和 Desktop 会在启动时生成运行时配置副本，设置相应路径变量。

## 6. 配置管理原则

- 以 `config/wunder.yaml` 为主，环境变量覆盖为辅。
- 运行时裁剪在 CLI / Desktop 初始化阶段完成，不在业务逻辑里散落模式判断。
- 变更配置结构后，同步更新示例配置、技术说明书和 API 文档。

## 7. 排查矩阵

| 问题 | 检查 |
| --- | --- |
| 服务端口不对 | `WUNDER_PORT` 与 `config.server.port` |
| 模式异常 | `WUNDER_SERVER_MODE` 与 `config.server.mode` |
| 工作区路径不对 | `workspace.root` 与目录路由规则 |
| MCP 不生效 | `config/mcp_config.json` endpoint、headers、enabled |
| 本地 CLI 配置漂移 | 运行时生成的配置副本 |

## 用户额度账户

普通用户每日统一发放 1000 额度，按服务端本地日期惰性入账，同一天只入账一次，不补发未使用日期。每次实际模型请求前在事务内完成发放和扣 1，重试、工具循环、压缩请求分别准入；准入钩子绑定在 LlmClient 的实际 HTTP 发送入口，参数降级与流式选项回退也逐次扣费，拒绝结果直接返回且不得继续重试；余额不足不发送请求。SQLite 使用 IMMEDIATE 事务，PostgreSQL 使用行锁。资料更新采用窄字段更新，额度修改通过专用存储操作，避免登录或资料保存覆盖并发扣减。

账户字段使用 `quota_*`，真实 Token 统计独立保留。升级迁移事务初始化 1000 额度并移除旧 Token 账户列，不能用零余额判断是否需要迁移。管理员设置余额的值是当天发放结转后的最终余额；普通用户等级与发放数量解耦。
