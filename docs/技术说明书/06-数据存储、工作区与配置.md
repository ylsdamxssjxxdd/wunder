# 数据存储、工作区与配置

存储总体约束见 [数据存储与状态模型设计](../设计文档/08-数据存储与状态模型设计.md)。运行链路见 [运行时与执行链路](./03-运行时与执行链路.md)，实时补水见 [实时投影与通信链路](./04-实时投影与通信链路.md)。

## 1. 数据归属

蛹默认使用本地存储根。canonical rollout 保存执行历史，独立 SQLite 分别承载完成态投影、状态、队列、目标、记忆和诊断。工作区文件与这些历史记录各自拥有生命周期。

| 载体 | 内容 | 能否删除重建 |
| --- | --- | --- |
| `sessions/`、`archived_sessions/` 中的 rollout JSONL | SessionMeta、TurnContext、ResponseItem、完成事件和上下文检查点 | 不能依赖投影还原原件 |
| `thread_history_1.sqlite` | 完成条目、轮次、预览、根轮次计数和投影水位 | 可从 rollout 重建 |
| `state_1.sqlite` | 当前 rollout、用户线程状态和本地业务目录 | 用户修改不能假定可还原 |
| `queue_1.sqlite` | 受理幂等键、用户轮次、待执行输入、队列和租约 | 业务状态，不能直接丢弃 |
| `goals_1.sqlite`、`memories_1.sqlite` | 目标、长期记忆及其任务状态 | 业务状态，独立保留 |
| `logs_1.sqlite` | 有界监控事实、工具计量、诊断和临时事件 | 可清理，不承担用户历史 |
| 附件与工作区 | 真实文件和独立资源 | 按所有权与显式删除策略处理 |
| 进程内状态 | 活动条目、实时 delta、watch、presence 和缓存 | 有界且允许丢失 |

完成条目的 `item_json` 保存完整持久化表示，SQLite 不只是偏移索引。模型上下文和展示条目存在必要语义重复，但不再创建 token block、补丁链和第三套展示正文。

## 2. 契约、配置与实现

### 2.1 线程历史与业务仓库

| 组件 | 位置 | 职责 |
| --- | --- | --- |
| ThreadStore 契约与类型 | `crates/wunder-core/src/thread_store/` | 线程身份、历史位置、生命周期、上下文和有界读取 |
| 持久化 policy | `crates/wunder-core/src/storage_policy/` | 持久化白名单和命令/MCP 输出限制 |
| LocalThreadStore | `storage/thread_store.rs` | 写入协调、恢复、fork/revert/archive/delete 和冷压缩 |
| RolloutRecorder | `storage/rollout.rs` | 有界 writer、逐条完整 JSONL、flush barrier |
| ThreadHistoryStore | `storage/thread_history.rs` | 增量 projector、完成态投影和 keyset 分页 |
| CanonicalThreadLog | `storage/canonical_thread_log.rs` | 现有 API/传输 DTO 的 canonical 查询适配 |
| 独立业务 trait | `wunder-core/src/storage_backend.rs` | 账号、目录、队列、目标、记忆及治理能力 |
| 控制面实现 | `storage/{sqlite,postgres}/` | 两种业务后端；历史均复用 canonical 存储 |

原有 ThreadLogStore 名称保留为应用契约，其实现没有独立 SQL 执行日志。旧 `thread_logs`、`thread_log_changes`、`thread_view_*` 和持久化 body chunks 已退出本链路。

### 2.2 后端与数据根

`storage/factory.rs` 根据 `storage.backend` 选择 SQLite 或 PostgreSQL 控制面，受 Cargo feature 门控。空值选择 SQLite；`postgres|postgresql|pg|auto` 选择 PostgreSQL，feature 缺失时明确报不可用。

数据根通过 `storage.data_root` 解析。新的默认数据库是角色文件，不读入旧单体库；不执行旧历史兼容、自动修复或迁移。独立角色 DAO 懒打开，每个角色拥有自己的连接与 WAL 生命周期，不在常驻连接上永久 ATTACH。

舰体配置 PostgreSQL 时仍需要持久的本地数据根保存 canonical rollout 与投影。PostgreSQL 承担控制面，不能因此在任意节点直接读到其他节点的文件。执行、历史补水和订阅须路由到线程所有者；当前本地 hub 不提供跨节点事件总线。

### 2.3 Schema 与变更

SQLite 干净初始 schema 位于 `storage/sqlite/schema_{state,queue,goals,memories,logs}.sql`，canonical 目录、受理表和历史投影分别由 `thread_store.rs`、`thread_admission.rs`、`thread_history.rs` 定义。文件名中的版本数字区分格式代际，不是从旧单体库执行迁移的游标。

PostgreSQL 控制面使用 schema 指纹判断是否需要初始化；投影水位只表示已消费的 rollout 边界，不能当作业务 schema 版本。后续改字段时先确定它属于不可丢弃状态还是可重建投影，禁止用一套兼容补列机制掩盖两者差异。

### 2.4 受理与写入

用户轮次和 `client_message_id` 幂等约束位于 `thread_admission.rs` 的 queue 仓库。已接受输入在执行前保留正文；首次 canonical 提交确认后回收队列正文，保留幂等与状态事实。

持久化顺序为 policy → 有界 writer → JSONL flush → SQLite 完成态投影提交 → hub 唤醒。JSONL/SQLite 没有跨介质事务，投影可落后但不可领先；失败从完整记录边界明确恢复。未以换行结束的半条记录不投影。

用户与助手文本按原文保留，命令/MCP 展示输出采用专用截断并标记，其他模型上下文按自身策略处理。诊断仅保存有限身份、状态、数值、布尔和有界轮次计数，不复制请求、事件队列、工具参数或完整输出。

## 3. 展示读模型与有界分页

### 3.1 常量

以下常量统一定义于 `crates/wunder-core/src/thread_view.rs`：

| 项 | 值 |
| --- | --- |
| 聊天页默认 / 上限 | 12 / 20 |
| 轨迹页默认 / 上限 | 80 / 100 |
| 聊天 / 轨迹响应预算 | 128 KiB / 192 KiB |
| 正文传输块 | 8192 字节，按 UTF-8 边界切分 |
| 完成历史存储页上限 | 200，定义于 `storage/thread_history.rs` |

### 3.2 投影表

`thread_history_1.sqlite` 包含 `thread_items`、`thread_turns`、`thread_root_counts`、`thread_history_projection_state`。完整完成条目与限量预览共处同一投影；写时计数避免每次打开列表全量重算。

投影从已 flush 的 rollout 字节偏移和 ordinal 继续；每批记录数、字节数和单行大小有界。条目、轮次、计数和水位在同一事务提交，重试不会重复累计。

应用只读适配通过请求级 state/queue 关联查询检查当前 rollout 和所有者。列表读取预览列；展开正文才读取对应完成条目并分页返回。正文块只作传输表达，不永久复制为 body chunks 表。

### 3.3 按需恢复与目录限量

没有后台投影发现或重建计时器。`services/thread_view_rebuild.rs` 仅报告 `mode=on_demand`、`background_enabled=false`。追加、明确恢复和显式重建推进投影，启动不扫描全部 rollout，页面打开不触发全量重放。

线程目录有分页和搜索扫描上限。活动执行状态优先读取运行时内存，再读取 canonical 轮次与 admission；不能通过在线 presence 或显示占位判断线程活性。

### 3.4 三个不同口径

- 执行快照用于调度与状态判断；展示分页用于 UI，两者资源边界独立。
- LLM 上下文压缩影响后续模型输入，不删除用户可见完成历史，也不由 UI 页大小决定。
- transport event id、临时 delta offset 与 canonical 历史位置各有语义；重连只使用已应用的持久历史位置。


## 4. 工作区与路径解析

### 4.1 根与映射

| 项 | 值 | 位置 |
| --- | --- | --- |
| 云端公共根 | `PUBLIC_WORKSPACE_ROOT = "/workspaces"` | `services/workspace.rs:44` |
| 桌面/舵机单根模式 | 环境变量 `WUNDER_WORKSPACE_SINGLE_ROOT` | `services/workspace.rs:45` |
| 容器映射键 | 按 scoped_user_id 解析 | `services/workspace.rs:555` |
| 用户私有容器 id | `USER_PRIVATE_CONTAINER_ID = 0` | `wunder-core/src/storage_constants.rs:1-4` |
| 沙箱容器 id | 1..10 | `wunder-core/src/storage_constants.rs:1-4` |

呈现口径：智能体的云端目录一律呈现为 `/workspaces/<user>/workspace`，**公共路径、主机真实路径、沙箱容器内路径三者同名同义**（2026-10-13 变更）。对外（前端与模型）不描述服务端绝对路径。

### 4.2 边界：隔离由沙盒承担

当前口径（2026-10-13）：

- 云端读、写、执行类工具一律在沙盒内执行。`execute_in_sandbox` 在舰体形态必然接管；**没有沙盒端点就直接失败，不回落宿主**。
- 沙盒侧 `allow_roots = ["/"]`，每用户一个容器、只挂该用户目录。因此**租户隔离由沙盒的挂载边界承担，`/workspaces` 代码分支不再做越界拒绝**。文档不得再写「云端路径校验负责隔离」。
- 舵机与蛹的本地形态仍保留配置化工作区边界：`security.allow_paths` / `deny_globs` 加上 `is_within_root`。
- 路径围栏工具函数：`wunder-core/src/path_utils.rs:47-53` 的 `is_within_root`，做 canonicalize 加 Windows verbatim 前缀与大小写归一；工具层广泛调用，如 `services/tools/file_tool.rs:1436`、`services/tools/edit_tool.rs:203`。
- 执行策略三态 Allow / Audit / Enforce：`wunder-core/src/exec_policy.rs:6-10`；未配置即 Allow（`:21-29`）。

## 5. 配置体系

### 5.1 加载优先级链

`wunder-core/src/config.rs:2478-2518`，按顺序：

1. 取 `WUNDER_CONFIG_PATH` 指定的文件，否则取 `config/wunder.yaml`。
2. YAML 内的 `${ENV}` 占位展开。
3. `apply_env_overrides` **最后生效**：环境变量覆盖已解析值（`WUNDER_STORAGE_BACKEND`、`WUNDER_STORAGE_DATA_ROOT`、`WUNDER_POSTGRES_DSN`、`WUNDER_POSTGRES_POOL_SIZE` 等，`:2552-2566`）。
4. 缺失字段与 `config/wunder-example.yaml` 模板做**稀疏合并**（`:2510-2513`）：只补用户没写的键，不覆盖已写的。

要点：

- **Rust 侧不加载 `.env`**（无 dotenvy 依赖）。`.env` 只被 docker-compose 与脚本层消费；`WUNDER_CONFIG_OVERRIDE_PATH` 没有任何 crate 读取。
- 已知隐患：直接对 `config/wunder-example.yaml` 走 `load_config_from_path` 会解析失败并**静默回落到 `Config::default()`**。模板文件不是可运行配置。
- 舵机与蛹启动时会在临时目录生成一份运行时配置副本（`<temp>/config/wunder.yaml`），再交给引擎加载，所以排查本地形态要区分「用户配置」与「生成的副本」。

### 5.2 读写与热更新

- 持久化：`ConfigStore` 单文件 YAML 回写 + 原子 version 计数（`crates/wunder-runtime/src/core/config_store.rs:60-90`）。
- 管理端在运行中调 `update()` 即热更新（`api/admin.rs:108`、`:490`、`:743`），无需重启；但读取配置的组件必须每次从 store 取，不能在初始化时把值拷死。
- 配置结构定义在 `wunder-core/src/config.rs`，`crates/wunder-runtime/src/core/config.rs` 是 re-export。

### 5.3 线程与运行时调优

`crates/wunder-runtime/src/core/runtime_tuning.rs:7-18` 的 env 上限：worker 128、blocking 512、PG 32、session-run 64/256。超限的值会被夹取。

`wunder-core/src/request_limits.rs:3-16` **只按字符计量输入，不含上限数值**；真正的输入上限是 `MAX_USER_INPUT_TEXT_CHARS = 1<<20`（`orchestrator/constants.rs:40`，校验在 `orchestrator/request.rs:358`），图片附件不计入。别把 `request_limits.rs` 当成限额定义处。

`crates/wunder-runtime/src/core/repo_assets.rs:3-6` 负责定位仓库内资产目录 `config/prompts`、`config/knowledge`、`config/skills`。`core/dpi.rs` 只服务 Windows 桌面，与配置加载无关。

### 5.4 关键开关与后果

| 键 | 默认 | 关掉/设错的后果 |
| --- | --- | --- |
| `agent_queue.enabled` | true（代码与模板一致） | 关掉后运行中再发消息被判「用户忙」且**不进排队条**；舰体启动会告警 |
| `storage.backend` | 空即 sqlite | 填 `pg` 而 feature 未开 → 后端不可用，不是回落 |
| `cron.enabled` | 见配置 | false 时 add/update/enable/run 全部拒绝 |
| `observability.server_log_dir` | `./config/data/logs/server` | 保留期默认 0 = 永不清理，需自行规划磁盘 |
| `observability.stream_event_retention_hours` | 168 | 0 表示禁用清扫，事件表只增不减 |

### 5.5 `config/` 目录内容

`wunder.yaml`、`wunder-example.yaml`、`sandbox-runtime.yaml`、`mcp_config.json(+example)`、`org_units.json(+example)`、`i18n.messages.json`、`app_version.json`、`fonts.conf`、`matplotlibrc`；子目录 `prompts/`、`skills/`、`knowledge/`、`data/`、`fonts/`、`ppt_templates/`、`preset_worker_cards/`、`benchmark/`。`config/org_units.json` 是单位树的启动播种源（`core/state.rs:317`）。

仓库内 `config/wunder.yaml` 与 `.env` 含真实形态的密钥值：**任何文档、示例、日志一律用占位符**，不得复制实际值。

## 6. 知识库、记忆与用户世界

### 6.1 知识库三型

由 `base_type` 归一为 `Literal | Vector | Ragflow`（`wunder-core/src/config.rs:1831-1835`）。

| 型 | 实现 | 磁盘根 / 关键配置 | 默认值 |
| --- | --- | --- | --- |
| Literal | `services/knowledge.rs`：内置词面 + LLM 检索 | — | `DEFAULT_MAX_DOCUMENTS = 5`、候选 80（`:19-20`） |
| Vector | `services/vector_knowledge.rs` | `config/data/vector_knowledge`，env `WUNDER_VECTOR_KNOWLEDGE_ROOT`（`:20`）；表 `vector_documents` / `vector_chunks` | chunk 800 / overlap 100 / top_k 5（`:27-29`） |
| Ragflow | `services/ragflow_knowledge.rs`（外部 HTTP） | `ragflow.base_url` / `api_key` / `timeout_s`（默认 120）（`wunder-core/src/config.rs:1864-1888`）；每库 `ragflow_dataset_id`、`chunk_method`（14 种）/`delimiter`/`top_k`/`score_threshold`（`:1804-1827`） | 超时 120s |

知识库按库动态注册为工具，取代旧的单一 `knowledge` 工具（见 ./05-工具、技能、MCP与外部能力.md）。

### 6.2 记忆分层

- 表：`memory_records`、`memory_fragments`、`memory_embeddings`、`memory_hits`、`memory_jobs`（`storage/sqlite/schema_memories.sql`）。
- 作用域 `user_id + agent_id`，`agent_id` 缺省为 `__default__`（`services/memory.rs:14-15`）。
- 三层内容 L0 标题 / L1 摘要 / L2 正文，加 tier 与 supersedes 链。片段 tier 为 core | working | peripheral，升级阈值 access ≥ 10 或 hit ≥ 4（`services/memory_fragments.rs:24-27`、`:43-44`）；召回默认 6、上限 30、列表 200（`:33-35`）。
- **语义召回当前禁用**（`services/memory_fragments.rs:36`）：`memory_embeddings` 表存在，检索路径不启用向量召回。写文档不得把它算作可用能力。
- 注入约束：长期记忆只在线程初始化时注入一次，落在 system prompt 冻结分支内（`orchestrator/prompt.rs:334`）；已存 prompt 命中复用时不再注入。详见 ./03-运行时与执行链路.md。

### 6.3 用户世界

`user_world` 是站内 IM 域（联系人/会话/群/消息/事件，表 `user_world_*`，`storage/sqlite/schema_state.sql`），API 前缀 `/wunder/user_world/...`（`api/user_world.rs:44-77`）。限额：联系人 100、列表 50、未读页 500 × 20（`services/user_world.rs:14-19`）。它**没有对应工具**——旧的「用户世界工具」已删除，只有服务与 API。

### 6.4 额度

普通用户每日发放固定额度，按服务端本地日期惰性入账、每天只入账一次、不补发；每次实际模型请求前在事务内完成发放与扣减。SQLite 用 IMMEDIATE 事务，PostgreSQL 用行锁。账户字段前缀 `quota_*`，与真实 token 统计分离；资料更新走窄字段更新，避免保存资料覆盖并发扣减。

## 7. 归档、清理与状态重置

| 主题 | 事实 | 位置 |
| --- | --- | --- |
| canonical 归档与删除 | 在同一线程所有权及写锁下协调文件、目录、projection 和 admission；显式用户历史删除按索引分批推进 | `storage/thread_store.rs` |
| 冷压缩 | 默认关闭，仅显式请求；保护活动线程，压缩与恢复使用临时文件和原子替换 | `storage/rollout_compression.rs`、`thread_store.rs` |
| 诊断范围清理 | 只清有界 monitor/stream/计量等运维数据，不隐式清线程目录与 canonical 历史 | `storage/{sqlite,postgres}/log_stats_store.rs` |
| 写驱动维护 | 实际新写入触发有限清理切片；空闲不设置周期清理任务 | `services/workspace.rs` |
| 目录删除 | `delete_logs=false` 保留历史；显式历史删除才调用 canonical 生命周期 | `storage/{sqlite,postgres}/session_cleanup.rs` |
| 已删会话宽限 | 宽限标记保持可重试，实际历史清理走 canonical 删除 | `services/workspace.rs` |
| 账号状态重置 | 按用户取消会话与任务、清工作区；是否删除历史必须由调用范围明确决定 | `services/work_state_reset.rs` |

服务端文件日志有独立的保留配置，默认保留期 0；它不承担用户线程历史，也不改变 rollout 生命周期。

## 8. 常见改动落点

| 想做的事 | 依次改 |
| --- | --- |
| 新增历史语义 | core canonical 类型和 policy → 生产 ThreadStore 写入/恢复 → projector → 查询/消费 → 生产压测 |
| 新增业务存储方法 | `wunder-core/src/storage_backend.rs` 的分域 trait → 对应 SQLite/PostgreSQL 控制面实现 |
| 新增记录字段 | 先确认事实归属 → core 类型 → 独立角色 schema 或完成态 projector → 行转换/有界查询 |
| 新增表 | 选择明确角色；可重建投影写入 `thread_history.rs`，业务表写对应角色 schema；不能重新混入执行正文 |
| 新增配置键 | `wunder-core/src/config.rs` 结构体和 Default → `config/wunder-example.yaml` → 按需增加环境变量映射 |
| 改展示分页/预算 | `wunder-core/src/thread_view.rs` → canonical 查询适配 → API 字节预算与消费侧；不影响 LLM 上下文预算 |
| 改工作区根/映射 | `services/workspace.rs` → `wunder-core/src/storage_constants.rs`、`path_utils.rs` |
| 加资源上限 | 在拥有该资源的入口定义；待写字节、投影批次、展示页、附件和模型上下文分别限制 |

## 9. 排障入口

| 症状 | 先看 |
| --- | --- |
| 时间线/轨迹翻页慢 | `thread_history_1.sqlite` 的索引和预览查询；页大小与响应字节预算；是否意外解码全历史 |
| 投影落后 | rollout 完整行边界与 `thread_history_projection_state`；明确恢复错误，不启动空闲扫描补偿 |
| 多节点历史缺失 | 请求是否到达线程执行所有者，其数据根是否持久；本地 hub 不提供跨节点访问 |
| 慢查询（PostgreSQL） | 控制面查询计划、池大小与锁范围；确认没有重新写入完整执行历史 |
| 慢查询（SQLite） | 是否访问正确角色库、有界 keyset 查询与短事务；避免永久 ATTACH 和全量统计 |
| 配置没生效 | 环境变量覆盖、YAML 和模板补值顺序；数据根使用 `WUNDER_STORAGE_DATA_ROOT` |
| 工具报路径越界 | 本地形态查 `security.allow_paths` 与路径围栏；舰体查沙盒端点与用户挂载 |
| 发消息被判忙且不排队 | `agent_queue.enabled` 与 admission 状态、任务线程作用域 |
| 空闲持续写库 | 是否持有无效执行租约、误触发 projector/retention；canonical writer 和 feeder 本身无空闲计时器 |
| 磁盘增长 | 区分 rollout、投影、logs、附件和工作区；确认没有复制完整请求/工具输出到诊断；文件日志保留期独立配置 |
| 记忆没被召回 | `memories_1.sqlite` 对应业务仓库与召回策略；长期记忆只在线程初始化时注入 |
