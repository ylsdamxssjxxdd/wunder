# 数据存储、工作区与配置

§8 是改动落点表，§9 是排障入口。运行链路见 ./03-运行时与执行链路.md，实时补水与事件游标见 ./04-实时投影与通信链路.md。

## 1. 四类数据

| 类型 | 特征 | 位置 |
| --- | --- | --- |
| durable 数据库 | 跨进程持久，事务与游标语义 | SQLite（蜂窝/舵机）或 PostgreSQL（舰体） |
| 文件现实 | 智能体真实读写的目录与文件 | 工作区根，§4 |
| 配置 | 启动加载、运行中可热更新 | `config/wunder.yaml` + 环境变量，§5 |
| 进程内状态 | 可丢失、可重建 | watch、presence、缓存、临时目录 |

判断原则：能被重建的不要入库；入库的必须能由 §2.5 的某个记录类型或某张表解释。

## 2. 存储分层与选型

### 2.1 契约与实现分家

- 契约全部在 `wunder-core/src/storage_backend.rs`：30+ 个分域 trait（`ThreadLogStore`、`ChatSessionStore`、`WorkspaceStore`、`MemoryRecordStore` 等），由 `StorageBackend` supertrait 组合（`wunder-core/src/storage_backend.rs:1544-1579`）。
- 实现分两套：`crates/wunder-runtime/src/storage/sqlite/`（如 `thread_log_store.rs`、`log_stats_store.rs`）与 `crates/wunder-runtime/src/storage/postgres/`，按同名分域一一对应。
- `crates/wunder-runtime/src/storage/backend.rs` 只做 re-export，不定义新方法。给存储加方法 = 在 core 的 trait 上加签名 + 两个实现各补一份，缺一处编译不过。

### 2.2 后端选型

`crates/wunder-runtime/src/storage/factory.rs:8-17`：

| 配置值 | 结果 |
| --- | --- |
| 空 | SQLite |
| `postgres` / `postgresql` / `pg` / `auto` | PostgreSQL |

受 cargo feature 门控：`sqlite-storage`、`postgres-storage`（`storage/factory.rs:21-45`）。feature 关闭时对应分支不编译，运行期落到「该后端不可用」的路径，不是回落。

参数定义在 `wunder-core/src/config.rs`：PG 为 `dsn` / `connect_timeout_s` / `pool_size`（`:2147-2153`）；SQLite 的 `db_path` 示例值 `./config/data/wunder.db`（`:3058`）。四项都能用环境变量覆盖（`WUNDER_STORAGE_BACKEND`、`WUNDER_SQLITE_DB_PATH`、`WUNDER_POSTGRES_DSN`、`WUNDER_POSTGRES_POOL_SIZE`，`:2552-2566`），env 优先级高于 YAML，见 §5.1。

### 2.3 schema 演进：没有版本表

- 建表靠幂等 DDL：`CREATE TABLE IF NOT EXISTS` 系列，见 `crates/wunder-runtime/src/storage/sqlite/schema.rs:10-48`；PostgreSQL 侧同理（`storage/postgres/schema.rs:99`）。
- 列的新增靠**列探测式 `ensure_*` ALTER**：启动时探测列是否存在，缺则 `ADD COLUMN`。没有 schema 版本表、没有迁移脚本目录、没有版本号顺序执行机制。
- 唯一持久化的内部游标是 meta 表里的 `thread_view_discovery_v2`（`storage/thread_view_store.rs:91-103`），用于展示投影的一次性发现，不是迁移版本。
- 因此加字段的标准做法：在 `CREATE TABLE` 里写上新列（照顾新库），同时补一个 `ensure_*`（照顾老库）。任何文档或注释写「按版本号 v3 迁移」都是失实的。

### 2.4 两种后端的规模差异

| 方面 | SQLite | PostgreSQL |
| --- | --- | --- |
| 日志大表 | 单表 + 索引 | 按月分区，启动与每日任务补建分区 |
| 用量统计 | 直接聚合查询 | 增量计数表 + 水位对账 |
| `tool_logs` | 原样列 | 含排除标记物化列，供统计侧跳过 |
| 并发写 | 单写队列串行化（§4） | 行锁 + 连接池（`pool_size`） |
| 目标形态 | 蜂窝、舵机本地 | 舰体/蜂巢 |

### 2.5 核心记录类型

权威定义在 `wunder-core/src/storage_records.rs`，一行一条，字段语义以源码注释为准。改记录类型时同步改两个后端的行转换（`row_to_*` / `*_to_row`）。

| 域 | 类型（行号） | 关键字段与语义 |
| --- | --- | --- |
| 用户与组织 | `UserAccountRecord`(:6)、`OrgUnitRecord`(:27)、`UserQuotaStatus`(:40) | 账号、单位树节点、额度状态；额度字段前缀 `quota_*`，与真实 token 统计相互独立 |
| 向量知识 | `VectorDocumentRecord`(:191)、`VectorChunkEmbeddingRecord`(:217) | 文档与其分块的向量 |
| 会话 | `ChatSessionRecord`(:235) | `session_id` / `agent_id` / `workspace_id` / `parent_session_id` |
| 工作区 | `WorkspaceRecord`(:256) | `root_path` 为规范化后的主机路径 |
| 轮次 | `ThreadTurnTail`(:273) | `user_turn_index` / `turn_status`，目录页尾读取用 |
| 目标态 | `SessionGoalRecord`(:290-308) | `revision` 做 CAS，`phase` 只有 `active|paused|blocked|complete` |
| 渠道 | `ChannelBindingRecord`(:435)、`ChannelUserBindingRecord`(:450)、`ChannelSessionRecord`(:461) | 渠道账号、对端与用户、渠道会话映射 |
| 附件 | `MediaAssetRecord`(:572) | 会话附件；目录常量 `CHAT_ATTACHMENT_DIR`（`services/chat_attachments.rs:16`） |
| 记忆 | `MemoryFragmentRecord`(:718)、`MemoryHitRecord`(:763)、`MemoryJobRecord`(:781) | 三层 L0 标题 / L1 摘要 / L2 正文，加 tier 与 supersedes 链 |
| 定时任务 | `CronJobRecord`(:633-663) | `dedupe_key`、租约（`runner_id`/`run_token`/`heartbeat_at`/`lease_expires_at`）、`consecutive_failures`、`auto_disabled_reason` |
| 互通 | `InterlinkChannelRecord`(:905)、`InterlinkShadowRecord`(:921)、`InterlinkCommandRecord`(:952)、`InterlinkApprovalRecord`(:970)、`InterlinkAuditRecord`(:985) | 影子记录带 revision + threads/workspace 的 JSON |

消息与工具的物理表不在记录类型文件里，而在建表处：`thread_items`、`thread_turns`、`tool_logs` 分别见 `storage/sqlite/schema.rs:607`、`:626`、`:694`。`thread_turns` 上的唯一索引限定 `trigger_kind='user'` 用来约束用户轮次单调（`schema.rs:623`）。旧的 `chat_history` 表已随线程日志收口移除，不再存在。

## 3. 展示读模型与有界分页

线程时间线（蜂巢）与轨迹视图（蜂窝/舰桥）不直接读源表，而是读**投影**。这一节的常量就是系统的性能口径。

### 3.1 分页与预算常量

`wunder-core/src/thread_view.rs:5-11`：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `CHAT_PAGE_SIZE` | 12 | 聊天页默认页大小 |
| 聊天页上限 | 20 | 客户端请求更大页时被夹到这个值 |
| `TRAJECTORY_PAGE_SIZE` | 80 | 轨迹页默认页大小 |
| 轨迹页上限 | 100 | 同上夹取 |
| 聊天响应预算 | 128KB | 超出即截断分块交付 |
| 轨迹响应预算 | 192KB | 同上 |
| `BODY_CHUNK_BYTES` | 8192 | 正文按块交付，客户端按需续读 |

### 3.2 投影表与批量

投影表建在 `crates/wunder-runtime/src/storage/thread_view_store.rs:8-52`：`thread_view_heads`、`thread_view_chat_rows`、`thread_view_trajectory_rows`、`thread_view_body_manifests`、`thread_view_body_chunks`、`thread_view_trajectory_tiles`。批量写入的批大小为重建批 8（`:97`）、发现批 64（`:137`）。

写时投影在 `storage/thread_view_projection.rs`：预览按 2048 / 256 / 96 字符分级截断；单行子智能体卡片上限 `MAX_ROW_SUBAGENTS = 8`（`:144`）。投影未就绪或不适用时回退源表，走有界窗口读（clamp + budget）：`storage/thread_view_source.rs:142-151`。

### 3.3 后台重建与目录限量

- 后台重建任务的占空比 ≤1%：空闲时长 = 本轮耗时 × 99，最小 1s；失败退避 5s → 300s（`services/thread_view_rebuild.rs:36-45`）。重建是尽力而为，不抢占前台请求。
- 线程目录分页上限 `MAX_PAGE_SIZE = 100`，搜索一次最多扫描 10 × 100 = 1000 条（`services/thread_catalog.rs:16-21`）。目录结果里的 `writable` 恒为 true（`:124-131`、`:437-442`），因为引擎侧已无后台编排运行可占有工作区。
- 运行时活动状态优先取内存快照，回退 `thread_turns`：`services/chat_runtime_projection.rs:40-80`。

### 3.4 两个必须分清的口径

- **执行快照 ≠ 展示分页**。运行态快照 API（`orchestrator/runtime_snapshot.rs`）服务于调度与状态判断，不受 §3.1 的页大小约束；展示读模型服务于 UI，必须分页且有预算。
- **LLM 上下文压缩 ≠ UI 分页**。`services/history.rs` 做的是上下文压缩限额（`get_auto_compact_limit`，`:79-91`），与前端取多少条消息无关。文档里把两者混为一谈是常见错误。

## 4. 工作区与路径解析

### 4.1 根与映射

| 项 | 值 | 位置 |
| --- | --- | --- |
| 云端公共根 | `PUBLIC_WORKSPACE_ROOT = "/workspaces"` | `services/workspace.rs:44` |
| 桌面/舵机单根模式 | 环境变量 `WUNDER_WORKSPACE_SINGLE_ROOT` | `services/workspace.rs:45` |
| 容器映射键 | 按 scoped_user_id 解析 | `services/workspace.rs:555` |
| 用户私有容器 id | `USER_PRIVATE_CONTAINER_ID = 0` | `wunder-core/src/storage_constants.rs:1-4` |
| 沙箱容器 id | 1..10 | `wunder-core/src/storage_constants.rs:1-4` |

呈现口径：智能体的云端目录一律呈现为 `/workspaces/<user>/workspace`，**公共路径、主机真实路径、沙箱容器内路径三者同名同义**（2026-10-13 变更）。对外（前端与模型）不描述服务端绝对路径。

### 4.2 边界：隔离由沙盒承担

当前口径（2026-10-13）：

- 云端读、写、执行类工具一律在沙盒内执行。`execute_in_sandbox` 在舰体形态必然接管；**没有沙盒端点就直接失败，不回落宿主**。
- 沙盒侧 `allow_roots = ["/"]`，每用户一个容器、只挂该用户目录。因此**租户隔离由沙盒的挂载边界承担，`/workspaces` 代码分支不再做越界拒绝**。文档不得再写「云端路径校验负责隔离」。
- 舵机与蜂窝的本地形态仍保留配置化工作区边界：`security.allow_paths` / `deny_globs` 加上 `is_within_root`。
- 路径围栏工具函数：`wunder-core/src/path_utils.rs:47-53` 的 `is_within_root`，做 canonicalize 加 Windows verbatim 前缀与大小写归一；工具层广泛调用，如 `services/tools/file_tool.rs:1436`、`services/tools/edit_tool.rs:203`。
- 执行策略三态 Allow / Audit / Enforce：`wunder-core/src/exec_policy.rs:6-10`；未配置即 Allow（`:21-29`）。

| doc2md 转换 | 10MB | `api/doc2md.rs:8` |

## 5. 配置体系

### 5.1 加载优先级链

`wunder-core/src/config.rs:2478-2518`，按顺序：

1. 取 `WUNDER_CONFIG_PATH` 指定的文件，否则取 `config/wunder.yaml`。
2. YAML 内的 `${ENV}` 占位展开。
3. `apply_env_overrides` **最后生效**：环境变量覆盖已解析值（`WUNDER_STORAGE_BACKEND`、`WUNDER_SQLITE_DB_PATH`、`WUNDER_POSTGRES_DSN`、`WUNDER_POSTGRES_POOL_SIZE` 等，`:2552-2566`）。
4. 缺失字段与 `config/wunder-example.yaml` 模板做**稀疏合并**（`:2510-2513`）：只补用户没写的键，不覆盖已写的。

要点：

- **Rust 侧不加载 `.env`**（无 dotenvy 依赖）。`.env` 只被 docker-compose 与脚本层消费；`WUNDER_CONFIG_OVERRIDE_PATH` 没有任何 crate 读取。
- 已知隐患：直接对 `config/wunder-example.yaml` 走 `load_config_from_path` 会解析失败并**静默回落到 `Config::default()`**。模板文件不是可运行配置。
- 舵机与蜂窝启动时会在临时目录生成一份运行时配置副本（`<temp>/config/wunder.yaml`），再交给引擎加载，所以排查本地形态要区分「用户配置」与「生成的副本」。

### 5.2 读写与热更新

- 持久化：`ConfigStore` 单文件 YAML 回写 + 原子 version 计数（`crates/wunder-runtime/src/core/config_store.rs:60-90`）。
- 管理端在运行中调 `update()` 即热更新（`api/admin.rs:108`、`:490`、`:743`），无需重启；但读取配置的组件必须每次从 store 取，不能在初始化时把值拷死。
- 配置结构定义在 `wunder-core/src/config.rs`，`crates/wunder-runtime/src/core/config.rs` 是 re-export。

### 5.3 线程与运行时调优

`crates/wunder-runtime/src/core/runtime_tuning.rs:7-18` 的 env 上限：worker 128、blocking 512、PG 32、session-run 64/256。超限的值会被夹取。

`wunder-core/src/request_limits.rs:3-16` **只按字符计量输入，不含上限数值**；真正的输入上限是 `MAX_USER_INPUT_TEXT_CHARS = 1<<20`（`orchestrator/constants.rs:40`，校验在 `orchestrator/request.rs:358`），图片附件不计入。别把 `request_limits.rs` 当成限额定义处。

`crates/wunder-runtime/src/core/repo_assets.rs:3-6` 负责定位仓库内资产目录 `config/prompts`、`config/knowledge`、`config/skills`。`core/dpi.rs` 只服务 Windows 桌面，与配置加载无关。

### 5.4 关键开关与后果

| 键 | 默认 | 关掉/设错的后果 |
| --- | --- | --- |
| `agent_queue.enabled` | true（代码与模板一致） | 关掉后运行中再发消息被判「用户忙」且**不进排队条**；舰体启动会告警 |
| `storage.backend` | 空即 sqlite | 填 `pg` 而 feature 未开 → 后端不可用，不是回落 |
| `cron.enabled` | 见配置 | false 时 add/update/enable/run 全部拒绝 |
| `observability.server_log_dir` | `./config/data/logs/server` | 保留期默认 0 = 永不清理，需自行规划磁盘 |
| `observability.stream_event_retention_hours` | 168 | 0 表示禁用清扫，事件表只增不减 |

### 5.5 `config/` 目录内容

`wunder.yaml`、`wunder-example.yaml`、`sandbox-runtime.yaml`、`mcp_config.json(+example)`、`org_units.json(+example)`、`i18n.messages.json`、`app_version.json`、`fonts.conf`、`matplotlibrc`；子目录 `prompts/`、`skills/`、`knowledge/`、`data/`、`fonts/`、`ppt_templates/`、`preset_worker_cards/`、`benchmark/`。`config/org_units.json` 是单位树的启动播种源（`core/state.rs:317`）。

仓库内 `config/wunder.yaml` 与 `.env` 含真实形态的密钥值：**任何文档、示例、日志一律用占位符**，不得复制实际值。

## 6. 知识库、记忆与用户世界

### 6.1 知识库三型

由 `base_type` 归一为 `Literal | Vector | Ragflow`（`wunder-core/src/config.rs:1831-1835`）。

| 型 | 实现 | 磁盘根 / 关键配置 | 默认值 |
| --- | --- | --- | --- |
| Literal | `services/knowledge.rs`：内置词面 + LLM 检索 | — | `DEFAULT_MAX_DOCUMENTS = 5`、候选 80（`:19-20`） |
| Vector | `services/vector_knowledge.rs` | `config/data/vector_knowledge`，env `WUNDER_VECTOR_KNOWLEDGE_ROOT`（`:20`）；表 `vector_documents` / `vector_chunks` | chunk 800 / overlap 100 / top_k 5（`:27-29`） |
| Ragflow | `services/ragflow_knowledge.rs`（外部 HTTP） | `ragflow.base_url` / `api_key` / `timeout_s`（默认 120）（`wunder-core/src/config.rs:1864-1888`）；每库 `ragflow_dataset_id`、`chunk_method`（14 种）/`delimiter`/`top_k`/`score_threshold`（`:1804-1827`） | 超时 120s |

知识库按库动态注册为工具，取代旧的单一 `knowledge` 工具（见 ./05-工具、技能、MCP与外部能力.md）。

### 6.2 记忆分层

- 表：`memory_records`、`memory_fragments`、`memory_embeddings`、`memory_hits`、`memory_jobs`（`storage/sqlite/schema.rs:790-896`）。
- 作用域 `user_id + agent_id`，`agent_id` 缺省为 `__default__`（`services/memory.rs:14-15`）。
- 三层内容 L0 标题 / L1 摘要 / L2 正文，加 tier 与 supersedes 链。片段 tier 为 core | working | peripheral，升级阈值 access ≥ 10 或 hit ≥ 4（`services/memory_fragments.rs:24-27`、`:43-44`）；召回默认 6、上限 30、列表 200（`:33-35`）。
- **语义召回当前禁用**（`services/memory_fragments.rs:36`）：`memory_embeddings` 表存在，检索路径不启用向量召回。写文档不得把它算作可用能力。
- 注入约束：长期记忆只在线程初始化时注入一次，落在 system prompt 冻结分支内（`orchestrator/prompt.rs:334`）；已存 prompt 命中复用时不再注入。详见 ./03-运行时与执行链路.md。

### 6.3 用户世界

`user_world` 是站内 IM 域（联系人/会话/群/消息/事件，表 `user_world_*`，`storage/sqlite/schema.rs:1117-1176`），API 前缀 `/wunder/user_world/...`（`api/user_world.rs:44-77`）。限额：联系人 100、列表 50、未读页 500 × 20（`services/user_world.rs:14-19`）。它**没有对应工具**——旧的「用户世界工具」已删除，只有服务与 API。

### 6.4 额度

普通用户每日发放固定额度，按服务端本地日期惰性入账、每天只入账一次、不补发；每次实际模型请求前在事务内完成发放与扣减。SQLite 用 IMMEDIATE 事务，PostgreSQL 用行锁。账户字段前缀 `quota_*`，与真实 token 统计分离；资料更新走窄字段更新，避免保存资料覆盖并发扣减。

| 清扫触发点 | 在「按时间范围删日志」的同一事务里触发 | `storage/sqlite/log_stats_store.rs:426-504` |
| 账号状态重置 | 按用户取消会话与任务、清工作区，返回 fresh_sessions 清单 | `services/work_state_reset.rs:12-19` |
| SQLite 空间回收 | 打开时 `auto_vacuum = INCREMENTAL`；清理后 incremental_vacuum + `wal_checkpoint(TRUNCATE)` | 清理入口同上 |

删除会话的语义：用户删除先写墓碑，宽限期（§4.3，默认 24h）到期后由清扫任务物理删除日志；服务端文件日志默认不自动清理（保留期 0）。

## 9. 排障入口

| 症状 | 先看 |
| --- | --- |
| 时间线/轨迹翻页慢或超限 | 是否走投影：`thread_view_heads` 有无该线程；重建任务日志（`services/thread_view_rebuild.rs`）；请求的页大小是否被夹到 §3.1 上限 |
| 投影与源表不一致 | 发现游标 `thread_view_discovery_v2`（`thread_view_store.rs:91-103`）是否卡住；必要时让后台重建覆盖 |
| 慢查询（PG） | 分区是否补齐（启动与每日任务）；用量统计走增量计数表还是回落到大表聚合；`pool_size` 与 `connect_timeout_s` |
| 慢查询（SQLite） | 本地库体积与 `auto_vacuum` 是否生效；写队列 2048 是否被打满（表现为工具写文件后落库延迟） |
| 配置没生效 | 按 §5.1 顺序倒查：env 覆盖 > `${ENV}` 展开 > YAML > example 稀疏合并。注意 Rust 不读 `.env` |
| 启动后配置像默认值 | 是否误把 `wunder-example.yaml` 当运行配置（§5.1 已知隐患：解析失败静默回落 default） |
| 工具报路径越界 | 本地形态查 `security.allow_paths` 与 `is_within_root`；云端形态查沙盒端点是否可达——**云端失败不是路径校验造成的**（§4.2） |
| 发消息被判「用户忙」且不排队 | `agent_queue.enabled` 是否为 false（§5.4） |
| 磁盘涨 | 服务端文件日志保留期默认 0；`stream_events` 保留 168h 是否被设为 0；日志清理接口只由管理员按时间范围调用 |
| 记忆没被召回 | §6.2：语义召回当前禁用；tier 与访问计数决定候选，召回条数默认 6、上限 30 |
