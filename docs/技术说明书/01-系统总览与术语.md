# 系统总览与术语

Wunder 的术语在文档和代码里必须指同一件事。遇到判断句和旧说法冲突时，以本页「已过期说法」清单和代码为准。

## 1. 形态与入口

Wunder（心舰）是**智能体调度平台**：把目标交给智能体，它拆解任务、调用工具、交付结果。四个可执行形态 + 一个网页工作台共享同一引擎与核心，差异只在接入层。

| 形态 | 定位 | 进程与产物 | 数据面 |
| --- | --- | --- | --- |
| 蜂窝（desktop） | 本地 AI 工作台，个人用户默认入口，主推应用 | 前端 `frontend-slint/`（可执行 `wunder-frontend-slint`），同进程原生调用 `crates/wunder-desktop/` 的 `NativeDesktop`，不起 HTTP/WebSocket、不拉子进程 | 本地 SQLite |
| 舵机（cli） | 手工本地操作入口，终端驱动、脚本化、自动化 | `crates/wunder-cli/`（bin `wunder-cli`）；三端为 TTY 时进 TUI，非 TTY 降级一次性执行 | 本地 SQLite |
| 舰体（server） | 用户与智能体管理平台：多租户、用户与单位、智能体应用构建发布、网关统一接入与调度，内置工具链、知识库与长期记忆，含管理界面（舰桥）与用户界面（蜂巢） | `crates/wunder-server/`（bin `wunder-server`）+ 引擎 | PostgreSQL（crate 默认 feature `postgres-storage`） |
| 蜂巢（web） | 云端 AI 工作台，随舰体提供，浏览器访问 | `frontend/`（Vue 3 + TypeScript）构建出的静态产物，**由 nginx 容器只读挂载对外提供**，无独立进程 | 舰体存储 |
| 舰桥 | 舰体自带的治理界面，面向管理员 | `web/`（原生 HTML + JS 模块，无构建步骤），由舰体 `mount_static(app, "web", "/")` 挂载（`crates/wunder-server/src/main.rs:117`） | — |

必须记住的两条边界：

- **蜂巢不由舰体托管**。舰体只挂 `web/`（舰桥）与头像、ppt 静态目录（`crates/wunder-server/src/main.rs:101-119`），没有挂 `frontend/dist`。蜂巢产物由 nginx 容器只读挂载并反向代理 API（`docker-compose-x86.yml:265-283`，`frontend/nginx.conf:33-92`）。
- **蜂窝与舵机不依赖舰体**。它们的 Cargo 依赖里没有 `wunder-server`（crate），只依赖引擎与核心，可独立分发。

Electron、Tauri 前端壳停止日常维护与功能迭代；「停止维护前端壳」不等于「停止维护蜂窝后端」。

## 2. 分层

```
接入层（每种形态一份，只做鉴权、协议适配、接线）
┌───────────────┬───────────────┬───────────────┬─────────────────────┐
│ 蜂窝           │ 舵机           │ 舰体           │ 蜂巢 / 舰桥          │
│ frontend-slint│ crates/       │ crates/       │ frontend/ (Vue)     │
│ + crates/     │ wunder-cli    │ wunder-server │ + web/ (HTML+JS)    │
│ wunder-       │               │ (只有 main.rs)│ → nginx 对外         │
│ desktop       │               │               │                     │
└───────┬───────┴───────┬───────┴───────┬───────┴──────────┬──────────┘
        └───────────────┴───────────────┴──────────────────┘
引擎 crates/wunder-runtime（lib 名 wunder_server）
  api 渠道接入/HTTP/WS · channels 外部渠道 · gateway 节点网关
  orchestrator 执行调度主链 · services 业务服务（线程运行时、工具、
  记忆、知识、互通、投影…）· storage SQLite/PostgreSQL 实现
  core AppState/配置存取/审批/日志 · sandbox 沙盒 · ops 观测与压测 · lsp
核心 crates/wunder-core（跨形态低依赖基础能力）
  config · auth · storage_backend（存储契约）· storage_records ·
  exec_policy · path_utils · thread_view（展示读模型契约）· i18n · schemas
存储  本地形态默认 SQLite；舰体默认 PostgreSQL
```

引擎与核心的分工判据：不依赖执行链路、多个形态都要用的类型和策略进 `wunder-core`；涉及执行、投影、外部协议进 `wunder-runtime`。

## 3. 五个 crate 的真实形状

| crate | 产物 | 关键事实 |
| --- | --- | --- |
| `wunder-core` | 仅 lib | `crates/wunder-core/src/lib.rs` 暴露 23 个 `pub mod`，并定义 `RuntimeShape { Server, Cli, Desktop }` |
| `wunder-runtime` | lib + 1 个可选 bin | **`[lib] name = "wunder_server"`**（`crates/wunder-runtime/Cargo.toml:7-9`），所以其它 crate 一律写 `wunder_server::…`；唯一的 bin `backend_sim` 需要 `sim-bins` feature；存储实现受 `sqlite-storage` / `postgres-storage` 门控 |
| `wunder-server` | bin `wunder-server` | **只有 `src/main.rs` 一个文件**，靠对 `wunder-runtime` 的依赖做 feature 转发组装，默认 feature 为 `postgres-storage`；是 workspace 的 `default-members` |
| `wunder-desktop` | lib + bin `wunder-desktop-bridge` | lib 入口是 crate 根 `lib.rs`（不是 `src/lib.rs`）；bridge bin 为 `bridge_main.rs`，仅给既有兼容客户端 |
| `wunder-cli` | bin `wunder-cli` | crate 根 `main.rs`，**没有 lib.rs**，不对外提供库接口 |

看到 `wunder_server::` 不要以为是笔误或旧名：那是 `wunder-runtime` 的 lib 名。

## 4. 统一语言

| 术语 | 定义（以代码为准） | 出处 |
| --- | --- | --- |
| **线程 / 会话** | 智能体的连续执行单元，一个智能体可同时拥有多个独立任务线程；调度、锁与实时状态都按任务线程隔离。代码里以 `session_id` 标识 | `crates/wunder-runtime/src/services/runtime/thread/runtime.rs:106`（`ThreadRuntime`） |
| **用户轮次** | 用户每发送一条消息记 1 次，由线程日志受理时分配、幂等 | `orchestrator/thread_log_committer.rs:67 accept_turn`，调用点 `services/runtime/thread/runtime.rs:274` |
| **模型轮次** | **引擎主循环每发起一次模型调用自增一次**；一个模型轮次内可以有多个工具调用，**工具调用不单独计模型轮次**；一个模型轮次恰好对应一个可见输出项 `{turn_id}:text-{model_round}` | `orchestrator/execute.rs:435`、`orchestrator/tool_exec.rs:152-161`、`orchestrator/types.rs:35-77` |
| **工具批次** | 时间线里同一模型轮次内的一批工具调用，是展示条目，不是独立模型轮次 | 见 [03 运行时与执行链路](./03-运行时与执行链路.md) |
| **工作过程** | 一个用户轮次里最终回复之前的全部中间内容（思考、工具批次、中间打印）折叠成的条目，蜂巢与蜂窝同名 | `frontend/src/views/messenger/sections/MessageTimelineAssistant.vue`、`frontend-slint/src/native_workflow.rs` |
| **线程轨迹** | 线程执行全过程的可视化台账，取代旧的「线程日志对话框」 | `services/thread_log.rs`、`web/modules/trajectory-view.js`、`frontend-slint/src/native_trajectory.rs` |
| **展示读模型** | 面向前端的**有界分页投影**（聊天行、轨迹行、正文分块），不是执行真相源 | `crates/wunder-core/src/thread_view.rs:1-11`（文件头即写明「Bounded presentation reads. Execution snapshots are not a page contract.」） |
| **执行快照** | 运行态状态（活动轮次、排队、状态机），用于判活与恢复，与展示读模型是两套契约 | `orchestrator/runtime_snapshot.rs`、`services/chat_runtime_projection.rs` |
| **工作区** | 工具执行的工作目录。蜂窝/舵机是本地目录；舰体形态下智能体的云端目录呈现为 `/workspaces/<user>/workspace`，公共路径、真实路径与沙盒容器内路径同名同义 | `services/workspace.rs:44` |
| **互通（interlink）** | 云端（舰体/蜂巢）与本地设备（蜂窝/舵机）之间的隧道与命令面：节点、影子投影、命令台账、审批工单、审计、L0–L3 风险分层 | `services/interlink/`、`api/interlink*.rs`、告警触发 `services/interlink/alerts.rs:67` |
| **子智能体** | 主智能体临时创建的工作单元，任务结束即回收；**这是当前唯一的协作形态** | `services/tools/subagent_control.rs`、`services/subagents/` |
| **蜂群编排** | 蜂群工具、蜂房、编排态、team run、蜂群包、广场——**已从引擎与调度面移除**，只能在「已移除」语境出现 | `services/thread_catalog.rs:120-127`（注释写明不再有后台编排运行持有线程写入权） |

### 能力面的四层

这四层不是一回事，文档和代码里不要互换用词：

| 层 | 是什么 | 落点 |
| --- | --- | --- |
| **工具** | 执行体。内置工具（规范名多为中文）、MCP 工具 `server@tool`、打包 MCP `server@__mcp_pack__` | `services/tools/catalog.rs`（注册）、`services/tools/dispatch.rs:27`（路由）、`services/tools/registry.rs`（元数据单一来源） |
| **技能** | 可调用知识与脚本：目录 + `SKILL.md` + 入口脚本，技能名本身可被直接调用 | `services/skills.rs`、`services/skill_archive.rs` |
| **知识库** | 检索型语料，按库名动态注册为工具，取代旧的单一 `knowledge` 工具 | `services/knowledge.rs`、`services/vector_knowledge.rs`、`services/ragflow_knowledge.rs` |
| **能力** | 治理面（管理员/用户选择层）的统一描述符，`source = builtin \| mcp \| skill \| knowledge \| user_mcp \| user_skill \| user_knowledge` | `services/abilities/mod.rs:17-23`、`services/agent_abilities.rs`、`services/user_tools.rs` |

## 5. 硬约束

每条都有代码落点，改动时视为契约。

1. **线程提示词冻结 + 长期记忆只注入一次**。落点在 `orchestrator/prompt.rs`：已存 prompt 命中校验就原样复用（`:293-302`），首次确定时快照 AGENTS.md（`:304-312`）并在同一分支内注入记忆（`:334`），随后经 `build_session_system_prompt_item` + 统一提交出口持久化冻结（`:353-370`）。`context.rs` 没有冻结逻辑，`runtime_snapshot.rs` 与冻结无关。
2. **轮次语义固定**。用户轮次由 `accept_turn` 分配；模型轮次只在主循环发起模型调用时自增。可见输出项 id 由模型轮次决定，改这里等于改前端的时间线主键。
3. **线程日志只有一个写出口**。`orchestrator/thread_log_committer.rs` 的头注释写明：每会话 gate 串行化、单事务提交、提交成功才发布 cursor；`thread_change_hub.rs:23 publish` **只是唤醒信号**，不是状态真相，多实例靠轮询收敛。
4. **展示读模型必须分页且有界**。聊天页 12 行（上限 20）、轨迹页 80 行（上限 100）、响应预算 128KB/192KB、正文分块 8192B（`crates/wunder-core/src/thread_view.rs:5-11`）。
5. **租户隔离由沙盒承担**。云端读/写/执行类工具一律在沙盒内执行，无沙盒端点直接失败、不回落宿主；`/workspaces` 公共分支不再做越界拒绝，舵机仍保留配置化工作区边界。路径围栏 `crates/wunder-core/src/path_utils.rs:47-53` 负责工具层边界，不负责租户隔离。
6. **蜂窝与舵机不依赖舰体**，且 **Rust 侧不加载 `.env`**（workspace 无 dotenv 依赖）。`.env` 只被 compose/脚本层消费；配置入口是 `WUNDER_CONFIG_PATH` 或 `config/wunder.yaml`，优先级与展开顺序见 [06 数据存储、工作区与配置](./06-数据存储、工作区与配置.md)。

## 6. 一条请求的最小链路

只记形状，细节看 [03 运行时与执行链路](./03-运行时与执行链路.md)：

```
WS 入口 api/chat_ws.rs:456
  → ThreadRuntime::submit_user_request   services/runtime/thread/runtime.rs:169
  → accept_turn（分配用户轮次，幂等）     orchestrator/thread_log_committer.rs:67
  → Orchestrator::stream                 orchestrator/request.rs
  → 主循环 execute.rs                     每次模型调用 model_round += 1
  → 工具编排与分发                        orchestrator/execute_tools.rs → services/tools/dispatch.rs:27
  → 最终回复落库                          orchestrator/tool_exec.rs:47 try_append_chat
  → 事件与 durable 提交同源               orchestrator/event_stream.rs
```

`orchestrator/thread_runtime.rs` 只是**状态登记表**（`ThreadRuntimeRegistry`），线程运行时本体在 `services/runtime/thread/runtime.rs`。这是最容易写错的一处。

## 7. 这些说法已过期

| 过期说法 | 现状 | 依据 |
| --- | --- | --- |
| 蜂巢（web）由舰体静态托管 | 舰体只挂 `web/`（舰桥）与头像/ppt 目录；蜂巢 dist 由 nginx 只读挂载对外 | `crates/wunder-server/src/main.rs:101-119`、`docker-compose-x86.yml:265-283` |
| `wunder-server` 是「入口 + middleware + 静态资源」的后端 crate | 引擎在 `wunder-runtime`；`wunder-server` 只有一个 `main.rs`，中间件层与路由都来自引擎 | `crates/wunder-server/Cargo.toml`、`crates/wunder-runtime/src/lib.rs` |
| 「工具调用记 1 轮模型轮次」 | 模型轮次只按模型调用计数，工具批次不算轮次 | `orchestrator/execute.rs:435` |
| 蜂群编排、蜂房、编排态、team run 可用 | 引擎与调度面已移除，协作形态只有子智能体；UI 与文案仍有残留（见 09 章工程缺口） | `services/thread_catalog.rs:120-127`、`services/swarm/`（空目录，未在 `services/mod.rs` 声明） |
| 线程写入权可能被后台编排运行持有 | 用户拥有的线程恒为可写，`ThreadWriteAccess` 只是保留的按线程查询接口 | `services/thread_catalog.rs` |
| 存储按版本号做 schema 迁移 | 没有版本表也没有迁移脚本目录：幂等 `CREATE TABLE IF NOT EXISTS` + 列探测式 `ensure_*` ALTER | `storage/sqlite/schema.rs`、`storage/postgres/schema.rs` |
| `网页搜索` / `ptc` 已移除 | 代码保留、当前**临时下架**（对模型与用户不可见），注释写明恢复时移除条目即可 | `services/default_tool_profile.rs` |
| 云端路径校验负责租户隔离 | 隔离由沙盒承担；云端执行类工具无沙盒端点直接失败 | 见 §5 第 5 条 |
| Electron / Tauri 是可选前端壳 | Electron 零残留；Tauri 只剩指向不存在目录的死脚本与 Dockerfile 里的 tauri-cli 安装 | 见 [09 开发、扩展与变更流程](./09-开发、扩展与变更流程.md) 工程缺口 |
| `orchestrator/thread_runtime.rs` 是线程运行时本体 | 它是登记表，本体在 `services/runtime/thread/runtime.rs` | 见 §6 |
| 提示词冻结逻辑在 `context.rs` / `runtime_snapshot.rs` | 在 `orchestrator/prompt.rs` | 见 §5 第 1 条 |
| `a2a_*` 工具与 A2A 运行时仍在 | Rust 全仓无 `a2a`；nginx 仍保留 `/a2a` 与 `/.well-known/agent-card.json` 代理，是死配置 | `frontend/nginx.conf:73-92` |

## 8. 产品边界

- 四个可执行形态 + 蜂巢/舰桥两套界面是**同一系统**，不是并列产品。
- 前端是投影消费层，不是运行时真相源；客户端只能消费投影，不能反向篡改运行态。
- 技能是能力组织方式，不是引擎原语；MCP 是外部资源接入机制，不是独立运行时。
