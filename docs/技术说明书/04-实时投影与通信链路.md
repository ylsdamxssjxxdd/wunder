# 实时投影与通信链路

## 1. 核心原则

wunder 的实时系统遵循一条铁律：**内部运行态先变成公开事件，再由前端消费**。前端、桌面、CLI 或外部观察者都只能通过公开事件流获取运行态，不能直接读后端内部状态。

| `src/api/core_ws.rs` | 核心实时链路 |
| `frontend/src/realtime/` | 前端实时消费者 |
| `frontend/src/stores/` | 前端状态存储 |

## 3. 事件模型

所有实时目标遵循统一事件模型：

```
Snapshot → 首次接入时获取完整状态视图
Delta    → 运行时变化时发送增量事件
Replay   → 断线后补齐未消费事件
```

`stream_events` 表持久化事件流，支持断线后 replay。

## 4. Presence 与 Watch

**Presence** — 记录哪些用户在线、哪些连接存在。Presence 是进程内观测状态，可丢失可重建，不是 durable business state。

**Watch** — 某个连接正在观察哪个目标。用于控制订阅、计算活跃观察者数量。

## 5. 前端消费流程

```
1. 路由确定观察目标
2. 本地缓存恢复已有视图
3. 首包获取 snapshot
4. WS 发起 watch
5. 接收 snapshot 或承接后续 delta
6. 断线 → replay → 补水 → 重同步
```

前端允许短暂 optimistic 更新，但最终必须服从后端事件回压。

## 6. 会话类实时链路

负责：当前会话消息流、渠道消息即时渲染、线程运行态、waiting/approval/user_input 控制态、resume 后状态收敛。

常见问题：

| 问题 | 原因 |
| --- | --- |
| 控制面事件被当成消息事件 | 事件类型过滤缺失 |
| 会话列表与正文不同步 | 两路消费时序未协调 |
| 冷会话恢复时详情和列表互相回压 | 缺少补水逻辑 |

## 7. 协作类实时链路

负责：mission 公开面板、beeroom 公开摘要、team run 状态和 agent activity。

beeroom 是实时房间附着点，不应承担领域聚合逻辑。领域逻辑在 swarm 层完成，beeroom 只做实时分发。

## 8. 通信原则

- **WebSocket 为主**，SSE 为兜底。
- 页面卸载只取消当前 watch，**不关闭全局共享连接**。
- 工具页、设置页、工作目录默认走补热链路，不抢占消息热路径。

## 9. 排查矩阵

| 现象 | 检查点 |
| --- | --- |
| 页面实时卡住 | 连接在线？watch 仍有效？ |
| 重连后列表不一致 | replay 命中？stream_events 是否连续？ |
| 活跃会话正文不刷新 | 当前 target 是否指向最新 session？ |
| 设置页切换变慢 | 是否重复请求同一份数据？ |
| beeroom 信息混乱 | 是否把 swarm 逻辑堆进了 beeroom 层？ |

## 聊天客户端一致性边界（2026-09-21）

客户端的 HTTP snapshot 与 WS 流需要独立的新鲜度门槛：记录请求发出时的实时修改版本和请求序号，拒绝倒退的响应；历史正文可以补缺，但不得覆写请求期间产生的实时尾部。运行快照的状态变化不要求 `last_event_id` 增长，因此不能按该游标生成去重键。workflow-only 历史补水保留当前会话运行状态，不得用旧轮次事件重新启动或结束当前任务。

手动压缩恢复同样遵守终态单向收敛：明确的 idle 快照立即清除临时 streaming 标记，不使用 marker 的 30 秒年龄保护；已结束模型轮次的历史请求只补充工作流，不把助手状态写回 tooling。服务端详情和事件接口共用活动投影服务；线程 runtime 缺失且 monitor 活跃时，异步读取最近 32 条事件，只有最新生命周期为终态且无更新活动或新轮次证据才判空闲。数据库异常保留原回退行为，不扩大历史查询。

`llm_output` 是模型动作输出，`finish_reason=tool_calls/function_call/tool_use` 或非空 `tool_calls` 表示还需执行工具，不能关闭请求或结算用户轮次。Socket、事件归一和工作流消费者共用 `frontend/src/utils/chatStreamTerminal.ts`。控制器替换与 AbortError 必须区分用户停止、连接恢复和视图销毁，旧 resume 的 finally 只允许清理自己持有的控制器。

具体投影、缓存和虚拟窗口约束见 `docs/设计文档/09-用户侧前端设计.md` 第 10 节。

工作线程目录的删除收敛通过普通列表请求附带最多 100 个已知 ID 批量核对，复用既有刷新节奏，不新增逐线程日志轮询。普通分页仅作合并；服务端明确返回的失效 ID 可清理活动线程、本地摘要与日志缓存。若首页返回的条目数等于 `total`（包括零），该响应覆盖查询范围内完整目录，可清理请求发出前已知但未返回的同范围条目，保留其他智能体及请求期间新建的线程。不能因某个 ID 不在已加载的部分目录里，就拒绝日志或恢复请求。

列表核对、详情失效和预加载失效共用有界失效集合；摘要更新、线程控制补丁、迟到列表和详情响应均检查该集合，事件缓存写入也要拒绝已失效线程。显式恢复归档后解除对应限制，账号状态重置时清空集合。点击失效线程时按导航意图处理提示和草稿跳转，不能把清理造成的 `activeSessionId` 为空误判为用户已切走；后续用户切换仍应优先。管理员删除以会话目录作为归属真相，监控历史不承担唯一所有者索引。

日志清理必须同时收敛 durable 目录：PostgreSQL/SQLite 在同一事务里删除指定时间范围日志，再清理同范围内已无历史证据的已使用线程目录及目标关联；未使用草稿、有保留历史、有定时任务或活动目标的线程不删。运行、排队、重试、等待审批通过监控、lease 和任务表共同保护；PostgreSQL 维护操作使用限时表锁防止检查后启动的竞态，SQLite 使用 immediate 事务。用户全量清理单独删除用户范围目录与定时任务，失败不得返回成功。已有残留使用 `scripts/repair_empty_thread_catalog.py` 显式修复，默认仅预览，应用前要求备份；不在列表热路径自动删数据，也不把缺少监控记录等同于线程失效。
