# 实时投影与通信链路

接口清单见 [07-接口、网关与渠道接入](./07-接口、网关与渠道接入.md)，执行链见 [03-运行时与执行链路](./03-运行时与执行链路.md)。

## 1. 三条不变量（代码里的兑现点）

| 不变量 | 含义 | 兑现机制（可点验） |
| --- | --- | --- |
| 前端不是状态真相源 | 界面只消费后端投影，断线、切线程、刷新都必须能从 durable 存储重建 | 线程日志唯一写出口 `ThreadLogCommitter`（`crates/wunder-runtime/src/orchestrator/thread_log_committer.rs:9-21`）；补水端点 `GET /wunder/chat/sessions/{id}/thread-log/snapshot`、`/view/*` |
| 单写者 | 一个会话在同一时刻只有一条变更推送流，避免同一 `change_seq` 区间被并发下发两次 | 每会话提交门 `gates: HashMap<session_id, AsyncMutex>`（同上 :25、:40-46）；`EventEmitter::emit_lock` 全程串行化 commit 与入队（`orchestrator/event_stream.rs:36-38`、:164）；同一连接上 `watch`/`resume` 按会话互斥替换（`api/chat_ws.rs:1473-1487`）；`start` 的请求级 feeder 用子令牌，流排空即释放（`api/chat_ws.rs:588-595`、:678-685） |
| 一切皆有界 | 队列、页、缓存、订阅数都有上限，宁可丢瞬时帧也不无界堆积 | 出站写队列 256、慢客户端水位 2、feeder 页 200（下表）；tail 帧满即静默丢弃；互通出站队列 256、旁观订阅队列 128 |

## 2. 三层投影：提交 → 唤醒 → 消费

```
引擎 emit ──► ① durable 提交（唯一出口，事务内写 thread_log_changes）
                     │  事务成功后才取 cursor
                     ▼
             ② 唤醒信号 ThreadChangeHub.publish(session, cursor)   ← 只是加速，不是真相
                     │  wake（同实例秒级）
                     ▼
             ③ 消费侧 feeder watch_thread_changes()                 ← 正确性靠轮询兜底
                     │  每页 200 帧，读满页立即续读
                     ▼
             WS 订阅 / CLI 折叠 / 蛹原生 façade
```

| 层 | 代码 | 关键语义 |
| --- | --- | --- |
| ① durable 提交 | `orchestrator/thread_log_committer.rs`；`orchestrator/event_stream.rs:160-219` | `emit()` 在持锁期间同步提交（`commit_item` 等），提交失败**不发游标**；幂等空操作（重复受理、状态未变、重复反馈）不产生变更行也不发唤醒。表 `thread_log_changes(session_id, change_seq, user_id, change_type, turn_id, item_id, revision, payload, created_time)`，主键 `(session_id, change_seq)`（`storage/sqlite/schema.rs:652-665`） |
| ② 唤醒信号 | `orchestrator/thread_change_hub.rs:23 publish`、`:56 subscribe` | 进程内 `watch<i64>`；只接受更大的 cursor；无订阅者的条目直接删除（:42-51）。**多实例部署不依赖它**——注释明确它只是唤醒，正确性由 poll 收敛 |
| ③ 消费 feeder | `services/thread_change_feeder.rs` | `FEEDER_PAGE_SIZE = 200`（:20）、通道容量 256（:22）、基础轮询 250ms、上限 4000ms、退避因子 2.0（:23-25）；产出三种帧：`Change{seq,event,data}` / `SnapshotRequired` / `Overflow{cursor,resume_recommended}`（:29-44） |

写侧游标读取入口 `services/workspace.rs:1835 try_load_thread_changes(session_id, after_seq, limit)`：`after_seq` 超过最新 seq → 返回单条 `thread_snapshot_required`；遇到 `snapshot_required` 变更行同样立即截断本页；`limit` 在服务端钳制为 `1..=500`。

### 4.1 连接期策略下发

`connect` 握手成功后服务端立刻发 `ready`，载荷带 `protocol{version,min,max}` + `policy` + `features`（`api/ws_helpers.rs:86-128`、`api/chat_ws.rs:228-247`）。客户端应当按 `policy` 而不是硬编码常量做本地限流：

```json
{"type":"ready","payload":{
  "connection_id":"ws_<id>","server_time":0,
  "protocol":{"version":1,"min":1,"max":1},
  "policy":{"max_message_bytes":524288,"stream_queue_size":256,"slow_client_queue_watermark":2,
            "resume_poll_interval_s":0.2,"resume_poll_max_interval_s":0.8,
            "resume_poll_backoff_factor":1.6,"resume_poll_backoff_after":3,"stream_event_fetch_limit":200},
  "features":{"multiplex":true,"resume":true,"watch":true,"ping_pong":true,"goal":true}}}
```

协议范围不合法时返回 `INVALID_PROTOCOL_RANGE` / `PROTOCOL_MISMATCH`（`api/ws_helpers.rs:143-160`）。

### 5.1 帧的线路形状

出站统一是 `{type:"event", request_id?, payload:{event, id, data}}`（`api/ws_helpers.rs:698-812`）。`enrich_ws_event_data`（:907-929）会把可解析为数字的 `id` 同时镜像进 `data.event_id` 与 `data.event_seq`。

`thread_item_tail` 携带 `item_id/field/offset/text`，offset 为 UTF-16 语义的显式位置，重复应用无害（`orchestrator/event_stream.rs:220-231`）。

### 6.1 三类帧的不同待遇

| 帧类 | 队列满时 | 依据 |
| --- | --- | --- |
| `llm_output_delta` | **等待**（backpressure，不丢字） | `api/ws_helpers.rs:820-831` |
| 普通事件 | 先 `try_send`；满则发一条 `slow_client{reason:"queue_full_resume_required",resume_recommended:true}`（3s 节流），再回压等待 | 同上 :832-849、:749-774 |
| `thread_item_tail` | **静默丢弃**；尾巴自带 offset，下一段 durable 正文块会自愈 | 同上 :852-870、`api/chat_ws.rs:641-643` |
| durable feeder 帧 | 队列水位 ≤2 即发 `stream_overflow{cursor,resume_recommended:true}` 并**终止该订阅** | `api/ws_helpers.rs:219-231`、:511-523 |
| 实时活投（`send_ws_live_event`） | 水位 ≤2 时发 `slow_client` 后返回 Err，把这条活投递摘掉；正常发送 1s 超时 | 同上 :872-905 |

> 纠偏：**没有名为 `resume_recommended` 的事件**。它是 `stream_overflow` / `slow_client` 事件 data 里的布尔字段，含义是「请从你最后落地的游标重新发起订阅」。发出后服务端只保证这条订阅已停，不保证你收到——收不到时靠下一次心跳缺席或游标缺口触发同样的重续。

### 6.2 断线重连与陈旧响应

1. 客户端持久化**最后已应用的 durable 游标**：聊天用 `change_seq`，展示读用 `epoch + view_seq`，站内世界用 `event_id`。
2. 重连后先 `connect`，再带游标发 `watch`（或 `resume`）；`after_change_seq` 缺失直接返回 `AFTER_CHANGE_SEQ_REQUIRED`，会话不存在返回 `SESSION_NOT_FOUND`（`api/chat_ws.rs:788-806`、:861-878）。
3. 服务端发现游标越过 durable 窗口 → 回 `thread_snapshot_required`， feeder 随即结束本页；客户端必须整体 reload 原子快照，不得继续增量续（`services/workspace.rs:1841-1857`、`services/thread_change_feeder.rs:100-103`）。
4. 展示读侧的对应信号是 `thread_view_required`（`reset_required` 或读失败）→ 重新 `view/bootstrap`（`api/ws_helpers.rs:315-327`、:349-361）。
5. transport `event_id` **不参与重连、去重或排序**；只有 durable 游标参与（`services/thread_change_feeder.rs:3-5`、`orchestrator/event_stream.rs:79-81`）。
6. 提交幂等键 `client_message_id`：重复受理时 `accept_turn` 返回 `created:false`，编排层直接判 `client_message_id already accepted`，不重复分配用户轮次（`orchestrator/request.rs:124-138`）。
7. 陈旧响应：请求发出时记录请求序号与实时版本，倒退的响应一律拒绝写入；历史正文可补缺但不得覆写请求期间产生的实时尾部（口径来自 [10-运维、排障与验收](./10-运维、排障与验收.md) 与 `docs/功能迭代.md` 聊天一致性条目）。
8. 同 scope 挤号是服务端主动断链：`AuthSessionService::force_logout_user` 推 `SESSION_REPLACED` 后关闭该连接（`services/auth_sessions.rs:62-96`、:7）。

> 2026-10-13 修复的口径，值得单独记：展示读模型重构曾把 `watch` 载荷里的 `after_change_seq` 写死成 0，服务端只有在识别到 `view_seq` 时才忽略它；不投影展示读的旧舰体会退回变更流并从 0 全量重放整条线程日志。现在 `watch` 按线程 durable 游标发送，与舵机/蛹口径一致。改前端 watch 载荷时，**游标口径三端必须同步**。

蛹的独立 bridge（`wunder-desktop-bridge`，默认端口 18123）只服务既有兼容客户端，用 `build_desktop_router` + 桌面票据鉴权，不是默认路径（`crates/wunder-desktop/bridge.rs:66`、:110-116、:582-607）。

## 8. Presence 与 watch 的边界

`services/presence/` 是**进程内可丢可重建的观测态**，不是业务真相：连接注册表 + 节点注册表，清理周期 30s（下限 10s），配置缺失时 TTL 90s，Web 节点空闲判 away 有独立阈值（`services/presence/mod.rs:24-32`、`nodes.rs` 导出的 `WEB_AWAY_IDLE_SECS`）。聊天 WS 在 `start` 期间持有 presence 的 busy 标记，任务结束即释放（`api/chat_ws.rs:576-581`，排队分支同理 :515）。

因此：**「在线」不能用来判断线程是否活着**。线程活性看 `thread_status` / durable Turn 状态（`services/chat_runtime_projection.rs`），跨实例收敛看轮询而不是看 presence。

## 9. 排障矩阵

| 现象 | 先看 | 抓手 |
| --- | --- | --- |
| 页面卡住不出字 | 连接是否 ready、`watch` 是否成功、游标是否被写死成 0 | WS 日志 `api/ws_log.rs`；`ready.policy` 是否被客户端读取 |
| 工具条目一直转圈、后续条目不出现 | 请求级 feeder 是否越过水位后永久停止、前端是否注册了 `stream_overflow` 恢复 | `api/ws_helpers.rs:219-231`；执行流排空并停掉请求级 feeder 后服务端补发一条 best-effort `final`（`api/chat_ws.rs:700-722`） |
| 刷新/切线程后短暂显示运行中 | 是否用本地占位气泡当活性判据 | watchdog 只看 durable Turn；活性判定 `services/chat_runtime_projection.rs:40-80` |
| 整段正文丢失或重复 | durable 游标是否推进、offset 尾帧是否被当成真相 | `thread-log/changes`、`thread-log/snapshot` 对账；`client_message_id` 去重 |
| 大线程打开慢 | 展示读是否 `projection_state = rebuilding`、页/字节预算是否被触顶 | `thread_view_heads`；`/view/bootstrap` 的 `reset_required`；重建指标 `services/thread_view_rebuild.rs:20-32` |
| 慢客户端告警刷屏 | 3s 节流是否生效、消费端是否阻塞写队列 | `slow_client` 事件、`STREAM_EVENT_SLOW_CLIENT_WARN_INTERVAL_S` |
| 队列积压/请求 busy | 各队列是否有界、是否有无界任务 | `core/runtime_metrics.rs` 的队列指标，经 `/wunder/admin/runtime_metrics` 读 |
| 会话锁竞争导致不响应 | 锁 TTL 120s、心跳 5s、忙等退避 0.8→3s | `orchestrator/limiter.rs`、`orchestrator/constants.rs:14-25`，见 [03-运行时与执行链路](./03-运行时与执行链路.md) |

## 10. 改动指引

1. **加一类实时内容**：先定义它是否 durable。durable → 走 `ThreadLogCommitter`（不得自己拼游标、不得提前 notify hub，见 :20-21 注释）；纯瞬时 → 走 tail/`live` 通道并接受可丢。
2. **加一个 WS 端点**：复用 `api/ws_helpers.rs` 的 `WsQuery`/`WsSender`/`WsPolicy`/`WsReadyPayload`，不要另写一套 ready；出站队列必须用 `STREAM_EVENT_QUEUE_SIZE`，`max_message_size` 与 `max_frame_size` 同值设置。
3. **改页大小/预算**：常量集中在 `wunder-core/src/thread_view.rs`，两侧（存储投影与 API）都从这里取；改数同时更新 [06-数据存储、工作区与配置](./06-数据存储、工作区与配置.md)。
4. **别做的事**：不要在 emit 路径里做无界拼接；不要把 `event_id` 当恢复游标；不要在前端缓存整线程；不要在多实例部署里依赖 `ThreadChangeHub`。
