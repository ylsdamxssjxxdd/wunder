# 运维、排障与验收

## 1. 运维目标

运维的目标不是"服务能启动"，而是：

- 线程、mission、事件流和工具链路**可观测**
- 异常时能快速判断属于**哪一层**
- 部署、升级、配置变更和回归验证有**统一口径**

## 2. 发布边界

当前默认发布场景：**一人一会话、各自分散聊天**。

验收围绕消息主链、连接恢复、会话列表/正文同步、设置页补热。shared hotspot 属于后续容量专项，不阻塞当前发布。

## 3. 观测对象

| 对象 | 关注点 |
| --- | --- |
| Thread Runtime | 当前状态、waiting、resume、失败原因 |
| Mission Runtime | 任务推进、agent activity |
| Stream Events | 事件连续性、replay 覆盖范围、断线恢复 |
| Tool Runtime | 审批等待、超时、失败、重试、日志 |
| Gateway / Channels | 连接状态、路由、认证、限流 |
| Storage | 数据库可用性、读写错误 |

## 4. 日志与监控入口

### 后端

| 位置 | 用途 |
| --- | --- |
| `src/ops/` | monitor、performance、throughput、benchmark |
| `src/services/stream_events.rs` | 事件流持久化与回放 |
| `src/orchestrator/event_stream.rs` | 事件流产出 |

服务版本地运行日志：

- `config/data/logs/server/`：仅 `wunder-server` 写入；`wunder-cli` 与 desktop 不写本地运行日志。
- 文件格式：JSONL 结构化日志，按天轮转，默认保留 14 天。
- 重点字段：`timestamp`、`level`、`target`、`fields.message`、HTTP span 字段（method/uri/status/latency）以及 panic 时的 `thread_name`、`location`、`panic_payload`、`backtrace`。

启动日志会打印：配置加载路径、server mode、bind 地址、日志目录、app state 初始化耗时。

### 管理端

| 位置 | 用途 |
| --- | --- |
| `web/modules/monitor.js` | 监控面板（系统指标、token 趋势、工具热力图、用户管理） |
| `web/modules/performance.js` | 性能面板（prompt build、file ops、command exec 等） |
| `web/modules/throughput.js` | 吞吐面板 |
| `web/modules/debug.js` | 调试面板（单次请求全流程跟踪） |

### API 端点

| 端点 | 用途 |
| --- | --- |
| `/wunder/admin/gateway/status` | Gateway 状态与指标 |
| `/wunder/admin/throughput/status` | 吞吐指标 |
| `/wunder/admin/channel/runtime/probe` | 渠道运行时探测 |

## 5. 排查矩阵

| 现象 | 第一检查点 | 第二检查点 |
| --- | --- | --- |
| 服务起不来 | 配置文件路径、端口占用 | `WUNDER_HOST` / `WUNDER_PORT` |
| 服务异常退出或崩溃 | `config/data/logs/server/` 最新日志文件 | panic 记录、HTTP failure、启动参数 |
| 前端打不开数据 | 后端 `18000` 是否可达 | 前端 dev 代理是否正确 |
| 消息流中断 | WS 是否断开 | stream_events 连续性 |
| 工具不执行 | 工具面是否可见 | 审批、沙盒、超时策略 |
| 恢复失败 | session 状态完整性 | stream_events 断档 |
| 渠道消息不进来 | 渠道配置与鉴权 | inbound_queue / outbox / rate_limit |
| MCP 不可用 | endpoint、headers、enabled | tool_specs 获取与超时 |
| 首轮 prompt 漂移 | prompt.rs 是否重复生成 | 配置与 agent 预设 |
| 工具结果丢失 | tool_logs 状态 | stream persist |
| 线程一直 waiting | turn_state 字段 | resume 调用匹配 |

### 5.1 连续空回复与输出预算耗尽

旧版本会把连续空最终回复误报为 `LLM_UNAVAILABLE`。当前使用 `LLM_OUTPUT_LOOP` 区分输出循环与服务连接故障。`progress.stage=empty_final_answer_reroute` 表示已进入本用户轮次唯一一次输出恢复，`recovery_action=disable_thinking` 表示下一请求关闭思考。

- 一次排查中，同一用户轮次的四次请求持续约 551 秒，累计输出为 32768 token，没有执行工具；此前另一轮的两个空回复累计输出 16384 token，一次参数不完整的工具调用输出为 8192 token。此模式强烈指向反复触及单次输出上限，而非工具执行缓慢。
- 当前适配器默认 `max_tokens=8192`、思考预算 `2048`，显式配置仍优先。提供方可能不支持思考预算扩展字段，必须核对实际请求及服务端语义。关闭思考时 Chat Completions 与 Responses 均不再携带思考预算。
- 空回复、仅思考、空最终答复工具与截断参数共享一次恢复预算；恢复时本轮关闭思考，保留正文输出上限。再次出现无效输出立即结束；中途工具成功不重置该预算。已完成的空响应不再触发底层非流式补拉或同配置重试，用量仍计入本轮。
- 参数回退包装内的 JSON 在末尾截断时，执行前返回恢复原因 `TOOL_ARGUMENTS_INCOMPLETE`，整批尚未执行的调用要求重新生成；不再用“缺少路径”掩盖解析失败，不自动补齐后执行。普通 `raw` 文本保持原语义。

`llm_output` 保留 Chat Completions、Responses 与 Anthropic 的停止原因，并记录 `output_limit_reached`、`max_output`、`thinking_token_budget` 和 `thinking_disabled`。预算和思考开关表示请求设置；提供方是否执行这些设置需实测。精简导出若缺少 `llm_output`，且 `reasoning_tokens=null`，仍不能确定无效输出全是思考。`context_cache_probe.content_chars` 不包含全部工具参数和思考内容，不能当作实际输入 token 数。

回归覆盖流式/非流式的空回复、仅思考、截断参数、空最终答复、关闭思考后成功以及再次失败终止；检查单次恢复、用量计费与冻结 system prompt。需要长代码时优先拆分生成和局部修改，不提高空回复重试次数。

## 6. 校验命令

日常开发、排障和回归统一使用 64 位编译链，避免把默认 i686 toolchain 或不匹配的 32/64 位 C 库错误误判为代码问题。Windows 应显式使用与本机 C 编译器匹配的 `x86_64-pc-windows-msvc`/`x86_64-pc-windows-gnu`；当前可用示例为 `1.95.0-x86_64-pc-windows-msvc`。只有最终 Desktop/CLI 分发、Win7 兼容构建和 PE 验收才使用 32 位链路。

Rust：
```bash
cargo fmt --all
cargo +1.95.0-x86_64-pc-windows-msvc check --release -j 8
# 必要时
cargo +1.95.0-x86_64-pc-windows-msvc clippy --release -j 8
# 定向回归
cargo +1.95.0-x86_64-pc-windows-msvc test --release -p <crate> -j 8
```

若排查的是最终 32 位 Desktop/CLI 包，再切换到发布脚本要求的 i686 toolchain 和匹配的 i686 C 工具链；不能用本机 64 位 MinGW 直接链接 i686 目标。

前端：
```bash
npm run typecheck --workspace wunder-frontend
npm run build --workspace wunder-frontend
```

## 7. 验收维度

### 7.1 功能验收

- 单智能体请求能稳定进入线程并完成一轮执行
- 多智能体任务能形成 team run 并完成公开摘要输出
- 工具、技能、MCP 至少有一条闭环路径可用

### 7.2 运行验收

- server、desktop、cli 三种形态都能启动
- 配置文件和环境变量覆盖关系清楚
- WebSocket 主链正常，断线后可恢复

### 7.3 稳定性验收

- waiting / resume / crash recovery 可工作
- 前端路由切换不出现重复订阅和状态回退
- 慢客户端不会拖垮事件分发

### 7.4 文档验收

- 本目录、`docs/设计文档`、`docs/API文档.md` 与实现事实一致
- 变更已记录到 `docs/功能迭代.md`
