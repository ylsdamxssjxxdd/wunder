## 1. 适用范围

- 一条请求卡住、重复输出、上下文爆量，要定位到模块与字段。
- 要改执行链的某一段（提交、排队、轮次记账、工具并发、压缩、提示词）。
- 要判断某个现象归哪个治理机制管（锁、配额、重试、超时、预算）。

## 2. 端到端链路

四个形态（舰体 / 蛹 / 舵机 / 蜂巢）共用同一条链。差别只在接入层：蛹 native 与舵机在自己进程里直接调引擎，舰体经 HTTP/WS，蜂巢经 nginx 反代到舰体。

### 2.1 接入与提交

- `api/chat_ws.rs:453-457` 是 WS 主入口；HTTP `api/chat.rs:322-337`、核心 WS `api/core_ws.rs:454-484`、定时任务 `services/cron.rs:1611-1615`、互通命令 `services/interlink/client/execute.rs:879-884` 走的是同一个 `ThreadSubmitOutcome`。
- `submit_request` 在受理轮次之前会剥掉请求里伪造的内部键：`__queue_task_id`、`__queue_priority`、`__thread_log_turn_id`、`__thread_log_user_round`（`runtime.rs:200-204`）。排队权威与轮次身份不由调用方授予。
- `runtime.rs:263-270` 先读一次 `latest_thread_change_seq_by_session` 作为 `resume_from_seq`，再受理轮次。这样「受理这次轮次产生的 durable change」会被补水流重放而不是被跳过。
- 幂等：`runtime.rs:276-278`，`accept_turn` 返回 `created == false` 时直接报 `client_message_id already accepted`。

### 2.2 轮次受理

`thread_log_committer.rs` 是聊天链上 **唯一的 ThreadLog 写出口**。它的契约写在文件头（`:9-21`）：

1. 每会话一把 gate（`:40-46`），保证 change 顺序 == commit 顺序；
2. 存储调用是一个短阻塞事务（`:79-82`，走 blocking 池）；
3. **只有事务成功**才把 durable cursor 发到 change hub（`:49-63`）；
4. 幂等空操作（重放受理、状态未变、重复反馈）不产 change、不发唤醒；失败的提交不发 cursor。

用户轮次号由 `storage/thread_admission.rs` 在 queue 短事务中分配；`(thread_id, client_message_id)` 唯一约束提供重放幂等。输入首次确认进入 rollout 后回收待执行正文，保留轮次与幂等事实。

### 2.3 入队还是直跑

`runtime.rs:309-335` 的判定顺序：

| 条件 | 结果 |
| --- | --- |
| `config.agent_queue.enabled` 为真，或本次是受信任的后台投递（`submit_scheduled_request`，`:176-181`） | 进入队列/lease 判定 |
| 强制入队 ‖ `should_queue` ‖ 已有 pending 任务 ‖ 有挂起会话在等恢复名额 | `Queued(QueueInfo)`（`:323`） |
| 拿不到 start lease（同会话已有执行者） | `Queued(QueueInfo)`（`:330`） |
| 其他 | `Run(request, lease)`（`:335`） |

队列消费在 `runtime.rs:1134 run_loop`：唤醒或轮询（`agent_queue.poll_interval_ms`，下限 200 ms）后 `list_pending_agent_tasks(50)` 有界取批（`:1160`），领取后在 `:1381` 调 `orchestrator.stream`。入队侧对客户端先回一条 `queued` 事件（`api/chat_ws.rs:473-480`），再由 queue 作用域的 resume 循环转发持久化的 `queue_enter/queue_start/queue_finish/queue_fail`。

`ThreadSubmitOutcome` 定义在 `runtime.rs:65-68`。

### 2.4 主循环

`execute.rs:82 execute_request` 是执行主链。循环骨架：`:427 loop` → `:428` 让出名额 → `:429-434` 轮次上限判定 → `:435 model_round += 1`。

- `:339-342` 在派生本轮模型输入之前 flush 写队列，注释写明原因：上一轮的异步历史写入若未落地，快速连发的用户消息会丢掉 append-only 尾部并破坏 KV cache 复用。
- `:365-374`：`is_admin` 或 `config.server.mode == "desktop"` 时 **不设轮次上限**；其余走 `resolve_non_admin_max_rounds`（`execute_support.rs:434-447`，默认 1000，下限 2）。
- `:399-403` 装配每轮预算 `ToolBudgetLimits { total: 10_000, db_query: 2_000/10_000, memory_recall: 2_000 }`；批量预检在 `:1019-1057`，计数在 `:1210-1216`，超限阶段名 `tool_budget_guard`（`:1824`）。
- `:410-412` 注释是关键口径：**上下文占用只认 provider 报告的 token，本地估算一律不参与压缩决策**，`request_overhead_tokens` 恒为 0。

### 2.5 模型调用

`orchestrator/llm.rs`：

- `:473-480 resolve_llm_timeout_s`：取 `llm.timeout_s`，缺省或 0 用 `DEFAULT_LLM_TIMEOUT_S = 120`（`constants.rs:35`）。
- `:577` 用 `with_quota_tracking_admission` 包住客户端，配额扣减发生在**每次模型请求前**。
- `:837 / :877`：流式调用套 `StreamActivity::with_idle_timeout`（`stream_timeout.rs:18-38`）——内容、思考、工具参数分片都会刷新活跃时刻，超过期限无分片才判 `LLM stream idle timeout`；非流式保持整体超时。
- `:168 build_context_cache_probe` 只是前缀哈希**观测**，用于诊断前缀是否稳定，不写任何缓存。

### 2.6 工具执行与最终回复

见第 5 节。最终回复的落库在 `tool_exec.rs:47 try_append_chat`：它不追加新条目，而是更新流式阶段就已登记的同一个 durable item（`:151-161`）。

## 3. 轮次语义（以代码为准）

权威类型 `orchestrator/types.rs:34-43`：

```rust
pub(super) struct RoundInfo {
    pub(super) user_round: Option<i64>,
    pub(super) model_round: Option<i64>,
    pub(super) thread_turn_id: Option<Uuid>,
    /// True while the runtime drives an armed goal: the turn was admitted by the
    /// goal driver rather than by a direct human message. Providers use it to
    /// avoid re-issuing goal-management calls that require human authority.
    pub(super) is_goal_round: bool,
}
```

构造与传播：`RoundInfo::user_only` / `user_only_thread` / `with_model_round`（`:55-80`），`insert_into`（`:82-92`）把 `user_round`、`model_round`、`turn_id` 打进每一个事件与持久负载。

| 概念 | 代码事实 | 锚点 |
| --- | --- | --- |
| **用户轮次** | 用户每发送一条输入记 1 轮；同一 `client_message_id` 重放不重复分配 | `storage/thread_admission.rs` |
| **模型轮次** | 模型调用、工具调用或最终回复每次动作各计 1 轮；与请求次数分开计量 | 平台轮次约定与 canonical 动作统计 |
| 一次模型请求内的工具 | 可产生多个工具动作；模型请求次数与工具动作数各自计量 | `execute_tools.rs`、`storage/stress_model.rs` |
| 可见输出项 | 以稳定 ItemId 关联活动尾部和完成记录；不按条目数推算模型轮次 | `event_stream.rs`、`tool_exec.rs` |
| 用户输入项 | `{turn_id}:user`，仅「已受理、无 model_round、带 turn_id」的用户消息占这个稳定槽位 | `tool_exec.rs:128-150` |
| `is_goal_round` | 该轮由目标驱动器受理而非人直接发消息；provider 据此**不重复发出需要人类权限的 goal 管理调用** | `types.rs:39-42`、`execute.rs:194` |
| 压测上限 | 用户轮次与模型轮次各 2000 | `storage/stress_model.rs:12-13` |

模型轮次遵循平台定义：模型调用、工具调用或最终回复每次动作各计 1 轮。`model_requests` 仅计模型请求次数，不能直接当作模型动作总数；压测分别报告请求、工具调用和模型动作，避免把展示条目行数当作轮次。

活动文本条目在模型请求准入时确定稳定身份，并在有界内存中接收 delta；完成、中止或失败后才保存最终语义，不能把 running 空条目和逐 token 尾部持久化为历史。错误和取消必须关联实际受理的 turn 与 ItemId。

## 4. 实时投影：三件事分开看

| 角色 | 位置 | 事实 |
| --- | --- | --- |
| 事件发射 + durable 提交 | `orchestrator/event_stream.rs`、`thread_log_committer.rs` | 同一发射序列串行 canonical 完成记录与事件；实时 delta 只在有界活动状态中维护；持久化经 JSONL flush、完成态投影后才发布位置 |
| 唤醒信号 | `orchestrator/thread_change_hub.rs` | canonical flush 与投影成功后发布本地信号；无订阅者不保留条目，空闲不 polling；多节点需路由到线程执行所有者 |
| 消费侧 | `services/thread_change_feeder.rs` | 页 200、通道 256；先订阅再读，满页续读，追平后等待提交、取消或通道关闭 |

游标口径：transport event id 不参与历史恢复；历史位置由 RolloutId、ordinal 和完整字节边界定义，传输 `change_seq` 是其适配。重连、溢出和 lineage 切换见 [实时投影与通信链路](./04-实时投影与通信链路.md)。

## 6. 上下文压缩、观测与缓存

### 6.1 三个触发面

`orchestrator/compaction_policy.rs`：`CompactionDecision { by_history, by_overflow, by_presampling }`（`:5-11`），`trigger()` 返回 `"history" | "overflow" | "pre_sampling" | "none"`（`:18-28`）。

| 触发 | 判定 | 出处 |
| --- | --- | --- |
| `history` | 占用 ≥ 阈值；阈值 = ratio × `max_context`，ratio 默认 `COMPACTION_HISTORY_RATIO = 0.9`（可被 `llm.history_compaction_ratio` 覆盖，`>1` 视为百分数） | `memory.rs:109-116`、`constants.rs:6-7` |
| `overflow` | 占用 ≥ limit（provider 报溢出，或上一轮溢出后的强制修复，`execute.rs:413-418`） | `compaction_policy.rs:60` |
| `pre_sampling` | 未溢出未达 history，但占用 ≥ `presampling_limit` | `compaction_policy.rs:62-63` |

presampling 公式（`compaction_policy.rs:31-43`，常量 `:1-3`）：

```
occupancy_trigger = round(limit × 0.9)
adaptive_headroom = clamp(limit / 8, 256, 8192).min(limit / 2)
headroom_trigger  = limit − adaptive_headroom
presampling_limit = clamp(max(occupancy_trigger, headroom_trigger), 1, limit)
```

即触发点 = `limit − clamp(limit/8, 256..8192)` 与「占用 90%」取更晚者。`presampling_floor` 保证投机预压**不会抢在显式 history 阈值之前**（`:52-56`、`:61-63` 注释）。

历史自动压缩上限的另一处计算在 `services/history.rs:79-91 get_auto_compact_limit`：`min(max_context − max_output(≥8192) − 512, 0.9 × max_context)`。注意 `services/history.rs` 服务的是 **LLM 上下文预算**，与蜂巢展示分页无关（分页见 `./06-数据存储、工作区与配置.md`）。

### 6.2 token 口径

只信任 provider 观测值：`execute.rs:410-412`。落地点 `orchestrator/usage_accounting.rs:4-6 request_context_tokens`——要求 `!usage.estimated && usage.input > 0`，只取观测 input。唯一的例外是虚拟模拟器（`simulated_request_context_tokens`，`:15-20`）：它的 `input` 是实际发出的精确计数，允许当观测值用，但不动 `estimated` 标志，以免触发输出上限启发式误判。

### 6.3 microcompaction

`orchestrator/microcompaction.rs`，压力触发的本地压缩，不调用摘要模型：

- 常量 `:6-8`：`KEEP_RECENT_GROUPS = 5`、`MIN_SAVINGS = 256` token、`PREVIEW_BYTES = 768`。
- 只压「旧的、可复现的」观测；受保护载荷 `:16-45`：失败结果（`ok=false` / `isError`）、需要续读的（`has_more` / `continuation_required`）、多模态与任何续读游标字段、深度 > 8 的嵌套。
- 替换历史以 **hidden marker 行**持久化：`"hidden": true` + `meta.replacement_history`（`:204-219`，键名 `COMPACTION_REPLACEMENT_HISTORY_META_KEY`，`constants.rs:4`）。模型输入推导从这一行重放（`:244`、`:261`），因此不再另设存储通道。
- 诊断事件 `progress.stage = microcompaction`；本地估算不参与计费。

### 6.4 窗口与预算保护

- 当前用户消息标 `meta.compaction_inflight_current_user`（`memory_compaction_window.rs:4-19`），压缩不得把它当历史吞掉；下限 `COMPACTION_MIN_CURRENT_USER_MESSAGE_TOKENS = 64`（`memory_support.rs:10`）。
- 保留交互的下限 `COMPACTION_MIN_RETAINED_INTERACTION_TOKENS = 128`（`memory_support.rs:28`）；保留预算 `:11-16`（头 8192 / 尾 16384 token，单条 5120 token，单轮 20000 字符）。
- 预算再平衡在 `memory_compaction_budget.rs`（`memory_support.rs:7` 引用），避免单条长消息吞掉整段历史。
- 摘要输出上限 `COMPACTION_SUMMARY_MESSAGE_MAX_TOKENS = 5120`、安全边距 `COMPACTION_SAFETY_MARGIN = 512`（`constants.rs:10-12`）。

## 7. 提示词冻结与记忆注入

提示词组装在 `orchestrator/prompt.rs`，冻结提交在 `orchestrator/thread_log_committer.rs`，唯一持久化来源是 canonical rollout 的 `SessionMeta`。

| 步骤 | 位置 | 事实 |
| --- | --- | --- |
| 复用已存 prompt | `prompt.rs::resolve_session_prompt` → `thread_store.session_meta` | 读 `SessionMeta.initial_system_prompt`，命中即**原样返回**；仅 `NotFound` 允许初始化，损坏或不可读会返回错误 |
| 首次快照 AGENTS.md | `prompt.rs::merge_agent_prompt_with_thread_agents_snapshot` | 只在线程 prompt 首次确定时快照，之后文件改动不影响本线程；`AGENTS.override.md` 优先于 `AGENTS.md` |
| 记忆注入 | `resolve_session_prompt` 调用 `memory.rs::append_memory_prompt` | 只在初始化分支执行，已有 canonical prompt 时直接返回 |
| goal 策略文本 | `resolve_session_prompt` | `<goal-policy>` 静态文本，随 prompt 一起冻结 |
| 持久化冻结 | `thread_log_committer.rs::freeze_session` | 每线程 gate 内创建 canonical `SessionMeta`，写入失败阻断本轮；不再创建 system Item |
| 工具协议恢复 | `execute_support.rs::resolve_frozen_session_tool_call_mode` | 无已存协议快照时从同一个 canonical prompt 推断，历史不可读时返回错误，不会按新配置静默重置 |

要点：

- 长期记忆**只在线程初始化时注入一次**。`append_memory_prompt` 在编排链里仅位于 `resolve_session_prompt` 的初始化分支；无会话的系统提示词预览只构建预览，不会改写线程 canonical prompt。
- 前缀稳定靠冻结，不靠缓存写入。`build_context_cache_probe`（`llm.rs:168`）只做前缀哈希观测。
- **`orchestrator/context.rs` 没有冻结逻辑**，`runtime_snapshot.rs` 只有一个 `get_tool_session_runtime_snapshot`（命令会话运行态快照，`:5`）。旧文档把这两处当冻结依据是错的。

## 10. 等待、让出与恢复

### 10.1 活动轮次登记

`orchestrator/turn_state.rs`：`ActiveTurnRegistry`（`:14`）按会话持有 `ActiveTurnSnapshot`（`:6`），负责待审批项（`add/resolve_pending_approval`，`:64/:77`）与等待用户输入标记（`:88`）。它是**进程内登记**，不是 durable 状态。

`orchestrator/thread_runtime.rs` 同样只是状态登记表：`ThreadRuntimeRegistry`（`:52`）与状态枚举 `NotLoaded/Idle/Running/Queued/WaitingApproval/WaitingUserInput`（`:5-15`）。**线程运行时本体是 `services/runtime/thread/runtime.rs:106 ThreadRuntime`**，别把这两个同名文件搞混。

### 10.2 协作让出

`execute.rs:428`（每轮开头）与 `:796`（动作边界）调 `yield_queue_slot`，`queue_handoff.rs:5` 的注释说明语义：在两个动作之间停住已有 future，不重放工具、不追加用户轮次。挂起只保存执行 future、模型轮次与已完成工具结果；恢复发出 `queue_start(queue_state=resumed)` 继续原动作。

### 10.3 恢复设计

| 场景 | 要求 |
| --- | --- |
| 中断/取消 | 取消后 `SuccessProgressGovernor::cancel` 等收尾不得把中断流记作成功；迟到回流不自动唤醒主智能体 |
| 崩溃 | 从 ThreadLog `change_seq` 游标恢复；受理基线 `thread_resume_from_seq`（`types.rs:28-31`）保证当轮 change 被重放 |
| 上下文溢出 | 先修复压缩再采样（`execute.rs:413-418`），溢出恢复最多 8 次 |
| 排队补水 | `queue_enter/queue_start/queue_finish/queue_fail` 是持久事件，`api/chat/events.rs:989-992` 在允许类型内；状态映射见 `api/ws_helpers.rs:1234-1236` |

## 11. 排障：三个常见现象

### 11.1 线程卡住不动

按这个顺序看，前三步都不用读代码。

1. **运行时状态**：`GET /wunder/admin/monitor/{session_id}`（`api/admin/monitor_admin.rs:45`）。看 `status`、`stage`、`cancel_requested`、`cancel_source`、`elapsed_s`、`model_request_count`、`tool_calls`（字段来源 `ops/monitor.rs:305-327`）。`model_request_count` 不动 = 卡在模型调用；`tool_calls` 在涨而正文不出 = 卡在工具循环。
2. **是否根本没在跑**：`GET /wunder/chat/sessions/{session_id}/queue`（`api/chat/queue.rs:17`）看排队；`session_locks` 表看锁持有者与到期时间（`storage/sqlite/schema.rs:740`）。锁 TTL 120 s、心跳 5 s，进程被 kill 后最长要等 TTL 才自然释放。
3. **durable 有没有在动**：`GET /wunder/chat/sessions/{session_id}/thread-log/changes`（`api/chat/events.rs:46`）看 `change_seq` 是否推进；不动说明不是前端投影问题。
4. **等待态**：`WaitingApproval` / `WaitingUserInput` 属正常等待，看 `thread_status` 事件与 `active_turns` 的待审批项；审批策略见 `wunder-core/src/exec_policy.rs`。
5. **深层**：`execute.rs` 主循环的 `yield_queue_slot`（是否被挂起未授予恢复名额，`scheduling.rs:state()` 返回 `suspended`）；LLM 侧看 `stream_timeout.rs` 是否已到空闲期限。

### 11.2 重复输出 / 同一条回复出现两次

根因几乎都在**输出项身份**上，不在前端。

1. 取 `{turn_id}:text-{model_round}` 这条 item：`GET .../thread-log/turns`（`api/chat/events.rs:38`）→ `GET .../thread-log/items/{item_id}`（`:58`）。
2. 检查结算时用的 `round_info`：`model_round` 必须是**实际已受理**的那一轮（`execute.rs:438-442` 注释）。用了初始 user-only 身份 → 会新起一个随机 UUID 的助手条目，而流式条目永远停在 running。
3. `output_slot` 判定在 `tool_exec.rs:143-148`：`role=assistant` 且有 `model_round` 且 `meta.hidden != true`。统计对象迟到不能参与身份判定。
4. hidden 的内部 model-context 消息必须保持 append-only（`tool_exec.rs:137-142` 注释），否则会把可见流条目覆盖掉。
5. 客户端侧的重复判定与去重见 `./04-实时投影与通信链路.md`。

### 11.3 上下文爆量 / 压缩不生效

1. 先看占用是不是**观测值**：`GET /wunder/admin/monitor/tool_usage` 与 `runtime_metrics`（`monitor_admin.rs:37/84`），或 monitor 的 `context_tokens` / `context_tokens_peak`。若模型没回 usage，占用就不涨——这是设计（`execute.rs:410-412`），不是 bug。
2. 看压缩是否触发、触发类型：`compaction` 事件（`memory.rs:357/561/1056/1645`）里的 trigger，值域 `history | overflow | pre_sampling`（`compaction_policy.rs:18-28`）。
3. trigger 一直 `none` → 检查 `llm.max_context` 与 `llm.history_compaction_ratio`；`limit/8` 的自适应余量被 clamp 在 256..8192，小窗口的模型触发点主要由 90% 决定。
4. 反复 `overflow` → 看 `session_context_overflow` 标记驱动的强制修复（`execute.rs:413-418`）与 8 次恢复上限（`execute_support.rs:115`）。
5. 工具结果过大 → 区分两条通道：模型输入侧看 `meta.truncated`/`truncation_reasons`/`output_chars`（`tool_exec.rs:390-400`）；展示侧见 `./11-工具结果裁剪与观测链路.md`。
6. 单轮工具太多 → `progress.stage = tool_budget_guard`（`execute.rs:1824`）与三个预算值（第 9 节）。
7. microcompaction 没省下 token → 检查载荷是否命中保护项（`microcompaction.rs:16-45`），或节省未达 `MIN_SAVINGS = 256`。
