# 运行时与执行链路

> 本文档与 `docs/设计文档/02-智能体核心设计.md` 互补：那篇讲"为什么这样设计"，这篇讲"代码怎么跑、怎么查、怎么改"。

## 1. 运行时全景

wunder 的执行核心围绕 **orchestrator + ThreadRuntime** 展开。不管入口是 HTTP、WS、gateway、channel 还是 CLI，最终都映射为线程请求、mission 请求或系统控制请求。

```
外部请求 → 接入层（API / WS / Channel / Gateway）
          → ThreadRuntime（lease、queue、dispatch）
            → Orchestrator（turn 执行主链）
              → Prompt → Model → Tools → Output
            → 事件发布（stream events、beeroom）
```

### 关键目录

| 目录 | 职责 |
| --- | --- |
| `src/orchestrator/` | Turn 状态机、prompt 组装、context 管理、工具执行、恢复链 |
| `src/services/runtime/thread/` | 线程生命周期、lease 管理、排队、dispatch |
| `src/services/runtime/mission/` | Mission 调度与 team run 管理 |
| `src/core/state.rs` | AppState 三层装配（kernel / projection / control） |
| `src/core/config.rs` | 运行时配置定义 |

## 2. 一次标准请求的执行流程

1. **接入** — API / WS / Channel / Cron 收到请求，鉴权，参数校验。
2. **定位线程** — 根据请求找到或创建线程。任务线程忙时入队。
3. **获取 lease** — ThreadRuntime 分配执行 lease，保证执行互斥。
4. **Turn 启动** — Orchestrator 接管 turn，初始化 turn state。
5. **Prompt 组装** — 从配置和 agent 预设中组装 prompt（身份、指令、上下文、工具面）。
6. **Context 预处理** — budget 分配、history normalization、必要时 compaction。
7. **模型推理** — 发起模型 API 调用。
8. **输出解析** — 文本回复直接输出；工具调用进入工具执行。
9. **工具执行** — 通过 `tool_exec` / `tool_parallel` 执行，写入工具日志。
10. **循环或结束** — 工具结果注入上下文，回到步骤 7；或到达最终回复。
11. **结果持久化** — 写入 stream events、chat history、session 状态。
12. **事件发布** — 推送到 beeroom、user world 等消费方。

## 3. 三层时间尺度

```
线程 (Thread)
 └─ 用户轮次 (User Round)    ← 用户发一次输入到最终回复
 │   ├─ 模型轮次 1 (Model Round)  ← 模型一次 API 调用 + 工具执行
 │   ├─ 模型轮次 2
 │   └─ ...
 ├─ 用户轮次 2
 └─ ...
```

对应 orchestrator 中 `TurnState` 的字段：
- turn ID 与状态
- 当前模型轮次索引
- 当前工具调用批次
- 重试计数

## 4. 用户轮次流水线

一轮用户轮次经历以下阶段：

```
接入:     RequestReceived → Preflight → PromptAssembled
上下文:   ContextBuilt → ContextBudgeted → ContextPrepared
模型轮次: LLMRequested → LLMResponded → OutputParsed
          ↕ ToolCalls → ToolExecuting ──→ PromptAssembled (循环)
终态:     ResultNormalized → StreamPersisted → Completed / Failed
```

其中 `PromptAssembled → … → ToolExecuting → PromptAssembled` 是模型轮次循环。

模型返回无效工具参数时，运行时发出可持久化的 `bad_tool_call_retry`，同时告知退避时间、是否继续及下一次采用非流式请求。普通 `llm_stream_retry` 同样持久化，保证实时显示与重连补水一致。前端 canonical/reducer 统一解释重试和 `invalid_tool_call_reroute/empty_final_answer_reroute` 恢复阶段，状态栏明确显示异常原因、次数与等待时间；已有思考或工具历史不隐藏恢复提示。有效输出清除恢复态，`turn_terminal` 清理重试字段和加载条目，迟到的恢复事件不得覆盖终态。增量正文热路径仅在恢复态切换时整理工作流，避免逐片扫描历史。

## 5. Prompt 链路

### 规则

- 首轮线程初始化时确定 system prompt，之后保持稳定。
- prompt 由基础指令 + 开发者上下文 + 用户上下文 + 可用智能体列表 + 记忆快照 组装。
- prompt 组装在 orchestrator 内完成，不在 API 层手工拼。

### 排查顺序

1. 线程是否已有缓存的 prompt？
2. 是否错误地把恢复逻辑走成了重新初始化？
3. prompt.rs 是否按当前语言和状态正确装配？

## 6. Context 链路

Context 链路让长会话可持续运行：

- **history 归一化** — 格式统一、去重、角色标注
- **budget 控制** — 为 system prompt、恢复说明、观察项预留空间
- **compaction** — 历史对话压缩（`context_compactor.rs`）
- **truncation** — 硬截断保底

### 排查顺序

1. 是预算配置问题还是 compaction 逻辑问题？
2. 是 context 重注入问题还是普通 history 超载？
3. 是否错误地重复注入 memory？

## 7. Tool 链路

工具调用经过 orchestrator 的统一治理链路：

```
tool_calls.rs (解析) → tool_exec.rs (调度) → tool_parallel.rs (并行)
  → 权限检查 → 审批判定 → 执行 → 结果归一化
```

关键原则：
- 模型只能看到当前线程允许的 **工具面**，不是全部后端能力。
- 调用前检查审批、并行策略和超时。
- 执行后写入 tool_logs 和 stream events。

### 排查区分

| 现象 | 可能原因 |
| --- | --- |
| 工具不可见 | 工具面构建或模型能力过滤问题 |
| 工具被阻塞 | 审批策略、沙盒限制 |
| 工具执行失败 | 运行时错误、超时 |
| 工具结果丢失 | stream persist 异常、tool_log 不一致 |

## 8. Waiting 与 Recovery

### Waiting 类型

| 类型 | 触发条件 |
| --- | --- |
| 审批等待 | 工具调用需要用户/管理员审批 |
| 用户输入 | 智能体请求用户补充输入 |
| 子智能体 | 等待子智能体完成 |

### 队列优先级与协作让出

- `agent_tasks.priority` 是队列排序的持久化权威字段，调度顺序为 `priority DESC, retry_at, created_at, task_id`。管理员提升只作用于仍处于 `pending/retry` 的任务，领取使用数据库原子条件，重复 worker 不会执行同一任务。
- 并发已满时，管理员任务不会强杀普通任务；调度器向最早的普通运行会话发送让出请求，执行流在模型动作或工具动作边界检查请求。边界前先刷新 stream persist，再把会话锁标记为 suspended 并发出 `queue_enter(queue_state=suspended)`。
- 挂起只保存当前执行 future、模型轮次和已完成工具结果，不重新追加用户轮次，也不重复执行已完成工具。管理员任务结束后按挂起顺序授予恢复名额，恢复会话发出 `queue_start(queue_state=resumed)` 并继续原动作。
- 用户主动取消会清理排队/运行任务并写入 `queue_fail(status=cancelled)`；取消任务不会因为迟到完成回调或队列轮询再次复活。刷新通过 stream events 和 runtime snapshot 补水队列状态。
- PostgreSQL 的会话锁领取在事务中串行化，SQLite 使用 `BEGIN IMMEDIATE`；两种存储都排除 suspended 锁的活动并发计数。进程内协作调度器只协调同一进程中的运行 future，跨进程实例仍依赖持久化队列恢复。

### 恢复场景

| 场景 | 设计要求 |
| --- | --- |
| 中断恢复 | 保留 waiting 状态，不降级为重新开始 |
| 崩溃恢复 | 从 session 状态和 stream events 恢复 |
| 工具结果缺失 | 识别缺失结果，给出后续策略 |
| 上下文溢出 | 先压缩 → 再恢复 |

### 流式输出、思考与恢复

- 流式模型调用由 `orchestrator/stream_timeout.rs` 按活跃分片重置无输出等待期限，非流式调用保持整体超时。客户端队列拥塞时，WS 发送恢复信号并停止当前实时订阅的直推，后台继续排空执行流；`resume/watch` 回放不得丢弃增量。
- 思考文本立即进入 canonical projection，但使用每消息 150ms 通知时钟，只刷新思考组件。首次思考出现仍触发结构通知以挂载组件；预览限制为尾部 640 字符，完整提示按展开读取。结束和 snapshot 使用结构时钟同步最终状态。
- 解码速度的 token 与时间必须属于同一次模型响应：可见输出 token / 正文首末增量间隔。最终事件与历史统计持久化明确的 `visible_decode_*` 字段，避免长工具循环的聚合值冒充当前回复速度。
- 压缩提示由持久轮次事件重建，补水保留 terminal workflowItems，旧 transcript 合并已完成标记时按现有身份去重；不能因为存在历史工作流就恢复 streaming 标志。

### Execution Lease

线程通过 ThreadRuntime 的 lease 机制保证同一时刻只有一个 owner 在执行。

### 排查顺序

1. session 状态是否完整？
2. stream events 是否有断档？
3. waiting 状态的 request_id 是否被错误覆盖？
4. 恢复链是否把续跑错误降级成了"重新开始"？

## 9. AppState 三层装配

`src/core/state.rs` 将服务组织为三层：

| Plane | 代表字段 | 主要职责 | 关键模块 |
| --- | --- | --- | --- |
| `kernel` | `AppKernelServices` | 智能体执行、线程推进、任务编排 | `orchestrator`、`runtime/thread`、`runtime/mission`、`swarm` |
| `projection` | `AppProjectionServices` | 用户世界、beeroom 的实时视图 | `services/user_world`、`services/beeroom_realtime` |
| `control` | `AppControlServices` | presence、gateway、channels、cron、审批、命令会话 | `services/presence`、`gateway`、`channels`、`cron`、`approval_registry` |

## 10. 典型排查路径

| 现象 | 第一检查点 | 第二检查点 |
| --- | --- | --- |
| 首轮 prompt 漂移 | prompt.rs 是否重复生成 | 配置与 agent 预设是否正确 |
| 工具结果丢失 | tool_logs 状态 | stream persist 是否异常 |
| 线程一直 waiting | turn_state 字段 | 前端或 resume 调用是否匹配 |
| 恢复后状态错乱 | session 状态内容 | stream events 与 session 对齐 |
| 上下文溢出后死循环 | retry_governor 尝试计数 | compaction 是否正常触发 |

## 工具结果与上下文预算

模型 observation 使用紧凑 JSON 原生数组，展示事件保留传输元数据；外部工具字段、分页游标和异步句柄不按通用噪音删除。自动摘要前调用 `orchestrator/microcompaction.rs`，尝试精简 5 组近期工具结果之前的可重复读取结果。只有能充分降低占用才持久化并跳过摘要模型，否则原样进入摘要。诊断事件为 `progress.stage=microcompaction`，本地 token 估算不参与计费。

摘要模型输出预算最多 2048 token；UTF-8 裁剪与估算共用字节口径，逐条裁剪以差量更新预算。详细边界、保护范围和恢复策略见 [上下文压缩设计](../设计文档/上下文压缩设计.md)。

压缩后预算分配集中在 `orchestrator/memory_compaction_budget.rs`：为已选首尾交互预留可读片段，长消息共享预算，避免当前请求或单条旧消息吞掉整段历史；手动压缩不把保留的历史用户消息误识别为当前请求。压缩事件中的裁剪统计反映摘要与当前请求的实际缩减。


## 工具条目指标与输入区上下文

工具调用/结果事件携带固定的 `request_context_tokens` 与 `request_usage`，以模型请求和调用 ID 归属。后续模型轮次、压缩和配额快照不得改写已有调用的请求指标。工具处理耗时以运行时 `meta.duration_ms` 为准，缓存命中重新计时，取消时收束所有并行调用并保留已完成调用的结果；事件间隔仅作为缺少运行时耗时的历史回退。

输入区保留最近明确的上下文与容量，缺字段不清空，明确零值或较小值立即生效。统计投影记录 `contextSnapshotSeq`，压缩条目的 `updatedSeq` 之前的占用失效，之后的观测可以恢复增长，避免压缩标记永久覆盖新快照。新会话/模型切换清除显示缓存，正文流式增量不增加占用。
