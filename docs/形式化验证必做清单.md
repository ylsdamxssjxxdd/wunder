# 形式化验证必做清单

盘点日期：2026-10-26。对象：wunder 共享核心、运行时及各入口的状态契约。本清单是待办与验收要求，不是验证通过报告；列出风险不代表已经证实存在漏洞。

蛹作为本地 AI 工作台，优先保障消息不丢、执行不串、停止可信、文件不越界。舵机复用相同引擎契约；舰体的蜂巢与舰桥还需要补充多租户、远程接入和管理权限边界。证明应从核心、存储和运行时开始，再验证各端投影，不能靠界面状态修补代替执行语义。

## 3. 每项要验证什么

### 本轮新增局部证据 · 蛹目录快照状态栅栏

- 旧模型 `NativeCatalogueStatus` 的反例是：目录读取先开始，用户随后发送消息，本地已进入执行中，但旧目录快照仍返回完成；线程条目、气泡和完成通知错误地一起回到完成态。
- 修复模型把本地状态版本、提交/执行所有权和目录读取版本作为独立事实：目录快照可以更新非状态字段，但不能回退本地状态；真实本地终态由直接执行路径结算，后台线程无本地所有权时仍允许目录 `hot -> done` 通知。
- 证据归档在 `docs/设计文档/蛹与舵机状态一致性验证/native-catalogue-status/`，生产实现为 `frontend-slint/src/native_chat_status.rs`、`frontend-slint/src/native_chat.rs` 与 `frontend-slint/src/completion_notice.rs`。
- 该证据只覆盖一个线程、一次目录读取和有限通知路径；没有推出任意并发、崩溃恢复、跨进程租约或毫秒级时延保证，仍需按 FV-01、FV-03、FV-04、FV-10、FV-20 扩展。

### 本轮新增局部证据 · 执行锁代次 fencing（FV-01）

- 旧模型 `ThreadOwnership` 的两条反例：执行锁持有者心跳停顿到锁过期、被接管后，旧持有者的迟到释放删除新持有者的锁行（16 条反例），迟到心跳给新持有者的锁行续期（8 条反例）。
- 修复：`session_locks` 增加 `lock_token` 代次列，获得时颁发，touch/release 的 WHERE 带 `session_id + lock_token`；修复模型同一配置下两条规则全部通过。
- 证据归档在 `docs/技术说明书/验证记录/fv-01-thread-ownership/`，真实回归为 SQLite 双实例共享库的迟到释放/心跳隔离测试。
- 该证据只覆盖两个执行者、各 2 代的限界交错与 SQLite 真实存储；没有推出打开租约接管竞争、提交与工具派发边界校验、PostgreSQL 运行时行为或任意并发，仍需按 FV-01 剩余范围与 FV-04 扩展。

### 本轮新增局部证据 · canonical create/fork 崩溃窗口（FV-03）

- 旧模型 `CanonicalCreate` 的两条反例：create/fork 先提交目录行、后写 SessionMeta 文件头，进程在两者之间崩溃留下"目录有行、rollout 文件从未创建"的线程（3 步），随后第一次 append 惰性建文件并跳过头部校验，静默写出无头 rollout（4 步）。
- 修复：create_thread/fork_known_source 反转为文件先行（崩溃只留谱系无引用的孤儿文件），append_records 增加"目录行 ⇒ rollout 表示存在"防御（缺失即 CorruptHistory 拒绝写入）。
- 证据归档在 `docs/技术说明书/验证记录/fv-03-canonical-commit-recovery/`，真实回归为 3 个崩溃窗口测试 + storage 子树 139 项通过。
- 该证据只覆盖 1 个线程、1 次 create saga 的提交顺序；没有推出断电耐久性、多线程并发 create、flush/recover 掩盖检测或 PostgreSQL 形态（服务端单事务无此窗口），仍需按 FV-03 剩余范围扩展。

### 本轮新增局部证据 · 停止四阶段与执行结清（FV-04）

- 旧模型 `StopCancel` 复现三个真实缺陷：停止受理后 `finish_request_success` 无取消闸且丢弃持久面拒绝、仍发完成语义（4 条反例）；监视器被 flap 为 `finished` 后无人修复；尾部补写把 `finished`/`error` 终态改写为 `cancelled`。
- 修复：收尾前取消闸 + 采纳 `update_turn` 拒绝结果改按取消结清（含手动压缩同构修复）；`mark_cancelled_with_source` 终态记录不改写。
- 证据归档在 `docs/技术说明书/验证记录/fv-04-stop-cancel-settlement/`，真实回归为挂起模型、挂起工具（审批等待）、停止晚于完成三条真实链路 + 2 个修复点单元测试（9/9 通过，全量 2126 项通过）。
- 该证据限界为单执行体、单停止管线、至多一个外部命令；多执行者/子智能体树交错、kill 物理时延、token 级流式一致性未覆盖，仍需按 FV-04 剩余范围扩展。

### 本轮新增局部证据 · 消息受理幂等与崩溃结算（FV-02）

- 受理事务（查重 → 分配轮次 → 插入受理行，单 Immediate 事务）的幂等与先写者胜语义在旧模型上即成立；两条崩溃窗口规则违反：受理提交后进程崩溃留下永不结算的孤儿轮次（3920 条反例），崩溃残留的 running/cancelling 监控记录永久挡住派发闸门（640 条反例）。
- 修复：`settle_orphaned_turns_in_tx` 在 accept 事务内与桌面打开线程路径结算孤儿（落 interrupted、stop_reason=process_restart、正文保留）；派发闸门改为 running/cancelling 监控记录只在会话锁存活时作数。删除与"启动绝不清锁"契约矛盾的旧恢复模块 `desktop_runtime_recovery.rs`。
- 证据归档在 `docs/技术说明书/验证记录/fv-02-message-admission/`，真实回归为 8 个新 SQLite 测试（并发重发、丢响应重放、同键改内容、重启结算孤儿、锁活性仲裁等），定向 43 项通过。
- 该证据限界为两条客户端消息、轮次限界 2；PostgreSQL 运行时验证、stuck 任务全库清扫、蜂巢侧结算触发点未覆盖，仍需按 FV-02 剩余范围扩展。

### FV-01 · 线程打开权、执行权与过期持有者隔离

- **必须守住：** 同一任务线程不能同时有两个有效的冲突执行所有者；不同线程可以独立工作。线程打开租约与执行锁分别建模，不能把“能打开”“正在执行”“有订阅”当成同一事实。
- **必须覆盖：** 两个本地实例同时打开、心跳延迟、租约到期后接管、旧持有者恢复、迟到释放与提交。旧代持有者不能释放新代租约，也不能在交接后继续被接受为当前执行者。
- **代码入口：** `crates/wunder-runtime/src/storage/sqlite/thread_open_lease_store.rs`、`crates/wunder-runtime/src/storage/sqlite/session_lock_store.rs`、`crates/wunder-runtime/src/storage/postgres/session_lock_store.rs`、`crates/wunder-runtime/src/services/runtime/thread/runtime.rs`、`crates/wunder-cli/main.rs`。
- **验收证据：** 两个进程/执行者的接管回归；验证真实提交与工具派发边界的持有权校验，而不只是证明租约表唯一。

### FV-02 · 消息受理、重试去重与用户轮次分配

- **必须守住：** 同一幂等身份在约定作用域与保留期内只受理一次，不重复分配用户轮次；独立用户消息不能被错误合并。被确认受理的输入最终可恢复，或有可观察的明确结算，不能静默丢失。
- **必须覆盖：** 受理落库后响应丢失、重发、并发重复发送、重启、排队后取消，以及同键不同内容。先明确冲突策略与线性化点，不能以客户端隐藏重复气泡代替服务端去重。
- **代码入口：** `crates/wunder-runtime/src/storage/thread_admission.rs`、`crates/wunder-runtime/src/storage/postgres/admission_store.rs`、`crates/wunder-runtime/src/services/runtime/thread/runtime.rs`、`crates/wunder-desktop/native_queue.rs`。
- **验收证据：** 真实受理存储中的消息数、用户轮次数和执行次数断言；区分用户轮次与模型轮次，不承诺外部副作用因此天然恰好一次。

### FV-03 · canonical 提交、队列确认与崩溃恢复

- **必须守住：** 已确认持久化的事实不能在恢复中消失；队列输入不能在 canonical 首次提交前被不可恢复地丢弃；派生历史与展示头可从权威日志修复，不能发布不存在的成功提交。
- **必须覆盖：** 文件追加、同步、数据库提交、派生投影、队列确认、发布唤醒之间的每个真实崩溃点；半条记录、重复恢复、存储写失败。文件与数据库不是一个原子事务，模型不得把整条链强行合成一个不可中断动作。
- **代码入口：** `crates/wunder-runtime/src/orchestrator/thread_log_committer.rs`、`crates/wunder-runtime/src/storage/rollout.rs`、`crates/wunder-runtime/src/storage/runtime_thread_store.rs`、`crates/wunder-runtime/src/storage/canonical_thread_log.rs`、`crates/wunder-runtime/src/storage/thread_history.rs`。
- **验收证据：** 真正中断/重启后的恢复测试，验证日志、受理记录与重建投影；SQLite、启用 PostgreSQL 的对应契约分别验收。

### FV-04 · 停止、取消、超时与执行结清

- **必须守住：** 停止请求、取消已受理、执行已隔离、外部命令已结束是不同阶段。对外确认“已停止”的边界必须明确；旧执行不得再启动新动作、覆盖新执行或被迟到完成帧改为成功。
- **必须覆盖：** 停止与工具启动、最终提交、新消息、队列交接、目标后继竞争；工具不响应取消、进程树退出延迟、超时后迟到结果。不可撤销的外部副作用应明确保留“结果未知”，不虚构回滚成功。
- **代码入口：** `crates/wunder-runtime/src/services/runtime/thread/runtime.rs`、`crates/wunder-runtime/src/services/runtime/thread/child_runs.rs`、`crates/wunder-runtime/src/orchestrator/execute.rs`、`crates/wunder-runtime/src/services/tools/command_tool.rs`、`crates/wunder-desktop/native_chat_turns.rs`。
- **验收证据：** 挂起模型/工具后停止，检查后续派发、持久化与进程资源；已有气泡/工具终态模型作为子模型复用，不代替执行隔离证明。

### FV-05 · 工具审批的一次性授权与失效

- **必须守住：** 审批绑定用户、线程、执行、工具及被批准的动作内容；拒绝、取消或过期后不能产生该授权保护的副作用；重复同意最多消费一次，旧审批不能批准后继调用。
- **必须覆盖：** 同意/拒绝同时到达、同意与超时/停止竞争、断线重连、参数在审批后变化、后台线程切换，以及一次性批准与作用域批准的不同规则。
- **代码入口：** `crates/wunder-runtime/src/core/approval.rs`、`crates/wunder-runtime/src/core/approval_registry.rs`、`crates/wunder-runtime/src/core/exec_policy.rs`、`crates/wunder-runtime/src/orchestrator/tool_exec.rs`、`crates/wunder-runtime/src/services/interlink/approvals.rs`。
- **验收证据：** 在真实执行入口统计副作用次数；不能只测面板关闭或 oneshot 通道最多接收一次。

### FV-06 · 用户/租户权限、凭证轮换与撤销

- **必须守住：** 无权限主体不能读、写、订阅或控制其他作用域的资源；管理员界面确认不能替代后端授权。凭证轮换/退出/撤权后，旧权限在约定生效边界之外不能继续使用。
- **必须覆盖：** 两个用户与不同资源所有者、越权标识替换、HTTP 与长连接差异、并发 refresh、refresh 与 logout 竞争、已建立订阅的权限变更、过期缓存授权。
- **代码入口：** `crates/wunder-runtime/src/core/auth.rs`、`crates/wunder-runtime/src/services/user_access.rs`、`crates/wunder-runtime/src/services/auth_sessions.rs`、`crates/wunder-runtime/src/api/auth.rs`、`crates/wunder-runtime/src/api/admin/`、`web/modules/admin-auth.js`。
- **验收证据：** 权限关系模型加真实跨用户 API/WS 拒绝测试；明确撤销窗口，不能把“已发送强制退出消息”证明成“服务端已经拒绝旧凭证”。

### FV-07 · 工作区路径围栏与本地能力授权

- **必须守住：** 文件、命令、桌面与互通操作只能作用于被授权的根和能力；检查通过后到实际访问前的路径替换不能绕过围栏；远程输入不得隐式获得本地高权限。
- **必须覆盖：** 规范化与真实打开之间的竞态、符号链接/目录联接、路径别名、目标尚不存在、工作区切换、能力撤销、读写与移动两端的权限。
- **代码入口：** `crates/wunder-core/src/path_utils.rs`、`crates/wunder-runtime/src/services/workspace.rs`、`crates/wunder-runtime/src/services/tools/file_tool.rs`、`crates/wunder-runtime/src/services/tools/apply_patch_tool.rs`、`crates/wunder-runtime/src/services/tools/capabilities.rs`、`crates/wunder-runtime/src/sandbox/`。
- **验收证据：** 抽象授权模型加 Windows/Linux 真实文件系统竞态与沙盒测试。仅验证字符串前缀不足以证明围栏，状态图也不替代系统调用审查。

### FV-08 · 目标控制、版本竞争与自动后继

- **必须守住：** 暂停、清除、完成或预算终止后不得再派发旧目标后继；旧版本更新不能覆盖新目标；同一后继最多被有效调度一次。目标领域状态与实际执行是否已停止必须分别验证。
- **必须覆盖：** 用户与模型同时控制、编辑与完成竞争、暂停/清除与 follower 领取竞争、重启后的激活策略、旧 guard 迟到释放、不同入口并发控制。
- **代码入口：** `crates/wunder-runtime/src/services/goal/authority.rs`、`crates/wunder-runtime/src/services/goal/command.rs`、`crates/wunder-runtime/src/services/goal/driver.rs`、`crates/wunder-runtime/src/services/goal/service.rs`、`crates/wunder-runtime/src/api/chat_goal.rs`。
- **验收证据：** 扩展已有目标控制模型，补 CAS、后继交接及恢复路径；从真实 façade/API 验证暂停返回边界与后继数，保留现有未通过回归的披露。

### FV-09 · 云端与本地互通命令台账

- **必须守住：** 命令受能力和有效审批约束；重复命令在约定去重窗口内不重复产生副作用；迟到 ACK/结果不能把终态重新打开，节点身份变化不能串用旧授权。
- **必须覆盖：** 下发后 ACK 丢失、执行后回执丢失、离线排队、取消与启动竞争、服务端/本地重启、去重记录到期、审批到期与重发。
- **代码入口：** `crates/wunder-core/src/interlink.rs`、`crates/wunder-runtime/src/services/interlink/commands.rs`、`crates/wunder-runtime/src/services/interlink/client/execute.rs`、`crates/wunder-runtime/src/services/interlink/client/approval.rs`。
- **验收证据：** 双端故障注入和真实命令副作用计数。没有持久幂等或远端去重能力时，明确“不确定结果需核对”，不得承诺跨崩溃恰好一次。

### FV-10 · durable 重放、快照、唤醒与游标协议

- **必须守住：** 已应用游标只在对应数据成功应用后推进；快照 revision、历史位置与状态水位不能混用；唤醒不是事实来源；慢客户端丢弃增量后能从可信边界恢复，旧执行终态不能影响新执行。
- **必须覆盖：** 订阅建立与初读竞争、提交后唤醒、分页、重复/乱序、快照在途、历史替换、溢出、断线与重新补水，以及只有控制状态变化而正文游标不变的情形。
- **代码入口：** `crates/wunder-runtime/src/orchestrator/thread_change_hub.rs`、`crates/wunder-runtime/src/services/thread_change_feeder.rs`、`crates/wunder-runtime/src/api/ws_helpers.rs`、`crates/wunder-core/src/thread_view.rs`、`crates/wunder-runtime/src/storage/thread_view_projection.rs`。
- **验收证据：** 扩展现有状态一致性模型；在“消息最终可送达、读取最终成功、消费者持续调度”等明确假设下检查收敛，并用真实 feeder/WS 与存储恢复回放对照。

### FV-11 · 问询、等待输入与恢复消费

- **必须守住：** 打开问询工具成功不等于用户已回答；同一回答消费身份不能产生两个恢复执行；提交失败可恢复，重复旧面板不能再次消费。原等待轮次按当前轮次契约结清，新用户消息不能误算成旧轮次。
- **必须覆盖：** 双击、刷新重放、自由文本回答、回答与停止竞争、提交成功但响应丢失、旧面板重现、跨线程回答，以及“续接旧轮次”和“新建用户轮次”的不同入口。
- **代码入口：** `crates/wunder-runtime/src/services/tools/panel_tools.rs`、`crates/wunder-runtime/src/services/runtime/thread/runtime.rs`、`crates/wunder-runtime/src/storage/canonical_thread_log.rs`、`frontend-slint/src/native_chat.rs`、`crates/wunder-cli/tui/app.rs`。
- **验收证据：** 先冻结轮次与消费键契约，再从真实问询条目到回答入账、恢复执行和历史重开验证，不能只在前端隐藏面板。

### FV-12 · 线程 system prompt 冻结与一次性记忆注入

- **必须守住：** 线程首次确定的 system prompt 不被后续轮次改写；长期记忆仅初始化注入一次。工具、目标提示、工作区配置变化与恢复不能绕过冻结边界。
- **必须覆盖：** 两个初始化竞争、冻结前崩溃、冻结后重试、续跑/重开、压缩恢复、模型切换和配置变化；线程分叉的继承或重新初始化规则应显式约定。
- **代码入口：** `crates/wunder-core/src/thread_store/mod.rs`、`crates/wunder-runtime/src/orchestrator/prompt.rs`、`crates/wunder-runtime/src/storage/runtime_thread_store.rs`、`crates/wunder-runtime/src/services/memory.rs`。
- **验收证据：** 持久化冻结内容和真实模型请求 system 段的一致性检查；缓存命中率另作测量，不是此不变量的形式化结论。

### FV-13 · 上下文压缩检查点与恢复切换

- **必须守住：** 有效检查点之前不得不可恢复地删除原历史；当前用户输入只保留一次；工具调用与结果的结构关系不被切断；压缩不能改写冻结的 system prompt。
- **必须覆盖：** 摘要生成、检查点提交、历史替换、取消、重试及崩溃交错；压缩期间有新输入/工具结果；失败后回退与重启恢复使用同一历史版本。
- **代码入口：** `crates/wunder-runtime/src/orchestrator/microcompaction.rs`、`crates/wunder-runtime/src/orchestrator/memory_compaction_window.rs`、`crates/wunder-runtime/src/orchestrator/compaction_policy.rs`、`crates/wunder-runtime/src/storage/thread_history.rs`。
- **验收证据：** 检查点状态模型加真实请求消息序列/恢复回归。证明结构与提交协议，不声称能证明自然语言摘要没有语义损失；涉及不可逆删除的子路径按 P0 门槛执行。

### FV-14 · 子智能体派生、取消传播与结果回收

- **必须守住：** 派生关系与结果归属不串线程；取消树不漏掉交接中的后代，也不取消无关线程；旧子任务清理不能移除新任务；父轮结束不等于所有子任务成功。
- **必须覆盖：** 派生与父取消竞争、嵌套派生、子任务完成与重启恢复、结果重复投递、父线程关闭后的存活策略、并发和深度上限。
- **代码入口：** `crates/wunder-runtime/src/services/runtime/thread/child_runs.rs`、`crates/wunder-runtime/src/services/runtime/thread/descendants.rs`、`crates/wunder-runtime/src/services/subagents/recovery.rs`、`crates/wunder-runtime/src/services/subagents/tree.rs`。
- **验收证据：** 父子/嵌套子任务的取消与恢复测试；仅验证当前子智能体机制，不为已移除的蜂群编排重新建模。

### FV-15 · 配额、目标预算与请求计量

- **必须守住：** 并发请求不能绕过账户准入；每次实际派发按明确计量口径处理一次；本地上下文估计、供应方用量、账户扣额和目标消耗不能互相冒充。预算终止后不再调度新的目标动作。
- **必须覆盖：** 并发最后一份额度、重试、压缩请求、豁免身份、派发前后失败、统计重复重放、预算检查与后继竞争。定义已在途请求的预留/超限政策，不能宣称硬预算而不建模在途消耗。
- **代码入口：** `crates/wunder-runtime/src/orchestrator/quota.rs`、`crates/wunder-runtime/src/orchestrator/usage_accounting.rs`、`crates/wunder-runtime/src/orchestrator/request_budget.rs`、`crates/wunder-runtime/src/storage/sqlite/quota_balance_store.rs`、`crates/wunder-runtime/src/storage/postgres/quota_balance_store.rs`、`crates/wunder-runtime/src/services/goal/driver.rs`。
- **验收证据：** 真实并发准入与两类存储的计量回归；先确认当前计费/预算契约，再验证守恒和边界，不自行发明退款政策。

### FV-16 · 工具/命令生命周期与副作用重试

- **必须守住：** 一次工具调用的启动、进度、结果、取消和关闭具有稳定身份；迟到结果不串到另一调用；未报告结果不能伪造成功；非幂等副作用不能因恢复/重试被盲目重复执行。
- **必须覆盖：** 工具部分成功后异常、外部命令已启动但回执丢失、输出先于结果、结果先于展示调用、超时后迟到完成、同名工具并发、多文件操作部分提交，以及只读/可并行声明与真实副作用不符。
- **代码入口：** `crates/wunder-runtime/src/orchestrator/tool_exec.rs`、`crates/wunder-runtime/src/orchestrator/tool_parallel.rs`、`crates/wunder-runtime/src/orchestrator/tool_result_recovery.rs`、`crates/wunder-runtime/src/services/tools/command_sessions/`、`crates/wunder-runtime/src/services/tools/apply_patch_tool.rs`、`crates/wunder-cli/exec_events.rs`。
- **验收证据：** 从真实执行到日志与展示的同一调用身份回归；外部系统没有幂等保证时保留未知结果，不能用模型假设所有工具都幂等。

### FV-17 · 队列交接、背压、限流与公平性

- **必须守住：** 任务只能被一个有效消费者领取；取消/关闭不丢已承诺输入；队列、等待者、后台任务、缓存及输出缓冲均有明确边界，不能只限制队列长度却无限 spawn。公平性应注明优先级政策。
- **必须覆盖：** 交出执行权与恢复许可竞争、重复唤醒、管理员优先任务、持续生产、消费者退出、慢 UI/WS、全容量、停止时资源归还。
- **代码入口：** `crates/wunder-runtime/src/core/bounded_queue.rs`、`crates/wunder-runtime/src/services/runtime/thread/scheduling.rs`、`crates/wunder-runtime/src/orchestrator/queue_handoff.rs`、`crates/wunder-runtime/src/services/runtime/thread/queue_tasks.rs`、`crates/wunder-cli/tui/thread_registry.rs`。
- **验收证据：** 模型检查资源守恒、容量上界和有条件不饥饿；真实压力测试检查内存/任务数上界与恢复。公平假设不能把生产中允许的永久饥饿藏掉。

### FV-18 · 渠道投递与定时任务的重试消费

- **必须守住：** 入口重复投递不重复受理同一任务；出站重试不凭空标为送达；定时任务的同一次触发不会被多个调度者有效领取。渠道入站、outbox、定时触发分别建小模型，不合成一个巨型状态机。
- **必须覆盖：** 发送成功但确认丢失、投递与状态写入间崩溃、调度者切换、重启补跑、禁用/删除与领取竞争、离线和重试退避。
- **代码入口：** `crates/wunder-runtime/src/channels/inbound_queue.rs`、`crates/wunder-runtime/src/channels/service/outbox.rs`、`crates/wunder-runtime/src/services/cron.rs`、`crates/wunder-runtime/src/storage/sqlite/cron.rs`、`crates/wunder-runtime/src/storage/postgres/cron.rs`。
- **验收证据：** 真实渠道/调度存储故障注入；供应方不支持幂等时明确允许重复或需要核对的范围，不承诺端到端恰好一次。

### FV-19 · 线程回退、分叉、归档与删除

- **必须守住：** 破坏性变更与有效执行互斥或被可靠隔离；回退后的旧游标/旧写入不能复活已移除内容；分叉只继承明确边界之前的历史；清理不删除仍被引用的日志/资源。
- **必须覆盖：** 变更意图落库、日志截断/移动、索引更新、压缩表示切换之间崩溃；分叉与原线程写入、删除与补水、归档与排队、恢复重复执行。
- **代码入口：** `crates/wunder-runtime/src/storage/thread_mutation.rs`、`crates/wunder-runtime/src/storage/runtime_thread_store.rs`、`crates/wunder-runtime/src/storage/rollout_compression.rs`、`crates/wunder-runtime/src/storage/postgres/thread_fork_store.rs`、`crates/wunder-runtime/src/api/chat/sessions.rs`。
- **验收证据：** 真实文件/数据库中断恢复与重新打开，验证引用、revision、权限及旧执行拒绝；不能仅以“列表已隐藏”代表删除或归档完成。

### FV-20 · 跨线程切换及多入口投影一致性

- **必须守住：** 异步响应绑定线程、执行和页面身份；切换 A→B→A 后旧响应不能覆盖新绑定；线程条目、气泡、工具在同一权威事实下无矛盾，独立子任务按自己的身份显示。
- **必须覆盖：** 初次加载、后台完成、折叠、历史页、进行中的读取、重连、组件销毁、进程退出、终态后合法正文回执与新执行启动；不因补水强制用户跳回最新页。
- **代码入口：** `frontend-slint/src/native_chat.rs`、`frontend-slint/src/native_chat_observer.rs`、`frontend-slint/src/chat_process.rs`、`crates/wunder-cli/tui/thread_registry.rs`、`crates/wunder-cli/tui/app.rs`、`frontend/src/realtime/chat/threadViewStore.ts`、`web/modules/trajectory-model.js`。
- **验收证据：** 扩展现有状态图，使用真实 reducer/组件/renderer 消费共同事件语料；蛹、舵机、蜂巢与舰桥逐一登记，不要求界面文案完全相同，也不拿一端通过替另一端背书。

## 4. 第一批实施顺序

1. **FV-01：先证明谁有权执行。** 没有所有者和代次，停止、提交、队列交接与恢复的证明都可能建立在错误前提上。
2. **FV-02 + FV-03：再证明消息受理与落库可靠。** 先拆成小模型，再检查受理→首次提交→确认这一交接契约。
3. **FV-04 + FV-08：证明停止和目标后继不会互相穿透。** 保留已有目标控制与终态展示模型，补执行隔离和 follower 竞争。
4. **FV-05 + FV-06 + FV-07：证明执行前的权限门不会被竞态绕开。** 互通能力开放或升级时，把 FV-09 同批纳入。
5. **FV-10 + FV-20：补完整恢复和多端一致性。** 在已可靠的执行事实之上验证收敛，再处理 FV-11～FV-18；破坏性历史能力变更单独触发 FV-19 的 P0 门槛。

这个顺序是依赖排序，不允许把后续项目的安全门槛顺延到相关能力发布之后。建议每项维护独立模型，只有发现共享交接假设时才组合验证，避免一次把整个运行时塞进同一状态空间。

## 5. 每项打勾的统一验收门槛

1. **先冻结契约。** 写明状态、身份、线性化点、安全性规则、活性目标及失败策略；未知结果、不可撤销副作用和权限撤销窗口不得省略。
2. **模型可溯源。** 每个动作对应生产代码中真实原子边界，迁移条件标注文件与行号；文件 I/O、数据库提交、网络发送与 UI 应用不能随意合并成一次原子操作。明确模型范围和遗漏。
3. **不削弱规则。** 有旧问题时保留旧模型反例，使用相同规则检查修复模型。没有发现反例只代表检查范围内未发现，不得把“预期可达”的取反规则误报为缺陷。
4. **条件活性说清楚。** 需要网络最终送达、存储最终恢复、调度公平或外部工具终止时逐项注明；仅有不变量不能当作活性证明。永久失联时要求可观察的未知/失败状态，而不是假设一定成功。
5. **真实入口回归。** 将关键交错重放到实际存储、运行时、API/façade 和消费组件，不复制一份 reducer 只测模型自身。包括崩溃恢复、线程隔离、重复投递及迟到响应。
6. **覆盖实际形态与存储。** 按适用范围登记蛹、舵机、蜂巢、舰桥、SQLite、PostgreSQL；声明不适用理由。未开启 feature、零测试或静态截图都不算对应契约通过。
7. **证据可重跑。** 保存 TLA+/配置/映射、TLC 结果、编号反例 PNG 与 Mermaid、文字路径、代码检查点、真实回归及失败清单；修复后的规则通过且没有未溯源条件，才能勾选对应范围。
8. **资源与时延另测。** 先用模型检查容量和释放规则，再实测内存、任务数、吞吐与延迟分位；不得从无时钟状态图推出毫秒 SLA，也不能从有限小模型自动推出任意规模正确。

起步边界可取两个线程、两个竞争持有者、两个调用、少量队列槽位与一个以上崩溃点；这只是发现交错的最小起点，不是完备性保证。扩大边界、增加对称主体、检查公平假设或证明参数化性质后，分别记录证据强度。

## 6. 不适合用状态图替代的验证
