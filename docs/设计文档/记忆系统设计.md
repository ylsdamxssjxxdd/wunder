# 记忆系统设计

> 本册讲长期记忆的边界、不变量、理由与反例。API 手册、前端接线与存储表结构细节属于技术说明书：`docs/技术说明书/06-数据存储、工作区与配置.md`、`docs/技术说明书/07-接口、网关与渠道接入.md`。实现主体：`crates/wunder-runtime/src/services/memory_fragments.rs`、`services/memory.rs`、`services/memory_auto_extract.rs`、`orchestrator/memory.rs`、`orchestrator/prompt.rs`。

## 1. 这页解决什么问题

- 想知道「记忆什么时候、以什么形态进入模型上下文」——看 §3 注入不变量。
- 想改召回、tier 升降或提取策略——先看 §2 数据结构边界与 §5 反例。
- 想厘清记忆 / 知识库 / 工作区文件 / 站内 IM 的分工——看 §6 相邻域边界。

一句话定位：长期记忆是**跨线程存活的事实索引**，它只在线程出生时注入一次索引清单，正文由模型按需经工具拉取，新事实由轮末自动提取或模型显式写入。

## 2. 数据结构与召回边界

### 2.1 片段三层与生命周期

权威记录类型 `MemoryFragmentRecord`（`crates/wunder-core/src/storage_records.rs:718-749`）。三层内容按「注入成本」分层：

| 层 | 字段 | 用途 |
| --- | --- | --- |
| L0 | `title_l0` | 索引标题，system prompt 注入的唯一正文 |
| L1 | `summary_l1` | 一行摘要，列表与搜索命中展示 |
| L2 | `content_l2` | 完整正文，只在 `get` 时返回 |

生命周期字段：`tier`（`core` / `working` / `peripheral`，新建默认 `working`）、`status`（`active` / `superseded` / `invalidated`）、`access_count` / `hit_count`、`supersedes_memory_id` / `superseded_by_memory_id` 承接链。常量出处 `memory_fragments.rs:24-50`。

tier 判定是带门的复合规则（`memory_fragments.rs:1602-1627`），不是单阈值：`pinned` 直接视同 `core`；升 `core` 需 importance≥0.82 且（access≥10 或 hit≥4 或生命周期评分≥0.72）；落 `peripheral` 于评分<0.18，或年龄≥60 天且 access<3 且 hit<1；`working` 为其余活跃态（access≥3 或 hit≥1 或评分≥0.38 或龄≤30 天）。tier 影响排序与保留权重，**不改变注入「只给索引」的形态**。

### 2.2 作用域

记忆按 `user_id + agent_id` 双键作用域隔离；`agent_id` 缺省归入 `__default__`（`services/memory.rs:14`）。同一用户换智能体不共享片段；记忆复刻是显式操作（`api/user_memory.rs:301-348`：先清空目标作用域，再逐条生成新 `memory_id` 写入，源作用域不动）。

### 2.3 召回参数与语义通道现状

| 参数 | 值 | 出处 |
| --- | --- | --- |
| 召回默认条数 | 6 | `memory_fragments.rs:33` |
| 召回上限 | 30 | `memory_fragments.rs:35`；提示词注入用 `PROMPT_MEMORY_RECALL_LIMIT=30`（`orchestrator/memory_support.rs:18`） |
| 列表上限 | 200 | `memory_fragments.rs:34` |
| 语义召回开关 | **当前禁用**：`MEMORY_SEMANTIC_RECALL_ENABLED=false`（`memory_fragments.rs:36`） | 常量门控 |

评分召回按 lexical / freshness / importance 多维合成（semantic 通道与 embedding 缓存 `MemoryFragmentEmbeddingRecord`、命中解释 `MemoryHitRecord` 已建好但不启用）。**文档与需求描述不得把语义召回写成现行能力**；重新启用是一个常量决策，届时需复核 embedding 配置与候选/超时参数（`memory_fragments.rs:39-42`）。

### 2.4 工具面与模型侧约定

- 规范名 `记忆管理`（别名 `memory_manager` / `memory_manage`，`services/tools/catalog.rs:1178-1179`、`dispatch.rs:108`），动作枚举 `list / search / get / add / update / remove / clear`（`catalog.rs:357`）。
- `memory_id` 对模型压缩到 8 字符以内（`MODEL_MEMORY_ID_LEN=8`，`memory_fragments.rs:53`）。
- 注入块只含 `memory_id + title_l0` 与时间戳，标题行按当前语言（`build_prompt_block`，`memory_fragments.rs:825-861`）；正文必须经 `get` 取回。
- 模型输入侧有记忆召回预算（每轮 `DEFAULT_MEMORY_RECALL_BUDGET_PER_TURN`，`orchestrator/execute.rs:399-403`），防止用召回灌上下文。

## 3. 注入不变量：只在线程初始化时注入一次

这是本系统最强的约束，代码兑现点：

1. `append_memory_prompt` 的编排调用位于 `orchestrator/prompt.rs::resolve_session_prompt` 的首次初始化分支，连同初始记忆快照一起冻结，后续轮次原样复用。
2. 读取唯一来源是 canonical rollout 首条 `SessionMeta.initial_system_prompt`；`thread_store.session_meta` 命中即原样返回，不再拼装记忆。仅 `NotFound` 进入初始化，损坏或不可读会返回错误。
3. 冻结结果经 `committer.freeze_session` 写入 canonical `SessionMeta`，由线程 gate 串行化初始化。写入失败阻断本轮，后续预览与执行读取同一个冻结值，不再写入或扫描 system Item。

推论：线程存活期间，模型看到的记忆索引清单是出生那一刻的快照；新建线程才会带上新记忆。跨线程的「知道新记忆」靠模型主动 `list/search`，不靠再次注入。

压缩路径是唯一的例外性补充：摘要压缩把 fresh memory 并入 `summary_text`（见 `docs/设计文档/上下文压缩设计.md` §6）——它是消息正文，不是 system prompt，不违反本不变量。

## 4. 写入路径与读取路径分离

自动提取与注入是两条不相交的链路：

- **写路径（轮末）**：主循环产出最终回复后，`execute_tools.rs:289-298` 触发 `spawn_auto_memory_extraction`（`orchestrator/memory.rs:1806`）；该函数注释明确「严格 opt-in（按智能体 `auto_extract_enabled`），且**绝不改动当前线程冻结的 system prompt**，只写长期记忆表」；真正的提取与落库在 `services/memory_auto_extract.rs`（`MemoryAutoExtractService`，:146 起，启发式 + LLM 候选），任务台账记入 `memory_jobs`。
- **读路径（线程出生）**：`append_memory_prompt` → `recall_for_prompt_inventory`（`memory_fragments.rs:609`）。

不变量：任何写入（add、auto_extract、replicate）都不触发对存活线程 prompt 的重算或重新注入。

## 5. 反例：三个不许做的实现

### 5.1 后续轮次再次改写线程 system prompt

错误形态：每轮把最新记忆清单拼进 system。后果：前缀逐轮变化，大模型 API 的提示词缓存全量失效（成本与首 token 延迟上升），且与 AGENTS.md 快照冻结、压缩层「不追加 system」构成同一设计约束的三处违背（对照 `prompt.rs:304-305` 注释与 `docs/设计文档/上下文压缩设计.md` §4-2）。要更新认知，走工具召回或新线程。

### 5.2 更新记忆用「覆盖写」而不是 supersedes 链

错误形态：`update` 直接改写原行正文。后果：旧事实的物理消失使承接关系不可追（谁替代了谁、何时失效），召回评分与轨迹无法解释「模型为什么记得一个已经变了的事实」，复刻/迁移时也无法判断版本。正确形态：新行指旧行（`supersedes_memory_id`），旧行置 `superseded` 并回填 `superseded_by_memory_id`；作废走 `invalidated` + `invalidated_at`，状态字段保留在 `storage_records.rs:735, 742-744`。字段级修改（如改标题、置顶）允许原位更新，语义级更替必须换代。

### 5.3 把注入做成「灌正文」

错误形态：把 L2 全文拼进 system。后果：30 条上限 × 正文长度会直接挤占上下文窗口，且与「索引 + 按需 get」的分层（§2.1）矛盾——注入成本应按 L0 计。召回清单已经给出总条数与「用 `get` 取详情」的引导行（`build_prompt_block`），这是设计的一部分，不是可选项。

## 6. 相邻域边界：记忆不是什么

| 域 | 与本系统的分界 | 出处 |
| --- | --- | --- |
| 知识库 | 三型 `Literal` / `Vector` / `Ragflow`，面向**文档语料检索**（内置词面+LLM、内置向量库、外部 RAGFlow），是外部资料；记忆是**交互中沉淀的事实**。二者存储、API、工具都不同 | `services/knowledge.rs`、`services/vector_knowledge.rs`、`services/ragflow_knowledge.rs` |
| 工作区文件 | 文件是模型可读写的数据载体，不进入提示词注入链路，无召回/生命周期语义 | `services/workspace.rs` |
| 站内 IM（user_world） | `user_world_*` 表与 `/wunder/user_world/*` API 是联系人/会话/消息域，与记忆片段无任何数据或调用关系；用户世界工具已删除 | `storage/sqlite/schema.rs`、`api/user_world.rs` |
| 线程历史压缩 | 压缩改变模型输入视图；记忆跨线程存活。交汇点只有一个（§3 推论） | `docs/设计文档/上下文压缩设计.md` |

## 7. 前端面边界

| 形态 | 记忆能力 |
| --- | --- |
| 蛹 | 设置页「记忆」类目 + 专家数据记忆卡片；用户 API 直连本地引擎 |
| 蜂巢 | 设置「记忆」类目，经 `frontend/src/api/memory.ts` 调上表用户 API（该文件同样以 `__default__` 兜底缺省智能体作用域） |
| 舰桥 | **无记忆面板**（`web/modules/state.js` 中的残留标志是死条目，不在导航） |
| 舵机 | 无记忆管理界面，仅工具卡映射 |

用户 API 路由（`api/user_memory.rs:31-54`）：列表/新增 `…/memories`、详情/更新/删除 `…/memories/{memory_id}`、复刻 `…/memories/replicate`（`migrate` 复用复刻）、确认候选 `…/memories/{memory_id}/confirm`、设置 `…/memory-settings`（承载 `auto_extract_enabled`）。

## 8. 做错回哪儿查

- 「新存的记忆当前线程看不到」→ 预期行为（§3），换线程或用 `记忆管理 list/search`。
- system prompt 字节级变化 / 缓存命中骤降 → 检查是否有代码在冻结分支外调用了 `append_memory_prompt`（全仓应只有 `prompt.rs:334` 一处生产调用）。
- 召回为空但库里有 → 先查作用域（`agent_id` 是否落 `__default__`），再查 tier/评分，最后才怀疑语义（当前禁用）。
- 提取没落库 → 查该智能体 `memory-settings` 的 `auto_extract_enabled` 与 `memory_jobs` 台账。
