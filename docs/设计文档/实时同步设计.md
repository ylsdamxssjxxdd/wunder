# 实时同步设计

> 这页讲线程实时状态的**同步契约与有界性不变量**：状态如何从引擎流向前端、每一层的上限在哪、慢客户端和断线时系统承诺什么行为。
> WS 帧格式、事件字段与端点参数不在本页：见 [技术说明书 · 实时投影与通信链路](../技术说明书/04-实时投影与通信链路.md) 与 [接口、网关与渠道接入](../技术说明书/07-接口、网关与渠道接入.md)。

---

## 1. 契约形状：Snapshot + Delta + Replay

线程同步不是「推一条流」，而是一个有明确提交点的三层契约。当前实现链条按顺序是：

**1) Durable 提交先于可见。** `EventEmitter`（`crates/wunder-runtime/src/orchestrator/event_stream.rs`）emit 时**同步 commit 到持久存储**，`ThreadLogCommitter`（`thread_log_committer.rs`）每会话 gate + 事务提交后才发 cursor。任何 cursor 都指向已落库的状态——这是 Replay 能成立的前提：客户端拿着 cursor 重连，看到的不会比断线前更新，但绝不丢。

**2) 变更唤醒只是信号。** `orchestrator/thread_change_hub.rs` 的 `publish` 只携带会话号与 cursor，不携带任何状态内容，通知「该线程有新变更」；无订阅者时直接丢弃。消费者收到唤醒后自己去读持久变更。hub 丢信号不产生错误状态，只产生延迟——因为有第 1 层的 cursor 兜底。

**3) 有界消费。** 消费侧 `services/thread_change_feeder.rs` 按页读变更，页大小 200。不存在「一次唤醒全量重放」的路径（这一条是 §4 反例的正面约束）。

**4) 有界展示投影。** 大数据量线程不靠推流扛，靠写时投影 + 分页读模型（常量在 `wunder-core/src/thread_view.rs`）：聊天页 12（上限 20）、轨迹页 80（上限 100）、响应预算聊天 128KB / 轨迹 192KB、正文分块 8192 字节。投影未就绪时走源表有界窗口读（`storage/thread_view_source.rs`，clamp + budget）。

**5) HTTP 补水端点。** 断线、溢出、投影过期都降级为「重新拉 snapshot/changes」：`/wunder/chat/sessions/{id}/thread-log/changes|snapshot|events`（`api/chat/events.rs`）。补水路径与推流路径读同一份 durable 状态，两者语义等价。

**游标与幂等键**：

| 键 | 作用域 | 说明 |
| --- | --- | --- |
| `change_seq` | 线程变更流 | 单调变更序号，watch 携带它做增量起点 |
| `view_seq` | 展示读模型 | 投影行版本，前端据此判断本地投影是否过期 |
| `event_seq` | 持久流事件 | `services/stream_events.rs` 的单调 event_id（供 external_workflows、user_world） |
| `client_message_id` | 提交入口 | 发送幂等键（`orchestrator/request.rs`、`thread_log_committer.rs`），重发同键不产生重复用户轮次 |

命令生命周期通知帧（互通远程会话视图里 `type=command` 的帧，只有 kind、status、command_id，无载荷无序号）不占用幂等序号：它是观测通知而非可重放的提交，客户端归约器显式识别并原样忽略，重复状态由快照与增量帧负责。

## 2. 不变量

- **前端不是状态真相源。** 前端本地的乐观更新（气泡先行、工具卡先置 pending）只是投影；事件回压到达后必须以服务端 durable 状态为准校正。任何「前端记了、后端没记」的状态不存在。
- **单写者原则。** 每会话写线程日志的出口只有 `ThreadLogCommitter` 一个（gate + 事务）；工具、编排器、渠道都经它排队。并行写会打乱轮次分配（`accept_turn` 取 `latest_user_turn + 1`），所以这不是性能选择而是正确性约束。
- **慢客户端降级是可见事件，不是静默丢帧。** 两条可见路径（都在 `api/ws_helpers.rs`）：watch 订阅侧，出站队列剩余容量降到水位 2（`STREAM_EVENT_SLOW_CLIENT_QUEUE_WATERMARK`）即发 `stream_overflow`（携带 cursor 与 `resume_recommended: true`），随后**只断开该订阅**，WS 连接本身与其他订阅者不受害；发送/请求侧走 lossy/strict 两路，发 `slow_client` 事件（同样带 `resume_recommended: true`），且限速为 ≥3s 至多一条。客户端收到 `resume_recommended` 的义务是走 §1 第 5 步补水，而不是抱怨丢帧。
- **缓冲必须有界，且不丢字。** 事件队列 256、WS 消息上限 512 KiB、fetch 页 200，全部有界；有界队列满则报 busy（`core/bounded_queue.rs`），不允许无界堆积。但**有界的是队列，不是内容**：token 增量按帧合并、原始消息完整落库，展示层降级（截断为预览）永远不影响持久层的字完整性。流式连续性优先于富文本完整性。
- **背压分角色。** 网关对连续 3 次慢命中的节点直接踢（`gateway/mod.rs`），与线程订阅的 resume 语义不同：节点是服务面，踢了会重连注册；订阅是用户面，断了要能补水。

## 3. 各前端消费面差异

同一个契约，三种消费形状，文档与排障时不要混用：

| 前端 | 消费面 | 要点 |
| --- | --- | --- |
| 蜂巢（`frontend/`） | **只有一条 `/wunder/chat/ws`**，多路复用 connect/watch/流事件（`utils/ws.ts`、`stores/chatWatcher.ts`） | 增量事件 + `threadViewLoader` 的分页读模型（bootstrap/chat-page/search）双轨；渲染限量在虚拟窗口与 worker 侧 |
| 蜂窝（`frontend-slint/`） | **同进程原生调用**（`wunder-desktop::NativeDesktop`），不经本机 HTTP/WebSocket | 经强类型 façade 直接订阅引擎事件（`native_follow.rs` 等）；bridge 仅为既有兼容客户端保留 |
| 舵机（`crates/wunder-cli/`） | 本地执行为同进程引擎调用；云端线程的增量回显走 `/wunder/chat/ws` 的 `watch`（带 `after_change_seq` 游标，`cloud_interlink.rs:1587-1643`） | `exec --json` 的 JSONL 是另一条脚本契约（`exec_events.rs`），不是实时订阅的替代品 |

三者对「服务端推什么」没有各自特权：都只消费 §1 定义的同一组事件与投影。给某个前端加专属事件即破坏本契约。

## 4. 反例与教训

**反例一：watch 载荷写死 `after_change_seq=0`（2026-10-13 已修复）。**
展示读模型重构时曾把蜂巢 watch 载荷的 `after_change_seq` 写死为 0；服务端只有在识别到 `view_seq` 时才忽略该字段，于是不投影展示读的旧舰体退回变更流、从 0 全量重放整条线程日志——大线程直接打爆 feeder 与带宽。修复后 watch 按线程 durable 游标发送，与舵机/蜂窝口径一致。**教训泛化：客户端指定读取起点的字段，默认值必须是服务端已提交的当前头而不是零；游标口径三端必须同步。**

**反例二：发送流只靠客户端自身判终。**
提交一条消息后，若终帧（完成/错误/取消）只由触发那轮执行的前端连接负责发出，连接在工具执行期间断开时，前端的工具条目会**永远转圈**。当前语义：发送流需要**服务端补发终帧**，且流溢出时立刻为会话挂载长驻 watcher，由 watcher 而非请求连接负责后续状态落地。**教训泛化：生命周期帧的生产者必须是 durable 侧（引擎/订阅），不能是易失侧（某次请求连接）。**

**反例三：展示读模型重建无占空比限制。**
投影表重建（`services/thread_view_rebuild.rs`）若不设占空比，启动或大批量补建时会吃满 IO、拖慢首屏。当前约束：占空比 ≤1%（空闲 = 耗时×99、最小 1s，失败退避 5s→300s），且**重建不阻塞启动**——投影未就绪期间读模型自动降级到源表有界窗口（§1 第 4 步）。**教训泛化：一切后台补偿类任务要有可见的节流参数，降级路径要读同一份真相源。**
