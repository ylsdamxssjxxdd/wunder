# 工具设计

> 这页讲工具子系统的**边界、不变量与设计理由**：什么算一个工具、工具层不允许做什么、结果为什么要走两条裁剪通道。
> 参数表、具体端点与配置字段不在本页：见 [技术说明书 · 工具、技能、MCP与外部能力](../技术说明书/05-工具、技能、MCP与外部能力.md) 与 [接口、网关与渠道接入](../技术说明书/07-接口、网关与渠道接入.md)；用户视角的工具清单见 [使用说明书](../使用说明书/zh-CN/index.md)。

## 1. 两条理念在代码里的兑现形式

AGENTS.md 的定位句「对开发者来说一切都是接口，对大模型来说一切皆工具」不是口号，落实为四个机械结构：

| 兑现点 | 代码位置 | 含义 |
| --- | --- | --- |
| 统一注册 | `crates/wunder-runtime/src/services/tools/catalog.rs` | 所有工具（内置、MCP、技能、知识库、用户工具）最终都注册为同一形态的 `ToolSpec`，进入同一目录 |
| 单一分发 | `crates/wunder-runtime/src/services/tools/dispatch.rs` | 模型给出的工具名经 `resolve_tool_name` 归一后，只有一个 dispatch 入口；不存在旁路执行器 |
| 统一返回骨架 | 约定形态见 `crates/wunder-runtime/src/services/tools/mcp_pack.rs` 的 `package_success` | 工具层约定返回 `ok/action/state/summary/data` 骨架；编排层把它收敛为 `ToolResultPayload`（`ok/data/error/meta`，`orchestrator/tool_result_payload.rs`），业务失败识别在 `orchestrator/result_normalizer.rs` |
| 错误元数据 | `crates/wunder-runtime/src/services/tools/tool_error.rs`（`ToolErrorMeta` / `with_error_meta`） | 失败结果在 `data` 内携带 `error_meta`（`code`/`retryable` 等），`result_normalizer` 优先读取；大模型据 `summary` 决策、据 `data` 取数、据 `error_meta` 重试或改道；调用方不需要理解每种工具各自的失败形态 |

由此推出的开发约束：**新增能力的第一动作是注册一个 ToolSpec，而不是新增一条协议、一个专用端点或一段提示词约定**。外部服务（MCP、RAGFlow、extra_mcp 的 Python 服务）全部折叠成工具进入同一目录，正是「一切都是接口」的落点——接入协议可以各异，模型侧看到的注册、调用与返回形态一致。

## 2. 动态注册四类与别名优先路由

除静态内置工具外，注册面在运行时按配置与用户数据动态展开（`catalog.rs`、`dispatch.rs:29-44`）：

1. **MCP 单工具**：`server@tool` 命名，重名冲突加后缀哈希；
2. **MCP 打包折叠**：配置 `packaged: true` 的服务器折叠为单工具 `server@__mcp_pack__`，动作为 list/get/call（`services/tools/mcp_pack.rs`）；
3. **技能名**：技能名本身即工具名，可直接被调用；`技能调用` 工具另承担读取技能正文与 `{{SKILL_ROOT}}` 路径替换（`services/skills.rs`）；
4. **知识库名**：按库动态注册（取代旧的单一 `knowledge` 工具），知识库名即工具名。

**路由优先级不变量**：dispatch 最优先按**用户工具别名**路由（`UserToolBindings.alias_map`，`dispatch.rs:29-33`），其后才是规范名/英文别名归一（如 `programmatic_tool_call` → `ptc`）。别名是用户面（`/wunder/user_tools/*`）与模型面之间的解耦层：用户可以改别名而不改底层工具实现。

**工具/技能/能力三层不是一回事**：工具是执行体，技能是「可调用知识 + 脚本」的打包形态（目录 + `SKILL.md` + 入口脚本），能力（abilities，`source = builtin | mcp | skill | knowledge | user_* | shared`）是管理员治理面的选择单元。治理面按能力勾选，执行面按工具名分发，两者经 `services/agent_abilities.rs` 衔接。

## 3. 分层不变量（工具层禁止事项）

以下三条是硬边界，评审新工具时逐条对照：

- **工具实现不得自己发起模型调用。** 模型调用只属于编排层主循环（`orchestrator/execute.rs`）。工具内需要「再问一次模型」的，一律表达为返回结果让主循环决定下一轮，否则轮次统计、配额扣减、重试治理（`quota.rs`、`retry_governor.rs`、`stream_timeout.rs`）全部失效。
- **工具实现不得绕过审批与超时治理。** 审批按 ToolKind（`Read | Write | Exec | Control`）分档归档（`core/approval_registry.rs`），批准缓存 600s（`core/exec_policy.rs` 的 `APPROVAL_CACHE_TTL_S`）；执行策略三态 Allow/Audit/Enforce（`wunder-core/src/exec_policy.rs`）；工具执行超时默认 120s、下限 1s（`orchestrator/constants.rs` 的 `DEFAULT_TOOL_TIMEOUT_S`）。工具自开子进程或自拼「确认后直连」的旁路，等于架空 `security.allow_commands/allow_paths` 与执行策略。
- **工具不得直接写线程日志。** 线程日志唯一写出口是 `ThreadLogCommitter`（`orchestrator/thread_log_committer.rs`，每会话 gate + 事务提交后才发 cursor）。工具想让用户看见中间状态，只能经事件发射器（`orchestrator/event_stream.rs` 的 `EventEmitter`）发出，由提交链落库——这保证「durable 先于可见」，见 [实时同步设计](实时同步设计.md)。

**并行与独占语义**：工具执行编排先做并行判定（`execute_tools.rs:388`），并行白名单（`orchestrator/tool_parallel.rs`）内的读类工具取 RwLock 读锁并发执行，写/执行/控制类取写锁独占；并行度上限 4（`resolve_tool_parallelism`，`execute_support.rs:429`、`constants.rs:39`）。设计新工具时先自问属于哪一档：给读类工具加写语义会直接造成同轮数据竞争，给写类工具申请并行则破坏「单写者」不变量。

**描述与返回的设计原则落点**：AGENTS.md 要求「工具描述要详细、减少歧义、方便模型调用；结果要精简、节省上下文」。落点在两处：ToolSpec 的 description 字段是模型唯一的选型依据，须写清适用与不适用场景（如 `文本编辑` 一工具含替换/补丁/子命令三形态，描述里必须分辨）；返回侧由统一裁剪通道兜底（见 §5），但**工具自身仍应返回摘要级 `summary` + 定向 `data`，不要把全量结果塞进 `data` 指望裁剪层救场**。

## 4. 命名口径

规范名是中文（`计划面板`、`问询面板`、`执行命令`、`读取文件`、`文本编辑`、`技能调用`、`记忆管理`、`定时任务` 等，权威清单在 `catalog.rs` / `dispatch.rs:57-110`），英文别名经 `resolve_tool_name` 归一。文档与 UI 引用工具时必须写「规范名 + 别名」，不要只写英文名——模型侧看到的名字大多就是中文规范名。

两个易错特例：

- **浏览器是单一工具**：启用后模型只调用严格的 `browser(action=...)`；每个 action 独立限制字段、必填项与互斥条件，用户侧「浏览器」仍是同一能力的聚合展示名（`services/browser/providers/playwright.rs`、`services/tools/browser_tool.rs`）。
- **`goal` 工具**（`action=get|create|edit|pause|resume|complete|blocked`）对桌面端不开放勾选，由运行时按会话自动注入，权威靠宿主盖章 `__source=human`（`services/goal/tools.rs`、`default_tool_profile.rs`）。

## 5. 两条裁剪通道必须分离

工具结果离开工具层后走**两条互不相干的通道**：

| 通道 | 位置 | 语义 |
| --- | --- | --- |
| 展示通道 | `services/tool_result_display.rs` | 只影响客户端展示：preview 截 2400 字符 / 16 行，原文完整落库 |
| 模型输入通道 | `finalize_tool_result`（`orchestrator/execute_tools.rs:741`）+ microcompaction + model_observation | 决定模型下一轮真正看到什么：头尾各 10000 字符、数组/分页限量（`orchestrator/constants.rs:41-50`），旧的可复现观测被 microcompaction 缩成 768B 预览 |

**为什么必须分离**：两者的裁剪目标是冲突的。展示层要「用户少刷屏但可补水看全文」；模型层要「上下文预算可控且缓存前缀稳定」。如果共用一条通道，要么客户端丢内容（用户看到的结果被上下文裁剪污染），要么每次上下文压缩都改写历史展示。分离后的不变量是：**原始结果永远完整持久化，两条通道各自做有界投影**。细化见 [技术说明书 · 工具结果裁剪与观测链路](../技术说明书/11-工具结果裁剪与观测链路.md)。

## 6. 当前工具面口径：临时下架 ≠ 已删除

这一节纠正旧文档的两类口径错误。

**临时下架（代码保留、对模型与用户不可见，恢复即移除隐藏条目）**——`TEMPORARILY_HIDDEN_TOOL_NAMES`（`services/default_tool_profile.rs`）：

- `ptc`：dispatch 分支与注册都在，仅被隐藏列表挡掉；
- `网页搜索`：`catalog.rs` 仍注册、`dispatch.rs` 仍有分支。

写成「已移除」是错的；正确表述是「当前临时下架」。

**已删除（不得出现在任何现存能力描述里）**：`a2ui`、渠道工具、`a2a_*` 系列、`final_response`（只在虚拟回放里判终，`execute_support.rs`）、LSP 查询/节点调用工具、用户世界工具（`user_world` 只剩内部服务与站内 IM 域，无 dispatch 分支）。

**已合并/改名**：`apply_patch` 已并入 `文本编辑`（替换/补丁/子命令三形态）；独立「休眠等待」工具已删，现语义是 `会话让出`。

默认工具集与分档（桌面额外默认、vision 门槛、多模态四件套的模型可用性门槛）以 `default_tool_profile.rs` 为准，清单表放技术说明书 05 章，本页不复述。

## 7. 反例

**反例一：把外部服务做成「专用提示词约定」而不做成工具。**
曾有过把外部能力写成提示词里的一段调用约定的诱惑——改动小、不用写 dispatch。它同时破坏三条不变量：模型输出没有 ToolSpec 约束，参数形态不可校验（`tool_args.rs` 的修复通道也接不上）；执行不进审批/超时/并行治理，等于给旁路开门；结果不经 `ToolResultPayload`，两条裁剪通道与错误包络全部失效，用量统计和重试治理也看不见它。**判据：只要模型需要在运行时决定「做不做、何时做、参数是什么」，它就必须是工具。** 提示词只负责描述意图，不负责承载执行协议。

**反例二：把展示投影和模型输入合成一条裁剪。**
见 §5：一条通道服务两种预算，结果是互相牵制——上下文压缩改写用户可见历史，或者展示截断把模型需要的数据裁掉。此外 LLM 历史压缩（`services/history.rs` 的 auto-compact）与 UI 分页（`thread_view.rs`）也同理不同域：一个是模型输入预算，一个是展示读模型预算，都不许借对方的机制。
