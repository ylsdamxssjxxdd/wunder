# 接入、网关与渠道系统设计

> 约束范围：本册约束接入面的统一性（所有入口共享同一执行核心）、gateway 作为 Hub 的定位、渠道适配器的分级与能力声明纪律、互通隧道的拓扑与风险分层审批、对外集成面的真实边界。端点与路由清单见 `../技术说明书/07-接口、网关与渠道接入.md`，本册不复述。

## 1. 接入面统一（不变量）

所有入口共享同一执行核心（`ThreadRuntime::submit_user_request` → orchestrator，见 `02-智能体核心设计.md`），接入层只做协议转换、鉴权与路由：

| 接入面 | 形态 | 传输 |
| --- | --- | --- |
| HTTP API | 业务与管理入口，前缀 `/wunder/*` | REST |
| WebSocket ×6 | 线程运行时主通道 `/wunder/chat/ws`、core 请求面 `/wunder/ws`、网关 `/wunder/gateway/ws`、互通节点 `/wunder/interlink/ws`、互通远端旁观 `/wunder/interlink/remote_ws`、世界与 LAN `/wunder/user_world/ws`、`/wunder/desktop/lan/ws` | WS |
| 渠道 webhook | 外部 IM 平台回调 | HTTP + 平台签名校验 |
| MCP 端点 | 内置 streamable-http 服务端 | HTTP |
| 外部工作流 | `/wunder/external/workflow*`，SSE 流式 | HTTP/SSE |
| Desktop 原生 | 蛹同进程调用，不经网络 | in-process |
| Desktop bridge | 仅为既有兼容客户端保留的本机 HTTP/WS | 兼容层 |

路由组装只有两面：舰体 `build_router` 与 bridge 用的 `build_desktop_router`（`api/mod.rs:52/:100`）。不变量：**新入口必须复用同一线程运行时与投影语义**，不得自带状态机；渠道/互通/A2A 之类「第二执行平面」是禁止项。API 层保持薄：鉴权、校验、转发、包络（错误包络唯一定义 `api/errors.rs`），不承载业务逻辑。

## 2. Gateway 是 Hub，不是 HTTP 网关（边界纠偏）

`gateway/mod.rs` 的实际语义是**接入注册表 + 定向 RPC + presence 广播的 Hub**：

| 对象 | 语义 |
| --- | --- |
| `GatewayRole { Operator, Node, Channel }` | 三类接入角色，握手时定角色、定路由所有权 |
| pending invoke 关联 | 定向 RPC 的请求—响应配对，网关不解析业务 |
| presence 快照与广播 | 连接态可观测出口（管理面 `gateway/presence`） |
| 协议版本 + 消息上限 + 健康检查 + 慢客户端阈值 | 连续 3 次慢命中踢除，保护 Hub 自身 |

唯一传输层是 `/wunder/gateway/ws`。它**不做** HTTP 反向代理、不做路径路由。把它写成「API 网关」是分类错误：HTTP 面的治理在 `api/*` 与中间件，gateway 面治理的是长连接角色与定向调用。

## 3. 渠道：分级现实与显式能力声明

渠道契约是 `channels/adapter.rs:29 ChannelAdapter{verify_inbound, parse_inbound, send_outbound, health_check}`。适配器必须按完成度分级如实声明能力——**能力声明要显式、可观测**是本册第一纪律：

| 级别 | 成员（实测 `registry.rs:63-71`、`service.rs:232-245`） | 含义 |
| --- | --- | --- |
| adapter + 长连接 supervisor（4） | feishu、qqbot、weixin（iLink 长轮询）、xmpp | 出入站完整链路 |
| adapter、webhook-only | wechat、wechat_mp、whatsapp_cloud | 无 supervisor，被动收信 |
| feature-gated stub | xmpp：默认 feature 关闭时所有出入站返回 `xmpp feature is disabled` | 注册了但明示不可用，不静默 |
| 无 adapter 的目录项 | telegram、discord、slack、LINE、DingTalk：仅 `catalog.rs` 中 `webhook_mode:"generic"` 条目 | **不是已支持渠道**，任何文档不得写成支持 |

默认注册 adapter 共 7 个（whatsapp_cloud、feishu、qqbot、wechat、wechat_mp、weixin、xmpp）。

渠道侧其余不变量：

- 适配器只做协议转换，**不复制智能体引擎**；入站最终落到同一提交链。
- 绑定路由按特异性打分（`binding.rs:16`：peer_id > peer_kind > account > channel，支持 `*` 通配）；工作区映射独立（`workspace_routing.rs`）。
- 入站有界队列（容量、并发、入队超时全为有界常量）+ 出站持久 outbox + 指数退避 + 令牌桶限流。任何一项去界即验收失败。
- webhook 校验按平台形态区分（verify_token、HMAC 签名、企业微信加密签名），校验失败拒绝且不降级。

## 4. 互通（interlink）：单隧道三平面 + 风险分层

拓扑不变量：**本地节点只出不入**。节点不开任何监听端口，启动一条 WSS（`/wunder/interlink/ws`）承载全部平面（`services/interlink/client/mod.rs:1-16`）：影子投影平面（shadow_full/shadow_delta）、命令执行平面（command/ack/event/result）、控制与事件平面（hello/ping/event/error/close）。协议帧、能力常量、审计事件集中在 `wunder-core/src/interlink.rs`。

风险分层与安全口径（L0–L3）：

| 规则 | 依据 |
| --- | ---|
| `tool.exec` / `agent.spawn` 属 L3；默认设备能力集**不含 L3** | `default_device_capabilities`（`interlink.rs:74-75`） |
| 节点按构建与平台声明能力：win7 构建不声明 `tool.exec`，无线程运行时不声明 `agent.spawn` | 能力集是构建事实，不是运行期开关 |
| 越集命令在本地 preflight 直接拒绝，不等云端下发执行 | 节点是最终执法者 |
| L3 审批**不可记忆**，只有 L1 票可 remember | `services/interlink/approvals.rs:63`、测试 `only_l1_tickets_can_be_remembered:154` |
| 待批队列有界（5），过期票按调用方时钟清理 | 防审批堆积 |
| 执行只回摘要（exit_code、超时标记、stdout/stderr 头部 + 字节数 + sha256），且受 `security.allow_commands` 约束 | 不把本地全文外泄，且本地策略最终裁决 |
| **云端目标在准入阶段即按越集拒绝** | 云端节点不满足「有人类审批面」前提：L3 依赖设备端人类确认，云端没有这个面 |
| 影子落库有 stale_channel 门禁；策略变更即拆隧道 | 投影与通道一致性 |
| 告警签名密钥只从环境变量取（理由见 `12-安全-权限与隔离设计.md`） | 配置会回显给管理面 |

## 5. 对外集成的真实边界（A2A 纠错）

- **A2A 当前没有任何实现**：`crates/` 全量 Rust grep `a2a|agent2agent` 零命中（已实测）。旧文档中的「A2A 互操作标准」「a2a_* 工具」必须删除；舰桥残留的「a2a 工具分组」文案读的是后端不返回的字段，属幽灵 UI（记录在 `10-管理员侧与运营后台设计.md`）。
- 对外集成面只有三个真实存在的东西：**外部工作流**（SSE、事件分页有界、上传限额）、**MCP 端点**、**渠道 webhook**。
- 身份口径：注册用户身份、线程归属身份、接入角色身份（operator/node/channel）、设备节点身份四类可关联、不可混同；`/wunder` 传入的 user 标识只决定线程归属，不自动等同后台账户。

## 6. 反例与缺口

| 项 | 现状 | 性质 |
| --- | --- | --- |
| 旧文档把渠道列为「飞书、微信、QQ、XMPP、WhatsApp、Telegram、Discord、Slack、LINE、DingTalk 等」 | 后四个没有 adapter | 已纠正，见第 3 节分级表 |
| gateway 被描述为统一 HTTP 接入层 | 实际是 WS Hub | 已纠正，见第 2 节 |
| 互通治理面板 | 后端 API only，舰桥无面板 | 归 `10` 册记录 |
| bridge | 仅兼容层，`lib.rs` 不导出，新客户端不得接入 | 保持边界 |
| 渠道 supervisor 完成度不均 | wechat/wechat_mp/whatsapp_cloud 为部分实现 | 文档按分级表表述 |

## 7. 验收判据

- 任一新入口（HTTP、WS、渠道、互通、外部工作流）的提交都能追踪到同一条 `submit_user_request → orchestrator` 主链，无私有状态机。
- 渠道能力清单与 registry/supervisor/feature 三层现实一致；无 adapter 的目录项在任何用户文档中不出现在「支持」列表。
- 互通命令在能力集外的路径 100% 本地拒绝并有审计；L3 审批无法被 remember 绕过（负向验证：尝试记忆 L3 票应失败）。
- 全仓文档不再出现 A2A 作为现有能力的表述。
