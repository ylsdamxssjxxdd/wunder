# 可观测性设计

## 1. 文档定位

这页定义 wunder 可观测性的**三支柱职责边界**、**设计不变量**与**当前缺口**。回答「什么该被观测、观测面该长在哪、边界在哪里」；不回答「阈值是多少、端点有哪些」——后者是阈值手册，归技术说明书第 10 章（[../技术说明书/10-运维、排障与验收.md](../技术说明书/10-运维、排障与验收.md)）与第 11 章（[../技术说明书/11-工具结果裁剪与观测链路.md](../技术说明书/11-工具结果裁剪与观测链路.md)），本页不复述清单。

## 2. 三支柱与职责边界

| 支柱 | 载体 | 主要回答 | 有界语义 |
| --- | --- | --- | --- |
| **日志** | 控制台彩色层 + JSONL 文件层（daily rolling，基名 `server.jsonl`） | 发生过什么、按 `trace_id` 串联细节 | 目录由 `observability.server_log_dir` 指定，默认 `./config/data/logs/server`（`core/logging.rs:25-27,162-178`）；**保留期默认 0 = 永不清理**（`wunder-core/src/config.rs:1943-1945`、`core/logging.rs:308-311`），清理是运维职责不是系统职责 |
| **指标** | 进程内运行指标 + 告警阈值 | 现在系统整体怎么样、是否越线 | blocking / queues / long_tasks / loop_ticks 四类计数 + alerts + thresholds（`core/runtime_metrics.rs:13-18`）；超时命中先出 critical，仅越过延迟阈值才 warning（回归测试 `blocking_timeout_alert_is_critical_before_latency_warning`，`runtime_metrics.rs:797-827`） |
| **线程轨迹** | durable 台账 + 有界展示投影 | 这条线程怎么走到现在的 | 取代旧「线程日志对话框」；投影分页与响应预算有硬上限（口径见技术说明书第 4/10 章） |

日志支柱的形态边界（均有代码出处，纠正旧文两处硬错误）：

- `server_mode=sandbox` 时**不落文件**，只有控制台层（`should_persist_server_logs`，`core/logging.rs:275`）。
- 保留期默认 **0（永不清理）**：清理函数对 `retention_days == 0` 直接返回（`core/logging.rs:308-311`），默认值在 `crates/wunder-core/src/config.rs:1943-1945`；旧文档写「默认保留 14 天」是错的。
- 级别默认 `info`，`RUST_LOG` 可覆盖，内置对噪声依赖的降噪指令（`core/logging.rs:243-259`）。
- 舵机进程默认 `warn` 且仅装控制台订阅器（`crates/wunder-cli/main.rs:114-117`）；desktop bridge 同为控制台层——文件层是舰体形态的职责。
- WS 连接日志带独立 target `wunder.ws`，覆盖 open/ready/handshake/handshake_error/message/parse_error/close（`api/ws_log.rs:37-171`）。

## 3. 设计原则（不变量）

### 3.1 观测面必须有界，且不反噬主链

观测的任何一层都不允许成为执行链的容量瓶颈或延迟来源：

- 读观测数据优先读**内存快照**，回退源表时也走有界窗口（`services/chat_runtime_projection.rs`、`storage/thread_view_source.rs`）。
- 渠道运行日志是**内存环形 300 条 + 20s 洪泛去重窗**（`channels/service.rs:78-79,212-213`），不是全量落库；要长期留存请导文件日志，不要在渠道面堆表。
- 后台投影重建有占空比上限（≤1%，`services/thread_view_rebuild.rs:36-45`），观测重建不能挤占执行。
- 实时事件在 emit 时持发送锁同步 commit 到 durable（`orchestrator/event_stream.rs:160-205`），唤醒信号（`orchestrator/thread_change_hub.rs`）只是通知不含载荷——**事实与信号分离**，信号丢了可以补水，事实不丢。

### 3.2 慢客户端与降级必须可见

降级永不静默：写队列超水位（`STREAM_EVENT_SLOW_CLIENT_QUEUE_WATERMARK=2`）后按 ≥3s 间隔发 `slow_client`，仍跟不上发 `resume_recommended`，最后断开该订阅（`orchestrator/constants.rs:32-33`、`api/ws_helpers.rs:710-768,884`）；网关对连续 3 次慢命中同样踢除（`gateway/mod.rs:24,358-366`）。被踢的客户端凭游标走 HTTP 补水端点重放，这正是「展示从属于事实」的落点：传输层丢弃的是推送，不是历史。

### 3.3 错误必须可串联

所有 API 错误走统一包络 `{ok:false, error:{code, message, status, hint, trace_id, timestamp}, detail:{}}`，同时回写响应头 `x-trace-id` 与 `x-error-code`（`api/errors.rs:132-160`）。排障动线由此固定：包络拿 `trace_id` → 文件日志 grep → 线程轨迹定位轮次。口径不一致的错误展示（只弹窗无码、只打日志无 trace）视为回归。

### 3.4 裁剪分层且各层留痕

工具结果有两条互不相干的裁剪通道：**展示通道**（`services/tool_result_display.rs`，只影响客户端渲染）与**模型输入通道**（`finalize_tool_result`，`orchestrator/execute_tools.rs:741` + microcompaction，影响模型所见）。观测排障必须先问「看的是哪一层的事实」：停留在展示裁剪后的文本上判断「模型没看到」是经典误诊。通道的完整定义与阈值归技术说明书第 11 章。

### 3.5 聚合视图不是原始事实

监控面板、用量摘要、presence 都是投影；权威数据源分别是 durable 线程日志、账户存储与进程状态。前端可以重组表达，不能反向定义后端真相。

## 4. 观测面分工

| 观测面 | 回答的问题 | 不承担 |
| --- | --- | --- |
| 聊天页 / 工作过程折叠 | 当前这一轮正在怎么运行 | 全局统计 |
| 线程轨迹（durable + 投影） | 单线程完整过程、轮次终态、失败可追溯 | 运维总览 |
| 舰桥监控（`/wunder/admin/monitor`，七态 running/waiting/queued/finished/error/cancelled/cancelling，`ops/monitor.rs:695-701`） | 系统负载、活跃线程、按会话导出 | 最细流式细节 |
| 吞吐与性能采样（`ops/throughput.rs`、`ops/performance.rs`） | 延迟、吞吐、是否退化 | 线上线程排障 |
| 渠道运行日志（用户面 `/wunder/channels/runtime_logs[/probe]`、管理面 `/wunder/admin/channels/runtime_logs[/probe]`） | 渠道连接与消息的近况 | 长期留存（环形 300 条） |
| JSONL 文件日志 / 舵机 | 离线排障、脚本消费、trace 串联 | 富交互展示 |

旧文中的 `/wunder/admin/channel/runtime/probe` 不存在，正确路径以上表为准。

## 5. 多执行体（子智能体）的观测要求

子智能体让一个任务内出现多个执行体，观测面必须额外满足：派生与回收可见、执行进度可见、汇总与终态可见、可从主线程跳到子智能体会话。投影层对单行子智能体卡片设数量上限（`MAX_ROW_SUBAGENTS=8`，`storage/thread_view_projection.rs:144`），超限折叠而非撑爆行——这是「有界」原则在复合场景的具体化。忌两种极端：只见汇总不见分工；只见列表不见当前动作。

## 6. 当前缺口（如实记录）

1. **互通治理面板后端 only**：互通的舰队/通道/命令/审计/策略治理有完整 API（`api/admin_interlink.rs`），但舰桥无 interlink 面板——`web/modules/` 下没有对应模块，仅 `web/modules/state.js:26` 残留 `panelLoaded.interlink` 死标志。写「舰桥互通治理面板」即为幻觉。
2. **舰桥无长期记忆面板、无 goal 界面**：`web/modules/state.js:25` 的 `memory` 同为死标志，且无 goal 相关模块；目标态治理只能走后端 API（见目标态系统设计）。
3. **`/wunder/throughput/ws` 设计性豁免 admin 门**：靠守卫路由签发的单次 ticket 鉴权（`api/admin/throughput_admin.rs:22-29`、`wunder-core/src/auth.rs:1-5`），是刻意设计，但意味着该通道的安全边界与常规 admin 面不同口径，评审新通道时不得援引为先例。
4. **线程渲染压测端点属用户面**：`POST /wunder/chat/stress-threads`（`api/chat/stress.rs:17-25`）不在 admin 门后，单 job 生成上限很高（600 万条量级，`storage/stress_model.rs`），暴露面与配额治理是待议工程项。
5. 沙箱 HTTP 服务自身无鉴权，依赖网络边界（安全设计页管辖，此处仅提示它同样影响观测链路的可信度）。

## 7. 与测试/验收的关系（只写原则）

- **同环境同入口前后对比**：性能结论只在同一标准入口表内可比（`docs/性能标准.md` 口径）。
- **三形态独立评分，不可跨形态相加**：蛹、蜂巢/舰体、舵机各按 `docs/性能评分体系.md` 独立 0–100 加权。
- **测试真实位置在 `crates/*/tests`**（如 `session_goal_storage.rs`、`cron_lease.rs`、`throughput_model.rs`、`gateway_regression.rs`），仓库根 `tests/` 只剩遗留脚本；新回归一律写进所属 crate。
- **负向验证**：宣称「某观测/筛选已生效」前，把修复改回旧写法跑一次，确认断言真会失败。

验收脚本清单、基准数值与压测参数归技术说明书第 10 章与第 13 章，本页不复制。

## 8. 推荐排障路径

| 问题类型 | 第一观察面 | 第二观察面 | 第三观察面 |
| --- | --- | --- | --- |
| 单线程异常 | 线程轨迹 | JSONL 日志（trace_id） | 调试导出（`/wunder/admin/monitor` 按会话 thread-log export） |
| 工具异常 | 线程轨迹工具批次 | 模型输入通道裁剪后观测 | 服务日志 |
| 渠道异常 | 渠道运行日志（环形 300） | JSONL 日志 | 重连端点探活 |
| 压缩异常 | 线程轨迹压缩条目 | 上下文占用观测（只信 provider 观测 input） | 服务日志 |
| 系统压力 | 运行指标（blocking/queues/long_tasks/loop_ticks） | 吞吐评测 | 服务日志 |
| 慢客户端/断流 | WS 事件序列 `slow_client`→`resume_recommended` | 补水端点重放验证 | `wunder.ws` 日志 |
