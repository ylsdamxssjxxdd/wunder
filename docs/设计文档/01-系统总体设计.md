# 系统总体设计

> 本册约束一类改动：**跨形态的分层归属**——新能力落在哪个 crate、哪个平面、哪种运行形态启用，以及「形态差异只允许出现在接入层」这条边界。改 `AppState` 装配、存储契约、形态入口或新增可执行目标时先读本册。命令、端口、启动参数与目录清单在 [`../技术说明书/02-仓库结构与模块职责.md`](../技术说明书/02-仓库结构与模块职责.md)、[`../技术说明书/08-部署、启动与运行模式.md`](../技术说明书/08-部署、启动与运行模式.md)。

## 1. 设计目标

- wunder 是什么、不是什么。
- 四个形态如何共享同一引擎，而不是各自长成一套系统。
- 核心模块如何分层、装配、协作、演进。
- 后续改动应落在哪里，哪些改动必须先收口边界。

一句话概括主架构：**请求进入某个接入面 → 同一个线程运行时准入 → 同一个 orchestrator 执行 → durable 结果与游标 → 有界展示投影 → 消费者呈现**。

## 2. 分层：核心 → 引擎 → 形态

wunder 不是「一个带聊天界面的模型调用器」，而是以 orchestrator 为核心的智能体运行时。真实分层只有两级依赖，形态层之上再接入面。

| 层 | 位置 | 承载 | 不许承载 |
| --- | --- | --- | --- |
| 核心 | `crates/wunder-core/`（仅 lib） | 配置与加载优先级、鉴权原语、存储契约与记录类型、路径围栏、执行策略、互通契约常量、展示分页常量 | 任何异步运行时循环、任何形态专属逻辑 |
| 引擎 | `crates/wunder-runtime/`（lib + 一个可选 bin） | `orchestrator/`（执行主链）、`services/`（线程运行时、工具、记忆、知识、工作区、渠道、互通、goal、cron…）、`api/`（HTTP/WS 路由装配）、`storage/`（双后端实现）、`gateway/`、`channels/`、`core/`（AppState 装配、日志、指标、审批登记表）、`ops/`（监控、吞吐、压测） | 直接依赖某个形态的前端或桌面系统能力 |
| 形态 | `crates/wunder-server/`（bin）、`crates/wunder-desktop/`（lib + 兼容 bridge bin）、`crates/wunder-cli/`（bin） | 入口组装、进程模型、本机能力、静态挂载、启动期配置覆盖 | 第二套执行链、第二套存储实现、自备终态判定 |
| 消费者 | `frontend/`（蜂巢）、`frontend-slint/`（蛹）、`web/`（舰桥）、TUI（舵机） | 呈现、交互、本地 optimistic 与恢复 | 定义后端真相、推导线程终态 |

依赖方向恒为 `形态 → 引擎 → 核心`；引擎不反向依赖形态。`crates/wunder-runtime` 的库名沿用历史标识，属事实细节，不作为设计口径。

### 2.1 形态与前端对应

| 形态 | 可执行 | 前端 | 与引擎的连接方式 |
| --- | --- | --- | --- |
| 舰体 | `crates/wunder-server/` | 舰桥 `web/`（由舰体静态挂载）、蜂巢 `frontend/`（构建产物由独立静态服务器下发） | 引擎即进程内 |
| 蜂巢 | 无独立进程 | `frontend/` | 只走舰体的 HTTP/WS 接口 |
| 蛹 | `frontend-slint/`（可执行目标） | `frontend-slint/`（Rust + Slint） | **同进程原生调用**引擎 façade，不经本机 HTTP/WebSocket，不拉起 bridge 子进程 |
| 舵机 | `crates/wunder-cli/` | ratatui TUI（非 TTY 降级为一次性执行） | 同进程内嵌 `AppState` |

独立 bridge 仅为已有兼容客户端保留，不是蛹的默认路径，也不是新能力的接入点。

## 3. 装配锚点与三平面

后端唯一装配锚点是 `crates/wunder-runtime/src/core/state.rs` 的 `AppState`，收口为三个平面加一组现实层设施。

| 平面 | 结构 | 职责 | 关键落点 |
| --- | --- | --- | --- |
| `kernel` | `AppKernelServices` | 智能体执行与线程推进 | `orchestrator/`、`services/runtime/thread/` |
| `projection` | `AppProjectionServices` | 面向用户侧的实时视图域 | `services/user_world.rs` |
| `control` | `AppControlServices` | 谁有权推进、谁在观看、谁能接入 | `services/presence/`、`gateway/`、`channels/`、`cron`、`core/approval_registry.rs`、`services/tools/command_sessions/` |
| 现实层设施 | `AppState` 直属字段 | 工作区、存储、记忆、技能、用户与配额、监控与压测 | `services/workspace.rs`、`storage/`、`services/memory.rs`、`services/skills.rs`、`ops/` |

划分的判据：

- `kernel` 必须能在没有前端页面、没有订阅者的情况下推进与收敛。
- `projection` 必须可从 durable 游标重建，不能成为线程认知态来源。
- `control` 只裁决准入与可见性，不承担模型推理语义。
- 消费者层只做呈现与恢复，不做真相。

展示读模型（`thread_view_*`）**不属于** `projection` 平面的领域服务对象：它是存储侧的派生读模型，与执行语义单向依赖（[03 册 §6](./03-实时投影系统设计.md)）。

## 4. 边界判据：形态差异只允许出现在接入层

这条边界要可验证，不接受「我们尽量共用」这种说法。判据：

| 判据 | 要求 | 检查方式 |
| --- | --- | --- |
| 同一状态装配 | 所有形态都经 `core/state.rs` 的同一构造路径获得 `AppState`，差异只体现为 `AppRuntimeProfile` 与启动期选项开关 | 新增形态入口时只允许传 profile/开关，不允许新建第二份状态结构 |
| 同一执行入口 | 所有执行都走同一 orchestrator 主链（`orchestrator/request.rs` → `execute.rs`），包括渠道、cron、goal、子智能体与互通远端命令 | 任何「绕过 submit_request 直接调 stream」或「本地自己跑一轮」的实现都是分裂 |
| 同一存储契约 | 只经 `crates/wunder-core/src/storage_backend.rs` 的分域 trait 访问持久化；SQLite/PostgreSQL 是同一契约的两种实现 | 形态代码不得持有裸连接、不得自带表结构 |
| 同一线程语义 | 轮次、状态、事件身份由执行侧单点定义（[02 册 §3](./02-智能体核心设计.md)、[03 册 §4](./03-实时投影系统设计.md)） | 前端或 façade 自行判定「完成/失败/忙碌」即为违规 |
| 接入面可有差异 | 路由集合、进程模型、本机能力、启停的后台任务、UI 呈现方式允许不同 | 差异必须能在代码里指到「接入层文件」，不能藏在执行链分支里 |

**可交付的反证检查**：同一份线程数据在蜂巢与蛹里读到的轮次号、条目身份与终态必须一致；不一致优先怀疑消费者侧造了真相。

## 5. 运行形态与能力开关

`AppRuntimeProfile` 区分三种可执行形态：`ServerDistributed`、`DesktopEmbedded`、`CliEmbedded`；`ServerDistributed` 对应产品上的舰体（附带蜂巢 web），蜂巢自身无进程。

- 差异只体现为：是否播种单位/默认管理员、是否启动网关维护循环、是否启动线程运行时后台循环与 cron、是否启用 LAN 叠加、是否强制打开会话排队开关。
- 本地形态（蛹/舵机）不依赖舰体即可完整执行；`embedded` 判定即为此而存在。
- 舵机显式关闭定时任务后台循环，避免与宿主其他实例重复触发；这是接入层开关，不是引擎缺能力。

设计含义：**新增后台循环时必须声明它在哪些 profile 启用**，否则本地形态会被迫承担服务形态的负载，启动速度与内存占用即失守。

## 6. 主链路与对象边界

主链路长期保持一致：

1. 用户、脚本、渠道或节点从接入层发起请求。
2. 接入层把请求映射为线程请求或系统控制请求。
3. 线程运行时做准入：会话锁、全局活跃上限、持久队列与协作让位。
4. orchestrator 完成 prompt 冻结复用、context 装配、工具面构建、模型执行与工具批次编排。
5. 工具写入工作区、访问知识、操作浏览器、派生子智能体或经互通触达远程设备。
6. 执行结果经统一提交出口落为 durable 状态并发布变更游标。
7. 蜂巢、蛹、舵机、渠道或外部观察者消费有界投影并呈现。

对象层级：

| 对象 | 说明 | 设计重点 |
| --- | --- | --- |
| 组织 / 用户 | 资源归属、隔离、额度账户与治理主体 | 多租户、多用户、权限与审计 |
| 智能体 | 可移植的角色定义（提示词、能力选择、运行时参数），非会话页对象 | 角色设定、工具面、模型与权限 |
| 任务线程 | 智能体的连续执行单元；**一个智能体可同时拥有多个**，彼此独立 | 冻结 prompt、context、恢复；调度与锁按线程隔离 |
| 用户轮次 / 模型轮次 | 权威定义见 [02 册 §3](./02-智能体核心设计.md) | 追加式、可幂等补水 |
| 子智能体 | 主智能体临时创建的工作单元，任务结束即回收 | 派生、隔离、结果回传、有界登记 |
| durable 变更 | 对外可观察的唯一事实游标 | Snapshot / Delta / Replay |
| 工作区 | 工具执行的工作目录；**多根**，按形态解析为本地/云端/远程设备目录 | 路径围栏、沙盒隔离、有界缓存 |
| 记忆 / 知识 | 长期记忆片段与三型知识检索 | 注入时机冻结，检索走工具 |

## 7. 反例：曾经的设计口径为什么不对

| 旧说法 | 为什么错 | 现在的口径 |
| --- | --- | --- |
| 「单智能体 + 每个用户只有一个智能体实例，工作区为唯一云端目录」 | 一个智能体可同时拥有多个独立任务线程，调度与锁按线程隔离；工作区有本地、云端、远程设备多种根，按形态解析 | 多任务线程 + 子智能体派生；工作区多根按形态解析 |
| 「当前发布边界固定为一人一会话、各自分散聊天」 | 同一用户已可并发多任务线程，有引擎级排队与协作让位，有云端-本地互通；把边界钉死会让准入设计按「用户级互斥」实现，直接压制并发并让排队条退化成 UI 补丁 | 并发单位是任务线程；会话锁保证单线程内顺序，全局上限约束总量 |
| 「实时事件系统的关键代码域是 `services/thread_log.rs` + `api/*_ws.rs`」 | `services/thread_log.rs` 是可见条目构造与尾部增量合并的执行侧助手，durable 提交在 `thread_log_committer.rs`，唤醒在 `thread_change_hub.rs`，展示分页在 `thread_view_*`。把它们混写成一层，就会让展示读模型参与执行判定，这是最近一系列故障的根因 | 四层划分：执行快照 / durable 提交 / 变更唤醒 / 有界展示投影（[03 册](./03-实时投影系统设计.md)） |
| 「蜂巢由舰体静态托管」 | 舰体只挂载舰桥与少量资源目录；蜂巢的构建产物由独立静态服务器只读挂载对外提供 | 蜂巢是舰体的接口消费者，不是它的文件；写「随舰体提供」指功能依赖 |
| 「`orchestrator/thread_runtime.rs` 是线程运行时本体」 | 该文件只是状态登记表；运行时本体（准入、排队、dispatch、取消）在 `services/runtime/thread/` | 状态登记与执行调度分开归属（[02 册 §5](./02-智能体核心设计.md)） |
| 「三形态是三套系统」/ 把网页壳形态当现役本地前端 | 引擎与核心只有一份；蛹唯一现役前端是 Slint 原生壳，网页壳已停止日常维护与功能迭代 | 差异只在接入层；停止前端壳 ≠ 停止蛹后端 |
| 以蜂群编排（群、房间、编排态、广场）为协作设计前提 | 该能力已从引擎与协议层移除，只在个别前端标签与兼容垫片留下残留 | 唯一协作形态是子智能体；残留属工程缺口，不是设计依据 |
| 把 A2A 之类的互联协议或未注册通讯平台写进接入能力 | 代码里没有实现 | 对外集成只有外部工作流、MCP 端点与已注册渠道 webhook（[07 册](./07-接入、网关与渠道系统设计.md)） |

## 8. 演进重点

两条主线：

- 持续稳定 orchestrator 的执行主链（轮次语义、冻结与压缩、工具编排、治理与恢复）。
- 持续把实时链路收口为「durable 提交 → 有界展示投影 → 消费者只读游标」单向依赖，并把展示层的容量问题在读模型内解决，而不是回头改执行语义。

结构性改动先归类，不要把不同层的债务混在同一模块里修补：智能体引擎问题 / 事件与投影问题 / 工具与现实层问题 / 接入与控制面问题。

## 9. 验收标准

- 任一入口都映射到统一线程主链，不携带独立状态机。
- 三种可执行形态共用同一 `AppState`、同一 orchestrator、同一存储契约；差异能在代码里指到接入层文件。
- 蜂巢、蛹、舵机、渠道消费统一的快照/增量/补水契约，终态只由执行侧宣布。
- 数据层明确区分 durable 状态、展示派生投影、事件缓存、临时目录与运行时内存态。
- 高风险能力都有明确治理落点（准入、审批、执行策略、沙盒、互通风险分层），不散落在 prompt 或页面逻辑里。
- 列表、日志、面板类能力都有分页/限量/有界语义的说明。
