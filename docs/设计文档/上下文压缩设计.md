# 上下文压缩设计

> 本册于 2026-09-25 按代码现状修订。实现主体：`orchestrator/memory.rs`（`maybe_compact_messages`）、`compaction_policy.rs`、`microcompaction.rs`、`memory_compaction_budget.rs`、`memory_compaction_window.rs`、`memory_support.rs`、`tool_result_payload.rs`。数值与函数名以代码为准。

## 1. 目标

- 压缩后提交一份新的 `replacement_history`；压缩后的本次继续执行请求、下一次真实请求、刷新后的历史回放，都基于同一份压缩基线。
- 请求体只保留继续任务真正需要的语义，不回放工具噪音。
- 运行中压缩不能让模型重复执行已经完成的工具，也不能丢失当前轮失败后的修复现场。
- 压缩决策只认供应商实测占用（`persisted_context_tokens`），本地 token 估算只用于内部裁剪，不参与触发判断。

## 2. 总览：四层

从轻到重依次尝试，前一层够用就不进后一层：

```text
1. 工具结果投影（tool_result_payload）   每次工具调用即发生，决定模型 observation 的形态
2. 微压缩（microcompaction）             摘要压缩前对更旧的可重读工具结果做本地替换，不调模型
3. 摘要压缩（summary compaction）        用摘要模型生成交接摘要，重建 replacement_history
4. Context Guard（memory_compaction_*）  压缩后仍超预算时的最后裁剪
```

命名澄清：`memory_compaction_budget.rs` / `memory_compaction_window.rs` 虽带 `memory_` 前缀，但作用于**压缩重建后的消息窗口**（摘要 + 当前请求 + 保留交互），与 `memory_fragments` 长期记忆表无关。

## 3. 触发决策

### 3.1 运行模式

| 模式 | `trigger_mode` | 场景 |
| --- | --- | --- |
| 手动压缩 | `manual` | 用户或管理员经 API 主动触发 |
| 运行中压缩 | `auto_loop` | 智能体循环每轮模型调用前检查 |
| 溢出恢复 | `overflow_recovery` | 主请求已触发上下文超限 |

### 3.2 决策与 trigger 值域

`should_compact_by_context`（compaction_policy.rs）产出 trigger：

| trigger | 条件 |
| --- | --- |
| `history` | `projected_request_tokens >= max_context * history_compaction_ratio`（每模型可配，默认 0.9；>1 且 ≤100 按百分比解释） |
| `overflow` | `projected >= limit` |
| `pre_sampling` | 未到上述两者，但达到预采样阈值：占用率 0.9 与自适应余量 `limit/8`（clamp 到 [256, 8192]）取较大者对应的水位 |
| `force` | 手动/溢出恢复强制 |
| `none` | 不压缩 |

### 3.3 limit 求解

`resolve_compaction_limit` + `HistoryManager::get_auto_compact_limit`：

```text
limit = min(max_context * 0.9, max_context - reserve_output - 512)
reserve_output = max(模型 max_output 配置, 8192)
```

模型未配置 `max_context` 时，自动压缩直接跳过（无法判断水位）；force 场景摘要限源自适应 `clamp(context/4, 5120..8192)`。

### 3.4 入口自愈

上一轮死于上下文溢出时，下一轮入口强制先压缩（`force_compaction_on_entry`，由持久化的 `session_context_overflow` 驱动），压缩后清除标记。这保证带病状态不会在下一轮再次撞墙。

## 4. 摘要请求组装

摘要请求只负责生成 `[上下文摘要]`，不直接继续执行用户任务。模型输入固定按下面顺序组装：

```text
system?
source_messages
user: CONTEXT CHECKPOINT COMPACTION 摘要指令（末尾并入动态产物索引）
```

约定：

- `system` 仍来自线程冻结后的 system prompt；压缩全程不改写它。
- `source_messages` 排除原始 `system`；运行中与溢出恢复压缩额外排除当前用户消息（`exclude_current_user=true`），避免摘要模型把当前请求当成待执行任务重跑。**手动压缩不排除**（`exclude_current_user=false`），最后一条用户消息会进摘要输入。
- 动态产物索引不是追加进 system，而是拼入摘要指令（`merge_compaction_system_message` 已忽略 artifact 参数，只规范化 role）。
- 当前轮用户消息之后已发生的模型输出、工具 observation、失败信息仍留在 `source_messages` 作为摘要证据。
- 摘要指令必须作为最后一条 `user` 消息追加；工具失败 observation 不能成为摘要请求尾消息。
- 摘要必须包含 `resume_action: final|continue|retry|ask_user`（解析缺省为 `unknown`），作为压缩后当前轮续跑的唯一结构化动作建议；续跑层不从 stdout/stderr、代码或任意文本里推断完成状态。
- 摘要请求带 `purpose=compaction_summary`，`progress / llm_request / llm_response / compaction` 事件携带同一个 `compaction_id`（格式 `cmp_{trigger_mode}_{uuid}`）。
- 摘要模型配置固定：`max_rounds=1`、`max_output=min(配置或 2048, 2048)`、`reasoning_effort=none`；用量核算以 `compaction` purpose 单独记账。
- 摘要失败先走 fallback 摘要（确定性拼接），fallback 仍失败则只做 guard，不提交坏摘要。

## 5. 摘要提交物

每次压缩成功提交两份结果：

1. `summary_text`：必须带 `[上下文摘要]` 前缀，最多 20000 字符。
2. `replacement_history`：写入摘要消息 `meta.replacement_history`，不含线程 `system`，不含运行中的当前用户续跑提示。

首尾保留按"归一化交互 block"计算，token 预算（`memory_compaction_window.rs`）：

| 预算 | 值 |
| --- | --- |
| 每侧交互段 token 预算 | head 8192 / tail 16384 |
| 每组交互目标 | 每侧最早 2 组、最近 2 组（实现上每侧最多 4 个 block） |
| 单 block 上限 | 5120 token / 20000 字符 |
| 最小保留 | 单交互 128 token，当前用户消息裁到 64 token 底线 |

交互 block 不足目标数时实际保留更少；此时 `tail` 允许为 0，不视为拼接 bug。

## 6. 本次继续执行请求

压缩完成后若当前轮还要继续，立即重建本次请求：

```text
system
retained_head_messages
user: summary_text
retained_tail_messages
current_user_replay_message?
```

- `summary_text` 以 `user` 消息进入请求，承载被压缩掉的历史。
- `current_user_replay_message` 只用于运行中续跑，不写入 `replacement_history`。
- `system` 保持冻结原样，不追加动态索引、压缩摘要或当前轮信息，避免破坏模型提示词缓存。

当前轮续跑按 `current_turn_progress_state` 分类：

| 状态 | 续跑方式 |
| --- | --- |
| `pending` | 追加原始当前用户消息，必要时按预算裁剪 |
| `tool_succeeded` + `resume_action=final/ask_user` | final continuation note（`current_user_replay_mode=final_continuation`）：基于摘要直接最终回复或询问用户，禁止重新调用工具、重写文件或重生产物 |
| `tool_succeeded` + `resume_action=continue/retry/unknown` | tool success continuation note（`tool_success_continuation`）：从最新 observation 和摘要继续；工具成功不等于用户任务完成 |
| `tool_failed` | 从保留的失败 observation 继续修复或解释 |
| `in_progress` | 从当前进展继续，而不是重新开始 |

约束：

- continuation note 语义上驱动模型继续执行，但协议层必须是 `user` 消息；不能以 assistant 尾消息追加（部分模型服务拒绝连续 assistant 尾）。
- `tool_success_continuation` 写入最新保留的 tool observation 摘要和结构化 `resume_action`：例如 `write_file` 成功只说明文件已写入，摘要要求继续时才继续运行或验证；摘要标记 `final` 或明确无剩余待办时直接 final，避免压缩后反复重画/重写。

## 7. replacement_history 规则

保留：压缩摘要消息、最早/最近几段用户-模型交互、非工具噪音的真实用户/模型文本。

不保留：线程 `system`、当前轮临时续跑消息、`tool_response:` 观测包装、工具 observation 原始负载、`Assistant issued tool call(s): ...`、`results_jsonl`/`duration_ms`/`retryable` 等原始工具回放字段、仅用于发起工具调用的 assistant 占位消息、`tool_calls`/`tool_call_id`/`reasoning_content` 等内部执行字段。

原则：优先保留"模型续跑确实需要"的用户意图和已确认事实；不为"看起来完整"把工具执行过程塞回请求体；不把运行中临时指令持久化为历史事实。

## 8. 落库、加载与回放

### 8.1 model_context_entries

压缩产物落 `model_context_entries` 表（`id/user_id/session_id/role/payload/created_time`，PostgreSQL 同构）：

- 压缩成功：`model_context_entries_from_messages` 规范化重建结果（剔 system、脱敏、规范化 role/content/tool_calls/reasoning）→ `replace_model_context_entries` 事务整体替换（DELETE+INSERT）→ flush。
- 每轮加载（`execute.rs`）：优先 `load_model_context_entries`；为空则回退 `chat_history` 并回填该表；normalize 有修复时整体重写回表。
- 手动压缩例外：`force_compact_session` 从 `chat_history` 重建摘要输入（非 model_context_entries），完成后会话 token 计数清零。

### 8.2 后续请求

刷新、重进、hydrate，或压缩后用户发起下一轮真实请求时：

```text
system
latest replacement_history
压缩之后新增的真实历史
current user?
```

只认最新一份 `replacement_history`，更老的压缩前历史不复活；老数据没有 `replacement_history` 时兼容旧逻辑。

## 9. 微压缩

微压缩在摘要压缩之前尝试（仅 `auto_loop` 且非 force），不调用模型。触发阈值取 `min(history_threshold, limit, presampling_limit)`，观察值用供应商实测占用。

- **对象**：按连续 tool/observation 消息分组，保护最近 5 组；只替换更旧的成功读取类结果——`读取文件`/`搜索内容`/`列出文件`。失败结果、媒体、待续分页（`has_more/next_cursor/continuation_token` 等）、技能、命令、写入、外部工具均不参与。
- **替换物**：保留定位字段（`path/files/query/returned_match_count/matched_file_count/truncated/read_output_omitted_bytes`）+ 头尾各 384 字节预览，中间插 `[older output omitted; repeat the read if needed]`。`read_output_omitted_bytes` 来自工具结果投影对读取截断标记的解析，让模型知道重读能取回多少。替换必须严格变短；`microcompacted` 标记保证幂等。
- **预算**：目标回落到触发阈值的 80%，预计至少节省 256 token 才提交；按实测占用与消息估算保守评估，不足时直接走摘要压缩。
- **落库验证**：写队列同步完成并在 blocking DB 回读核对 `load_model_context_entries` 一致后才接受；失败回退摘要压缩。成功时 `model_context_replaced=true` 而 `compaction_id=None`。
- **事件**：`progress.stage=microcompaction`，字段含 `observed_context_tokens/estimated_tokens_before/estimated_tokens_after/estimated_tokens_saved/reduced_messages/kept_recent_tool_groups` + round。不产生 compaction 分隔线。

## 10. 溢出恢复

主请求撞上下文上限时（错误码 `CONTEXT_WINDOW_EXCEEDED` 或文本匹配）：

- 最多恢复 `MAX_CONTEXT_OVERFLOW_RECOVERY_ATTEMPTS=8` 次。
- 从错误消息解析 `context_window_limit_hint` 并持久化到会话；无 hint 时自适应推导，每次减半、下限 5120。
- force 压缩后发 `progress.stage=context_overflow_recovery`（含 attempt/max_attempts）与 `compaction` 收尾事件。

## 11. Context Guard

压缩后仍超预算时进入 `context_guard`，步骤（`apply_rebuilt_context_guard`）：裁摘要 → 丢非保留消息 → `trim_summary_to_preserve_retained_interaction_budget` → `rebalance_retained_interaction_context`（短回复优先完整保留、长消息共享剩余空间，避免第一条长消息挤掉下一组交互）→ `tighten_retained_interaction_context` → 极端时删摘要、把当前用户消息裁到 64 token 底线。

最终原则：下一次请求和历史回放必须基于同一份已提交基线，不能出现"请求体一套、刷新回放另一套"。

## 12. 记忆注入与自动提取的关系

- 压缩提交前会注入 "fresh memory"：`build_fresh_memory_block_for_compaction` → `recall_for_prompt_inventory`（上限 30）→ 并入 summary_text。这是压缩产物的一部分，不改线程 system prompt。
- 记忆自动提取（`memory_auto_extract`）是独立的轮后机制，按智能体 `auto_extract_enabled` 开关运行，与压缩没有调用关系；输入截断为问题 1200 / 窗口每条 600 / 回答 1000 字符，最多产出 4 条 fragments。

## 13. 压缩后口径

- `persisted_context_tokens=0`，会话 token 计数清零，occupancy 重置。
- 每轮发 `context_usage` 事件，压缩后首次带 `context_usage_source=unobserved_after_compaction`，前端快照在此期间不显示数字，等下一次实测。

## 15. 配置

- 模型级（`LlmModelConfig`）：`max_context`、`max_output`、`history_compaction_ratio`（≤0 回落 0.9，>1 且 ≤100 按百分比）。
- 会话级持久状态：`session_context_tokens` / `session_context_overflow` / `session_context_limit_hint`。
- 入口：`POST /wunder/chat/sessions/{session_id}/compaction`（支持 `debug_payload`，异步执行）；管理员 `POST /wunder/admin/monitor/{session_id}/compaction`（同步，拒绝 running/cancelling 会话）。
- 提示词：`config/prompts/compact_prompt.txt`、`config/prompts/memory_auto_extract.txt`。
- 无压缩总开关：不配置 `max_context` 即跳过自动压缩；手动压缩始终可用。

## 16. 边界情况

| 场景 | 行为 |
| --- | --- |
| 用户一次输入超长文本 | 允许直接触发压缩；仍超限走 guard；禁止落库空摘要、坏摘要、半截前缀 |
| 一次输入大量多模态内容 | 当前用户消息仍作为本轮真实输入或 pending 续跑输入保留 |
| 运行中读取大文件 | 优先保留摘要、首尾交互和续跑指令，不回放大段工具输出 |
| 工具已成功 | 按 `resume_action` 续跑：final/ask_user 直接响应，continue 才执行剩余步骤 |
| 工具失败或补丁失败 | 从保留的失败 observation 改策略继续，不从头开始 |
| 连续多次压缩 | 只认最新 `replacement_history`，老基线不复活 |
| 摘要失败 | fallback 摘要 → 仍失败只做 guard，不提交污染基线 |

## 17. 常量速查

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `COMPACTION_RATIO` / `COMPACTION_HISTORY_RATIO` | 0.9 | limit 与 history 阈值比例（均可被模型配置覆盖） |
| `COMPACTION_OUTPUT_RESERVE` | 8192 | 输出预留 token |
| `COMPACTION_SAFETY_MARGIN` | 512 | 安全余量 |
| `PRE_SAMPLING_OCCUPANCY_RATIO` | 0.9 | 预采样水位 |
| 预采样自适应余量 | limit/8，clamp [256, 8192] | 与占用率水位取大者 |
| `COMPACTION_SUMMARY_MESSAGE_MAX_TOKENS` | 5120 | 摘要输入单条上限 |
| `COMPACTION_SUMMARY_MAX_CHARS` / `TURN_MAX_CHARS` | 20000 | 摘要与单 block 字符上限 |
| `RETAINED_HEAD/TAIL_INTERACTION_TOKENS` | 8192 / 16384 | 首尾交互 token 预算 |
| `EXCHANGE_COUNT_PER_SIDE` | 2（每侧 4 block） | 交互组目标 |
| `MIN_RETAINED_INTERACTION_TOKENS` / `MIN_CURRENT_USER_MESSAGE_TOKENS` | 128 / 64 | 最小保留底线 |
| 摘要模型 max_output | min(配置或 2048, 2048)，reasoning_effort=none | — |
| `MAX_CONTEXT_OVERFLOW_RECOVERY_ATTEMPTS` | 8 | 溢出恢复上限 |
| `KEEP_RECENT_GROUPS` / `PREVIEW_BYTES` / `MIN_SAVINGS`（微压缩） | 5 / 768 / 256 | 近距窗口、预览字节、最小节省 token |
| 微压缩目标水位 | 触发阈值的 80% | 回落目标 |

## 18. 调试时看什么

1. 摘要阶段 `llm_request`：`system? + source_messages + user: compaction instruction`；最后一条必须是摘要指令，不应是工具 observation。
2. `compaction` 事件：`compaction_id`、`trigger_mode`、`status`；`summary_text`、`replacement_history_*`；`source_interaction_block_count` / `retained_head|tail_block_count_target` / `retained_head|tail_messages_debug`；`current_turn_progress_state`、`current_user_replay_mode`、`current_turn_has_tool_success|failure`；`rebuilt_request_debug` 确认请求尾部没有连续 assistant。
3. 摘要消息 `meta`：`meta.replacement_history` 中不应有运行中的 continuation note。
4. 压缩后第一条普通 `llm_request`：运行中续跑应为 `system + retained head + summary + retained tail + current_user_replay_message`；新一轮或刷新回放应为 `system + replacement_history + 压缩后真实历史 + current user`。
5. 微压缩：`progress.stage=microcompaction` 的估算前后占用与 `model_context_replaced` 状态。
