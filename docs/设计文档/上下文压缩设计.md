# 上下文压缩设计

> 本册讲边界、不变量、理由与反例。事件字段表、完整常量手册、前端接线与排障命令属于技术说明书：见 `docs/技术说明书/03-运行时与执行链路.md`、`docs/技术说明书/04-实时投影与通信链路.md`、`docs/技术说明书/11-工具结果裁剪与观测链路.md`。实现主体：`crates/wunder-runtime/src/orchestrator/` 下的 `memory.rs`、`compaction_policy.rs`、`microcompaction.rs`、`memory_compaction_budget.rs`、`memory_compaction_window.rs`、`memory_support.rs`、`execute.rs`。

## 1. 这页解决什么问题

- 想知道「压缩到底动了什么、没动什么」——看 §3 职责分层与 §4 不变量。
- 想新增触发条件、改阈值或加压缩层——先看 §2 边界，再看反例 §5。
- 排查「压缩后模型重复执行 / 历史丢了 / 缓存失效」——看 §4 不变量逐条对照。

压缩的唯一目的：让下一轮模型请求的输入在窗口内可容纳，且**续跑语义正确**。它不是存储回收手段，也不是展示优化手段。

## 2. 边界：四层压缩，各管一段

从轻到重依次尝试，前一层够用就不进后一层。四层各自的作用面对象不同，混层是大多数 bug 的来源。

| 层 | 模块 | 作用对象 | 是否调模型 | 产物 |
| --- | --- | --- | --- | --- |
| 触发决策 | `compaction_policy.rs:5-28` | 投影后的请求 token 数 | 否 | `history` / `overflow` / `pre_sampling` 三触发判定 |
| 微压缩 | `microcompaction.rs` | 旧的、可复现的工具观测 | 否 | 就地替换 + hidden marker 持久化 `replacement_history` |
| 摘要压缩 | `memory.rs`（`maybe_compact_messages`） | 整段历史 | 是（摘要模型一次） | `[上下文摘要]` + `replacement_history` 新基线 |
| 预算再平衡与窗口保护 | `memory_compaction_budget.rs`、`memory_compaction_window.rs`、`memory_support.rs` | 压缩重建后的消息窗口 | 否 | 保留交互的再分配与底线裁剪 |

命名澄清：`memory_compaction_budget.rs` / `memory_compaction_window.rs` 虽带 `memory_` 前缀，作用于**压缩重建后的消息窗口**（摘要 + 当前请求 + 保留交互），与 `memory_fragments` 长期记忆表无关。

### 2.1 触发决策

`should_compact_by_context`（`compaction_policy.rs:45-70`）产出三触发之一：

| trigger | 条件 | 出处 |
| --- | --- | --- |
| `history` | 投影占用 ≥ `0.9 × max_context`（比例可被模型配置 `history_compaction_ratio` 覆盖，≤0 回落 0.9，>1 且 ≤100 按百分比解释） | `memory.rs:109-118`、`constants.rs:7` |
| `overflow` | 投影占用 ≥ `limit` | `compaction_policy.rs:60` |
| `pre_sampling` | 未到上两者，但达到 `max(0.9 × limit, limit − clamp(limit/8, 256, 8192))`；且不得早于显式 history 阈值触发 | `compaction_policy.rs:1-3, 31-43, 61-63` |

边界规定：**「未声明窗口」不等于「不压缩」**。模型未配置 `max_context` 时按内置默认窗口计量（`DEFAULT_MODEL_CONTEXT_TOKENS = 131072`，`wunder-core/src/config.rs:857, 862-866`；`services/history.rs:75-78` 注释明确「把 unknown 当 never compact 会让请求长到被供应商拒绝」），不存在「压缩总开关」配置项。上一轮死于上下文溢出时，下一轮入口强制先压缩自愈（`execute.rs:413-418` 的 `force_compaction_on_entry`，由持久化的 `session_context_overflow` 驱动）。

### 2.2 微压缩

只处理「更旧的可复现观测」：按连续 tool/observation 分组，保护最近 `KEEP_RECENT_GROUPS=5` 组；只替换更旧的、成功返回的读取类结果（`读取文件`/`搜索内容`/`列出文件`）；失败结果、媒体、待续分页（`has_more`/`next_cursor`/`continuation_token` 等）一律不碰（`microcompaction.rs:6-8, 16-56`）。

替换为头尾各 384 字节（合计 `PREVIEW_BYTES=768`）加定位字段的预览；预计节省不足 `MIN_SAVINGS=256` token 不提交；替换必须严格变短，`microcompacted` 标记保证幂等。

持久化边界：微压缩不是「只改内存」——向 `thread_items` 追加 hidden marker 行（`meta.type=microcompaction` + `replacement_history` 快照，`microcompaction.rs:216-233`），flush 后回读最后一行核对类型与条数才宣告成功（`:248-264`），失败回退摘要压缩。这样执行视图的基线与 append-only 线程日志在同一存储面上，刷新与跨进程回放看到的是同一份东西。

### 2.3 摘要压缩

产出一份 `[上下文摘要]` 与一份 `replacement_history`。`replacement_history` 是后续一切加载的唯一基线：本次续跑请求、下一轮真实请求、刷新回放，都从「最新一份 `replacement_history` + 其后新增真实历史」派生；老基线不复活。`system` 不写入 `replacement_history`，运行中的当前用户续跑提示（replay message）也不持久化——它是本轮临时指令，不是历史事实。

### 2.4 预算再平衡与窗口保护

压缩重建后的窗口预算在 `memory_support.rs:10-17`：首尾交互各 8192/16384 token、单 block 上限 5120 token/20000 字符、每侧目标 2 组交互（4 个 block）。`memory_compaction_budget.rs` 的再平衡原则：短回复优先完整保留，长消息共享剩余空间，避免第一条长消息挤掉下一组交互。

窗口保护的硬不变量：**当前用户消息不得被整体压掉**。压缩进行期用 `compaction_inflight_current_user` meta 标记保护（`memory_compaction_window.rs:4-27`、`memory_support.rs:19-20`）；极端裁剪下当前用户消息只允许裁到 64 token 底线、任一保留交互只留 128 token 底线（`memory_support.rs:10, 28`；应用点 `memory_compaction_budget.rs:31, 42, 61`），且优先删摘要而不是删本轮请求。

## 3. 压缩与工具结果投影的分工

工具观测有两条独立通道：展示通道（`services/tool_result_display.rs`，只影响客户端展示）与模型输入通道（`finalize_tool_result` + microcompaction + `model_observation`）。压缩只作用于模型输入通道；两层裁剪的细节见 `docs/技术说明书/11-工具结果裁剪与观测链路.md`。边界：任何一层的裁剪都不改变线程日志中落库的原始内容。

## 4. 不变量（违反任何一条即为缺陷）

1. **只信任 provider 观测 token。** 压缩决策的输入是供应商回报的实测占用（`persisted_context_tokens`）；本地 token 估算只用于内部裁剪取舍，不参与触发判断。出处：`execute.rs:410-412` 注释与 `request_overhead_tokens = 0` 的刻意置零。理由：各家分词不一致，估算触发会造成「没满也压」或「满了不压」，后者直接撞墙。
2. **压缩不得破坏 system prompt 前缀稳定。** 线程 system prompt 首次确定后冻结（`prompt.rs:304-305` 的 AGENTS.md 快照注释、`:329-331` 的记忆冻结注释）；压缩全程不改写它，摘要、动态产物索引、当前轮信息一律不追加进 `system`。这与「提示词冻结」是同一条设计约束的两面：前缀稳定才有大模型 API 的提示词缓存命中。出处：`prompt.rs:305, 330`。
3. **先生成模型输入，必须先 flush 写队列。** 每轮派生模型输入前调用 `flush_writes_async`（`execute.rs:339-342`）：上一轮的异步历史写入若未落库，快速跟进的用户消息会漏掉 append-only 历史的尾部，直接破坏 KV cache 前缀复用，还会让压缩基线建立在残缺历史上。
4. **原始内容必须完整保留，降级只影响展示与模型输入视图。** 压缩重写「提交给模型的请求」，不删除、不改写线程日志里的原始行；微压缩的替换以新增 hidden marker 行表达，摘要压缩以追加 `meta.type=compaction_summary` 摘要行表达（`constants.rs:3`，加载侧 `services/history.rs:57`），原行俱在。用户侧复制与轨迹展示的原文不因压缩缺损。
5. **压缩后口径归零。** 压缩成功即清零会话 token 计数，下一条 `context_usage` 标记 `context_usage_source=unobserved_after_compaction`（`execute.rs:675`、`memory.rs:921`），前端在此期间不显示数字，等下一次 provider 实测——不得用估算回填。
6. **请求与回放同源。** 续跑请求与刷新回放必须基于同一份已提交的 `replacement_history`，不允许「请求体一套、回放另一套」。

## 5. 反例：三种错误实现及其后果

### 5.1 「压缩 = 删历史」

删除最省事，但它同时违反不变量 4 与 6：线程日志是 append-only 的事实台账（轨迹回放、补水、审计、导出都读它），删了不可恢复；压缩一旦删行，回放与执行视图分叉，且丢失「当前轮失败后的修复现场」——模型会重复执行已完成的工具或从头重做。正确形态是**追加新基线**（marker 行 / 摘要行携带 `replacement_history`），加载时「只认最新基线 + 其后新增行」，旧区间自然失效但物理保留。

### 5.2 把压缩计数算进模型轮次

模型轮次 = 引擎主循环一次模型调用（`execute.rs:435` `model_round += 1`），且一个模型轮次恰好对应一个可见输出项 `{turn_id}:text-{model_round}`。摘要请求是 `purpose=compaction_summary` 的内部一次性子调用，若它也占一个 `model_round`，账本上就会出现一个没有任何用户可见输出的空轮，时间线项 ID 序列错位，补水与回放会把「压缩」当成一轮正常回答渲染。因此压缩走独立事件（`compaction_id`、`progress.stage=compacting|microcompaction|context_guard|context_overflow_recovery`），不进轮次账。

### 5.3 执行快照与展示投影不分家

若压缩同时裁剪展示内容，或展示层裁剪（preview 截断）反向进入模型输入，两条通道就耦合了：展示降级（Markdown 渲染失败、预览截断）会「吃掉」模型需要的观测，而用户侧本应可复制的完整原文也会缺失。设计上两者分属不同链路（§3），各自有独立的裁剪规则与常量；交叉引用 `docs/技术说明书/04-实时投影与通信链路.md`（投影与补水）与 11 章（观测双通道）。

## 6. 与长期记忆的关系

- 压缩提交前会把「fresh memory」并入 `summary_text`（`recall_for_prompt_inventory`，上限 30）；这是压缩产物的一部分，不改线程 system prompt。
- 记忆注入、自动提取与压缩的边界归属，以 `docs/设计文档/记忆系统设计.md` 为准，本册不复述。

## 7. 关键数值速查（只列构成边界的那些）

| 数值 | 值 | 出处 |
| --- | --- | --- |
| history 阈值比例 | 0.9 × max_context | `constants.rs:7`、`memory.rs:109-118` |
| 预采样余量 | limit/8，clamp [256, 8192]，与 0.9 占用水位取大 | `compaction_policy.rs:1-3, 31-43` |
| 微压缩保留近组 / 预览字节 / 最小节省 | 5 组 / 768 B / 256 token | `microcompaction.rs:6-8` |

| 保留交互底线 | 128 token | `memory_support.rs:28` |
| 首尾交互预算 | 8192 / 16384 token | `memory_support.rs:14-15` |

完整常量（摘要单条上限、溢出恢复次数、摘要模型参数等）见技术说明书与代码。

## 8. 做错回哪儿查

- 压缩后模型重跑已完成工具 → §2.3 replay message 与 `replacement_history` 持久化边界、§5.1。
- 缓存命中率骤降 → 不变量 2（system 是否被追加）与 3（flush 顺序）。
- 前端数字与真实占用不符 → 不变量 1、5；展示口径问题查技术说明书 04 章。
- 压缩后历史回放缺段 → 不变量 4、6；marker/摘要行是否落库查 §2.2 的读回验证。
