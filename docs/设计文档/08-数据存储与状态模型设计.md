# 数据存储与状态模型设计

> 约束范围：本册约束存储抽象分层、双后端一致性契约、schema 演进的真实机制与其代价、展示投影模型的取舍、有界删除与保护条件、保留期策略。表清单、字段与索引细节见 `../技术说明书/06-数据存储、工作区与配置.md`，本册不复述。

## 1. 存储抽象分层（不变量）

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 契约层 | `wunder-core/src/storage_backend.rs`：30+ 个分域 trait（ThreadLogStore、ChatSessionStore、WorkspaceStore、MemoryRecordStore……），由 `StorageBackend` supertrait 组合（:1544 起，已实测） | 定义跨后端最小语义；记录类型权威定义在 `wunder-core/src/storage_records.rs` |
| 实现层 | `crates/wunder-runtime/src/storage/{sqlite,postgres}/` | 各自实现分域 trait；`storage/backend.rs` 只做 re-export |
| 选型层 | `storage/factory.rs:8-17`：配置为空默认 **sqlite**；`postgres|postgresql|pg|auto` → PostgreSQL；受 cargo feature `sqlite-storage`/`postgres-storage` 门控 | 形态默认：舰体 PG、蜂窝/舵机 SQLite |

分域 trait 的意义：新域（如互通、目标态）以新 trait 接入，两个后端各自实现，运行时只依赖契约。禁止出现「只有某一个后端满足某语义」的 trait 方法设计。

## 2. 双后端一致性契约

SQLite 与 PostgreSQL 不是「一个真实现 + 一个近似实现」，以下语义必须两端一致，任何一端偏离即缺陷：

| 语义 | 一致性要求 |
| --- | --- |
| 分页 | 页大小、上限、游标推进规则由 `wunder-core/src/thread_view.rs` 单一来源定义（聊天页 12/上限 20，轨迹页 80/上限 100，响应预算 128KB/192KB，正文分块 8KiB——已实测常量在位），两端不得各自解释 |
| 裁剪 | 投影预览截断（2048/256/96 字符）、单行子智能体卡片上限在投影层统一，不因后端不同而呈现不同截断行为 |
| 水位与对账 | 增量计数与水位对账在两端等价：PG 侧日志大表按月分区、启动与每日任务补建分区，用量统计走增量计数表 + 水位对账，`tool_logs` 有排除标记物化列；SQLite 侧以等价查询计划保持同一统计口径 |
| 布尔与时间 | 时间统一秒级浮点（来源 `now_ts`）；布尔 SQLite 用 INTEGER 0/1，PG 保持比较语义一致 |

一致性验证方式：同一契约测试面（`crates/wunder-runtime/tests/backend_contracts.rs` 等）对两后端跑同一组断言；不允许「SQLite 过了就算」。

## 3. 没有 schema 版本表——现实与代价（必须如实写）

当前**没有 schema 版本表、没有迁移脚本目录**（已实测）：

- 机制：`ensure_initialized` 幂等建表（`CREATE TABLE IF NOT EXISTS`）+ 列探测式 `ensure_*` ALTER 补列补索引（`storage/sqlite/schema.rs`、`storage/postgres/schema.rs`）。
- 唯一持久化游标：meta 表中的 `thread_view_discovery_v2` 标记（`thread_view_store.rs:91-103`），用于投影发现策略，不是版本迁移指针。
- 设计取舍：原型阶段换取零依赖升级与分发简单（蜂窝面向本地用户，不能要求用户跑迁移工具）。
- **代价**：只能加列、不能改列类型、不能搬数据、不能可靠表达约束变化。一旦某字段需要重typeing，只能走「新列 + 后台回填 + 旧列退役」的显式代码路径。
- 文档纪律：不得写「按版本号迁移」；新增存储对象时同步更新两个 `schema.rs` 与本册的分类。

## 4. 状态分层：真相 vs 派生 vs 短暂

| 类别 | 示例 | 设计要求 |
| --- | --- | --- |
| Durable Business State | 用户、组织、agent、渠道绑定 | 业务真相源 |
| Durable Runtime State | 线程日志（`thread_items`/`thread_turns`）、durable change 游标、会话目标、工具日志 | 恢复与审计的依据；断线恢复唯一真相是 `thread_log_changes` 游标与帧 |
| Derived Projection State | 展示投影表、摘要缓存、树缓存 | **可重建、不可替代真相源**；缺失只降性能不降正确性 |
| Ephemeral State | 进程内 watch、连接态、审批缓存、热缓存 | 允许丢失，必须有界 |

很多实时故障的根因是把派生状态当真相源。验收时先问：这个数据删掉后能否从 durable 层重建？

## 5. 展示投影模型（写时投影 + 受占空比约束的重建）

为大数据量线程的时间线/轨迹读取建立的模型：

| 组件 | 语义 |
| --- | --- |
| 投影表 | `thread_view_heads` / `chat_rows` / `trajectory_rows` / `body_manifests` / `body_chunks` / `trajectory_tiles`（`storage/thread_view_store.rs`），重建批与发现批均为固定小批量 |
| 写时投影 | `storage/thread_view_projection.rs`：写路径顺带产出展示行，预览按常量截断 |
| 后台重建 | `services/thread_view_rebuild.rs`：占空比 ≤1%（空闲 = 耗时×99、最小 1s；失败退避 5s→300s，已实测含 ≤1% 断言测试） |
| 未就绪兜底 | 源表有界窗口读（`storage/thread_view_source.rs`：clamp + 响应预算），投影缺时功能不缺 |
| 活动态 | 运行时活动优先内存快照、回退 `thread_turns`（`services/chat_runtime_projection.rs`） |

取舍理由：展示读不能反查全量历史（全量重算违反性能纪律），所以预投影；预投影可能落后或损坏，所以必须「可整表重建 + 未就绪有界兜底」；重建不能挤占交互资源，所以有 ≤1% 占空比硬上界。`services/history.rs` 服务的是 LLM 上下文压缩，与 UI 分页无关，两者不得混写。

## 6. 有界删除与保护条件

- 删除必须分批、有界：线程目录分页上限 100，搜索扫描上限 10×100 条（`services/thread_catalog.rs`），删除任务同样按批推进，禁止一次全表扫删。
- 空会话清扫有**保护条件**：`storage/session_cleanup_empty.sql`（8 项 NOT EXISTS）与 `session_cleanup_live.sql`——会话只要还有锁、任务、运行或目标即受保护，清扫只碰真正空会话；触发点收敛在按时间范围删日志的单事务里。
- 用户删除会话先写墓碑（`deleted_session_log_grace`），宽限期后物理；管理侧删除立即物理。两条路径的边界必须在代码评审中显式声明。
- SQLite 空间回收：`auto_vacuum=INCREMENTAL` + 清删后 incremental_vacuum + WAL checkpoint，避免删除风暴锁库。

## 7. 保留期策略（含既成事实与风险）

| 数据 | 默认策略 | 备注 |
| --- | --- | --- |
| `thread_log_changes`（durable change 游标与帧） | 永久保留 | 断线恢复唯一真相，不可设短保留期 |
| `stream_events` | 168 小时；轮次完成后折叠删除该轮 `llm_output_delta` | 有 `0=禁用` 语义 |
| 服务器日志文件 | **默认 0 = 永不清理**（`default_server_log_retention_days()` 返回 0，已实测） | 既成事实 + 风险：长期运行磁盘单调增长；旧文档「默认保留 14 天」是错的。清理机制存在（daily rolling + 过期删除），只是默认关 |
| 已删除会话日志 | 宽限 24h 后物删 | 见第 6 节 |
| 互通影子 | `shadow_retention_days` 配置 + janitor 周期清理 | janitor 仅在 `interlink.enabled` 时启动 |

设计立场：默认值可以保守（原型期宁可不删），但**风险必须写进文档并在容量验收中覆盖**；舰体部署验收要求显式配置日志保留期。

## 8. 反例与缺口

| 项 | 现状 | 性质 |
| --- | --- | --- |
| 旧文档 ER 图仍画 `chat_history` | 该表已在 ThreadLog 收口后 DROP，正文真相是 `thread_items` | 已删除的错误依赖，投影/恢复设计都不得引用它 |

| `agent_tasks`/`thread_logs` 等旧表口径 | 以当前 `schema.rs` 实际表清单为准 | 细节归技术说明书 |

## 9. 验收判据

- 同一契约断言在 SQLite 与 PG 两端同绿；分页/裁剪/水位差异测试为负向必红。
- 删除任一投影表后，读路径自动落入有界兜底，功能正确性不变，重建在 ≤1% 占空比内收敛。
- 空会话清扫在有锁/有任务/有目标的会话上不产生删除（保护条件负向测试）。
- 全新库启动即幂等建表成功；老库补列路径不需要人工迁移命令。
