# 目标态系统设计

## 1. 文档定位

这页回答三个问题：目标态（goal）在 wunder 里**是什么**、它受哪些**不变量**约束、它与相邻机制（定时任务、子智能体、引擎排队）的**职责边界**在哪里。

目标态的一句话定义：**按模型轮次预算驱动的会话级持久目标**。用户给一条会话线程设定目标正文后，引擎在线程空闲时自动发起「目标轮次」持续推进，直到目标完成、被阻塞、或轮次预算耗尽。

本页只写边界、不变量、理由与缺口。端点清单、字段逐条语义、常量速查与操作口径在技术说明书第 13 章（[../技术说明书/13-目标态系统.md](../技术说明书/13-目标态系统.md)），本页不复述阈值表。

## 3. 不变量

I1–I8 是目标态的设计红线，改动目标态代码前先对照这张表。

1. **I1 预算按模型轮次计。** 预算单位是 `rounds_started / max_goal_rounds`，默认上限 256。不存在按 token 或墙钟时间计的预算维度。
2. **I2 驱动三门。** 一个目标轮次被自动发起，当且仅当：phase 为 `active`、进程内有 `Armed` 标志、`rounds_started < max_goal_rounds`（`goal/driver.rs:353`）。三门缺一即不续跑。
3. **I3 入队失败即阻塞，不重试轰炸。** 驱动轮次入队失败时，目标直接转 `blocked`，写 `blocked_code=queue-failed` 与可读的 `blocked_message`（`goal/driver.rs:370-378`）。驱动器不静默吞错、不无限重试。
4. **I4 自报阻塞有最低轮次门槛。** `blocked` 主要由模型经 `update_goal action=blocked` 自报，且要求同一阻塞条件已持续至少 `BLOCKED_AFTER_CONSECUTIVE_ROUNDS=3` 个目标轮（`goal/tools.rs:302-313`，不足门槛返回 `GOAL_TOOL_BLOCK_THRESHOLD`）；该门槛同时随 goal 策略注入系统提示词，指导模型「困难、不确定或仍有可用进展不构成 blocked」（`goal/prompt.rs:23-35`）。引擎侧的自动阻塞只有入队失败这一条硬路径（I3）。
5. **I5 armed/disarmed 不持久。** 驱动许可是进程内状态（`goal/types.rs:76-90`、`goal/service.rs:55-63`；记录层注释明示 activation 永不持久化）。进程重启、会话恢复或分叉后，目标可能仍是 `active` 但处于 disarmed，不再自动续跑——恢复路径是 `update_goal action=resume` 重新 arm（策略文本见 `goal/prompt.rs:30-33`）。这是刻意的：重启后自动烧预算是事故，不是特性。
6. **I6 权威性靠宿主盖章。** 人类指令与目标轮次的区分不靠模型自觉，而靠宿主在请求 overrides 上写入的 `__source=human` / `__goal_round` 标记（`goal/authority.rs:12-16`）；模型无法设置这两个键，因此无法伪造「人类说了什么」。运行时侧 `is_goal_round` 让目标轮不再重复发出需要人类权限的 goal 管理调用（`orchestrator/types.rs:35-43`）。
7. **I7 冻结的 system prompt 不因目标改写。** 每个目标轮的续跑指令是一段渲染后的 `<goal_round>` 消息，作为普通会话历史项保留（`goal/prompt.rs:7-21`），目标正文以 JSON 数据嵌入以防正文升格为指令；这不回写线程 system prompt，符合「线程提示词首次确定后冻结」的全仓约束，也保护大模型 API 的提示词缓存前缀。
8. **I8 状态迁移只能前进或显式。** `revision` 是并发控制锚点（每次持久化变更自增，CAS-on-revision），`rounds_started` 只增且 `max_goal_rounds` 不得下调到已起轮次之下（`goal/service.rs:230-245,423-442`）；phase 的四值迁移由受控入口（`/goal` 命令、HTTP、WS）或驱动器写入，模型工具按动作与权威分级获得写权限。

## 4. 工具面：三个工具、运行时注入

模型看到的是三个独立工具，而不是一个带 action 的万能工具：

| 工具 | 角色 |
| --- | --- |
| `get_goal` | 读取当前目标快照，不改状态 |
| `create_goal` | 建立新目标 |
| `update_goal` | 更新目标，动作枚举 `edit \| pause \| resume \| complete \| blocked`（`goal/tools.rs:85`）；另有别名 `goal` 归一到 `update_goal` |

注册与注入方式：三个工具随内置工具规格统一注册（`services/tools/catalog.rs` 中 `specs.extend(goal::goal_tool_specs())`，约 :1136），并有别名 `goal` 归一到 `update_goal`（同文件别名表约 :1180）；它们**不对桌面端开放选择**（`DESKTOP_HIDDEN_TOOL_NAMES`，`services/default_tool_profile.rs:24-30`），由运行时按会话自动注入。设计理由：goal 工具是会话语义的一部分而非可插拔能力——是否具备目标态取决于会话本身有没有目标，把选择权交给开发者只会产生「选了工具却没有会话」的组合态。`update_goal` 的动作侧有权威分级：需要人类权威的动作校验 `__source=human` 盖章（I6），`blocked` 必须携带 `blocked_reason`（`goal/tools.rs:294-301`）。

## 5. 职责边界：分清四件事

四个机制都可能造成「线程在没人发消息时自己动」，但语义完全不同，文档与排障时不得混用：

| 机制 | 触发源 | 作用域 | 与目标态的分界 |
| --- | --- | --- | --- |
| **目标态** | 引擎驱动器（进程内 Armed + phase） | 单会话、按模型轮次预算 | 续跑**准入**：决定空闲线程是否继续追同一目标 |
| **定时任务（cron）** | 外部时钟（调度循环 claim_due） | 可指向当前会话或新建 isolated 会话 | **外部触发**：到点投递新输入，与目标是否 active 无关 |
| **子智能体** | 主智能体在执行中临时 spawn | 独立子会话，任务结束回收 | **临时工作单元**：不携带目标态预算语义 |
| **引擎排队（session queue）** | 同用户在运行中再发消息 | 会话级挂起、按序起跑 | **并发调度**：解决多轮次抢锁，不做任何「继续追目标」判断 |

排队与目标态的交互只有一条：驱动轮次入队失败即转 blocked（I3），排队本身的忙判定不受目标影响。

## 6. 入口与前端覆盖

- HTTP：`GET/PUT/DELETE /wunder/chat/sessions/{session_id}/goal`（`api/chat_goal.rs:13-20`）。
- WS：`/wunder/chat/ws` 上的 `goal.get` / `goal.set` 多路复用指令（`api/chat_ws.rs:1036`）。
- 人类侧 `/goal` 命令语法由 goal 域自己持有：`/goal [<objective>|clear|edit <objective>|pause|resume]`（`services/goal/command.rs:10`），空参为查看当前目标。前端落点：蜂巢 `frontend/src/components/chat/MessageGoalBar.vue`、蛹 composer 目标横幅（`frontend-slint/ui/composer.slint:680` + `crates/wunder-desktop/native_follow.rs:344`）、舵机斜杠命令（`crates/wunder-cli/slash_command.rs:92`）。

**现实缺口：舰桥没有 goal 界面。** `web/` 内无任何目标态面板，管理员目前只能通过后端 API 观察目标记录。这与「面板Loaded 死条目」类残留同属工程缺口，见第 9 节。

## 7. 为什么预算按轮次，不按 token 或时间（反例）

旧设计按 token 预算 + 墙钟统计驱动，这条路已被移除，原因有三：

1. **不可判定。** 引擎只信任 provider 观测到的 usage token（`orchestrator/execute.rs:410-412` 口径）；provider 计量口径不一、部分响应缺 usage，用它做「继续/停止」的硬门等于把调度建立在最不可靠的输入上。轮次数是引擎自己数出来的（`execute.rs:435` 主循环自增），永远可得。
2. **语义错位。** 「目标推进了多少」的自然单位是模型轮次（一次模型调用及其工具批次），不是计费单位。用户设定「最多推进 256 轮」可直读；「最多烧 N token」在不同模型间不可比。
3. **时间预算与离线形态冲突。** 蛹/舵机默认本地运行、允许长时间离线与重启，墙钟累计会惩罚挂机用户；轮次预算则对停机免疫（反正 armed 不持久，I5）。

## 8. 存储设计要点

- 目标与会话同生命周期：记录以 `session_id` 挂会话、`user_id` 做归属校验；删除会话时目标随行删除（`delete_session_goal`，调用点 `api/chat/sessions.rs:1084`）。连接断开、页面切换不触碰目标。
- `objective` 纯文本归一后持久化，上限 `MAX_OBJECTIVE_CHARS=4000`，所有入口共用同一校验（`validate_objective`，`services/goal/service.rs`）。
- `revision` 单调、CAS 更新；`rounds_started` 只增；`blocked_code`/`blocked_message` 仅在 blocked 期存在（记录注释 `storage_records.rs:299-301`），保证「为什么停了」在台账里可直接回答。
- 原型期硬切换：检测到旧预算形态的 `session_goals` 表即整表丢弃重建为 revision/phase 形态（`storage/sqlite/schema.rs:274-282`，`storage/postgres/schema.rs` 同型）；这与「无版本化迁移脚本」的存储总策略一致。表结构与双方言细节见技术说明书第 13 章。

## 9. 缺口清单（如实记录）

1. 舰桥无 goal 治理界面，API only（`web/modules/` 无对应模块）。
2. armed 不持久意味着「恢复后不自动续跑」是用户可感知的行为差异，依赖模型按注入的策略文本响应人类「继续」诉求来重新 arm（`goal/prompt.rs:30-33`）；各端提示强度不一，属体验缺口。
3. 旧文档语义（token 预算、`budget_limited`、`[GOAL_CONTINUATION]` 等）仍散落在历史章节，凡引用本页的文档重写任务须按第 2 节清单清洗。
4. 集成测试夹具残留旧形态：`crates/wunder-runtime/tests/session_goal_storage.rs` 仍按 `token_budget`/`tokens_used`/`STATUS_BUDGET_LIMITED` 构造记录，与当前 `SessionGoalRecord`（revision/phase 形态）不一致，属待清理的工程欠账。

## 10. 做错回哪儿查

| 症状 | 第一落点 | 第二落点 |
| --- | --- | --- |
| 目标 active 但线程不动 | 是否 Armed（进程重启/分叉后未 resume，I5） | `rounds_started` 是否已达 `max_goal_rounds`（I1） |
| 目标莫名转 blocked | `blocked_code`（`queue-failed`？I3） | 模型自报 blocked 的门槛与 `blocked_reason`（I4） |
| 模型声称「用户要求暂停」 | `__source` 盖章链（I6） | 线程轨迹中该轮的 `is_goal_round` |
| 重启后又自动烧轮次 | I5 是否被破坏（armed 被持久化即为回归） | `goal/service.rs` 的 CAS 路径 |
