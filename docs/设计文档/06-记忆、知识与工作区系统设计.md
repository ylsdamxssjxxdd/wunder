# 记忆、知识与工作区系统设计

> 约束范围：本册约束长期记忆的分层与生命周期、prompt 注入的冻结不变量、知识库三型边界、工作区多根模型与隔离责任归属、用户世界域的定位。表结构、限额数值与配置键的完整清单见 `../技术说明书/06-数据存储、工作区与配置.md`，本册不复述。

## 1. 定位

记忆、知识、工作区共同构成智能体的「资料现实层」，三者回答不同问题：

| 子系统 | 回答 | 真相位置 |
| --- | --- | --- |
| 长期记忆 | 应该记住什么 | `services/memory.rs`（记录 CRUD）、`services/memory_fragments.rs`（片段与生命周期）、`services/memory_auto_extract.rs`（提取落库） |
| 知识库 | 需要查什么资料 | `services/knowledge.rs` / `services/vector_knowledge.rs` / `services/ragflow_knowledge.rs` |
| 工作区 | 真正操作什么文件 | `services/workspace.rs` + 沙盒容器 |

## 2. 记忆三层与 tier 生命周期（不变量）

内容分三层（`MemoryFragmentRecord`，`wunder-core/src/storage_records.rs:718`）：

| 层 | 字段语义 | 用途 |
| --- | --- | --- |
| L0 | 标题（`title_l0`） | 索引与注入清单，进 prompt 的只有这一层 + memory_id |
| L1 | 摘要（`summary_l1`） | 召回结果的中间表示 |
| L2 | 正文（`content_l2`） | 详情，只在 `记忆管理` 工具按 memory_id 检索时取回 |

生命周期 tier（`services/memory_fragments.rs:24-27,43-48`，已实测）：

| tier | 进入条件（关键阈值） |
| --- | --- |
| `core` | access_count ≥ 10 或 hit ≥ 4（另有评分门槛 0.72） |
| `working` | 默认层；access ≥ 3 且 hit ≥ 1 可维持（评分门槛 0.38） |
| `peripheral` | 低分或老化（60 天）沉降 |

配套不变量：

- 作用域 `user_id + agent_id`，缺省 agent_id 为 `__default__`（`services/memory.rs:14-15`）。
- 冲突用 `supersedes` 链表达，状态 `active | superseded | invalidated`；不做物理覆盖，保留演化轨迹。
- 召回默认 6 条、上限 30、列表上限 200（`memory_fragments.rs:33-35`）；**语义召回当前禁用**（`MEMORY_SEMANTIC_RECALL_ENABLED = false`，:36），embedding 表存在但不参与在线召回——文档不得写「向量召回记忆已上线」。
- 自动提取在轮末触发（`orchestrator/execute_tools.rs:290` → `spawn_auto_memory_extraction`，`memory.rs:1806`），提取器是「启发式 + LLM 候选」，构造请求与落库分离在 `orchestrator/memory_auto_extract.rs` 与 `services/memory_auto_extract.rs`。

## 3. 注入一次的冻结不变量（本册最硬的约束）

**长期记忆只允许在线程初始化时注入一次；线程 system prompt 一经确定即冻结。**

代码保证链（均已实测）：

| 环节 | 位置 |
| --- | --- |
| 冻结读取 | `orchestrator/prompt.rs:290-301`：已存 prompt 命中即原样复用 |
| 首次快照 | `prompt.rs:304-307`：首次确定时把 AGENTS.md 快照进线程 prompt |
| 记忆注入唯一口 | `append_memory_prompt`（`memory.rs:1741`）生产调用只有 `prompt.rs:334` 一处，且在冻结分支内 |
| 持久化 | `build_session_system_prompt_item` + `committer.append_item`（`prompt.rs:353-370`） |

注意：`orchestrator/context.rs` **没有**冻结逻辑，`runtime_snapshot.rs` 只是运行态快照 API——旧文档把这两处当冻结依据是错的。

理由：注入的形态是记忆清单（inventory，只含 memory_id + L0 标题，`recall_for_prompt_inventory`）。反复注入会改写 system prompt 前缀，破坏大模型 API 的 prompt 缓存复用，并让同一线程的历史语义随记忆状态漂移（不可复现）。冻结保证「同一线程的每一轮请求共享同一个稳定前缀」。

推论：记忆变更要生效于既有线程，只能通过工具按 memory_id 检索进入当轮观测，不能回头改线程 prompt。

## 4. 知识库三型（边界与选型理由）

三型由配置 `base_type` 归一（`wunder-core/src/config.rs:1831-1844`，已实测）：

| 型 | 实现 | 选型理由 | 边界 |
| --- | --- | --- | --- |
| Literal | `services/knowledge.rs`：内置词面匹配 + LLM 二次筛选 | 小库、文档量有限时零外部依赖、结果可解释 | 默认最多 5 文档、候选 80 |
| Vector | `services/vector_knowledge.rs`：内置向量库（`vector_documents`/`vector_chunks`） | 中等规模语义检索，仍不依赖外部服务 | chunk 800 / overlap 100 / top_k 5；磁盘根 `config/data/vector_knowledge` |
| Ragflow | `services/ragflow_knowledge.rs`：外部 RAGFlow HTTP 客户端 | 大库、需要专业切分（14 种 chunk_method）与重排 | 外部服务可用性成为运行时依赖，超时、score_threshold 必须显式配置 |

共同不变量：

- 知识检索**按需召回**，每库动态注册为独立工具（取代旧 `knowledge` 单工具），不允许把整库内容灌进上下文。
- 三型共享同一治理：都从 dispatch 的知识库分支进入（见 05 册），受同一裁剪通道。
- 向量检索不是唯一手段也不是默认前提；Literal 路径必须保持可用。

## 5. 工作区多根与新隔离边界

工作区根有三类来源，语义必须一致：

| 根 | 形态 | 位置依据 |
| --- | --- | --- |
| 本地目录 | 蜂窝/舵机的个人工作目录 | 蜂窝 `~/.wunder/workspace`（`wunder-desktop/runtime.rs:469-505`）；舵机配置化 |
| 云端目录 | 呈现为 `/workspaces/<user>/workspace` | `PUBLIC_WORKSPACE_ROOT = "/workspaces"`（`services/workspace.rs:44`）；公共路径、真实路径与沙盒容器内路径**三者同名同义**（2026-10-13 变更） |
| 远程设备目录 | 互通场景下本地设备的目录经影子投影暴露 | `07-接入、网关与渠道系统设计.md` |

**新边界（2026-10-13 口径，文档必须照此写）：隔离由沙盒承担，路径校验不再兼职。**

- 云端读/写/执行类工具一律在沙盒内执行：`execute_in_sandbox` 在 server 形态必然接管，无沙盒端点**直接失败、不回落宿主**。
- 每用户一个容器、只挂本用户目录，沙盒 `allow_roots = ["/"]`——容器内整树可写是安全的，因为容器边界就是租户边界。
- `/workspaces` 公共分支不再做越界拒绝；`is_within_root`（`wunder-core/src/path_utils.rs:47-53`）的职责收敛为**路由一致性与误操作防护**（canonicalize + Windows verbatim/大小写归一），不是租户隔离机制。
- 舵机仍保留配置化工作区边界（本地无容器，fence 仍是主要防线）。
- 容器映射按 scoped_user_id；`USER_PRIVATE_CONTAINER_ID = 0`、沙箱容器 1..10（`wunder-core/src/storage_constants.rs`）。

旧表述「云端路径校验负责隔离」已失效，不得再写。

限额与缓存方向（数值出处见技术说明书）：上传/转换/附件各有独立上限；工作区树缓存有 TTL 与行数上限；写入经单写队列；这些都必须有界。

## 6. 用户世界：站内 IM 域，不是工具

- `user_world` 是站内 IM 域：联系人 / 会话 / 群 / 消息 / 事件五表（`user_world_*`），API 前缀 `/wunder/user_world/...`，限额均为有界常量（`services/user_world.rs:14-19`）。
- **用户世界工具已删除**：dispatch 无对应分支。智能体不以「工具」身份读写用户世界；用户世界消息与智能体线程是两套域，只在投影层并列呈现。
- 设计含义：把「像 IM 一样的用户社交面」与「智能体执行面」分开建模，避免智能体获得无界的站内消息写能力。

## 7. 反例与缺口

| 项 | 现状 | 性质 |
| --- | --- | --- |
| 语义召回 | 表与 embedding 缓存都在，在线召回开关为 false | 写成「已支持向量召回记忆」即失实 |
| 冻结依据误引 | 旧文档引用 `context.rs` / `runtime_snapshot.rs` 作冻结依据 | 已纠正，依据在 `prompt.rs` |
| 附件与临时目录 | `temp_dir`、doc2md 等是传输通道，不是长期业务存储 | 保持：业务数据只落工作区或存储 |
| `memory_task_logs` 等旧表名 | 以 `storage/sqlite/schema.rs:790-896` 实际五表为准 | 文档跟代码，不跟旧清单 |

## 8. 验收判据

- 同一线程第二个轮次的 system prompt 字节级不变（含记忆注入）；新增记忆只能在后续轮次的工具观测里出现。
- 三型知识库的工具都由库名动态注册，删库即删工具，无残留注册。
- server 形态任何文件/命令工具在沙盒端点不可用时 fail-fast，不出现宿主回退日志。
- 蜂窝、舵机、舰体三形态下「工作区」呈现路径规则一致，仅根位置不同。
