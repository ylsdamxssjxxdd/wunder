# 经验教训（每次一条）
- 2026-10-09 悬停高亮「变白 + 抖动」和回复完「多一个气泡」，两条都是同一类：把两个不该各自成立的东西叠在了一起。（一）**Slint 的行内 hover 底色只能是行容器自身的 background，命中区要在内容之前声明**：把色带做成声明在正文之后的同层覆盖 Rectangle，绘制顺序就把它压在了标签上（浅灰盖深字，读起来像「变白」）；而它的 background 在 transparent 与不透明之间来回切换，命中路径也跟着来回变，表现就是抖动。修法没有第二条路：色带即容器底色 + TouchArea 先声明，正文块本来就是这么写的、所以只有它没坏。（二）**没有真鼠标也要能验证层序**：把 `x.has-hover ? A : B` 临时改成常量 `A` 渲一张图，一眼就能看出谁盖住谁，比读源码可靠，也比猜鼠标位置快；改完记得用备份还原，别把手改的分支留在文件里。（三）**跨来源的身份不能靠 id 相等做交接**：直播轮次用会话 id、持久轮次用根消息 id，两个 id 永远不会相等，于是「快照是否已接管这一轮」的判断恒为假，走成拼接分支，同一轮被画两遍。判据要换成状态 + 结构差分：本轮是否已落定（回合结束置位、新回合清零），以及快照尾部相对已渲染前缀是否推进（数量与最新一条身份都比，因为有界轮次表会从头部丢弃，只比数量在长会话里会误判）。这类 bug 的回归用例必须按真实形状构造两侧不同的 id，用一个 id 自洽的夹具测不出来。
- 2026-10-09 「偏黄」查了一个死枚举值，「折叠没反应」查了一个没人读的标志位，同一类 bug 的两个方向。（一）**缺省枚举必须是自己白名单里的成员**：主题校验只接受四个名字，而原生缺省、前端归一缺省和设置页第一个名字都是退役的历史名，于是所有按主题分支的中性色一律走 else 回退，页面拿到一份过期暖黄——功能全正常、没有一处报错、用户只说「底色太黄了」。这类 bug 只能靠把实际取值量出来发现（截图逐像素采样），读源码看不出来，因为每个分支单看都对。规矩：①同一枚举的「合法值集合 / 缺省值 / UI 展示名单」只允许有一处定义，其余从它派生；②复制出去的色值副本（各面板各写一份 theme global）一律删掉改成引用全局，否则它会以过期值继续生效；③改枚举时给旧值写归一化映射而不是报错，配置文件能自愈。（二）**状态要问「谁读它」**：批次折叠态被归约器逐行写入、随事件反复刷新、还参与下标位移重算，但视图里没有任何消费者，表现是箭头转了内容不动，看起来像样式问题。检测办法是给状态配一条渲染断言（同一批行，折叠态与展开态的可见行数必须不同），而不是只测写入。（三）两个只有实测才暴露的细节：①把可见性条件同时压句柄行和条目行，会把句柄一起藏掉，用户再也展不开——「常驻的把手」要按类型豁免而不是按分组豁免；②布局内边距与父级已有缩进会叠算（一处 44px 量出 68px），像素级对齐必须量不能心算。（四）采样前先 `cargo build`：`cargo test` 不重建 bin，第一轮量到的仍是旧产物色值，会误判成「改了没生效」。
- 2026-10-09 走查用例把「服务端预置内容」当运行前提，环境一变就整条红。蜂巢文件区 §6.2 走查原本假定新用户的云端根目录已有 agents/global/knowledge/skills（那其实是智能体内视层的落地时机，不属用例可控范围），本轮把新建目录/移动/复制改成右键菜单项后真机复跑，两条用例在第一条断言（「刷新」后应渲染出根目录行）就全红。用只读 HEAD 副本（`git show HEAD:<path>` 导出的同名 spec）跑出完全相同的失败签名，才确认是前提不再成立而不是自己改坏的。规则：①端到端走查必须自带夹具——登录前用 `/workspace/dir` + `/workspace/upload` 铺好「根文件 + 一个含子文件的目录」，服务端预置内容改成 annotation 记录而不作硬断言；②删 UI 入口时先确认它是不是某条用例的唯一触发路径，并把「入口已下线」写成负向断言（打开行菜单断言不含移动/复制），而不是直接删掉这段覆盖；③依赖「空白落点」的用例要把前置条件显式断言出来（量 `.workspace-files-rows` 之下还剩多少高度），否则落点静默命中某一行、弹出的是行菜单，要等到很后面才失败且看不出原因。附带一条页面脚本时序：Vue 的 `@contextmenu` 处理器改状态后菜单要下一拍才进 DOM，同步读 `.workspace-files-menu-item` 必拿到空数组；隐藏标签页里 `requestAnimationFrame` 根本不触发，浏览器内探针一律用 `setTimeout` 让拍。
- 2026-10-09 舵机 win7-x86 首次真机跑通，三条教训。（一）**builders/ 下的 .ps1 不能随手写中文**：这些脚本没有 UTF-8 BOM，Windows PowerShell 5.1 按 cp936 解码，注释里的中文字节能把下一行黏进注释，表现是变量恒为空、`Test-Path : 参数为空`，而错误消息自身又是乱码，看起来像路径问题。本轮就是给发布脚本加两行中文注释导致资源目录根本没生成。规矩：.ps1 内注释一律英文（仓库其余构建脚本皆如此），要中文必须带 BOM（参考 win7_host_tools.ps1）；排查先 `grep -cP '[^\x00-\x7F]'` 看有没有非 ASCII，再怀疑逻辑。同源第二个坑：`Set-Content -Encoding UTF8` 写出带 BOM 的 YAML，而引擎模板读取用 serde_yaml 会直接拒解析——发布资产用 `[IO.File]::WriteAllText(..., (New-Object Text.UTF8Encoding $false))`，并给模板读取补 BOM 容忍（核心配置加载器早就做了，舵机自己的模板读取是漏掉的第二个入口）。（二）**「找不到项目根」的默认行为不是报错而是静默降级**：无界祖先上溯以「存在 config/wunder.yaml」判定项目根，会把用户主目录里某次服务端部署留下的 YAML 当成自己的引擎模板，连带继承它的密钥与 allow_paths；更阴间的是它还能跑通——同一条提问的 prompt 从 7k token 掉到 169，工具与提示词全部消失却一句不错。判据要写成「结构性标记」而不是「文件存在」：源码检出须同时具备工作区清单与模板，随包资源只认 exe 同级与 exe 同级 resources；本地形态的工作区边界更不能从模板继承，allow_paths 由本地自有四根整体重建，否则部署机留下的路径直接把「工作区」变成摆设。（三）**协议类默认值必须在真机上看产物，不能只看代码跑通**：用户层 provider 投影把 tool_call_mode 钉成文本标签协议，功能上「能用」（工具确实执行了、文件确实写了），但调用块被写进回复正文并原样打到 stdout，模型还会按中文显示名猜工具名触发「未知内置工具」失败；同一任务换成原生 function calling 才是工具卡与正文分离。验证口径就两条：非 TTY 的 stdout 是否干净、多轮里是否出现失败工具卡——这两条在纯单测与快照测试里都看不见。附带一条：展示层兜底（config show/模型列表/状态快照）应复用引擎的解析函数，别各自假设一个默认值，否则展示与生效值长期不一致。
- 2026-10-08 Postgres schema 的 batch_execute 是「一整段多语句隐式事务」，CREATE TABLE/INDEX 之间存在三类列漂移，且全新库与老库暴露的是**不同**形态，只测一种永远测不全。本轮实战三处：①chat_sessions 建表缺 workspace_id，batch 内 idx_chat_sessions_workspace 引用它——全新库必炸；老库因表已存在（旧版含该列）跳过 CREATE TABLE 而隐身。②老库 chat_sessions/user_tokens 缺新列（workspace_id/family_id）时，batch 内同名索引照样炸——因为补列的 ensure_* 迁移排在 batch **之后**，顺序反了；修法是把索引创建挪进对应的 ensure_* 函数（先补列再建索引），batch 里只留与新表同批诞生就成立的索引。③session_goals 是硬切换设计（legacy 形状整体删除重建），ensure 只删不建、注释却写 rebuilt，且删除排在 batch 后：batch 内 phase 索引对旧表先炸，即使不炸删完也没人重建——修法是把 legacy 清理挪到 batch **之前**，删掉后由 batch 的 CREATE TABLE IF NOT EXISTS 按当前 schema 自然重建。规矩：①凡 batch 内索引/约束引用的列，要么在 CREATE TABLE 里、要么其 ensure_* 迁移必须在 batch 前完成补列，索引本体跟着迁移走；②「删表重建」类硬切换的清理必须排在 batch 前；③验证必须三管齐下：全新库首跑、重复跑（幂等）、对真实老库预演（把 batch SQL 提取出来 psql -v ON_ERROR_STOP=1 复跑，每修一处就重跑，能连环钓出后面所有漂移，本轮 432/512 行两处就是老库预演钓出来的）；④报错只有「db error」时别猜，提取 SQL 原文直接复跑，第一手错误行号立刻现形；⑤Docker 验证走 entry 脚本：源码比 target/x86/release/wunder-server 新就会自动增量重编，重启容器即可，健康检查 curl /wunder/i18n 返回 200 且日志出现 init_storage_done 才算过。
- 2026-10-08 做输入区上方悬浮状态条（蜂巢 Vue + 蜂窝 Slint 双端对齐外部参考图）攒下四条。（一）**本环境跑 `vite build` 会被 safe-delete 批量删除保护拦下**：vite 清空 `dist/assets`（>50 个文件）触发 `[SAFE_DELETE_BULK_CONFIRM_REQUIRED]`，报错在 `[vite:prepare-out-dir]` 阶段——此前 `✓ N modules transformed` 已完成，说明代码没问题、是环境保护误伤；验证构建改用全新输出目录 `vite build --outDir ../temp_dir/fe_build_verify` 即全绿，别顺着报错去改代码。（二）**悬停弹层与触发钮之间的视觉间隙会吃掉 mouseleave**：弹层绝对定位在钮上方留 8px 间距时，指针穿越间隙落在两元素的命中区之外，mouseleave 先于抵达弹层触发、弹层在移过去路上就关掉；修法是弹层打开时给根元素加一个覆盖间隙的透明桥（`::before` 定位到 `bottom: 100%`），Slint 侧同型问题用常驻 bridge TouchArea（`enabled: capsule.has-hover || self.has-hover` 靠 has-hover 自锁，参考 ContextUsageIcon）。（三）**目标暂停/恢复走 PUT `action: pause|resume`**（`api/chat_goal.rs` 的 `goal_command_from_payload`），`{status: 'active'}` 这类载荷没有 `action` 也没有 `objective` 会被 400 拒绝——旧 MessageGoalBar 的「继续」按钮一直是这样坏的；接 goal API 前先核对 `GoalUpsertPayload` 的分支。（四）**Slint 挂载顺序即视觉顺序**：VerticalLayout 里先写在上；子代理把状态胶囊挂在 GoalBanner 之后编译照样通过，`slint-viewer --screenshot` 离线截图一眼看出顺序反了——布局类改动用 viewer 截图验收，不要只信编译。
- 2026-10-07 隔离副本跨树共享 `CARGO_TARGET_DIR` 会在依赖元数据上骗人：主树被别的开发者改过 `wunder-core`（`UserAgentPresetConfig` 新增 `customizable`、StorageBackend 新增 trait 项）而副本里的 core 已还原成 HEAD，编 `wunder-cli` 时却报「missing field `customizable`」——报错指向副本里根本没有该字段的结构体，说明 cargo 复用了另一棵树编译出的 `wunder_core` rlib。判据是直接读副本源文件确认字段不存在，再去比对报错文本；修法是给隔离副本一个**自己的** `CARGO_TARGET_DIR`（本次 `D:\proj\wunder-verify\target`），代价是一次全量重建，收益是结论只反映副本里的代码。另有两条隔离副本的维护经验：（一）用 `git show HEAD:<path>` 逐文件还原非本人改动比 `git archive | tar -x` 可靠——本仓库存在中文路径，`git archive` 在 Windows 上直接以 `Invalid empty pathname` 失败；（二）副本必须同时**删掉**工作树里 HEAD 不存在的新文件（别人新增的模块），否则旧 `mod.rs` 与残留文件会互相矛盾，还原脚本要按 `git ls-tree -r HEAD` 做双向同步（新增即删、改动即还原），只做「还原」不做「删除」会留下幽灵模块。还有一条 PowerShell 自伤：`$home` 与只读自动变量 `$HOME` 同名（变量名大小写不敏感），赋值会**失败但脚本继续跑**，于是后续 `"$home\config.toml"` 指向了用户主目录，探针往 `C:\Users\<用户>\config.toml` 写了文件并把 `WUNDER_HOME` 指到了用户主目录。写探针的路径变量一律用 `$probeHome` 这类前缀名，并在脚本开头 `Set-StrictMode -Version Latest` 让未赋值变量直接报错，别靠眼力发现赋值失败。
- 2026-10-07 前端大文件「机械合并」连续踩到两类**静态检查抓不到**的缺陷。（一）**合并进来的实现必须真的被调用**：`messengerControllerInstall.ts` 是 31 个 controller 合并成的 1.5 万行文件，24 个 `installMessengerControllerXxx` 实现被套在 `installPartN` 包装里**从未被调用**，结尾还调用了模块作用域不可见的嵌套函数；`vite build` 与 `vue-tsc` 全绿，但运行时 `ctx` 是空的、整页不渲染（该文件带 `@ts-nocheck`，类型检查根本进不去）。判据只能是**真机走一遍**：起一个隔离服务端 + 真实浏览器登录并断言主视图可见；本项目已把这条通道固化成 `scripts/check-web.py`。（二）**helper 赋值与 watcher/生命周期创建的先后顺序决定成败**：`ctx.t` 在 `installPart0`（约 256 行）赋值、`ctx.normalizeAgentId` 在文件尾部某个嵌套 installer（约 15324 行）赋值，而 `installParts` 数组**第一个执行的是 `installPart23`**——先跑的部分已经创建了 watcher/computed/组件 setup，它们引用的 helper 尚未赋值，于是 `ctx.X is not a function` 满屏、`Invalid vnode type … undefined` 连串、主视图依旧不渲染。合并这类文件时必须把「只做定义与赋值」的装配放在**最前**（或集中成一个 `installCoreHelpers(ctx)` 在入口第一行调用），「注册 watcher/computed/onMounted」放在其后；排查顺序是先用「赋值集合 vs 读取集合」脚本（本项目 `temp_dir/ctx-audit.mjs`）确认**有没有赋值**，再用真机确认**赋值够不够早**。
- 2026-10-07 验证 ANSI/颜色输出时，别用 shell 的 `2>file` 去数转义：本机命令管道会经过一层控制台再渲染，子进程 stderr 里的 `\x1b[2m` 会被吃掉（落盘文件里连一个 0x1B 都没有，换行还被改成 CRLF），于是「颜色功能没生效」的结论完全错误——代码里 `{:?}` 打印出的 `\u{1b}` 才是真相。可靠做法是用 OS 级重定向（`Start-Process -RedirectStandardError <file>`）让句柄直接指向文件，再按字节数 `0x1B`；先跑一个「写 ESC 再读回」的小探针确认测量链路本身不吞字节，再下结论。另注：同一个仓库里其他开发者可能在重构引擎（本次是蜂群/蜂房/team run 全链路移除），主树会长时间处于编译中间态；此时用「HEAD + 仅自己的改动」建一份隔离副本（robocopy 排除 target/.git/node_modules，逐个文件 `git show HEAD:<path>` 还原非本人改动，`CARGO_TARGET_DIR` 指向原 target 复用编译缓存）即可独立完成编译与测试验证，不要为了让自己编译通过去 stash 或回滚别人的工作。
- 2026-10-07 舰桥做「预设智能体 1:1 绑定」时踩到两条。（一）**跨面板复用的模态控件必须与面板的惰性初始化解耦**：影响面预览/二次确认模态的按钮原先只在预设面板 `init` 时绑定监听，于是「先打开用户管理面板 → 重建智能体」这条路径上模态弹得出来、确认按钮却毫无反应；修法是把监听下沉到「打开模态」这一步（幂等兜底绑定），而不是要求每个调用方先初始化宿主面板。舰桥的面板是懒加载的，任何共享控件的生命周期都不能挂在某一个面板的初始化上。（二）**契约未就绪要有状态机而不是分支判断**：后端接口尚未交付时，若每个调用点各自判空，很容易在同一会话里反复请求 404 端点、或在缺字段时把 `undefined` 当 0 渲染出「绑定用户 0」这种假数据。正确形态是薄适配层持有 `unknown/ready/unavailable` 三态：404/501、缺 `data` 包裹、缺关键字段统一置 `unavailable` 并短路后续请求，只读列表仍返回原字段供旧界面渲染，并留一个显式 `reset` 供刷新恢复；再用 Node + 最小 DOM 桩真跑模块断言「0 次请求未交付端点、不伪造 0、请求体符合契约」，比人工走查可靠得多。

- 2026-07-04 聊天发送结束或停止时不能只清 `loadingBySession`、controller 和 busy getter；本地 optimistic assistant 占位、runtime projection 的 model turn、legacy raw 消息数组必须一起收到终端事件并清除 streaming 标志。后端事件若只带 `model-turn:<session>:user:<round>` 这类弱模型轮次，也必须折叠到同一用户轮次已有的强本地 turn，否则停止后再发送会出现一直转圈或额外空气泡。
- 2026-07-04 聊天投影合并弱模型轮次和强最终轮次时，不能只保留最终正文气泡；速度、工具调用次数、workflowItems 和 subagents 都是用户可见投影元数据，必须按稳定业务 id 合并到保留气泡，并让渲染物化缓存按元数据内容失效。否则实时过程中看似去重成功，刷新或回到历史会话后气泡底部统计和智能体循环信息会丢失。

- 2026-07-04 智能体工具调用可能发生在同一用户轮次的强 `model_round=1`，最终回复和平均速度发生在强 `model_round=2`，而 canonical transcript 只保留一个 assistant 气泡；刷新迁移投影元数据时不能只迁移弱/legacy 轮次。单 assistant 用户轮次应合并同轮所有带 workflow/stats/subagents 的投影源，多 assistant 用户轮次再按 model turn 保守分配，否则历史会话会丢工具调用但保留最终正文。
- 2026-07-04 聊天实时渲染链路里，后到的 legacy/session snapshot 若带空 `workflowItems`、空 `subagents`、空 `stats` 或旧别名零值，只能视为“未携带投影元数据”，不能清空 canonical events 已恢复的智能体循环和速度统计；工具结果行也必须保留模型原始 tool call 参数，右键调试优先读 `toolCallRawDetail` 而不是后来覆盖的结果明细。

- 2026-07-04 蜂群派发流不能只更新蜂群本地运行状态和最终补水；它收到的 chat stream 事件也必须进入统一 `chatStore.runtimeProjection`，并在用户提交时先建立本地 user/model turn 占位。否则右侧栏和智能体卡片只能等 session hydrate 才恢复，表现为消息不同步、工具调用条目实时缺失但刷新后正常。
- 2026-07-04 蜂群画布这类二级实时视图不能靠自身 dispatch 缓存反推当前聊天上下文；进入蜂群时必须显式绑定当前消息会话 id 和所属 agent id，并让统一缓存接口优先物化 runtime projection、再兜底当前 active messages。智能体卡片如果产品语义是“工具调用情况”，就不能继续使用任务摘要、session id、模型事件或非工具 workflow fallback，否则会出现实时不渲染、必须再问一句才同步、节点条目杂乱和刷新后才恢复的假象。
- 2026-07-04 蜂群页、右侧栏、实时 watch 这类二级视图的组件卸载只能表示“本地脱离监听”，不能等同于用户停止运行；本地 `AbortController.abort()` 必须显式关闭 WS 自动 cancel，用户点击停止再走统一 stop/cancel 协议。否则从蜂群页切到聊天页会把仍在运行的会话误停止，表现为页面切换触发后端 cancel 或本地状态被写成 stopped。
- 2026-07-05 蜂群派发在创建本地 optimistic user/model turn 后，后续 chat stream、工具调用和最终回复必须继续携带同一组 `client_message_id/user_turn_id/model_turn_id/assistant_message_id`；不能只依赖后端 `user_round/model_round` 回推。否则前端实时投影会先生成 `round:N` 的额外空 assistant 气泡并排到用户消息前，刷新后才被 canonical transcript 纠正。
- 2026-07-05 execute_command 同时存在 command_session_delta 与 legacy tool_output_delta 时，前端只能选择一个源写入命令会话 tail；command_session_delta 应作为实时终端权威增量，tool_output_delta 只保留工作流兼容投影，否则聊天工具条目会把同一段 stdout/stderr 追加两次。
- 2026-07-05 命令终端实时流不能只覆盖本地 execute_command 路径；server/sandbox 执行路径也必须有独立流式协议，并把 stdout/stderr 增量桥接为 command_session 事件。前端对这类一次性在线增量应按 tool_call_id 立即关联工作流条目，但不能用较大的 command_session event_seq 推进严格顺序水位，否则后到的普通模型或工具事件会被误判为 stale，表现为终端或正文仍像阻塞到最终结果才出现。
- 2026-07-05 命令会话事件和原始工具调用必须以 `tool_call_id` 作为主关联键，`command_session_id` 只能作为别名；命令会话事件也不能用 `event_id` 兜底生成假的 tool call id。刷新补水可能先到 summary 再到 tool_call，前端应保持同一终态行并只补充原始 `toolCallRawDetail`，否则会出现重复 execute_command 条目或丢失 `timeout_s` 等原始参数。
- 2026-07-05 智能体设置页的工具选中态必须在工具目录、表单、保存 payload 和历史配置之间共用同一套 alias canonical 规则；网页抓取/网页搜索这类同时有中文运行时名和英文别名的内置工具不能只在后端识别别名，前端也要在选项 value 与已保存 tool_names 比较前归一化，否则保存成功后刷新会表现为未选中。
- 2026-07-05 智能体设置页的工具目录不能使用“配置启用”口径而保存接口使用“运行时可用”口径；带 Cargo feature 或 provider 开关的内置工具必须在 catalog 和保存过滤中共享同一可用性判断。否则会出现“页面能选、保存无报错、刷新后丢选中”的假保存。
- 2026-07-05 命令终端流式展示要区分“工具调用条目”和“进程会话条目”：聊天工作流里同一个工具调用的原始参数可用 `tool_call_id` 关联，但舵机/TUI 的实际终端进程必须以 `command_session_id` 作为主键；`tool_call_id` 只能作为启动前占位别名。否则一次 `execute_command` 拆出多条命令时，会把多个进程输出合并到同一张卡片，或者最终 `tool_result` 覆盖前一条会话。
- 2026-07-06 聊天用户轮次不能只依赖 MonitorState 的内存计数。冷启动、历史未 warm 完、很久以前的会话继续发送或异步写队列乱序时，必须先按 session 精确补水 monitor/stream events 中的最大 `user_round`，并让存储 upsert 保持 `updated_time` 单调，否则后续发送会重新从 1 开始，前端投影顺序和工具调用归属都会被污染。
- 2026-07-06 智能体循环条目的上下文占用不能复用“本次消耗 token”解析器；`context_occupancy_tokens/context_usage` 是窗口占用，`request_consumed_tokens/usage/round_usage` 是请求或计费消耗，展示层要分别解析并给回归测试覆盖。否则一次渲染优化很容易只保留消耗和时长，导致工具循环条目丢失上下文占用。
- 2026-07-06 智能体循环右键展示的“工具调用原文”只能来自真实 `tool_call` 或显式保存的 `toolCallRawDetail`；`tool_result`、`command_session_summary` 和运行时结果快照不能反推成模型调用参数。命令状态也必须读取 `exit_code/returncode/timed_out/error`，不能只相信 `status=completed`，否则失败命令会显示绿色且右键看到的是结果。
- 2026-07-07 聊天普通文本流式输出不能让每个 token 增量驱动父页面大模板、Markdown 解析、资源卡片 DOM 扫描和全局投影刷新一起跑；正文渲染应隔离成小组件，普通文本流式阶段走轻量文本路径，最终再补 Markdown，资源补水只在确实出现资源卡片时触发。否则即使后端流式很快，头像动画、工作目录树和右侧面板也会被主线程重活拖卡。
- 2026-07-07 聊天普通文本流式输出必须把“正文内容变化”和“消息结构变化”拆成两个刷新通道；稳态正文 delta 只能触发按 messageId 归属的轻量 content clock，不能递增全局 `runtimeProjectionVersion` 重建消息外壳。头像、浮动形象、工作目录、智能体循环面板和统计区都应只订阅结构或运行态信号，否则即使 Markdown 已经轻量化，父级大模板仍会被每个 token 拖卡。
- 2026-07-07 本地模型流式输出比网络 API 更容易暴露前端主线程问题：网络延迟会天然摊平 token 到达，而本地推理可能同机抢占 CPU/GPU 并把多个 delta 突发塞进同一渲染窗口。前端处理本地模型流时必须同时做 reducer 快路径、按帧合并 content clock、动画组件隔离订阅和必要的本地模型线程/资源限制，否则会表现为前几个字卡住后突然刷出一大段。
- 2026-07-07 用户可见的 `llm_output_delta` 不能作为 lossy WebSocket 事件处理，也不能在队列低水位时返回错误触发流转发循环退出；本地模型高频输出会比网络 API 更快填满内存队列，一旦中间 delta 被静默丢弃或转发中断，前端就只能显示开头并等待最终 `llm_output` 快照一次性补全。
- 2026-07-07 聊天流式卡顿排查时，debug 本身不能成为热路径负担；`chat.stream.perf`、projection shadow、render source、terminal-debug 这类大 payload 日志应保留在内存导出历史里，避免直接 `console.info` 完整对象。浏览器 console 展开大对象、序列化 payload size、以及逐 token 布局测量都会和动画、工作目录交互抢同一个主线程，导致用户看到头像和浮动形象卡顿。
- 2026-07-07 本地模型流式体验必须同时观察后端 `ttft/prefill`、上游 chunk 间隔和前端 flush 延迟；如果 `prefill_ms` 或 `max_chunk_gap_ms` 已经很大，前端优化只能减少放大效应，不能制造真实 token 流。后端 `llm_output` 需要携带轻量 `stream_timing` 诊断字段，前端 debug 需要记录 content clock 慢 flush，才能区分“模型没吐”“服务端攒包”和“前端主线程掉帧”。
- 2026-07-07 聊天在线发送流不能把持久 `event_id/event_seq` 等同于“必须连续的可渲染文本序号”；状态、工具、诊断、被过滤事件和持久化合并 delta 都可能正常占用或跳过 id。`phase=send` 的交互 WS 事件应优先保持可见投影推进，继续用 `event_id` 去重和 replay cursor 兜底；严格连续只适合 watch/replay/snapshot 等补水链路，否则状态或工具事件也会触发 `send_event_seq_gap`，让最终内容等终态才一股脑出现。

- 2026-07-08 聊天页面用 `v-show` 隐藏消息面板时，虚拟列表和保留会话类型不能跟随设置页状态退回空/全量渲染；否则长会话从设置页回聊天页会销毁再重建大量消息 DOM。气泡操作按钮也应使用行级 hover/focus 的 CSS 隐藏，避免常态噪声和气泡内部 hover 规则造成额外样式 churn。

- 额度账户的零余额是有效业务状态，不能作为初始化或迁移标志；迁移必须依据 schema 并在事务内完成。请求准入与扣费必须共用数据库锁，资料、登录与密码更新只能写身份字段，防止旧账户快照覆盖并发扣费。回归应覆盖最后一份额度竞争、跨日发放、精确设零和重启不补发，并在 PostgreSQL 与 SQLite 上验证。

- 2026-09-23 额度由 Token 计费切换为模型请求计数后，不能沿用旧消息的 quotaConsumed 字段展示线程额度，也不能用用户总用量差值归因。列表与流式事件需共享独立的线程累计值，重放取最大值；监控事件裁剪或历史基线缺失时保留未知，避免将不完整记录显示为零。

- 2026-09-23 蜂窝默认切换原生后，不能继续沿用仅 Slint 前端的离线 vendor 清单；必须按目标平台解析完整后端依赖，并在缺包时明确提示，或使用完整 Cargo registry 离线缓存。默认启动回归需在隔离目录不带参数运行，验证无 bridge 子进程/监听、窗口关闭与跨进程配置回读；仅显式原生测试入口成功不能证明默认启动已迁移。

- 2026-10-01 删除旧流式持久化队列时，先沿实际读取路径核对恢复协议，再调整测试断言；函数名仍含 stream_events 不代表仍读取旧表。ThreadLog 提交与 hub 通知必须成对覆盖命令、压缩和排队入口，已有 receipt 时直接发布其 cursor，避免额外读库。测试应验证持久版本、状态迁移与通知，而不是为了旧表断言恢复双写。

- 2026-10-01 聊天 durable feeder 的正确性不只取决于 change_seq 幂等：同一连接同一会话在 start、watch、resume 三种入口之间必须有明确所有权和取消边界。start 结束后若其 feeder 未停止，随后 watch 会并发推送相同 change；遗留的本地占位气泡也不能参与 v2 watchdog 的活性判定，否则会持续重连并扩大重叠窗口。

- 2026-10-01 聊天回归不能只对 reducer 输入做孤立断言：应以可复放的用户会话剧本经生产帧适配器进入真实 MessengerView，逐段等待渲染，覆盖工具、主动/被动压缩、目标续跑、取消、排队和断线重连。虚拟列表的 DOM 数量不是历史总量，验收需分别核对完整 durable 投影的稳定气泡序列与可见窗口中的实际文本。

- 2026-10-01 一个模型轮次的正文、终态和统计必须写入同一个稳定 `{turn}:text-{round}` Item。将统计只写到随机历史快照，再由前端过滤该快照以避免重复气泡，会同时丢失耗时、速度和用量；而把会话级 busy 状态套到“最后一个气泡”又会在发送下一轮时复活已完成气泡。存量数据只能按 `(turn_id, model_round)` 把统计补到稳定 Item，新的后端提交必须直接更新稳定 Item；卡片展示只读自身 durable 生命周期。
- 2026-10-02 聊天页面即使已采用 ThreadLog 投影，乐观发送占位、历史补水或虚拟列表尾部固定项仍可能在短暂交接窗口把同一用户轮次的多个助手行同时送入 DOM。必须在虚拟列表入口按 durable `turn_id` 再执行一次“一用户气泡、一助手气泡”结构守卫：durable 行优先，终态清除所有遗留 streaming 标记，正文、统计和工作流按稳定身份合并。该守卫只约束显示，不能回写或替代 durable reducer。

- 2026-10-02 虚拟列表的验收必须分成两层：先用完整 durable 投影断言稳定气泡身份、顺序和终态，再滚动到目标窗口截图核验可见渲染；不能因为当前 DOM 未挂载历史项就判断消息不存在。停止必须结算原助手气泡，保留已完成工具和统计，仅将未完成项标为 cancelled；手动压缩必须使用稳定 {turn}:text-{round} 正文条目，否则 durable 投影会过滤结果。
- 2026-10-02 Slint 布局两条硬约束：一是 ScrollView 内的 VerticalLayout 子元素再绑定 `width: parent.width` 会产生 flickable.content-width → min-width → layoutinfo 的静态绑定环，编译直接报错；需要滚动的列表行只在行内绝对定位（外层仅设 height，内层用 `x/width: parent.width - Npx`），固定导航类短列表干脆不用 ScrollView。二是 HorizontalLayout 中多个固定宽度子元素（如固定宽度列表列 + 固定宽按钮行）的最小宽度会累加，主区随窗口收窄时内容被裁切而不是自适应；每个新页面都必须用 `slint-viewer --screenshot --size 760x580` 实测窄窗口，用像素采样确认右缘不再贴边，不能只看 1360 宽截图下正常。

- 2026-10-02 聊天事件注入剧本不能标成真实端到端测试：必须在报告中区分模拟、真实 UI 操作和后端日志来源，未触发的工具/压缩/排队/重连明确记为证据缺失。自动分析应独立检查用户轮次唯一性、游标连续性、终态和工具状态，并在失败时仍采集日志与整段滚动截图。长任务和 Vue 警告不能因为最终截图正确或重跑成功而被忽略；原始诊断需留存。

- 2026-10-02 durable 迁移不能只接气泡：提前 return 若跳过会话 busy、完成通知、workspace_update 和工具展示元数据，会出现正文结束但外壳仍工作中。必须从 reducer 已按序接受的变更派发副作用，覆盖 gap 补齐和重复回放；测试使用后端真实 `turn_upsert` 终态及嵌套快照行，而非自造只有 `turn_status` 的协议。新输入占位应进入同一轮次状态，不能靠渲染层字符串合并补救（取代此前将结构合并守卫作为根治手段的建议）。工具终态替换调用条目时必须保留参数、请求上下文和耗时，刷新恢复测试须验证右键调用 JSON 所读的同一字段。

- 2026-10-02 将 HTTP handler 提取为共享渠道服务时，错误类型必须沿辅助函数及所有调用点同步迁移：服务内部统一 ChannelServiceResult，只有 HTTP 边界使用 map_err(channel_service_response)，不要让 Response 回流服务层。身份参数从 String 改为 &str 后，写入拥有型字段必须显式 to_string；验收应检查 wunder-server 及部署启用的特性，不能只检查默认无特性的 runtime。

- 2026-10-02 聊天验收必须从真实输入框经模拟 HTTP/WebSocket 驱动，独立核对每轮正文、顺序、统计与展开工具结果；工具失败后模型仍可正常完成，不能用最后一条工具的 failed 覆盖 completed 轮次。模拟流式尾部必须配套 durable 正文块，否则旧尾部会掩盖最终正文。展开多个 details 应等待逐项 toggle 落地，避免测试点击互相抢占状态。

- 2026-10-02 取消后的部分正文不能依赖最终 assistant item 全文兜底。ThreadLog 文本块实际将正文、推理及 UTF-16 offset 放在事件 data 中，实时 reducer 和原子快照必须走同一归一化入口；回归必须使用真实存储信封、空全文 item 和清空 tail 后的重载。多个 Markdown 行同帧渲染时，资源加载调度必须合并消息键，并为批次设上限；页面清理须隔离旧异步请求，错误清理只能删除属于该请求的缓存，避免迟到结果污染新页面。浏览器验收应覆盖双图片、缓存返回、刷新和下载中切页。

- 2026-10-02 并发上限造成的排队必须以 durable queue 条目表达，排队气泡与后续执行共用同一 user turn；前方人数只能取 queue_ahead，wait_ahead 包含执行中占用槽位，不能直接展示。对 snapshot 新增并行请求时，竞态测试不可断言固定请求数，且所有挂起 mock 响应必须在 finally 释放。

- 2026-10-02 监控接口的主机指标采集可能在容器磁盘枚举时阻塞十几秒，不能放在管理请求路径同步执行；应返回最近快照并用单飞后台刷新。聊天停止是会话级动作，不能同时逐个取消 start、watch、resume 再发会话取消；请求 abort 也要关闭自动 request cancel，避免一次点击重复触发后端结算。

- 2026-10-02 聊天流式迁移后的页面副作用不能只依赖独立轮询状态：ThreadLog 已确认的正常 `completed` 终态到达时，应携带稳定 `(session_id, turn_id, agent_id)` 触发一次 UI 完成提示，并按该身份去重；轮询仍负责状态补水，但可能延迟或暂缺 idle 行。取消和失败不能复用成功提示。真实页面剧本须直接断言这一提示，并覆盖重复帧与断线续传。

- 2026-10-02 工具循环默认展开内容必须是结果视图：只展示完成/失败、目标和极短结果摘要；调用参数、内部统计和原始 JSON 会干扰用户判断，应保留在显式调试入口中。所有工具的未知字段都必须经过有界摘要，不能直接把原始 payload 回退到页面。

- 2026-10-02 工具展示精简应保留可核验的实际结果：文件内容、命令输出与补丁增删行不能全部退化成“已完成”。状态必须先于内容分支判断，失败或待执行的写入不能用调用参数伪装已落盘内容。舵机/TUI、蜂巢和蜂窝需分别审查真实渲染入口；静态步骤示意不算工具结果接入，未知工具不得回退为整段协议 JSON。

- 2026-10-02 上下文压缩是独立工作流活动，必须按持久类型确定身份并本地化名称，不能用通用事件标题推断工具名。已有活动或调用 ID 时，找不到对应调用应创建独立条目，不得回退配对到上一个未完成工具；回归同时检查实时、快照恢复和实际组件折叠/展开标题。

- 2026-10-02 模型输出或工具完成不等于用户轮次完成，气泡终态必须由持久轮次决定；临时轮次绑定服务端身份时保留客户端消息渲染 key。线程列表展示当前工作状态，不能把历史完成状态永久显示为成功提示。新建会话可能尚无 ThreadLog，已鉴权的空快照应正常返回。工具摘要不能取代实际结果，压缩、脚本执行和记忆操作必须用真实组件验证必要信息仍可见；图片预览要验证非正方形图片在适应窗口与原始尺寸下均保持比例。

- 2026-10-02 一问一答的单气泡结构不代表拼接所有模型轮次正文。回复正文只属于最新稳定输出项，带工具调用的中间说明留在持久过程记录；后续输出尚空时不能回退展示旧说明。必须分别断言最终正文、迟到旧轮次 tail、空最终轮次与刷新恢复，避免把错误的拼接行为固化进测试。

- 2026-10-02 `/goal` 命令和自动续跑是不同执行 `turn_id`，但属于同一个根用户轮次；气泡必须按 `root_turn_id` 聚合，文本块和工具仍保留各自执行身份。受理事件、行信封归一化、快照和流式尾部失效键必须保留该关系；不能仅隐藏空头像。模拟测试必须生成真实的命令根轮次与内部 continuation，覆盖模型轮次重置、重复回放及刷新恢复，不能用单轮普通回复替代目标态。

- 2026-10-02 新聊天投影接管消息后，子任务等附属卡片也必须拥有父轮次归属和稳定运行身份，经统一持久化提交与订阅更新；仅写旧事件流或旧 messages 数组会造成条目消失。子任务生命周期独立于父回复，进度修订属于结构更新；非响应式物化缓存必须向组件发布变化后的条目列表。回归必须使用真实组件验证状态不变时的消息/计数更新、终态和刷新，额度扣除与模型请求次数分别断言。

### 固定用户轮次结构与独立 DOM 验收

- 重复助手气泡不能只靠最终消息列表去重解决。执行 turn 与用户 turn 必须分开：后端所有生命周期/快照携带根身份，页面物理结构固定为一个用户区域和一个助手区域，内部执行仅填入区域。无根输入的数据不得创建页面行。
- 测试必须用真实用户输入协议，不能用助手孤立记录要求页面生成气泡；目标测试必须生成独立续跑执行，并验证运行中、终止、恢复及刷新。最终截图之外，使用独立 DOM 观察器持续验结构，且注入重复节点验证检查器有效，计数不能因刷新清零。
- 复用可变物化对象时，下游 Vue computed 可能因 prop 引用不变而保留旧统计，出现正文完成但仍显示排队。通过浅层发布输入触发统计更新，并同时断言终态、耗时速度和排队消失；只断言最终正文不足以验收。

### 原生蜂窝同样必须区分用户轮次与模型动作

- 蜂窝不能在 model_round 增加时追加助手行，否则蜂巢修复后蜂窝仍重复。UI 模型使用强类型 user/assistant 双字段，整轮裁剪与虚拟化；取消仅结算当前字段。
- 历史恢复直接使用 root turn 和持久化 item identity；禁止用内容包含关系匹配气泡。文本块接口存在服务端分页上限，必须根据游标逐页读取，不能传大 limit 就假设拿到全部。
- Viewer 截图证明布局，原生事件投影测试证明状态处理，两者均不能替代真实模型与后台续跑订阅验收。

- 2026-10-02 原生直接流结束不代表根用户轮次结束。目标续跑与队列执行必须复用持久事件订阅：先记录游标、释放执行租约，再调度并订阅；终态需等待最终正文提交被消费。执行身份改变必须重置模型轮次时钟，但不能创建助手行。隔离 SQLite 测试应直接证明部分正文在任务完成前到达，并验证满缓冲取消、关闭订阅不取消目标、快照补水和迟到旧执行状态；只手工注入 UI 事件无法发现订阅断链。

- 2026-10-02 子智能体卡片详情不能只展示原始 JSON；用户需要按运行顺序查看模型输出、思考和工具结果。详情读取子线程自己的 durable 快照，并以独立 watch 接收更新；关闭详情只能取消 watch，不能发送运行取消。复用聊天组件到 Teleport 弹窗时必须重新建立主题变量作用域，并用真实弹窗检查标题对比度。子智能体展示的“额度”按模型请求次数统计，不能使用免扣费时为零的账户扣费字段，也不要重复显示同义指标。

- 2026-10-02 子智能体调用会产生多个模型轮次和历史 append_chat 行，历史行可能没有 model_round，但仍携带终态生成速度。投影统计不能只按稳定文本项的精确 model_round 查找；应优先精确匹配，缺失时在同一用户轮次选择带有效速度的终态统计，并增加子智能体工具轮次刷新回归。

- 2026-10-02 渠道、命令和文件提示等非网页入口必须使用同一 ThreadLog 受理、稳定回复项和提交后唤醒链路；不要只写 channel_message 或无轮次历史行。提前受理后执行必须复用身份，消费执行流必须等结算完成，缺少本轮答案不得回退上一轮内容。删除聊天线程需事务性解除渠道映射，失效映射必须换新 ID。验证包括后台推送、刷新、一问一答和删除映射的用户隔离。

- 2026-10-02 原生蜂窝不能把本地发送流当作线程订阅：渠道、计划任务等后台入口在没有本地发送时也必须可见。选中线程应持续观察 durable 提交，终态后保持监听，解除监听只释放观察者；先读游标再读历史防止初始化漏帧，按根轮次合并更新并限制缓冲。验收要从 SQLite 提交经过实际 feeder 到原生投影，覆盖连续输入、部分正文、重订阅、终态及跨用户隔离。单次模型动作完成不能提前结算用户轮次。

- 2026-10-02 定时任务创建成功不等于调度可执行：关闭调度必须拒绝创建/启用/手动运行，并在列表返回调度状态；离线回归应运行真实调度循环，验证到期领取、执行和终态落盘，不能只向前端注入完成事件。生成速度须保留正文流自身的计时，工具调用和估算用量不能使其清空；切页期间完成、返回与刷新必须一起验证。

- 2026-10-02 定时任务执行入口不能手工拼接一套简化智能体权限：缺失审批模式会回退到 suggest，造成已列出的命令/PTC 工具被拒绝。默认智能体必须按用户读取持久配置，工具别名、声明技能、冻结工具基线和授权交集应与交互入口共享实现；缺失或无权访问的显式智能体必须报错。回归需比较交互与定时请求的实际工具集和审批配置，并覆盖用户限制、线程限制与跨用户隔离。

- 2026-10-02 渠道运行开关不应阻断设置及日志的只读查询。HTTP 与原生 façade 共用服务应返回明确的 runtime_enabled，页面展示未启用状态并禁用依赖运行服务的操作；写入校验放共享服务，不能只在 HTTP handler 校验。回归须包含默认关闭配置，不能所有测试都先启用功能而遗漏首次打开页面。

- 2026-10-02 子智能体权限必须对 session/run/dispatch/parent 与批量目标统一检查同用户、同根任务树，不能只在 send 校验直属关系而让 status/close 绕过；开启同树协作后取消传播仍需保留持久祖先。进程恢复只能结算失去心跳的运行，持久层必须阻止迟到写入复活旧执行，不能自动重放工具。上下文继承按根用户轮次查询且在数据库截短文本，不复制 system 或隐藏协议；实际模型工具精简路径也必须保留范围和参数语义。

- 2026-10-02 隔离定时任务不能只把最终 answer 复制到绑定线程：这会造成新气泡只显示触发成功，模型轮次和工具条目仍落在不可见子线程。交付轮次必须复制子线程 durable workflow 条目并重写 session/turn/item 身份，保留顺序与统计；源线程缺失时才使用单条最终摘要兜底，并验证幂等重试不产生重复条目。

- 2026-10-02 聊天气泡的生成速度属于用户轮次聚合指标，必须使用所有可测模型轮次的输出 token 总数除以解码时长总和；最后一个模型轮次速度不能代表包含工具调用和多轮请求的整轮。缺少可测解码计时必须保持为空，不能用工具耗时或交互总时长伪造。

- 2026-10-02 渠道配置写入不能与运行服务开关绑定：关闭运行只应阻止连接、探测、收发消息和绑定等运行操作，新增账号与保存凭据必须可用，否则设置页会出现按钮无法点击或可点击但提交失败。

- 2026-10-03 定时任务的主线程投递不能因交互队列被关闭而直接调用编排器。受理后再争抢会话锁会留下独立 rejected 轮次，同时旧模型轮次会把失败解释为自身工具结果，形成‘内容回到上一气泡’的错觉。计划任务必须走内部强制持久队列：新根轮次和 queue 条目先落盘，锁释放后才执行；蜂巢和蜂窝只按 root_turn_id 展示该新轮次。

- 2026-10-03 durable 文本块的活跃尾部会被写入端原位重写（同一 block_index、相同起始 offset、更长正文、新 change_seq），消费 reducer 不能假设帧是纯追加；必须以 durable 块为权威内容续接并只向 UI 下发新增后缀，UTF-16 切分要拒绝落在代理对内部的边界。冒烟断言也要跟随事件语义演进（旧 final 事件已被 llm_output 权威提交 + turn_terminal 取代），并且被动观察器补水是异步的，重载断言前必须等待 Reset 到达，否则把竞态误判为数据错误。

- 2026-10-03 session=main 定时任务若只进入同一会话的等待队列，会被正在运行的原轮次反向阻塞；会话级取消还会污染后来入队的定时轮次，造成两个气泡都停在取消或运行状态。主线程定时投递应先中断并结算旧轮次，待锁释放后由新根轮次独占继续；只有 isolated 任务允许与父线程并行。

- 2026-10-03 定时任务抢占旧轮次时，旧 WebSocket watcher 的 finally 可能晚于新 watcher 返回；如果旧实例仍能清理或自发重启，就会重叠消费 ThreadLog，重复完成提示并丢失新根轮次的实时投影。watcher 的清理、重连和提示必须以当前 controller 身份校验，并在会话/轮次边界做有界幂等去重。

- 2026-10-03 微信 iLink 入站不能只依赖单一 JSON 形状或严格数字类型；协议边界应统一兼容数组、嵌套 envelope 和数字字符串，并记录原始消息数、提取数、入队结果，才能区分服务未启用、轮询无消息和解析丢弃。

- 2026-10-03 蜂群画布的派发预览线程不能直接冒充编排母线程或当前聊天线程。首次发送必须由后端按用户与蜂群持久绑定独立聊天 session，前端拿到 session 后切换消息页并复用该绑定；否则消息虽已写入 durable history，聊天页仍因未切线程而看不到。

- 2026-10-03 对接 Tencent iLink 时，二维码能成功不代表 getupdates 可用；必须同时发送 iLink-App-Id、iLink-App-ClientVersion 等客户端身份头，且二维码接口使用 POST/local_token_list。渠道 worker 应由 active 账号驱动，不能被默认关闭的部署级开关静默挡住。

- 2026-10-03 新建线程后页面卡死排查应优先检查响应式监听是否在每次回调写入等价数组；置顶、排序等操作必须幂等，否则监听依赖自身投影会形成同步重算循环。创建空线程后也不要立即重复详情水合，创建流程已完成问候语、缓存和 watcher 初始化。

- 2026-10-03 Slint 图表使用 Path 绘制数据曲线时，默认 fit 会把各路径独立缩放到自身边界，导致折线与数据点错位。按像素坐标绘制应设置 fit: preserve，并用至少三个非零、非等高的数据点渲染验证；仅通过编译或只画零值无法发现此问题。

- 2026-10-04 轻量 Markdown 降级不能用行前缀直接删除整行。围栏必须记录标记类型、长度及物理行边界，无法完整渲染的语法保留源码；流式测试需断言实际展示文字，不能只验证 raw 未丢失。长回复展示上限必须明确提示，并与完整原文复制分离验证。
- 2026-10-04 frontend-slint vendored 的 slint::Image 不是 Send/Sync，不能用全局静态缓存或后台线程预热 UI 图片；解码缓存应放 UI 线程 thread_local。蜂窝文件图标采用 build.rs 构建期 resvg 栅格化 + 生成查找表方案后，运行时无需 SVG 解码器，新增图标只改网页侧主题并用 scripts/sync_desktop_file_icons.py 重新同步即可。
- 2026-10-04 Slint 布局会把子元素的固定宽度沿嵌套布局向上收敛为最大宽度：被拉伸面板内若存在"全部子元素均为固定宽度"的 HorizontalLayout（如一排固定宽按钮），整个祖先链条会被截断回首选宽度，表现为右侧大片空白。修复方式是在该行内补一个 `Rectangle { horizontal-stretch: 1; }` 占位；给布局或包装 Rectangle 显式设置 width 不能解决，反而会再次破坏伸展分配。验证时必须用宽窗口截图确认面板真正撑开，仅编译通过说明不了布局问题。

- 2026-10-04 Markdown 表格的 TableHead 与 TableRow 是独立事件，必须分别结束表头，单元格行内代码也要写入当前单元格；代码块复制不得 trim。Slint 富内容块应显式按自身内容计算高度，图片只在后台读取、限量解码后投递像素，UI 模型不能跨线程传递。需同时验证窄窗口横向滚动与真实渲染截图。

- 2026-10-04 工具详情不能复用短摘要作为唯一数据源：补丁文件分组、行号、增删类型和命令退出码会在摘要截断时永久丢失。实时事件与历史回放必须共用有界结构化投影，展开时再创建原生详情布局，复制同步使用该投影；样式核对必须读取网页实际组件与颜色变量。

- 2026-10-04 工具条目指标对齐必须同时核对网页渲染组件和运行时字段投影：token 标签实际来自 request_usage.total_tokens/total，不能仅凭标签猜测为上下文占用，也不能递归搜索工具业务结果同名字段。回归测试应使用真实 tool_call/tool_result 元数据形状，覆盖实时更新和 durable 历史恢复。


### 2026-10-04：原生命令不能只做输入菜单
- 斜杠命令必须在发送模型前路由至共用运行时入口，菜单填入文本不代表功能已接入。受理、目标续跑、停止、历史恢复都需验证。
- 工作流是否显示必须同时检查结构化条目，不能只依赖摘要字符串；压缩失败或进行中可能没有摘要，但仍有可展开的状态与错误详情。
- 目标态与当前执行忙闲是独立状态，续跑冷却时仍需保留目标标记和停止入口。

- 2026-10-04 frontend-slint 的 ui/i18n.slint 虽是 build_i18n.py 生成文件，但存在他人未回写 catalog 的手工改动时，直接全量再生成会失败或覆盖他人工作；此时应在 catalog 加键后对生成文件做等价的局部追加，并保留 catalog 为最终事实源。Windows 控制台运行 build_i18n.py 需先设 PYTHONIOENCODING=utf-8，否则中文输出触发 GBK 编码错误。
- 2026-10-05 Slint 双列表单行（HorizontalLayout 两列各 horizontal-stretch:1）中，基于 Rectangle 的自定义字段组件没有内在首选宽度，而 ComboBox 的最小宽度随当前文本增长，窄窗口或长预设名会把右侧列挤压成十几像素且标签被裁切；给 ComboBox 设 min-width: 0px 让其回到纯伸展分配即可均分。注意不能用 width: (parent.width-x)/2 修复：ScrollView 内子元素显式宽度会把 min-width 默认收敛回自身宽度，与视口 content-width 成环，且 Slint 禁止 width 与 min-width 同设。窄窗截图必须放大采样确认每列实际宽度，仅宽窗正常说明不了分配问题。
- 2026-10-05 ui/i18n.slint 再生成会掉键的问题按 2026-10-04 预案再次出现（dock/files/tray 侧新键未回写 catalog 时全量再生成导致整包编译失败）；处理顺序：先从 git diff 抢救被删键原文，按引用点补回生成文件恢复编译，再把全部键写入 catalog 后整体再生成对齐，catalog 仍是唯一事实源。
- 2026-10-05 Slint 拖拽浮层不要用两个元素的 absolute-position 相减求容器内坐标：事件回调期的跨元素相减不可靠（表现为浮动条目贴到容器最左）。跟随鼠标的浮层一律在行事件里记录窗口绝对坐标（row.absolute-position + mouse-x/y），浮层挂到主窗口根直接用窗口坐标定位；行内高亮、落点索引用自身 absolute-position 与窗口坐标自比较（DragRow 已验证模式）。渲染期声明式绑定读取 absolute-position 是正确的，仅事件期跨元素相减有问题。
- 2026-10-05 UserAgentRecord 的 tool_names、ability_items、declared_tool_names/declared_skill_names 是一组必须联动的字段：工蜂卡投影 build_worker_card 优先取 ability_items/declared，只改 tool_names 会在下一次 inner_visible 双向同步时被旧能力集覆盖（表现为"保存成功但刷新后丢失"）。改智能体工具选择的入口必须与网页版 API 路由一致，经 resolve_agent_ability_selection 同步全部字段；排查此类"已落盘却被还原"问题应先直读存储记录（export_agent_document/owned）区分写入侧与投影侧。
- 2026-10-05 Slint 1.18 的 DropArea/DropEvent 只覆盖应用内 DragArea 拖拽：vendored winit 后端不转发 WindowEvent::HoveredFile/DroppedFile/HoveredFileCancelled，外部 OS 文件拖放默认到不了任何 DropArea（表现为"能编译但拖不进来"）。接入点是 WindowInner::process_drag_event(BackendDragEvent::Move/Drop/Leave)：悬停期累积 per-file HoveredFile、CursorMoved 转发 Move 供 has-drag/can-drop 高亮，首个 DroppedFile 消费整套路径构造 DataTransfer::set_file_paths。另外 DropEvent 是 #[non_exhaustive]，跨 crate 不能结构体字面量构造，必须在 core 补 pub new 构造器；.slint 回调参数可以直接声明 DropEvent（对 .slint 不透明，路径只能在 Rust 侧经 event.data.file_paths() 读取），can-drop 返回类型是 DragAction 而非 bool。
- 2026-10-06 build.rs 生成“资源表 + include_bytes!”时，若生成的 .rs 文件放在 OUT_DIR 并被 include!，表内的 include_bytes! 必须用 CARGO_MANIFEST_DIR 拼绝对路径：相对路径按“包含它的文件”解析，会指向 OUT_DIR 而报“系统找不到指定的路径”，且报错发生在编译生成文件阶段、容易被误判为资源缺失。同一批改动里，Slint 的 global 与 struct 只有在入口 ui/main.slint 显式 export 后才在 Rust 侧以 crate 根类型出现（否则只有带 deprecated 标记的内部别名，global::<X>() 直接报 no X in the root）；Slint 也没有运行时“字符串→color”转换和 String.charAt，需要 Rust 侧预先算好 brush/glyph 之类的展示值随结构体下发。形象对话框验证用 slint-viewer --screenshot 直接出图，不必等整包构建；icon 载荷里的底色（`"color":"#3b82f6"`）会让 `r#"…"#` 原始字符串在 `"#` 处提前结束、整条断言变成语法错误，写这类 JSON 字面量固定用 `r##"…"##`。

### 2026-10-06：蜂窝原生浮窗与 windows-sys
- 2026-10-06 要每像素 alpha 的桌面浮窗，不能靠 Slint 窗口：frontend-slint vendored 的 winit 后端在软件渲染路径把 `set_transparent()` 实现为空操作，透明主窗只会得到不透明矩形。可行做法是独立原生线程自己持有 `WS_EX_LAYERED | WS_POPUP | WS_EX_TOPMOST | WS_EX_TOOLWINDOW` 窗口、以 `UpdateLayeredWindow(ULW_ALPHA)` 提交预乘 BGRA，不依赖 DWM；全透明像素天然点击穿透，形象轮廓即命中区，不需要额外命中测试。跨线程只传小值指令（`PostThreadMessageW(WM_APP, 0, Box::into_raw(..) as isize)`），像素缓冲始终留在浮窗线程。
- 2026-10-06 windows-sys 0.52 高频踩点：样式/标志参数是 u32 别名（字面量不要写成 i32，`SetWindowLongW` 返回值才是 i32）；`MSG` 字段是 `wParam`/`lParam`；`SetCapture`/`ReleaseCapture` 在 `Input::KeyboardAndMouse` 而非 WindowsAndMessaging；`DrawTextW`、`DT_*`、`SetBkMode`、`TRANSPARENT` 在 `Graphics::Gdi`，且 `SetBkMode` 收 i32 需 `TRANSPARENT as i32`；`CreateDIBSection` 第五参是 `HANDLE = isize`（传 `0`）；`RGBQUAD`/`BITMAPINFO` 没有 `Default`，只能零值结构体字面量；`GetDeviceCaps(hdc, LOGPIXELSX as i32)`；`SystemParametersInfoW(SPI_GETWORKAREA, 0, &mut RECT as *mut _ as *mut c_void, 0)`。文本量算走两趟 `DrawTextW`：先 `DT_CALCRECT`（此时不得传入真实高度上限，否则被裁），再光栅化到 1×1 占位 DIB 之外的临时表面并取任一通道作为 alpha 遮罩。
- 2026-10-06 原生回调会重入控制器：菜单选择、拖拽结束在 `handle_event` 内改状态后又要求重投影，若在 `RefCell` 借用期间调用会直接 panic。规则是把 Slint 调用（`invoke_open_message_agent` 等）留到释放借用之后、每 tick 至多一次；重投影入口用 `try_borrow().is_err()` 做重入护栏；需要同时改 `overlay.pets` 与 `overlay.service` 时传不相交字段引用，而不是把整个 `&mut Overlay` 与其中某字段一起传，否则借用检查器判为冲突。
- 2026-10-06 “显示/隐藏”这类覆写与设置面板双向耦合时，要防单向门：桌面形象对话框确认时拿不到智能体 id，若菜单覆写永不回收，被隐藏的形象就再也显示不出来。做法是面板保存成功时清掉该智能体的本地覆写（`binding_saved`）再重投影，覆写只作为菜单期的临时偏好存在。
- 2026-10-06 验证原生窗口链路不要整包构建截图：`#[ignore]` 的运行时探针（Present 带气泡的形象，断言窗口高过精灵框且顶边上移）20ms 内即可覆盖线程启动、消息通道、GDI 量算与合成几何。注意只被测试使用的 Win32 API 要 `use` 在 `#[cfg(test)] mod tests` 内，否则常规构建出 unused import 警告；返回 `()` 的函数里不能用 `?`，改用 `let Some(..) else { return; }`。
- 2026-10-06 窗口类归属注册它的线程：同进程再起一条浮窗线程时，若前一条还没退出，`RegisterClassExW` 直接失败，线程静默返回，表现为“形象再也不出现”。类名要带线程 id，且测试/诊断取窗口一律用 `EnumThreadWindows(自己的 tid)`，不要用 `FindWindowW` 按类名找——同进程多服务时会拿到别人的窗口。
- 2026-10-06 几何断言查不出内容错位：气泡把精灵的居中偏移 `sprite_left` 又用了一遍，气泡比精灵宽时整块被推到表面边缘外裁掉，窗口尺寸与顶边上移都仍然“正确”，单测与几何探针全绿。浮窗这类自绘内容必须看像素：在 `render()` 里加 `#[cfg(test)]` 的表面快照，把预乘 BGRA 反预乘存成 RGBA PNG，再叠一层棋盘底铺平副本（否则白底查看器里白色气泡整体隐形）。
- 2026-10-06 本机实测：GDI 抓屏（`GetDC(0)` + `BitBlt`，`SRCCOPY` 与 `SRCCOPY|CAPTUREBLT` 都试过）不包含 `UpdateLayeredWindow` 呈现的分层窗，同一矩形“有形象/无形象”两次抓屏逐字节相同，而 `WindowFromPoint` 能命中形象窗口，证明窗口确实置顶可见——即抓屏盲区不是显示故障。含义是蜂窝自带的全屏截图不会把桌面形象拍进去；要拍分层窗只能走 `Windows.Graphics.Capture`（Win7 不可用）或自绘表面快照。
- 2026-10-06 遮罩只取单通道当覆盖率时，字体质量必须是 `ANTIALIASED_QUALITY`：`DEFAULT_QUALITY` 可能选到子像素渲染，笔画右缘的覆盖落在红/绿子像素上，取蓝通道就丢字。文本两趟 `DrawTextW`（量算/绘制）必须用同一个换行宽度，绘制框比量算框窄会二次换行。

- 2026-10-07 Slint 的 ListView 单元格高度必须是“确定值”，不能由自身内容推导：`ui/timeline.slint` 里 `TimelineRowView` 先写成 `height: cell.preferred-height`（cell 是内部 VerticalLayout），再把 `self.preferred-height` 绑到该布局的高度上，结果是绑定环 + 首次测量发生在视口宽度已知之前，所有单元格塌成约 20px、整个时间线叠在一起；`height: max(root.entry.h, cell.preferred-height)` 同样无效，因为 ListView 只在建卡时读一次高度，模型更新不会触发重新布局。可用的写法是 `height: root.entry.h > 0px ? root.entry.h : 24px`，并由投影侧给每行播种一个合理的首帧高度（`timeline::seed_height`），等布局回调报回实测值再替换。用 slint-viewer 验证这类问题时，`--screenshot` 的产物差异才是事实：文件大小/SHA 相同就说明改动没生效，别只看源码已经改了。另一条同轮踩到的坑：用 pwsh 的 `Set-Content -Encoding UTF8` 改 .slint 会写出 BOM，Slint 解析带 BOM 的文件会表现异常；改 slint 源文件统一用编辑工具，不要用 shell 重写整个文件。
- 2026-10-07 Slint 布局里“绝对定位的点击层”会按普通子元素吃掉一整份高度：`FoldEntry`/`GroupBar` 把一个 `x:` 定位、用于铺满整行命中区的透明 `Rectangle`（内含 `TouchArea`）写成了外层 `VerticalLayout` 的子元素，外层 `height: col.preferred-height` 于是把它算进去，每一条思考/工具条目的行距从 28px 变成 54px——肉眼只表现为“时间线太散”，不像布局错误。规矩：覆盖式命中层/装饰层必须是**承载组件的直接子元素**（与布局同级、不进布局），布局里只放真正参与排版的流式子元素；判据是“这条元素是否该影响兄弟的位置”。定位子元素上写 `y:` 会直接编译报错（`Cannot use the 'y' property … in a layout`），只有 `x:` 合法，但合法不等于不占位。定位这类问题不要靠读源码推理：开一个只含目标结构的最小 `.slint` 探针用 `slint-viewer --screenshot` 出图，再用逐行像素扫描读出每个色块的实际起止 y，一次就能把“谁多占了 26px”钉死（本次探针里带覆盖层 54px、去掉后 28px，与真实界面完全一致）。
- 2026-10-07 嵌套 `ScrollView` 会把内层内容画到卡片外面：补丁卡片自带一个 `ScrollView` + `height: parent.height - 70px`，而卡片本身又处在时间线的 `ScrollView` 里，内层视口最终取值大于卡片高度，diff 行直接盖住卡片圆角边框、并溢出到卡片下方（表现为“卡片上下有背景色带”“最后一行被切”），而卡片外部尺寸看起来正常。规矩：滚动视口只留一层，卡片内部不再自建 `ScrollView`，行数由后端投影限量（每文件 ≤200 行）；卡片高度用 `height: body.preferred-height`（body 是自身布局）从内容推导，不要写 `34px + 表头 + min(行数,12)*20px` 这类手算公式——手算公式一旦与真实行高不一致就会裁掉或空出内容。另注意 `ScrollView` 里给子布局写 `width: parent.width` 会取到视口被上层 `min-width` 约束后的宽度（本次 930px 的卡片内部被算成 200px），宽度一律用 `horizontal-stretch` + `min-width: 0px` 交给布局分配。
- 2026-10-07 时间线的行数上限必须由 reducer 兜住，不能只靠投影：`ui/timeline.slint` 的 `rows-column` 是一个 `for item in root.rows` 的 `VerticalLayout`，`visible: false` 才不参与布局，所以「标记为 visible 的行数」就是每帧的真实布局成本——既没有视口裁剪，也没有离屏跳过，展开全部历史时 49 轮 × 28 行 = 1399 行会让 2560×1476 视口的首帧 1957ms、滚动每帧 447ms（release 实测；debug 大约再差 10 倍）。规矩：任何会随用户点击增长的项都要有 reducer 侧上限，本处取 MAX_OPEN_TURNS = 8，超出时把最旧的一轮折回并把它的分隔条也隐藏（折回的分隔条若仍 visible，每轮又多一行，41 轮就是 41 行）；上限生效后展开全部历史只铺 243 行，首帧 242ms、每帧 38ms。自查两个坑：一是判断「哪些轮是展开的」只能用 fold 状态（row.open），不能再要求 visible，否则被上限折回的轮不计入，下一轮又会折一个，一次点击就会把整个历史关掉；二是测量必须走用户的真实路径（逐个 toggle 打开轮次），直接构造一个「全部标记 visible」的模型会量到一个运行期已经无法产生的状态，得出假数字。
- 2026-10-07 验收「重启后还剩什么」的检查自己不能改库，复用写入型守卫会让整条验收失去意义：`check-native.py` 的第二阶段 `--native-restore` 一直是个空壳——`src/main.rs` 把 `--native-smoke` 与 `--native-restore` 指向同一个 `native_smoke::run`，而它只写 `smoke.txt`，全仓没有任何代码生成 harness 断言的 `restore.txt`。这个缺口长期不可见，因为第一阶段卡在导航步骤、根本走不到第二阶段；第一阶段修好后它立刻暴露。补的时候有一条容易踩反的纪律：新阶段的运行时守卫**不能**复用 `native_smoke::check_runtime`，那个守卫会 `create_session` 并注入探针消息，「会改库的检查」证明不了重启后还剩什么，所以恢复阶段另写了一个只读守卫（列会话 + 拒绝未知会话）。跨进程识别被测轮次也不能靠标题：会话标题取自该会话的第一条消息，同一个会话在流式轮次之后标题会显示成更早的那条消息（实测恢复出来的列表是 `新会话 / native-queue-first / native-cancel`，而被测的 `native-long` 轮次并不以自己命名），所以第一阶段要把会话 id 与期望答案写成交接文件，第二阶段按 id 找回、按交接内容逐字节比对。另有一条 UI 时序：选会话是异步的，调完 `select_conversation` 必须让出这一拍并在下一拍确认 active 会话已切换，否则后续断言会对着空时间线跑。

2026-10-07 离线构建报 no matching package named X 时先查 vendor 树，不要先改代码：Rust-builder 各平台的 cargo-vendor-slint 是锁文件之外的独立快照，新增依赖只改 Cargo.toml 时本地 registry 缓存能解析、离线树却不能，三个平台会一起失败。判断方法是一句目录名匹配，不需要构建。补齐依赖要按闭包成组加：用临时 crate 声明该依赖，让 cargo vendor --versioned-dirs 生成带校验和的目录，拷贝后必须先回读锁文件确认实际锁定的次版本（vt100 声明 vte ^0.11.0，锁住的是 0.11.1，只补 0.15.0 仍然报 failed to select a version），再加一个真正编译该 crate 的目标构建才算验证通过。

- 2026-10-09 蜂窝聊天时间线「回复结束后条目全没了」，三条教训。（一）**一个模型两个写者，必须先定义谁拥有哪一段**：直播归约器和历史观察者共用同一个 `VecModel`，观察者在每次 turn 变化时 `set_vec(全量历史)`，于是回复一结束、`active` 置空，下一帧就把刚建好的直播行整段截断——表现是「最后一条答案落地的瞬间时间线清空」。修法是只替换持久前缀、保留快照还没覆盖到的直播尾部，并在前缀位移时同时重算归约器存下的行下标**和**行内的折叠句柄（`payload` 是绝对下标，视图按它定位，漏算就会点到别的行）。判据：任何「整体替换共享模型」的写法都要问一句——被替换的那一半是谁建的？（二）**UI 看起来坏了，先怀疑投影层丢信息，而不是视图**：真正让思考与中间正文消失的不是视图，是原生 façade 把整轮压成「最新一条 assistant_message」，多轮的 reasoning 与每轮正文在数据里就已经不存在了，前端再怎么改都补不出来。持久存储本来就是按 `model_round` 一轮一条（含 reasoning 字段与被中断轮次的文本块），所以修法是把契约改成按轮分组的数组，让重开线程与直播走同一条投影；顺带删掉只被旧投影写入、无人读取的三个字段。经验：字段「编译通过、默认值合法、永远没人写」比缺失更危险。（三）**逐像素对齐必须拿截图量，不能靠眼睛**：Slint 的 padding 会叠加——外层列已有 24px 页边距，展开体又写 `24 + 20`，实测落在 68px 而网页版是 44px，肉眼看缩进「差不多」；解 PNG 扫每行第一个非背景像素才暴露出来。同源第二个坑：条件分支 `if ... : X := ...` 里声明的 id 在外层作用域不可见，跨分支取 `preferred-height` 直接编译失败，只能各自成块或换成无条件容器。附带一条口径：批次条在 0 次工具时网页版文案是「已处理」而非「执行工具 0 次」，对齐样式要把这类空态文案一起对，否则差异会以「样式没对齐」的形式被再次报回来。
