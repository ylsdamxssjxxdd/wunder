
## Slint 的 clip 是矩形裁剪，圆角只管绘制 2026-11-25 [桌面版/UI/渲染]
- 现象：设置弹层顶部是正常圆角，底部却是直角；用 `slint-viewer` 截图复看时四角都是圆的，像是修好了。
- 判因：卡片 `border-radius` + `clip: true`，里面的设置页自带整块底色并铺到边。App 跑的是软件渲染器，裁剪按矩形算，底色盖掉了下沿的弧线与 1px 描边；viewer 默认的 femtovg 按圆角裁剪，所以预览看不出这个问题。
- 规矩：圆角容器里不要放铺满到边的实色子元素——留出与圆角同宽的内边距让内容止步于弧线起点，或自己画弧角；圆角类验收必须再用 `--backend winit-software` 截一张，预览器通过不等于 App 通过。

## `if` 条件块里的元素名在外层不可见，原生命中判断会拿到假几何 2026-11-25 [桌面版/前端/原生交互]
- 现象：窄窗输入区点加号能打开菜单，再点加号收不起来，必须点到别处。
- 判因：原生「这一下是不是点在触发钮上」靠 Slint 导出的 `plus-trigger-*`。宽窗那颗加号在动作行里，窄窗动作行整体 `visible: false` 且高 0，导出的正是它的坐标；真正的加号在另一颗按钮里，被 `if root.touch-layout :` 包着，名字出不了条件块。于是按加号被判成「点在别处」：按下先 dismiss，松手 onClick 又 `!plus-open` 打开一次。
- 规矩：要导出给原生做命中判断的元素一律用 `visible:` 而不是 `if` 包，保证名字留在外层作用域；导出几何按当前布局分支选元素（`root.touch-layout ? a : b`），别让原生读一个没参与布局的控件。

## 外部拖放后的输入焦点要同时恢复 OS 窗口与 Slint 编辑器 2026-11-24 [桌面版/拖放/测试]
- 现象：Slint 内部拖放回归明明确认编辑器已聚焦，真实用户从文件管理器拖入后却仍不能直接输入，被其他窗口盖住时也不会主动置前。
- 判因：文件源应用仍持有操作系统键盘焦点，`TextInput.focus()` 只处理场景内焦点；直接 `WindowInner::process_drag_event` 的测试绕过了系统窗口激活，因此会给出假阳性。
- 规矩：外部拖入后先调用 `native_window::restore_and_focus` 恢复/置前窗口，再设置编辑器与 UTF-8 光标；验证至少覆盖另一窗口真实占据前台后的拖放，不能只测 Slint 内部事件链。

## 上下文占用这类「当前快照」指标，0 不能当未知用 2026-11-24 [桌面版/引擎/前端]
- 现象：桌面版输入区大脑图标的上下文占用在**前几轮明显偏低**：新线程第一轮整段读作 0 / 400000 tokens，答完才跳到一万多；`/compact` 完成后直接掉到 0；越往后越"正常"。
- 判因：数值取自 `context_usage` 事件里的 `context_tokens`，而请求**发出前**这一帧填的是「上一次已观测的 prompt」，新线程与刚压缩过的线程这个持久值就是 0（压缩还会显式存 0）。于是窗口里明明已经装着系统提示词与全部工具定义，仪表却画成空；轮次越多占用的绝对值越大，同一个错误换算成百分比反而越小，看起来就"后面正常了"。桌面端还把这个 0 当已知值（云端版有 `used === 0 && unobserved → 未知` 兜底，桌面没有），`/compact` 的响应又把 0 写进 `final_context_tokens`。
- 规矩：①「当前占用」必须区分「已观测」与「未观测」，未观测就报未知（`None` / `—`）或用真实测量兜底，绝不能拿 0 当占位；②请求发出前那一帧要携带本轮**即将发出**的请求规模（系统提示词 + 历史 + 工具），而不是上一轮的观测；③压缩或重建历史后立刻推一帧重建后的占用，别让仪表停在归零或旧值上；④分母用引擎准入时的同一个窗口值（模型卡片值 min 提供方学到的上限），否则同一份占用会读出两个百分比。

## 测试夹具里的展示文案会顺着保存链路写进真实用户数据 2026-11-24 [桌面版/后端/测试]
- 现象：桌面版「智能体」设置页的名称栏显示成「工具选择」（一段测试里硬编码的名称），用户以为页面错位。
- 判因：内置智能体的名称本来由预设拥有（各端都渲染成只读），但 `agent_management::update` 照样接受调用方传来的 name；集成测试的 `save_tools` 又编造了一个展示文案当名称。一旦测试进程的 WUNDER_HOME 没生效或调试运行时连到真实 home，这条草稿就直接改写记录，materialize 还会把它投影成 `agents/<name>--__default__.worker-card.json`。

## FAT32/exFAT/U 盘上的 WUNDER_HOME 没有硬链接，资源发布不能只走 hard_link 2026-11-23 [桌面版/命令行/存储]
- 现象：Win7 用户从 U 盘或共享目录运行桌面版，界面能起来，但提示「无法启动内嵌运行时」；CLI 报 `Incorrect function. (os error 1)`。把 exe 单独拷到本机 NTFS 后正常。
- 判因：安装根的 `.wunder-home` 让 WUNDER_HOME 落在 FAT32/exFAT/共享目录；首次释放内置资源用 `hard_link` 做 create-if-absent，FAT32 没有硬链接，`CreateHardLinkW` 返回 ERROR_INVALID_FUNCTION(1)。单独 exe 没有标记，home 回落 `%USERPROFILE%\.wunder`（NTFS）。
- 规矩：任何「写 staging 再原子发布」都要给不支持硬链接的卷留 rename 回退（先检查目标存在再 rename），并覆盖回退成功、目标已存在、普通错误不被吞掉的测试；便携运行不等于支持任意文件系统，数据目录仍优先本机 NTFS。

## 补充包里的 Playwright 只认注册表目录，WUNDER_BROWSER_BIN 覆盖不到模型手写的脚本 2026-11-23 [桌面版/命令行/浏览器/打包]
- 现象：Win7 补充包明明带了 Chrome 109，`browser_*` 工具能出图，但模型写 `playwright.chromium.launch()` 时仍报 `Executable doesn't exist`，随后反复 `where chrome`、查 PATH、翻补充包目录。
- 判因：`WUNDER_BROWSER_BIN` 只被桥接和少数技能脚本读取，普通 Python 进程不认；Playwright 自身只按 `PLAYWRIGHT_BROWSERS_PATH` 下的 `chromium-<revision>` 目录查找，而旧补充包把 Chrome 放在 `opt/browser/chrome-win`，不属于注册表布局。
- 规矩：补充包浏览器一律按内置 Playwright 的 `browsers.json` revision 放到 `<browser_root>/chromium-<revision>/<layout>/`，启动时在未显式配置的情况下发布 `PLAYWRIGHT_BROWSERS_PATH` 与 `WUNDER_BROWSER_BIN`；Windows 7 同时设置 `PLAYWRIGHT_SKIP_VALIDATE_HOST_REQUIREMENTS`（Chrome 109 早于 x64 宿主依赖门禁）。升级 Playwright 必须重新核对 revision 与 Chrome 109 的配对，构建脚本要校验而不是静默换目录。

## 安卓内置浏览器的本地页面必须由 WebViewClient 应答，不能依赖 HTTP 服务或域名解析 2026-11-22 [安卓版/浏览器/预览]
- 现象：安卓版浏览器工具传 `path` 报「url 必须是 http(s)」，改传 `http://wunder.preview` 报 `ERR_CLEARTEXT_NOT_PERMITTED`，改 `https://wunder.preview` 报 `ERR_NAME_NOT_RESOLVED`，工作区 HTML 完全打不开。
- 判因：`wunder.preview` 只存在于 Playwright bridge 的 `page.route` 里，安卓的 WebView 宿主既没有拦截该域名，它也不是真实域名；换成本地 HTTP 服务同样会碰到 WebView 的明文策略。
- 规矩：安卓预览由运行时把 `path` 解析成 `preview_root/preview_path`，Java 在 `shouldInterceptRequest` 里把 `https://wunder.preview/...` 直接从工作区读盘应答（拒绝绝对路径与 `..`，目录回退 `index.html`，返回正确 MIME 与 `no-store`），离开预览页立即清空根目录；不要为预览起本地 HTTP 服务，也不要假设该域名可解析。

## 手机浏览器适配要同时处理 16px 输入下限与软键盘视口 2026-11-22 [云端版/手机/UI]
- 现象：云端版在桌面宽度下正常，手机浏览器里聚焦输入框会整页放大，软键盘弹出后输入区被键盘盖住。
- 判因：iOS Safari 对 `font-size` 小于 16px 的输入控件会在聚焦时自动缩放页面；`100dvh` 只跟随地址栏收放，不随软键盘收缩，根视图只写 dvh 时输入区仍按完整高度布局。

## Cargo 特性会把随产品交付的能力静默砍掉 2026-11-21 [桌面版/命令行/安卓版/构建]
- 现象：桌面版工具页点「连接」MCP 服务器直接弹 `mcp feature is disabled; rebuild with --features mcp`；命令行 `mcp` 子命令和安卓版设置页的同一操作也一样失效，但编译、启动、界面都正常。
- 判因：把 rmcp 拆成显式 `mcp` feature 时，`wunder-desktop/frontend`（桌面版前端壳）和 `wunder-android` 都用 `default-features = false` 逐项列举 `wunder-desktop` 特性，新拆出的 `mcp` 既没进列举清单、也没进 `wunder-desktop`/`wunder-cli` 的 default；feature 关闭时 runtime 走轻量 stub，只有 `tool_specs` 为空才报错，所以没人发现发布物根本没有 MCP。
- 规矩：给随产品交付的能力加 feature 时，一次改齐四处——crate 的 default 特性、所有逐项列举特性的下游清单（前端壳/安卓版等）、各独立 workspace 的 `Cargo.lock`、以及离线 vendor 快照；验证不能只看“能编过”，要用 `cargo tree -e features -i <dep>` 确认依赖真的进了图，并就地点一次该功能。vendor 只认锁文件里的精确版本，重新解析出的新版本（如 rmcp 3.5→3.11）会带着 vendor 里没有的传递依赖，离线构建会在解析阶段直接失败。

## Slint 单行 TextInput 不会自己横向滚动，Android 的光标又用选区色绘制 2026-11-21 [安卓版/表单/UI]
- 现象：智能体设置里的问候语一长，右边那截永远看不见；点进字段后光标也几乎找不到，拖光标文字不动。
- 判因：单行 `TextInput` 只按自身宽度裁剪文本，官方文档明确写着「光标移出可见区不会自动滚动，由外层负责」；`FormField` 一直用 `width: parent.width - 20px` 定宽，超出部分连同光标一起被裁掉。另外 `cursor_uses_selection_color()` 在 Android/iOS/macOS 上把光标画成 `selection-background-color`，而 FormField 的选区是浅色 `accent-soft`，光标在白底上等于隐形。
- 规矩：单行字段照 `LineEditBase` 的写法做——编辑器宽度取 `max(可视宽 - 光标宽, preferred-width)`，外面套一层 `clip` 可视区，`cursor-position-changed` 里把横向偏移夹在可达范围内跟着光标走；触摸端（`mobile: true`）统一 `text-cursor-width: 2px` + 深色选区（`accent-ink` 底 + 白字），不要用浅色选区委曲光标。

- 现象：跑 `cargo test -p wunder-desktop` 后，本机默认智能体的工具勾选被改掉（桌面控制等工具被取消），用户以为「桌面版默认没启用桌面控制」。
- 判因：桌面运行时里 `--temp-root` 只决定临时文件目录，配置、SQLite 用户库与默认智能体仍落在 `WUNDER_HOME`（默认 `~/.wunder`）。测试只设了 temp_root 与 workspace，等于直接修改开发者的真实用户数据；不带 `desktop-control` feature 的测试保存工具清单时还会把该工具从默认智能体里删掉。
- 规矩：任何启动 `NativeDesktop` 的测试都要把 `WUNDER_HOME` 指到临时目录，并用进程内锁串行启动（`WUNDER_HOME` 是进程级环境变量，并行测试会互相覆盖）；测试里创建的临时目录用 `mem::forget` 保活到进程结束。若已有用户数据被旧测试改坏，用带 marker 的一次性迁移修复，并保留用户之后手动取消的权利。

## 布局里的子元素高度由 min/preferred 决定，组件根上的 height 绑定不起作用 2026-11-21 [安卓版/聊天/UI]
- 现象：安卓版输入卡怎么改 `height` 都不随草稿行数长高，多出来的行被裁在卡片里；可同一份代码里 `editor-box-height` 用 `debug()` 打出来明明已经涨到 108px。
- 判因：`Composer` 放在 `composer-band` 的 `VerticalLayout` 里，布局按子元素的 min/preferred 分配尺寸，组件根上的 `height:` 绑定被忽略；而卡片里真正决定高度的那一层只给了固定 `min-height: 46px`，所以行数再多也只按一行分配。桌面版基准高度本来就接近布局的偏好值，这个问题一直没显形。
- 规矩：要让布局里的组件随内容长高，把高度写到**子元素**的 `min-height`/`preferred-height` 上（`min-height: editor-box-height`），组件根的 `height` 只当非布局宿主的兜底；判断「到底有没有长高」别靠肉眼，先 `debug()` 打出 box/preferred/宽度/可视高度四个值。

## 输入法高度不要逐帧跟随：动画中间帧一律丢弃 2026-11-21 [安卓版/聊天]
- 现象：手机呼出键盘时整页卡顿，键盘每动一下聊天列表就重排一次。
- 判因：`WindowInsetsAnimation.onProgress` 每帧回调一次 IME 高度，33ms 的 UI tick 每读到一个新值就写 `ime-height`；而这个属性是 header/列表/输入卡共用的高度基准，等于一次键盘动画触发十几次全页重排。
- 规矩：IME 高度按「稳定采样」处理——连续两拍（约 66ms）不变才落值，动画中间帧丢弃，一次动画只布局一次（动画期间的内容本来就被键盘表面盖住）；需要在动画期间就判定「键盘是否在场」的地方（如硬件返回键）读未平滑的原始 inset，别读平滑后的属性。

## splash 图标要给「有尺寸的透明图」，颜色资源在部分 ROM 上会退回应用图标 2026-11-21 [安卓版/启动]
- 现象：启动主题里把 `windowSplashScreenAnimatedIcon` 设成 `@android:color/transparent`，AOSP 上正常（启动页只剩底色），但用户仍反馈「图标突然放到很大」的一瞬间。
- 判因：颜色资源在 AOSP 被当 `ColorDrawable` 画成空白；而系统/部分 ROM 会向图标要固有尺寸（intrinsic size）来做 splash 的图标位，拿不到就回退成 launcher 图标并居中放大——正好就是那一下。Android 12+ 的系统 splash 无法关闭，只能把它画空。
- 规矩：splash 图标用一张 `108dp` 的全透明 vector drawable（`res/drawable/wunder_splash_icon.xml`），背景与首帧同色、`windowSplashScreenAnimationDuration` 设 0；断言别只认 `ColorDrawable`，要能同时接受透明色或这张矢量并校验固有尺寸。真机验证时区分两种来源：系统 splash（可画空）与 launcher 自身的图标放大动画（应用侧管不了）。

## 系统识别只能兜底，别拿它当主路径 2026-11-21 [安卓版/语音]
- 现象：想省掉「先配一个 ASR 模型」这道门槛，直接用手机自带的 `SpeechRecognizer` 做语音输入。
- 判因：系统识别在设备之间差异极大——国产 ROM 常常没有 Google 语音服务，中文离线包也未必装好（`ERROR_LANGUAGE_UNAVAILABLE`）；API 33 才有 `isOnDeviceRecognitionAvailable` 可靠判定离线能力，minSdk 26 的机器只能走在线服务；而且它只回文本、拿不到音频，识别错了没法用别的模型重跑。
- 规矩：主路径仍是自录 WAV + 配置的 ASR 模型（质量、离线、可重试都可控），系统识别只在「没配模型且设备确实支持」时兜底，并在界面上标明「系统识别」；两者都不可用时直接提示去设置，而不是静默失败。`SpeechRecognizer` 必须在主线程创建，`stopListening()` 后等 `onResults` 再 `destroy()`；上滑取消走 `cancel()`，别等结果。

## 相机输出用自带的 ContentProvider，别为了 FileProvider 引入 androidx 2026-11-21 [安卓版/拍照]
- 现象：拍照要交给系统相机写文件，`ACTION_IMAGE_CAPTURE` 只能往 `content://` 写；第一反应是用 `androidx.core.content.FileProvider`。
- 判因：这个 APK 的依赖表刻意只留本地 `android/app/libs/*.aar`（rustls 校验器与 kotlin 标准库），远程 Maven 只在 androidTest 里出现；为了一个 FileProvider 引入 `androidx.core` 会把「离线可构建」这条前提改掉。
- 规矩：需要「授权别人往应用私有目录写」时，自己写一个 ~100 行的 `ContentProvider`（`PhotoProvider`：authority `<pkg>.camera`，只认 `photo/<纯文件名>`，按 `mode` 决定读写/截断），manifest 里 `exported=false` + `grantUriPermissions=true`，用 `FLAG_GRANT_WRITE_URI_PERMISSION` 逐次授权；OEM 相机只认 clip data 上的授权，两边都要给。落盘后按「文件有字节就算拍到」判定，别只看 `RESULT_OK`。

## 共享一个视口的界面，线程切换要按线程存 UI 状态 2026-11-18 [桌面/UI]
- 现象：桌面版聊天区只有一个 ScrollView，切线程后新线程会停留在上一个线程滚到的位置；如果上一线程是向上翻历史（follow=false），新线程还会丢掉「跟随最新」状态。反过来，切回原线程也回不到原来位置。
- 判因：视口偏移和 follow 标志都是组件级状态，模型换了但状态没换。`bind_reducer` 换模型只解决「显示谁的行」，不解决「看到哪一行」；而 Slint 的 `content-y` 在内容变短时会被静默 clamp，靠一次赋值也补不回来。

- 验证：加 `--scroll-restore-probe` 这类可重复探针（长/短两组行 + 请求偏移/请求尾部 + 断言），比人眼切线程可靠。

## Git for Windows 的 bin/bash.exe 不是 bash 2026-11-18 [打包/工具]
- 现象：决定往补充包里塞 bash 时，清单写的是 `bin/bash.exe` + `bin/sh.exe`（Git Bash 快捷方式用的就是它），看着天经地义。
- 判因：`bin/bash.exe` 只有 48 KB，是个启动器，运行时会去 exec `../usr/bin/bash.exe`；真正的解释器 2.1 MB，在 `usr/bin/bash.exe`。只把 bin 里那份和 msys DLL 拷走，等于发一个起不来的 shell —— 而且这种错误在打包机上不做「真跑一次」是看不出来的。
- 规矩：从 PortableGit/MinGit 里挑二进制，先量体积、看导入表，再决定拷哪个；`usr/bin` 才是 MSYS 二进制的家。落位后必须真跑一次（`--version` + `bash -n` 正反例），只看文件存在不算验收。
- 附带：闭包只需要 `bash.exe`、`sh.exe`、`msys-2.0.dll` 三个文件（约 5.6 MB）；`usr/bin/msys-*.dll` 那 75 个是给 apr/crypto/glib 等工具用的，语法校验用不上。

## 给 Win7 补充包加一个解释器，四层都要动，且必须带真冒烟 2026-11-18 [打包/工具]
- 现象：写后语法校验在 Linux 上一直正常，Windows 上 `.js`/`.sh`/`.ps1` 全是 skipped。查下来是三件不同的事：`.js` 不是没有 node，而是 Playwright 驱动的 `node.exe` 在 `opt/python/**/playwright/driver` 这个按 Python 版本变化的目录里，从没进过 PATH；`.sh` 是补充包压根没有 bash（MinGit 是「非交互发行版」，文档写得很清楚：不带 Git Bash）；`.ps1` 是路由表里只有 js/ts/sh/css，PowerShell 从来没接进校验。
- 判因：解释器「在包里」不等于「能被执行到」。路径发现、PATH 发布、探测顺序、扩展名分发是四个独立环节，缺一环就表现为「检查不生效」，而回执只写 skipped，看起来像功能没做。
- 规矩：加解释器要同时改——manifest（版本/SHA-256/归档 URL）、构建脚本落位段（含 PE 架构与 DLL 闭包门禁、真实冒烟）、core 的 `supplement.rs`（`find_tool` 候选与 `path_entries`）、runtime 的探测顺序与扩展名分发。落位段必须跑一次真实的 `-n` / `--version` 且要求「合法输入通过、非法输入被拒」，只看 `--version` 会放过缺少运行时的树。
- 附带：bash 校验前要把 CRLF 归一成 LF，否则 `then\r` 会被 bash 当成非法 token，整份 Windows 风格的脚本都误报。

## 没有 pwsh 时怎么验 PowerShell 脚本：先验证检查器本身 2026-11-18 [工程]
- 现象：改完 `.ps1` 的打包脚本想在 Linux 上自检，先写了个「括号配平」检查器，结果连未修改的基线脚本都报了几百处 stray `}`，看着像脚本被改坏了。
- 判因：那个检查器没处理 PowerShell 的 here-string（`@' … '@` / `@" … "@`）与 `<# #>` 块注释，把 here-string 里的引号和括号当成了代码。**检查器本身不可信时，它给出的结论一律无效**，不能据此判断对方代码有问题。
- 规矩：自检工具先在已知可用的基线（`git show HEAD:<path>`）上跑，基线必须 0 报错，再去跑改动版本；基线都报错就说明是工具坏了，先修工具。没有真解释器时只能保证「括号与引号配平」这一类结构性错误，语义正确性必须留给真实环境验收，别把猜测说成验证过。
## Windows 上任何子进程都要显式关控制台，探测也算 2026-11-18 [引擎/工具]
- 现象：只要写入一个 `.py`，Windows 桌面版就闪一下黑框；Linux/安卓完全无感。

## 限流闸门要按资源族分开，否则慢的兄弟会拖垮快路径 2026-11-18 [引擎/工具]
- 现象：写入校验的全局单闸下，并行测试里 Python 校验稳定拿到 `skipped (python checker busy)`；生产上连续写多个文件时也会偶发降级。
- 判因：闸门原本用一个全局 `Mutex`，而 TypeScript 检查要 `require('typescript')`（实测 137 ms，冷启动更久），python/node 普通检查只有 17–20 ms。同一把锁让「慢家族」吃光等待预算，快家族的结论被白白丢掉。
- 规矩：限流限的是**内存/并发进程数**，按解释器家族分闸（python/node/shell/powershell 各自一把，同族并发仍为 1）就能守住内存上限又不互相排队；排队与子进程运行共用一份总预算（`Budget`），最坏耗时只有一份而不是两份。新增族时记得补「族闸门互不相同」的回归断言。

## 安卓版缺字是方块、桌面版不是：Skia 会画 .notdef，软件渲染器直接跳过 2026-11-18 [安卓版]

- 判因：两端 UI 的字体集合都只有随包的微软雅黑（`create_collection` 关闭了宿主机字体枚举），雅黑不含 emoji 与多数象形符号；parley 找不到覆盖字体时把衬底 glyph 0（.notdef）留给渲染器。安卓版用 Skia 的 `draw_glyphs_at`，glyph 0 会被真实画成方块；桌面版软件渲染器用 `NonZeroU16` 表示字形，glyph 0 无法表示，直接跳过，所以桌面只是缺字、不会出现方块。

## 跨进程判活用 flock 实例文件，不要猜 pid 2026-11-20 [运行时/线程]
- 现象：命令行崩溃或被强杀后，桌面版点开它刚才占用的线程要等满 15 秒租约 TTL，期间只回 `THREAD_IN_USE`；反过来也一样。
- 判因：`thread_open_leases` 只靠 TTL 判断所有权，读不到“持有者进程还在不在”。用 pid 判断会被复用和权限干扰，且 Windows/Linux 语义不一致。
- 规矩：每个本地实例启动时在 `data/instances/<instance_id>.lock` 上拿一把 flock（`InstanceGuard`），进程消失内核必然释放；别的实例遇到 Busy 时“能拿到锁 = 已死”，立即回收租约并重试。“文件不存在/无权限”一律视为未知，保持 TTL 兜底，绝不抢占可能还活着的实例。桌面版与命令行共用这套判定（`instance_liveness::reclaim_dead_thread_lease`），不要各自发明 pid 探测。

## 安卓字体直接用系统字库：shared collection 不认 `load_system_fonts` 2026-11-20 [安卓版]
- 现象：想改成「不内嵌字体、直接用手机字体」，只删掉内嵌字号后文字整片消失；给 `shared_collection()` 调 `load_system_fonts()` 也没有任何效果。

- 规矩：安卓版从 `/system/fonts` 挑系统字体时用 `register_fonts`（或共享的 `load_fonts_from_paths`）显式注入，再设置 `SansSerif/SystemUi/UiSansSerif` 与 `Hani/Hans/Hant` 回退；同一份 TTC 里按 family 名（SC/Hans 优先，TC/Hant 次之）排序，避免简体界面先命中日文字形。字体集合按线程上下文存在，幂等标记要用 thread-local，不能用进程级 OnceLock。

## 下标式历史栈：删中间一格必须连带压实编号与游标 2026-11-17 [引擎/工具]
- 现象：快照 @1/@2 里 @2 损坏被删后，cursor 还停在 2，再撤销直接报「已到最早」，而 @1 明明还在——更早的历史被永久跳过。

## 写用户文件不能只保证原子性，还要保证属性不变 2026-11-17 [引擎/工具]
- 现象：重写一个 755 的 shell 脚本后变成 644，直接 Permission denied；硬链接的另一条路径停在旧内容；40 万行的文件改了却报「0 行变更」。
- 判因：`临时文件 + rename` 只保住「内容不残缺」，新 inode 的权限位来自 umask、链接数重算为 1；而有界性守卫放弃 diff 时又默认填 0，把「没算」写成了「没改」。
- 规矩：替换前 `set_permissions` 复制原权限（新建文件才用 umask）；`nlink > 1` 时改为就地写保留 inode；符号链接要先 `canonicalize` 写穿而不是替换链接；任何「没算出来」的统计量一律给 null 并配 `diff_unavailable`，绝不填 0。

## 限流的等待上限要按真实耗时定，否则并行场景会大面积降级 2026-11-17 [引擎/工具]
- 现象：给语法校验子进程加全局闸门，等待上限先取 200 ms，全量测试里 4 个用例立刻变红——不是锁坏了，是排队深度超过 10 个请求后全部拿到 `skipped (checker busy)`。
- 判因：单次校验约 20 ms，200 ms 只够排 10 个；测试并行度和真实写入并发都可能超过这个数。上限设小了，「限流」就变成了「随机丢掉校验结果」。
- 规矩：等待上限 ≥ 典型耗时 × 预期并发（此处 1 s ≈ 50 个请求），只有解释器卡死这类异常才走到降级；降级文案要和开关关闭、解释器缺失一样落进 `syntax` 字段，绝不阻断写入。

## Slint 里没有 contains，字符串赋给属性后还会被 move 2026-11-14 [桌面版]
- `[string]` 只能用 `index-of`（不存在返回 -1），写 `list.contains(x)` 直接编译失败。判断“当前值是否在本类型的预设里”要写 `ModelPresets.for-type(kind).index-of(root.value) >= 0`。
- `let x = ...; prop = x;` 之后局部已被移动，再拿它比较会报 `borrow of moved value`；要么把赋值挪到后面，要么回读属性（注释里写清“read the property back”），不要为此另存一份副本。
- 预设表这类纯逻辑放在 `export global` 的 `public pure function` 里，Rust 侧才会生成 `invoke_xxx`，单元测试可以直接断言表格本身（见 `native_pages::tests::provider_presets_follow_the_model_type`），不必靠截图猜下拉里有什么。

## 折叠行右侧指标要靠 payload 字段，不要指望后来帧补 2026-11-14 [前端]
- 现象：工作过程里「上下文压缩」条目右侧只有模型轮次，压缩后的上下文占用和耗时都是空；其他工具行正常。
- 判因：工具行的字数/耗时来自 `NativeWorkflowEntry::from_payload`，它只认 `request_context_tokens`/`request_usage` 与 `duration_ms`；压缩事件的占用是 `context_tokens_after`（重建后），也没有耗时字段，所以两项都取空。且 `Timeline::upsert_tool` 每次都用新帧覆盖 `tokens/duration`，同一 id 的后续帧（如溢出恢复事件）会把已显示的指标清空。
- 修法：压缩类条目单独取「重建后」字段族（`context_tokens_after` 等）与 `duration_ms`；运行时在发起压缩时记一次 `Instant` 并写入 `duration_ms`；折叠行指标改为「新帧非空才覆盖」。
- 附带：completed 时间线条目不可改写（`commit_item` 先写者胜），同一 `compaction_id` 的第二个事件持久化会被丢弃——所以耗时必须在真正完成压缩的那条 payload 里。

## 换远端地址不等于换 pull 的目标 2026-11-13 [工程]
- 现象：`git remote set-url origin https://github.com/<org>/<repo>.git` 之后 `git pull` 回「已经是最新的」，但本地与 GitHub 明显不一致。
- 判因：`git pull` 走的是分支的 upstream（`git branch -vv` 显示 `[gitea/main]` 一类），与 `origin` 的 url 无关；只要 `branch.<name>.remote` 还指着另一个 remote（本地裸仓库），pull 就永远「已是最新」。`set-url` 只改地址，upstream 要单独 `git branch --set-upstream-to=origin/main main`。
- 落后还是分叉只需三步：`git fetch <remote>` → `git rev-list --left-right --count main...origin/main` → `git log --oneline <remote>..main`。别把 pull 的「Already up to date」当结论。
- 附带坑：多形态共用的便携 git 若把 exec-path 编译成构建机路径，`git-remote-https` 一类 helper 全部找不到，报 `git: 'remote-https' is not a git command`，而 `status/log/commit` 照常工作——先看 `echo $GIT_EXEC_PATH` 与 `ls $(git --exec-path)`，别去查网络和凭据。
- 日志类文件（`docs/功能迭代.md`、`docs/经验教训.md`）的冲突几乎都是两侧追加：两侧内容都保留，合并后相对两侧都应只有新增行，且真实 BOM（`EF BB BF`）不能被改写。

## 问询面板/计划面板：先宽松恢复，再严格校验
- 面板类工具的参数错误里，“结构不对”和“语义不对”要分开处理：包装层（`raw`/`input`/`arguments`）、列表被写成字符串、裸数组、别名键、字符串布尔值都属于**编码抖动**，必须在工具边界修好并让调用成功；未知字段、未知状态、冲突项才报错。
- 报错必须指向真正的问题（哪个字段、解析器定位、收到什么），并附**唯一**规范示例。工具描述与 args 文档里直接写示例，比只在报错里教更省一轮。
- 只给一个选项（字符串或对象）是合法形态，别用 `unwrap_or(0)` 之类的计数把它算成“缺 options”。

## Slint ListView 的 content-height 只在被写入时重算：滚动跟随必须有外部节拍
- 列表末尾行变高（流式思考、命令输出）时，`ListView` 不会主动重算 `content-height`，`scrolled` 也不会自发触发。因此“内容变化 → 置一次 settle → 写一次 `content-y`”只能修正一帧；之后没有任何写入，跟随就永久停住。条目少（不需要滚动）时看起来仍正常，条目一多就变成“结束时一次性贴出”。
- 跟随要用运行期间的短节拍（如 50ms）持续贴底，值未变化时不写属性（无重绘成本）；一次性修正只能用于分页锚点这类离散事件。
- 判断“读者是否停在尾部”只能用**滚动偏移的方向**（偏移真的向上移动才算上滚），不能用 `visible − content − content-y` 的高度差：内容增长会让这个差值为负，被误判成上滚。
- 折叠区高度按整行（26px）量化，避免行内文本逐帧增长时整块高度抖动。
- 2026-11-12 [桌面版/忙碌判定] 前台的「活跃轮次」不是线程是否在跑的答案：它只属于本窗口正在泵的那一条流，切到别的线程再回来、重启应用、或运行时自己开启下一轮时它就空了，于是「运行中再发消息」的本地持有判定失效，消息又交给引擎 park 成「排队中」气泡——而且轮次越长（工作过程条目越多）越容易遇到，看起来像「条目多了就复发」。正确口径是把本地泵送、在途提交与 durable 快照（轮次状态里仍在生成/排队）合并判断，并由观察器在该线程真正静默时释放等待消息；前台泵收到 done 时若 durable 仍显示有后续轮次，不能抢先把 busy 清掉。- 同一处还有个连带坑：持有分支在此之前已经写过 submitting 栅栏，早退时没有复位，于是「提交中」永不复位、历史观察器因为 local_busy 恒真而整段停更，界面卡在「模型输出中」。凡是提前 return 的路径，都要检查它是否留下了别人等的栅栏或锁。

## 长嵌套参数：先怀疑自己漏字符，再怀疑传输
- 报错位置恒定、回显原文与自己的输入差一两个字符时，第一步是把两份文本逐字符比对，而不是改文案重试。实测 `write_file` 对 `{"`、`{'`、`{{"` 都原样保留，说明管线不吞字符，漏的是生成端。
- 同时要查修复器本身：补 `{"` 时若只补 `{"` 而留下裸键名（`question"`），后续扫描会把键名收尾引号当字符串开头，整段错位并把后面的容器字符一起吞掉——这会让"能修"的载荷变成"修坏"。
- 补出的容器必须同步入栈，否则对象内部的逗号会被当成数组里的新对象起点。

## 工作过程折叠区：`process_newer` 守卫会冻住正在流式的思考行

折叠区一旦加载过分页，`process_newer` 就为真。`sync_process_entry`（timeline.rs）和 `merge_reasoning_tail`（timeline_text.rs）都用 `if bar.process_newer { return; }` 挡住 live 数据覆盖分页——这条守卫本意正确，但它把**当前正在流式的那一行**也一起挡了，于是多步之后思考条目停在半句，只有开头几步看着是流式的。

判据要按“这是不是当前 reducer 的活行”区分，而不是按“有没有更新的页”或“这一刻是不是还在流式”一刀切：
- 同一 id 的活行在分页折叠中应当始终可更新：流式文本、结算（DONE）、随后到达的 token/耗时要走同一条通路。只放行 `STATUS_RUNNING` 仍会丢掉收尾那一次 patch，而 `process_newer` 为真时尾部刷新定时器不跑（tool_process.slint 要求 `!has-newer`），折叠里那条思考就会一直转圈并缺指标，直到用户往前翻页。
- 合并时保留页侧更完整的数据：传入两列为空则沿用旧值；已结算且旧文本更长则保留旧文本与摘要；已结算条目不允许被活行退回运行中。
- 条目不存在 → `process_newer` 时仍然不能插入，否则会在未加载的页之上重复或错序。
- 但“不存在”的条目里还有一类必须插入：**新一轮正在流式的思考行（新 id）**。分页只带已提交的步骤，正在写的思考永远不在页里；只放行“同 id 活行”时，读者看到的是开头几轮流式正常、之后突然整轮整轮地出现——形如“第 N 轮之后没有流式了”。放行条件是 `process_paged && !process_newer && 仍是运行中`（`timeline_text::live_tail_fits`）；已结算且页里没有的条目保持不插入。

回归测试：`timeline::tests::streaming_thought_survives_a_paged_fold_with_a_newer_page`；反向保护由 `chat_process::tests::delayed_process_page_keeps_the_live_thought_and_older_page_stays_put` 守住，改守卫时两个都要跑。

排查教训：视图侧跟随（ListView content-height、settle、50ms 节拍）都正常时，不要再在 Slint 里缝补——先用 Rust 测试直接驱动 `Timeline`，把“数据层有没有增长”和“视图有没有跟上”分开，能一步定位。

## 一次思考预算触顶，不要把后续每一轮都关思考

`EmptyOutputGuard` 有两个用途不同的状态，早期被合并成一个：
- `recovery_used`：本用户轮次只允许恢复一次，防空输出循环 —— 这个必须是全轮次。
- 关思考：只是那次恢复重发需要，不能传染。

原先 `config_override` 直接看 `recovery_used` 就返回 `reasoning_effort = none`，而 `orchestrator/execute.rs` 每轮 `call_llm` 都传它。结果一次思考预算触顶（传输层重发会置 `transport_recovery_used`，`observe` 再把 `recovery_used` 置真）之后，该用户轮次剩余所有轮次全部关思考。实测 31 轮会话里第 10 轮起连续 22 轮没有思考过程。

判据：`config_override` 回答的是“下一次请求要不要关思考”，不是“这一轮对话是不是在恢复状态”。用 `thinking_override` 单独表示前者；覆盖要一直有效到该轮真正返回（`observe` 时清除），不能在被读取时就清掉——`execute.rs` 的上下文溢出重试会重新发起同一轮请求，第一次尝试失败就把关思考丢了。

诊断手法：导出会话 jsonl，按 `model_round` 打表看 `reasoning` 长度、`thinking_disabled`、`transport_recovery_used`、`thinking_token_budget`。注意 `round_usage` 里的 input/reasoning tokens 是累计值，要算增量才能判断该轮到底有没有思考。

## 完成态是状态，不是新闻：别让三处默认 idle 各自否决
- 线程最后一轮的终态是持久事实，只有新一轮开始才能替换；「刚完成」的新鲜度只属于 toast、伙伴动画这类瞬时表现。把两者混在一起就会在「满屏绿勾」和「完成后全是空闲」之间反复翻转——每加一道过滤只是移动翻转点，没有解决状态所有权。这次同一个侧栏状态点被 Rust 状态投影（6 秒 TTL）、Slint 已读判定、目录/历史回读三处各写一次，任一晚到的读都能把刚写的终态改回 idle。
- 同一份状态只能有一个写入者。其余路径只读，或用 revision 栅栏阻止旧读覆盖新值；视图层不要自己重新推导「已看过/是否本窗口内」，那会把业务状态变成 UI 局部状态。
- 绝对 Unix 秒不能塞进 f32：当前量级步长 128 秒，同一线程 128 秒内连续两轮完成的「结算时间」会变成同一个值，所有基于它的 `<=` / `>=` 判定随机失效，表象正是「偶尔正常」。身份用单调递增轮次 id，时间用 f64 或相对窗口秒数，绝不用时间戳当身份。
- 回归锁不变量而不是时长：断言「通知过期后行仍保持终态」「transport idle 不覆盖 completed」「新轮次清除旧终态」，不要只测「6 秒后是否消失」。

## 命令里再套一层壳：按宿主意图分流，别让第二层文本解析发生

- 现象与代价：模型写 `powershell -Command "..."` 时外层 shell 会先解析一次，`$var`/`$_`/`$env:` 被提前展开、`\"` 被吞。最坏的不是报错而是静默算错：实测 `& { $x = 41; $x + 1 }` 输出 `1`。
- 判据按「宿主意图」而不是按写法：裸 `powershell`/`pwsh`（与当前宿主同一解释器）= 冗余包装，剥掉直接执行；完整路径或 `-Version` = 确实要系统 Windows PowerShell，保留子进程并把内层脚本改走 `-EncodedCommand`。两条路都只解析一次。
- 剥壳是改语义的操作，边界必须保守：`-File`、`-EncodedCommand`、位置参数、包装后还跟别的语句，一律原样放行。
- 还原转义只碰外层引入的那几种（`""`、`\"`、反引号 + 引号），内层语法（如反引号 `n`）原样保留；`\"` 是否算转义取决于后面还有没有收尾引号，否则 `"...\Windows\"` 的路径会被吃掉。
- 提示词里写「不要嵌套」只能缓解：习惯改不掉的模型永远存在，工具边界必须兜住。

## 改工具“提示”先分清模型到底看哪一层

内置工具的模型侧签名不是 `builtin_tool_specs_with_language` 里的原文：`prompt_surface::prompt_tool_spec` 会把带 `SurfaceRule` 的工具换成手写 `brief_zh/brief_en`，并整段删掉参数 `description`、按 `drop_fields` 删掉字段。于是改 `config/i18n.messages.json` 里 `tool.spec.*.args.*` 只能改管理端/设置页文案，模型一个字都看不到；被 `drop_fields` 掉的参数（例如图像生成的 `mask_path`、`strength`）模型连字段名都不知道，给了也不会填。
- 判断影响面：先看 `prompt_surface.rs` 的 `SURFACE_RULES` 有没有这个工具。有 → 改 brief + drop_fields；没有 → i18n 描述才直达模型。
- 行为约束放哪：`tools_protocol.txt` 的 `[[HAS_*]]` 块只在非 `function_call` 模式渲染，`function_call` 模式整块省略；要所有模式都生效的规则写进 `engineering.txt` 的条件块，并在 `build_system_prompt_skeleton` 的 `engineering_flags` 里加同名开关。
- 改完用 `tool_spec_prompt_budget_report` 复核模型侧字符预算：内置工具的精简投影总长有 20k 级上限，加字段/加文案会顶到阈值，需要显式调阈值而不是悄悄裁能力。

窗口内跨线程共享的本地状态（例如"等待发送"的本地持有条目）在投影到界面时必须按当前线程过滤：投影函数内部统一用当前 active session 过滤，而不是指望每个调用点自己筛。切换线程的第一步应是清掉上一线程的引擎行缓存并立即重绘条带，再异步补齐新线程的行；否则旧条目会一直挂在新线程的输入框上方（异步刷新回调重新发布时还会把它再带回来）。

"本地持有、延后发送"的消息必须有明确的移交时机：只在用户停留在该线程时成立。切走线程要么交给引擎队列，要么由后台观察完成事件，否则完成信号只会在回到该线程时才被看到。另外，本地持有不等于"已发送"，任何把它写进对话记录的分支（例如切回时重建等待气泡）都会让它看起来像一条正式消息，只应在输入区条带里出现。

## 覆盖层要跟“用户刚做的动作”对齐，别跟“后端还没回写的台账”对齐
- 现象：`输入其他答案` 这行的占位提示一直压在已输入内容上面。根因是真实的输入控件在编辑时**故意不回写模型**（保住光标与输入法），而占位提示/勾选态读的是模型里的旧值（还是空串），于是提示一直认为“这里没内容”。占位提示又是后声明的，天然盖在输入控件上方。
- 判据：凡是“用户正在改、但状态要延后发布”的控件，覆盖层与其状态标记一律读控件自身的属性（`input.text` / `input.preedit-text`），不读延迟台账；覆盖层还要声明在输入控件之前（z 序在下）。台账清零的外部动作（如“无偏好”会清空答案）需要单独同步：`changed` 只吃本组件的简单属性，先把它镜像成本地 property 再监听。
- 悬停读全文不要用 `Tooltip { text: … }`：该文本模式不折行，长句会拉出一条比窗口还宽的提示。长文本一律自绘卡片，固定最大宽度 + `wrap: word-wrap`，高度按各行 `preferred-height` 相加（而不是按 layout 的 preferred-height 猜）。
- Tooltip 内容拿不到外层作用域，循环里的行要先把行本身抽成组件，再让卡片读组件自己的 root 属性。
- **Tooltip 必须挂在真正接管指针的那个元素内部**（`TouchArea { ... Tooltip {...} }`，即 drag_row / host_hud 的写法）。挂在行的 Rectangle 根上、或做成某个 Text 的兄弟节点时，hover 一次都不会触发：`TooltipArea` 靠 `input_event_filter_before_children` 统计悬停，而事件只沿命中项那条路径下发，被上层 `TouchArea` 或 Text 挡住的兄弟节点收不到任何事件。判断"是否真的被截断"用 `elided-text.preferred-width > elided-text.width`（elide 的 Text 的 preferred-width 仍是完整文本宽），不要用字符数猜。

## 思考/正文“只剩整块贴出”先怀疑线程生命周期，不是折叠渲染
- 现象：长任务中途切到别的线程再回来，工作过程里的思考条目不再逐字流出，而是跟着工具行整块出现、内容已完整；不切线程时多轮都正常。
- 判因顺序：先看这条文本凭什么进界面。前台是 `pump_stream` 把 token 写进 reducer（`append_reasoning_item` → `flush_thinking`，33ms/帧）；切线程后只剩 durable 快照 `NativeThreadUpdate::Reset/Turns`，而 assistant 的 reasoning 是**每轮结束才 commit**，正在跑的那轮在快照里根本不存在。所以“切回来整块出现”= 流断了，不是渲染或分页守卫的问题。
- 根治形态：**每个线程各自持有一个 reducer**。切走时不 take 前台流、不 stop 泵、不 clear 模型，只把流和它的 reducer 挪到 `background` 继续 drain（不 drain 会让引擎的 bounded channel 反压，把整轮卡住）；切回时把该线程的 reducer 重新绑回窗口，思考行、折叠、正文块都还在，下一拍就续上。
- 关键约束：窗口级写入（`set_timeline`、`set_busy`、`set_stopping`、plan 面板、`stream_updates`）必须按“这个 reducer 是不是当前线程”门控，否则后台线程的帧会把读者拽进另一个线程；per-session 的（`set_session_status`）可以照写。
- 两个坑：①`Timeline::needs_publish()` 只返回一次 true，重绑同一 reducer 时必须显式 `set_timeline`；②有活轮的 reducer 绝不能被 LRU 淘汰，否则泵写的是孤儿模型，界面静默不更新。

## 终端里的半块浮雕：字格不是方的，VTE 也不会告诉你像素 2026-11-14 [命令行]
- 现象：命令行欢迎头像在 Windows 正常、在 Ubuntu 的 GNOME Terminal 里看起来“左右扁扁”。
- 判据：半块字形（▀/▄）每个字符覆盖 2×2 源像素，屏幕上的源像素是 `cell_width × cell_height/2`。终端字格比（高/宽）来自字体，不是常数：Windows 光栅字格 8×16=2.0，而实测这台 GNOME Terminal 是 10×26=2.6。按 2.1 猜就会多画 20% 的行，头像被竖向拉高 → 读起来是横向压扁。量法：截图里数半块行高，或直接看标题两行的行距。
- 修法：`TIOCGWINSZ` 的 `ws_xpixel/ws_ypixel` 在 VTE（GNOME Terminal/Tilix）里恒为 0，量不到；改问终端本身——`CSI 14 t` 回 `ESC[4;h;w t`（文本区像素），`CSI 18 t` 回 `ESC[8;rows;cols t`（文本区字数），两者相除就是真字格比（VTE 不答 `CSI 16 t`）。探测要 `poll(2)` 加超时、只读不等待、结果 `OnceLock` 缓存；迟到的应答是不认识的 CSI，事件循环会忽略。
- 提示：CLI 的头像/图表类 ASCII 艺术都要按这个比例算行数，否则换台机器就变形；`WUNDER_CLI_CELL_ASPECT` 留作手动覆盖。

## `dry_run` 预览不能沿用「已落盘」的字段口径 2026-11-15 [工具][模型契约]
- 现象：`文本编辑`/`写入文件` 带 `dry_run: true` 时，模型收到的结果里仍是 `changed: true`、`changed_files: 1`。预览根本没写盘，模型却容易当成「已经改好了」，直接跳过真正的写入。
- 判因：写入结果的投影层（`orchestrator/tool_result_payload.rs`）用 `file_write_change` 判「是否真的改了」，该函数对 `dry_run` 故意返回 `None`（无法判定就不许断言没变），随后回落到 `changed_files > 0`——而预览也照样把 diff 计数和 `changed_files: 1` 填满，于是被投影成 `changed: true`。
- 规矩：`changed` 只表示「磁盘已变」，预览期间恒为 `false`；「若执行会不会改」单独用 `would_change`/`would_change_files` 表达（`file_write_would_change` 复用同一套计数口径，并允许编辑类结果缺少 `existed` 时按 diff 计数判定）。新增任何写类工具时都不要让预览走「已落盘」的键。

## 状态文本不是存活事实 2026-11-15 [runtime][desktop]
- 现象：线程明明空着，侧边栏和归档入口却一直说「正在运行，请先停止再归档」，重启也不消失。
- 判因：监视缓存里的 `running` 与任务台账里的 `running` 都被当成了「有人在跑」。进程半路消失后，前者停在文本上，后者的行队列根本不会领取（只领 pending/retry），于是两处都永久残留；归档门禁据此永久拒绝。
- 规矩：存活只认三种可失效的证据——本进程的执行集合、未过期的会话锁（到期即失效，别用心跳提前判死，一次续期失败就会误杀正在跑的轮次）、队列仍会领取的任务行（pending/retry，或刚领取 15s 内的 running）。文本、stage、summary 一律只作展示。
- 配套：崩溃残留必须有人结算。启动扫描把这些 running 行落为 cancelled（跳过仍持锁的实例），否则任何「只领取 pending/retry」的队列都会把它们留到天荒地老。
- 复用检查：任何「是否在途」的判定都要能列出它的失效条件；只有「有没有这一行」而没有到期判断的查询（例如锁行存在性）不属于存活判定。

## 跨异步读的跳转按 id，不按位置 2026-11-15 [desktop][ui]
- 现象：归档一个线程后，侧边栏展开了另一个工作区，像自己跳到了别处。

- 规矩：凡是跳转要跨一次异步读（事务、刷新、轮询），都必须在落地时用稳定 id 重新解析目标；位置只在同一次投影内有效。

## 子进程的语义要按它自己认，不按 `wait_with_output` 认 2026-11-15 [cli][clipboard]
- 现象：命令行按右键复制第一次成功，之后复制新内容一直不生效，剪贴板停在最早那段文字；「已复制」提示也不再出现。
- 判因：`xclip` 写完 stdin 后会 fork 一个守护子进程持有 X 选择权，并**继承 stderr 管道**。`Command::wait_with_output` 要把 stderr 读到 EOF 才返回，而 EOF 要等那个守护进程退出（也就是等别人下一次复制），于是写入任务永不结束；同时「写入在途」的判断把后续每一次复制都静默丢弃了。
- 规矩：凡是可能 fork 后驻留的子进程，都不要用管道 + `wait_with_output` 收尾；stderr 走临时文件、只 `wait()` 自己的进程，并给在途任务留一个「最新一次待写」的槽位而不是丢弃。写剪贴板、拉起浏览器、调用常驻守护进程都属于这一类。
- 同一处还有：剪贴板命令列表必须全量尝试（装 `wl-copy` 但跑在 X11、装 `xclip` 但跑在 Wayland 都很常见），第一个失败就返回会让本来能用的后端永远轮不到。

## 思考流式的两条通道（tail 先、delta 后）让首字重复 2026-11-16 [desktop][runtime][stream]
- 现象：思考条目一出现，最前面的一个 token 是重复的（「我我…」），过一会儿轮次结束又恢复正常。
- 判因：运行时对同一段文本发两帧——`thread_item_tail`（带 UTF-16 offset）先入队，随后才是语义 `llm_output_delta`；桌面桥的 `TailLedger` 只在 tail 越过水位时才放行，而这一轮的第一段 tail 水位必为 0，于是 tail 先落地建立思考行，紧接着的 delta 又是同一段文本，reducer 盲追加就多写了一遍。此后水位被「放行的 tail + 同一段的 delta」重复记账，超过屏幕上的文本，后面的 tail 全被当成重复丢掉，只有轮末 `llm_output.reasoning` 对齐才修好。
- 规矩：同一份文本有两个载体时，去重必须按位置（发送方游标），不能按到达顺序。`llm_output_delta` 上的 `reasoning_offset` 与 tail 的 `offset` 是同一个值；reducer 两路都走 `apply_reasoning_delta` / `apply_reasoning_tail` 按 offset 落地，水位用 `max(offset+len)` 记账而不是累加。
- 排查提示：看到「只有开头重复一个 token」「前几秒不对、轮末自愈」，先查是不是两个通道在同一段文本上各落地一次；再看水位是不是累加记账（累加会让真正的补段被误判为重复）。

- 判因：`ScrollView` 只从**布局子项**推断内容尺寸；把 `WorkflowDetail` 这样的组件直接塞进去，它的 `preferred-height` 是「测量那一刻宽度」下的值，而 `content-height: max(visible-height, detail.preferred-height)` 用的是同一个旧值 → 内容高＝视口高，滚动条自然不出现。面板高度 `min(240px, detail.preferred-height + 16px)` 同样拿到旧值，于是连面板本身都偏矮。这个坑已经踩过三次（思考面板、工具面板、`FoldEntry` 里的同一段）。
- 规矩：往 `ScrollView` 里放会换行的内容，一律「`content-height: max(self.visible-height, column.preferred-height)` + 中间加一层 `VerticalLayout { width: scroll.visible-width }`」，让布局在宽度确定之后再去量文本；不要用子组件的 `preferred-height` 直接当 `content-height` 或面板高度。窄屏（`mobile: true`）走「内联撑高、由页面滚动」，不做嵌套滚动。

## 快照分页里 `has_older` 不能和 `truncated` 共用 2026-11-18 [storage][admin][trajectory]
- 现象：管理端轨迹视图向上滚到最早一页后不再加载，且若用 `truncated` 判断「还能往前」会永远为真——线程一长就变成反复请求一个不存在的更早窗口。
- 判因：`truncated` 原本表示「本次快照被裁过」（`item_total > 本页 items`），翻页时这个条件恒成立；而「还有更早窗口」只该由窗口切分本身给出（轮次上限截断、条目预算不够、单轮被切）。

## 撤销栈的游标别存下标 2026-11-17 [backend][tools][history]
- 现象：删掉中间某一版快照后，再撤销直接报「已退回最早的可用版本」，更早的历史明明还在却永久不可达。
- 判因：游标存的是「第几态」的下标，快照却按编号 `name@N-sha` 落盘。删一格不压实，下标与文件编号就错位，`cursor-1` 找不到文件被当成栈底。
- 规矩：游标存稳定身份（快照文件名），不存会漂移的下标；删除/回收必须把更大的编号整体前移；读取侧再留一道「编号不超过游标的最近一版」兜底，让已经被弄坏的旧目录能自愈。
- 附带：容量兜底不能只有「每 N 小时扫一次」，两次扫描之间足够塞进远超上限的数据；再加一个按写入量触发的闸门（累计 > 8 MiB 立即回收），总占用才有硬边界。

## 回收测试要先算预算，再看「没删」是不是对的 2026-11-17 [backend][tools][history]
- 现象：造了 42 MB / 913 份快照后触发回收，文件一个没少，被当成「上限没做」。
- 判因：当时只有 64 MiB 的字节上限，42 MB 本来就在预算内；而且那批文件是手工造的，绕过了 `snapshot()` 的累计写入计数，闸门也就没被顶开。
- 规矩：写回收/清扫类断言时，先写「预算内必须一份不动」，再写「超预算必须砍到线内」；两个方向都覆盖，才能区分「阈值没触发」和「逻辑不对」。上限可用环境变量临时调小来验证，不必造真实大文件（稀疏文件 `set_len` 就够）。

## 「有上限」不等于「上限会生效」 2026-11-17 [backend][tools][history]
- 现象：连续两轮反馈「全局容量上限没做」。第一轮：42 MB 在 64 MiB 预算内，不动是对的；第二轮同样 42 MB 不动，是因为闸门只看时间和写入计数，而目录是手工造进去的，计数根本没涨。
- 判因：把「阈值存在」当成了「兜底存在」。真正的兜底要满足两条：阈值要落在用户会遇到的量级上，闸门要能在超限后的**下一次写入**就发现超了。
- 规矩：容量类限制用「账本 + 实测」两层——账本记上次实测的总量，之后按写入增量推进；账本缺失或越线就立即实测回收。默认预算按产品真实磁盘预期定（历史是保险不是备份），别把「先给 64 MiB 保守点」当稳妥。
- 附带：造数据测回收时走真接口（`snapshot()`），手搓目录会绕过所有计数，测出来的是「没触发」而不是「没实现」。

## 流式聊天里 JS 钉底和浏览器滚动锚定只能留一套 2026-11-18 [frontend][ui][scroll]
- 现象：云端版长会话（轮次多、虚拟列表已生效）流式期间，最新一轮的工作过程标题会短暂出现两层：上一层颜色发灰、右侧耗时比下一层少 1s，正文与状态条正常，过一两秒自愈。
- 判因：40px 高的兄弟行不可能错位 10px 重叠，DOM 与虚拟行 key 也都查不到重复；差值 1s 说明那是上一帧/上一秒的样式被留在了画面上。流式时一行内容的高度变化会分别触发「外层列表钉底」和「过程区内部跟随钉底」两条滚动写入，而浏览器自带的滚动锚定在看到可视区上方高度变化时还会再补一次 scrollTop——同一帧存在两套滚动位置，合成器就会把内容画在旧偏移上。
- 规矩：跟随位置只允许一个所有者。自管跟随的滚动容器加 `overflow-anchor: none`；任何钉底写入前先算 `scrollHeight - clientHeight`，已经在底部就不再赋值；内层滚动区同样只在真正落后时写。验证时用「一行一个 `.timeline-process-head`、行矩形互不重叠、连续滚动的每个采样都成立」来区分「DOM 重复」和「绘制重影」。

## 工具超时打断不能连坐正在干活的进程 2026-11-18 [backend][runtime][tools]
- 现象：模型跑分钟级渲染/构建时，exec_command 在约 60 秒处返回 `execution_outcome=unknown`；命令其实已启动，模型去重试，第二次被自己的单实例锁拦下，只能靠 `ps` 判断到底跑没跑。
- 判因：可脱离路径在「等待窗口结束前」由工具调用自身持有子进程与进程树守卫，外层看门狗一旦触发就把 future 丢掉，`ProcessTree::drop` 连同子进程整棵树一起杀掉或留下半死状态；同时结果里只有一句「结果未知」，不带会话 id。另有一处旧账：看门狗按 yield 算（yield+30s），比工具前台阻塞路径的 timeout_s（默认 120s）还窄，导致「工具自己超时回收」被替换成「被打断 + 结果未知」。

## 云端版"流式消失"不是帧率问题，是两套渲染源各自丢了 tail 2026-11-18 [frontend][realtime][streaming]

## 流式渲染的失效信号必须由「写数据的那条路径」给出 2026-11-18 [frontend][realtime][streaming]

## 云端版流式「卡在开头再整段冒出」的两个真因 2026-11-19 [frontend][realtime][streaming]
- 现象：思考与正文都只流开头一小段，然后停住，工具调用/轮次结束时整段出现；1.0.1 把持久展示行改成「截断窗口 + 实时 tail」之后一直存在，之前修的都是时钟/渲染源。

- 规矩：展示窗口（云端版的渲染源）里，偏移只用来定位，不用来证明连续性——只有「窗口里已存在同一段文字」才算重放，其余（前跳、回退、归零）一律追加，缺口交给终态正文；实时窗口按自身长度寻址，偏移空间重建时窗口不能移动；正文渲染源必须是连续实时文本，持久预览只能当兜底。durable 兜底路径（展示窗口尚未提交时）保留「回退帧丢弃」，因为那条路每一步都有持久行可对齐，丢掉一段不会冻住后续。排查先量三件事：WS 帧率与 offset 序列、store 里 `__thread_live`/`reasoning` 长度、DOM 文本长度，三者比例失衡即定位是哪一层。诊断脚本 `frontend/scripts/verify-chat-stream-pacing.mjs`，回归 `thread-view-live-tail-regression.test.ts`。

## WS 通道「按请求投递」与「按连接去重」的冲突 2026-11-19 [frontend][realtime][streaming]
- 现象：云端版长回答只流开头一小段（约 1/4），工具调用或轮次结束后整段出现；服务端 WS 帧本身完整、无长间隔。
- 判因：同一条 chat/ws 连接上并存两个实时通道（`watch` 与 `start`）。客户端在发送时会本地中止显示 watcher（`cancelOnAbort:false`，不发 cancel），服务端 feeder 却继续按那个 request_id 发布 tail；服务端为省带宽对每条连接只投递一次 tail（`sent_tails` 去重，首个通道赢），于是大部分 tail 被投给已经死掉的通道。客户端 `if (!entry) return` 不认识这个 request_id，整批丢弃 → 正文停在 1/4，终态正文到达时一次性补齐。
- 规矩：①「每条连接只投一次」的优化只有在客户端「按会话兜底」时才安全——多路复用器遇到无主的实时会话帧，必须按 `session_id` 落到同会话仍存活的通道，而不是丢；②终态与控制帧（final / transport_final / error / queued / stream_started）绝不借道，否则会误结算别的轮次；③借道帧只渲染，不参与该通道的结算记账。
- 排查手法（省几轮猜测）：在页面里临时埋点记三件事——WS 收到多少帧、`applyChatThreadServerEvent` 收到多少帧、store 里 `__thread_live` 长度，再看多路复用器 `pending` 命中情况；三者比例失衡就说明丢在传输/路由层，而不是渲染层。真实栈验收用构建产物（nginx 直出 dist），dev server 的源码模块实例与页面实例可能不是同一份，读 store 会得到空值。

## 写类工具不要把自己刚发出去的内容原样回灌 2026-11-19 [tools][context][diff]
- **已反转（2026-11-20）**：真实会话里模型会把历史参数占位符复制回来当正文，且不回灌会让模型忘记刚写内容、频繁回读。现在改为「完整回显 unified diff（2 MiB 安全阀）」+「历史参数用对象哨兵并在工具边界拦截」。下面的 32KB/DiffEcho::Authored 仅作历史记录，不要按它改回去。
- 现象：「写入文件结果不再压缩」之后，新建一个 300 KB 文件会得到同体积的 unified diff（全 `+` 行），一次调用就把上下文顶满，历史里还会随每次写操作累积。
- 判因：`write_file` 只在「原来存在」时才做源大小守卫（`MAX_DIFF_SOURCE_BYTES`）；新建文件走 `diff_added_file`，`unified_diff` 又对 <512 KB 的源重算完整区域，等于把模型刚发出去的正文再送回去一遍，信息增量为零。观察层现在对写类结果不做压缩，上游也没有第二道闸。
- 规矩：①写类回执的价值在「回显模型没说过的事实」，不在这份正文本身——默认根本不给 diff（`DiffEcho::Authored`），只给回执 + 计数 + `changed_lines`；新建文件同理（`NewFile`）。②只有三处必须给 diff：`dry_run` 预览、undo/redo 恢复快照（内容不是这次调用写的）、落盘字节与提交内容不一致（BOM 回填）。③必须给 diff 时套结构预算（`line_diff::MAX_UNIFIED_DIFF_BYTES`=32KB），放不下的 hunk 折成「头 + 省略行数」，计数与 `diff_omitted` 保持准确；④「不被观察层压缩」与「不设上限」是两件事，生产者层要自己兜底。

## 花括号“被吃掉”的真凶是流式分片的前缀去重 2026-11-20 [llm][stream][tools][write]
- 现象：模型反馈 `write_file` / heredoc 把 Python 的 `'{:.1f}'.format(...)` 落盘成 `':.1f}'`，左花括号丢失；`py_compile` 仍通过，导致生成的 SVG 坐标全废。
- 判因（已定案，之前的两次误判都写在这里供后人避坑）：真凶是 `services/llm/stream_tool.rs` 的 `merge_stream_delta_field`。它为了兼容「有些提供方把累积快照塞进 delta 通道」，写了 `if target.starts_with(fragment) { return; }`——把「片段是累积文本前缀」当成过期快照丢弃。而**工具参数正文永远以左花括号开头**，于是任何一个「单独一个左花括号」的合法 delta 分片都满足这个条件，被静默吞掉。这只解释得通丢的全是左花括号、位置随机、同一句里有的丢有的不丢、桌面版与云端版同时复现、以及 `}` 从不受影响（它不是前缀）。
- 误判一：以为模型自己复制参数时手滑。误判二：以为写入/编码链路。两次都只看到「缺左花括号的落盘结果」，没意识到 JSON 本身仍然合法，所以任何「解析是否成功」的检查都发现不了。
- 修复：反向前缀去重只对 ≥64 字符的整段快照生效，短分片一律按正常内容追加；回调用 `merge_stream_delta_field_keeps_brace_only_fragments` 与 `update_stream_tool_calls_keeps_a_lone_brace_delta` 两个测试钉住（修复前分别是 `{"content": "a :.1f}}` 与期望值不符）。
- 规矩：①写入回执给出 sha256、`echo_content`（小文件）和完整 unified diff，先看落盘事实；②Python 语法校验补 `.format()` 花括号配平，孤立 `}` 直接报行号——`py_compile` 只查语法，查不出这种语义损坏；③行区间替换回显 `range_echo`（实际首尾行与相邻行），边界错位当场可见；④`read_file` 单文件不再把 `>>> path` 放进正文，正文行号以 `content_start_line` 为准。定位同类问题时，导出 JSONL 对比「工具收到的参数」与「工具回执里的文件内容」，不要只凭模型自述。

- 现象：一次长任务（单轮 71 次模型请求、上下文 228k）触发 overflow 压缩，摘要本身质量很好、明确列了 6 条待办，交接后模型却回「已完成主体制作」并把渲染/配乐列为「下一步」，用户看到的是「压缩后忘了任务」。

- 判因：`line-height-factor` 乘的是字体的 ascent+descent(+line gap)，实测雅黑 1.32–1.36em、文泉驿微米黑 1.17em，同一 factor 在不同字体上差 20% 以上；而且上游 `StyledText` 压根没有这个属性（只有 `Text`/`TextInput`/`TextEdit` 有），不补 fork 就只能吃字体原始行距。

## 跨进程传命令：别让包装器和引擎各记一套约定 2026-11-21 [安卓版/命令执行]

- 判因：`FACE.with(|slot| slot.get_or_init(...))` 的返回值借用自闭包形参，而 `LocalKey::with` 的签名是 `FnOnce(&T) -> R`，`R` 在外部已确定，无法携带这个匿名生命周期；`OnceCell::get_or_init` 只能把借用绑到 `&self` 上。于是「线程局部缓存 + 返回引用」在类型上就不成立，加 `move` 只是让闭包自己持有 `slot`，同样逃不出 `with`。

- 判因：气泡宽度 `min(bubble-row*0.7, bubble-body.preferred-width + 24px)`，而 `bubble-body` 又写了 `width: parent.width - 24px`——一个自带显式宽度的布局会把「自己的实际宽度」当成 `preferred-width` 报回去，于是「气泡宽度 ← 内容首选宽度 ← 气泡宽度」成了闭环，Slint 只能收敛到一个偏小的值；卡片本身又固定 `column-width: 360px`，比气泡内宽大，就画到气泡外面去了。行本身 `clip: true`，于是被裁。

- 现象：安卓版内置浏览器在 `scroll` 之后截图，顶部出现与滚动距离等高的空白，滚动超过一屏整张图全白；DOM 与 `observe_text` 都正常，回滚到顶部截图立刻恢复。

- 规矩：Windows 输入回归要用真实窗口发送目标消息形态，不替它补正常情况下不存在的前置事件；模态菜单的按键收尾放在 Winit 消息层统一处理，不在单个弹窗里补另一颗按键；嵌套 paint 必须 PostMessage 到回调和系统模态循环都退出之后，验收要同时断言动作生效与新帧实际派发。

## 同一 ~/.wunder 多开桌面实例会打断在途轮次 2026-11-24 [桌面版/单实例/崩溃恢复]
- 现象：正在对话的线程每次完成后状态都是「已停止」，而受理表里对应轮次是 `interrupted`、`stop_reason=process_restart`。
- 判因：单实例锁按可执行文件路径区分；安装版与开发版路径不同但共用同一个 `~/.wunder`，第二个实例启动时的崩溃清扫把第一个实例的线程租约当成残骸清掉，并把它正在执行的轮次和监视状态结算成中断。
- 规矩：启动清扫只在本机没有其它存活桌面实例时执行；单实例按本地数据目录认领，而不是按 exe 路径。需要截图/验证界面时不要另起一个共享同一 home 的桌面进程，优先用 smoke/离屏渲染；确需多开时必须确认它不会跑启动清扫。


## 外部文件拖入不能用单次合成 DragMove 验收 2026-11-24 [桌面版/winit/X11/拖放]
- 现象：工作目录和输入区在 synthetic DropArea 测试里有提示，从文件管理器真实拖入却完全没有；补上 X11 坐标后又变成第一次移动闪现、随后立即消失。
- 判因：X11 `XdndPosition` 自带根坐标，不能只靠普通鼠标事件留下的旧位置；同时 winit 适配层把一次外部坐标移动既发成 `DragMove` 又排队成普通 `MouseMoved`，后者命中编辑器后会对刚接受拖入的 DropArea 发 `Exit`。单次合成 DragMove 没有普通事件穿插，因此两条断链都测不到。
- 规矩：外部拖入验收必须走真实 XDND 协商并连续移动，至少覆盖进入、持续悬停、移出和松手；拖拽期间只派发 DragMove，不再派发普通 Moved。提示浮层用常驻元素切换 visible，避免条件创建改变命中树；Windows、X11 的外部拖拽坐标都要从各自系统事件持续回报。

## 读文件去重要按“正文是否还在上下文”失效，别按请求参数判重 2026-11-24 [引擎/工具/上下文]
- 现象：给读取工具加“同内容不返回第二遍”后，最危险的不是漏命中，而是模型收到“内容未变”却找不到那段正文——压缩、结果转存成 tool-result 句柄、单条结果被 token 预算截断都会让旧工具结果离开请求。
- 判因：去重键若按路径+行号，改了范围写法就漏命中；若只看文件大小/mtime，同秒写入、保留时间戳的同步工具会误判“文件没改”。真正等价的条件是“这次要发出的字节和上次一模一样，且那段字节还在请求里”。
- 规矩：①判重用将要发给模型的正文字节摘要，范围写法、预算、编码、截断自然参与比较；②上下文压缩（`model_context_replaced`）、观测被截断或转存句柄时整条线程的回执立即作废，跨两个用户轮次自动过期；③只在整段结果完整发出后才登记回执，并提供 `fresh=true` 让模型显式强制重取；④去重是省 token 的手段，元数据（行数、范围、content_start_line）必须仍取自本次调用，不能照抄旧结果。

## 右键菜单后假死要在渲染请求闩锁层收口，别只补 Win32 消息 2026-11-25 [桌面版/winit/Slint/右键菜单]
- 现象：Windows 上有工作线程持续跑时，工作目录右键呼出菜单即停帧；选“重命名/引用到聊天”后动作已执行但界面完全停在旧帧，最小化再恢复立即可用；此前两轮修 `WM_EXITMENULOOP` 右键释放与嵌套 `WM_PAINT` 仍未根治。
- 判因：原生 `TrackPopupMenu` 的模态循环里一次 `RedrawRequested` 丢失，Slint 适配层 `pending_redraw` 闩锁一旦留在 true，后续所有 `request_redraw()` 都空转（`winitwindowadapter.rs:2291`、单帧 `frame_throttle.rs:85-117` 无重试）；工作线程 33ms 刷帧使 `Focused(true)` 的 `recently_presented<250ms` 分支跳过强制 `draw()`（`:1506-1547`），无法自愈；最小化恢复走 `set_visibility()` 清闩锁并重新排帧（`:2026-2028`），所以必然“变好”。上游 Slint #5863 同类现象也定位在 request_redraw/RedrawRequested 丢失。
- 规矩：菜单类假死验收必须断言“新帧真的画出来”，不能只断言动作执行或消息计数；修复要落到适配层闩锁（焦点回来强制清 `pending_redraw` 并重排帧，或加可见窗口下的看门狗重排），并配真实窗口 + 后台持续刷帧的回归；Win32 鼠标释放/嵌套 paint 补丁只能解决输入与消息层，替代不了渲染状态机复位。

## 一帧丢失不能变成永久：闩锁要能自证超时，空脏区也要上屏 2026-11-25 [桌面版/Slint/软件渲染]
- 现象：同上条右键假死。给 `pending_redraw` 加看门狗后仍会复发：某些序列里看门狗连试两次都没拿到帧，随后闩锁永远留在 true，之后每一次 `request_redraw()` 都被合并进这个死闩锁，界面停在旧帧直到用户最小化再恢复。
- 判因：①看门狗是"计数重试"，只重试 2 次就放弃，且放弃时不清闩锁；②软件渲染器在 damage 为空时直接跳过 `present_with_damage`，于是"系统要求重画"（原生菜单收起、`WM_SETREDRAW` 恢复、窗口被遮挡后暴露）这一类没有 Slint 脏区的帧一像素都不上屏；③原生菜单关闭没有任何强制整帧，只有焦点切换/移动/尺寸变化才 `occluded(true)`。
- 规矩：①重绘闩锁必须记录“从什么时候开始等”，超过一个刷新周期（本项目取 400ms）就判为丢失、清闩锁并强制整帧，不能靠重试次数耗尽来收场；②`draw()` 被调用就说明有人在要像素，damage 为空时也要 `present()` 整幅，别让"没有变化"变成"没有画面"；③原生 Win32 弹层（右键菜单、下拉、系统对话框）收起后要主动补一帧完整画面，这与内嵌 popup 的 `popup_repaint` 是两套来源；④验收必须同时断言"动作生效"和"新帧真的上屏"，只看消息计数或动作日志一定会漏。

## 平台原生菜单和“页面持续刷新”是互斥的 2026-11-25 [桌面版/Slint/Win32]
- 现象：右键菜单选项不再卡死之后，菜单**打开期间**页面仍然冻结（流式回复停住、动画不动），收起菜单立刻恢复。
- 判因：`TrackPopupMenu` 是 UI 线程上的嵌套模态循环，Slint/winit 的事件处理器在派发 `PointerPressed` 时已被借出，模态循环里的消息只能排队；Slint 定时器又由事件循环驱动，于是既不出帧也不跑定时器。补闩锁、补 paint 都只能让“菜单收起后”恢复，改不了“菜单开着”这段。
- 规矩：只要产品要求“菜单开着页面照常刷新”，就不能用平台菜单（Win32 `TrackPopupMenu`、macOS `NSMenu` 同理），必须用 UI 框架自绘弹层；`Window::set_native_popup_menus_enabled(false)` 这类开关要在启动时一次性关掉。自绘弹层还要补两条平台语义：失焦/最小化时关闭弹层（原生菜单本来就会关），以及弹层位置按窗口边界翻转，避免贴边被裁。
