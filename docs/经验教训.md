
## 问询面板/计划面板：先宽松恢复，再严格校验
- 面板类工具的参数错误里，“结构不对”和“语义不对”要分开处理：包装层（`raw`/`input`/`arguments`）、列表被写成字符串、裸数组、别名键、字符串布尔值都属于**编码抖动**，必须在工具边界修好并让调用成功；未知字段、未知状态、冲突项才报错。
- 报错必须指向真正的问题（哪个字段、解析器定位、收到什么），并附**唯一**规范示例。工具描述与 args 文档里直接写示例，比只在报错里教更省一轮。
- 只给一个选项（字符串或对象）是合法形态，别用 `unwrap_or(0)` 之类的计数把它算成“缺 options”。

## Slint ListView 的 content-height 只在被写入时重算：滚动跟随必须有外部节拍
- 列表末尾行变高（流式思考、命令输出）时，`ListView` 不会主动重算 `content-height`，`scrolled` 也不会自发触发。因此“内容变化 → 置一次 settle → 写一次 `content-y`”只能修正一帧；之后没有任何写入，跟随就永久停住。条目少（不需要滚动）时看起来仍正常，条目一多就变成“结束时一次性贴出”。
- 跟随要用运行期间的短节拍（如 50ms）持续贴底，值未变化时不写属性（无重绘成本）；一次性修正只能用于分页锚点这类离散事件。
- 判断“读者是否停在尾部”只能用**滚动偏移的方向**（偏移真的向上移动才算上滚），不能用 `visible − content − content-y` 的高度差：内容增长会让这个差值为负，被误判成上滚。
- 折叠区高度按整行（26px）量化，避免行内文本逐帧增长时整块高度抖动。
- 2026-11-12 [桌面版/忙碌判定] 前台的「活跃轮次」不是线程是否在跑的答案：它只属于本窗口正在泵的那一条流，切到别的线程再回来、重启应用、或运行时自己开启下一轮时它就空了，于是「运行中再发消息」的本地持有判定失效，消息又交给引擎 park 成「排队中」气泡——而且轮次越长（工作过程条目越多）越容易遇到，看起来像「条目多了就复发」。正确口径是把本地泵送、在途提交与 durable 快照（轮次状态里仍在生成/排队）合并判断，并由观察器在该线程真正静默时释放等待消息；前台泵收到 done 时若 durable 仍显示有后续轮次，不能抢先把 busy 清掉。- 同一处还有个连带坑：持有分支在此之前已经写过 submitting 栅栏，早退时没有复位，于是「提交中」永不复位、历史观察器因为 local_busy 恒真而整段停更，界面卡在「模型输出中」。凡是提前 return 的路径，都要检查它是否留下了别人等的栅栏或锁。

## 长嵌套参数：先怀疑自己漏字符，再怀疑传输
- 报错位置恒定、回显原文与自己的输入差一两个字符时，第一步是把两份文本逐字符比对，而不是改文案重试。实测 `write_file` 对 `{"`、`{'`、`{{"` 都原样保留，说明管线不吞字符，漏的是生成端。
- 同时要查修复器本身：补 `{"` 时若只补 `{"` 而留下裸键名（`question"`），后续扫描会把键名收尾引号当字符串开头，整段错位并把后面的容器字符一起吞掉——这会让"能修"的载荷变成"修坏"。
- 补出的容器必须同步入栈，否则对象内部的逗号会被当成数组里的新对象起点。

## 工作过程折叠区：`process_newer` 守卫会冻住正在流式的思考行

折叠区一旦加载过分页，`process_newer` 就为真。`sync_process_entry`（timeline.rs）和 `merge_reasoning_tail`（timeline_text.rs）都用 `if bar.process_newer { return; }` 挡住 live 数据覆盖分页——这条守卫本意正确，但它把**当前正在流式的那一行**也一起挡了，于是多步之后思考条目停在半句，只有开头几步看着是流式的。

判据要按“这是不是当前 reducer 的活行”区分，而不是按“有没有更新的页”或“这一刻是不是还在流式”一刀切：
- 同一 id 的活行在分页折叠中应当始终可更新：流式文本、结算（DONE）、随后到达的 token/耗时要走同一条通路。只放行 `STATUS_RUNNING` 仍会丢掉收尾那一次 patch，而 `process_newer` 为真时尾部刷新定时器不跑（tool_process.slint 要求 `!has-newer`），折叠里那条思考就会一直转圈并缺指标，直到用户往前翻页。
- 合并时保留页侧更完整的数据：传入两列为空则沿用旧值；已结算且旧文本更长则保留旧文本与摘要；已结算条目不允许被活行退回运行中。
- 条目不存在 → `process_newer` 时仍然不能插入，否则会在未加载的页之上重复或错序。
- 但“不存在”的条目里还有一类必须插入：**新一轮正在流式的思考行（新 id）**。分页只带已提交的步骤，正在写的思考永远不在页里；只放行“同 id 活行”时，读者看到的是开头几轮流式正常、之后突然整轮整轮地出现——形如“第 N 轮之后没有流式了”。放行条件是 `process_paged && !process_newer && 仍是运行中`（`timeline_text::live_tail_fits`）；已结算且页里没有的条目保持不插入。

回归测试：`timeline::tests::streaming_thought_survives_a_paged_fold_with_a_newer_page`；反向保护由 `chat_process::tests::delayed_process_page_keeps_the_live_thought_and_older_page_stays_put` 守住，改守卫时两个都要跑。

排查教训：视图侧跟随（ListView content-height、settle、50ms 节拍）都正常时，不要再在 Slint 里缝补——先用 Rust 测试直接驱动 `Timeline`，把“数据层有没有增长”和“视图有没有跟上”分开，能一步定位。

## 一次思考预算触顶，不要把后续每一轮都关思考

`EmptyOutputGuard` 有两个用途不同的状态，早期被合并成一个：
- `recovery_used`：本用户轮次只允许恢复一次，防空输出循环 —— 这个必须是全轮次。
- 关思考：只是那次恢复重发需要，不能传染。

原先 `config_override` 直接看 `recovery_used` 就返回 `reasoning_effort = none`，而 `orchestrator/execute.rs` 每轮 `call_llm` 都传它。结果一次思考预算触顶（传输层重发会置 `transport_recovery_used`，`observe` 再把 `recovery_used` 置真）之后，该用户轮次剩余所有轮次全部关思考。实测 31 轮会话里第 10 轮起连续 22 轮没有思考过程。

判据：`config_override` 回答的是“下一次请求要不要关思考”，不是“这一轮对话是不是在恢复状态”。用 `thinking_override` 单独表示前者；覆盖要一直有效到该轮真正返回（`observe` 时清除），不能在被读取时就清掉——`execute.rs` 的上下文溢出重试会重新发起同一轮请求，第一次尝试失败就把关思考丢了。

诊断手法：导出会话 jsonl，按 `model_round` 打表看 `reasoning` 长度、`thinking_disabled`、`transport_recovery_used`、`thinking_token_budget`。注意 `round_usage` 里的 input/reasoning tokens 是累计值，要算增量才能判断该轮到底有没有思考。

## 完成态是状态，不是新闻：别让三处默认 idle 各自否决
- 线程最后一轮的终态是持久事实，只有新一轮开始才能替换；「刚完成」的新鲜度只属于 toast、伙伴动画这类瞬时表现。把两者混在一起就会在「满屏绿勾」和「完成后全是空闲」之间反复翻转——每加一道过滤只是移动翻转点，没有解决状态所有权。这次同一个侧栏状态点被 Rust 状态投影（6 秒 TTL）、Slint 已读判定、目录/历史回读三处各写一次，任一晚到的读都能把刚写的终态改回 idle。
- 同一份状态只能有一个写入者。其余路径只读，或用 revision 栅栏阻止旧读覆盖新值；视图层不要自己重新推导「已看过/是否本窗口内」，那会把业务状态变成 UI 局部状态。
- 绝对 Unix 秒不能塞进 f32：当前量级步长 128 秒，同一线程 128 秒内连续两轮完成的「结算时间」会变成同一个值，所有基于它的 `<=` / `>=` 判定随机失效，表象正是「偶尔正常」。身份用单调递增轮次 id，时间用 f64 或相对窗口秒数，绝不用时间戳当身份。
- 回归锁不变量而不是时长：断言「通知过期后行仍保持终态」「transport idle 不覆盖 completed」「新轮次清除旧终态」，不要只测「6 秒后是否消失」。

## 命令里再套一层壳：按宿主意图分流，别让第二层文本解析发生

- 现象与代价：模型写 `powershell -Command "..."` 时外层 shell 会先解析一次，`$var`/`$_`/`$env:` 被提前展开、`\"` 被吞。最坏的不是报错而是静默算错：实测 `& { $x = 41; $x + 1 }` 输出 `1`。
- 判据按「宿主意图」而不是按写法：裸 `powershell`/`pwsh`（与当前宿主同一解释器）= 冗余包装，剥掉直接执行；完整路径或 `-Version` = 确实要系统 Windows PowerShell，保留子进程并把内层脚本改走 `-EncodedCommand`。两条路都只解析一次。
- 剥壳是改语义的操作，边界必须保守：`-File`、`-EncodedCommand`、位置参数、包装后还跟别的语句，一律原样放行。
- 还原转义只碰外层引入的那几种（`""`、`\"`、反引号 + 引号），内层语法（如反引号 `n`）原样保留；`\"` 是否算转义取决于后面还有没有收尾引号，否则 `"...\Windows\"` 的路径会被吃掉。
- 提示词里写「不要嵌套」只能缓解：习惯改不掉的模型永远存在，工具边界必须兜住。

## 改工具“提示”先分清模型到底看哪一层

内置工具的模型侧签名不是 `builtin_tool_specs_with_language` 里的原文：`prompt_surface::prompt_tool_spec` 会把带 `SurfaceRule` 的工具换成手写 `brief_zh/brief_en`，并整段删掉参数 `description`、按 `drop_fields` 删掉字段。于是改 `config/i18n.messages.json` 里 `tool.spec.*.args.*` 只能改管理端/设置页文案，模型一个字都看不到；被 `drop_fields` 掉的参数（例如图像生成的 `mask_path`、`strength`）模型连字段名都不知道，给了也不会填。
- 判断影响面：先看 `prompt_surface.rs` 的 `SURFACE_RULES` 有没有这个工具。有 → 改 brief + drop_fields；没有 → i18n 描述才直达模型。
- 行为约束放哪：`tools_protocol.txt` 的 `[[HAS_*]]` 块只在非 `function_call` 模式渲染，`function_call` 模式整块省略；要所有模式都生效的规则写进 `engineering.txt` 的条件块，并在 `build_system_prompt_skeleton` 的 `engineering_flags` 里加同名开关。
- 改完用 `tool_spec_prompt_budget_report` 复核模型侧字符预算：内置工具的精简投影总长有 20k 级上限，加字段/加文案会顶到阈值，需要显式调阈值而不是悄悄裁能力。

窗口内跨线程共享的本地状态（例如"等待发送"的本地持有条目）在投影到界面时必须按当前线程过滤：投影函数内部统一用当前 active session 过滤，而不是指望每个调用点自己筛。切换线程的第一步应是清掉上一线程的引擎行缓存并立即重绘条带，再异步补齐新线程的行；否则旧条目会一直挂在新线程的输入框上方（异步刷新回调重新发布时还会把它再带回来）。

"本地持有、延后发送"的消息必须有明确的移交时机：只在用户停留在该线程时成立。切走线程要么交给引擎队列，要么由后台观察完成事件，否则完成信号只会在回到该线程时才被看到。另外，本地持有不等于"已发送"，任何把它写进对话记录的分支（例如切回时重建等待气泡）都会让它看起来像一条正式消息，只应在输入区条带里出现。

## 覆盖层要跟“用户刚做的动作”对齐，别跟“后端还没回写的台账”对齐
- 现象：`输入其他答案` 这行的占位提示一直压在已输入内容上面。根因是真实的输入控件在编辑时**故意不回写模型**（保住光标与输入法），而占位提示/勾选态读的是模型里的旧值（还是空串），于是提示一直认为“这里没内容”。占位提示又是后声明的，天然盖在输入控件上方。
- 判据：凡是“用户正在改、但状态要延后发布”的控件，覆盖层与其状态标记一律读控件自身的属性（`input.text` / `input.preedit-text`），不读延迟台账；覆盖层还要声明在输入控件之前（z 序在下）。台账清零的外部动作（如“无偏好”会清空答案）需要单独同步：`changed` 只吃本组件的简单属性，先把它镜像成本地 property 再监听。
- 悬停读全文不要用 `Tooltip { text: … }`：该文本模式不折行，长句会拉出一条比窗口还宽的提示。长文本一律自绘卡片，固定最大宽度 + `wrap: word-wrap`，高度按各行 `preferred-height` 相加（而不是按 layout 的 preferred-height 猜）。
- Tooltip 内容拿不到外层作用域，循环里的行要先把行本身抽成组件，再让卡片读组件自己的 root 属性。
- **Tooltip 必须挂在真正接管指针的那个元素内部**（`TouchArea { ... Tooltip {...} }`，即 drag_row / host_hud 的写法）。挂在行的 Rectangle 根上、或做成某个 Text 的兄弟节点时，hover 一次都不会触发：`TooltipArea` 靠 `input_event_filter_before_children` 统计悬停，而事件只沿命中项那条路径下发，被上层 `TouchArea` 或 Text 挡住的兄弟节点收不到任何事件。判断"是否真的被截断"用 `elided-text.preferred-width > elided-text.width`（elide 的 Text 的 preferred-width 仍是完整文本宽），不要用字符数猜。

## 思考/正文“只剩整块贴出”先怀疑线程生命周期，不是折叠渲染
- 现象：长任务中途切到别的线程再回来，工作过程里的思考条目不再逐字流出，而是跟着工具行整块出现、内容已完整；不切线程时多轮都正常。
- 判因顺序：先看这条文本凭什么进界面。前台是 `pump_stream` 把 token 写进 reducer（`append_reasoning_item` → `flush_thinking`，33ms/帧）；切线程后只剩 durable 快照 `NativeThreadUpdate::Reset/Turns`，而 assistant 的 reasoning 是**每轮结束才 commit**，正在跑的那轮在快照里根本不存在。所以“切回来整块出现”= 流断了，不是渲染或分页守卫的问题。
- 根治形态：**每个线程各自持有一个 reducer**。切走时不 take 前台流、不 stop 泵、不 clear 模型，只把流和它的 reducer 挪到 `background` 继续 drain（不 drain 会让引擎的 bounded channel 反压，把整轮卡住）；切回时把该线程的 reducer 重新绑回窗口，思考行、折叠、正文块都还在，下一拍就续上。
- 关键约束：窗口级写入（`set_timeline`、`set_busy`、`set_stopping`、plan 面板、`stream_updates`）必须按“这个 reducer 是不是当前线程”门控，否则后台线程的帧会把读者拽进另一个线程；per-session 的（`set_session_status`）可以照写。
- 两个坑：①`Timeline::needs_publish()` 只返回一次 true，重绑同一 reducer 时必须显式 `set_timeline`；②有活轮的 reducer 绝不能被 LRU 淘汰，否则泵写的是孤儿模型，界面静默不更新。

## 批量操作别在循环里逐用户重建上下文
- 现象：管理端保存预设智能体（尤其是默认智能体）要等好几秒到十几秒，用户数越多越慢；点推送更慢，但用户并没有把配置推到全员之外的动作。
- 病因有两层：①前端保存成功后 `await loadSyncPreview()`，把「影响面统计」的全舰队 dry-run 挂在保存按钮的等待链上；②后端 `sync_*_across_users` 对每个用户重复 `build_user_tool_context`（配置克隆 + 技能注册表克隆 + 用户工具绑定 + 工具白名单 + 组织架构查询），默认智能体一条路径里同一个用户就要建 4 次上下文。
- 判据：但凡看到批量循环里出现 `build_user_tool_context` / `config_store.get()` / `list_org_units()` / `load_effective_*_record`，先算「每用户次数 × 用户数」，这类开销是线性的且全是同步 SQL/深拷贝，直接占住 tokio worker，旁边的保存、列表请求也会一起排队。
- 修法：整轮只取一次只读快照（`UserToolContextBase`），每个用户只算与他强相关的一次绑定与白名单；写操作（保存配置）不要把舰队级统计放进 await 链，改为后台刷新并在摘要区显示「统计中」，推送前再 await 正在跑的那次预览，避免并行双扫。
