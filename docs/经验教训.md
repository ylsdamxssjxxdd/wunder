
## 问询面板/计划面板：先宽松恢复，再严格校验
- 面板类工具的参数错误里，“结构不对”和“语义不对”要分开处理：包装层（`raw`/`input`/`arguments`）、列表被写成字符串、裸数组、别名键、字符串布尔值都属于**编码抖动**，必须在工具边界修好并让调用成功；未知字段、未知状态、冲突项才报错。
- 报错必须指向真正的问题（哪个字段、解析器定位、收到什么），并附**唯一**规范示例。工具描述与 args 文档里直接写示例，比只在报错里教更省一轮。
- 只给一个选项（字符串或对象）是合法形态，别用 `unwrap_or(0)` 之类的计数把它算成“缺 options”。

## Slint ListView 的 content-height 只在被写入时重算：滚动跟随必须有外部节拍
- 列表末尾行变高（流式思考、命令输出）时，`ListView` 不会主动重算 `content-height`，`scrolled` 也不会自发触发。因此“内容变化 → 置一次 settle → 写一次 `content-y`”只能修正一帧；之后没有任何写入，跟随就永久停住。条目少（不需要滚动）时看起来仍正常，条目一多就变成“结束时一次性贴出”。
- 跟随要用运行期间的短节拍（如 50ms）持续贴底，值未变化时不写属性（无重绘成本）；一次性修正只能用于分页锚点这类离散事件。
- 判断“读者是否停在尾部”只能用**滚动偏移的方向**（偏移真的向上移动才算上滚），不能用 `visible − content − content-y` 的高度差：内容增长会让这个差值为负，被误判成上滚。
- 折叠区高度按整行（26px）量化，避免行内文本逐帧增长时整块高度抖动。
- 2026-11-12 [桌面版/忙碌判定] 前台的「活跃轮次」不是线程是否在跑的答案：它只属于本窗口正在泵的那一条流，切到别的线程再回来、重启应用、或运行时自己开启下一轮时它就空了，于是「运行中再发消息」的本地持有判定失效，消息又交给引擎 park 成「排队中」气泡——而且轮次越长（工作过程条目越多）越容易遇到，看起来像「条目多了就复发」。正确口径是把本地泵送、在途提交与 durable 快照（轮次状态里仍在生成/排队）合并判断，并由观察器在该线程真正静默时释放等待消息；前台泵收到 done 时若 durable 仍显示有后续轮次，不能抢先把 busy 清掉。- 同一处还有个连带坑：持有分支在此之前已经写过 submitting 栅栏，早退时没有复位，于是「提交中」永不复位、历史观察器因为 local_busy 恒真而整段停更，界面卡在「模型输出中」。凡是提前 return 的路径，都要检查它是否留下了别人等的栅栏或锁。

## 长嵌套参数：先怀疑自己漏字符，再怀疑传输
- 报错位置恒定、回显原文与自己的输入差一两个字符时，第一步是把两份文本逐字符比对，而不是改文案重试。实测 `write_file` 对 `{"`、`{'`、`{{"` 都原样保留，说明管线不吞字符，漏的是生成端。
- 同时要查修复器本身：补 `{"` 时若只补 `{"` 而留下裸键名（`question"`），后续扫描会把键名收尾引号当字符串开头，整段错位并把后面的容器字符一起吞掉——这会让"能修"的载荷变成"修坏"。
- 补出的容器必须同步入栈，否则对象内部的逗号会被当成数组里的新对象起点。

## 工作过程折叠区：`process_newer` 守卫会冻住正在流式的思考行

折叠区一旦加载过分页，`process_newer` 就为真。`sync_process_entry`（timeline.rs）和 `merge_reasoning_tail`（timeline_text.rs）都用 `if bar.process_newer { return; }` 挡住 live 数据覆盖分页——这条守卫本意正确，但它把**当前正在流式的那一行**也一起挡了，于是多步之后思考条目停在半句，只有开头几步看着是流式的。

判据要按“条目是否已在分页里”区分，而不是按“有没有更新的页”一刀切：
- 条目已存在（同一 id）且 `status_kind == STATUS_RUNNING` → 必须继续更新，它是引擎正在写的最新一步，不属于任何页。
- 条目不存在 → `process_newer` 时仍然不能插入，否则会在未加载的页之上重复或错序。

回归测试：`timeline::tests::streaming_thought_survives_a_paged_fold_with_a_newer_page`；反向保护由 `chat_process::tests::delayed_process_page_keeps_the_live_thought_and_older_page_stays_put` 守住，改守卫时两个都要跑。

排查教训：视图侧跟随（ListView content-height、settle、50ms 节拍）都正常时，不要再在 Slint 里缝补——先用 Rust 测试直接驱动 `Timeline`，把“数据层有没有增长”和“视图有没有跟上”分开，能一步定位。

## 一次思考预算触顶，不要把后续每一轮都关思考

`EmptyOutputGuard` 有两个用途不同的状态，早期被合并成一个：
- `recovery_used`：本用户轮次只允许恢复一次，防空输出循环 —— 这个必须是全轮次。
- 关思考：只是那次恢复重发需要，不能传染。

原先 `config_override` 直接看 `recovery_used` 就返回 `reasoning_effort = none`，而 `orchestrator/execute.rs` 每轮 `call_llm` 都传它。结果一次思考预算触顶（传输层重发会置 `transport_recovery_used`，`observe` 再把 `recovery_used` 置真）之后，该用户轮次剩余所有轮次全部关思考。实测 31 轮会话里第 10 轮起连续 22 轮没有思考过程。

判据：`config_override` 回答的是“下一次请求要不要关思考”，不是“这一轮对话是不是在恢复状态”。改动后用 `thinking_override` 单独表示前者，传输层重发在 `observe` 里清掉它。

诊断手法：导出会话 jsonl，按 `model_round` 打表看 `reasoning` 长度、`thinking_disabled`、`transport_recovery_used`、`thinking_token_budget`。注意 `round_usage` 里的 input/reasoning tokens 是累计值，要算增量才能判断该轮到底有没有思考。
