
## 下标式历史栈：删中间一格必须连带压实编号与游标 2026-11-17 [引擎/工具]
- 现象：快照 @1/@2 里 @2 损坏被删后，cursor 还停在 2，再撤销直接报「已到最早」，而 @1 明明还在——更早的历史被永久跳过。
- 判因：游标存的是「第几态」这个下标，快照却是按编号落盘的；删一格不压实，下标与文件编号就错位，`cursor-1` 找不到东西时被当成栈底。
- 规矩：任何「删某一版」的路径（损坏回收、过期清扫、手工清理）都必须 ① 把更大的编号整体前移 ② cursor ≥ 被删编号时减一；读取侧还要有兜底——游标对应的文件不在时退到「编号不超过游标的最近一版」，绝不能直接判定到底。回收时同一文件的多格删除按编号从大到小处理，先删大号才不会打乱待删的小号。

## 写用户文件不能只保证原子性，还要保证属性不变 2026-11-17 [引擎/工具]
- 现象：重写一个 755 的 shell 脚本后变成 644，直接 Permission denied；硬链接的另一条路径停在旧内容；40 万行的文件改了却报「0 行变更」。
- 判因：`临时文件 + rename` 只保住「内容不残缺」，新 inode 的权限位来自 umask、链接数重算为 1；而有界性守卫放弃 diff 时又默认填 0，把「没算」写成了「没改」。
- 规矩：替换前 `set_permissions` 复制原权限（新建文件才用 umask）；`nlink > 1` 时改为就地写保留 inode；符号链接要先 `canonicalize` 写穿而不是替换链接；任何「没算出来」的统计量一律给 null 并配 `diff_unavailable`，绝不填 0。

## 限流的等待上限要按真实耗时定，否则并行场景会大面积降级 2026-11-17 [引擎/工具]
- 现象：给语法校验子进程加全局闸门，等待上限先取 200 ms，全量测试里 4 个用例立刻变红——不是锁坏了，是排队深度超过 10 个请求后全部拿到 `skipped (checker busy)`。
- 判因：单次校验约 20 ms，200 ms 只够排 10 个；测试并行度和真实写入并发都可能超过这个数。上限设小了，「限流」就变成了「随机丢掉校验结果」。
- 规矩：等待上限 ≥ 典型耗时 × 预期并发（此处 1 s ≈ 50 个请求），只有解释器卡死这类异常才走到降级；降级文案要和开关关闭、解释器缺失一样落进 `syntax` 字段，绝不阻断写入。

## 小尺寸图标不要靠降采样，按目标像素密度重制网格 2026-11-18 [桌面版/云端版]
- 现象：云端版问候语左侧的 eva01 徽标发虚。槽位只有 40px，挂的是 80px 位图，而源图 `images/eva01-head.png` 是 512px 级细密像素画（几乎每个像素都是独立 cell，带半透明），512→40 等于压缩 12:1，LANCZOS 降采样把整张图熔成一团灰边。
- 判因：素材尺寸不是关键，关键是「一个设备像素对应一格网格」。40px 槽位在 DPR1 只有 40 格，喂再高分辨率的平滑缩略图也只能糊；DPR2 才有 80 格。
- 规矩：先用源图在目标格数上重采样（LANCZOS）成网格图，再 NEAREST 放大到交付尺寸，前端配 `image-rendering: pixelated`（Slint 1.18 的 `Image` 同样支持该属性）。web 用 `srcset` 给两档不同格数的图（1x 40 格 / 2x 80 格），桌面单张 4x。统一由 `scripts/generate_eva01_mark.py` 产出。
- 附带：渐隐边缘要先把 alpha 低于阈值（24）的像素清零、只保留最大连通域，否则 pixelated 会把半透明残留放大成孤立杂点。

## 工作台内部快捷键要走窗口层，别抢系统的 F1/F2 2026-11-18 [桌面版]
- Slint 的 `key-pressed`/`capture-key-pressed` 只存在于 `FocusScope`，要覆盖输入区、时间线、侧栏就得给整个界面套一层 FocusScope；窗口根不是 FocusScope，`key-pressed` 写在根上收不到事件。想做到「不管焦点在哪个控件都生效」，就在窗口层拦：Windows 子类化主 HWND 的消息过程（32 位只有 `SetWindowLongW`，`SetWindowLongPtrW` 仅 64 位有），X11 用第二条 Display 连接 `XSelectInput` 监听本窗口按键（事件掩码按客户端独立，Slint 照常收事件，不是抢占）。

## 全局拖拽状态必须分域，共用组件要认「这是哪个列表」 2026-11-14 [桌面版]
- 现象：设置页模型列表复用侧栏的 `DragRow` 后，拖模型行时侧栏浮标、插入缝与落点解析一起动，像在拖线程；同时拖一格会跳好几条。

## Slint 里没有 contains，字符串赋给属性后还会被 move 2026-11-14 [桌面版]
- `[string]` 只能用 `index-of`（不存在返回 -1），写 `list.contains(x)` 直接编译失败。判断“当前值是否在本类型的预设里”要写 `ModelPresets.for-type(kind).index-of(root.value) >= 0`。
- `let x = ...; prop = x;` 之后局部已被移动，再拿它比较会报 `borrow of moved value`；要么把赋值挪到后面，要么回读属性（注释里写清“read the property back”），不要为此另存一份副本。
- 预设表这类纯逻辑放在 `export global` 的 `public pure function` 里，Rust 侧才会生成 `invoke_xxx`，单元测试可以直接断言表格本身（见 `native_pages::tests::provider_presets_follow_the_model_type`），不必靠截图猜下拉里有什么。

## 折叠行右侧指标要靠 payload 字段，不要指望后来帧补 2026-11-14 [前端]
- 现象：工作过程里「上下文压缩」条目右侧只有模型轮次，压缩后的上下文占用和耗时都是空；其他工具行正常。
- 判因：工具行的字数/耗时来自 `NativeWorkflowEntry::from_payload`，它只认 `request_context_tokens`/`request_usage` 与 `duration_ms`；压缩事件的占用是 `context_tokens_after`（重建后），也没有耗时字段，所以两项都取空。且 `Timeline::upsert_tool` 每次都用新帧覆盖 `tokens/duration`，同一 id 的后续帧（如溢出恢复事件）会把已显示的指标清空。
- 修法：压缩类条目单独取「重建后」字段族（`context_tokens_after` 等）与 `duration_ms`；运行时在发起压缩时记一次 `Instant` 并写入 `duration_ms`；折叠行指标改为「新帧非空才覆盖」。
- 附带：completed 时间线条目不可改写（`commit_item` 先写者胜），同一 `compaction_id` 的第二个事件持久化会被丢弃——所以耗时必须在真正完成压缩的那条 payload 里。

## 换远端地址不等于换 pull 的目标 2026-11-13 [工程]
- 现象：`git remote set-url origin https://github.com/<org>/<repo>.git` 之后 `git pull` 回「已经是最新的」，但本地与 GitHub 明显不一致。
- 判因：`git pull` 走的是分支的 upstream（`git branch -vv` 显示 `[gitea/main]` 一类），与 `origin` 的 url 无关；只要 `branch.<name>.remote` 还指着另一个 remote（本地裸仓库），pull 就永远「已是最新」。`set-url` 只改地址，upstream 要单独 `git branch --set-upstream-to=origin/main main`。
- 落后还是分叉只需三步：`git fetch <remote>` → `git rev-list --left-right --count main...origin/main` → `git log --oneline <remote>..main`。别把 pull 的「Already up to date」当结论。
- 附带坑：多形态共用的便携 git 若把 exec-path 编译成构建机路径，`git-remote-https` 一类 helper 全部找不到，报 `git: 'remote-https' is not a git command`，而 `status/log/commit` 照常工作——先看 `echo $GIT_EXEC_PATH` 与 `ls $(git --exec-path)`，别去查网络和凭据。
- 日志类文件（`docs/功能迭代.md`、`docs/经验教训.md`）的冲突几乎都是两侧追加：两侧内容都保留，合并后相对两侧都应只有新增行，且真实 BOM（`EF BB BF`）不能被改写。

## 问询面板/计划面板：先宽松恢复，再严格校验
- 面板类工具的参数错误里，“结构不对”和“语义不对”要分开处理：包装层（`raw`/`input`/`arguments`）、列表被写成字符串、裸数组、别名键、字符串布尔值都属于**编码抖动**，必须在工具边界修好并让调用成功；未知字段、未知状态、冲突项才报错。
- 报错必须指向真正的问题（哪个字段、解析器定位、收到什么），并附**唯一**规范示例。工具描述与 args 文档里直接写示例，比只在报错里教更省一轮。
- 只给一个选项（字符串或对象）是合法形态，别用 `unwrap_or(0)` 之类的计数把它算成“缺 options”。

## Slint ListView 的 content-height 只在被写入时重算：滚动跟随必须有外部节拍
- 列表末尾行变高（流式思考、命令输出）时，`ListView` 不会主动重算 `content-height`，`scrolled` 也不会自发触发。因此“内容变化 → 置一次 settle → 写一次 `content-y`”只能修正一帧；之后没有任何写入，跟随就永久停住。条目少（不需要滚动）时看起来仍正常，条目一多就变成“结束时一次性贴出”。
- 跟随要用运行期间的短节拍（如 50ms）持续贴底，值未变化时不写属性（无重绘成本）；一次性修正只能用于分页锚点这类离散事件。
- 判断“读者是否停在尾部”只能用**滚动偏移的方向**（偏移真的向上移动才算上滚），不能用 `visible − content − content-y` 的高度差：内容增长会让这个差值为负，被误判成上滚。
- 折叠区高度按整行（26px）量化，避免行内文本逐帧增长时整块高度抖动。
- 2026-11-12 [桌面版/忙碌判定] 前台的「活跃轮次」不是线程是否在跑的答案：它只属于本窗口正在泵的那一条流，切到别的线程再回来、重启应用、或运行时自己开启下一轮时它就空了，于是「运行中再发消息」的本地持有判定失效，消息又交给引擎 park 成「排队中」气泡——而且轮次越长（工作过程条目越多）越容易遇到，看起来像「条目多了就复发」。正确口径是把本地泵送、在途提交与 durable 快照（轮次状态里仍在生成/排队）合并判断，并由观察器在该线程真正静默时释放等待消息；前台泵收到 done 时若 durable 仍显示有后续轮次，不能抢先把 busy 清掉。- 同一处还有个连带坑：持有分支在此之前已经写过 submitting 栅栏，早退时没有复位，于是「提交中」永不复位、历史观察器因为 local_busy 恒真而整段停更，界面卡在「模型输出中」。凡是提前 return 的路径，都要检查它是否留下了别人等的栅栏或锁。

## 工作过程折叠区：`process_newer` 守卫会冻住正在流式的思考行

折叠区一旦加载过分页，`process_newer` 就为真。`sync_process_entry`（timeline.rs）和 `merge_reasoning_tail`（timeline_text.rs）都用 `if bar.process_newer { return; }` 挡住 live 数据覆盖分页——这条守卫本意正确，但它把**当前正在流式的那一行**也一起挡了，于是多步之后思考条目停在半句，只有开头几步看着是流式的。

判据要按“这是不是当前 reducer 的活行”区分，而不是按“有没有更新的页”或“这一刻是不是还在流式”一刀切：
- 同一 id 的活行在分页折叠中应当始终可更新：流式文本、结算（DONE）、随后到达的 token/耗时要走同一条通路。只放行 `STATUS_RUNNING` 仍会丢掉收尾那一次 patch，而 `process_newer` 为真时尾部刷新定时器不跑（tool_process.slint 要求 `!has-newer`），折叠里那条思考就会一直转圈并缺指标，直到用户往前翻页。
- 合并时保留页侧更完整的数据：传入两列为空则沿用旧值；已结算且旧文本更长则保留旧文本与摘要；已结算条目不允许被活行退回运行中。
- 条目不存在 → `process_newer` 时仍然不能插入，否则会在未加载的页之上重复或错序。
- 但“不存在”的条目里还有一类必须插入：**新一轮正在流式的思考行（新 id）**。分页只带已提交的步骤，正在写的思考永远不在页里；只放行“同 id 活行”时，读者看到的是开头几轮流式正常、之后突然整轮整轮地出现——形如“第 N 轮之后没有流式了”。放行条件是 `process_paged && !process_newer && 仍是运行中`（`timeline_text::live_tail_fits`）；已结算且页里没有的条目保持不插入。

回归测试：`timeline::tests::streaming_thought_survives_a_paged_fold_with_a_newer_page`；反向保护由 `chat_process::tests::delayed_process_page_keeps_the_live_thought_and_older_page_stays_put` 守住，改守卫时两个都要跑。

排查教训：视图侧跟随（ListView content-height、settle、50ms 节拍）都正常时，不要再在 Slint 里缝补——先用 Rust 测试直接驱动 `Timeline`，把“数据层有没有增长”和“视图有没有跟上”分开，能一步定位。

## 一次思考预算触顶，不要把后续每一轮都关思考

`EmptyOutputGuard` 有两个用途不同的状态，早期被合并成一个：
- `recovery_used`：本用户轮次只允许恢复一次，防空输出循环 —— 这个必须是全轮次。
- 关思考：只是那次恢复重发需要，不能传染。

原先 `config_override` 直接看 `recovery_used` 就返回 `reasoning_effort = none`，而 `orchestrator/execute.rs` 每轮 `call_llm` 都传它。结果一次思考预算触顶（传输层重发会置 `transport_recovery_used`，`observe` 再把 `recovery_used` 置真）之后，该用户轮次剩余所有轮次全部关思考。实测 31 轮会话里第 10 轮起连续 22 轮没有思考过程。

判据：`config_override` 回答的是“下一次请求要不要关思考”，不是“这一轮对话是不是在恢复状态”。用 `thinking_override` 单独表示前者；覆盖要一直有效到该轮真正返回（`observe` 时清除），不能在被读取时就清掉——`execute.rs` 的上下文溢出重试会重新发起同一轮请求，第一次尝试失败就把关思考丢了。

诊断手法：导出会话 jsonl，按 `model_round` 打表看 `reasoning` 长度、`thinking_disabled`、`transport_recovery_used`、`thinking_token_budget`。注意 `round_usage` 里的 input/reasoning tokens 是累计值，要算增量才能判断该轮到底有没有思考。

## 完成态是状态，不是新闻：别让三处默认 idle 各自否决
- 线程最后一轮的终态是持久事实，只有新一轮开始才能替换；「刚完成」的新鲜度只属于 toast、伙伴动画这类瞬时表现。把两者混在一起就会在「满屏绿勾」和「完成后全是空闲」之间反复翻转——每加一道过滤只是移动翻转点，没有解决状态所有权。这次同一个侧栏状态点被 Rust 状态投影（6 秒 TTL）、Slint 已读判定、目录/历史回读三处各写一次，任一晚到的读都能把刚写的终态改回 idle。
- 同一份状态只能有一个写入者。其余路径只读，或用 revision 栅栏阻止旧读覆盖新值；视图层不要自己重新推导「已看过/是否本窗口内」，那会把业务状态变成 UI 局部状态。
- 绝对 Unix 秒不能塞进 f32：当前量级步长 128 秒，同一线程 128 秒内连续两轮完成的「结算时间」会变成同一个值，所有基于它的 `<=` / `>=` 判定随机失效，表象正是「偶尔正常」。身份用单调递增轮次 id，时间用 f64 或相对窗口秒数，绝不用时间戳当身份。
- 回归锁不变量而不是时长：断言「通知过期后行仍保持终态」「transport idle 不覆盖 completed」「新轮次清除旧终态」，不要只测「6 秒后是否消失」。

## 命令里再套一层壳：按宿主意图分流，别让第二层文本解析发生

- 现象与代价：模型写 `powershell -Command "..."` 时外层 shell 会先解析一次，`$var`/`$_`/`$env:` 被提前展开、`\"` 被吞。最坏的不是报错而是静默算错：实测 `& { $x = 41; $x + 1 }` 输出 `1`。
- 判据按「宿主意图」而不是按写法：裸 `powershell`/`pwsh`（与当前宿主同一解释器）= 冗余包装，剥掉直接执行；完整路径或 `-Version` = 确实要系统 Windows PowerShell，保留子进程并把内层脚本改走 `-EncodedCommand`。两条路都只解析一次。
- 剥壳是改语义的操作，边界必须保守：`-File`、`-EncodedCommand`、位置参数、包装后还跟别的语句，一律原样放行。
- 还原转义只碰外层引入的那几种（`""`、`\"`、反引号 + 引号），内层语法（如反引号 `n`）原样保留；`\"` 是否算转义取决于后面还有没有收尾引号，否则 `"...\Windows\"` 的路径会被吃掉。
- 提示词里写「不要嵌套」只能缓解：习惯改不掉的模型永远存在，工具边界必须兜住。

## 改工具“提示”先分清模型到底看哪一层

内置工具的模型侧签名不是 `builtin_tool_specs_with_language` 里的原文：`prompt_surface::prompt_tool_spec` 会把带 `SurfaceRule` 的工具换成手写 `brief_zh/brief_en`，并整段删掉参数 `description`、按 `drop_fields` 删掉字段。于是改 `config/i18n.messages.json` 里 `tool.spec.*.args.*` 只能改管理端/设置页文案，模型一个字都看不到；被 `drop_fields` 掉的参数（例如图像生成的 `mask_path`、`strength`）模型连字段名都不知道，给了也不会填。
- 判断影响面：先看 `prompt_surface.rs` 的 `SURFACE_RULES` 有没有这个工具。有 → 改 brief + drop_fields；没有 → i18n 描述才直达模型。
- 行为约束放哪：`tools_protocol.txt` 的 `[[HAS_*]]` 块只在非 `function_call` 模式渲染，`function_call` 模式整块省略；要所有模式都生效的规则写进 `engineering.txt` 的条件块，并在 `build_system_prompt_skeleton` 的 `engineering_flags` 里加同名开关。
- 改完用 `tool_spec_prompt_budget_report` 复核模型侧字符预算：内置工具的精简投影总长有 20k 级上限，加字段/加文案会顶到阈值，需要显式调阈值而不是悄悄裁能力。

窗口内跨线程共享的本地状态（例如"等待发送"的本地持有条目）在投影到界面时必须按当前线程过滤：投影函数内部统一用当前 active session 过滤，而不是指望每个调用点自己筛。切换线程的第一步应是清掉上一线程的引擎行缓存并立即重绘条带，再异步补齐新线程的行；否则旧条目会一直挂在新线程的输入框上方（异步刷新回调重新发布时还会把它再带回来）。

"本地持有、延后发送"的消息必须有明确的移交时机：只在用户停留在该线程时成立。切走线程要么交给引擎队列，要么由后台观察完成事件，否则完成信号只会在回到该线程时才被看到。另外，本地持有不等于"已发送"，任何把它写进对话记录的分支（例如切回时重建等待气泡）都会让它看起来像一条正式消息，只应在输入区条带里出现。

## 覆盖层要跟“用户刚做的动作”对齐，别跟“后端还没回写的台账”对齐
- 现象：`输入其他答案` 这行的占位提示一直压在已输入内容上面。根因是真实的输入控件在编辑时**故意不回写模型**（保住光标与输入法），而占位提示/勾选态读的是模型里的旧值（还是空串），于是提示一直认为“这里没内容”。占位提示又是后声明的，天然盖在输入控件上方。
- 判据：凡是“用户正在改、但状态要延后发布”的控件，覆盖层与其状态标记一律读控件自身的属性（`input.text` / `input.preedit-text`），不读延迟台账；覆盖层还要声明在输入控件之前（z 序在下）。台账清零的外部动作（如“无偏好”会清空答案）需要单独同步：`changed` 只吃本组件的简单属性，先把它镜像成本地 property 再监听。
- 悬停读全文不要用 `Tooltip { text: … }`：该文本模式不折行，长句会拉出一条比窗口还宽的提示。长文本一律自绘卡片，固定最大宽度 + `wrap: word-wrap`，高度按各行 `preferred-height` 相加（而不是按 layout 的 preferred-height 猜）。
- Tooltip 内容拿不到外层作用域，循环里的行要先把行本身抽成组件，再让卡片读组件自己的 root 属性。
- **Tooltip 必须挂在真正接管指针的那个元素内部**（`TouchArea { ... Tooltip {...} }`，即 drag_row / host_hud 的写法）。挂在行的 Rectangle 根上、或做成某个 Text 的兄弟节点时，hover 一次都不会触发：`TooltipArea` 靠 `input_event_filter_before_children` 统计悬停，而事件只沿命中项那条路径下发，被上层 `TouchArea` 或 Text 挡住的兄弟节点收不到任何事件。判断"是否真的被截断"用 `elided-text.preferred-width > elided-text.width`（elide 的 Text 的 preferred-width 仍是完整文本宽），不要用字符数猜。

## 思考/正文“只剩整块贴出”先怀疑线程生命周期，不是折叠渲染
- 现象：长任务中途切到别的线程再回来，工作过程里的思考条目不再逐字流出，而是跟着工具行整块出现、内容已完整；不切线程时多轮都正常。
- 判因顺序：先看这条文本凭什么进界面。前台是 `pump_stream` 把 token 写进 reducer（`append_reasoning_item` → `flush_thinking`，33ms/帧）；切线程后只剩 durable 快照 `NativeThreadUpdate::Reset/Turns`，而 assistant 的 reasoning 是**每轮结束才 commit**，正在跑的那轮在快照里根本不存在。所以“切回来整块出现”= 流断了，不是渲染或分页守卫的问题。
- 根治形态：**每个线程各自持有一个 reducer**。切走时不 take 前台流、不 stop 泵、不 clear 模型，只把流和它的 reducer 挪到 `background` 继续 drain（不 drain 会让引擎的 bounded channel 反压，把整轮卡住）；切回时把该线程的 reducer 重新绑回窗口，思考行、折叠、正文块都还在，下一拍就续上。
- 关键约束：窗口级写入（`set_timeline`、`set_busy`、`set_stopping`、plan 面板、`stream_updates`）必须按“这个 reducer 是不是当前线程”门控，否则后台线程的帧会把读者拽进另一个线程；per-session 的（`set_session_status`）可以照写。
- 两个坑：①`Timeline::needs_publish()` 只返回一次 true，重绑同一 reducer 时必须显式 `set_timeline`；②有活轮的 reducer 绝不能被 LRU 淘汰，否则泵写的是孤儿模型，界面静默不更新。

## 批量操作别在循环里逐用户重建上下文
- 现象：管理端保存预设智能体（尤其是默认智能体）要等好几秒到十几秒，用户数越多越慢；点推送更慢，但用户并没有把配置推到全员之外的动作。
- 病因有两层：①前端保存成功后 `await loadSyncPreview()`，把「影响面统计」的全舰队 dry-run 挂在保存按钮的等待链上；②后端 `sync_*_across_users` 对每个用户重复 `build_user_tool_context`（配置克隆 + 技能注册表克隆 + 用户工具绑定 + 工具白名单 + 组织架构查询），默认智能体一条路径里同一个用户就要建 4 次上下文。
- 判据：但凡看到批量循环里出现 `build_user_tool_context` / `config_store.get()` / `list_org_units()` / `load_effective_*_record`，先算「每用户次数 × 用户数」，这类开销是线性的且全是同步 SQL/深拷贝，直接占住 tokio worker，旁边的保存、列表请求也会一起排队。
- 修法：整轮只取一次只读快照（`UserToolContextBase`），每个用户只算与他强相关的一次绑定与白名单；写操作（保存配置）不要把舰队级统计放进 await 链，改为后台刷新并在摘要区显示「统计中」，推送前再 await 正在跑的那次预览，避免并行双扫。

## 桌面版终端里跑测试会被注入 WUNDER_I18N_MESSAGES_PATH，i18n 断言假失败
- 现象：在 wunder 桌面版的 shell 工具里 `cargo test -p wunder-runtime`，工具描述类断言（如“图像生成 description 应包含『优先使用本工具』”）失败，但文案在仓库 `config/i18n.messages.json` 里明明是对的。
- 病因：桌面版进程给子进程导出了 `WUNDER_I18N_MESSAGES_PATH=/home/<user>/.wunder/config/i18n.messages.json`，那是安装目录里的旧副本；`wunder-core` 的 i18n 会优先读这个文件，只有缺失 key 才回落到 `include_str!` 的内置文案，所以测试读到的是过期文案。
- 判据：看到文案类断言失败时先 `env | grep WUNDER_I18N_MESSAGES_PATH`，再和仓库里的 key 对照；两条通道不一致就是环境问题，不是代码问题。
- 做法：验证 i18n 相关测试用 `env -u WUNDER_I18N_MESSAGES_PATH cargo test ...`；实机要让新文案生效需重启桌面版（启动时会重写安装目录的 i18n 资产），不要手改 `~/.wunder` 下的副本。

## 安卓版没有独立 i18n.slint：改文案只改桌面版这一份
- 现象：想在安卓版改一条设置提示，`crates/wunder-android/ui/` 里找不到 `i18n.slint`，只能看到 `settings.slint` 里引用 `I18n.st_param_*`。

- 做法：三端文案一致性只查两处——`crates/wunder-desktop/frontend/ui/i18n.slint`（Slint 端）与 `config/i18n.messages.json`（引擎/管理端工具说明）；`crates/wunder-desktop/frontend/ui-i18n.json` 是另一条生成链，别当唯一来源。
## 终端交互里"慢"要分 I/O 冷启动、每帧重算和每字符重建三类 2026-11-13 [命令行]
- 现象：命令行滑选后右击复制、以及粘贴都要等一下。三个独立病因叠在一起：①每次剪贴板读写都冷启动外部脚本宿主，且读文本时还顺带加载位图程序集探测图片；②滑选时每个 drag 记录强制一帧，而每帧把整个可见窗口深拷贝两次并逐行做 tab 投影；③不支持括号粘贴的终端会把剪贴板内容回显为逐字符按键，吞回显时每吞一个字符就 `remaining.collect()` 重建剩余整段，长粘贴退化成二次复杂度，此外粘贴文本还会按空格切成词、逐词做 URL 解析与磁盘 `is_file`。
- 判据：先看"这件事每次操作要起几个进程/几次全量扫描"，再看"每个输入事件是否无条件触发全帧"，最后在长文本链路里找"每处理一个字符就重建一次容器"。三者互不掩盖，只修一个仍会觉得卡。
- 修法：本地剪贴板文本走原生 API 的 Unicode 文本格式（一次 OpenClipboard 会话同时判断文本与图片格式），外部进程只留给图片转换并作为原生调用被拒绝时的降级；渲染缓存同时保存逻辑行与投影行，帧只 clone 一次投影行，且只有选区端点真的变化时才请求重绘；回显吞字符改用字节游标，文本归一化无 `\r`/NUL 时零分配，路径识别先做长文本与路径语法快速否定。
- 验证坑：自动化/隔离会话里 `OpenClipboard` 会返回 ERROR_ACCESS_DENIED(5)，外部脚本宿主同样失败，这只能说明该会话没有交互式 window station，不能据此判定原生实现有问题；这类剪贴板改动必须在真实交互终端里做写入—读回—恢复的往返验收。

## 拉取前先单独处理 `docs/功能迭代.md` 2026-11-13 [命令行][工程]
- 现象：`git pull` 直接中止在 `Your local changes to the following files would be overwritten by merge: docs/功能迭代.md`，即使上游只动了这一个文件的两条记录。这份文件几乎永远是脏的——日志脚本每次都往里追加。
- 判据：不要整仓 stash。工作区通常还有大量未提交改动，`stash pop` 回来既要处理冲突又容易把别人的改动卷进去；只针对这一份文件做备份—还原—回填。
- 修法：`cp` 备份到 `.git/` 下 → `git checkout --` 该文件 → `git pull --ff-only` → 用 diff 定位每条本地新增行所属的 `### 区块`，在新区块顶部按原顺序插回。校验标准是 diff 只剩新增行、无删除行（出现删除行说明首行或换行被改写）。
- 编码坑：脚本以 `utf-8-sig` 写入，回填时必须保留真实 BOM（字节 `EF BB BF`）。把 BOM 当普通字符读写会写成 `ï»¿`（`C3 AF C2 BB C2 BF`），首行从此每次 diff 都脏。

## 发布物缺能力先查构建 manifest，别先查运行时开关 2026-11-14 [桌面版][命令行][工程]
- 现象：桌面版默认没有「网页抓取」工具、只剩「浏览器」，但配置里 `tools.web.fetch.enabled=true`、内置工具清单也列了它、`crates/wunder-desktop/Cargo.toml` 的 `default = ["sqlite-storage", "web-fetch"]` 看着也没问题。
- 判据：桌面版所有发布构建都从 `crates/wunder-desktop/frontend/Cargo.toml`（wunder-frontend-slint）出包，它对 `wunder-desktop` 显式写 `default-features = false` 并只列白名单 features，白名单里没有 `web-fetch` → `#[cfg(feature = "web-fetch")]` 整段落空，`web_fetch_enabled()` 落到 disabled 分支恒 false，本地模式再据此把它从 allowed 集合滤掉。快速判据：`strings <发布二进制> | grep 'web_fetch_tool_impl'` 为空、同时残留 "rebuild with --features web-fetch" 提示，就是没编进去。
- 修法：只要某个 manifest 用了 `default-features = false`，能力的启用必须逐条写进它的 features 白名单，crate 自己的 default features 再全也不作数；改完用 `cargo tree -p <包> -e features -i <该能力独占依赖>` 确认接线（无输出即没接上），再补一条"默认工具面含该能力"的回归测试。

## 上下文“凭空缩水”先看本轮的请求形态，再怀疑丢历史 2026-11-14 [后端][引擎]
- 现象：轨迹里出现“请求上下文从 77501 降到 69292 tokens，本轮未记录本地压缩”，用户第一反应是历史被截断或图片被省略。
- 判据：先对齐同一轮的 `transport_recovery_used`、`account_credits_consumed` / `model_request_count` 增量。本轮若 +2 请求且 `transport_recovery_used=true`，就是“思考预算触顶→断流→关思考重发”：重发提示词不再计入此前的思考文本，数字自然下跳，本地历史反而更长（用消息字符数/本地估算复核即可）。全程没有图片工具时，“内联图占位”一类解释直接排除。
- 修法：`context_shrink` 事件必须自带 `likely_cause`（thinking_budget_resend / inline_images_omitted / provider_accounting）与 `local_estimate_tokens`，把“猜”留给代码；提示文案只描述确定的事实。
- 关联坑：一次 `写入文件` 带 3.5 万字符正文 ≈ 1.7 万 tokens，会随工具调用参数留在历史里、之后每轮重复计费；工具参数的大块正文应在模型历史投影里省略（落盘参数保留完整），投影必须是纯函数且幂等，否则 append-only 前缀与提示词缓存会被改写。

## DeepSeek 思考模式：assistant 缺 reasoning_content 会让整条请求 400 2026-11-14 [后端][引擎]
- 现象：一条 43 步的工具链跑到最后突然 `LLM_REQUEST_REJECTED`，HTTP 400 `The reasoning_content in the thinking mode must be passed back to the API`，前面每一轮都正常。
- 判据：看失败请求前一条 assistant 是不是“关思考的恢复轮”（`thinking_disabled=true`、`reasoning=""`）。DeepSeek 要求历史里每条带 `tool_calls` 的 assistant 消息都带 `reasoning_content`：缺字段 → 400，空字符串可以通过，请求显式 `reasoning_effort:"none"` 时服务端跳过校验（所以恢复轮自己不报错，下一轮重新开思考才炸）。

## 终端里的半块浮雕：字格不是方的，VTE 也不会告诉你像素 2026-11-14 [命令行]
- 现象：命令行欢迎头像在 Windows 正常、在 Ubuntu 的 GNOME Terminal 里看起来“左右扁扁”。
- 判据：半块字形（▀/▄）每个字符覆盖 2×2 源像素，屏幕上的源像素是 `cell_width × cell_height/2`。终端字格比（高/宽）来自字体，不是常数：Windows 光栅字格 8×16=2.0，而实测这台 GNOME Terminal 是 10×26=2.6。按 2.1 猜就会多画 20% 的行，头像被竖向拉高 → 读起来是横向压扁。量法：截图里数半块行高，或直接看标题两行的行距。
- 修法：`TIOCGWINSZ` 的 `ws_xpixel/ws_ypixel` 在 VTE（GNOME Terminal/Tilix）里恒为 0，量不到；改问终端本身——`CSI 14 t` 回 `ESC[4;h;w t`（文本区像素），`CSI 18 t` 回 `ESC[8;rows;cols t`（文本区字数），两者相除就是真字格比（VTE 不答 `CSI 16 t`）。探测要 `poll(2)` 加超时、只读不等待、结果 `OnceLock` 缓存；迟到的应答是不认识的 CSI，事件循环会忽略。
- 提示：CLI 的头像/图表类 ASCII 艺术都要按这个比例算行数，否则换台机器就变形；`WUNDER_CLI_CELL_ASPECT` 留作手动覆盖。

## `dry_run` 预览不能沿用「已落盘」的字段口径 2026-11-15 [工具][模型契约]
- 现象：`文本编辑`/`写入文件` 带 `dry_run: true` 时，模型收到的结果里仍是 `changed: true`、`changed_files: 1`。预览根本没写盘，模型却容易当成「已经改好了」，直接跳过真正的写入。
- 判因：写入结果的投影层（`orchestrator/tool_result_payload.rs`）用 `file_write_change` 判「是否真的改了」，该函数对 `dry_run` 故意返回 `None`（无法判定就不许断言没变），随后回落到 `changed_files > 0`——而预览也照样把 diff 计数和 `changed_files: 1` 填满，于是被投影成 `changed: true`。
- 规矩：`changed` 只表示「磁盘已变」，预览期间恒为 `false`；「若执行会不会改」单独用 `would_change`/`would_change_files` 表达（`file_write_would_change` 复用同一套计数口径，并允许编辑类结果缺少 `existed` 时按 diff 计数判定）。新增任何写类工具时都不要让预览走「已落盘」的键。

## shell 命令替换里取终端尺寸：重定向顺序决定成败 2026-11-15 [packaging][shell]
- 现象：安装器开场画面读不到终端行列数，`stty size` 在 pty 里明明可用，放进 `$( )` 就返回空。
- 判因：两条坑叠在一起。① `$( )` 内 stdout 已换成捕获管道，`<&1` 复制到的是管道而不是终端；② `stty size 2>/dev/null <&2` 是**从左到右**生效的，先把 stderr 指向 /dev/null，后面的 `<&2` 就复制到了 /dev/null。

- 判因：头像属于转录里的一条条目，整段转录按（宽/高/revision/条目数/滚动位置）做渲染缓存。动画期间条目数、宽度都不变，只是那条条目内部的行数在变，缓存键完全一样，于是每帧原样复用首帧。
- 规矩：上一条讲的是「样式随时间变 → 缓存存静息值、每帧叠实时图层」；若变化的是**内容**（行数、字符、排版随相位变），缓存里没有可复用的静息内容，就必须把相位量化后放进缓存键（这里用 `reveal_frame()`，静止时为 `None`），让它到点自然失效重建。
- 附：量化用「帧号」而不是 `phase: f32`——`f32` 做键每次都不相等，会帧帧重建；帧号又正好对上排帧节奏，且结束时落到 `None`，最后一帧重建出的就是静止画面。

## 状态文本不是存活事实 2026-11-15 [runtime][desktop]
- 现象：线程明明空着，侧边栏和归档入口却一直说「正在运行，请先停止再归档」，重启也不消失。
- 判因：监视缓存里的 `running` 与任务台账里的 `running` 都被当成了「有人在跑」。进程半路消失后，前者停在文本上，后者的行队列根本不会领取（只领 pending/retry），于是两处都永久残留；归档门禁据此永久拒绝。
- 规矩：存活只认三种可失效的证据——本进程的执行集合、未过期的会话锁（到期即失效，别用心跳提前判死，一次续期失败就会误杀正在跑的轮次）、队列仍会领取的任务行（pending/retry，或刚领取 15s 内的 running）。文本、stage、summary 一律只作展示。
- 配套：崩溃残留必须有人结算。启动扫描把这些 running 行落为 cancelled（跳过仍持锁的实例），否则任何「只领取 pending/retry」的队列都会把它们留到天荒地老。
- 复用检查：任何「是否在途」的判定都要能列出它的失效条件；只有「有没有这一行」而没有到期判断的查询（例如锁行存在性）不属于存活判定。

## 子进程的语义要按它自己认，不按 `wait_with_output` 认 2026-11-15 [cli][clipboard]
- 现象：命令行按右键复制第一次成功，之后复制新内容一直不生效，剪贴板停在最早那段文字；「已复制」提示也不再出现。
- 判因：`xclip` 写完 stdin 后会 fork 一个守护子进程持有 X 选择权，并**继承 stderr 管道**。`Command::wait_with_output` 要把 stderr 读到 EOF 才返回，而 EOF 要等那个守护进程退出（也就是等别人下一次复制），于是写入任务永不结束；同时「写入在途」的判断把后续每一次复制都静默丢弃了。
- 规矩：凡是可能 fork 后驻留的子进程，都不要用管道 + `wait_with_output` 收尾；stderr 走临时文件、只 `wait()` 自己的进程，并给在途任务留一个「最新一次待写」的槽位而不是丢弃。写剪贴板、拉起浏览器、调用常驻守护进程都属于这一类。
- 同一处还有：剪贴板命令列表必须全量尝试（装 `wl-copy` 但跑在 X11、装 `xclip` 但跑在 Wayland 都很常见），第一个失败就返回会让本来能用的后端永远轮不到。

## 定时任务要有「自己进程里的消费者」 2026-11-15 [cli][runtime][cron]

## 思考流式的两条通道（tail 先、delta 后）让首字重复 2026-11-16 [desktop][runtime][stream]
- 现象：思考条目一出现，最前面的一个 token 是重复的（「我我…」），过一会儿轮次结束又恢复正常。
- 判因：运行时对同一段文本发两帧——`thread_item_tail`（带 UTF-16 offset）先入队，随后才是语义 `llm_output_delta`；桌面桥的 `TailLedger` 只在 tail 越过水位时才放行，而这一轮的第一段 tail 水位必为 0，于是 tail 先落地建立思考行，紧接着的 delta 又是同一段文本，reducer 盲追加就多写了一遍。此后水位被「放行的 tail + 同一段的 delta」重复记账，超过屏幕上的文本，后面的 tail 全被当成重复丢掉，只有轮末 `llm_output.reasoning` 对齐才修好。
- 规矩：同一份文本有两个载体时，去重必须按位置（发送方游标），不能按到达顺序。`llm_output_delta` 上的 `reasoning_offset` 与 tail 的 `offset` 是同一个值；reducer 两路都走 `apply_reasoning_delta` / `apply_reasoning_tail` 按 offset 落地，水位用 `max(offset+len)` 记账而不是累加。
- 排查提示：看到「只有开头重复一个 token」「前几秒不对、轮末自愈」，先查是不是两个通道在同一段文本上各落地一次；再看水位是不是累加记账（累加会让真正的补段被误判为重复）。

- 判因：两层。①`thread_items.message_context` 用来判定「这一行算不算会话消息」，原来只认 `payload.role == "tool"`；工具结果后来演化成富载荷（`tool`/`args`/`data`，没有 `role`），这个标志就恒为 0，`load_history`（`messages` 过滤）把 29700+ 条工具行整体丢弃。②恢复逻辑只读 `record.content`，工具行没有 `content`，即便读到了也只剩 `[history] ...` 纯文本。
- 规矩：投影列（`message_context`、`visible` 之类）的派生条件必须跟着载荷形态一起改，并且**要能被回填**——改判定函数只对未来行生效，老库必须写一条带 `user_version` 的迁移，用 `preview_json` 里已存的字段把旧行补回来（`json_extract(preview_json,'$.payload.tool')`）。恢复/回放路径不要自造渲染，直接复用实时流那套 builder（命令卡/补丁卡/通用工具卡），否则两条路径必然分叉。
- 排查提示：`/resume` 少条目先数一遍存储：`select item_type,message_context,count(*) from thread_items group by 1,2`；某一类整整齐齐全是 0，就是判定条件写错了，不用看渲染层。

## 工具轮的「过渡正文」属于会话内容，不能随工具阶段一起丢掉 2026-11-16 [cli][stream][ui]
- 现象：命令行里跑长任务，只有思考和工具条目，模型在两次工具之间说的「我先定位一下…」「现在补上迁移」这类过渡正文一条都看不到；同一模型在桌面版/云端版正常显示。
- 判因：`apply_stream_event` 的 `llm_output` 分支先判 `payload_has_tool_calls`，命中就 `emit_tool_phase_notice()` + 清 `active_assistant` 后 `return`——该轮 `content`/`reasoning` 全被丢掉。流式时正文靠 `llm_output_delta` 已经落地，所以看不出问题；一旦 provider 整段回包（不流式/`--no-stream`/部分网关），就整段消失。
- 规矩：事件分支里的「阶段切换」只能重置流状态、收尾卡片，不能顺手丢掉这一帧自带的正文；先按最终回复同一套规则落地 `reasoning`/`content`（`stream_received_content_delta` 为真用整段替换，否则按增量合并去重），再进工具阶段。桌面版能看到的内容，命令行必须能从同一份事件重建。
- 排查提示：判断是「模型没发」还是「CLI 丢了」，先看持久化的 assistant_message 条目里有没有这段文字（`payload.content`），有就是前端丢；再用 `feed_stream_event` 造 `llm_output(content + tool_calls)` 一帧，看 `app.logs` 里有没有 Assistant 条目，一分钟定位。

## 详情面板的正文不要回放「行展示文本」，那会把标题、状态、目标再抄一遍 2026-11-17 [desktop][ui][tool-card]
- 现象：工作过程里执行命令条目展开后，命令出现两次——卡片标题是完整命令，正文又以「执行 · 运行中 / 命令」原样重放一遍。
- 判因：`tool_result_display` 产出的是「行展示文本」（动作 · 状态 → 目标 → 结果），它同时被当成行摘要和 `sections` 投影的兜底正文；命令段已经把命令做成 section 标题、把状态做成 meta 芯片，兜底正文再抄一次就成了重复。流式会话更糟：兜底正文里还带着同一段输出。
- 规矩：section 的正文只从结构化结果取（stdout / stderr / 流式 output），行展示文本只在没有结构化内容时兜底，且使用前必须剥掉「动作 · 状态」首行与目标行（`without_display_echo`）。新增工具卡时同理：标题/状态芯片已经显示的东西不要再进正文。
- 排查提示：`--command-fold-probe <dir>` 现在走 `NativeWorkflowEntry::from_payload` 的真实投影，直接出图；`WUNDER_COMMAND_PROBE_LINES=0` 就是「运行中还没输出」的样子，用来判断空正文有没有留下空白。

## 徽标这类「数字」必须和它旁边的列表共用同一个可见性谓词 2026-11-17 [desktop][storage][sidebar]
- 现象：工作区里只有 1 个工作线程，工作区标题却显示 3；点开也没有多出来的两条。
- 判因：树只列工作线程目录（`list_work_chat_sessions`，排除 `spawned_by in ('model','subagent_control')` 的子线程、`cron` 轨迹线程和渠道会话），而徽标用的是 `count_chat_sessions_by_workspace` 对 `status='active'` 的裸计数。子智能体运行留下的子线程按设计保持 active（Keep 复用），于是永远多算。
- 规矩：任何「数字/徽标/分页 total」都要和它对应的列表查询共用同一个 SQL 谓词常量（现在收在 `storage::chat_visibility::WORK_THREAD_VISIBLE_SQL`，SQLite 与 Postgres 共用），不要各写一份；改可见性时两处同时生效才不会被下一次改动再次拆开。

## 从 Windows 拷过来的仓库会让容器入口脚本死在 `set -o pipefail` 2026-11-17 [docker][deploy]
- 现象：服务器上 `docker compose up` 后 `wunder-server` 反复 `exited with code 2 (restarting)`，日志里只有一行像被覆盖过的 `...: line 2: set: pipefail` / `invalid option name`，随后 compose 报 `dependency wunder-server failed to start`；同栈的 `wunder-postgres`、`wunder-frontend` 都正常。
- 判因：`docker-compose-*.yml` 用 `./:/app` 把仓库目录直接挂进容器，`bash /app/scripts/docker-rust-entry.sh` 读的是宿主机文件。若这份 checkout 是 Windows 复制/`autocrlf` 产物，第 2 行变成 `set -euo pipefail\r`，bash 把 `pipefail\r` 当成非法选项名，`set` 内建报错即退出 2——脚本一行正文都没执行，所以日志看起来只是一个莫名其妙的选项错误。
- 规矩：`.sh` / `Dockerfile` / `docker-compose*.yml` 一律 LF，靠根目录 `.gitattributes` 固化；往服务器送代码必须走 git 或二进制传输，不要用文本模式拷贝整个目录。
- 排查提示：`sed -n '2p' scripts/docker-rust-entry.sh | od -c | tail -3` 看到 `\r` 就是它；`grep -rlI $'\r' scripts/*.sh` 可一次性找出所有被 CRLF 污染的脚本，修法是 `sed -i 's/\r$//'` 而不是改脚本逻辑。

## X11/Wayland 的剪贴板内容归写入进程所有 2026-11-17 [desktop][clipboard]
- 现象：截图后把图塞进剪贴板「成功返回」，切到别的软件粘贴却是空的；同进程里读回还正常。
- 判因：Linux 的剪贴板是**由写入方托管**的——arboard 用自己的选择窗口响应读取请求，最后一个 `Clipboard` 实例析构时把数据交给剪贴板管理器（没有管理器就没人接）并销毁窗口。用一次性的 `Clipboard` 写完就丢，等于写完立刻撤回；Windows 才是每次操作临时打开，持不持有实例不影响结果。
- 规矩：桌面版所有图片写入都走一个进程级常驻宿主线程，实例活到进程退出，写入在该线程串行（Windows 同时只允许一个线程打开剪贴板）。验收必须在**另一个进程**里读回来（`xclip -o -t image/png` / 聊天软件粘贴），同进程 round-trip 骗得过自己。
- 补充：i-slint-backend-winit 已启用 arboard 的 wayland-data-control（`cargo tree -e features -i arboard` 可确认），Wayland 会话下能直接写，不用退回 XWayland。

## 固定高度的单行行不能直接吃用户原文 2026-11-18 [desktop][ui][composer]
- 现象：输入区上方「等待发送」条带里贴入多行内容后发送，队列行看着是空的，文字却跑到卡片上方、盖住「等待发送 N」标题。
- 判因：Slint 的 `Text` 即便写了 `overflow: elide` 也照样按 `\n` 换行；行是 `height: 28px` + `vertical-alignment: center`，多行文本块按块高居中，行数越多越往上/往下溢出。卡片 `clip` 又只加在背景 `frame` 上，而正文 `card-body` 是它的兄弟节点，所以什么都没裁住。
- 规矩：固定高度的行（队列行、预设问题行、侧栏行…）喂进去的文本必须先在 Rust 侧折叠成一行（`native_chat_queue::strip_label`：空白折叠 + 200 字截断 + 省略号），并在行组件自身加 `clip: true` 兜底；`clip` 要加在真正包住内容的那个元素上，不要加在同级背景矩形上。
- 附带：`Composer.queue-height` 是手写的卡片高度公式，曾把底部 padding 算两遍（多 6px），导致输入卡比布局槽位低 6px；改条带内边距/行高时公式和 `QueueStrip` 的内容高度要一起改。

- 现象：`npm run typecheck:vue` 报「vue-tsc is not installed」，`npx playwright test` 也起不来；仓库根 `node_modules` 是个空目录。

## 快照分页里 `has_older` 不能和 `truncated` 共用 2026-11-18 [storage][admin][trajectory]
- 现象：管理端轨迹视图向上滚到最早一页后不再加载，且若用 `truncated` 判断「还能往前」会永远为真——线程一长就变成反复请求一个不存在的更早窗口。
- 判因：`truncated` 原本表示「本次快照被裁过」（`item_total > 本页 items`），翻页时这个条件恒成立；而「还有更早窗口」只该由窗口切分本身给出（轮次上限截断、条目预算不够、单轮被切）。
- 规矩：分页信号 `has_older` 只由窗口计算产生，且游标必须严格前移；前端再叠一层「空页即停 + 游标不前进即停」。`truncated` 保留恢复语义，两者不要互相赋值。
- 附带：预览页预算应按「请求」封顶而不是按「线程」封顶（旧的 500 条目 ≈ 20 个用户轮次），并只切完整轮次——半轮会让线程看起来莫名中断。

## 撤销栈的游标别存下标 2026-11-17 [backend][tools][history]
- 现象：删掉中间某一版快照后，再撤销直接报「已退回最早的可用版本」，更早的历史明明还在却永久不可达。
- 判因：游标存的是「第几态」的下标，快照却按编号 `name@N-sha` 落盘。删一格不压实，下标与文件编号就错位，`cursor-1` 找不到文件被当成栈底。
- 规矩：游标存稳定身份（快照文件名），不存会漂移的下标；删除/回收必须把更大的编号整体前移；读取侧再留一道「编号不超过游标的最近一版」兜底，让已经被弄坏的旧目录能自愈。
- 附带：容量兜底不能只有「每 N 小时扫一次」，两次扫描之间足够塞进远超上限的数据；再加一个按写入量触发的闸门（累计 > 8 MiB 立即回收），总占用才有硬边界。

## 回收测试要先算预算，再看「没删」是不是对的 2026-11-17 [backend][tools][history]
- 现象：造了 42 MB / 913 份快照后触发回收，文件一个没少，被当成「上限没做」。
- 判因：当时只有 64 MiB 的字节上限，42 MB 本来就在预算内；而且那批文件是手工造的，绕过了 `snapshot()` 的累计写入计数，闸门也就没被顶开。
- 规矩：写回收/清扫类断言时，先写「预算内必须一份不动」，再写「超预算必须砍到线内」；两个方向都覆盖，才能区分「阈值没触发」和「逻辑不对」。上限可用环境变量临时调小来验证，不必造真实大文件（稀疏文件 `set_len` 就够）。

## 「有上限」不等于「上限会生效」 2026-11-17 [backend][tools][history]
- 现象：连续两轮反馈「全局容量上限没做」。第一轮：42 MB 在 64 MiB 预算内，不动是对的；第二轮同样 42 MB 不动，是因为闸门只看时间和写入计数，而目录是手工造进去的，计数根本没涨。
- 判因：把「阈值存在」当成了「兜底存在」。真正的兜底要满足两条：阈值要落在用户会遇到的量级上，闸门要能在超限后的**下一次写入**就发现超了。
- 规矩：容量类限制用「账本 + 实测」两层——账本记上次实测的总量，之后按写入增量推进；账本缺失或越线就立即实测回收。默认预算按产品真实磁盘预期定（历史是保险不是备份），别把「先给 64 MiB 保守点」当稳妥。
- 附带：造数据测回收时走真接口（`snapshot()`），手搓目录会绕过所有计数，测出来的是「没触发」而不是「没实现」。
