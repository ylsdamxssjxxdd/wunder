# 桌面版性能测试对比方案（蜂窝 vs deepseek-harness 桌面端）

## 1. 目的与范围

对比 wunder 蜂窝（`frontend-slint/` + `crates/wunder-desktop` 原生进程）与 deepseek-harness 桌面端（`@deepseek-ai/dsh-desktop`，Electron 壳）的**软件性能**：耗时、内存占用、包体积。只比拼桌面应用本身，不比智能体框架层（引擎内部基准、模型能力、任务完成率等不在本方案范围内）。

形态差异本身就是对比价值：原生 Rust + Slint 单进程 vs Electron（Chromium + Node 运行时捆绑）多进程。

## 2. 对比对象

| 项 | wunder 蜂窝 | dsh 桌面端 |
| --- | --- | --- |
| 技术栈 | Rust + Slint 原生窗口，无 WebView | Electron 壳 + bundled dsh runtime |
| 进程模型 | 单进程（`NativeDesktop` 同进程调用后端） | 多进程（main / renderer / GPU / utility + runtime） |
| 本地存储 | 本地 SQLite | 会话 JSONL（zstd） |
| 分发 | Windows（开发 64 位口径；Win7 32 位仅作兼容验收） | `package:win:x64` 安装包；macOS arm64/x64 |

## 3. 指标体系

### 3.1 耗时（墙钟，主指标）

| # | 场景 | 计时起点 → 终点 | 负载 |
| --- | --- | --- | --- |
| T1 | 冷启动首帧 | 进程启动 → 窗口首帧绘制 | 无预置数据 |
| T2 | 冷启动可交互 | 进程启动 → 会话列表与对话可用 | 无预置数据 |
| T3 | 线程冷打开 | 点击会话 → 历史完整渲染 | 合成 200 轮 × (500 文本 + 125 推理增量) ≈ 127,400 事件 |
| T4 | 线程重开 | 二次打开同一线程 → 渲染完成 | 同上 |
| T5 | 长会话渲染首帧 | 打开线程 → 首屏内容可见 | 同上 |
| T6 | 长会话滚动流畅度 | 滚动全程帧耗时分布 | 同上，滚动到底再回顶 |
| T7 | 流式输出首显 | 发送消息 → 首个增量可见 | 固定速率合成 token 流 |
| T8 | 流式期间交互 | 输出过程中滚动/输入响应耗时 | 持续输出 ≥ 30s |
| T9 | 断流重连 | 人为断开 → 恢复且补水完整（不丢字） | 固定大小流 + 指定断点 |

### 3.2 内存占用（与耗时分开采样）

| # | 端点 | 定义 |
| --- | --- | --- |
| M1 | 空闲驻留 | 启动完成静置 10 分钟后 |
| M2 | 长会话加载后 | T3 完成后立即采样 |
| M3 | 流式输出峰值 | T8 期间每秒采样取最大 |
| M4 | 滚动峰值 | T6 期间每秒采样取最大 |

Windows 统一口径：`Working Set` + `Private Bytes`，**多进程求和**（dsh 全部 Electron 进程 + runtime；wunder 单进程）。进程数单独记录。

### 3.3 包体积与分发

| # | 指标 | 定义 |
| --- | --- | --- |
| P1 | 安装包大小 | dsh `package:win:x64` 产物 vs 蜂窝打包产物 |
| P2 | 安装后磁盘占用 | 安装目录总大小（含运行时、资源、依赖） |
| P3 | 可执行文件/模块数 | 安装目录内 exe/dll/node_modules 规模 |
| P4 | 首启额外开销 | dsh runtime prepare 下载/解压量；wunder 应为 0 |
| P5 | 数据目录占用 | 相同合成负载写入后的本地数据大小 |

### 3.4 附加（可选）

- CPU 占用：M1/M2/M3 端点的进程 CPU 占比。
- 磁盘写入：运行全程写入字节数。

## 4. 测量方法（两边统一口径）

1. **合成固定输入**：负载来自评审过的常量（沿用 dsh 会话形状 127,400 事件），禁网络、禁真实用户数据；两边写各自的合成数据生成器。
2. **采样**：每场景预热 1 次、全新进程采样 5 次，取中位数；报告全部原始值。
3. **计时终点显式化**：每个场景在实现时写明起点/终点埋点位置，不允许事后解释。
4. **内存独立采样**：不与计时样本混算；采样端点固定（M1–M4）。
5. **同机同环境**：同一台机器、接通电源、关闭高负载后台程序；记录 CPU 型号、核数、内存、OS 版本、双方版本号与编译 profile（release/优化等级）。wunder 64 位口径与 32 位 Win7 验收分开，不混基线。
6. **预算（可选门禁）**：`预算 = ⌈中位数期望 × 1.25⌉`；跨机对比需附机器比测量。
7. **走真实入口**：两边都用正常启动方式打开桌面应用，不用调试专用捷径；dsh 侧如借用其 vitest bench 的引擎数字，只能作参考对照，不作主对比。

## 5. 场景矩阵（对应关系）

| 本方案场景 | dsh 侧参考 | wunder 侧实现 |
| --- | --- | --- |
| T1/T2 启动 | Electron `whenReady` → `ready-to-show` → 首帧 | `wunder-desktop` 原生启动埋点（参考已有启动首帧基线方法） |
| T3/T4/T5 线程打开 | `session-open` 基准形状（200 轮×(500+125)） | SQLite 合成线程 + 引擎真实打开路径 |
| T6 长会话滚动 | `long-session-browser` 思路 | Slint 虚拟列表，原生帧耗时 |
| T7/T8 流式 | 客户端流式渲染 | WebSocket/同进程事件 → 按帧合并（16–33ms 节奏） |
| T9 重连 | `active-stream-reconnect` | 断线 replay/补水语义 |
| M1–M4 内存 | Electron `process.getProcessMetrics` | `Get-Process` 计数器 / 原生埋点 |
| P1–P5 包体积 | `package:win:x64` 产物 | `cargo build --release` + 打包产物 |

## 6. 运行流程

1. 同机准备：安装两个应用的最终产物（非开发模式）；清空各自数据目录后写入相同形状合成数据。
2. 依次跑 T1–T9（每场景 1 预热 + 5 样本）；M1–M4 与 P1–P5 分别采样。
3. 记录完整环境与双方版本；原始值 + 中位数落 JSON/CSV。
4. 产出并排对比表与结论，归档 `docs/性能基线/<日期>-蜂窝-vs-dsh-桌面性能.md`。

## 7. 首批数量级参考（dsh 公开口径，仅作对照）

| 项 | dsh 参考值 | 说明 |
| --- | --- | --- |
| 重开线程首次历史 | 48 ms | 参考机，×1.25 为预算；wunder 自建基线后另定 |
| 重开 Agent 恢复 | 40 ms | 同上 |
| 引擎驻留堆 | 26.1 MB | 仅为引擎部分，不含桌面壳；wunder 对应端点自行测量 |

包体积无 dsh 公开数字，首次运行时以 `package:win:x64` 实测为准。

## 8. 实施 SOP（如何比测）

### 8.1 阶段划分

| 阶段 | 内容 | 产出 |
| --- | --- | --- |
| 0 环境准备 | 同机、接通电源、关闭高负载后台；记录环境清单 | 环境记录表 |
| 1 产物就绪 | 两边拿到最终形态产物（非开发模式） | 蜂窝安装产物 + dsh win-x64 产物 |
| 2 工具自检 | `scripts/desktop-bench/` 三脚本对已知进程空跑 | 校验通过的测量脚本 |
| 3 黑盒比测 | T1 启动、M1 空闲内存、P1–P5 包体积（同一套脚本测两边） | JSON/CSV 原始数据 |
| 4 交互比测 | T2–T9：wunder 侧加 `--bench-scenario` 埋点自报时间戳；dsh 侧黑盒 + 其公开基准数对照 | 分场景数据 |
| 5 汇总归档 | `summarize.py` 合成并排表 → 写入 `docs/性能基线/<日期>-蜂窝-vs-dsh-桌面性能.md` | 对比报告 |

### 8.2 产物获取

- **蜂窝**：`cargo build --release -p wunder-desktop` 后打包产物；包体积测量同时记录裸 exe 与完整打包目录两个口径。
- **dsh 桌面端**（二选一）：
  1. 本地源码构建：`pnpm install && pnpm run build`，再 `pnpm --filter @deepseek-ai/dsh-desktop package:win:x64:dir`（`--dir` 出免安装目录，测量与安装版等价且省去安装器签名步骤）。
  2. 官方发布渠道下载现成安装包（版本号记录进环境表）。
- 两边产物版本、构建时间、构建参数必须写进报告。

### 8.3 各阶段执行要点

**阶段 3（黑盒，第一批可立即执行）**

```powershell
# T1 启动耗时：同脚本测两个应用，1 预热 + 5 样本
powershell -File scripts\desktop-bench\measure-startup.ps1 -ExePath <蜂窝exe> -Runs 5 -OutJson bench-wunder-startup.json
powershell -File scripts\desktop-bench\measure-startup.ps1 -ExePath <dsh主exe> -Runs 5 -OutJson bench-dsh-startup.json

# M1 空闲内存：先启动应用静置，再采样 10 分钟
powershell -File scripts\desktop-bench\measure-memory.ps1 -ProcessName <进程名> -DurationSec 600 -OutCsv bench-m1.csv

# P1–P3 包体积
powershell -File scripts\desktop-bench\measure-package.ps1 -Target <安装包或目录> -OutJson bench-pkg.json
```

黑盒口径说明：T1 以「进程启动 → 主窗口句柄出现」为准，轮询粒度 ~10ms，两边完全一致即可公平；进程按名称聚合（覆盖 Electron 多进程子窗口）。

**阶段 4（交互场景，第二批）**

- wunder 侧：给 `wunder-desktop` 增加 `--bench-scenario <名>` 参数，程序按场景自动执行并输出 JSON 时间戳（线程冷打开/重开、长会话首帧、滚动帧分布、流式首显、断流重连）。埋点进主干代码、走生产路径，同时服务日常回归。
- 预置数据：按 127,400 事件形状各写生成器——wunder 侧写合成 SQLite 线程；dsh 侧参照其 `synthetic-released-v0-session.ts` 生成会话 JSONL。
- dsh 侧 T3–T9 若无法黑盒触发，用其 vitest bench 公开数字（session-open / long-session-browser）作对照并显式标注「引擎口径，非桌面端到端」。

### 8.4 公平性原则

1. **黑盒优先**：能用同一外部脚本测的场景，绝不给一方加专用测量捷径。
2. **埋点只归自己**：应用内埋点仅用于 wunder 侧自报；dsh 侧同类数据要么黑盒测、要么用其公开基准并标注口径差异。
3. **口径先写后测**：每个场景的起点/终点定义在执行前落到本 SOP，测完不改。
4. **原始值全保留**：报告必须附全部样本，不只发中位数。
