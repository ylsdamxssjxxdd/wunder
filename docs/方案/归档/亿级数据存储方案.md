# 亿级数据存储方案

## 1. 背景

2026-10-12 的舰体卡顿事故暴露了存储层在数据量增长下的结构性弱点：一个被删除的压测线程在 `thread_items` 残留 122 万行（2.6 GB）、`tool_logs` 残留 81 万行（1.2 GB），叠加全表聚合查询与 BRIN 失效索引，导致登录与监控路径被 30–60 秒的扫描占死。本次已完成的止血修复（孤儿清理任务、SWR 缓存、btree 时间索引、run_db 纪律、shared_buffers 调优）解决了"页面卡死"一类问题。

本方案回答下一个量级的问题：当核心日志表达到**亿行（10⁸）规模**时，读写路径如何保持稳定。目标形态是舰体（server）的 PostgreSQL 存储；蛹/舵机的本地 SQLite 见 §4.6 边界说明。

## 2. 规模假设与瓶颈定位

| 假设（亿行规模） | 数值 |
|---|---|
| 单表行数 | thread_items / tool_logs / thread_item_blocks 各 ≥ 1×10⁸ |
| 单表体积 | 100–400 GB（含 TOAST） |
| 活跃用户 | 10⁴ 量级并发读写 |
| 写入节奏 | 高峰每秒数千行日志追加 |

当前代码中对表总量敏感（O(全表)）的路径，按危险程度排序：

1. `get_user_tool_stats` / `get_user_chat_stats`（[workspace.rs](../crates/wunder-runtime/src/services/workspace.rs) 用量缓存）——全表 GROUP BY，已改后台单飞，但数据越大后台烧得越狠，亿行下单次刷新将以分钟计
2. `tool_logs.data NOT LIKE '%…%'` 过滤——逐行解压 TOAST 大字段，是全表扫描慢的真正放大器
3. 监控页 3 小时窗口聚合——已有 btree 索引，O(窗口)，但窗口内若含海量 TOAST 行仍会退化
4. 会话删除、retention 清理——亿行表上的大 DELETE 产生等量死元组，autovacuum 追不上
5. 孤儿扫描、压测灌数——批量路径必须走分区裁剪

不构成瓶颈、维持现状：会话列表（分页）、线程按轮次加载（按 turn 分页）、SWR 缓存读、监控计时埋点。

## 3. 总体策略

四根支柱，每根独立可交付、可回滚：

| 支柱 | 解决什么 | 核心动作 |
|---|---|---|
| A. 增量用量统计 | O(全表) 聚合 → O(1) 读取 | 计数汇总表 + 写入队列合并更新 + 水位对账 |
| B. 时间分区 | 大 DELETE、扫描裁剪、分区级运维 | created_time 月分区 + 自动建分区 + DROP 代 DELETE |
| C. 大字段治理 | TOAST 解压放大器 | excluded 标记列替代 LIKE；超大 payload 出库 |
| D. 生命周期与资源 | 无限增长与配置错配 | 热/冷分层归档、autovacuum/连接参数基准、pg_stat_statements 护栏 |

## 4. 详细设计

### 4.1 支柱 A：增量用量统计

新表（PostgreSQL 与 SQLite 同构）：

```sql
CREATE TABLE user_usage_summary (
  user_id      TEXT PRIMARY KEY,
  chat_records BIGINT NOT NULL DEFAULT 0,
  tool_records BIGINT NOT NULL DEFAULT 0,
  last_chat_time  DOUBLE PRECISION,
  last_tool_time  DOUBLE PRECISION,
  watermark_id BIGINT NOT NULL DEFAULT 0,   -- 已计入的日志流水号
  updated_ts   DOUBLE PRECISION NOT NULL
);
```

- **写入侧**：在 `StorageWriteQueue` 批量落库的同一事务里，按 user 合并本次插入行数做一次 UPSERT（`ON CONFLICT (user_id) DO UPDATE SET chat_records = user_usage_summary.chat_records + EXCLUDED.chat_records`）。每批次每用户一条语句，不是每行一条，避免热行竞争。
- **删除侧**：会话清除路径同步递减对应计数（与现有 purge 路径同事务）。
- **对账（防漂移）**：挂在保留期维护任务（[workspace.rs](../crates/wunder-runtime/src/services/workspace.rs) janitor）里，每日一次按 `watermark_id` 之后的新增流水增量校准，不做全表重算；全量重算降级为每周一次的低峰后台任务，作为最终兜底。
- **读取侧**：`get_user_usage_stats` 直接读汇总表（毫秒级），现有 SWR 缓存保留作为前端突发流量的第二层缓冲，TTL 可放大到 300s。
- 涉及文件：[wunder-core/storage_backend.rs](../crates/wunder-core/src/storage_backend.rs) 新增 trait 方法；postgres/sqlite 各实现；`write_queue` 批处理路径挂接。

### 4.2 支柱 B：时间分区（PostgreSQL）

核心日志表 `thread_items`、`thread_turns`、`thread_item_blocks`、`thread_log_changes`、`tool_logs`、`artifact_logs` 改为 `PARTITION BY RANGE (created_time)` 月分区。

- **分区键与主键**：分区表唯一约束必须包含分区键，主键从 `(session_id, item_id)` 调整为 `(session_id, item_id, created_time)`；所有按 session 的查询通过 catalog 拿到会话创建时间后附加 `created_time >= session_created` 提示，实现分区裁剪；无法提供时间提示的路径退化为逐分区索引探测（有 `(session_id, …)` 局部索引，36 个分区 × 索引探测仍在毫秒级）。
- **自动建分区**：[postgres/schema.rs](../crates/wunder-runtime/src/storage/postgres/schema.rs) 新增 `ensure_time_partitions(table, months_back, months_ahead)`，初始化时建 当前±3 个月，维护任务每日检查滚动补建。
- **删除即 DROP**：会话清除、retention、孤儿清理对"整月可弃"的数据改用 `DROP TABLE partition`（瞬时、零死元组）；会话级删除仍走行级 DELETE 但因分区裁剪只锁目标分区。
- **autovacuum**：父表统一 `autovacuum_vacuum_scale_factor = 0.02`，大分区（>1GB）单独降低。
- **索引**：每分区继承 `idx_*_time`（created_time btree）与 `(user_id, session_id)` 前缀索引；BRIN 仅允许用于确认物理顺序强相关且 `pages_per_range` 显式调小的追加型表，默认禁用（本次事故直接诱因）。
- **迁移路径**：新建影子分区表 → 存量数据按月分批 INSERT SELECT → 校验计数 → 事务内 RENAME 换名 → 旧表保留观察 7 天后 DROP。原型期数据可重生，允许简化为"直接重建 + 重新灌数"；有不可再生存量时走影子表方案。

### 4.3 支柱 C：大字段治理

1. **excluded 标记列**：`tool_logs` 增加 `excluded BOOLEAN NOT NULL DEFAULT false`，写入时若命中 skill-read 等排除标记则置 true；所有统计路径的 `data NOT LIKE '%…%'` 替换为 `excluded = false`，彻底消除统计扫描时的 TOAST 解压。存量数据一次性回填（分区迁移时顺带完成）。
2. **payload 出库**：超过阈值（建议 64 KB）的工具输出不再内联在 `tool_logs.data` / `thread_item_blocks.payload`，转存 `log_payload_blobs(id, content)` 侧表，主表存引用 id。读路径按需取，列表/统计路径永不触碰。
3. 现有 `data` 列保留兼容读取，双读期结束后收缩。

### 4.4 支柱 D：生命周期与资源

- **冷热分层**：默认在线保留 90 天热数据；更早的分区按月导出为 zstd 压缩 JSONL 归档（写入 `archive/` 目录或对象存储），校验行数与哈希后 DROP 分区。导出任务挂在维护任务，失败重试且 DROP 前强校验。
- **护栏**：启用 `pg_stat_statements`，维护任务定期抓取 top 慢查询写 WARN 日志（复用现有 admin monitor timing 通道）；对 O(全表) 新查询形成制度性发现。
- **连接与内存基准**：`shared_buffers = 25% RAM`（写进部署文档与 compose 注释），连接池上限 = 核数×2+磁盘数，亿级用户量引入 PgBouncer（transaction pooling）作为部署项而非代码项。
- **run_db 纪律**：所有同步 DB 调用必须在阻塞线程池（本次已修两处，作为代码评审红线）。

### 4.5 读取路径纪律（随分区落地的配套）

- 按 session 加载线程：附加创建时间提示（catalog 已有）。
- 监控/统计端点：一律读汇总表或窗口索引，禁止新增长窗口全表聚合。
- 列表类接口：保持既有分页/限量要求（AGENTS.md 性能条款），分区后按分区裁剪进一步提速。

### 4.6 SQLite 本地形态边界

蛹/舵机面向单用户本地库，不追亿行目标；本方案仅取三件套：`excluded` 标记列、`user_usage_summary` 计数表、retention 归档（导出后 DELETE + `wal_checkpoint(TRUNCATE)` 收缩）。SQLite 不做分区；单库超过数十 GB 时由归档策略控制体积。

## 5. 实施阶段与验收

| 阶段 | 内容 | 停机 | 验收指标 |
|---|---|---|---|
| 一（本迭代后立即） | 支柱 A 计数表 + 支柱 C excluded 列 + pg_stat_statements + autovacuum 基准 | 无（在线加列/加表） | /wunder/auth/me P99 < 50ms；用量读取 O(1)；对账零漂移 |
| 二 | 支柱 B 分区迁移 + payload 出库 + 自动建分区 | 一次低峰窗口 | 存量迁移计数一致；会话读写 P99 < 100ms；删除改 DROP 零死元组堆积 |
| 三 | 冷热分层归档 + PgBouncer 部署 + 副本隔离统计查询 | 无 | 归档校验通过率 100%；在线表体积受控于热窗口 |

**压力验证**：复用现有压测线程生成器（含 `stress_bench` 示例与 bulk INSERT 路径）构造 ≥ 1×10⁸ 行数据集，在阶段二合并前跑完整读写剖面（登录、监控、会话加载、删除、归档），对照 §5 指标出具数据。

## 6. 风险与回滚

| 风险 | 缓解 | 回滚 |
|---|---|---|
| 计数漂移 | 水位增量对账 + 每周全量兜底重算 | 汇总表可随时全量重建，读路径退回 SWR 全表聚合（已隔离在后台） |
| 分区键调整破坏唯一性 | 主键变更纳入影子表迁移；item_id 生成含会话内序号，全局不依赖单表唯一 | 影子表换名前旧表不动，秒级切回 |
| excluded 回填漏标 | 回填以 marker 常量为准并留校验查询；写路径单点收口在 log 写入函数 | 列默认 false，等价于现状过滤集 |
| payload 出库双读期不一致 | 写入先落侧表再落引用，同事务 | 阈值调大即回到内联 |
| 大批量 DELETE 仍发生在会话级路径 | 会话删除前先查 catalog 时间，裁剪到单分区 | 保留行级 DELETE 兜底路径 |

## 7. 明确不做

- 引入新的存储引擎/中间件（ClickHouse、ES 等）——当前 PostgreSQL 分区 + 归档足够覆盖 10⁸–10⁹ 行，避免原型期技术栈膨胀。
- 蛹/舵机本地库做分区或分库——单用户形态不适用。
- 实时流式物化（物化视图自动刷新）——对账机制更可控。

## 8. 落地记录（与方案的偏差）

阶段一与阶段二已落地，以下为实现时相对本方案的最终决定：

1. **计数不走写路径 UPSERT，改为"水位对账"为唯一计数者**（§4.1 写入侧条款作废）。chat/tool 的插入点分散在存储层多个 commit 路径（accept_thread_turn、append_chat、commit_thread_item 等），写队列钩子无法覆盖全部入口，漏计即漂移。实现为：janitor 每 600s 调 `reconcile_user_usage(false)`，按 meta 水位（`usage_tool_watermark`、`usage_chat_watermark_ts`）聚合新增行 ADD 进 `user_usage_summary` 并在同一事务推进水位；`usage_full_reconcile_ts` 超 7 天或水位缺失时自动全量重算兜底。
2. **删除侧递减带水位过滤**：所有删除路径（按用户/按会话/按时间段/孤儿清扫）只对"已计入水位内的行"递减——tool 侧 `id <= 水位 AND excluded = false`，chat 侧 `created_time <= 水位 AND kind IN (user/assistant_message) AND visibility='user'`；水位外行未计数，直接删除不递减。PG 用 CTE 聚合避免大结果 RETURNING。
3. **thread_turns 不分区**（§4.2 六表改五表）。其 `UNIQUE(session_id, client_message_id)` 与 partial UNIQUE 承担轮次准入原子性，分区表唯一约束必须含分区键会破坏该语义；且 turns 规模是 O(轮次) 而非 O(条目)。实际分区表：`thread_items`、`thread_item_blocks`（补 created_time 列，回填自 thread_items）、`thread_log_changes`、`tool_logs`、`artifact_logs`。
4. **payload 出库（§4.3.2）跳过**。`tool_logs.data/args` 已被 `truncate_tool_log_column` 硬截为 head+tail 4000 字符，TOAST 风险已被消除；事件放大问题由 excluded 列 + 汇总表 + 分区共同消除；block 本身是增量块。侧表方案留作未来数据超限时的演进项。
5. **两个受唯一约束影响的 upsert 重写**：分区父表无全局唯一索引，`append_thread_item` 与 `upsert_thread_text_block` 从 `ON CONFLICT` 改为 update-or-insert，正确性由 `thread_logs FOR UPDATE` 会话级串行化保证；`thread_items` 的 `UNIQUE(session_id, root_turn_id, item_index)` 降级为普通索引。
6. **"删除即 DROP 分区"暂缓**：会话级删除与 retention 仍走行级 DELETE（分区裁剪保证只触及目标分区），整月 DROP 留给归档阶段一并实现，避免 DEFAULT 分区与新月份分区的行冲突处理复杂化。
7. **排除集补充**：`TOOL_LOG_EXCLUDED_NAMES` 补入 `final_response`/`最终回复`（既有测试长期期望该行为但常量缺失，测试此前已红）；excluded 判定改为写路径 `tool_log_row_excluded(tool, data)` helper，在截断前的完整 data 上判 marker。
8. 线上库迁移脚本：`scripts/migrate_pg_billion_scale.sql`（加表加列、回填 excluded、五表分区重建重灌、序列对齐），原型期直接重建无影子表。
9. **pg_stat_statements 护栏已启用**（§4.4）：线上库 `ALTER SYSTEM` 预加载 + `CREATE EXTENSION`（配置持久化于 bind-mount 的 auto.conf）；janitor 每 3600s 调 `StorageLifecycle::report_slow_queries()`，PG 实现抓 `mean_exec_time >= 200ms` 的 top 5 归一化语句写 WARN 日志，扩展缺失降级为 debug。偏差：护栏直接走 WARN 日志，未接 admin monitor 通道（原型期日志足够，接通道属 UI 项）。SQLite 无对应物，默认空实现。
