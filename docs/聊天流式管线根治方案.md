# 聊天流式管线根治方案

状态：方案评审中（未实施）
关联：`docs/线程日志重构方案.md`（统一线程日志的上一阶段）、`docs/架构评估与演进路线.md`

---

## 0. 一句话结论

用户侧聊天气泡"更新不及时 / 阻塞 / 顺序颠倒 / 错乱缺漏"的根因是架构性的：**同一气泡存在 6 个写入方、2 套互不相通的游标，气泡的身份与顺序靠前端启发式合并猜测**。本方案把系统收敛为：**一线程（会话）、一日志（thread log）、一游标（change_seq）、一渲染路径（确定性投影）**，删除全部启发式层与竞争写入方。

## 2. 目标与非目标

### 目标

1. 会话内事件全序可依赖：任何客户端在任意时刻重连，都能从单一游标无损续传，最终渲染结果与线程日志重放结果严格一致。
2. 气泡身份 = 服务端 `item_id`，气泡分组 = `(turn_id, model_round)`，顺序 = `change_seq`。前端不存在任何启发式合并、评分、猜测。
3. 流式延迟不劣化：正文增量到渲染 p95 < 100ms；断线重连恢复 < 1s；长会话不阻塞输入与滚动。
4. 删除（而非新增）复杂度：迁移完成后净删除前端 coalesce/score/watchdog 回填层与后端 pump 补洞/event_id 注入层。

### 非目标

- 不改 `orchestrator.stream()` 内部 ReceiverStream 及其其他消费方（a2a、core_ws、core、external_workflows、channels、cron、mission、session_run_stream、benchmark——它们不经过 chat_ws 用户推送路径，保持原样）。
- 不改线程日志存储层 schema（`thread_items` / `thread_log_changes` / `thread_item_blocks` 已满足需求）。
- 不在本方案内做子智能体事件迁移（列入 M4 单独实施，避免一次变更面过大）。
- 不动 TUI（`crates/wunder-cli`）与 desktop slint façade 的消费方式；M1 仅做耦合审计确认其不受协议演进影响。

## 3. 目标架构

### 3.1 六条不变量（新契约，实现与测试都以它为准）

- **I1 单一事实源**：会话的全部持久状态变化（item upsert、text block、turn 生命周期）在 `thread_log_changes` 中产生恰好一行 change，`change_seq` 会话内严格单调，在会话 emit 锁内分配。
- **I2 全序**：emit 串行化保证 **入库顺序 == 通知顺序 == WS 推送顺序 == 客户端应用顺序**。客户端不再需要任何重排序逻辑。
- **I3 帧二分**：WS 帧只有两类——
  - **durable 帧**（`thread_change`）：带 `seq`，幂等可重放，永不静默丢弃（队列满走背压）；
  - **ephemeral 帧**（`thread_item_tail`）：正文/推理的低延迟尾部增量，带 `item_id + field + offset`，offset 幂等，**允许丢弃**，由下一帧 durable block 快照修复。
- **I4 身份即渲染**：气泡 identity = `item_id`（`{turn_id}:text-{model_round}` / `{turn_id}:tool-{tool_call_id}` / …），渲染 key = item_id，分组 = `(turn_id, model_round)`，无合并评分。
- **I5 一游标续传**：断线重连 = `watch/resume after_change_seq=lastSeq`，与实时推送走同一读路径；全量快照仅发生在首次装载与 `thread_snapshot_required`，且应用前必须通过游标守卫（snapshot.cursor >= lastSeq）。
- **I6 纯 reducer**：客户端状态是 durable 帧序列的幂等折叠 + offset 守护的 ephemeral 尾巴；一切缓冲有界（数值见 §5.2）。

### 3.2 数据流（目标态）

```
模型/工具/控制代码
   │ emit(type, data)
   ▼
【会话 emit 锁】(串行化，见 §4.1)
   ├─ 同步写 thread_items / thread_log_changes(change_seq) / thread_item_blocks
   ├─ 通知 session change registry（tokio::watch<u64> cursor）
   └─ ephemeral 尾部增量 try_send（可丢）
   ▼
【每连接 session feeder】（每个 WS 连接 × 每个被订阅会话一个任务）
   loop: watch cursor 变更或 poll 超时(0.08s→0.8s 退避兜底)
         → 读 changes after cursor (page 200) → 按 change_seq 顺序推 thread_change 帧
   ▼
用户前端：唯一数据入口 = thread_change + thread_item_tail
   reducer（幂等折叠）→ 版本时钟（保留现有时钟合帧）→ 确定性投影 → 虚拟列表
```

要点：

- **`start` 不再直接转发实时事件**。`start` 的应答只做三件事：返回 `turn_id` + 当前 `change_cursor` 的 `stream_started` 帧；保留 stream 任务 drain（释放运行租约、approval 转发、goal 续跑判定都挂在它上面，见 `chat_ws.rs:590-666`）；客户端随后以 watch 模式从该 cursor 消费。start 实时流与 watch 轮询双路并推（B3/F3 的直接来源）就此消失。
- **排队任务与直连任务统一**：排队执行本就只落线程日志（`services/runtime/thread/runtime.rs:1354-1390`），在 feeder 模型下与直连在客户端视角完全一致，`queue_enter/queue_start/queue_finish` 就是普通 thread_change。
- **慢客户端**：WS 出口队列超过水位 → 停止推送并下发带 cursor 的 `stream_overflow` 提示帧，客户端重连后从 cursor 续传，无损（durable 帧可重放，尾部由 block 快照再生）。替代现有 `slow_client reason=queue_full_resume_required` 语义（`ws_helpers.rs:436-469`）。
- **多实例部署安全**：in-process 通知只是加速；feeder 始终保留轮询兜底（复用现 `resume_poll_interval_s` 退避参数，`ws_helpers.rs:97-109`），跨实例不丢正确性。

### 3.3 帧协议 v2

```jsonc
// durable：与 thread_log_changes 一一对应（页读展开）
{ "event": "thread_change", "seq": 1234, "change_type": "item_upsert|text_block|turn_status",
  "item_id": "turn_x:text-1", "revision": 3,
  "data": { /* item upsert 或 block 快照（field/block_index/offset/text）或 turn 状态 */ } }

// durable 特例：索引裁剪后游标失效
{ "event": "thread_snapshot_required", "seq": 1235 }

// ephemeral：低延迟尾部（正文/推理/工具输出），可丢可乱（按 offset 守护）
{ "event": "thread_item_tail", "item_id": "turn_x:text-1", "field": "content",
  "base_seq": 1233, "offset": 4096, "text": "……增量……" }
```

- `seq` 即 `change_seq`，全会话单调；durable 帧按 seq 升序推送。
- `thread_item_tail` 的 `offset` 沿用 TextTail 的 **UTF-16 code unit 计数**（`thread_log.rs:265-268` 已用 `encode_utf16().count()`），与 JS 字符串索引天然一致，前端不做任何编码换算。
- 废弃：WS 层 `event_id`/`event_seq` 双写注入（`ws_helpers.rs:471-495`）、transport `next_event_id` 基线（B5）。兼容期保留（§6）。

### 3.4 客户端状态机（新 store：`chatThreadState`）

```
ThreadState（每会话，markRaw 非响应式，沿用版本时钟失效机制）{
  lastSeq: i64
  turns: Map<turn_id, { turnId, userRound, status, clientMessageId? }>
  items: Map<item_id, Item>       // Item { itemId, turnId, modelRound, kind, status,
                                  //        revision, content, reasoning, workflow?, subagents? }
  blocks: Map<`${item_id}:${field}:${block_index}`, { offset, text }>
  tail: Map<item_id, { contentOffset, reasoningOffset, content, reasoning }>  // ephemeral 尾
  gapBuffer: Frame[]              // 有界，见下
}
```

Reducer 规则（纯函数，可单测）：

1. `thread_change`：`seq <= lastSeq` → 丢弃（幂等）；`seq > lastSeq + 1` → 进 gapBuffer；`seq == lastSeq + 1` → 应用。应用 = item upsert（仅接受 `revision` 更高者）或 block upsert 或 turn 状态迁移；随后消费 gapBuffer 中已连续的帧。
2. gapBuffer 溢出（> 64 帧或 > 1000ms）→ 触发一次 `resume after_change_seq=lastSeq` 续传（不是全量重载）。服务端保证 per-connection 有序，缺口只出现在重连接缝，正常流不会触发。
3. `thread_item_tail`：`offset == tail 当前位置` → 追加；`offset < 当前位置` → 忽略（已有）；`offset > 当前位置` → 忽略，等下一帧 block 快照整体修复。
4. `thread_snapshot_required` 或显式刷新 → 全量装载（现 loadSessionDetail），装载结果仅在 `snapshot.cursor >= lastSeq` 时应用；应用后 `lastSeq = snapshot.cursor`。
5. 乐观用户轮次：按 `client_message_id` 建立 pending 映射，`stream_started`/首个含该 turn 的 thread_change 到达后映射到 `turn_id` 并被服务端内容取代（`accept_thread_turn` 的幂等语义保持不变，`thread_log_store.rs:380`）。

确定性投影（取代 coalesce/score，`chatThreadProjection`）：

- 气泡分组：同一 `(turn_id, model_round)` 的 `assistant_message` item + 其 reasoning 构成一个 assistant 气泡正文；同组 `tool_call` item 渲染为该气泡的工作流卡片；`approval/plan/compaction/terminal` 各自确定性归位。排序键 = `(userRound, modelRound, kind 序)`，无任何字符串模式匹配与评分。
- 兼容：无 `model_round` 的历史 item 按 `change_seq` 定序（不再按 `id.localeCompare`）。

## 4. 后端改造明细

### 4.1 M1-A：emit 串行化（修 B1/B2/B3 的顺序根）

文件：`orchestrator/event_stream.rs`

- `EventEmitter` 增加 `emit_lock: tokio::sync::Mutex<()>`，`emit()` 全程持锁：turn_context 合并 → text item 注册 → TextTail 追加/flush → `event_item` 持久化 → 实时事件入队，整个函数体包进 `let _g = self.emit_lock.lock().await`。
- 效果：`change_seq` 分配、thread_change 入队、实时事件入队成为原子序列；runner 与 ToolEventForwarder 并发 emit 时按锁获取序全序化。
- 成本：并发发射方串行。可接受——SQLite 写本身串行，且 TextTail 已把每 token 写库摊销为 150ms/8KB 批。
- 保留 `next_event_id`（兼容期 transport 帧仍带 id），但其分配也移入锁内。

### 4.2 M1-B：session change registry + feeder（单一推送通道）

新文件：`services/thread_change_hub.rs`（或挂到 `orchestrator/thread_runtime.rs` 旁）

- `ThreadChangeHub`：`HashMap<session_id, tokio::sync::watch::Sender<u64>>`（有界清理：无订阅者即移除，复用 thread_runtime 的注册表风格）。
- emit 持锁段内在 `commit_thread_item` / block 写库成功后 `hub.publish(session_id, change_seq)`（非阻塞）。
- feeder 任务（`api/ws_helpers.rs` 重构 `resume_stream_events`）：

```
loop {
  wait(watch 变更, 超时 = poll_interval)        // notify 只是提前唤醒
  rows = list_thread_changes_by_session(session, cursor, page=200)
  for row in rows { send thread_change 帧; cursor = row.change_seq }
  text blocks 活跃尾随页附带（现语义保留，快照幂等覆盖）
  退避：无新数据按 resume_poll_backoff 放大；有新数据回到 base
}
```

- `resume` / `watch` / `start`（v2 客户端）三种入口都收敛到这一个 feeder 循环；`resume_stream_events` 现有轮询体（`ws_helpers.rs:576-734`）即 feeder 雏形，改造而非重写。

### 4.3 M1-C：帧分类与丢弃政策（修 B4）

文件：`orchestrator/event_stream.rs`、`api/ws_helpers.rs`

- `enqueue_event` 按帧分类取代 `should_backpressure_online_stream_event` 的字符串判断：
  - durable（thread_change / thread_snapshot_required / 生命周期）：队列满 → 阻塞 send（背压），永不丢；
  - ephemeral（`*_delta` → `thread_item_tail`）：`try_send`，满即丢（offset + 快照修复保证无损）。
- `record_overflow` 仅对 ephemeral 计数。

### 4.4 M1-D：ephemeral 尾部帧加坐标（修 F6 的对端配套）

- `llm_output_delta` 及工具/命令 `*_delta` 帧（现 `thread_item_delta`，`event_stream.rs:290-294`）统一改为 `thread_item_tail` 语义：补 `item_id`、`field`（content/reasoning/tool 输出各自的 field 名）、`offset`（该 item 当前已发送位置的 UTF-16 计数）。
- TextTail 的 `content_offset/reasoning_offset` 已维护该坐标，从 `text_tail` 读出随帧带上。
- TextTail flush 节奏参数化：`150ms → THREAD_TEXT_FLUSH_INTERVAL_MS = 80`（常量入 `orchestrator/constants.rs`），flush 边界（`llm_output`/`turn_terminal`/error，现 :226-233）不变。

### 4.5 M1-E：start 应答携带游标 + v2 分流

文件：`api/chat_ws.rs`

- `start` 应答首帧 `stream_started { request_id, turn_id, change_cursor }`（turn_id 来自 `accept_thread_turn` 回执，cursor 取 accept 后的 change_seq）。
- 握手 `WsFeatures` 增加 `change_stream: bool`（`ws_helpers.rs:112-119`）。v2 客户端：stream 任务**不再**逐条 `send_ws_live_event`（保留 drain、approval 转发、goal 续跑、错误帧），推送全部由 feeder 承担；v1 客户端：走现路径不动。

### 4.6 M3：删除后端旧路径

- 删 `drain_until` / `load_overflow_events` / `overflow_version` / `note_overflow` 及 pump 内 event_id 缺口逻辑（`event_stream.rs:400-570` 相关段）。
- 删 `enrich_ws_event_data` 的 `event_id/event_seq` 双写（`ws_helpers.rs:471-495`）与 `request.rs:230-244` 的 `max_stream_event_id` 基线读取。
- `persist_event_on_emit`（恒 false 的死代码，`event_stream.rs:156-165`）删除。

## 5. 前端改造明细

### 5.1 M2-A：新状态层

新增 `frontend/src/realtime/chat/chatThreadState.ts`（数据结构与 reducer 见 §3.4）：
- 复用现有非响应式 + 版本时钟失效基建（`chatRuntimeProjectionInvalidation.ts` 的 24ms 内容 / 150ms 推理 / rAF 结构 / 250ms 后台合帧时钟**原样保留**，它们只负责"何时 bump 版本"，与数据来源解耦）。
- 复用 `chatRuntimeRenderAdapter.ts` 的 materialize 缓存与 `buildBoundedStructuralRevision`（输入换成 items/blocks/tail）。

### 5.2 M2-B：WS 消费收敛

修改 `stores/chatWatcher.ts`、`stores/chatSendActions.ts`、`utils/ws.ts`：

- watch 连接参数只带 `after_change_seq = lastSeq`；重连后 80ms 重启逻辑保留，`after_event_id` 四路 max / `tailEventId` 文本反推（F5）全删。
- watchdog 职责缩减为**活性探测**：status=running 且 N 秒（建议 6s，2 倍心跳）无任何帧 → 强制重连。删除其快照应用职责（不再是写入方）。
- `thread_change` 的 HTTP 回填路径（`chatWatcher.ts:182-310` `mergeThreadTurnItems` + `syncChatRuntimeProjectionFromSnapshot`）删除——feeder 已把 change 推到实时流。
- send 路径：`start` 拿到 `stream_started` 后只做 pending→turn 映射与错误呈现；send 流不再应用任何气泡事件（terminal-tail-smoothing 动画迁移到渲染层或删除）。
- `ws.ts` 解析层为 v2 帧加类型与 `seq` 字段透传；仍保持同步分发，但 reducer 应用是 O(1)（无全表 sort、无评分），高频 delta 的主线程成本可控；delta→渲染仍走时钟合帧。

### 5.3 M2-C：确定性投影与渲染绑定

## 8. 测试方案

**Rust 单测**（`orchestrator` / `api` / `services`）：
- emit 串行化：并发 runner + forwarder emit，断言入队顺序 == change_seq 顺序（现 B2 的回归用例）。
- TextTail：flush 边界、UTF-16 offset 单调、block 不可变、8KB/80ms 触发。
- feeder：cursor 续传页语义、`snapshot_required` 4096 裁剪触发与恢复、退避参数。
- 慢客户端：水位触发 nudge → 重连续传集合 == 缺失集合。

**前端单测**（vitest，reducer 纯函数）：
- 幂等：重复 seq、乱序、revision 回退均不改变状态。
- gapBuffer 溢出走 resume 不走全量重载。
- tail offset 三分支（等于/小于/大于）。
- 快照游标守卫：旧快照拒收。
- 投影：多模型轮次并发到达，气泡分组与顺序确定性（专测 e7c97f30 修过的场景类）。

**E2E 黄金对账**：脚本驱动一次含工具调用、多模型轮次、中途强制断连、超长会话触发裁剪的完整流；对账 `渲染终态 == thread log 重放`。该用例作为 M2-M4 的常驻回归门。

**性能门**：1000 token 连续流 p95 帧到渲染 < 100ms；长任务期间输入框可输入（主线程长任务审计）；会话内存有界（缓冲全有上限）。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| emit 锁跨 DB await 串行化拖慢高吞吐工具流 | DB 写已串行且批量化；压测确认后如仍不足，把 block 写改为锁外带序号队列（保持分配序）——方案预留此退路 |
| ephemeral 尾部 offset 坐标在多 field（content/reasoning/工具输出）间混淆 | 坐标按 `(item_id, field)` 二元组独立维护，TextTail 已是此结构（`thread_log.rs:279-281` 注释的教训直接沿用） |
| feeder 轮询在多实例下延迟劣化 | notify 命中时 0 延迟；未命中走 0.08s base 轮询，与现 watch 一致，不劣化 |
| 前端迁移期双管线并存引入新竞态 | 特性位按会话二选一，同一会话不存在双管线；快照与续传全部有游标守卫 |
| 删除量大引发隐性依赖断裂 | M3 前跑全量回归 + grep 清单核对；`orchestrator.stream()` 内部消费方（§2 非目标清单）在 M1 审计中逐一确认耦合面 |

## 10. 迁移完成后的终态（保持项目干净）

- 后端：一个发射锁、一个 hub、一个 feeder；无 pump 补洞、无 event_id 注入、无静默丢弃。
- 前端：一个数据入口（thread_change/thread_item_tail）、一个 reducer、一个确定性投影；无评分合并、无 watchdog 写入、无 HTTP 回填、无双真值。
- 排序、去重、合并从"启发式"变为"定义"：seq 决定顺序，item_id 决定身份，revision 决定覆盖。
