# 聊天流式管线根治方案

状态：M0–M4 已落地并验收。聊天只使用 durable `change_seq`，不保留 transport 事件恢复、协议灰度或回退路径。统一 session commit API、跨实例轮询恢复、前端 reducer 回归和真实浏览器性能门均已通过。
关联：`docs/线程日志重构方案.md`、`docs/架构评估与演进路线.md`。本方案不再拆分为独立的子智能体执行书，所有后续实施、测试和记录由主智能体完成。

---

## 0. 结论

聊天气泡更新延迟、阻塞、倒序、重复和缺漏的共同根因，是同一会话同时存在传输事件游标与线程日志游标，以及多条前端写入和合并路径。本方案收敛为：**一会话、一份线程日志、一个 durable 游标 `change_seq`、一条确定性渲染路径**。

`thread_log_changes` 是可恢复状态的唯一增量来源；低延迟文本只作为可丢弃的 `thread_item_tail` 提示，永远不能承担最终正确性。聊天 transport `event_id` 只标识当前连接的在线帧，绝不参与重连、去重、排序或状态恢复。

## 1. 现状与实施边界

已确认的问题包括：pump 用 transport `event_id` 请求按 `change_seq` 工作的重放；多 emitter 交错发射；实时流和轮询流并推；满队列时丢失生命周期事件；前端按字符串和评分合并气泡；以及 `after_event_id` 从多处推测。这些问题不能靠增加前端补丁消除。

实现由 `emit_lock`、`ThreadChangeHub`、`thread_item_tail`、`chatThreadState` 与 `chatThreadProjection` 组成完整契约。旧 replay pump、前端事件游标恢复分支和异步文本块持久化队列均已移除。

用户聊天 WebSocket 只使用 durable 路径。`stream_events` 如仍被其他独立产品模块使用，必须经其独立 API 访问；聊天代码不得调用它。

## 2. 不变量

### I1：单一 durable 事实源

一次线程状态提交在**同一个存储事务**中写入状态表和对应的 `thread_log_changes` 行。每行都有会话内严格递增的 `change_seq`，以及可独立应用的不可变 payload。读取历史 change 时不得再以“当前 item/block”补全旧 change。

逻辑操作可产生多行 change，例如接受用户轮次可产生 `turn_upsert` 和 `item_upsert`；每一行都必须完整、可重放、可幂等。

### I2：会话级提交顺序

同一 `session_id` 的 durable 提交经过会话级 commit gate。gate 覆盖“生成变更、事务提交、取得 cursor、发布通知”，不覆盖 WebSocket 写出和长期等待。因而：提交顺序 = `change_seq` 顺序 = feeder 读取和发送 durable 帧的顺序。

`EventEmitter` 私有锁不足以证明此不变量；排队任务、状态更新和任何直接存储写入都必须复用同一个 session commit API/gate。

### I3：durable 与 ephemeral 分工

- `thread_change` 是 durable 帧，携带 `seq=change_seq`，可重放、可幂等、不静默丢弃。
- `thread_item_tail` 是 ephemeral 帧，只承载低延迟文本增量，允许丢弃。其文本必会在后续 durable `text_block` 中得到修复。
- `thread_snapshot_required` 和 `stream_overflow` 是控制帧，不是新的 change，不虚构连续 `seq`。

尾帧携带 `(item_id, field, offset, base_seq)`。每个连接只有一个 writer：它必须先发送至 `base_seq` 的 durable 帧，才可发送该尾帧。客户端也只在 `lastSeq >= base_seq` 后应用尾帧。这样 tail 与 durable 交错不会让尚未出现的 item 接收文本。

### I4：身份、顺序和分组由服务端定义

`item_id` 是稳定渲染 identity，`(turn_id, model_round)` 是助手气泡分组。列表顺序为 `(user_round, model_round, kind_order, created_seq/item_index)`；同类工作流项以持久化 `created_seq` 或 `item_index` 收尾排序。不得使用客户端到达顺序、字符串匹配、评分或 `localeCompare` 推测关系。

### I5：一个游标与原子快照

v2 的 `watch`/`resume` 仅接受 `after_change_seq`。首次加载、显式刷新和 `thread_snapshot_required` 使用快照；快照必须在同一读事务中取得“全部投影数据 + snapshot_cursor”。客户端只接受 `snapshot_cursor >= lastSeq` 的快照。

### I6：有界增量投影

客户端 reducer 是 durable 帧的幂等折叠，加上按 offset 校验的 tail。gap、tail 暂存、投影缓存和 WebSocket 出口队列都必须有明确上限；长文本的已完成块不可重建，只有活动尾块可变。

## 3. 协议与数据流

### 3.1 durable 帧

```jsonc
{
  "event": "thread_change",
  "seq": 1234,
  "change_type": "turn_upsert|item_upsert|text_block|turn_status",
  "turn_id": "turn_x",
  "item_id": "turn_x:text-1",
  "revision": 3,
  "data": { "...": "该 change 在提交时写入的完整不可变 payload" }
}
```

`text_block` 的 payload 必含 `item_id`、`field`、`block_index`、UTF-16 `offset` 和该块完整文本。item/turn 的 payload 同样必须是对应版本的完整投影。`thread_log_changes.payload` 不再存空对象或仅存引用后在 feeder 临时查询最新记录。

```jsonc
{
  "event": "thread_item_tail",
  "item_id": "turn_x:text-1",
  "field": "content",
  "offset": 4096,
  "base_seq": 1234,
  "text": "增量"
}
```

offset 是 JavaScript UTF-16 code unit 计数。文本 tail 状态必须按 `(item_id, field)` 保存；一个全局 `TextTail` 不能安全处理交错的模型轮次。切换 item 前必须提交旧 tail，或直接使用按 item/field 分片且有界的 tail map。

```jsonc
{
  "event": "thread_snapshot_required",
  "required_from_seq": 600,
  "earliest_available_seq": 900
}
```

```jsonc
{
  "event": "stream_overflow",
  "cursor": 1234,
  "resume_recommended": true
}
```

### 3.2 start 的基线游标

`start` 不能返回 accept 后 cursor 并要求客户端从该 cursor 拉取，因为这会跳过刚接受的用户轮次。采用以下契约：

1. 服务端在接受 turn 前读取 `resume_from_seq`；
2. 接受 turn 的事务提交其所有 change；
3. `stream_started` 返回 `turn_id`、`client_message_id`、`resume_from_seq`；
4. feeder 从 `resume_from_seq` 开始读取，客户端按普通 durable 帧取得该 turn；
5. 客户端已有更高 `lastSeq` 时，使用自身 `lastSeq`，但不得高于服务端确认的已应用基线。

可选优化是在 ack 中携带已提交的完整 durable 帧；若采用该优化，ack 必须明确给出 `applied_through_seq`，客户端在写入这些帧后才从该值继续 watch。两种方式只能选一种，初版采用前者以减少双入口。

### 3.3 连接结构

```
模型 / 工具 / 控制代码
        │ session commit API
        ▼
会话 commit gate
        │ 一个事务：状态表 + immutable thread_log_changes
        ▼
提交成功后 publish(session_id, change_seq)
        ├── ThreadChangeHub：同进程快速唤醒
        └── poll：跨实例正确性兜底
        ▼
每连接、每会话 feeder：按 change_seq 分页读取 durable change
        ▼
单连接 writer：durable 优先；base_seq 已发后才写 tail
        ▼
chatThreadState → 增量投影缓存 → 虚拟列表
```

`ThreadChangeHub` 仅是唤醒信号，保存的 cursor 不能当作数据事实；无订阅者的 session entry 必须清理。feeder 每页 200，持续读满页后再等待。它不附带“当前所有文本块”的旁路快照，避免把无游标的数据重新变成第二写入路径。

### 3.4 慢客户端

durable 帧不在模型执行路径中无限等待。连接 writer 达到水位后：停止该 session 订阅、记录已发送 cursor、尽力写出 `stream_overflow`，随后取消 feeder 或关闭连接。控制帧写失败也不影响正确性；客户端通过活性检测重连，并从本地 `lastSeq` 续传。tail 可直接 `try_send` 丢弃。

## 4. 后端改造

### M1-A：统一 session commit API（阻断项）

新增或收敛 `ThreadLogCommitter`：所有 turn、item、状态和文本块更新均通过它提交。API 在 per-session gate 内执行短事务，事务中同时更新状态表、分配 `change_seq`、写 immutable change payload、裁剪 change 索引；提交后才通知 hub。

移除文本块的异步“写块后不发布”路径。若保留后台批处理，其任务必须是按 session 有序的 commit command，并在每次事务成功后发布 receipt；不得绕过 gate，也不得让后续终态先于块提交可见。

### M1-B：tail 分片与落块

将 `TextTail` 改为按 `(item_id, field)` 管理，设置会话内项目数和每项字符数上限。80ms 或 8KB 触发 durable block 提交；轮次结束、错误、取消、item 切换时强制 flush。tail 的 `base_seq` 取其依赖的 item/block durable 基线。

### M1-C：feeder 与 writer

将 `resume_stream_events` 收敛为 v2 feeder：只读 `thread_log_changes` 的 immutable payload，按 `change_seq` 顺序分页写入单连接 writer。`watch`、`resume` 与 `start` 都创建同一类 feeder；同一会话同时存在的旧 feeder 必须被取消或复用，防止双推。

### M1-D：删除旧恢复语义

立即删除聊天 pump 的 `drain_until`、`load_overflow_events`、`overflow_version`、event_id 缺口补拉、`event_id/event_seq` 的 v2 注入，以及 `max_stream_event_id` 作为聊天 start 基线的读取。聊天协议不再保留 v1 分支；其他产品模块若仍使用 `stream_events`，必须通过独立 API 隔离。

## 5. 前端改造

### M2-A：唯一状态入口

`chatThreadState` 接收 `thread_change` 和 `thread_item_tail`，使用 `lastSeq`、有界 gap buffer、revision 和 offset 规则折叠。`stream_started` 只绑定乐观 `client_message_id → turn_id`，不写入气泡内容。watchdog 只检查活性；它不加载或覆盖聊天快照。

gap 上限为 64 帧或 1000ms。超限时只发起一次 `resume after_change_seq=lastSeq`，在该请求完成前抑制重复恢复。收到 snapshot-required 才发起原子快照加载。

### M2-B：确定性投影和增量缓存

`chatThreadProjection` 只读取 `chatThreadState`。删除 coalesce、评分、字符串模式归并及 `sessionMessages` 双真值同步。

每个 `(item_id, field)` 缓存已完成块的拼接文本及活动 tail；block 更新只重算该 item。按 item/turn 的脏标记增量更新投影和结构 revision，避免每个 token 遍历所有 item、排序全部 block 或复制整段历史。渲染仍以 16–33ms 合帧，输入、选择和滚动不在 token 处理路径中执行全量工作。

### M2-C：原子快照

快照 API 返回 `{ turns, items, blocks, cursor }`，服务端保证同一读事务。前端先进行 cursor 守卫再原地替换状态；快照后的 `lastSeq=cursor`。快照失败时停止该 watcher 并报告恢复失败，绝不切换到另一条聊天通信路径。

## 5.1 当前落地状态（2026-10-01）

M0–M4 已完成：接受 turn 前记录 `resume_from_seq`；turn、item、终态、文本块、反馈、冻结系统提示词、排队状态与子智能体消息均经 session commit API 写入 immutable change payload；SQLite 与 PostgreSQL 均支持相同事务语义。提交成功后才发布 hub cursor，重复 no-op 不分配 change 或唤醒订阅者。

聊天 WebSocket 的 `start`、`watch` 与 `resume` 只读取 durable feeder；旧 `after_event_id`、`resume_stream_events`、event-id 补洞、旧 replay pump、协议特性开关和前端事件游标恢复已删除。`stream_events` 只允许聊天之外的独立消费者使用。文本 tail 以 `(item_id, field)` 分片并受 durable `base_seq` 门控，文本块会修复丢失 tail。

子智能体消息使用 `message_id` 生成稳定 item identity，重复投递不会产生重复 durable 项。queue 生命周期使用 `{turn_id}:queue-{queue_id}` 稳定 identity，并经同一 committer 提交。hub 只缩短同进程延迟；feeder 每页 200 的数据库轮询保证跨实例、无 hub 信号时仍能恢复不可变 payload。

已验证：前端 durable reducer 语义 16/16、WS multiplexer 11/11、后端 durable 事件 8 项、feeder 4 项、默认和 PostgreSQL feature 编译检查均通过。浏览器实际 MessengerView 性能门通过：1000 token 流 p95 17.8ms，断线后 durable block 恢复 35.5ms，无超过 50ms 的长任务，输入、滚动和复制持续可用。

## 7. 完成定义

聊天不存在协议灰度、版本切换或 fallback。发生连接中断、gap 或慢客户端控制帧时，停止当前 feeder 并从 reducer 的最后 durable cursor 重建 watch；快照窗口失效时只加载原子快照。

完成后的系统只有：会话 commit gate、change hub、durable feeder、连接 writer、一个前端 reducer 和一个确定性投影。排序由持久序决定，身份由 `item_id` 决定，覆盖由 revision/offset 决定；不再依赖 event_id 推测、评分合并、watchdog 回填或全量轮询覆盖。
