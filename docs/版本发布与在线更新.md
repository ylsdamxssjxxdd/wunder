# 版本发布与在线更新

蛹的在线更新有两个可选源与三类更新对象，用户在「设置 → 常规 → 软件更新」里组合选择（更新源持久化，更新对象为会话级选择）：

- **更新源**：**云端账号**登录舰体后走 `/wunder/cloud/updates/*`，发布物放舰体 `{storage.data_root}/releases/`，适合组织内网或托管舰体的场景；**GitHub** 从公开仓库的 latest release 拉取，有公网即可升级，不依赖舰体登录。
- **更新对象**：**蛹本体**（`desktop`）、**舵机**（`cli`）、**补充包**（`supplement`）。每个对象独立检查、下载与应用；检查会先探测本地版本（蛹取编译期版本、舵机执行 `--version` 探测、补充包读版本标记），再与远端比较，界面显示「本地 → 最新」。

两个源共用同一份 `manifest.json` 格式、同一套 sha256 校验与落盘/应用链路，区别只在传输层（鉴权内网端点 vs 公开 CDN 直链）。未配置 GitHub 仓库的二进制在选择 GitHub 源检查时给出明确提示。

## 版本号

- 唯一来源：`config/app_version.json`。
- 发布前 bump 后运行 `python scripts/sync_app_version.py`，同步 workspace `Cargo.toml` 与各端清单。
- 蛹运行时版本取 `CARGO_PKG_VERSION`（workspace version），登录时随设备注册上报舰体。

## 舰体发布（管理员）

发布不需要重启舰体：把文件放进舰体的 `{storage.data_root}/releases/`（`wunder.yaml` 的 `storage.data_root`，默认 `config/data`）：

```
releases/
  manifest.json
  wunder-desktop-0.2.7-win7-x86.exe
```

`manifest.json` 结构（一次 release 同时携带三类对象的资产）：

```json
{
  "releases": [
    {
      "version": "0.2.7",
      "published_at": 1790000000,
      "assets": [
        {
          "client": "desktop",
          "os": "windows",
          "arch": "x86",
          "file": "wunder-desktop-0.2.7-win7-x86.exe",
          "sha256": "<小写 hex，与包文件一致>",
          "size": 52428800,
          "notes": "本次更新说明（单行）",
          "mandatory": false
        },
        {
          "client": "cli",
          "os": "windows",
          "arch": "x86",
          "file": "wunder-cli-0.2.7-win7-x86.exe",
          "sha256": "<小写 hex>",
          "size": 20971520
        },
        {
          "client": "supplement",
          "os": "windows",
          "arch": "x86",
          "file": "wunder-supplement-0.2.7-win7-x86.zip",
          "sha256": "<小写 hex>",
          "size": 524288000
        }
      ]
    }
  ]
}
```

- `client` 取值：`desktop`（蛹本体）、`cli`（舵机）、`supplement`（补充包），三类对象共用同一清单与端点；`os/arch` 与客户端编译目标常量一致（如 `windows`/`x86`），一个 release 可带多个平台。
- 服务器只下载**清单里登记过**的文件；`file` 必须是单一安全路径段（字母数字与 `._-()`），否则返回 400。
- 蛹与舵机的更新包是各自 exe 单文件；补充包是「设置 → 本地运行时」导入链路接受的 zip/tar.gz（携带 `opt/` 运行树）。
- **补充包版本标记（发布约定）**：包内必须携带 `opt/supplement.json`（`{"version": "0.2.7", "built_at": "..."}`），随导入落到 `{WUNDER_HOME}/opt/supplement.json`，是「本地是否最新」判定的唯一依据；没有标记的旧包在检查时按「本地版本未知」处理，始终给出最新版。
- 打包产物 `*.sha256` / `*.manifest.json`（`packaging/windows/`）可直接换算成上面的 asset 字段，后续可在舰桥加发布上传页自动化。

**GitHub 发布**：在配置了 `WUNDER_UPDATE_GITHUB_REPO` 的仓库创建 release（tag 建议 `v<版本>`，客户端按 `v` 前缀归一比较），上传 `manifest.json` 与各平台包文件即可；release 里缺失 `manifest.json` 或清单登记的包文件都会得到明确错误。

## 接口

**云端源**（均要求登录态，Bearer token，`local_desktop`/`local_cli` scope），定义在引擎 `api::updates` 与 `services::cloud::update`：

- `GET /wunder/cloud/updates/latest?client=&os=&arch=`：返回最新 asset（版本取数值点分比较，预发布后缀按 semver 习惯处理，`v` 前缀归一）；无目录/无匹配返回 `{"data": null}`，旧舰体无此路由时按 404 同样降级为「无更新」。
- `GET /wunder/cloud/updates/download?file=`：流式下发，响应头 `x-wunder-sha256` 携带校验值。

**GitHub 源**（免登录）：客户端请求 `GET api.github.com/repos/{repo}/releases/latest`（稳定版，排除 prerelease/draft），要求该 release 携带 `manifest.json` 资产；拉取清单后按同一规则选取 asset，下载直连 `browser_download_url`（自动跟随 CDN 重定向）。仓库标识在构建期通过环境变量注入：

```
WUNDER_UPDATE_GITHUB_REPO=<owner>/<name>
```

未注入时 GitHub 源不可用（检查时报「GitHub 更新源未配置」）。注意 GitHub API 免登录限额为每 IP 每小时 60 次查询，手动检查足够；客户端已带 User-Agent（GitHub 必需），并遵循系统代理环境变量。

## 蛹侧流程（`crates/wunder-desktop/native_update.rs`）

1. **检查**：按所选对象取本地版本（蛹=编译期版本；舵机=对程序目录旁的 `wunder-cli` 执行 `--version` 探测，3 秒兜底超时，未安装按「未安装」呈现；补充包=读 `{WUNDER_HOME}/opt/supplement.json`），再走云服务 `authed_send`（401 自动续期）或 GitHub 清单比对，进入 `available` 或 `up_to_date`。
2. **下载**：无总超时流式写入 `{WUNDER_HOME}/updates/staging/package.part`（60 秒逐块空闲看门狗），边下边算 sha256，校验通过后按清单文件名落盘并写 `meta.json`（含对象标识）；大小与哈希任一不符即删除重报失败。同一时刻只保留一个待应用包，切换对象重新下载会覆盖。
3. **应用（按对象分派）**：
   - **蛹本体**：把 staging 包复制到 exe 同目录（同卷 rename 的前置，复制后再次校验哈希）→ `wunder-desktop.exe` rename 为 `.old` → `.new` rename 回原名 → 带 `WUNDER_UPDATE_RELAUNCH=1` 环境变量启动新 exe → 前端立即 `request_exit()`。新进程在 10 秒内重试单实例认领，完成交接。
   - **舵机**：同一套同卷改名轮换作用于程序目录旁的 `wunder-cli`，**不重启进程**——正在运行的 TUI 持旧文件继续工作，下次启动即新版本；程序目录没有舵机时等价于安装最新版到该目录。
   - **补充包**：把 staging 压缩包直接交给既有导入管线（严格校验、流式解压、覆盖合并到 `{WUNDER_HOME}/opt/`、进程内热刷新工具环境），**立即生效、无需重启**；完成后显示导入摘要。
4. **恢复**：启动时清理蛹与舵机的 `.old`/`.new` 残留；staging 里待应用的包跨重启保留——蛹本体仅在版本高于当前运行时恢复，舵机/补充包只要有包即恢复为「待应用」，否则清空 staging。

## 必做验证

- Win7 x86 真机完整跑一轮检查 → 下载 → 重启升级，确认 rename 轮换、单实例交接与杀软共存表现。
- 舵机对象：TUI 运行中执行「应用更新」，确认旧会话不受影响、下次启动为新版本；未安装舵机时走安装分支。
- 补充包对象：下载 → 导入后「设置 → 本地运行时」工具路径已刷新、无需重启；旧格式包（无 `opt/supplement.json`）检查时按本地版本未知处理。
- 中断路径：下载中断（重启后可继续应用已完成的包）、应用中途被杀（`.old` 可手动恢复）。
- 旧舰体（无更新路由）与新舰体（无发布目录）两种降级显示。
- GitHub 源：正常发布升级、release 缺 manifest.json、未配置仓库三个分支。
