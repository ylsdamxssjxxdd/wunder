# 版本发布与在线更新

桌面版的在线更新有一个可选源；用户在「设置 → 常规 → 软件更新」里选定更新源后，点「检查更新」会自动检测全部有新版本的组件，点「更新」一键依次下载并应用（更新源持久化，更新对象由检查结果自动决定，无需手动选择）：

- **更新源**：**云端账号**登录服务端后走 `/wunder/cloud/updates/*`，发布物放服务端 `{storage.data_root}/releases/`，适合组织内网或托管服务端的场景；**GitHub** 从公开仓库的 latest release 拉取，有公网即可升级，不依赖服务端登录。
- **更新对象**：检查会遍历**桌面版本体**（`desktop`）、**命令行**（`cli`）、**补充包**（`supplement`），先探测本地版本（桌面版取编译期版本、命令行执行 `--version` 探测、补充包读版本标记），再与远端比较，界面显示「本地 → 最新」；一键更新把所有检测到新版本的组件依次下载并应用（桌面版本体排在最后，应用后需重启生效）。

两个源共用同一份 `manifest.json` 格式、同一套 sha256 校验与落盘/应用链路，区别只在传输层（鉴权内网端点 vs 公开 CDN 直链）。未配置 GitHub 仓库的二进制在选择 GitHub 源检查时给出明确提示。

## 版本号

- 唯一来源：`config/app_version.json`。
- 发布前 bump 后运行 `python scripts/sync_app_version.py`，同步 workspace `Cargo.toml` 与各端清单。
- 桌面版运行时版本取 `CARGO_PKG_VERSION`（workspace version），登录时随设备注册上报服务端。

## 服务端发布（管理员）

发布不需要重启服务端：把文件放进服务端的 `{storage.data_root}/releases/`（`wunder.yaml` 的 `storage.data_root`，默认 `config/data`）：

```
releases/
  manifest.json
  wunder-desktop-0.2.7-win7-x86.exe
```

`manifest.json` 结构（一次 release 同时携带三类对象的资产）：

```json
{
  "releases": [
    {
      "version": "0.2.7",
      "published_at": 1790000000,
      "assets": [
        {
          "client": "desktop",
          "os": "windows",
          "arch": "x86",
          "file": "wunder-desktop-0.2.7-win7-x86.exe",
          "sha256": "<小写 hex，与包文件一致>",
          "size": 52428800,
          "notes": "本次更新说明（单行）",
          "mandatory": false
        },
        {
          "client": "cli",
          "os": "windows",
          "arch": "x86",
          "file": "wunder-cli-0.2.7-win7-x86.exe",
          "sha256": "<小写 hex>",
          "size": 20971520
        },
        {
          "client": "supplement",
          "os": "windows",
          "arch": "x86",
          "file": "wunder-supplement-0.2.7-win7-x86.zip",
          "sha256": "<小写 hex>",
          "size": 524288000
        }
      ]
    }
  ]
}
```

- `client` 取值：`desktop`（桌面版本体）、`cli`（命令行）、`supplement`（补充包）、`android`（安卓版 APK），共用同一清单与端点；`os/arch` 与客户端编译目标常量一致（如 `windows`/`x86`、安卓 `android`/`aarch64`），一个 release 可带多个平台。
- 服务器只下载**清单里登记过**的文件；`file` 必须是单一安全路径段（字母数字与 `._-()`），否则返回 400。
- 桌面版与命令行的更新包是各自 exe 单文件；补充包是「设置 → 本地运行时」导入链路接受的 zip/tar.gz（携带 `opt/` 运行树）。
- **补充包版本标记（发布约定）**：包内必须携带 `opt/supplement.json`（`{"version": "0.2.7", "built_at": "..."}`），随导入落到 `{WUNDER_HOME}/opt/supplement.json`，是「本地是否最新」判定的唯一依据；没有标记的旧包在检查时按「本地版本未知」处理，始终给出最新版。
- 打包产物 `*.sha256` / `*.manifest.json`（`packaging/windows/`）可直接换算成上面的 asset 字段，后续可在管理端加发布上传页自动化。

**GitHub 发布**：在配置了 `WUNDER_UPDATE_GITHUB_REPO` 的仓库创建 release（tag 建议 `v<版本>`，客户端按 `v` 前缀归一比较），上传 `manifest.json` 与各平台包文件即可；release 里缺失 `manifest.json` 或清单登记的包文件都会得到明确错误。

## 接口

**云端源**（均要求登录态，Bearer token，`local_desktop`/`local_cli` scope），定义在引擎 `api::updates` 与 `services::cloud::update`：

- `GET /wunder/cloud/updates/latest?client=&os=&arch=`：返回最新 asset（版本取数值点分比较，预发布后缀按 semver 习惯处理，`v` 前缀归一）；无目录/无匹配返回 `{"data": null}`，旧服务端无此路由时按 404 同样降级为「无更新」。
- `GET /wunder/cloud/updates/download?file=`：流式下发，响应头 `x-wunder-sha256` 携带校验值。

**GitHub 源**（免登录）：客户端请求 `GET api.github.com/repos/{repo}/releases/latest`（稳定版，排除 prerelease/draft），要求该 release 携带 `manifest.json` 资产；拉取清单后按同一规则选取 asset，下载直连 `browser_download_url`（自动跟随 CDN 重定向）。仓库标识在构建期通过环境变量注入：

```
WUNDER_UPDATE_GITHUB_REPO=<owner>/<name>
```

未注入时 GitHub 源不可用（检查时报「GitHub 更新源未配置」）。注意 GitHub API 免登录限额为每 IP 每小时 60 次查询，手动检查足够；客户端已带 User-Agent（GitHub 必需），并遵循系统代理环境变量。

## 桌面版侧流程（`crates/wunder-desktop/native_update.rs`）

1. **检查**：按所选对象取本地版本（桌面版=编译期版本；命令行=对程序目录旁的 `wunder-cli` 执行 `--version` 探测，3 秒兜底超时，未安装按「未安装」呈现；补充包=读 `{WUNDER_HOME}/opt/supplement.json`），再走云服务 `authed_send`（401 自动续期）或 GitHub 清单比对，进入 `available` 或 `up_to_date`。
2. **下载**：无总超时流式写入 `{WUNDER_HOME}/updates/staging/package.part`（60 秒逐块空闲看门狗），边下边算 sha256，校验通过后按清单文件名落盘并写 `meta.json`（含对象标识）；大小与哈希任一不符即删除重报失败。同一时刻只保留一个待应用包，切换对象重新下载会覆盖。
3. **应用（按对象分派）**：
   - **桌面版本体**：把 staging 包复制到 exe 同目录（同卷 rename 的前置，复制后再次校验哈希）→ `wunder-desktop.exe` rename 为 `.old` → `.new` rename 回原名 → 带 `WUNDER_UPDATE_RELAUNCH=1` 环境变量启动新 exe → 前端立即 `request_exit()`。新进程在 10 秒内重试单实例认领，完成交接。
   - **命令行**：同一套同卷改名轮换作用于程序目录旁的 `wunder-cli`，**不重启进程**——正在运行的 TUI 持旧文件继续工作，下次启动即新版本；程序目录没有命令行时等价于安装最新版到该目录。
   - **补充包**：把 staging 压缩包直接交给既有导入管线（严格校验、流式解压、覆盖合并到 `{WUNDER_HOME}/opt/`、进程内热刷新工具环境），**立即生效、无需重启**；完成后显示导入摘要。
4. **恢复**：启动时清理桌面版与命令行的 `.old`/`.new` 残留；staging 里待应用的包跨重启保留——桌面版本体仅在版本高于当前运行时恢复，命令行/补充包只要有包即恢复为「待应用」，否则清空 staging。

## 安卓版侧流程（`crates/wunder-android/src/update.rs`）

安卓版在「设置 → 帮助与关于 → 在线更新」里同样可在**云端**与 **GitHub** 两个源之间切换，选择与桌面版一样持久化在偏好设置的 `update_source`：

1. **云端源**：登录云端账号后查询 `client=android&os=android&arch=<aarch64|x86_64>` 的清单资产，下载走鉴权端点；未登录时检查直接提示「请先登录云端账号」。
2. **GitHub 源**：不需要 `manifest.json`，按 `wunder-android-<版本>-<arm64|x64>.apk` 文件名识别版本，校验 GitHub asset digest 的 sha256；夜间构建同版本但发布时间晚于本机安装时间也视为更新。
3. **下载与安装**：APK 流式写入应用缓存并校验大小与 sha256，然后交给系统 PackageInstaller；Java 侧再校验包名、签名证书与 versionCode，未知来源授权、取消与失败都有回退提示。安卓版不支持桌面版的 exe 改名轮换，安装由系统完成。
4. **本地覆盖**：`{WUNDER_HOME}/config/android-update.json`（`version/notes/url/sha256/size/published_at`）优先于 GitHub 源，供自托管与离线测试；云端源不受该文件影响。

## 必做验证

- Win7 x86 真机完整跑一轮检查 → 下载 → 重启升级，确认 rename 轮换、单实例交接与杀软共存表现。
- 命令行对象：TUI 运行中执行「应用更新」，确认旧会话不受影响、下次启动为新版本；未安装命令行时走安装分支。
- 补充包对象：下载 → 导入后「设置 → 本地运行时」工具路径已刷新、无需重启；旧格式包（无 `opt/supplement.json`）检查时按本地版本未知处理。
- 中断路径：下载中断（重启后可继续应用已完成的包）、应用中途被杀（`.old` 可手动恢复）。
- 旧服务端（无更新路由）与新服务端（无发布目录）两种降级显示。
- GitHub 源：正常发布升级、release 缺 manifest.json、未配置仓库三个分支。
