# wunder 心舰简介

> 前端是温暖的蜂巢，后端是庞大的飞船。

wunder（心舰）是一个智能体调度系统。你把目标交给它，它把目标拆成任务，在带工具的执行环境里一步步做完，最后交付结果。

它和常见的问答式 AI 不是一类东西。问答式 AI 的产出是一段文字；wunder 的产出是做完的事：写进工作区的文件、执行过的命令、改好的代码、发出去的消息、设好的定时任务。过程有事件流可以看，高风险动作有审批把着，断了线能恢复现场。

## 核心概念

```text
心舰
├─ 用户
│  └─ 蜂群
│     └─ 智能体
│        └─ 线程
└─ ...
```

- 用户：资源与数据的归属主体，相互隔离。
- 蜂群：围绕一个目标组织起来的一组智能体。母蜂主持协作，把任务拆解后派给工蜂，工蜂的结果归并回母蜂。
- 智能体：具体干活的角色，有自己的模型配置、工具集、知识库和长期记忆。
- 线程：智能体里连续的执行上下文，一次会话的全过程都发生在线程里。

线程内部按两级计量：用户每发一条消息记 1 个用户轮次；模型每调一次 API、执行一批工具或给出最终回复，记 1 个模型轮次。一个用户轮次里往往有很多个模型轮次，工具循环就发生在这里。

## 它怎么干活

1. 目标进入线程。system prompt 在首次确定后冻结，长期记忆以索引形式注入一次，之后不再改动，以保住模型的提示词缓存。
2. orchestrator 组装上下文，发起模型调用。
3. 模型返回工具调用时，运行时解析参数、按需请求审批、执行工具，把裁剪后的结果喂回模型，进入下一轮循环。文件、命令、浏览器、桌面控制、网页抓取、外部渠道，全部走这一条治理链路。
4. 全程以流式事件对外发布。网页端、桌面端都只是这些事件的投影，断线后靠快照和补拉恢复。
5. 上下文快满时，先对更旧的可重读工具结果做本地微压缩，还不够再生成交接摘要、重建历史。长会话因此可以一直工作下去。
6. 任务完成或用户停止后，线程状态落库，刷新页面或重新打开都能原样恢复。

## 三种形态

**wunder-server** 是核心。多用户、多租户、智能体应用构建与发布、网关统一接入，内置工具链、知识库和长期记忆，PostgreSQL 存储。日常开发的主战场。

**wunder-desktop**（开发中）是个人用户的主推形态。Rust + Slint 原生界面，启动后在同一进程内直接调用后端，不经本机 HTTP。SQLite 存储，兼容目标是 Windows 7 32 位。

**wunder-cli**（开发中）是命令行形态，复用 runtime 内核，用于脚本化和自动化。

三种形态共享同一套内核：线程、工具、存储抽象、实时事件和权限语义是同一份代码，差异只在接入层。desktop 和 cli 还没有覆盖 server 的全部能力，想完整体验建议从 server 入手。

## 设计上的几条硬规则

- 对开发者来说一切都是接口，对大模型来说一切皆工具。
- 线程 system prompt 一旦确定就冻结；长期记忆只在初始化时注入一次，中途不改写。
- 前端不是状态的真相源。后端发事件流，前端消费投影；乐观更新的部分最终要被事件回压校正。
- 所有外部能力都是工具，走统一的审批、超时、预算和结果裁剪，不靠提示词自觉。
- server 用 PostgreSQL，desktop 用 SQLite，共享同一个存储抽象。
- 单写者原则：一个事件目标只有一条发布路径，一个线程同一时刻只有一个执行者。

## 能力概况

- 多智能体协作：蜂群（调度已有智能体）与子智能体（临时派生）两种模式
- 工具链：文件、命令、浏览器、桌面控制、网页搜索与抓取、LSP、PTC 等，MCP 与 Skills 可扩展
- 定时任务、网关与多渠道接入（飞书、微信、QQ、Telegram 等）
- 长会话：上下文压缩、长期记忆、额度与用量计量
- 知识库与向量检索
