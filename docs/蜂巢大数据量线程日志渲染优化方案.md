# 蜂巢大数据量线程日志渲染优化方案

> 版本：v3，2026-10-12，按当前重构后的代码重新审计。
> 状态：方案重写完成，业务实现待执行；本文延迟、内存和流畅度数值是验收目标，尚未实现或通过真实端到端压测。
> 对象：蜂巢（云端 AI 工作台，frontend/）聊天页、轨迹视图及舰体提供的读取、存储、实时投影能力。
> 原则：优先性能，直接替换不合适的契约与架构，不保留两套聊天渲染来源、旧快照恢复或功能开关回退路径。保留完整原始消息与日志的可访问性。
> 证据与复现：[本轮诊断报告](性能基线/2026-10-12-frontend-thread-read-diagnosis.md)。

## 1. 决策：让打开页面的成本与线程总量脱钩

当前的问题不能继续靠增加超时、调小快照参数、分片应用快照解决。重构后仍将执行日志窗口作为聊天与轨迹的共同输入，再在浏览器重建展示模型。读取条数虽受限，数据库扫描、单条 payload 大小、整窗投影、状态替换与恢复仍没有正确边界。

目标是：无论线程包含几百条还是数百万条执行记录，打开聊天页都只读取最近一屏所需的用户轮次与答案；打开轨迹只读取固定数量的时间桶和台账摘要。完整正文、思考、工具输入输出、中间模型轮次在用户查看时分页读取。持续输出只更新活动文本块和受影响行。

采用以下统一架构：

1. **执行记录继续作为事实源，新增事务内增量维护的展示读模型。** 聊天、轨迹、正文分别读取小型结构，不读取原始日志 payload 来现场归约。
2. **聊天首屏只有一个必要请求。** 返回线程元信息、最近轮次展示页、确定的空态、实时基线。事件回放、工作过程、账号活动、文件列表不进入首屏等待链。
3. **线程页面状态与连接状态分别建模。** 已显示内容在请求失败、watch 重连、恢复与缓存淘汰期间保留；欢迎页只能来自服务端确认的真实空线程。
4. **窗口基线与历史分页分别定义。** 不再把截断的日志窗口当整线程完整快照；恢复只替换当前展示范围，历史页不推进实时游标。
5. **轨迹采用服务端多级摘要、分页台账、Canvas 时间轴。** 摘要不丢失失败和运行中事件，详细记录可继续钻取。
6. **用真实入口验收。** 以点击到有意义内容实际绘制、输入响应、长任务、SQL 扫描量、未压缩字节、恢复正确性作为门禁。

复杂度约定：设 N 为线程总执行记录数、P 为单页记录数、V 为可见行数、B 为当前读取或显示的文本字节数、D 为本批次改变的记录数。

| 操作 | 允许的工作量 | 明确禁止 |
| --- | --- | --- |
| 聊天首屏与历史页 | 索引定位 + O(P + B) | 扫描 N、计算总数、回放工作流 |
| 轨迹首屏 | 有界摘要桶 + O(P) 台账 | 加载整窗 payload 后构建所有 cell/span |
| 文本增量 | O(D + 新增字节) | 拼接全部答案、扫描所有历史 item、重算所有轮次 |
| 滚动、缩放、悬停 | O(log P + V) 或固定像素桶预算 | 先全量 map/filter 再采样 |
| 重连恢复 | 当前页基线 + 有界增量 | 重新加载全部历史、先清空当前展示 |

索引定位通常为 O(log N)；“与总量脱钩”指禁止随线程总量线性增长的读取、归约和对象分配，并非宣称数据库访问严格为 O(1)。

## 2. 本轮复核：哪些已做，哪些仍然错

### 2.1 已落地的能力不能再次当作缺陷

代码已恢复请求取消与部分陈旧判定，已经有 transcript 兜底、快照分片 planner、轮次缓存、轨迹 shallowRef/markRaw、指针帧级节流、2000 个 span 的 DOM 限额、工作流请求 20000 条总上限、gzip、侧栏可见行状态计算与延后排序持久化。

PostgreSQL 快照读取也已经使用 REPEATABLE READ。本文不再重复 v2 的“无 LIMIT、取消恒关闭、没有压缩、轨迹深代理、折叠算法仍为二次方”等历史结论。已经有效的侧栏虚拟化、Markdown Worker 与纯文本保底继续复用。

### 2.2 仍然存在的瓶颈与正确性问题

| 编号 | 当前事实 | 为什么影响秒开或稳定性 |
| --- | --- | --- |
| R1 | loadSessionDetail 的 Promise.all 仍等待 transcript、events、workflow events、snapshot；快照 deadline 为 8 秒 | 最慢请求决定聊天内容何时发布。正常拿到 transcript 也不能立即出首屏 |
| R2 | 默认快照仍有 200 个 turn、20000 个 item、40000 个 block；调用方可放大到 2000/200000/400000 | 条数上限过大，且单条 payload/文本无字节预算；远超一屏所需 |
| R3 | item 按最新 created_seq 截断；turn 的输入在 payload.content，applySnapshotTurn 只读顶层 entry.content | 截掉较早的用户 item 后 userContent=null；投影跳过该轮。非空日志窗口可能产生零聊天行 |
| R4 | 兜底将 registry entry 存在解释为窗口可用；startSessionWatcher 会先创建空 entry | 有 transcript 的页面可从兜底行变为空行，再显示欢迎卡。entry 存在没有证明基线完成 |
| R5 | 分片恢复直接清空在线 state，随后分批填充；中断不回滚已清空的内容 | 页面可观察到半成品。保留旧 cursor 不代表保留旧数据；WS 与分片也缺少独立构建/提交边界 |
| R6 | 首次打开仍调用同步 hydrateChatThreadRuntime；Worker 只 flatten/slice，原始 JSON 已在主线程解析，对象又双向 structured clone | “有 Worker”并未让首屏 reducer、投影、解析全部离开主线程；队列也未设条数/字节硬限 |
| R7 | 快照 SQL 的 turn_id IN (...) 与现有 root_turn_id 索引不匹配，最后按 created_seq 全局排序 | LIMIT 限制输出量，不能限制候选扫描量与临时排序；同一小页随线程总量变慢 |
| R8 | slot 缓存命中前仍扫描所有 turn/item、分桶、排序、为每轮生成包含完整文本的字符串 signature | 对象身份保持稳定，CPU 与临时字符串仍按历史规模增长；一个 token 也可能触发整窗扫描 |
| R9 | 轨迹仍请求同一个原始快照，主线程串联 layout、flatten、filter、collapse、group、prefix、timeline；台账保留全文工具详情 | DOM 虚拟化没有减少加载和建模的工作；搜索会触发所有 lazy 文本、拼接与转小写 |
| R10 | projectedSpans 先为所有 span 分配坐标对象再 filter/采样；选区使用 timelineFocusIndexes 再次派生时间轴 | 限制 2000 个 DOM 和每帧调用一次，仍然可能是每帧扫描数万记录 |
| R11 | thread_snapshot_required 失败仍通过 onSnapshotRequired: () => controller.abort() 停掉 watcher；恢复 loader 没有接收外层 signal | 请求去重存在，但失败恢复生命周期未闭合；切换/淘汰的取消不能完整传递到网络请求 |
| R12 | /thread-log/turns 每页附带两次 COUNT(*)；session handler 内仍直接同步调用历史读取和活动正文补水 | 把原始分页端点直接接首屏仍会扫描总量或阻塞 async 执行线程 |
| R13 | 截断 items/blocks 后仍推进全局 cursor；item_total 实际是返回页 item 数，省略 items_truncated/blocks_truncated 的分别描述 | 全局实时进度与内容覆盖被混用，已遗漏的数据可能不会再次补回，空态无法可信判定 |
| R14 | 旧性能报告主要验证指标注册，手工记录固定耗时；heavy-history harness 测 400 条自造消息，容许 6 秒加载和 220ms 帧间隔 | 不能证明真实大线程打开链路通过，也守不住用户要求的秒开 |

轨迹默认 45 秒超时与聊天 8 秒快照兜底都是失败边界，不能当首屏设计。gzip 可以缩小网络传输，不能消除 SQL 扫描、JSON 解析、解压后的对象量和浏览器计算。

### 2.3 欢迎页回退的可复现触发链

~~~text
items 最新优先截断 → 用户 item 被排除
turn.payload.content 未进入 userContent → 投影跳过非空轮次
runtime 存在 → transcript 兜底停用
轮次行数量为 0 + historyLoading=false → 欢迎卡
~~~

还有独立触发路径：快照失败后 transcript 兜底已经可见，watcher 为恢复创建空 runtime，兜底随即被关掉。分片恢复清空在线 Map 则进一步扩大“有内容后变空”的窗口。

本轮通过真实 reducer、projection、materializer、兜底函数的匿名诊断确认：

| 诊断 | 结果 |
| --- | --- |
| 4 个 turn、164 个 item 的完整快照 | 4 个聊天 slot |
| 相同 turn，仅保留最新 20 个 item | 0 个聊天 slot，但 cursor 已推进到 200 |
| runtime 不存在，transcript 含一组用户/助手消息 | 显示 1 个兜底轮次 |
| 只创建空 runtime，transcript 保持原样 | 变为零行，欢迎卡判定为 true |
| 旧状态恢复到一半后取消 | 旧 4 轮/164 item 变为 1 轮/0 item，旧 cursor 仍在 |

这是代码级触发链复现；本轮没有访问真实用户线程，也没有声称已逐帧复现用户机器上的全部症状。路由、权限或线程删除引发的导航变化，仍需真实浏览器测试分别识别，不能与欢迎卡条件混为同一原因。

### 2.4 SQL 与“缓存命中”也未做到有界

在保留相关索引、匿名数据的内存 SQLite 诊断中，固定选择 2 个 turn、返回 20 个 item：

| 总 item 数 | 查询三次中位数 |
| --- | ---: |
| 20000 | 2.72ms |
| 200000 | 24.18ms |
| 500000 | 58.57ms |

EXPLAIN QUERY PLAN 显示 item 只按 (user_id, session_id) 定位，之后仍需过滤与临时 B-tree 排序。该结果证明当前查询形状会随总量增长，不代表线上数据库延迟；生产查询计划与 PostgreSQL 仍要在实现阶段复测。

匿名 Node 投影诊断，状态完全不变且缓存命中，20 轮/2020 item 中位数 5.90ms，200 轮/20200 item 中位数 50.49ms。字符串签名比较仍然消耗整窗 CPU，不能作为真正增量的实现。

## 3. 秒开与流畅度的硬预算

以同一发布构建、固定浏览器和数据库、普通办公电脑测试档为基准，同时记录 4 倍 CPU 降速的压力档。参考网络为 RTT ≤ 80ms、吞吐 ≥ 10Mbps。首次打开测试使用冷客户端缓存；服务首次启动、冷磁盘读取另建档，不与热 DB 结果混用。

规模至少覆盖 1000 条、10 万条、100 万条、约 500 万条执行记录，以及“用户轮次少、单轮步骤极多”和超长正文。所有以下目标都要记录 p50/p95/p99，不能只报最优一次。

| 指标 | 门禁目标 | 测量口径 |
| --- | --- | --- |
| 点击到目标线程框架与可用输入框 | p95 ≤ 100ms | 区分选择后的首帧；不等待请求 |
| 聊天冷客户端首屏 | p50 ≤ 500ms，p95 ≤ 1000ms | 已绘制目标线程实际用户输入与答案预览/真实运行状态，骨架不算 |
| 聊天同进程缓存重开 | p95 ≤ 150ms | 同一线程已有展示页，含 paint |
| 轨迹首屏 | p95 ≤ 1000ms | 最新台账摘要已绘制；摘要时间轴完成或明确标注仍在刷新 |
| 首屏期间输入反馈 | p95 ≤ 50ms，p99 ≤ 100ms | 键入到输入框绘制，滚动与输出并存 |
| 首屏主线程单任务 | 不出现 > 50ms 的产品长任务 | CPU 压力档单独报告，不隐藏 JSON/clone/layout 成本 |
| 常态增量发布预算 | 每批主线程 JS p95 ≤ 8ms | 按 16–33ms 合并；只投影变化与可见块 |
| 滚动/缩放/拖动 | p95 帧间隔 ≤ 33ms，p99 ≤ 50ms | 含连续操作与自动输出 |
| 首屏服务端处理 | p95 ≤ 250ms | 鉴权后队列、DB、构造、序列化全部计入 |
| 首屏必要请求 | 聊天 1 个；轨迹 1 个 bootstrap | 各自目标页面的请求；共享 WS 不作为 HTTP 屏障 |
| 首屏未压缩 JSON | 聊天 ≤ 128KiB；轨迹 ≤ 192KiB | 最终序列化后的 UTF-8 字节，压缩前计数 |
| 每次详情响应 | ≤ 128KiB | 字段与范围分页，无完整大 item 返回 |
| 浏览器展示数据缓存 | 全局逻辑预算 ≤ 48MiB | 活跃页、后台页、正文、Worker、队列分别计账；不以 entry 数代替字节 |
| 单页聊天/轨迹的增量 JS heap | ≤ 64MiB | 独立真实浏览器 heap 测量，包含对象放大；避免拿逻辑字节冒充 heap |
| 缓存与内存随总量变化 | 100 万→500 万，固定操作时不随 N 线性增长 | 同环境、同可见页比较 |
| 内容回退欢迎页、错误串线程 | 0 次 | 重连、取消、页切换、并发写入与长时间观察 |
| 游标、文本、权限错误 | 0 次 | 无跳字、重复字、越权与历史页覆盖活动尾部 |

参考前端首屏分配：JSON parse ≤ 6ms、状态提交 ≤ 8ms、Vue 更新/布局约一帧。超预算时减小页/字段和拆分块；禁止通过延长 deadline 通过验收。

“全量完整长答案首次打开也在一秒内加载完”不是有限带宽下可满足的要求。秒开必须显示真实正文片段、完整性标志与可继续读取的定位，同时让完整原文可分页查看、完整复制或导出。预览、分段展示不会改写原文。

## 4. 后端：将展示读取从执行日志中抽离

### 4.1 建立按写入增量维护的读模型

在 wunder-core 声明强类型读取契约，在 wunder-runtime 维护投影与 SQLite/PostgreSQL 实现。浏览器不再将原始 turns/items/blocks 作为页面状态。

建议新增以下职责清晰的结构；最终表名可按仓库规范调整，字段职责与预算不得省略：

| 读模型 | 粒度与核心字段 | 不进入该模型的内容 |
| --- | --- | --- |
| thread_view_heads | 每线程：epoch、view_seq、真实 root/user 轮次计数、latest_round、状态、摘要代次、投影状态 | 原始正文、提示词、完整工具 JSON |
| thread_chat_rows | 每 root 用户轮次：稳定 id/round、row_revision、用户与答案有限预览/长度、正文引用、当前执行状态、少量工作过程计数 | 数千个模型步骤数组、全部 reasoning、工作流事件 |
| thread_trajectory_rows | 每可展示 item：稳定 id/root、step 序号、类别、状态、开始结束时间、有限摘要、detail 引用、行版本 | args/result/schema 全文与上下文原文 |
| thread_body_chunks | 每正文版本、字段、chunk：连续定位、有限文本块、长度、校验/版本 | 整条答案作为一次响应 |
| thread_trajectory_tiles | 每线程/层级/桶：记录数、错误数、活跃状态、类别计数、时间范围、聚合统计 | 保存所有 span id 的无界数组 |
| thread_view_changes | 最近有界展示变更：view_seq、对象 id、版本、有限 patch/失效信息 | 原始大 item payload 副本 |

聊天行固定代表一个 root 用户轮次。用户输入在接受时直接建立该行，目标延续执行更新原行状态；队列仍有独立状态与操作入口，不凭“没有用户 item”隐藏已经有数据的线程。

最新答案的选取与中间工作过程的展示须与现有“一轮用户输入对应一组用户/助手气泡”规则一致。这里预先维护结果选择与计数，不能在首屏把中间模型输出全部拼接为答案，也不能每个 token 重读所有模型轮次。

### 4.2 写入路径与一致性

1. 接受输入、item 创建/修订、正文块提交、terminal 状态、反馈、队列与子智能体卡片变化，都在现有持久化写事务中同步更新**受影响的标量投影与展示变更**。
2. 提交同时推进该线程 view_seq。序号按展示变更定义，所有消费者使用同一含义；不得沿用原始 change_seq 却过滤帧导致客户端出现人为 gap。
3. row_revision 由后端递增，客户端比较版本。禁止用全量文本、JSON.stringify 或长字符串哈希判断某轮是否变化。
4. 正文按不超过 8KiB UTF-8 文本块追加。内存中的活动小缓冲也设硬限。完成时提交活动尾块，保留内容/版本/段索引；不能每个 token 重写整段长答案或重算全部正文摘要。
5. 工具 args/result/schema、原始 prompt 等大字段在写入时存入正文/详情存储，并建立有限引用。页面查询不选择、解码这些大字段；只在返回后删除字段的实现仍不合格。
6. 用户输入为空但包含附件也必须建立用户轮次行，附件只提供有限元信息和引用；不将 base64 混入 bootstrap。
7. 投影写入失败则事务失败，不能留下“head 宣称已完成而行缺失”的半成功状态。

正文版本采用小型 manifest 引用已经封存的块；追加或修订只增加新块/变更引用，不能为每个版本复制全部正文。manifest 本身按固定大小分层或分页，首次读取也不能返回全部 chunk id。UTF-8 字节预算在完整字符边界切块；协议另外固定文本定位单位，不能混用字节、Unicode 字符数和 JavaScript UTF-16 offset。Markdown 跨块的代码围栏等上下文以有限解析状态传递，无法完成时显示可读文本，不为补全富文本读取全部前文。

事实日志、模型上下文、系统提示词保持独立职责。**线程 system prompt 仍在首次确定后冻结，长期记忆只在初始化注入一次**；展示重建、游标恢复与摘要读取不得改写它们。

### 4.3 时间轴聚合不能以延后扫描代替增量

每个新增/变化 span 更新有限个多级桶，旧值修订使用 before/after 差量。计数、错误数、类别数、耗时和、极值或可撤销摘要在有限层数内维护；不得每次改动对线程执行 GROUP BY。

极值与时长重叠修订等不适合简单相减的量，采用小桶重算并逐层合并，或可撤销的聚合结构。每次只允许固定记录数/字节的桶内读取；超过预算标记该 tile dirty，后台有界更新。实时状态来自 head，不能因概览暂时 dirty 而显示线程为空。

sequence 轴使用稳定全局步骤序号；time 轴按记录开始时间分桶，桶同时记录最大结束时间，跨桶长 span 有明确覆盖摘要。duration/actual 模式保留当前语义：如压缩空闲时间，需维护可分页的活动区间与前缀度量；禁止浏览器拉全部 span 后排序构造压缩轴。历史修订只使相关摘要代次失效，后台分段修复，不在前台全局重编号。某模式摘要尚未就绪时，在已有轨迹页内显示构建状态并允许已就绪轴和台账使用。

### 4.4 索引、查询计划与执行预算

- 聊天页按 (user_id, session_id, round DESC, root_turn_id) seek，查询有限列，利用 limit + 1 判断 has_more。root 不被 item 截断破坏。
- 台账按 (user_id, session_id, trajectory_seq, item_id) seek；root 内详情按 (user_id, session_id, root_turn_id, trajectory_seq, item_id) seek。排序和游标使用同一完整比较键。
- 时间轴读 (user_id, session_id, level, bucket_index)；正文读 (user_id, session_id, body_id, body_revision, field, chunk_index)，均有匹配复合索引。
- 首屏与翻页禁止 COUNT(*)、大 OFFSET、SELECT *、原始 payload JSON 解析、IN(大量 root) 后全局排序、逐 item N+1 正文补水。
- 计数在 head 增量维护。若投影未就绪返回明确状态与有限已构建数据，不回退到同步扫描日志。分区数据库需要在执行计划中确认分区定位，防止向全部分区发起相同索引探测。
- SQLite 使用短只读事务；PostgreSQL 单次 bootstrap 使用只读 REPEATABLE READ，或单 SQL 同一快照。head、水位、行版本与基线必须来自同一一致读取。
- 所有同步 DB 操作包括鉴权存储查询、元信息与正文读取进入阻塞执行边界。禁止 async handler 直接同步读取历史、持有 async 锁等待 DB。
- 设置请求队列等待、SQL 执行、响应构造各阶段的独立预算。短交互读取与导出/重建具有明确资源配额，避免大任务占满交互池；线程级恢复去重，用户级公平限流，队列设条数和字节上限。
- 超时/取消要传到底层：PG 使用 statement_timeout 与查询取消；SQLite 为专用操作连接注册取消/截止检查，不能误中断共享连接上的其他线程。不宣称仅 AbortController/未来对象被丢弃即可取消已运行 SQL。
- byte cap 在存储投影字段、页组装和最终 JSON 编码三个阶段验证。触达预算正常返回可继续分页的数据；异常超限拒绝，不先构造数十 MiB 再截断。
- gzip 继续保留，但不计入满足未压缩字节预算的证明。

上述索引以双库执行计划与实际 rows visited/buffers 为验收条件，不能仅用“加了索引”的静态测试通过。

## 5. 新读取与实时协议

### 5.1 bootstrap 契约

直接替换蜂巢聊天打开的四路读取，新增用途明确的端点：

~~~text
GET /chat/sessions/{id}/view/bootstrap?kind=chat
GET /chat/sessions/{id}/view/bootstrap?kind=trajectory
GET /chat/sessions/{id}/view/chat?before={cursor}
GET /chat/sessions/{id}/view/trajectory?before={cursor}&root_turn_id={optional}
GET /chat/sessions/{id}/view/tiles?axis={axis}&range={range}&level={level}
GET /chat/sessions/{id}/view/search?q={query}&cursor={cursor}&field={field}
GET /chat/sessions/{id}/bodies/{body_id}?revision={revision}&field={field}&cursor={cursor}
~~~

bootstrap 返回强类型 envelope：

| 字段 | 定义 |
| --- | --- |
| session | 目标线程的有限元信息、权限允许的操作、运行状态 |
| epoch | 展示模型代次，清空、重建切换等不连续变动递增 |
| view_seq | 同一读取事务下展示变更水位 |
| projection_state | ready/rebuilding/failed，不可用不能被解释为空 |
| thread_empty | 只有已就绪、用户轮次确为零时为 true；未知为 null |
| coverage | 当前读取的根轮次/台账范围、页边界与行版本；不代表完整线程 |
| page | 有界聊天行或轨迹台账摘要；每行必须有稳定身份、版本、正文引用 |
| next_before / has_more | 不透明 seek 游标与精确翻页信息，不能只用 len==limit 推断 |
| overview | 轨迹 bootstrap 的有限摘要桶、摘要版本、dirty 状态；聊天不返回 |

响应编码字节在服务端内部采样，客户端不需要消费则不增设无用字段。

服务端 page count 初值：聊天默认最近 12 个 root 轮次，硬上限 20；每行用户与答案合计预览 ≤ 6KiB，状态/元信息 ≤ 1KiB；仍以总响应 ≤ 128KiB 为最终限制。根据空间预算减少行数，不能移除某行用户身份后只返助手 item。

轨迹默认最近 80 条台账摘要、硬上限 100，每条有限摘要 ≤ 768B；overview 最多 1024 桶，总体 ≤ 192KiB。选择新时间范围时选对应聚合层，不增加 bucket 数。详情正文单页 ≤ 128KiB，单块 ≤ 8KiB；长度、范围、字段、版本和 has_more 明确。

游标绑定线程、排序键、过滤条件和 epoch，服务端校验。客户端不能以任意 cursor 绕过鉴权或增大读取范围；所有 API 逐次验证用户对该线程和正文引用的访问权。

bootstrap 默认读取最新页；重开/恢复支持有限 anchor（root id 或台账稳定键）定位当前阅读位置，按同一小页/字节预算返回其覆盖范围，并可附带有限的最新活动摘要。恢复旧历史页不能无条件用最新尾页替换导致跳到底部。全文搜索结果也使用有限页、摘要和同一详情引用，query 长度/字段/时间范围均设上限。

### 5.2 window baseline 与历史页的不同语义

**当前展示范围可以建立基线并推进实时水位，前提是该范围的展示数据完整、后续变更协议覆盖所有身份/失效信息。** 它不需要含全部历史正文。这与旧“任意 items/blocks 截断的 snapshot 仍整状态覆盖并推进 cursor”完全不同。

- bootstrap 建立 {epoch, view_seq, coverage}，同时给出已加载行在该水位的展示数据和正文引用。
- watcher 从该 view_seq 订阅展示变更；先加载 bootstrap，再 subscribe 时遗漏的提交必须从保留窗口回放。连接先到可握手等待基线，不能先创建空 runtime 后宣布页面 ready。
- 序号严格单调且同线程隔离。服务端传所有有限展示变更或连续 cursor checkpoint，不能按可见范围跳过序号却继续要求连续。
- 对已加载 root 的变化应用有限 patch。对窗口外变化仅更新 head/标记该范围缓存失效，**不能不断向页面 store 填入历史原始 item**。
- 历史页只 merge 行与覆盖范围，不改变当前 watch 游标。迟到页只接受更高 row_revision，不覆盖更新的活动行；不同 epoch 的页直接丢弃并重新定位。
- 缓存正文绑定 body_revision；正在读取的旧版本可继续显示但标明过期。复制/下载完整原文固定一个版本，分页中不混入更新后的正文。
- 字段预览省略和分页省略明确区分。全局 has_more 不能替代某个正文的未加载范围描述。

实时帧也有字节边界：单帧 ≤ 64KiB，基线追赶单批最多 200 个有限变更且合计 ≤ 128KiB；单线程暂存最多 128 帧/512KiB，全局暂存 ≤ 2MiB，先触达任一边界即进入重新取基线流程。相同字段的连续文本可合并，状态与终结不能被丢弃。短时 token tail 明确携带 body_revision、字段、起始 offset 和持久块覆盖水位；仅当正文缺口闭合才追加，重连按持久块补齐，避免把未经持久化的尾部当 view_seq 已覆盖内容。引用失效帧必须能触发有界补水，不能静默跳过正文更新。

### 5.3 恢复必须先构建，再提交

baseline_required / resync_required 为展示流协议的明确状态；收到后连接可以结束，但 frontend supervisor 必须继续负责恢复，不能以 abort 等同“用户关闭了线程”。

流程：

1. 保留当前已提交页，状态设 recovering，显示连接恢复提示。
2. 每线程只允许一个带 deadline、signal、generation 的 bootstrap/recovery 请求。相同范围合并；范围已变化的请求废弃。
3. 在独立候选结构构建、验证基线；当前 live Map/页不清空、不写半成品。完成后在一个小提交中替换页引用。
4. bootstrap 到重新订阅之间依靠新 view_seq 回放覆盖。若构建期仍有旧流，缓冲设帧数/字节上限；先提交新基线，再应用高于基线且属于同 epoch 的后续帧。
5. 如果追赶速度落后或缓存溢出，放弃候选并获取更新基线，不无限积压。原已显示页继续保留。
6. 同时有 navigation_generation 和线程恢复 generation。每个 await、Worker 返回和提交前检查拥有者；同一线程 A→B→A 的旧请求也不能只因 sessionId 相同而提交。
7. 临时失败按 0.5/1/2/5 秒上限加随机抖动重试；网络离线等待恢复。重试任务有界，并可由页面离开/用户停止取消。鉴权失败、明确线程删除在目标页显示对应状态。

冷启动首屏请求必须在约定延迟内返回，客户端超时显示保留骨架/内联错误和可重试状态；8/30/45 秒等待后才兜底的模式退出聊天/轨迹打开链路。

## 6. 聊天前端：一个展示 store，一条首屏路径

### 6.1 状态机代替“数组空就是欢迎页”

每线程维护以下状态，不与 loadingBySession 的模型运行状态混用：

~~~text
uninitialized → opening → ready | verified_empty | error
ready → refreshing | recovering → ready
ready → recovering_failed（保留最后成功内容）
任意状态 → forbidden | deleted（明确响应且仍属于当前请求）
~~~

- 欢迎卡仅在 verified_empty 展示。registry.has、rows.length===0、history load 已结束都不能证明真实空线程。
- opening 展示目标线程框架与骨架，输入框保持可用；不能把上一线程正文当本线程首屏。
- refreshing/recovering/recovering_failed 保留当前线程已提交行与滚动锚点，提示放在页内。
- WS、tool detail、overview、活动卡、侧栏刷新失败不得调用 openAgentDraftSession 或清空目标线程内容。
- forbidden/deleted 只来自当前 generation 的明确授权/资源响应，并显示说明；不无声回退欢迎页。
- 新建线程也由创建结果确认 verified_empty，首条输入进入后立即切到 ready 并建立稳定行。

### 6.2 首屏调度

1. 点击立即更新导航意图、generation、线程标题/框架，取消上一线程前台请求。已缓存本线程页立即提交，可后台校验；无缓存则显示 skeleton。
2. 只发 chat bootstrap；不等待预取详情、session events、workflow events、snapshot、问候热力图、文件树、头像等。
3. 响应校验 generation、epoch、page budget 后，一次提交小页并 nextTick/paint。首屏完成的指标来自真实可见文本节点与 paint，不能在“任务已排队”时结束。
4. 建立/恢复展示 watch、补充轻量权限/状态。展开工作过程、附件、详情才启动对应请求；这些请求不改页面 ready 状态。
5. 预取仅限最多 2 个相邻候选线程的 chat bootstrap，低优先级、共享字节配额、有取消。点击必须可以抢占预取；禁止等待正在运行的原始 detail 预取完成。

正在 opening 时发送的输入由独立有限 optimistic overlay 保存，以 client_message_id 与服务端 root 绑定；bootstrap/恢复提交不能抹掉尚未确认的本地输入，也不能重复建立气泡。发送仍检查目标线程与操作权限，输入框能响应不等于绕过授权。

迁移完成后，删除蜂巢打开链路对 legacy transcript/runtimeProjection 与 thread state 的双写、兜底仲裁及原始 event 重放。输入、停止、队列、附件、反馈等原来读取 messages 的操作改为使用新 store 的强类型行/命令接口，不能只换模板却继续维持隐式旧依赖。

### 6.3 状态存储与增量失效

- 非响应式实体 Map 按 root/id 存有限字段；Vue 订阅行版本、分页版本和可见 key。行使用 shallowRef，已完成的正文块保持对象身份。
- reducer 更新受影响 id、dirtyRoots/dirtyRows；一批只发布这些行。token 更新订阅正文块时钟，不能 bump 使整列表重建的全线程结构版本。
- 不再缓存“全输入字符串 signature”；版本由协议直接提供。不扫描全部 turn/item 去发现变化。
- 标题、线程状态、队列等由 head/有限控制投影直接消费；不能在侧栏每个可见行扫描其全部 turn 判断状态。
- 线程缓存以字节和页双限额管理。前台 pin；后台按最近访问淘汰，淘汰不改变当前已提交页。活跃线程之间调度、锁和 watch 独立。
- 建议全局逻辑预算 48MiB：聊天/轨迹摘要页 12MiB、正文与 Markdown 结果 24MiB、Worker/网络候选与队列 8MiB、元信息/索引 4MiB。严格分配，缓存不因长期输出无限长大；真实 JS heap 另测。
- 每线程最多约 5 个页缓存，达到字节限额先停止预取、淘汰远页，保留当前页与活动尾部。查看旧历史时新输出只更新最新页和“新消息”计数，不打断用户位置。

### 6.4 长文本与单轮巨量工作过程

外层轮次虚拟列表不能解决单个超大气泡：一轮可能有数千模型步骤、数 MiB 正文、数万工具结果。

- 初始气泡只显示有限 user/answer 片段与过程统计，缺内容有明确 continuation 标识。工作过程默认折叠时不读取详情、不构造全部 timeline/workflowItems。
- 正文按段/块加载与块级虚拟化；单块 HTML/纯文本节点数量也有上限。展开大正文不渲染一个含数 MiB 的 Text node 或完整 HTML。
- Markdown Worker 仅处理可见正文块及少量 overscan；结果缓存按 body_revision + block identity + render options，不存全答案来源副本。
- 流式输出按 16–33ms 合并，通过 text append/尾块替换落 UI。已完成块冻结；每批不扫描全文、不重新 parse 已完成块。主线程工作超过 8ms 时拆下一帧。
- “跳到底部”定位最新块；向前翻页保持 root/block/offset 锚点。完整复制/导出按固定 body 版本流式读取，不要求先把全文载入页面，也不能只复制预览。
- Worker fetch/parse 只用于有必要的正文/详情或重建任务；小 bootstrap 不强制等待 Worker 启动。大型任务在 Worker 内获取与归约，回传有限 patch/Transferable 数据，避免主线程 parse 大 JSON 后双向复制。
- Worker 错误或取消不回退到主线程同步规划巨量快照。队列显式限定最多 4 个重任务且合计 ≤ 2MiB 输入描述/候选数据，详情/正文另受全局缓存预算约束；超额取消低优先级任务并保留可读预览。

## 7. 轨迹：摘要、台账、详情分别读取

### 7.1 打开只消费摘要读模型

轨迹 bootstrap 返回最近台账页与固定数量 overview 桶；UI 直接显示类别、时间、状态和有限预览。删除 attachTurnItems 和原始快照→完整 trajectory model 的打开路径。

台账可以遍历全部历史，通过 seek 继续翻页；单轮展开也分页。summary/detail 采用同一稳定 item id 与 revision，跨页 tool 调用配对使用持久化 call_id/ref，不靠 Array.find 查找刚好同时已加载的记录。

全线程搜索必须在服务端支持分页与成本预算，索引在写入/后台维护。搜索范围和字段明确。SQLite 可采用经过验证的 FTS，PG 使用适当全文索引；未建好的索引返回状态，不把全部正文下载到浏览器执行 includes。搜索需防抖、signal、generation，命中结果只带有限片段。全文索引按封存文本块增量维护，活动尾部可延迟并标明索引新鲜度；禁止每个 token 更新整篇长文的全文索引。

### 7.2 Canvas 时间轴与多级摘要

- 时间轴用一个 Canvas 与固定 overlay/tooltip/选框 DOM。台账继续 Vue 虚拟列表；详细操作在选中记录的面板中进行，提供键盘与台账等价入口。
- overview 按宽度选择聚合层，最多 1024 桶，Canvas 像素比与最大尺寸有界。缩放、平移请求目标范围摘要，旧摘要保留到新摘要就绪。
- 每桶表达记录密度、类别、错误、运行中状态等，不能等步长抽样导致失败记录、稀疏记录或长任务消失。
- 放大到低密度范围时才读取详细 spans，单页最多 512，返回稳定区间/记录引用；区间索引查重叠，不能用开始时间二分漏掉跨越视口的长 span。
- 命中测试使用当前桶或已加载区间索引；悬停仅改变 tooltip/游标。不调用 deriveTimeline、timelineFocusIndexes、全记录 find/map/filter。
- 拖动时先画选区；pointerup 后用范围去请求有界台账/聚合统计，不在每帧建立所有命中 index 的 Set。
- 时间轴与台账不共用全历史数组。时间桶只保存有限聚合，台账只保存分页摘要，详情只有选中/展开后读取。

### 7.3 台账虚拟化与失效边界

滚动范围用页内高度前缀 + 二分或树结构定位。每次只渲染可见行与有限 overscan，不在折叠/拖动时全量重新 flatten/group/计算高度。页面缓存保留有界的 id/高度摘要，正文内容单独淘汰。

切换时长/时间轴样式只选择服务端已经维护的坐标与摘要版本；尚未构建的模式显示局部构建提示。单个已知 span 更新只使对应台账行、有限 tiles 和相关页失效。

详情输入、输出、思考、上下文、工具 schema 等全部用字段分页端点；当前选项未展开不拉取。详情请求失败不清空时间轴或台账。

## 8. 实施顺序与模块拆分

以下按依赖顺序交付。每阶段都要以用户可见打开链路复测，不能把单项 helper 测试通过当整个阶段完成。不按旧 v2 的独占文件边界保留架构错误。

| 阶段 | 内容 | 主要位置 | 出阶段条件 |
| --- | --- | --- | --- |
| P0：冻结证据与协议 | 保留匿名触发链，增加真实入口时序/预算采样；定义 head/row/body/epoch/view_seq/coverage | scripts/diagnostics/、frontend/tests/e2e/、wunder-core | 新旧打开过程可同口径测量，缺根输入/空 runtime 等失败样例可重现 |
| P1：展示存储与写入投影 | 强类型契约、双库投影表/索引、写事务增量维护、正文分块、展示变更流 | crates/wunder-core/src/storage_backend.rs、storage_records.rs；crates/wunder-runtime/src/storage/、services/thread_log* | 固定小页查询不扫描整线程；投影、正文引用、seq 同事务一致 |
| P2：聊天 bootstrap 与状态 store | 一个请求、一个 store、明确状态机、generation、短首屏路径；操作调用方一起迁移 | api/chat/、frontend/src/api/chat.ts、stores/、realtime/chat/、messenger 页面 | 真实聊天冷开 ≤ 1 秒；缺输入/超长单轮仍有真实首屏且不变欢迎页 |
| P3：实时和正文 | 展示 WS、window baseline、独立候选提交、有限重试、dirty row、块级展示/完整复制 | thread_change_feeder/WS helpers；前端实时与正文组件 | 并发写入/断线/恢复/切换下完整正确，长期输出内存稳定 |
| P4：轨迹 | 摘要维护/tiles API、分页台账、Canvas、索引搜索与按需详情 | services/thread_view/、双库 storage；views/trajectory/、ThreadTrajectoryView.vue | 轨迹首屏 ≤ 1 秒；拖动/缩放无全历史处理 |
| P5：清理与完整验收 | 删除旧首屏快照/工作流重放/兜底与影子双写，迁移调用方；双库/多并发/降速验证 | 所有旧路径实际消费者与回归 | 本文全部门禁真实通过，报告有原始资料与前后对比 |

建议新增 services/thread_view/ 与对应 storage 子模块；前端拆 threadViewStore、threadViewLoader、threadViewRealtime、threadBodyViewport、trajectoryDataSource、trajectoryCanvas。messengerControllerInstall.ts 只装配这些能力，不再增加数百行业务。

### 8.1 切换与历史投影重建

- 新写入先建立同事务投影。历史投影由后台任务按线程/root seek 分段构建，checkpoint/批大小/内存/并发/IO 有硬限。
- 重建使用 shadow generation，记录事实源水位，回放重建期间变化；验证覆盖与身份后原子切换 head epoch。不得边重建边将半成品宣布为空或 ready。
- 新 API 遇到未就绪的历史线程明确返回 rebuilding。部署切换前完成目标历史的投影构建，不靠用户打开时同步重建保证秒开。
- 初始化和索引创建不阻塞聊天前台；PG 索引按部署流程建立，SQLite 大量回填在后台维护模式受控执行。完整保留事实日志，没有“为性能删除用户历史”的步骤。
- 这是读模型重建与数据完整性要求，不增加旧客户端兼容层、双渲染源或降级快照协议。

### 8.2 删除清单与共享调用方

删除蜂巢首屏的 getThreadLogSnapshot、同步 hydrate、snapshot planner 的页面恢复用途、legacyTurnRowAdapter、transcript fallback/windowing 回退开关、工作流历史重放、无消费者 shadow projection 与全量文本 signature。

先枚举并迁移实际消费者：聊天打开/watcher、轨迹、SubagentRunDetail、舰桥监控、native follow/trajectory、Slint trajectory、运行时 workspace/互通等。**不要把共享 thread_snapshot 的含义再次悄悄改成聊天页。** 改动共享 trait 时，所有实际消费方同批接入明确的分页读取/基线契约；日志导出独立流式读取，不经 UI bootstrap。

蜂窝保留强类型 Rust façade，使用同一引擎展示读契约时通过 native 调用，不增加本地 HTTP 或 bridge。Electron/Tauri 壳不在维护范围。子智能体卡片复用有界详情能力，不重新引入已移除的蜂群编排。

## 9. 验收：正确性、复杂度与真实体验同时通过

### 9.1 必测数据分布

| 数据形态 | 必须证明 |
| --- | --- |
| 空线程、纯文本、只有附件输入、已排队线程 | 空态与运行态准确，真实用户输入不因为空字符串消失 |
| 约 500 万 item 的多轮历史 | 小页打开耗时与 heap 不按总量线性增长，所有历史可翻页 |
| 单用户轮次含数千/数万模型与工具记录 | 初始聊天不加载全部过程，用户身份和答案仍可见 |
| 单正文数 MiB、工具详情大 JSON | 请求、解析、布局、复制都按块有界且原文完整 |
| 延续执行、跨页工具配对、思考与答案交错 | 稳定 root/record 身份，答案与过程一致 |
| 热线程持续写入、连续重连、过期游标 | 基线覆盖与增量完整，恢复不清空已有内容 |
| A→B→A 快切、同线程两次刷新、恢复中取消 | 旧 generation 不提交、不导航、不覆盖新页 |
| 冷缓存失败后 watch 启动、已显示页恢复失败 | 不凭 runtime 存在判定为空，不回欢迎页 |
| 多线程并行输出 + 同时翻页/输入 | 线程隔离、前台配额与输入预算保持 |
| 10/50 并发打开，另有导出/重建/日志写入 | 队列有界，无 DB 停滞许可积累，交互不被重任务饿死 |

所有样例使用匿名通用值，不包含业务名称、身份、密钥、真实路径或场景意图。

### 9.2 三层门禁

1. **正确性回归**：在真实 storage→API→store→页面链路断言身份、版本、覆盖、文本内容、空态、失败恢复与滚动锚点。必须覆盖本轮复现的“item cap 丢 user”“空 registry 禁用兜底”“取消破坏旧状态”。
2. **复杂度门禁**：记录 SQL 实际访问/返回行、排序 spill、未压缩响应字节、dirty 行数量、全文拼接次数、Worker clone 字节、队列水位、DOM 与画布对象数。固定页扩大总量不应导致扫描总量；只改一个尾块不能重投影未变化行。
3. **发布构建真实 E2E**：侧栏点击真实持久化的大线程，经过真正鉴权/API/WS与聊天/轨迹组件。测试输入、滚动、搜索、折叠、缩放、断线与页面返回，持续观察至少 60 秒捕捉迟到回退；持续输出/分页切换另做 15 分钟内存稳定性测试。

每数据规模至少 30 次打开以观察 p95；长耗时或受噪声影响的对照至少重复 3 轮取中位数，同时保留失败和最慢样本。SQLite 和 PostgreSQL 分别报告；没有 PG 环境不能写双库性能已通过。

### 9.3 指标与采样规则

为每次导航使用短生命周期 trace，记录：click→shell_paint→request→queue_wait→db→encode→headers→body→parse→commit→content_paint。前端另采 LongTask、帧间隔、输入 paint、heap、Worker/队列峰值、cache bytes、paint 后的 60 秒状态变动。

性能埋点仅记录耗时、计数、版本/代次与匿名 trace，不存消息正文、用户身份、路径和工具敏感输入。page size 与字节计数来自实际网络/编码，不能用 fixture 中固定写入的数值作为性能结果。

现有指标注册测试与 helper 回归保留其正确性用途，但不能被标为用户体验性能通过。旧 heavy-history harness 的宽松时间阈值不能作为本方案的放行门禁。

报告存入 docs/性能基线/，包含环境、发布构建、数据生成方式、具体入口、重复次数、基线与新实现、p95/p99、错误率、内存、SQL计划、HAR/trace 摘要与限制。固定页每条核心读取访问的候选行不得超过返回上限的小常数倍，纯分页不允许对整线程排序或 spill；大型时间范围只访问对应层的固定数量 tiles。指标缺失、实际页面入口被替换为 mock helper、只显示 skeleton、只测压缩字节，均不验收。

本轮已经完成 P1～P4 的主链路实现：双存储事务展示投影、聊天/轨迹有界 bootstrap、分块正文、独立展示变更流、后台重建、轨迹 tiles/搜索、前端 generation 状态机、历史分页、实时尾流水位校验和失败恢复退避。旧聊天首屏不再等待原始 transcript、events、snapshot 或详情请求；展示页面只把已完成的投影页宣布为空。
