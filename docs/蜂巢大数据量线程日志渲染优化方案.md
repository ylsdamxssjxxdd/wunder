# 蜂巢大数据量线程日志渲染优化方案

> 状态：方案 v2（已按当前代码实测复核，v1 的偏差见附录 B）
> 范围：蜂巢（`frontend/`，Vue3 + TypeScript）消息面板、线程轨迹视图、侧栏线程树；舰体后端 thread-log 传输契约与阻塞预算（`crates/wunder-runtime/`、`crates/wunder-core/src/storage_backend.rs`）。
> 关联：《亿级数据存储方案》（存储层已按月分区与增量统计演进，本文解决其上游的**读取、传输与渲染链路**）。
> §5 的工作分解按「一个工作项 = 一个子智能体 = 一组独占文件」组织，可直接并行分派。

## 0. 结论摘要

v1 方案的方向正确（渲染源单一、快照无界、主线程全量重算），但按 v1 的动作落地**解决不了问题**：

- 打开链路里还有一个**比快照更先到达的百万级无界请求**（workflow-events），v1 全篇未提；只给它加 deadline 而不给它范围参数，首屏依旧白屏。
- 客户端 abort **不终止服务端序列化**，而 DB 阻塞许可不可取消，反复大快照会把整个 Db 类打成 wedged 并拒绝后续所有 DB 流量；v1 把问题当带宽，风险判断错位。
- `thread_snapshot` 的**原子整线程替换**契约被 v1 的分页参数直接改写，会丢头部或反复触发 `snapshot_required`；且 HTTP 参数只覆盖 9 个调用方中的 2 个，蜂窝/舵机/舰桥/互通仍在拉全量。
- v1 的 P0-1「加个兜底分支」被低估：v1/v2 的 id 命名空间互不相交（`tturn:` 前缀），不存在可对齐的去重键；`chatStore.messages` 被就地裁剪到约 120 条，且没有任何现成组件渲染扁平 legacy 消息 → 兜底是**新建轮次行构建器**。
- S2/S3/S4 的归因需要重排：真正的主因是**被硬编码关闭的取消与陈旧闸口**、**整份快照被挂成深层响应式代理**、**侧栏排序的同步 localStorage 写**。

保留价值最高的三条：快照传输有界化、投影记忆化 + Worker 化、轨迹视图空态与算法修复。

|---|---|---|---|

## 2. 链路与真实边界（实测）

### 2.1 规模基数

- 压测上限：`user_rounds ≤ 2000`、`model_rounds ≤ 2000`、`user_rounds × (model_rounds×5 + 1) ≤ 6_000_000`（`storage/stress_model.rs:12-19`）；默认画像约 5M 行，debug 构建实测约 4.3k items/s、约 11 分钟写完（`services/stress_thread.rs:25-30`）。
- `thread_log_changes` 每会话只保留最近 **4096** 条变更，且裁剪发生在**四条持久化写路径上（同步）**，不是后台清扫：`sqlite/thread_log_store.rs:316,550,651,745`，PG 同构 `postgres/thread_log_store.rs:321-324`。
- 线程尺寸**已有廉价探针**：`GET /thread-log/turns` 用两条 `COUNT(*)` 返回 `user_round_total` + `item_total`（`api/chat/events.rs:135,145` ← `thread_log_store.rs:772-791`）。前端包装函数 `getThreadLogTurns` / `getThreadLogTurn` 已存在但**零调用方**（`api/chat.ts:104-107`）。

### 2.2 打开链路：四个并发请求的真实边界

`loadSessionDetail` 在 `chatSessionOpenLoadActions.ts:724-767` 发 `Promise.all`：

| 请求 | 前端参数 | 服务端上界 | 中止/超时 | 后果 |
|---|---|---|---|---|
| `GET /chat/sessions/{id}`（transcript） | `limit=80`（`chatRuntimeControls.ts:546`）、`summary:true` | 有界 | 应带 signal，实际**恒为 null**（R3） | 正常 |
| `GET /chat/sessions/{id}/events` | `limit=80` | 有界 | 同上 | 正常 |
| `GET /chat/sessions/{id}/events?workflow_only=true` | **不带范围、不带分页**（`chatRuntimeState.ts:698-725`） | `100 轮 × 每轮 ≤10_000 条事件`，即**最多约 100 万条**（`events.rs:19-20,611,656-690`），且在一次 `run_db` 内做约 1 万次分页查询 | **无任何上界**（不在 8s deadline 覆盖范围） | R2，v1 未识别 |
| `GET /chat/sessions/{id}/thread-log/snapshot` | 无参数（`api/chat.ts:110`） | **无 LIMIT**，三条全表扫描 + 全量 `Vec<Value>` 常驻（`thread_log_store.rs:1043,1056,1069`） | 8s `AbortController`，`.catch(() => null)`（`:714-723,761-762`） | R1 |

`WORKFLOW_TURN_ITEMS_MAX` 的计数 `loaded` 在 `thread_turn_to_workflow_round` **内部**声明，所以它是**每轮**上限而非整次请求上限。

### 2.3 渲染源（更正 v1 的机制描述）

聊天区轮次行**只来自 v2 线程状态**：

- `agentTurnSlots = buildChatThreadMaterializedSlots(activeSessionId) ?? []`（`messengerControllerInstall.ts:1870-1877`）；`?? []` 就是把 `null`（registry 无 entry）和 `[]`（有 entry 但无轮次）**合并成同一种空态**（`chatThreadRuntime.ts:414-417`）。
- 下游全部锁定轮次行结构 `{key, rootTurnId, kind, user:{key,sourceIndex,message}, assistant:{...}}`：`agentConversationRows`（`:1878-1883`，只在头部插一条 greeting）、`agentVirtualWindow`（`:2067-2077`）、`MessengerTurnRow.vue:51-56`。
- **v1 transcript 并没有被"覆盖"**。v1 实测：`chatThreadRuntime.ts:419-420` 改写的是该函数自用的私有 `entry.renderProjection`（`:34,51` 注释即"保活 materialize 缓存的投影壳"），而 `syncChatRuntimeProjectionFromSnapshot` 写的是 `store.runtimeProjection`，`this.messages` 也仍在。**是渲染源不读它们，不是数据被销毁**。
- 唯一从 v1 进入渲染的是问候语气泡：`resolveSyntheticGreetingRenderable`（`:1849-1863`）只扫 `chatStore.messages` 里的 `isGreetingMessage`。
- 欢迎网格条件（`MessengerMessagePanel.vue:214-220`）：`agentTurnSlots` 为空 **且** `historyLoading` 为假 → `SessionActivityCard`（53 周 × 7 天的**账号级**热力图，`SessionActivityCard.vue:110,124-130` + `dailyActivityGrid.ts:42`，对本次失败零信息量）。模板里网格与问候行互斥（`:27,35`）。

结论：快照失败 → `threadSnapshot = null` → 跳过 `hydrateChatThreadRuntime`（`:793-796`）→ v2 空 → `agentTurnSlots=[]` → 网格成为唯一渲染态。**数据在，没人读。**

### 2.4 失败终态：watcher 不会自愈

`startSessionWatcher`（`:1238`）以 `after_change_seq = lastSeq ?? 0` 起 watch（`chatWatcher.ts:246-252`，注意该文件在 `stores/`）。游标落后于裁剪窗口时，服务端返回单条标记并**终止投递**：

- 读侧：`thread_log_store.rs:1100-1101,1125-1126` → `workspace.rs:1829,1838-1840` → `thread_change_feeder.rs:100-102`（发完 `return`，通道关闭）。
- 帧侧：`ws_helpers.rs:242-250` 把 `thread_snapshot_required` 标成控制帧，`:264-267,285-287` 发完即结束。**Web WS 路径不内联快照体**（`data` 为空标记）；把整份快照塞进一帧的是互通隧道（`interlink/client/mod.rs:1419-1425`，`"snapshot": is_baseline`）。
- 前端 `dispatchSnapshotRequired`（`chatThreadRuntime.ts:320-345`）**无并发闸口**（`:332` 是 `void (async()=>{})()`，而 `dispatchResume` 有 `THREAD_OVERFLOW_RESUME_COOLDOWN_MS` 闸，`:353-359`），loader 类型不带 signal（`:303`），注册的 loader `getThreadLogSnapshot(sessionKey)` 不传参 → 吃 axios 默认 30s（`api/http.ts:39`）。
- 失败分支 `catch { hooks.onSnapshotRequired?.(data) }`（`:341-343`）落到 `chatWatcher.ts:227` 的 `controller.abort()`，而 abort 又同时**关掉 watcher 的 80ms 自动重启**（`:289` 的 `!controller.signal.aborted`）和 `setSessionLoading(false)`（`:263`）。

即大线程的稳定终态是：**空渲染 + watcher 已死 + 不再重试**，每帧 `snapshot_required` 还会并发再拉一次全量。任何"退回仅 watcher 增量"的设计都必须先解决这条终止语义。

## 4. 设计决策（先冻结契约，再并行开发）

**D1 不改 `thread_snapshot` 的原子语义，另开一条有界"窗口读"。**
`storage_backend.rs:226-228` 明确契约是"cursor/turns/items/blocks 在同一事务读，避免撕裂投影"，所有消费方按**整线程替换 + cursor 推进**使用（`wunder-cli/tui/app.rs:5203-5222`、`native_follow.rs:26-55`）。分页体仍带 `cursor=最新` 会让客户端要么标记已应用而永久丢头部，要么不推进而反复回到全量。
→ 新增 `thread_snapshot_window(user, session, before_turn, turn_limit, fields)`：返回 `{cursor, window_start_turn, turns, items, blocks, has_more, item_total}`，**blocks 查询必须按 turn 收敛**（今天 `:1069` 用 `item_id IN (SELECT …)` 覆盖全部 user items，不改就白加分页）；响应里显式声明 `partial=true`，客户端**不得**据此推进 durable cursor。原 `thread_snapshot` 保持不动，`snapshot_required` 的恢复语义不变。

**D2 服务端预算优先于客户端 deadline。** 客户端 abort 不能中止服务端（R4）。顺序必须是：先查 `get_thread_log_counts` 决定走窗口读还是拒绝；给全量快照加服务端行数/字节硬上限并返回结构化 `oversized` 错误；启用响应压缩。压缩与预算对所有形态（蜂窝/舵机/舰桥/互通）同时生效，HTTP 参数只对蜂巢生效——这一点要在风险表里如实标注。

**D3 首屏不依赖全量；兜底需要新建轮次行构建器。** v1/v2 id 命名空间不相交（v2 气泡带 `tturn:` 前缀，`chatThreadProjection.ts:28-29,159,226`；legacy 走 `resolveChatRuntimeMessageRenderKey` 的 `runtime:/legacy:` 前缀，`chatRuntimeMessageKeys.ts:18-29`），**不存在能把 v1 行与 v2 行对齐去重的公共键**。所以兜底是"要么用窗口投影，要么用 transcript 构建器，二选一"，而不是二者拼接。优先级：窗口投影（真轮次结构）→ transcript 构建器（`limit=80`，且 `chatStore.messages` 已被 `applyMessageWindow` 就地 `splice` 到约 120 条，`chatRuntimeState.ts:260-264` + `chatRuntimeControls.ts:539`）→ 网格。兜底必须区分 `null`（registry 无 entry，可能是快照失败）与 `[]`（真没有用户轮次），否则会把合法的空线程也渲染成兜底内容。

**D4 `snapshot_required` 必须有界、幂等、且失败不杀 watcher。** loader 需带 signal + deadline + 并发闸（同 `dispatchResume` 的 cooldown 模式）；失败只能降级为"停止增量并给出可见状态"，不得让 abort 顺带关掉自动重启；对 `partial` 窗口，游标推进规则要单一出处（建议：窗口不推进 cursor，仅记录 `window_start_turn`，由显式的补齐动作推进）。

**D5 主线程只做增量投影。** 快照解析与应用移出主线程（Worker 可终止回收内存），深层响应式一律禁用（`shallowRef` / `markRaw`）。判定口径：任何一次打开线程，主线程单任务 ≤ 200ms。

**D6 一切新增路径自带开关与回归断言**，沿用 `chatRuntimeControls.ts:548,578`（`WINDOWING_ENABLED_KEY` 的 `wunder_chat_*` localStorage、fail-open）风格；每项工作项必须交一条**会因旧写法而失败**的断言（见 §5 的验收列）。

## 7. 风险与回滚

- **只覆盖 2/9 消费方**：`thread_snapshot` 还有桌面/Slint/CLI/互通/渠道持久化等 7 个进程内调用方（`native_follow.rs:326`、`native_trajectory.rs:14`、`wunder-cli/tui/app.rs:5196`、`frontend-slint/src/thread_trajectory.rs:1548`、`interlink/client/mod.rs:1485`、`subagents.rs:1841`、`channels/service/persistence.rs:523`）。HTTP 参数救不了它们，**服务端预算（W1-A）是唯一能全覆盖的闸**，必须最先落地。
- **互通隧道把整份快照塞进一帧**（`interlink/client/mod.rs:1419-1429`）：窗口化需要新的多帧"snapshot part"协议或明确不上互通，否则互通侧仍是全量。原型阶段可直接限制"超大线程不走互通基线"。
- **D1 新增 `thread_snapshot_window` 会改 trait**，双实现与 shim 必须同批落地，否则两端语义静默分叉（今天两端是刻意逐字节一致的，包括空线程返回体）。
- **W1-D/W1-C 动的是恢复语义**，风险最高；用现有 `chatRuntimeInvariants` 与 `thread-log-recovery` 断言守护，窗口不推进 cursor 的规则必须只有实现处一个来源。
- **W2-E 兜底与窗口投影并存**时可能重复渲染，二者按 D3 互斥选取（优先级窗口 > 兜底 > 网格），不做合并列表；开关可一键退回纯网格。
- 各阶段可独立回滚：W1-A 预算阈值、W1-C 闸口、W1-D cooldown、W2-E/F/G 各自 `wunder_chat_*` 开关。
