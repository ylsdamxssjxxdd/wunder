# 架构评估与演进路线

## 1. 结论先行

当前架构的核心方向是正确的：线程运行时、工具治理、持久化、实时事件和三种运行形态已经形成了共同内核。真正影响开发效率的不是“智能体和业务系统必须在一起”，而是两者之间缺少稳定的应用边界，导致很多模块通过 `AppState`、全量存储接口和共享记录直接互相调用。

后续不建议再次做“智能体服务与业务服务分成两个进程”的粗粒度拆分。这个系统的权限、额度、工具策略、线程归属、审批和恢复都要求在一次命令和同一事务语义中协同。更合适的方向是：

> 保留一个模块化单体，保留一条线程执行主链；把智能体执行内核、业务应用服务、领域存储和接入投影之间的依赖方向收紧。

目标调用链应逐步收敛为：

```text
HTTP / WS / Desktop / CLI / Channel
        ↓
Application Command（身份、租户、权限、幂等）
        ↓
Thread Application Service / Mission Application Service
        ↓
Thread Runtime
        ↓
Agent Kernel（prompt、context、tool loop、recovery）
        ↓
Ports：Model / Tool / Policy / Memory / Workspace / ThreadStore / EventSink
        ↓
Durable ThreadLog + Domain Events
        ↓
Projection：Web、Desktop、CLI、Admin、Channel
```

智能体定义、用户、组织、蜂群、渠道等业务对象仍由业务域管理；线程启动时将经过授权的智能体版本、工具策略和记忆初始快照绑定到线程。线程运行期间只消费这个不可变执行快照，业务配置后续变化不回写正在运行的线程。

## 2. 当前架构画像

仓库已经有明确的意图分层：

- `wunder-core` 承载配置、协议、记录和存储抽象等低依赖类型。
- `wunder-runtime` 承载智能体编排、线程运行时、工具、服务、API、渠道、网关和存储实现。
- `wunder-server`、`wunder-desktop`、`wunder-cli` 是不同运行形态的入口。
- Vue 用户端、原生管理端和 Slint 桌面端主要消费后端接口与事件投影。
- `AppState` 已经显式分为 `kernel`、`projection`、`control` 三组服务。

这说明项目已经从“一个聊天接口”走向了“可恢复的智能体运行时”。但代码上的依赖关系仍然比目录结构宽：运行时包同时包含 Axum API、业务服务、LLM 客户端、工具实现、渠道适配器和 SQLite/PostgreSQL 实现；入口只是在同一个巨型包上选择启动哪些后台任务。

从规模上看，运行时的 `services` 约有 12 万行，`api` 约有 6 万行，`orchestrator` 约有 2.6 万行，存储读写约有 3 万行。这些数字本身不是问题，问题是这些代码仍共享少数几个宽对象：

1. `AppState` 是几乎所有路由和部分服务的依赖入口。
2. `Orchestrator` 同时持有配置、工作区、监控、存储、技能、用户工具、审批、命令会话、网关、用户世界和协作投影等依赖。
3. `StorageBackend` 将约 26 个领域存储 trait 组合成一个总接口，覆盖约 59 张表。
4. `UserStore` 既处理身份，又暴露会话、智能体、蜂群、任务等多类读写。
5. 一些 API 文件直接组合存储、权限、工作区和编排状态，而不是只做协议转换。

因此，当前结构属于“模块目录已经形成，依赖图还没有形成”的阶段。

## 3. 当前架构的优势

### 3.1 共同内核避免了三套执行语义

服务端、桌面端和 CLI 共用线程、工具、存储抽象、审批和实时事件语义。这避免了本地端重新实现一套模型循环，也让线程恢复、工具结果裁剪、上下文压缩和额度计量有机会保持一致。桌面端同进程调用还减少了本机 HTTP、桥接进程和序列化开销，符合本地性能目标。

### 3.2 智能体运行时的硬约束已经进入程序结构

prompt 冻结、长期记忆一次性注入、线程 lease、队列准入、审批、超时、重试、工具并行限制、结果截断和终态收敛都有运行时落点。系统没有把可靠性完全寄托在提示词或页面逻辑上，这是最重要的长期资产。

### 3.3 ThreadLog 和实时协议的方向正确

稳定 Item、Turn、revision、change cursor、快照与增量分离，解决了流式正文逐 token 写库、断线后乱序和重复合并等问题。`Snapshot + Delta + Replay` 让前端成为投影消费者，而不是状态真相源。这个方向应继续收口，不能重新退回到各页面自行拼装状态。

### 3.4 存储后端和运行形态有统一抽象

SQLite 与 PostgreSQL 共享存储契约，运行形态通过 profile 和 capability 选择后台任务。这样桌面离线能力、服务端多用户能力和 CLI 自动化能力能够共享大量行为测试。

### 3.5 接入和控制面已有可复用骨架

渠道目录、入站队列、出站队列、媒体、网关、A2A、WebSocket 和桌面桥接已经有独立模块。新增入口原则上可以复用线程和事件主链，而不是复制模型循环。

### 3.6 测试、性能和恢复意识较强

仓库包含大量运行时回归、存储契约、队列、租约、实时回放和吞吐验证。有限队列、分页、游标、增量投影和本地恢复也已经成为明确要求。这些基础设施使后续重构可以采用逐步迁移，而不是一次推倒重来。

## 4. 主要问题与影响

### 4.1 `AppState` 是装配容器，也是隐式服务定位器

`AppState::new_with_options` 一次性创建存储、工作区、监控、技能、用户工具、用户存储、网关、编排器、蜂群、线程运行时、渠道和定时任务。路由通过 `State<Arc<AppState>>` 获得全部对象，服务函数也常把 `&AppState` 继续向下传。

这带来三个后果：

- 新增一个依赖时，构造器、状态结构、多个运行形态和测试初始化都可能一起修改。
- 任何模块都可以轻易绕过应用服务，直接读取别的领域存储或运行时状态。
- 单元测试需要初始化大量与被测能力无关的服务，测试速度和隔离性下降。

`kernel / projection / control` 是有价值的第一步，但目前更像字段分组，而不是访问边界。只要 API 仍能拿到完整 `AppState`，耦合仍然存在。

### 4.2 `Orchestrator` 已经承担了超过执行内核的职责

编排器本应负责一次线程回合的 prompt、context、模型、工具和恢复。现在它还直接持有用户工具、技能、LSP、工作区、网关、用户世界、蜂房实时服务、审批和命令会话等依赖。这样做早期开发很快，但任何执行语义改动都可能触及业务投影或外部接入。

线程运行时也同时处理队列、租约、会话创建、目标续跑、用户存储和监控。调度层、应用层和执行层因此互相了解实现细节。

### 4.3 智能体既是业务配置，又是执行身份

当前智能体记录同时包含名称、头像、描述、系统提示词、模型、工具、技能、审批、沙箱、蜂群归属和展示偏好。智能体管理还会同步工蜂卡文件、工作区和广场资产。业务配置变化、文件投影和运行时工具面由同一个服务串联。

这会造成一种危险：为了新增一个目录、广场或管理字段，开发者容易触及线程执行；为了调整模型或工具策略，又容易触及业务资产和文件同步。

应把以下对象分开：

| 对象 | 生命周期 | 是否可变 |
| --- | --- | --- |
| `AgentDefinition` | 业务目录、编辑、权限、发布 | 可变 |
| `AgentVersion` | 发布后的提示词、模型、工具和策略 | 不可变 |
| `Thread` | 一次连续执行上下文 | 状态可变，认知快照不可回写 |
| `Turn` / `ToolCall` | 线程中的执行事实 | 追加或状态收敛 |
| `Mission` / `Task` | 多智能体业务协作 | 可调度、可重试 |

线程创建时绑定 `AgentVersion` 和经过策略过滤的执行快照。这样既保留智能体与业务系统的授权关系，又不会让业务目录修改直接改变正在运行的模型上下文。

### 4.4 API 层仍然包含大量业务编排

聊天、会话、蜂群、用户频道、工作区和管理员 API 中可以看到直接读写存储、处理权限、修改工作区、重建编排状态和拼装前端 JSON 的逻辑。API 文件不再只是鉴权、校验和接线，而是成为另一个业务服务层。

这会造成同一能力在 HTTP、桌面 façade、CLI 或渠道入口出现不同校验和副作用顺序，也使 API 测试不得不覆盖很多内部细节。新功能往往需要“先找一个能拿到 AppState 的入口”，而不是先找到对应领域的用例服务。

### 4.5 存储抽象过宽，类型边界偏弱

`StorageBackend` 将身份、智能体、会话、线程日志、记忆、向量、用户世界、蜂群、渠道、网关、媒体、定时任务和配额等所有存储 trait 组合在一起。后端实现可以统一，但上层不应因此拥有全部权限。

同时，监控、事件和部分业务字段以 `serde_json::Value` 在层间传递，导致字段约束、版本兼容和错误位置不够明确。通用 `meta` 也容易形成隐式协议：写入方和读取方只靠字符串键保持联系，编译器无法帮助发现变更。

建议保留“SQLite/PostgreSQL 共享实现”这一优点，但让调用者只依赖窄接口，并在领域边界使用类型化命令、结果和事件。跨域写入用明确的事务用例或 Unit of Work 解决，不能靠暴露一个更大的总接口解决。

### 4.6 `wunder-core` 的拆分尚未完成

稳定类型已经移动到 `wunder-core`，但运行时仍保留一套 `core` 目录并通过 re-export 兼容旧路径；`wunder-runtime` 还同时包含 Axum、存储后端、LLM、工具、渠道和桌面相关能力。包名和库名也仍然带有服务端意味，使“核心运行时”和“服务端传输壳”的边界不够清楚。

这不是马上拆成很多 crate 的理由。当前更需要先清理依赖方向，再把已经稳定的边界逐步提升为 crate 边界。

### 4.7 事件真相正在迁移，过渡面仍然偏多

ThreadLog 已成为更可靠的线程事实和恢复基础，但历史记录、流事件、监控快照和兼容接口仍同时存在。过渡期间必须明确每类数据的权威性：

- ThreadLog：线程事实和可恢复内容。
- Domain Event / Outbox：跨模块事实通知。
- Stream Event：面向连接的回放缓存。
- Monitor / 列表摘要：派生投影。

如果新功能继续直接写多个层级，长期会再次出现“刷新结果、实时结果和恢复结果不一致”。

### 4.8 构建和运行形态的组合复杂度会放大耦合成本

服务端、桌面、CLI 共享 runtime 是正确选择，但当前 runtime 既含协议路由又含大量可选功能，profile、feature、后台任务开关和桌面兼容路径叠加后，构造和验证矩阵越来越大。新能力如果没有明确的 capability 和 adapter 边界，容易默认进入所有形态，增加启动时间、依赖体积和 Win7/Linux 兼容风险。

## 5. 为什么之前的“分离”容易失效

从当前结构看，过去的分离很可能遇到了以下问题：

1. **按产品页面或进程拆，而不是按依赖方向拆。** 把智能体和业务搬到两个服务后，权限、工具策略、线程锁和事务仍需要互相读取，结果只是增加 RPC 和 DTO 转换。
2. **没有不可变执行快照。** 业务配置、智能体提示词和运行中的线程共用记录，分离后任何一方更新都会影响另一方，最终只能用同步补丁维持一致。
3. **没有唯一的线程真相源。** 运行态、聊天历史、事件和业务任务各自保存一部分状态，拆分后重复投影和乱序更明显。
4. **把调度和执行一起拆散。** 一个入口负责排队，另一个入口负责模型循环，审批、取消、恢复和重试的边界会变得模糊。
5. **把共享数据库当成服务接口。** 进程虽然分开，双方仍直接读同一批表，逻辑耦合没有消失，只是更难调试。

因此，下一次分离必须先完成“语义分离”，再考虑“部署分离”：先让依赖通过命令、端口和事件传递，再根据吞吐、故障域和发布节奏决定是否拆进程。

## 6. 推荐的目标架构

### 6.1 四个内部平面

| 平面 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| Agent Kernel | prompt 冻结、上下文、模型调用、工具循环、压缩、重试、终态 | 用户查询、蜂群页面、渠道协议、数据库 SQL |
| Application | 身份、权限、额度、幂等、线程提交、任务调度、跨域事务 | 模型循环细节、HTTP/WS 格式 |
| Domain | 用户组织、智能体目录、蜂群任务、工作区、记忆、渠道目录 | 直接驱动前端、跨域随意写表 |
| Adapter / Projection | SQLite/PostgreSQL、LLM、MCP、文件、渠道、WS、桌面、CLI | 改变线程认知态、绕过应用策略 |

业务域可以继续在同一进程内运行。关键是依赖只向下：传输依赖应用，应用依赖领域和端口，内核依赖端口，适配器实现端口；领域服务不依赖 Axum，内核不依赖用户世界或蜂群投影。

### 6.2 建议的核心端口

第一阶段不必创建很多新 crate，可以先在现有 runtime 中定义这些窄接口：

- `ThreadStore`：接受用户轮次、读取上下文、写入 Turn/Item、保存运行状态。
- `AgentCatalog`：按租户和权限读取已发布 `AgentVersion`。
- `ModelPort`：完成非流式和流式模型调用。
- `ToolCatalog` / `ToolExecutor`：返回版本化工具描述并执行已授权能力。
- `PolicyPort`：审批、权限、配额、沙箱和并发限制。
- `MemoryPort`：只提供线程初始化时的记忆快照和明确的管理操作。
- `WorkspacePort`：文件现实层能力，不让内核知道路径布局。
- `EventSink`：追加领域事实或线程变更，由统一出站链路发布。
- `Clock`、`IdGenerator`、`Cancellation`：便于恢复和确定性测试。

编排器的入口应接收一个类型化的 `ExecutionContext`，而不是从 `AppState` 反查用户、智能体、配置和工作区。这个上下文应包含 actor、租户、thread、agent version、工具策略、预算、工作区句柄和记忆快照。

### 6.3 业务和智能体之间的正确耦合点

业务系统应通过以下方式影响智能体：

- 创建线程时选择一个有权限的 `AgentVersion`。
- 应用服务生成经过权限、配额和工具策略过滤的 `ExecutionContext`。
- 模型调用和工具调用产生 ThreadLog 与 Domain Event。
- 蜂群、定时任务、渠道和外部工作流只提交线程命令或 mission 命令。
- 投影订阅事件并展示状态。

业务系统不应通过修改正在运行线程的 system prompt、直接插入模型上下文或绕过 ThreadRuntime 来影响智能体。

### 6.4 事件模型

定义统一事件包络：

```text
EventEnvelope {
  event_id,
  aggregate_type,
  aggregate_id,
  revision,
  tenant_id,
  actor_id,
  causation_id,
  event_type,
  payload,
  occurred_at
}
```

ThreadLog 事务成功后写入 Outbox；Outbox 负责投影、WS、渠道和管理端通知。连接级 stream event 只是可回放传输缓存。这样新业务可以订阅同一事件，而不需要在几十个 API 和服务中手写广播逻辑。

## 7. 分阶段路线

### 阶段 0：建立边界护栏

目标是停止耦合继续扩大，暂不改变主要行为。

- 新服务和新 API 禁止把完整 `AppState` 继续向下传递。
- 新 API 禁止直接调用存储写方法；先进入应用用例服务。
- 为模块标出允许的依赖方向，增加简单的架构检查脚本或编译测试。
- 为线程事实、领域事件、投影和传输事件写一页权威性说明。
- 为每个领域指定 owner：Identity、Agent Catalog、Thread Runtime、Mission、Memory/Knowledge、Workspace、Integration、Projection。

验收：新增功能不需要修改无关模块的状态字段；API 单测可以用窄服务 fake，而不是初始化完整应用。

### 阶段 1：先拆类型和端口

- 在 `wunder-core` 中稳定 `ActorContext`、`TenantScope`、`AgentVersionRef`、`ExecutionContext`、Thread Command/Event 类型。
- 将模型、工具、策略、线程存储和事件发布抽成窄 trait。
- 将 `StorageBackend` 的调用者改为领域仓储组合；SQLite/PostgreSQL 仍可由同一个 adapter 实现。
- 逐步减少 `Value` 作为核心命令和结果的使用，保留它作为扩展字段或外部协议载荷。

验收：内核可以在内存 fake port 上运行一轮完整测试；切换 SQLite/PostgreSQL 不需要修改应用服务。

### 阶段 2：抽应用服务，压薄 API

优先处理高频变更和耦合最高的入口：

1. `ThreadApplicationService`：发送、取消、续跑、压缩、读取线程。
2. `AgentCatalogService`：创建、编辑、发布、导入、删除智能体资产。
3. `MissionApplicationService`：蜂群任务、母线程、工蜂任务和汇总。
4. `WorkspaceApplicationService`、`MemoryApplicationService`、`ChannelApplicationService`。

每个服务只接收 actor、输入命令和窄端口；HTTP、桌面 façade、CLI 和渠道都调用同一服务。API 只保留鉴权、协议转换、错误映射和响应投影。

### 阶段 3：分离 Agent Kernel

当阶段 1、2 的依赖检查通过后，再把 orchestrator 的执行链迁移到独立模块，必要时再提升为 `wunder-agent-kernel` crate。迁移顺序建议是：

1. prompt/context/turn state。
2. model/tool loop。
3. compaction/retry/usage。
4. event sink 和 recovery。
5. ThreadRuntime 的 lease、队列和调度保留在应用运行时，内核只推进一个执行上下文。

内核 crate 不应依赖 Axum、UserStore、Hive、Beeroom、Channel、Gateway 或具体数据库。

### 阶段 4：统一 Outbox 与投影

- ThreadLog 和业务事务成功后写 Outbox。
- Web、Desktop、CLI、Admin、Channel 都使用统一事件包络和快照补偿。
- 将散落在 API、渠道和服务中的直接广播迁移到 projector/subscriber。
- 完成旧 chat history、旧流事件兼容路径的权威性收口；每个字段只保留一个真相源。

### 阶段 5：只在指标证明需要时拆进程

如果未来出现明确的吞吐或故障隔离需求，优先拆：

- Agent Worker：消费线程命令，写回 ThreadLog/Outbox。
- Integration Gateway：渠道、网关和外部连接的连接池与协议适配。
- Projection Worker：统计、搜索和管理视图的异步构建。

不要首先把“智能体定义服务”和“线程执行服务”拆成两个互相查询的服务。AgentVersion 快照、ThreadLog 和 Command/Event 协议稳定后，进程拆分才不会重新制造隐式耦合。

## 8. 优先级建议

| 优先级 | 工作 | 原因 |
| --- | --- | --- |
| P0 | 禁止新增完整 `AppState` 传递和 API 直写存储 | 立即停止耦合增长 |
| P0 | 固定 ThreadLog、Outbox、Stream Event、Monitor 的权威性 | 防止恢复和实时继续分叉 |
| P1 | 引入 AgentDefinition / AgentVersion / ThreadSnapshot | 解决智能体配置与执行身份混用 |
| P1 | 建立 ThreadApplicationService 和 AgentCatalogService | 让 HTTP、Desktop、CLI 共用用例 |
| P1 | 将 StorageBackend 使用面收窄为领域仓储 | 降低跨域读写和双后端修改半径 |
| P2 | 抽出 Agent Kernel 端口并建立 fake-port 测试 | 让执行内核可独立演进 |
| P2 | 统一 Outbox 和投影订阅 | 降低实时、渠道和管理端重复接线 |
| P3 | 按指标拆 Worker/Gateway/Projection 进程 | 只在需要时增加部署复杂度 |

## 9. 应持续保留的设计

以下内容不应在重构中被“顺手简化”：

- 一个线程同一时刻只有一个执行者。
- system prompt 冻结和长期记忆一次性注入。
- 工具统一经过权限、审批、超时、预算和结果裁剪。
- ThreadLog 的稳定 Item、Turn、revision 和恢复游标。
- 有界队列、分页、增量投影和断线补偿。
- Server/PostgreSQL、Desktop/SQLite 的统一存储语义。
- 渠道、网关、桌面、CLI 复用同一线程主链。

重构的目标是缩小依赖和明确责任，而不是让智能体失去业务上下文。业务上下文应在进入内核前被授权、快照化和类型化；内核只负责稳定地把这份上下文执行完。

## 10. 衡量重构是否有效

不要只以 crate 数量或文件数量判断解耦是否成功，应跟踪这些可验证指标：

- 新增一个工具、一个业务字段或一个入口时，必须修改的模块数量。
- API handler 中直接出现 `StorageBackend` 和业务写入的数量。
- 服务和编排器接收 `AppState` 的数量。
- 内核在不启动 Axum、数据库和完整应用状态时可通过的测试数量。
- 一次线程回合涉及的持久化写入次数、事件重复率和恢复补水时间。
- SQLite/PostgreSQL 行为契约通过率，以及 Desktop/CLI/Server 的线程回归一致性。
- 发生业务配置变更后，已运行线程的 prompt、工具面和记忆快照是否保持不变。

如果这些指标没有改善，仅仅把文件移动到新目录或新增 crate，不算完成架构演进。
