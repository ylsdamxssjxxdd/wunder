# 单节点 PostgreSQL 服务存储验收

本轮交付将舰体服务的线程历史、准入队列、展示索引、运行指标和业务状态统一到 PostgreSQL。蛹与舵机继续使用本地 JSONL + SQLite；工作区文件、附件和诊断输出仍使用文件系统。完整的完成消息、思考和工具轨迹按持久化策略保留，流式增量不另存成长期补丁历史。

验收仅使用隔离的合成数据库、用户、工作区和 Compose 项目。没有迁移、修复或删除已有用户数据库，也没有重启现有部署。测试模型通过真实 HTTP/SSE 返回确定性内容，浏览器通过真实 HTTP/WebSocket 访问服务，不拦截产品接口。

## 环境和构建边界

- 本机：Windows 11 AMD64，32 个逻辑 CPU，约 64 GiB 内存。
- Docker：Linux x86_64，32 个逻辑 CPU，约 31.2 GiB 可用内存；PostgreSQL 16；Docker 29.2.1、Compose 5.1.0。
- 服务使用 4 个工作线程。Linux release 与 Windows debug 分别验证，不将 debug 请求时延视为发行版性能。
- 报告分别保存二进制 SHA256。十分钟空闲和浏览器报告早于最后的异步栈、分页字节预算与搜索优化；最终 API 回归单独列出，不能把不同构建合成一次全项运行。

## 已确认的行为

服务的 canonical、admission、开始/终态与展示投影遵循 PostgreSQL 事务边界；沙箱使用部署中的数据库连接配置，连接失败明确报错。主服务和沙箱均检查没有生成本地 SQLite、会话 JSONL 或本地历史根标识。重启前后 canonical 数量、ordinal 和内容摘要一致，重开后可以继续对话。

读取采用 keyset 分页及字节预算：canonical 列表正文每批 4 MiB，展示重建每批 2 MiB；合法的较大单条记录独占一批，单条上限为 8 MiB。聊天响应、正文补水和搜索结果各自有界。超限、缺行或序号不一致时报告损坏，不能越过错误推进重建水位。

搜索在数据库内匹配解码后的正文，只返回限量片段。完整预览仅用于排除确定不命中的候选，截断、包裹或缺少元数据时仍查 canonical；隐藏字段、模型内部上下文不作为用户搜索结果。33 组只读比较结果一致，特定样本的 canonical 解码次数从 2121 降至 21；单次空载耗时没有改善，因此不据此宣称整体搜索提速。

Windows debug 实测发现首次执行的大型 async future 会耗尽默认线程栈，已在模型、压缩及工具调度边界局部堆分配；通过默认栈的完整文件工具生命周期和 future 尺寸约束验证，没有依靠增大线程栈绕过问题。

## 容量与样本口径

默认 API 样本为 30 个用户轮次 × 每轮 30 次模型请求，实际生成 900 次模型请求、708 次工具调用、1608 个模型动作、1638 个完成展示条目和 4267 条 canonical 记录（含初始化）。压力生成复用生产写入与投影链路，没有用直接插表代替。

[容量报告](2026-10-25-storage-capacity.json) 使用每张业务表 100 万行和 20 次初始化采样，大表初始化 P95 为 67.84 ms；业务行未重写、索引 OID 稳定、无旧执行历史表、分区维护无操作。这是业务表启动容量测试，不能描述为百万历史动作或百万并发用户验收。

canonical 逻辑字节、数据库和表索引物理字节分别记录。数据库总量包含基础表及整套用例的其他线程，不能直接除以某一个线程的正文大小当作放大倍数。本轮没有旧版近 10 GB 数据库的同负载前后对照，不承诺固定节省比例。

## 回归范围和复现

回归覆盖 PostgreSQL 准入竞态、幂等、冻结初始提示词、canonical 提交、分页/UTF-8/字节预算、展示重建、搜索、fork 独立性、连接释放、沙箱配置及无回退。另有共享 canonical/压力/事件流 45 项、本地 admission/生命周期 12 项、默认栈与 future 尺寸 2 项、外部验收驱动 27 项，以及蜂巢思考去重、统计和恢复 135 项定向前端测试通过。

此前集中 PostgreSQL 回归为 34 项中 33 项通过，一项搜索触发 300 ms statement timeout，单独复测通过。后续搜索候选过滤保持原有时限，没有通过放宽超时掩盖失败；最终针对搜索/重建与三项 reader 契约的 4 项真实 PostgreSQL 回归全部通过。SQLite-only 的 runtime 编译检查也通过。各次测试结果应按实际构建和执行范围理解，不将未执行或 ignore 项记为通过。

Docker 复现使用已经构建的 Linux 二进制和预先准备的运行镜像：

```powershell
python scripts/experience-bench/measure-hive.py --server-binary target/x86/release/wunder-server --output temp_dir/hive-storage-acceptance --profile smoke --user-rounds 30 --model-rounds 30 --idle-seconds 600
```

默认 14 个场景，包含两用户、两个容器作用域的真实沙箱并发文件写读、重启恢复和存储审计。省略 `--idle-seconds 600` 时只有 12 秒空闲 smoke。每个 API 场景只运行一次的 smoke 用于正确性和部署验收，报告中的同值 P50/P95 不代表稳定分位数；稳定时延对比应使用 daily/release 多样本并记录机器负载。

本轮验收范围是单节点本机和 Docker 服务。Win7/Ubuntu 18.04 真机性能、多节点共享存储和故障接管不属于本轮门槛。方案及后端边界见[存储设计方案](../对齐codex存储设计方案.md)。
