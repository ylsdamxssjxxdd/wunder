# 舰体 PostgreSQL 与 2000 用户并发审计

后续吞吐优化与 Linux 数据卷/Windows 挂载对照见 `2026-10-28-服务吞吐优化.md`。本页保留优化前的正确性与延迟基线，不将旧数据覆盖成新结果。

## 结论与适用范围

2026-10-28 使用本机 Docker Compose、隔离 PostgreSQL 16、新建合成账号和异步 SSE 模型进行实际压测。原实现确实存在并发异常，不是单纯的模型变慢。修复后的阶梯实测中，2000 个不同账号保持连接，随后同时提交 2000 个任务，全部收到终态、逐线程核对持久化输入与完整回复一致，清理前断连为 0。

这是短时合成负载下的正确性通过，不是“2000 个真实模型同时执行且低延迟”。2000 级完成 P95 为 120.725 秒，仍不能当作低时延生产 SLA。并发运行槽上限为 300，请求准备和受理共享 8 个异步准入槽；本次模型进程累计实际并行峰值为 27。

## 实测环境

- Linux AMD64 release 服务，Docker VM 32 vCPU、31.16 GiB；不是目标 ARM 服务器测试。
- 8 个业务 worker，PostgreSQL 连接池 64，固定独立 PostgreSQL I/O runtime；受限阻塞执行池最多 64 个 blocking 线程。
- 2000 个不同合成账号、不同令牌、独立任务线程；账号由 SQL 种子生成，不包含 2000 次密码散列登录峰值。
- 2000 路 WebSocket 完成握手，保持约 30 秒并检查应用层 ping；覆盖每 15 秒重新鉴权，不缓存凭据有效性。
- 模型每次返回 64 个片段，每段间隔 8ms；不使用真实推理、不计费，不代表大响应、工具调用或外部渠道吞吐。
- 阶梯为 100、500、2000，同时保留舰桥监控探针。探针中的 `health` 实际访问 `/wunder/i18n`，只代表 HTTP 存活，不是数据库深度健康检查。
- 每级核对 WebSocket 终态、UTF-16 文本增量位置和最终正文；再经真实 HTTP bootstrap 逐线程检查 `client_message_id`、用户输入、完整回复及 `completed` 状态。

| 100 | 100 | 100 | 0 | 4.315s | 7.186s | 7.457s | 7.625s |
| 500 | 500 | 500 | 0 | 15.101s | 26.028s | 26.773s | 27.635s |

阶段耗时包括最后的持久化核对；完成延迟从同时提交开始计算，包含请求准备等待和队列等待。500 级没有进入持久队列，不表示没有异步准入等待。2000 级 1111 个排队任务均通过最终显示快照取得一致正文；其他任务检查真实增量，不将补水伪装成实时 token。

在线建立 2000/2000 成功，连接 P95 118.630ms，约 30 秒在线检查无异常；最终所有连接清理前仍存在。三个阶段共 2600 次模型调用与 2600 次持久化核对通过。

2000 级 HTTP 存活探针 124/124 返回 200，P95 31.663ms、最大 186.983ms；舰桥监控 124/124 返回 200，P95 110.132ms、最大 268.677ms。500 级监控 P95 338.013ms、最大 727.386ms，未发生请求超时。最后 2000 行服务日志分类计数中，鉴权失败、数据库队列超时、执行超时和缺失线程均为 0；这是有界日志窗口，不宣称覆盖所有日志。

43 个资源样本覆盖约 220 秒。采样峰值：服务 599.5 MiB、401.74% 单核口径 CPU、113 个 PID/线程；PostgreSQL 418.8 MiB、488.63%、72 个 PID；模型 28.7 MiB。CPU 100% 表示一核，没有除以 32 核，也不是全阶段 CPU 平均值。容器内存是 Docker 统计值，不等于纯 RSS；约 5 秒采样不能保证捕获瞬时峰值。

## 独立复测

同一 release 二进制、另一全新 Compose 项目及数据库，再次保持 2000 个不同账号在线后，直接同时提交 2000 个任务：2000/2000 收到终态、2000/2000 持久化全文一致，清理前断连为 0。完成 P50 63.107 秒、P95 114.692 秒、最大 118.087 秒，含持久化核对的阶段耗时 121.473 秒；模型实际并行峰值为 34。

此次没有进入持久任务队列，主要等待发生在准备/受理准入闸；这与阶梯首轮的 1111 条持久排队不同，不能把“无持久排队”理解为没有等待。舰桥监控 103/103 返回 200，P95 415.470ms、最大 561.942ms。最后 2000 行服务日志的四类失败计数仍均为 0，33 个资源样本完整。两次均通过支持正确性结论，样本数量仍不足以给出稳定生产容量上限或时延承诺。

## 已复现根因与修复

1. **数据库驱动与业务线程环等待。** 同步 PostgreSQL 桥接曾使用调用者 runtime，连接网络驱动依附业务调度。业务 `block_in_place`、直接 `spawn_blocking` 与替补 worker 争用线程预算，可能让数据库网络驱动彻底没有机会运行。改为始终在复用的独立 PostgreSQL I/O runtime 驱动连接。
2. **受限类别仍共用耗尽的执行池。** 仅有不同 semaphore 不足以隔离，已获许可的工作仍会排在业务 runtime 的 blocking 池后。受限工作改用固定独立执行池；超时后不可取消的闭包仍持有许可，直到真实返回，不无限扩线程或提前释放额度。鉴权保留独立 8 槽通道，失败仍拒绝访问。
3. **256 活动提交被误拒绝。** 原提交闸把资源上限当参数错误；改为 256 槽异步背压并维持线程级互斥与有界弱引用目录。2000 调用回归检查峰值、回收与排空。
4. **显示降级误终止控制状态观察。** 排队任务的展示 feeder 短超时退出后，旧控制观察也随之退出，造成数据库已完成而页面一直忙。现在显示通道降级后继续观察任务终态，瞬时存储错误以可取消的故障重试处理，健康路径仍事件驱动。
5. **鉴权多次往返与无准入的请求准备。** 2000 次突发会同时做多阶段同步数据库准备，挤占业务与鉴权容量。PostgreSQL 将令牌、账号和登录代次合并为一次索引连接查询，不缓存有效性；过期、登录代次失效、设备撤销仍拒绝，旧令牌清理保持。请求准备与受理共享小型异步准入闸，在进入数据库通道前背压，运行中的线程、心跳和舰桥不再被突发准备任务挤死。
6. **舰桥标题 N+1。** 按线程 owner/session 成对批量读取标题，只取所需字段并分块；不逐线程打开完整会话，不越权读取其他用户标题。

## 反例不能抹去

| 修复阶段 | 真实结果 | 暴露问题 |
| --- | --- | --- |
| 原始基线 | 2000 在线；100 任务在 240 秒内完成 0，模型调用 0，舰桥超时 | 数据库 I/O 调度饥饿 |
| 仅隔离 PostgreSQL I/O | 100 完成；500 突发出现 181 个拒绝 | 256 提交闸错误拒绝 |
| 提交背压 | 500 全落库，仅 450 收到终态 | 显示 feeder 降级误结束观察 |

没有通过增加模型执行槽、无限扩缓存、关闭重鉴权或放宽撤销规则换取通过。300 执行槽的跨进程容量锁仍保留，表级准入锁与排队吞吐可能是进一步优化点，不能无事务约束地删除。

## 长线程与存储的相关验证

此前同一隔离 Compose 验证了 64 用户轮次、2048 模型请求、1573 工具调用、3685 条目和 9611 条 canonical 记录。继续执行 8 用户轮次的同时，每类取 24 个探针：舰桥概览 P95 19.702ms、元信息 27.673ms、预览快照 61.246ms。真实舰桥登录、线程管理点击轨迹、按需详情通过，展示 44 行虚拟 DOM，无 JS/HTTP 错误。

另一次 12 秒无 HTTP/WS 静默观察，单核 CPU 0.0833%、8 个历史业务表写入为 0、历史 SELECT 为 0、RSS 增量为 0。该观察不是 10/15 分钟静默验收，也不是 2000 压力后的长期泄漏证明。以上长线程/UI 结果来自前阶段构建，不冒充本次并发构建重新完成全部 UI 验收。

PostgreSQL 未发现本地旧链路的“完整文件再存数据库完整副本”。服务权威记录与有界展示预览的职责、仍可能重叠的模型回放/完成事件正文，详见 `2026-10-27-服务长线程性能.md`。本轮未删除业务历史、未执行物理缩库，不宣称所有正文只保存一次。
