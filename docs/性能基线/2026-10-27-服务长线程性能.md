# 服务长线程存储与性能审计

## 结论

舰体 PostgreSQL 没有发现与本地旧实现相同的「sessions 完整文件 + 数据库完整副本」双存链路。服务的权威历史位于 `service_thread_records`；展示表保存有限预览与消息 ID，监控表仅保存聚合事实，不保存完整请求、回复或事件数组。

这不代表正文在数据库中绝对没有重复：canonical 的 `response_item` 服务模型协议回放，`item_completed` 服务展示和审计，两者可能含相同正文；压缩检查点也保存被保留的上下文。它们的语义不完全相同，模型输入可能与可见输出不同。本轮没有删除这些记录，没有进行跨记录正文去重或现有业务库缩容，不能把「没有第二套完整日志」解释成「所有正文只出现一次」。

已确认并修复的长线程放大因素是：监控事件仅限条数、未限总字节；元信息查询在全局锁内复制事件正文；舰桥周期快照重复读取全文；统计查询反复扫描整条线程的条目。

## 存储权责核对

| 数据 | 实际内容 | 随历史增长的风险 |
| --- | --- | --- |
| `service_thread_records.record_json` | 权威 canonical 记录，含模型回放、完成事件与检查点 | 合法历史会增长，模型/展示正文可能重叠；没有宣称本轮已去重 |
| `service_thread_sessions.session_json` | 一线程一份冻结初始配置 | 与 SessionMeta 有小量重叠，但不是每轮复制整段日志 |
| `service_thread_items.preview_json` | 单条有限预览、身份和可见性 | 与条目数成正比，不是完整工具输出副本 |
| `service_thread_chat_heads.summary_json` | 每轮 ID、计数等展示摘要 | 不保存完整对话正文 |
| `service_thread_admissions.input_json` | 尚未物化的受理输入 | 物化提交后清 NULL，未执行输入保留；不是永久复制所有用户消息 |
| `monitor_sessions.payload` | `runtime_logs::monitor_facts` 白名单中的状态、计数 | 不含完整事件数组、请求与工具输出 |

审计入口为 `storage/postgres/thread_store.rs`、`thread_display.rs`、`admission_store.rs`、`monitor_store.rs` 和 `storage/runtime_logs.rs`。流式 delta 不作为逐 token 长期 canonical 历史保存。PostgreSQL 自身的索引、TOAST、WAL 和旧行版本也不能直接当作应用层日志副本。

合成样本的 2048 个完成事件占 canonical 逻辑 JSON 73,093,066 字节，展示预览占 4,952,839 字节；该样本刻意只写完成事件，用于比较展示读取开销，不能拿它推算真实模型回放的去重率。样本中的一条受理输入尚未物化，因此 `pending_inputs=1` 是预期状态。这里统计逻辑字段字节，不等同数据库物理占用。

## 根因与修复

1. **监控热路径。** 原事件 deque 虽然最多 500 条，单条仍可能带兆字节正文。`get_record` 及 overview 的整记录复制发生在共享 sessions 锁内，运行、停止、状态和舰桥查询均会受影响。现在每条诊断数据有 8 KiB 硬预算，并限制嵌套、数组与字段数量；最新 500 条之外淘汰，元信息查询不再携带事件。明确请求诊断尾部时另取最多 64 条；问题、摘要也限长。计费读取原始数值事实，不依赖截断预览，累计用量和模型轮次高水位独立保存。
2. **展示与恢复分离。** 新增 `thread_preview_snapshot`，PostgreSQL 舰桥轮询只取预览，最多 200 个用户轮次、500 条候选，预览 JSON 总预算 512 KiB；连同协议包装，最终响应可略大于 512 KiB。先选有限 ordinal，再读取预览，不把每轮全文拉入内存。通用 `thread_snapshot_window` 保留完整条目的恢复契约与原有字节预算。
3. **详情按需。** 舰桥仅在选中记录时读取完整 canonical 单条，并解析该条的 Schema；合并工具调用/结果最多取两条。仅缓存当前详情，切线程、关闭和销毁取消请求并释放数据；迟到响应不能覆盖新线程。轮询保留相同记录的选择，不反复重新解析当前长正文。
4. **统计增量维护。** `service_thread_display_state` 增加条目数和可见条目数；成功插入才增加，水位与计数共事务提交，重放不重复计数，fork 同事务初始化。旧线程缺少计数时仅在首次访问补算，随后不再按历史条数 COUNT。首次补算仍可能扫描长线程，升级不是零成本。
5. **轮询合并。** 调试轨迹最多一个快照请求在途，期间刷新合并为一次后继请求，并拒绝线程已切换的结果。

## 实测边界与数据

Windows AMD64 debug 测试程序连接隔离 Docker PostgreSQL 16，回环网络。使用生产 canonical 写入、展示读取和投影逻辑；没有访问、迁移或清理业务数据库。统计 SQL 交替采样 30 次，快照各单次；没有测生产 ARM release、高并发 p95、真实模型网络延迟或进程 RSS，因此不据此承诺生产 SLA。

| 规模 | 全文快照字节 | 预览快照字节 | 全文快照 ms | 预览快照 ms |
| --- | ---: | ---: | ---: | ---: |
| 128 条长输出 | 4,572,201 | 329,769 | 214.89 | 26.89 |
| 2048 条长输出 | 16,755,294 | 557,821 | 861.01 | 91.96 |

这是第一轮独立压测数据，后续全存储回归再次执行同一压测时有正常波动，原始输出另存。第一轮 2048 条场景传输量减少约 96.7%，单次读取约快 9.4 倍。它是同一修复构建对完整读取与预览读取的对照，不是两份历史二进制的全面性能对比。

第一轮统计 SQL 的 p50/p95：128 条时旧 COUNT 为 2.159/2.666 ms、计数投影为 2.162/2.555 ms；2048 条时分别为 2.781/3.340 ms 与 2.343/2.688 ms。小样本网络成本占比高，不能夸大收益；EXPLAIN 显示 COUNT 访问 2048 条历史索引记录和 158 个 buffer hit，投影访问一张小状态表的 1 个 buffer。状态表仅有少量行时 planner 合理选择 Seq Scan，不强制声明所有查询必走 Index Scan。

监控单测连续输入 600 次、每次含 1,300,000 字节正文，deque 保持 500 条，元信息响应约 0.6 KiB，100 次热读取 p95 在两次记录中约 0.007～0.015 ms。该测量不包含异步持久化、跨进程网络和并发竞争，不代表全请求延迟。

形式化模型和结果说明见 `../形式化证明/service-history-20261027/README.md`，原始测量见 `2026-10-27-service-history-benchmark.json`。模型复现三条旧反例，修复后四条不变量通过，`summary.json` 中原模型状态数为 1400、未溯源条件为空。模型只检查有限资源和事务投影抽象，不证明 PostgreSQL 引擎、任意规模正确性、活性或毫秒时延。

```powershell
cargo test -p wunder-runtime --lib --no-default-features --features sqlite-storage,postgres-storage ops::monitor:: -- --nocapture --test-threads=1

```

PostgreSQL 命令要求 `WUNDER_TEST_POSTGRES_DSN` 指向可丢弃的隔离数据库；不要对业务库运行。浏览器回归使用真实舰桥模块和受控 HTTP 响应，覆盖不提前取正文、工具调用/结果补齐、失败重试、轮询保持选择与跨线程迟到响应；不是完整部署的登录鉴权端到端测试。API 测试真实执行 SQLite/PostgreSQL 路由与完整正文读取，验证线程身份隔离，并检查新路由仍属于现有管理员鉴权路径。

本轮最终通过：PostgreSQL 存储 17/17、监控单元 20/20、监控集成 7/7、轨迹 API 2/2、self_status 相关 7/7、会话投影 16/16，以及舰桥 Playwright 回归与四个 JS 文件语法检查。不是仓库全量测试通过声明。API 合成环境曾因误用嵌入形态、缺少组织种子文件而失败，已经改用服务形态和合成组织数据后重跑通过；压测首次批量超过既有写入字节预算，缩小批次后通过，未放宽生产预算。

## 未声称解决的范围

- 不删除冻结 system prompt，不重新注入长期记忆，不丢弃模型恢复正文。
- 不自动清理业务历史、不执行 `VACUUM FULL`；已有物理空间不会因读路径优化自动缩小。
- 单次旧投影重建仍可能按多个有限事务扫描至固定水位；多用户总缓存规模、显式全历史导出、超大单条详情、模型上下文压缩和外部工具耗时仍需各自测量。不能宣称所有长时间运行变慢均只由这三处导致。
- 本轮定位的是确定存在的历史放大路径；若部署后仍卡，需要在目标服务器按同一线程采集 CPU、RSS、锁等待、慢 SQL 与模型/工具耗时，区分资源瓶颈。
