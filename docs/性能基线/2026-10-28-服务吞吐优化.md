# 舰体请求吞吐优化与磁盘对照

## 结论

之前的正确性通过不代表延迟合格。2000 个任务同时提交，模拟模型只需要约半秒，原 Windows 挂载目录环境的完成 P95 仍为 120.725 秒；不能解释成真实模型推理慢，也不能称作低延迟生产容量。

本轮保持 8 个 API worker、64 个 PostgreSQL 连接、300 个运行槽、8 个准备/受理准入槽不变，在后端减少数据库往返、同步阻塞与重复写文件。相同 Linux 数据卷环境，2000 任务完成 P95 从 48.769 秒降至 24.657 秒，减少 49.44%；原 Windows 挂载环境从 120.725 秒降至 100.800 秒，减少 16.50%。环境切换与代码优化必须分开比较，不能把 120.725 秒到 24.657 秒全部算成代码收益。

## 代码根因与处理

- PostgreSQL 同步适配器原来每次把 SQL 文本交给驱动重新准备；现在复用连接自带的预编译语句。连接独占使用，事务沿用同一个缓存，达到 256 条后清理；不会随动态 SQL 无限增长。缓存只保存语句，不保存查询结果或鉴权有效性。
- 请求初始化逐用户同步智能体配置，包含目录检查、JSON 读取、数据库读取及原子落盘，原实现直接在异步任务里执行。现在移至固定有界文件工作池，保留用户互斥；8 槽异步背压在进入文件队列前生效，不靠延长超时或扩线程掩盖慢磁盘。
- 工作卡每次导出都会改变 `metadata.exported_at`，导致逻辑未变化也进行原子替换与刷盘。现在比较投影的业务内容，仅忽略导出时间；真实提示词、模型、工具和其他字段变化仍写入，损坏文件仍修复，不关闭原子写安全性。
- 用户同步锁目录不再永久持有所有访问用户的强引用，改为活动锁的弱引用，按阈值回收空闲条目；正在执行及等待的同用户任务仍使用同一把锁。阻塞闭包持有许可和用户锁直到真正结束，取消等待不提前放开后台写入。
- 增加准备、受理及其等待阶段的聚合计时；压测保存真实运行指标，区分可恢复的显示超时与后端失败，不能只看最后部分日志就声称零超时。

线程首次系统提示词冻结、长期记忆初始化注入、登录代次、令牌撤销和设备撤销检查均不改变；跨进程运行容量表锁仍保留，没有用无界并行或放宽鉴权换吞吐。

## 实测比较

全部场景都是 Linux AMD64 release、PostgreSQL 16、2000 个不同账号和独立 WebSocket，在线约 30 秒后同时提交指定数量任务。模型每次 64 段、每段等待 8ms，不含真实推理、密码登录突发、工具执行及 ARM 性能。下表为完成 P95；最终构建各阶段全部收到终态且逐线程核对完整落库输入与回复，清理前断连为零。

| 数据路径与版本 | 100 任务 | 500 任务 | 2000 任务 |
| --- | ---: | ---: | ---: |
| Windows 挂载目录，旧版正式基线 | 7.186s | 26.028s | 120.725s |
| Windows 挂载目录，本轮最终构建 | 5.949s | 25.142s | 100.800s |
| Linux 数据卷，旧版对照 | 2.852s | 12.817s | 48.769s |
| Linux 数据卷，本轮最终构建 | 1.834s | 6.660s | 24.657s |

同一最终构建另起独立 Compose 与全新数据库，只跑 2000 级复测：全部完成并核对落库一致，断连零，完成 P50 13.753s、P95 22.690s、最慢 23.320s；后端队列/执行超时和 join 错误零，显示读取累计降级 348 次。两轮最终卷结果相互支持，但不是长时间稳定性验收。脱敏逐阶段数值、计时、诊断和资源摘要见 `2026-10-28-service-throughput.json`。

Linux 数据卷只用于工作目录及用户工具配置，PostgreSQL 在所有场景中原本就使用 Docker 卷。旧版卷对照保持旧二进制；最终两种存储路径使用完全相同的二进制，SHA-256 为 `497eb991e3582a319d5983944dccda00a056f9e56eddc5ea4465550fa99ecfe7`。模拟模型的并行峰值为进程累计值：旧版卷为 46，最终卷为 100，最终 Windows 挂载为 24，不把它当每级独立峰值。

最终卷场景的 2000 级舰桥监控 25 次请求全部成功，P95 75.657ms、最大 99.467ms；Windows 挂载场景 104 次全部成功，P95 40.163ms、最大 43.127ms。探针只覆盖 HTTP 监控，不替代完整浏览器交互。

运行指标显示：最终卷有累计 679 次显示读取短队列超时，触发既有视图降级与补水，但所有任务正文和终态一致；后端队列超时、执行超时和 join 错误均为零。Windows 挂载最终运行以上各类超时均为零。显示降级仍是性能问题，不宣称零异常或所有 token 都实时展示。

最终卷 Docker 资源采样的服务内存峰值 773.8MiB、CPU 峰值 638.43%（单核为 100%）、PIDs 峰值 112；缓存和更多同时运行让内存高于部分旧对照，不能宣称本轮降低内存。采样是 Docker 统计而非 RSS，间隔数秒，不是瞬时峰值或长期泄漏证明。

## 尚存瓶颈与优先级

1. **部署数据路径。** Linux 服务将数据库及热工作目录放本机 Linux 文件系统或 Docker 命名卷；不要用 Windows 跨系统挂载、网络盘等慢路径推断 Linux 上限。模型、附件和工作目录均需备份，迁移数据不可直接删卷。
2. **受理仍偏慢。** 最终卷三阶段累计受理耗时均值 81.58ms、受理等待均值 9.179s、最大 20.607s；准备约 15.03ms，准备等待均值 1.465s。这些是三阶段累计值，明确表明后端准备/受理吞吐仍是重点；不是 2000 个模型同时慢。
3. **跨进程容量协调。** 运行锁仍用表级串行事务，下一步可评估短事务或专用容量槽模型，但必须同时覆盖过期接管、暂停/恢复、取消、队列优先级和多实例容量上限，不能直接删除表锁。
4. **显示查询。** 合并同线程重复预览读取、减少每个状态边沿的数据库往返，继续保持分页、字节预算与最终补水。不能靠无界缓存或取消超时换取表面通过。
5. **目标服务器验收。** ARM、真实模型限流、长工具输出、多个服务副本及持续运行仍需在目标部署复测；本次不承诺 2000 用户同时运行低于数秒。

## 回归与反例

首个优化构建在卷场景通过，但移出同步文件操作后，Windows 慢挂载环境的 500 级出现 244 次文件队列超时。这是未通过的中间实验，不能删掉后只报告快的一轮。加入同步入口背压后，最终构建两种数据路径均通过 100/500/2000。

真实 Rust 回归通过：配置同步 12 项、聚合计时 3 项、PostgreSQL 6 项（含真实数据库语句缓存复用/上限/事务回滚和 I/O 饥饿）、鉴权快照 2 项、队列控制 3 项、受限工作池 8 项、WebSocket 帮助器 9 项、提交闸 5 项、准备背压取消 1 项、用户存储 11 项。队列控制重复运行须使用新 schema；复用旧测试数据曾导致断言失败，换全新隔离 schema 通过，不修改业务记录消除失败。

Python 容量工具回归 10 项、外部体验工具 27 项、形式化目录 6 项、容量摘要 4 项通过。形式化重新实际运行数据库 I/O 隔离模型：912 状态、2912 迁移，原反例成立，修复后两条不变量通过，并检查两张图。该模型不证明本轮语句缓存、磁盘容量、真实延迟或公平性；不能拿有限模型当吞吐证明。
