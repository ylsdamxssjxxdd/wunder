# 线程日志重构方案

> **落地修订（2026-09-30）**：ThreadLog 是唯一持久化聊天日志。启动时会删除旧 `chat_history` 表；聊天正文、分页、长内容、反馈、上下文、队列状态和用户删除均读取或写入稳定 Turn/Item。旧聊天 `/history` 和基于 `{history_id}` 的消息/反馈路由、前端回填与监控反馈副本均已移除。`stream_events` 仍保留给非聊天诊断与兼容业务，聊天恢复不再读取它。

| 已完成 | 单用户轮次助手气泡 | 转录层以持久 `turn_id` 合并同一根 Turn 的多次模型调用、工具调用前中间输出与最终回复；实时投影同步按规范用户轮次合并，并保留最终正文、推理、工具工作流和统计 |

本轮修订将用户侧 `workflow_only` 目录投影改为读取 ThreadLog Turn/Item；事件表只保留兼容传输和诊断用途，不得再作为轮次目录真相。后续实现必须按“写入闭环 → 上下文投影 → 实时协议 → 删除旧职责”的顺序推进，不能通过前端再次拼接事件补洞。

### 0.1 集成验收缺口

以下问题仍须以实际运行链路验证，不得以接口存在或编译通过作为完成依据：

- 上下文消息读取 `user_message/assistant_message/tool_message/system_message`，诊断条目不能替代工具结果；压缩标记与冻结 system prompt 通过稳定 Item 写入。数据库按 `created_seq` 裁剪，服务层将零或负数 limit 统一限制为 2,000 条，避免无界上下文。
- `thread_change` 必须使用已提交事务的真实 revision 和 change cursor，失败写入不得广播成功；Item 写入已返回事务提交后的真实版本与游标，无变化或失败不广播；已拒绝跨 Turn 复用 Item ID。Turn 状态变化现已原子递增接收 Item revision 并写入 item_upsert，内部用户角色消息不受影响；Turn 通知版本改用事务 change 序号。在线帧和重连补水已接通：客户端按受影响 Turn 拉取 Item 页面并以 `(item_id, revision)` 幂等合并，缺少稳定身份或游标过期时执行详情快照刷新。
- 增量帧保留助手/工具/命令的类型、稳定 Item 身份和内容序号；文本块是有界覆盖快照，不作为追加历史重放。
- WebSocket 恢复须实际消费 change cursor、过期快照与终态；恢复投影已读取 durable change cursor 并在游标过期时返回快照要求；生命周期变更与文本块使用各自序号，正文块作为有界覆盖快照返回。客户端已消费稳定身份并补水受影响 Turn；完整快照和队列 Item 终态已接入，仍需真实部署环境做一次端到端验收。
- 内容块 API 已实现 `field/from_block` 参数、`next_block/has_more` 分页响应；写入必须先存在同一会话、同一用户的 Item，读取继续执行 visibility 过滤。流式文本 Item 在 `llm_request` 提交时登记，后续增量只刷新对应正文/思考块。
- 分支复制必须分页覆盖所有根轮次与条目，保留内部模型消息、续跑关联、工具结果、内容块和终态；已移除单页助手复制适配器，改为 SQLite/PostgreSQL 事务内按根轮次边界复制完整 Turn/Item/Block 图，保留线程内身份、可见性、内容序号及终态，改写所属 session_id；目标必须为空，计数按复制边界重建。冻结提示词与运行检查点的分支语义仍须集成验收。
- `chat_history` 已硬删除：不创建、不迁移、不双写；启动初始化对既有数据库执行 `DROP TABLE IF EXISTS chat_history`。聊天反馈以 assistant `item_id` 原子写入对应 ThreadLog Item 的 versioned payload；分页游标使用 `created_seq`，不再暴露或生成 `history_id`。

### 0.2 刷新恢复与工具指标修订（2026-09-30）

- 工具结果 Item 保存 `event_type=tool_result`、`request_context_tokens`、`request_usage` 与 `meta.duration_ms`；历史投影按 Item 终态区分调用和结果，禁止把已完成工具重新投影为运行中。历史事件以 `(item_id, revision)` 去重，不能把轮内 `item_index` 当全局传输序号。
- 工作流快照按根 Turn 的 `next_after` 分页读取，单轮总量设为 10,000 Item 上限；恢复适配器展开 Item 的事件载荷封装，保留工具调用 ID、状态、上下文占用和耗时。会话首屏同时把 workflow-only 快照写入 canonical runtime projection，不能只在转录挂接阶段暂存轮次。
- 手动压缩将模型用量、请求数、额度、上下文占用、交互耗时和可测解码速度写入终态助手 Item；压缩状态仅在 `done/completed` 等明确终态时显示完成，`compacting` 保持进行中。
- 会话详情在读取消息前取得 `thread_change_cursor`，按字段、每页最多 100 块补齐进行中助手的正文与思考；完成消息仍以最终 Item 内容为准。块偏移采用 UTF-16，补水不得裁剪空白改变偏移。
- SQLite/PostgreSQL 的内容块更新和变更游标递增在同一事务提交；重复或过期块不生成新变更，变更索引保留最近 4,096 条。重连按持久游标读取变更并返回块覆盖快照，游标过期或超出当前高水位时要求重新加载快照；存储错误不得伪装为空页。
- 网页恢复统一为“详情补水 → watch”，移除旧 resume 文本处理链。watch 只在补水成功后确认游标，按受影响 Turn 顺序分页读取；正文块不触发整轮/整会话查询，工具与终态同步到实际消息投影。不可见 Item 只推进游标，不触发普通用户的内容补水。
- 运行状态与历史恢复分开：缓存没有活动连接时先显示静态历史，随后以服务端状态校正；恢复连接本身不产生运行状态。历史工具与晚到文本块不得复活终态消息；watch 在变更补齐后应用最新运行状态，状态变化不使用日志游标去重。
- 自动化覆盖活动文本跨页、正文/思考分离、重复块、独立游标、工具上下文与耗时、真实 store/watcher 的最终消息更新，以及刷新和切换线程期间的假运行状态。部署环境的真实模型、浏览器网络中断与 PostgreSQL 运行迁移仍属于集成验收，不能用本地编译与模拟传输测试替代。

### 0.3 单气泡归并修订（2026-09-30）

- 一个根 `Turn` 可以有多次 `model_round`：工具调用前的模型推理、工具执行和工具后的最终回答都属于同一条用户输入。历史转录必须以持久 `turn_id` 聚合普通 assistant Item，不能把 `model_round` 或 Item 数量映射成多个聊天气泡。
- 聚合选择含最终正文、稳定文本 Item 或统计的最终助手快照作为展示主体；正文与推理仅接受同一消息的前缀扩展或更完整快照，互不为前缀的中间模型文本不能拼接进最终回答。工作流、子智能体与统计字段做去重合并，保留工具上下文占用和耗时。
- 旧历史缺少持久 `turn_id` 时不得根据可能复用的 `user_round` 强行合并，保持既有保守投影；实时阶段已有规范用户轮次的临时消息仍在 runtime projection 中收敛，最终快照到达后由持久 Turn 投影定型。
- 手动压缩标记、取消和失败终态保持各自独立的特殊助手消息，不能被普通回答吞并。回归覆盖工具循环的中间输出、重复物化快照、最终统计以及权威停止快照，确保刷新前后都只显示一个普通助手气泡。

## 1. 重构背景与结论

重构前的“用户轮次缺失”来自同一会话存在三套不一致的数据源：

| 用途 | 重构前来源 | 结果 |
| --- | --- | --- |
| 用户聊天正文 | `chat_history` | 与事件日志分别保存，身份和分页不统一 |
| 用户侧线程日志 | `stream_events` 的 `workflow_only` 过滤结果 | 受事件保留期、事件类型过滤和事件分页影响 |
| 管理员线程详情 | `monitor_sessions.payload.events` | 仅保留内存/持久化记录中的最新 500 条事件 |

因此，“一个用户发送对应一个稳定用户轮次”只存在于部分运行路径中，没有成为可查询的持久化实体。管理员和用户侧都在从事件片段反推轮次，下拉选项自然会随事件数量、页面和保留状态改变。

应将线程日志重构为唯一的持久化模型：**线程（Thread）→ 执行轮次（Turn）→ 稳定条目（Item）**。用户侧和管理端使用相同的日志服务、相同的分页和相同的实时变更协议，只在后端鉴权后决定可见字段。`chat_history`、`stream_events` 和监控会话事件不再承担聊天历史或轮次目录职责。

`llm_output_delta` 应从持久化日志中移除。它只能作为在线传输帧存在；流式恢复改用进行中条目的文本块和快照，不再回放大量 token 事件。

本方案按原型阶段设计，**不保留旧接口、旧表或旧数据兼容层**。

## 2. 已定位的问题

### 2.1 管理端详情只有最新 500 条事件

`ops/monitor.rs` 的 `SessionRecord.events` 是 `VecDeque`，上限为 `MONITOR_SESSION_EVENT_LIMIT = 500`。超过上限时从队首删除；`get_detail_page` 仅对这个已经截断的队列做 `offset/limit` 分页。`admin/monitor/{session_id}` 因而无法读取较早的完整日志。

`web/modules/monitor.js` 又只根据当前响应页的事件生成轮次选项。只要当前页仍包含任意轮次，代码就不会使用 `session.user_rounds` 补齐缺口。事件多的轮次会挤掉更早轮次，翻页后下拉选项也会变化。这解释了“有时只剩中间一部分日志”。

### 2.2 用户侧把事件页当成轮次目录

`api/chat/events.rs` 的 `workflow_only` 读取 `stream_events`，按事件 ID 分页并从本页事件分组出 `rounds[]`。`MessengerTimelineDetailDialog.vue` 同样只从当前页面的 `rounds[]` 构造轮次选择器。

这有三个缺陷：

- 一个轮次是否出现取决于该页是否恰好含有可展示的工作流事件；轮次边界和用户输入本身不是独立的权威记录。
- `workflow_only` 会排除 `llm_output_delta`、`llm_output`、`final` 和 `thread_closed`；只含被排除事件的轮次无法成为目录项。
- `stream_events` 是重连缓冲区，配置的保留清理会删除旧行。旧事件消失后，用户侧日志目录也随之消失，尽管 `chat_history` 中的可见消息还在。

### 2.3 完成轮次主动删除增量，语义却仍依赖事件流

当前运行时会缓冲并持久化 `llm_output_delta`；模型轮次完成且助手消息写入 `chat_history` 后，又按 `(session_id, user_round)` 删除该轮的增量行。这个节省空间的动作本身合理，但它暴露出架构矛盾：完成消息放在 `chat_history`，日志目录和工具过程放在 `stream_events`，管理员又读监控事件镜像。任一来源被裁剪、过滤或延迟写入，视图就不完整。

### 2.4 事件不是轮次

事件适合短期传输和调试，不适合定义业务历史：

- 一次用户轮次可产生任意数量的模型、工具、队列和子智能体事件。
- 同一条目的开始、进行中、完成会产生多条重复状态。
- 分页单位是事件会将一个轮次切开；按事件数量限制也会令高频输出挤掉低频轮次。
- 监控载荷会裁剪、合并或保留尾部；它不能承担会话恢复的真相来源。

## 3. 重构目标与约束

1. 每条被服务端接受的用户输入，先原子创建一个可查询的用户根轮次；排队、失败、取消、空回复都保留该轮次及终态。
2. 用户轮次、自动续跑和模型调用均使用稳定 ID；不得再由时间、正文或当前事件页推断身份。
3. 任意历史页、管理端详情页和实时重连都能列出完整轮次目录。列表分页只按轮次进行，条目分页只在单个轮次内进行。
4. 流式输出保持低延迟。在线传输可以发送增量，持久化层只保存稳定条目和有界的正文恢复状态。
5. 用户界面和管理端读取同一 `ThreadLogService` 投影。管理员可查看经后端授权的诊断字段，不能拥有另一套轮次分组规则。
6. 线程首次确定的 system prompt 继续冻结；长期记忆仅在线程初始化时写入。日志重构不得通过重新拼接历史来改写它们。
7. 读取、写入、缓存和队列均有界；不全量扫描事件、不完整复制长正文、不把整个会话重建到 UI 线程。

## 4. 目标领域模型

参考 Codex 的“`Turn` 持有稳定 `Item`，实时只发布变更集”的思路，采用以下对象。

```text
Thread
├── Turn（一次执行单元，稳定 turn_id）
│   ├── UserMessageItem
│   ├── ModelCallItem × N
│   ├── AssistantMessageItem × N
│   ├── ToolCallItem × N
│   ├── ApprovalItem / PlanItem / CompactionItem / SubagentItem × N
│   └── ErrorItem / TerminalItem
└── Change cursor（仅用于实时重连，不是历史真相）
```

### 4.1 Thread

`Thread` 与现有会话一一对应，保存所有权、组织范围、创建时间、冻结提示词引用、最新变更游标和最新用户轮次序号。它是访问控制与日志查询的根。

### 4.2 Turn

`Turn` 是服务端调度的稳定执行单元，使用不可变 `turn_id`。字段至少包括：

- `turn_id`、`root_turn_id`、`session_id`
- `trigger_kind`：`user`、`continuation`、`system`
- `user_turn_index`：仅用户根轮次有值且严格递增
- `status`：`queued`、`running`、`waiting_input`、`completed`、`failed`、`cancelled`、`interrupted`
- `started_at`、`completed_at`、`duration_ms`
- `input_item_id`、`last_visible_item_id`
- 用户轮次汇总指标和终态错误摘要

一次用户输入创建一个 `trigger_kind=user` 根轮次。由子智能体回流、目标续跑或定时任务触发的自动执行创建独立 `turn_id`，以 `root_turn_id` 关联原用户轮次。页面按根用户轮次组织；自动续跑不会伪造新的用户输入，也不会覆盖旧轮次。

`model_round` 不再用来定义轮次目录。它仅是 `ModelCallItem` 在所属 Turn 内的序号，用于诊断和模型调用关联。

### 4.3 Item

`Item` 是一个可独立更新、完成和分页的稳定对象，使用不可变 `item_id` 与 Turn 内严格递增的 `item_index`。公共字段为：

- `item_id`、`turn_id`、`item_index`、`kind`、`status`、`revision`
- `visibility`：`user`、`admin`、`model_internal`
- `created_at`、`updated_at`、`completed_at`
- `summary`、`payload`、`content_ref`、`error`

`kind` 初始覆盖用户消息、助手消息、模型调用、工具调用、审批、计划、压缩、子智能体活动、命令会话、状态提示和错误。一个工具调用以同一个 Item 从 `running` 更新到终态，不能再用“调用事件 + 结果事件 + 前端配对”恢复它。

完成的 Item 内容不可变。确有迟到结果时更新原 Item 的 `revision`；客户端依据 `(item_id, revision)` 幂等覆盖。显式回退、裁剪或删除使用墓碑变更，不能依靠前端猜测消失原因。

## 5. 存储设计

SQLite 与 PostgreSQL 采用相同逻辑表和索引；具体类型由各自方言实现。

| 表 | 职责 | 关键约束与索引 |
| --- | --- | --- |
| `thread_logs` | 线程根、归属、冻结上下文引用、最新游标 | `session_id` 主键；所有权/组织范围索引 |
| `thread_turns` | 稳定 Turn 及终态、汇总指标 | `(session_id, turn_id)` 主键；`(session_id, user_turn_index DESC)`；用户根轮次唯一约束 |
| `thread_items` | 条目元数据、状态、小型结构化载荷和内容引用 | `(session_id, item_id)` 主键；`(session_id, turn_id, item_index)` 唯一 |
| `thread_item_blocks` | 用户正文、思考、命令输出等大文本的分块内容 | `(session_id, item_id, field, block_index)` 主键 |
| `thread_log_changes` | 有界的实时重连游标、条目变更引用和墓碑 | `(session_id, change_seq)` 主键 |
| `thread_log_metrics` | 管理端列表、统计图和配额需要的聚合指标 | 按会话、时间和必要维度建立索引 |

`thread_log_changes` 只保存 `turn_upsert`、`item_upsert`、`item_delete` 和终态变更的标识、版本和游标。读取时将同一条目在一个批次内合并为最新版本；历史真相始终来自 `thread_turns` 与 `thread_items`，因此变更游标过期时可安全要求客户端获取快照。

长文本不放入重复 JSON 事件中。进行中的助手文本使用固定大小内容块，另有一个固定上限的活动尾块。块按顺序落库，完成时先刷新尾块再提交 Item 与 Turn 终态。这样刷新或服务重启能重建已确认正文，又不会每收到一个 token 就复制整段内容。

`model_internal` Item 可服务于下一次模型上下文构建，但默认不会返回给普通用户。冻结 system prompt、记忆初始化结果和会话运行检查点仍由各自专用存储保存；日志只保存它们的引用和必要状态，避免重复注入或泄露。

## 6. 写入与实时协议

### 6.1 原子写入边界

1. 接受用户请求：同一数据库事务创建根 Turn、用户消息 Item、初始状态和第一个变更游标。`client_message_id` 在 `(session_id, client_message_id)` 上唯一，重复请求返回原 Turn。
2. 调度执行：创建或更新模型、工具、审批等 Item。每次状态变化与对应变更游标在同一事务提交。
3. 流式正文：仅向在线连接发送 `thread_item_delta`；后台以固定时间或固定字节阈值刷新内容块和活动尾块。在线合并按帧进行，按序号校验，不能丢字。
4. 结束执行：先刷新正文块，再在单一事务中写入最终 Item、Turn 终态、汇总指标和终态游标；事务提交后才广播终态。

监控指标由上述提交后投影更新。监控写入失败不能影响 ThreadLog 真相；监控不再反向作为会话恢复输入。

### 6.2 新协议

实时通道统一发送三类帧：

- `thread_change`：已持久化的 Turn/Item 版本或墓碑，携带 `cursor`。
- `thread_item_delta`：仅在线连接的文本增量，携带 `item_id`、`content_seq` 与字段名，不进入持久化变更日志。
- `thread_snapshot_required`：客户端游标过旧、检测到间隙或切换线程时要求重新拉取快照。

重连时客户端提交最后确认的 `cursor`。服务端返回有界 `thread_change` 批次；若游标已清理，返回当前活动 Turn 的快照和最新游标。客户端以 `item_id + revision` 合并，实时尾部以 `content_seq` 合并；不再读取或拼接 `llm_output_delta`。

## 7. 统一查询 API 与页面投影

新 API 以 Turn 为分页单位：

- `GET /chat/sessions/{id}/thread-log/turns?before=&limit=&view=summary`：倒序读取轮次目录和每轮摘要。
- `GET /chat/sessions/{id}/thread-log/turns/{turn_id}?view=full`：读取一个 Turn 的完整 Item 列表；长内容按需读取块。
- `GET /chat/sessions/{id}/thread-log/changes?after=&limit=`：实时重连补水。
- `GET /chat/sessions/{id}/thread-log/items/{item_id}/content?field=&from_block=`：分块读取长内容。

管理端可通过管理路由使用同一服务和响应结构；权限解析发生在服务端，普通用户不能借由 `view=full` 得到 `admin` 或 `model_internal` 内容。管理员查看的“运行日志”与用户看到的“线程详情”使用同一 Turn 时间线，差异只在可见 Item 和诊断字段，不得再各自从监控事件或工作流事件分组。

前端不再使用轮次下拉框承载无界历史。两端均使用虚拟化轮次列表：初始读取最近有限页，向前加载旧轮次；当前选择保持 `turn_id`，翻页不会替换或删掉已选择的轮次。单轮内部也使用 Item 分页和展开式内容读取。

聊天主界面的消息列表是 ThreadLog 的用户可见 Item 投影。原 `transcript`、轮次详情、日志导出和会话恢复必须调用同一投影器，不能另行根据正文或时间戳排序。

## 8. `llm_output_delta` 的处置

| 项目 | 新规则 |
| --- | --- |
| 在线流式 | 保留能力，事件改名为 `thread_item_delta`，只走 WebSocket/SSE 内存传输 |
| 持久化事件 | 移除 `llm_output_delta`，不再进入 `stream_events`、监控记录或导出 |
| 刷新与重连 | 读取进行中 Item 的内容块、活动尾块和稳定变更游标 |
| 完成消息 | `AssistantMessageItem` 的最终内容和统计为唯一权威记录 |
| 速度统计 | 从 `ModelCallItem` 的最终计时和用量读取，不统计 token 事件 |
| 命令与工具增量 | 同样仅作为在线尾部传输；完整输出进入对应 Item 的内容块或受限摘要 |

这不是取消真实流式输出。用户仍会立即看到连续文本；区别是传输增量不再被误当作历史数据模型。完成、刷新、切换会话和管理员查看均直接读取稳定 Item。

## 9. 实施顺序

1. 在 runtime 新建 `thread_log` 领域模块、SQLite/PostgreSQL 表实现、结构体和统一投影服务；先覆盖 Turn、Item、内容块、变更游标与访问控制。
2. 将编排器写入链改为上述原子边界；队列、取消、工具、审批、压缩、目标续跑和子智能体回流全部传递 `turn_id/root_turn_id/item_id`。
3. 将聊天历史上下文构建改为读取 ThreadLog 的模型可见 Item；保留会话冻结提示词与初始化记忆的现有边界。
4. 替换用户侧聊天恢复、线程详情和导出；替换管理端会话详情、筛选和导出，使二者调用同一投影服务。
5. 替换实时推送与重连逻辑；删除 `llm_output_delta`、`tool_output_delta`、`command_session_delta` 的持久化分支及其前端回放逻辑。
6. 将监控改为只读聚合投影，移除 `monitor_sessions.payload.events` 作为日志存储的职责。
7. 删除 `chat_history` 的消息真相职责、`stream_events` 的会话历史职责、旧 `/history`、`/events`、管理员监控详情日志接口及其测试夹具。发布时清空旧会话日志数据并删除旧表，不提供双写、回退读取或数据迁移。

## 10. 验收

- 创建超过 500 个用户轮次后，用户侧和管理端均能通过轮次分页访问首、中、尾任意轮次；轮次目录不依赖当前 Item 或事件页。
- 无工具、空回复、排队、模型失败、取消和自动续跑均会保留对应 Turn，并有明确终态。
- 刷新、断线重连、服务重启和切换会话后，已确认的助手文本、工具状态和选中 Turn 一致；重复变更和重复实时帧不会造成重复消息或漏字。
- 同一会话的用户侧与管理端在相同权限可见范围内返回相同 Turn ID、Item ID、顺序和状态。
- 长文本、长命令和高频 token 输出不会使单次查询、内存队列、DOM 或数据库 JSON 行无界增长。
- 严格验证所有权、组织范围、管理员权限与 `visibility`；普通用户无法读取内部上下文或管理员诊断字段。
- 全量删除旧持久化增量类型后，代码搜索不再存在将 `llm_output_delta` 作为历史恢复、轮次目录或日志导出输入的路径。

## 11. 参考实现的取舍

参考实现的关键价值不是照搬其文件格式，而是三项模型边界：稳定 Turn ID、稳定 Item ID，以及将实时变化压缩为幂等的 `changed_items/changed_turns/removed_turn_ids`。其分页历史也区分 Turn 元数据、摘要 Item 和完整 Item，避免通过重放原始事件构造界面。

Wunder 应采用这三项边界，并保留自身的多租户、队列、工具审批、蜂群、长期记忆和冻结提示词语义。ThreadLog 负责可见历史和工作流投影；调度运行态、模型上下文和监控指标分别保持专用存储，不能再混为一条事件流。
