# 工作区与工作目录

## 原理

wunder 的工作区是有明确隔离策略的文件空间。隔离只有一层：**按用户隔离**。

### 一层隔离

```
用户A的工作区（唯一云端目录）
├── 用户上传的文件
├── 智能体生成的文件
├── 智能体可见的配置（技能、知识、全局设置）
└── 运行期快照与诊断

用户B的工作区（完全隔离）
└── 与用户A互不可见
```

- 不同用户的文件完全隔离，互相看不到
- 同一个用户只有一个工作区，不再按「个人文件 / 智能体文件」再分一层
- 用户工作区与智能体实例一一对应：一个用户，一个智能体，一个云端目录

### 关键约定

| 约定 | 说明 |
|------|------|
| **唯一** | 每个用户在同一时刻只有一个工作区目录，服务端不为第二个智能体再开目录 |
| **固定** | 目录由服务端在数据根下按用户划分，用户不能新增、删除或更换 |
| **不可绑定本地路径** | 云端工作区始终在服务端，不映射用户本机目录 |
| **相对路径** | 界面上展示与接口收发的路径一律是工作区相对路径，不展示服务端绝对路径 |

## 作用

### 数据隔离

- 不同用户的文件完全隔离，任何用户只能访问自己的工作区
- 工作区以用户根为界做路径校验，越界读写会被拒绝
- 智能体的文件工具以这个用户目录为根，不再按智能体或容器派生第二个根

### 文件持久化

- 工作区是持久存储，不会自动清理
- 用户上传的文件、智能体生成的文件都会持久保存
- 需要长期保留的文件放工作区；临时中转放临时目录

### 智能体可见配置的根

工作区同时是「智能体能看到的配置」的根目录：

- 技能目录
- 知识文件
- 全局设置

智能体启动时会读取这些内容来初始化。需要说明的是，**智能体的模型、提示词、工具与审批模式等配置由管理侧预设绑定与设置页管理，不是靠用户在工作区里手写文件**。

## 实践

### 访问工作区

- **网页端**：左栏工作区下方的「工作目录」区，含文件树与工具栏（上传 / 新建 / 刷新 / 多选）
- **本地形态**：蜂窝使用本机上的一个持久目录，可直接用系统文件管理器查看
- **对话中使用**：上传文件，或让智能体读写文件
- **引用到聊天**：文件行菜单选「引用到聊天」，把文件带进输入区
- **下载文件**：在文件树里选中文件下载，多选可打包下载

### 文件组织建议

**按项目或主题建子目录**：

- 一个项目一个目录，目录内再分资料与产物
- 想让智能体分析的文件先上传，再在消息里说明路径或文件名
- 智能体生成的报告、脚本、中间产物也落在同一个目录树下，需要时自行整理

**及时清理与命名规范**：

- 不需要的文件及时删除，保持目录整洁
- 文件名取有意义的名字，方便自己和智能体查找

### 用量与空间

- 文件区底部显示已用容量、文件数与目录数
- 统计走有界遍历，大目录下会标注统计为下界
- 服务端若配置了配额，超限时上传会被拒绝并提示清理；未配置配额时只显示已用量，不显示配额分母

### 本地形态的差别

蜂窝（desktop）在本地运行，工作目录是用户本机上的持久目录而不是临时沙箱：

- 目录内容持久保存，不走定期清理
- 智能体可以访问本机路径，取决于本机安全设置
- 更灵活，但也要更清楚目录边界

## 常见误区

- **工作区可以换目录吗？** 不可以。云端工作区由服务端按用户固定分配，不能更换，也不能新增第二个。
- **智能体越多，工作目录越多吗？** 不是。每个用户只有一个智能体实例，也只有一个工作目录。
- **文件要分「个人容器」和「智能体容器」放？** 不用。这个分层已经取消，用户和智能体共用同一个用户目录。
- **路径写绝对路径更快？** 不要。接口收发都是相对工作区根的路径，绝对路径不对外暴露。
