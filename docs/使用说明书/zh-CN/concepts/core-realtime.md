实时性指的是三件事：**过程持续可见**、**断线能补齐**、**客户端看到的与后端真相一致**。做法是「持久事件 + 游标补水 + 有界投影」，不依赖重连后的全量重拉。

## 真相与投影

线程日志是唯一真相源。每一次事件推送在发出前，都会**先同步写入持久层**，然后才走实时通道。变更唤醒信号只负责叫醒订阅方，**不是数据源**，也不是真相。

由此有三个直接后果：

- 推送丢了可以补回来，真相不会丢。
- 界面显示异常时，以实际执行状态为准，不要凭界面判断任务是否结束。
- 判断一轮结束没有，只看终态事件，不看「好像没动静了」。

## WebSocket 端点

聊天内容的流式输出只走 WebSocket。用 HTTP 请求聊天流会被拒绝，并回提示改用 `/wunder/chat/ws`。SSE 只用于外部工作流，**不是聊天的兜底通道**。

端点按用途分布：

| 端点 | 用途 |
| --- | --- |
| `/wunder/chat/ws` | 线程运行时主通道：连接、心跳、启动、恢复、订阅、取消，以及目标类与审批类消息 |
| `/wunder/ws` | 核心请求面：请求提交与流式返回 |
| `/wunder/gateway/ws` | 网关三种角色（操作端、节点、渠道）的请求/响应/事件/心跳 |
| `/wunder/interlink/ws`（配套 `POST /wunder/interlink/channel_ticket`） | 本地节点反向隧道 |
| `/wunder/interlink/remote_ws` | 浏览器旁观远端单线程，纯转发不落库 |
| `/wunder/user_world/ws`、`/wunder/desktop/lan/ws` | 世界会话的订阅与发送；局域网组网 |

握手与鉴权：先发一个连接信封，或直接用 `access_token` / `token` 查询参数。握手没完成的其它消息会被拒绝。

## 事件

事件名没有集中枚举，散在各发送处，新增时也直接补在发送处。当前实际存在的事件按用途分成这些：

| 类别 | 事件 |
| --- | --- |
| 投影与补水 | `thread_view_change`、`thread_view_required`、`thread_snapshot_required`、`thread_status` |
| 线程内容 | `thread_item_tail`、`thread_item_delta` |
| 模型输出 | `llm_output_delta`、`llm_request` |
| 工具 | `tool_call`、`tool_result` |
| 排队 | `queue_enter`、`queue_update`、`queue_start`、`queue_finish`、`queue_fail` |
| 用量与额度 | `model_request_usage` |
| 终态 | `final`、`turn_terminal` |
| 流控与错误 | `heartbeat`、`slow_client`、`stream_overflow`、`error`；`resume_recommended` 随 `slow_client` 或 `stream_overflow` 一并发出 |

## 断线补水

断线重连不重新拉全量，而是带游标补齐。三个游标各管一段：

| 游标 | 含义 |
| --- | --- |
| `change_seq` | 线程变更序列，请求时带 `after_change_seq` 指明从哪之后开始补 |
| `view_seq` | 展示投影序列，客户端按它判断本地投影是否落后 |
| `event_seq` / `event_id` | 单条事件的序号，随事件一起下发 |

补齐走 HTTP 端点，鉴权与用户面相同：会话线程日志的变更、快照与事件（`/wunder/chat/sessions/{id}/thread-log/changes|snapshot|events`），以及展示投影的引导、聊天、轨迹、变更与搜索（`/wunder/chat/sessions/{id}/view/bootstrap|chat|trajectory|changes|search`）。消费侧每次固定取 200 条变更，读满一页立刻继续取下一页。

提交是幂等的：提交时带上 `client_message_id`，重复提交会直接判「已接受」并返回原结果。重连后重发同一条消息不会写两份。

## 背压与上限

实时通道处处有界，关键数值如下：

| 项 | 值 |
| --- | --- |
| 单订阅写队列 | 256 |
| 慢客户端水位 | 队列剩余 ≤ 2 即判慢 |
| 单次拉取上限 | 200 |
| 心跳间隔 | 15 秒 |
| 单条消息上限 | 512 KiB（互通远观为 256 KiB） |
| 用户输入上限 | 1,048,576 字符（图片附件不计入） |

慢客户端的处理是**先通知再脱钩**：写队列越过水位时，先发 `slow_client` 或 `stream_overflow`，并带上 `resume_recommended`，随后断开该订阅。落后的订阅退出、走补水重建，慢客户端不会把整条流和引擎拖住。

收到 `resume_recommended` 后，走上面的补水端点重建投影，再带新游标重新订阅；同一个连接不会把漏掉的内容补回来。

## 展示读取分页

大数据量线程的时间线与轨迹不靠一次拉全，而是分页且有响应预算：

| 项 | 值 |
| --- | --- |
| 聊天页大小 / 上限 | 12 / 20 |
| 轨迹页大小 / 上限 | 80 / 100 |
| 响应预算 | 聊天 128 KB、轨迹 192 KB |
| 正文分块 | 8192 字节 |

投影还没就绪时，读取会回落到源表的**有界窗口**：页大小按上限截断，再按响应预算截断。后台重建有占空比上限（不超过 1%，失败后按 5 秒到 300 秒退避），所以刚导入或刚被大量改动的线程，可能短时间仍从源表读，表现是首屏稍慢，而不是数据缺失。

线程目录分页上限是 100，关键词搜索最多扫描 10 页 × 100，也就是 1000 条，超出部分搜不到，这是刻意的延迟上限。

## 互通

本地设备（蛹、舵机）与云端之间的实时面是互通，与上面的客户端 WebSocket 不同：

- **本地节点只出不入**：不开监听端口，由本地自己发起一条长连接，控制、数据、命令三个平面都复用这一条连接。
- **影子投影**：云端持有本地线程与工作区目录的投影，落库有活通道门禁，通道过期就不再写新影子。
- **命令台账与审批**：命令、确认、事件、结果都记账。风险按 L0–L3 分层，`tool.exec`、`agent.spawn` 属 L3，默认设备能力集不含 L3，且 L3 审批不可记忆。
- 互通治理目前只有后端接口，**舰桥没有互通的面板**。

细节与协议见 [互通](/docs/zh-CN/capabilities/interlink/)。
