# 应用补丁

> **已并入**：`应用补丁`（`apply_patch`）已并入 `文本编辑`（`edit_file`），不再作为独立工具暴露，只保留旧调用名可被识别。

补丁形态适合“少量文件、少量改动、上下文明确”的精确修改，并保留上下文便于审查。整文件写入交给 `write_file`，命令执行交给 `execute_command`。

## 怎么写一份补丁

最小示例：

```text
*** Begin Patch
*** Update File: src/main.rs
@@
-fn old() {}
+fn new() {}
*** End Patch
```

模型侧常用参数只有两个：`input` 和 `dry_run`。

## 推荐流程

按这个顺序：

1. 先读取目标文件或精确片段
2. 一次只构造一个很小的补丁
3. 不确定上下文是否稳定时，先加 `dry_run` 预演
4. 预演通过后，再去掉 `dry_run` 正式提交
5. 改动跨很多分散区域、或已接近整文件改写时，改用 `write_file` 或脚本

## 更新文件的硬规则

- `@@` 之后每一行都必须有前缀：空格、`-` 或 `+`
- 空白上下文行不能留空，要写成“只有一个前导空格的一行”
- 改某一行时，必须写成 `-旧行` 再 `+新行`
- 不要把旧行和新行都写成普通上下文行
- 不要复制读取结果里的 `>>> 路径`、行号或分隔符
- 每处修改前后，尽量保留 2-3 行原始上下文

工具会容忍几类常见小偏差（比如漏写 `*** Begin Patch`、把 `@@ -1,3 +1,3 @@` 写成 unified diff 头、`Add File` 中误写 `@@` 或漏写 `+`），但这只是为了提高首次成功率，仍建议按最小标准格式写。

## 新增文件

```text
*** Begin Patch
*** Add File: notes.txt
+第一行
+第二行
*** End Patch
```

## 预演（`dry_run`）

`dry_run` 与正式执行共用同一套暂存、目标冲突检查和上下文匹配逻辑，通过后丢弃结果、不写磁盘。不确定格式、改动位置敏感、或第一次用这个工具时，先预演一遍。

## 改动预览

结果里会带一份改动预览：每个文件最多显示 80 行，单次调用合计最多 320 行、24 KiB。超出剩余预算的行会整行省略，已显示的行内容和原始行号保持准确。这个限制同样适用于预演，只影响展示，不会缩减实际改动，也不能当作被删内容的备份。

模型只收到文件摘要和准确的增删行数，不接触预览正文。

## 出错时怎么判断

补丁失败通常落在这几类：补丁为空、输入过大、文件操作数或改动块过多、执行过程中任务失败，以及解析失败、路径越界、目标冲突、上下文不匹配。用户侧看到的是一句失败说明加下一步提示。

常见失败原因：

- 补丁正文又被包了一层 JSON 或 Markdown 代码块
- `@@` 后直接粘贴原文件内容，没有给每一行加前缀
- 空白上下文行写成了真正的空行
- 旧行和新行都写成了空格前缀的上下文行
- 复制了读取结果里的行号或 `>>> 路径`
- 一次改太多分散区域，超出它的适用范围
- `-旧行` 和 `+新行` 内容实际相同，补丁“执行成功却没有变化”

## 更具体的修正提示

上下文匹配失败时，工具会尽量说清是哪一类问题，而不只是“上下文没找到”：

- 某个改动块只有上下文、没有实际改动 → 空块
- 后一个块复用了前一个空块的同一组锚点 → 重复锚点、多写了一个 `@@` 块
- 把要删除的行同时又当成了上下文行
- 补丁看起来有改动、文件却没变化 → 区分“只有上下文”和“旧行新行相同”

遇到这类提示时：删掉没有 `+` / `-` 的空块；把同一处的插入或替换合并回一个块；不要让两个连续的块复用同一组锚点；纯插入的块尽量同时保留头部和尾部原文。

## 适合与不适合

它更适合“中小批量精确编辑”：改几行代码、加一个小函数、调整几个独立文件。

不适合整文件重写、大批量生成文档或资源、需要先跑脚本再产出结果的修改，以及跨很多分散区域的大型重构。整文件重写用 `write_file`，先跑命令再用 `execute_command`。

## 和 `write_file` 的区别

- `apply_patch`：保留上下文，便于审查
- `write_file`：直接覆盖最终内容

已经知道整个文件应该长什么样，用 `write_file` 更直接；只想做精确改动，补丁形态更稳。
