# 蜂窝本地模式

蜂窝本地模式是 wunder 当前最贴近真实个人使用的形态。

## 常见误解

不要把它理解成「小号 server」或「少了管理员后台的 server」。它是本地优先的完整运行形态：一台电脑上就能完成日常全部工作。

## 本地模式最核心的特点

### 工作目录是持久的

本地模式下，工作目录不是临时 sandbox。

- `WUNDER_WORK/` 按持久目录处理
- 不走 24 小时自动清理

### 工作目录是本地真实目录

本地形态下，工作目录直接落在用户本机的持久目录上：

- 目录内容持久保存，不走定期清理
- 智能体直接读写这个目录，不需要在「沙箱目录」和真实目录之间来回映射
- 与云端形态的区别只是位置：云端是服务端数据根下按用户划分的唯一目录，本地是本机上的持久目录
- 两种形态都是「一个用户一个智能体实例 + 一个工作目录」，没有容器分层

### 优先使用附带运行时

蜂窝本地模式优先使用安装包附带的 Python 运行时，减少首次配置成本。

## 本地模式作为第一入口的原因

个人使用的完整主链路——用户侧界面、对话执行、工具调用、工作区文件、智能体设置、子智能体——在本地模式下都能覆盖，日常使用不需要再切换其他形态。

## 本地模式下的文件能力特点

当前一个关键约定是：

- 本地模式下，内置文件工具可以访问本机绝对路径

这比纯工作区限制更灵活，但也意味着用户要更清楚本地目录边界。

## 一键重置工作状态

本地模式现在提供 `一键重置工作状态`。

它适合这些场景：

- 会话卡在运行中
- 子智能体运行状态明显不一致
- 工作区里留下半截运行态文件
- 用户想让智能体回到干净任务线程

执行后会：

- 中止当前用户仍在运行的会话
- 清空排队任务
- 为智能体重建任务线程
- 清理对应工作态目录

## 重置后保留的内容

这次重置针对的是「工作态」，不碰「长期资产」。

会保留的典型内容包括：

- `global`
- `skills`
- `knowledge`
- 用户长期配置

所以它做的是「把运行现场清干净」，而不是「恢复出厂设置」。

## 改用舰体（server）的时机

如果用户只是个人使用，本地模式通常已经够用。

当用户开始需要这些能力时，改用浏览器访问蜂巢（web，随舰体提供）：

- 多用户治理
- 管理员后台
- 单位/组织控制
- 统一渠道与服务接入

## 本地模式容易踩的坑

- 把本地模式当作无状态运行
- 以为本地目录还要再分「个人容器 / 智能体容器」
- 以为修改提示词会回写当前老线程
- 以为重置工作状态会顺手删除长期技能或知识
