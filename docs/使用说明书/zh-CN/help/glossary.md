# 术语表

## 产品与形态名称

| 中文名 | 英文/技术标识 | 说明 |
|------|------|------|
| 心舰 wunder | `wunder` | 产品本身，**智能体调度平台**的总称：把目标交给智能体，它拆解任务、调用工具、交付结果。 |
| 核心 | `wunder-core` | 代码底层：配置、鉴权、存储契约、执行策略等基础设施。 |
| 引擎 | `wunder-runtime` | 代码执行层：orchestrator、线程运行时、工具、渠道与网关。蜂窝与舵机直接依赖引擎，不依赖舰体。 |
| 舰体 | `wunder-server` | **用户与智能体管理平台**：服务端形态，面向团队与组织，负责多用户、权限与渠道接入，并提供蜂巢（web）。 |
| 舰桥 | `web/` | 治理前端，系统管理员的管理界面，用于系统配置、用户与渠道治理。 |
| 渠道舰桥节点 | `bridge node`（`bridge_center`） | 渠道桥接节点：承载渠道账号接入与消息路由的节点，由后端治理接口（`/wunder/admin/bridge/*`）统一管理，当前无独立前端页面；注意与治理前端「舰桥」区分。 |
| 蜂巢 | `frontend/` | **云端 AI 工作台**（web）：随舰体提供的网页端，用户通过浏览器访问。 |
| 蜂窝 | `wunder-desktop` | **本地 AI 工作台**（desktop）：桌面形态，个人用户的默认入口，本地运行，可直接访问本机文件。 |
| 舵机 | `wunder-cli` | **手工本地操作入口**（cli）：命令行形态，面向手工操作、开发者与自动化脚本，终端驱动。 |

文档中的「舰体/舰桥/蜂巢/蜂窝/舵机」都指代 wunder 的具体形态，「核心」「引擎」指代码分层（wunder-core / wunder-runtime），两类说法不要混用。文档标题与正文首次出现处会以「中文（英文标识）」标注对应关系，如舰体（server）、蜂窝（desktop）、舵机（cli）。

## 用户

用户的身份标识。可以是注册账号，也可以是临时用的虚拟名称，系统都能识别。

## 智能体

执行任务的 AI 角色。智能体拥有自己的模型、工具和提示词配置。每个用户**有且仅有一个**智能体实例，由管理侧预设 1:1 绑定生成；用户侧没有创建、删除、切换或排序智能体的入口，只有预设声明「允许自定义」的字段可以改。

## 预设智能体

管理侧维护的智能体模板。预设可以有多份，但每个用户只绑定其中一份，并由此生成该用户唯一的智能体实例；预设更新可以按「同步未自定义项 / 强制覆盖」推送到绑定用户。

## 线程

一次连续的对话。一个智能体可以有多个线程，每个线程独立维护上下文。

## 子智能体

主智能体在任务中临时创建的工作单元，任务完成后回收。它不是独立智能体，也不是用户拥有的第二个智能体。

## 工作区

用户的持久文件空间。每个用户**有且仅有一个**工作区，工具以它为根：蜂窝（desktop）里是本机上的持久目录，可直接读写本机文件；舰体（server）部署时是服务端数据根下按用户划分的唯一目录，通过蜂巢访问。工作区不可新增、删除或更换。

## 工作目录

界面上的工作区入口：位于网页左栏工作区下方，包含文件树、工具栏（上传 / 新建 / 刷新 / 多选）、用量条和预览弹层，不是操作系统的文件浏览器。

## 用户轮次

用户每发一条消息，就是一轮用户轮次。

## 模型轮次

模型每执行一次动作（思考、调用工具、回复），就是一轮模型轮次。一轮用户轮次里可能包含多轮模型轮次。

## 技能（Skill）

给模型用的能力包。通常包含说明文档、脚本和资源文件，让智能体能完成特定类型的任务。

## MCP

模型上下文协议。一种标准接口，让 wunder 能接入外部工具服务。

## A2A

智能体之间的互操作协议。让不同系统的智能体能互相发现和协作。

## 渠道（Channel）

外部消息通道，比如飞书、企业微信、QQ、XMPP 等。通过渠道，智能体能收发外部消息。

## Token

模型处理文本的基本计量单位。Token 数反映当前对话的上下文长度，不等于实际费用。

## 上下文压缩

对话太长时，系统会自动压缩历史内容，让模型能继续工作而不丢失关键信息。

## 长期记忆

智能体跨对话记住的知识。可以手动添加，也可以让系统自动提炼。
