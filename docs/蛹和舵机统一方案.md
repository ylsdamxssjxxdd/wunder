# 蛹和舵机统一方案

> 状态：统一方案持续落地（原型阶段）。蛹与舵机共享同一 `WUNDER_HOME`、内嵌资源释放结果、本地配置、登录状态、SQLite 线程数据和租约；秒开优化与跨进程一致性仍按本方案继续收敛。

## 1. 目标与边界

蛹是本地 AI 工作台，舵机是手工本地操作入口。两者继续保留各自交互方式，但对同一 `WUNDER_HOME` 使用同一份引擎配置、同一个本地 SQLite 数据库、同一份云登录凭据和同一套线程目录。

本方案解决同一台机器、同一操作系统账号下的跨进程一致性。`WUNDER_HOME` 被显式设为不同路径、`WUNDER_CONFIG_PATH` 或 `WUNDER_SQLITE_DB_PATH` 指向不同位置时，属于用户主动选择的隔离配置，不承诺共享线程和登录状态。舰体与蜂巢仍由服务端身份和存储管理，不使用本地租约代替服务端权限。

必须满足以下不变量：

- 默认路径完全相同：两端都从 `WUNDER_HOME` 解析配置、数据库、登录态与用户数据；启动目录、安装目录和程序形态不能改变默认数据根。
- 默认本地身份相同：蛹与舵机使用同一逻辑用户 ID，读取同一份会话和工作区记录。显式 `--user` 参数继续代表隔离身份。
- 每个配置项只有一个持久化真相源；客户端私有偏好放在同一配置目录下的独立文件中，不互相回写覆盖。
- 同一线程任一时刻只能由一个本地程序实例打开；正在运行、排队或等待执行的线程不能被其他实例打开。线程目录摘要可浏览，打开完整线程前必须取得租约。
- 会话执行仍由运行时 durable 锁裁决；窗口租约负责独占打开，二者职责不同，任何一层都不能被进程内锁替代。
- 崩溃恢复只回收确认过期的实例与租约，不得在蛹或舵机启动时清理另一存活进程正在执行的任务。

参考 `codex-main` 的组织方式，把用户主目录下的单一 home 作为配置、认证与状态数据库的共同边界：两种入口共享同一个 home 和状态库，配置、凭据、数据库各自有清楚位置。Wunder 继续使用自己的 TOML/YAML、SQLite 与运行时协议，不照搬 Codex 的文件格式或会话实现。

秒开要求建立在“进程内嵌、首次释放、后续复用”三层边界上：可随程序发布的静态资源编译进蛹和舵机，启动只把缺失文件释放到统一 home；释放完成后不再从启动目录扫描、复制整棵资源树或等待网络。SQLite、登录态、用户工具、向量知识、日志和工作区始终使用 home 下的持久目录，`--temp-root` 只承载临时文件。首屏可以先显示静态壳，配置校验、云探测、技能索引等非必要工作在后台完成，不能阻塞首屏。

## 2. 改造前的问题与当前落地状态

改造前，两端虽然都使用用户目录下的 `.wunder`，但数据库、身份和登录态仍有分叉。以下记录改造前的问题；这些问题的主要实现已经落地，具体测试结果与剩余验收边界见 §9.1，不能将本表视为当前代码行为：

| 项目 | 改造前行为 | 当前实现方向 |
| --- | --- | --- |
| 引擎数据库 | CLI 写 `wunder_cli.sqlite3`，桌面写 `wunder_desktop.sqlite3` | 共用 `data/wunder.db` |
| 默认本地用户 | `cli_user` 与 `desktop_user` | 共用一个本地用户 ID |
| 云登录文件 | 舵机 `cloud.json`，蛹 `config/cloud.session.json` | 一个规范路径、一个当前凭据 |
| 配置写入 | 两个进程各持有 `ConfigStore` 内存副本 | 文件锁串行更新、基于最新磁盘值合并、原子替换并通知其他实例 |
| 运行锁 | SQLite `session_locks` 已能跨进程原子占用，但按轮次执行使用；查看线程没有完整的打开租约 | 打开线程和执行线程均有可校验的跨进程所有权 |
| 启动恢复 | 蛹启动会按用户回收活动态和任务 | 仅回收实例心跳已过期的数据，保留其他活跃实例的状态 |

实现入口：`crates/wunder-core/src/local_bootstrap.rs` 定义统一 home 布局，`crates/wunder-runtime/build.rs` 生成同一份内嵌资源清单，`crates/wunder-runtime/src/core/local_assets.rs` 负责幂等释放；蛹与舵机启动阶段都调用该释放器，再将 `config/wunder.yaml`、提示词、内置技能、技能执行脚本和 i18n 文件指向 home。`crates/wunder-runtime/src/services/cloud/session.rs` 定义共享会话文件；`crates/wunder-runtime/src/storage/sqlite/session_lock_store.rs` 实现会话执行锁；两端默认路径入口在 `crates/wunder-cli/runtime.rs`、`crates/wunder-desktop/runtime.rs`。

## 3. 统一目录

`WUNDER_HOME` 是唯一可移动的数据根。未设置时，两端都解析为当前 OS 用户主目录下的 `.wunder`；路径解析代码应收敛到 `wunder-core` 的共享函数，避免 Windows 用户目录回退规则与无 HOME 时的临时目录策略分叉。

```text
WUNDER_HOME/
  config/
    wunder.yaml             # 引擎共享配置：模型、工具、策略及存储路径
    i18n.messages.json      # 内嵌后按需释放的多语言资源
    prompts/                 # 内嵌后按需释放的系统提示词
    preset_worker_cards/     # 内嵌后按需释放的预置卡片
    config.toml             # 舵机用户偏好；蛹不拥有或覆盖其中的字段
    profiles/               # 舵机配置档
    cloud.session.json      # 蛹与舵机共用的登录态
    desktop.settings.json   # 蛹独有的界面、工作区与本机路径偏好
    cli.settings.json       # 舵机独有的终端偏好（按需引入）
    config.lock             # 跨进程配置更新锁，不存放秘密
  data/
    wunder.db               # 两端唯一默认 SQLite 数据库
    wunder.db-wal
    wunder.db-shm
  workspace/
  skills/
  scripts/
  user_tools/
  vector_knowledge/
  temp/
  logs/
```

### 3.1 内嵌资源与首次释放

蛹和舵机由同一个 `wunder-runtime` 构建清单生成资源包，不能各自维护一份默认文件。当前清单包含无秘密的示例配置、i18n、系统提示词、预置卡片、内置技能和技能执行脚本；部署用 `config/wunder.yaml`、MCP 密钥、数据库、日志、浏览器缓存和向量数据不进入二进制。字体由蛹单独内嵌，属于展示资源，不进入共享引擎种子清单。首次启动按固定相对路径释放到 `WUNDER_HOME`，目标已存在时保留用户文件，释放操作是原子且幂等的。

资源释放必须先于运行时路径设置，但不应阻塞首屏：桌面先显示原生壳，后台初始化共享运行时；舵机当前在统一运行时完成后准备终端，文件索引、技能目录等随后增量填充。启动热路径只做有限目录创建、缺失文件检查和 SQLite 连接；禁止全量复制、无界扫描和同步网络请求。

路径规则：

- `config/wunder.yaml` 的 `storage.backend` 固定为 `sqlite`，默认 `storage.db_path` 指向 `WUNDER_HOME/data/wunder.db`。两端不得再把客户端名称拼进数据库文件名。
- `WUNDER_SQLITE_DB_PATH` 是显式数据库覆盖项，两端按同一规则读取；`WUNDER_CONFIG_PATH` 同理。覆盖路径不同即形成隔离 profile。
- `--temp-root`、`WUNDER_DESKTOP_TEMP_ROOT` 只控制临时文件，不得迁移、复制或改变共享配置和数据库路径。
- `config.toml` 从当前根目录迁入 `config/config.toml`；项目级 `.wunder/config.toml` 仍是项目覆盖层，不与全局用户配置混为一份。
- 蛹与舵机的私有设置可以不同，但必须放在同一 `config/` 下并有单一写者。模型目录、云模型合成项和引擎策略继续以共享 `wunder.yaml` 为唯一持久化来源。

## 4. 登录状态共享

### 4.1 单一会话文件

统一使用 `WUNDER_HOME/config/cloud.session.json`。`CloudSessionFile::path_for` 不再按 `desktop` / `cli` 选择路径；`client` 可以保留为最近登录入口的诊断元数据，但不得参与路径、凭据隔离或登录状态判定。蛹登录后，舵机的 `cloud status`、云模型调用及互通能力读取同一会话，无需二次登录；反向亦然。

会话文件包含 access token、refresh token 和设备状态，必须原子写入并维持最小文件权限。Unix 使用仅当前用户可读写的权限；Windows 保持用户配置目录 ACL。日志、错误、配置路径打印和诊断导出不得包含 token。

舵机和蛹各自的桌面/API 调用 token 属于进程入口的本机访问凭据，不是用户云账号会话；它们不因此共用、不输出给另一入口，也不能替代 `cloud.session.json` 中的账号状态。

### 4.2 跨进程刷新和登出

进程内 `refresh_lock` 无法防止两个客户端同时轮换同一个 refresh token。静默刷新现在先取得 `config/cloud.session.lock`，重新读取磁盘会话；若 token 已变化则直接采用新会话，不重复提交旧 refresh token。锁有等待上限和过期回收，网络请求仍受明确超时约束。登录、刷新、登出都更新内存 fingerprint，另一进程通过有界 fingerprint 检查重新载入文件；删除文件会变为 `logged_out`，不会继续使用旧 token。

其他实例通过会话文件 fingerprint 的有界检查刷新内存快照：登出后及时显示已登出并停止使用旧 token；刷新后更新状态，不要求重启。文件监听失败时，周期校验仍以磁盘为准。`auth_generation` 尚未写入文件格式，不能作为已完成能力对外承诺。

若迁移时只存在一份旧会话，直接校验并迁入规范路径。若两份都存在且属于同一服务与账号，优先选取有效且较新的凭据；若身份冲突或无法判断，保留受权限保护的迁移副本并提示用户重新登录选择，不能静默覆盖其中一份。迁移完成且新文件可读后，清除旧路径上的凭据副本。

## 5. 线程目录与独占打开

### 5.1 两种租约

现有 `session_locks` 继续表达线程正在执行或等待执行，是提交请求的并发保护。另增 `thread_open_leases` 表达某个本地实例正在打开线程，至少包含：

| 字段 | 语义 |
| --- | --- |
| `user_id`, `session_id` | 线程唯一范围与主键 |
| `owner_instance_id` | 进程启动时生成的随机实例 ID，不用 PID 作为唯一身份 |
| `client_kind` | `desktop` 或 `cli`，用于明确展示占用方 |
| `fencing_token` | 每次成功取得/接管租约递增，阻止过期实例继续写入 |
| `heartbeat_at`, `expires_at` | 活跃租约续期与崩溃回收依据 |

线程租约只保存占用状态，不保存消息、工具输出或大对象。SQLite 通过短事务和唯一键原子争抢；查询按用户和租约到期时间建索引。所有租约读写走现有 `StorageBackend` 契约；当前实现与验收范围为本地 SQLite，PostgreSQL 默认返回 Busy/false，不宣称支持同等租约语义。

当前原型已实现 `owner_instance_id`、`client_kind`、更新时间和到期时间，并以 SQLite 短事务完成互斥；打开检查还会阻断有效 `session_locks`、`agent_tasks`（pending/retry/running）及 `thread_turns`（accepted/queued/running/waiting_input/waiting_approval）。`fencing_token` 尚未加入表结构，后续在需要强制接管和迟到写入隔离时补齐。PostgreSQL 目前沿用契约默认行为，未作为本地双端路径使用。

### 5.2 打开流程

1. 启动时为每个进程创建 `owner_instance_id`，并定期续期进程心跳。它不代表用户身份，也不作为鉴权凭据。
2. 打开线程前，运行时在一个短事务内确认线程未被其他实例持有、未处于排队/运行/等待执行状态，然后原子取得 `thread_open_leases`。
3. 取得租约后再读取完整线程视图。打开失败返回稳定错误码 `THREAD_IN_USE` 或 `THREAD_RUNNING`，附带占用端类型与可重试提示；不得先把新线程设为当前线程再异步报错。
4. 同实例重复打开同一线程幂等；同一实例可拥有多个不同线程。用户切换线程或关闭线程时释放对应租约。
5. 每次心跳、提交、取消和状态变更都携带实例 ID 与 fencing token。只有当前 token 的所有者可以续期或释放租约；旧进程不能删除新实例的锁，也不能提交迟到的状态写入。
6. TUI/蛹的退出路径主动释放租约。非 TTY 的 `exec`、恢复命令只在命令生命周期内持有打开租约；命令结束时释放。正在执行的请求无论 UI 是否关闭，都保留 `session_locks`，其他实例仍不能打开该线程。

线程列表、名称、所属工作区和有限摘要可以只读展示，不算打开线程；加载完整聊天页、轨迹正文、恢复流、发送/重试/取消必须验证租约。线程切换时先成功取得新租约，再释放旧租约，避免竞争失败后页面丢失当前上下文。

### 5.3 忙碌、崩溃和恢复

- 活跃租约由实例心跳续期。进程崩溃后，仅在实例和线程租约均过期、且不存在有效执行锁/任务时，清除打开占用并把中断轮次标记为可恢复状态。
- 租约到期由数据库时间统一判定；同一事务中递增 fencing token。旧进程恢复后每次写入都会因 token 过期而被拒绝。
- 执行 lease 的 `touch` / `release` 必须携带 owner 与 fencing token，并检查受影响行数。不能只按 `session_id` 删除锁。
- 心跳和租约扫描使用有界批次，不启动全表无界清扫；可恢复任务按实例归属处理。启动蛹不能再无条件删除整个用户的锁或取消所有活动任务。
- 当一个线程被其他活跃实例占用时，不提供隐式抢占。用户需在持有方关闭线程；确认进程已崩溃后才允许过期接管。管理提示不能泄漏 token 或完整本机路径。

### 5.4 实时一致性

持有线程的程序继续从共享 durable 线程日志和 change cursor 读取增量；另一个程序只展示目录摘要，不订阅或缓存其完整时间线。线程租约释放、任务状态变化、线程被删除等事件通过现有 change stream / replay 链路跨实例可见。连接断开后按 durable cursor 补水，不以本地内存快照覆盖数据库。

## 6. 配置并发写入

共用文件不能只做到相同路径；各进程持有独立的 `ConfigStore` 内存副本，必须防止后写者用旧快照覆盖先写者：

- 更新流程为“取得 `config.lock` → 重新读取最新 YAML → 对指定字段应用变更 → 校验 → 临时文件写入并原子替换 → 增加配置 revision → 释放锁”。配置锁内不执行网络调用；云刷新锁必须覆盖一次有超时的令牌轮换请求与落盘。
- 配置 API 以字段/分区为粒度提交 patch，不把一端完整内存快照写回。客户端启动时不再每次重写整个 YAML 来设置自己的 `server.mode`、数据库路径或工作目录。
- 共享模型条目只在 `wunder.yaml` 保存。`desktop.settings.json` 不缓存并回灌模型列表；舵机配置投影只更新它明确拥有的字段。
- 变更后通过有界文件监听或 revision 轮询让其他进程刷新对应运行服务；若运行中的线程 system prompt 已冻结，更新只影响后续新线程，不改写现有线程提示词。
- 写入失败应保留旧文件并可诊断，不允许用默认配置静默覆盖解析错误文件。配置锁等待有超时并给出忙碌错误，避免长时间阻塞 UI。

## 7. 数据迁移与兼容

当前原型按用户要求不实现旧目录、旧数据库和旧会话文件的迁移兼容；统一路径直接作为唯一规范路径。后续若重新引入兼容读取，必须先增加幂等备份与冲突审计，再开放旧数据导入。

若未来需要迁移，必须幂等、可恢复、保留源数据，且两端共享同一迁移实现：

1. 在 `WUNDER_HOME` 创建统一目录，并取得进程级迁移锁；校验数据库与目标目录可写、磁盘空间可用。
2. 备份 `wunder_cli.sqlite3`、`wunder_desktop.sqlite3`、旧配置和两份旧登录文件。原文件在新数据库验证完成前不删除或改写。
3. 用 schema-aware SQLite 迁移器合并两份旧数据库到 `data/wunder.db`，保留 session/thread/message/event IDs 和时间线顺序；把 `cli_user`、`desktop_user` 归并到统一默认本地用户，把会话及相关记录中的用户外键一致更新。其他显式用户 ID 保持原样。
4. 合并工作区记录时保留各自根路径和名称，消解仅由默认用户身份导致的键冲突；不得把项目工作目录改成蛹工作区，也不得批量复制或重算线程正文。
5. 迁移标记与导入游标写入目标库。中断后可以重复执行，已导入行不重复创建；冲突写入有确定规则并产出不含秘密的诊断摘要。
6. 配置迁移把 CLI 用户配置、profiles、引擎 YAML 和桌面设置归入规范目录。默认数据库路径统一指向新库；显式覆盖保留原值并提示其会建立隔离 profile。
7. 将旧登录状态按 §4 规则迁到唯一文件；新客户端成功读回登录态和线程目录后再结束兼容读取。保留短期回滚备份，清理旧 token 文件需确认新文件原子落盘。

在 Win7/Ubuntu 18.04 目标环境验证 SQLite WAL、多进程写入、文件锁和原子替换行为；`WUNDER_HOME` 不支持放在不具备可靠本地锁语义的网络共享目录。发生数据库忙时应做有限退避并明确报错，不改用另一份数据库继续启动。

## 8. 实施顺序

当前已完成共享 home、SQLite、配置锁、资源 bootstrap、线程租约和基础恢复隔离；跨进程云会话 fingerprint、刷新文件锁、排队/等待状态阻断以及一次性 CLI 的租约 heartbeat 已接入。云探测已从舵机初始化关键路径移到后台；蛹原生入口仍需继续拆分互通启动和本地索引，才能把“可见首屏”和“后台就绪”做成可测预算。本轮补充 fencing token、事务内提交校验、内核文件锁和运行时配置刷新；PostgreSQL 租约语义与目标系统首屏基准仍需独立验收。

已落地的关键行为：

- 蛹与舵机默认使用 `local_user`、`WUNDER_HOME/data/wunder.db` 与 `config/cloud.session.json`。
- SQLite `thread_open_leases` 以实例 ID 和租约 TTL 记录打开者；蛹打开/读取/发送、舵机 TUI 切换及一次性执行均先争抢租约。
- 租约续期、同实例幂等打开、切换时先获取后释放、退出释放均已接入；有效 `session_locks` 存在时，第二实例得到 `THREAD_IN_USE`。
- 蛹启动不再按用户删除其他实例的锁、监控或任务；配置更新在 `config.lock` 下重读磁盘并原子写入，避免旧快照覆盖。
- 蛹原生入口不等待互通隧道的阻塞恢复；隧道在后台启动，首屏先返回可用桌面句柄，连接状态随后通过运行时状态流收敛。
- PostgreSQL 契约保留默认实现；本地蛹与舵机默认只使用 SQLite。

1. **统一资源 bootstrap**：构建阶段生成唯一内嵌清单；两端首次启动幂等释放到同一 home，后续仅检查缺失文件。
2. **路径与身份收敛**：在 `wunder-core` 实现唯一 home/config/database 路径解析；蛹与舵机使用同一 SQLite 文件和默认用户 ID；移除共享字段互相覆盖。
3. **登录与配置协调**：统一云会话文件，增加 fingerprint reload、跨进程刷新锁、登出通知和配置锁内重读。
4. **线程打开租约**：覆盖运行、排队、等待状态；桌面/TUI/exec/resume/视图读取均验证所有权并续期。
5. **秒开优化**：首屏与后台初始化分层，建立首屏可见、资源释放、SQLite 可用的启动基准；将云探测、索引、日志上传和大目录扫描移出关键路径。
6. **强制接管与验收**：加入 fencing token、崩溃接管和 Win7/Ubuntu 18.04 多进程测试；不引入旧目录迁移或兼容读取。

## 9. 验收标准

- 蛹与舵机在无覆盖参数时打印出的 home、配置路径、数据库路径完全相同；分别启动不会创建客户端专属数据库。
- 在蛹登录后启动一个新的舵机进程，`cloud status` 显示同一账号且可使用已登录云能力；反向测试同样通过。任一端登出后，另一端在有界时间内显示登出并停止用旧凭据请求。
- 两端并行添加不同模型或修改不同配置字段，最终文件同时包含两次修改；不同字段的 patch 在锁内基于最新文件合并；同一字段按成功取得写锁的顺序后写生效，当前没有跨进程 CAS revision API。
- 蛹打开线程 A 后，另一舵机实例和第二个蛹实例打开 A 均收到 `THREAD_IN_USE`；A 正在排队或运行时，即使原实例关闭窗口，其他实例仍收到 `THREAD_RUNNING`，直至运行态终结。
- 任一实例可以打开不同线程 B；实例正常关闭后 A 可重新打开；强制结束进程后等待租约过期，A 可由新实例恢复，旧 fencing token 无法继续写入。
- 同一实例内切换线程、重复打开、读取分页、重连补水和取消请求不会泄漏或误释放其他实例的租约；目录分页与线程视图仍有界。
- 首次启动蛹或舵机后，另一端看到相同的 `config/wunder.yaml`、提示词、skills、i18n、脚本和目录结构；第二次启动不重复复制资源。
- 两个旧 SQLite 库迁移后，原有线程、轮次、轨迹和会话归属可查；重复运行迁移不重复记录，源库备份仍可用于回滚。（当前原型按用户要求不实现迁移，此条仅作为未来重新启用迁移时的验收标准。）
- 启动一个新客户端不取消另一个存活进程的任务；死进程残留能在过期后被回收，SQLite busy/文件权限错误不会静默创建第二份状态库。

## 9.1 本轮实现与验收边界

- **线程租约**：SQLite 在短事务中分配递增 `fencing_token`，释放后保留代数；续期和释放同时匹配实例 ID 与 token。蛹、TUI、单次执行携带租约证明，轮次接受事务在写入消息前再次验证；已接受轮次仍由 durable 执行锁与任务状态保护。这不等于所有任意线程字段写入均已支持事务级 fencing。
- **云会话锁**：`cloud.session.lock` 与 `config.lock` 使用内核文件锁。锁文件常驻，进程退出或崩溃由操作系统释放所有权，不按文件年龄删除。云令牌轮换从请求到落盘保持独占；偏好、账号快照、日志游标、互通密钥回写均遵循锁内重读。锁忙有界返回，云锁等待上限 8 秒，单次网络请求上限 20 秒。
- **界面同步**：蛹启动即每 2 秒读取本地云状态，不受设置页开关影响，最多一个轮询在途；舵机状态栏缓存 1 秒。网络故障保持 reconnecting，不错误显示为主动登出。
- **配置刷新**：每次 `get()` 检查文件长度与修改时间，变化后重载；解析错误保留最后有效快照。更新先落盘再修改内存和进程内版本。配置刷新不会重新注入已冻结线程的 system prompt；数据库连接、监听地址等启动时资源仍需重启，不能把配置快照更新称为全部资源热重建。
- **内嵌资源**：只包含示例 YAML、i18n、prompts、内置 skills、预置卡片与技能执行脚本。`logs/`、`user_tools/`、`vector_knowledge/`、数据库和登录文件是统一创建的运行数据目录或文件，不嵌入用户内容。Python、Git、ripgrep、winpty 等原生依赖属于平台补充包；字体属于蛹展示资源，不属于两端共享的引擎种子。
- **首次释放**：完整临时文件以硬链接的 create-if-absent 方式发布，避免两个首次启动进程互相覆盖已写入的种子。Windows 竞争失败后若目标已为普通文件，视为另一实例完成发布；目标不存在时保留错误。需要支持硬链接的本地文件系统；不支持时显式报错。
- **发行验收**：本轮在当前 Windows 开发环境执行定向测试与 Release 构建；Win7 32 位、Ubuntu 18.04 实机运行与秒开时延不得据此标记通过。发行物必须分别记录构建结果、资源清单、启动检查以及目标系统验收结果。

### 本轮已确认的验证结果

- 核心定向测试：60 项通过，含配置并发/刷新、失败不发布、资源清单与释放、活锁超时、强制结束持锁子进程后的恢复。
- SQLite 租约测试：3 项通过，含跨连接互斥、过期接管、旧 token 提交被拒绝和执行锁阻断。
- 云会话集成测试：10 项通过，包含独立实例并发 token 轮换、外部登出、刷新/登出竞态、网络重连及失效处理。
- Slint：`slint-viewer --check` 与原生壳渲染通过；此项不替代后台状态轮询的实际登录交互验收。
- Windows 原子替换定向测试 5 项、统一目录与资源释放测试 3 项通过，包含 128 次双线程同步竞争发布；使用独立 OS 线程同时更新配置的测试通过。相同工作目录的两个并发 CLI 初始化复用同一工作目录记录的回归测试通过。
- 蛹 Release 演示模式冒烟通过，覆盖原生渲染、发送校验、草稿隔离、线程切换和有界历史；不包含真实云登录交互，也不作为首屏时延指标。
- 发行资源审查工具：`scripts/audit_local_release.py` 对最终 Release 的两个 exe 与各自构建清单逐项验证内嵌字节，并比较共享资源摘要；两个程序各 243 项，摘要一致且无缺失。
- 独立发行启动检查：`scripts/smoke_local_cli_release.py` 将 CLI 复制到源码目录外，在隔离 home 中验证冷启动、热启动与三组双进程冷启动。报告只记录退出码、统一目录检查和命令完成耗时；该耗时不能替代 TUI 首屏指标。
- CLI 启动优化：资源种子发布改为最多 8 个有界工作线程并行执行，配置投影仍在锁内重读，内容未变化时不再原子重写 YAML；外部配置变化仍更新本地版本和快照，缺失文件仍会生成。三组双进程冷启动均成功，命令完成约 732–892 ms。命令完成和 TUI 首帧是两个指标。
- 蛹首屏诊断通过 `WUNDER_STARTUP_TIMING=1` 开启，分别记录平台、字体集合、字体解压/注册、窗口创建、`show()` 返回、首次成功提交画面、后台初始化与 UI 接线完成。软件渲染器在非空画面成功 present 后上报 `first_frame_presented`；`show()` 返回和事件循环入口仅用于定位耗时。Win7 兼容路径关闭系统字体枚举，唯一内嵌中文字体必须在首次文本排版前注册。

### 启动耗时测量与优化依据

`scripts/measure_local_startup.py` 在源码目录外为每组创建独立 `WUNDER_HOME`，先运行首次启动，再复用该目录测已有目录启动；不清理操作系统缓存，因此“首次目录启动”不等于重启系统后的磁盘缓存冷态。CLI 丢弃配置正文，只保留阶段计时；蛹同时记录从 Rust `main()` 起算和父进程观察到的时间，在真实画面提交且后台完成 UI 接线后终止本次隔离测量进程。

秒启验收分别约束“看得见”和“能操作”：蛹以成功 present 的首帧和后台 UI 接线完成为准，舵机以首帧写入终端和输入可用为准，目标均小于 1000 ms。计时从父进程启动程序起算，另保留内部阶段用于定位；静态壳先出现但后端长期不可用不算完成。重复测量必须保留最慢值，3 次样本只报告范围与中位数，不推算 p95。发行前还需在目标系统覆盖首次目录、已有目录、离线与双实例竞争；尚无真实 TTY 首帧测量时，CLI 命令完成只能作为启动成本参考。

CLI 资源并行发布前的一次分层样本中，命令完成约 1467 ms，其中资源与目录约 935 ms，运行时约 151 ms，配置约 18 ms，工作区约 60 ms，旧线程归属检查约 31 ms；主要瓶颈是首次大量小文件的串行落盘，云探测只调度后台工作，没有等待网络响应。

负载减轻后，同一新版 Release 的三组重复结果（命令：`target/local-startup-cli-current.json`；真实终端：`target/local-startup-tui-current.json`）：

| 指标 | 首次目录启动 | 已有目录启动 |
| --- | --- | --- |
| CLI 命令完成 | 382–502 ms，中位 502 ms | 178–252 ms，中位 185 ms |
| CLI 内部初始化完成 | 273–412 ms，中位 360 ms | 94–126 ms，中位 101 ms |
| 舵机 TUI 首帧（父进程观察） | 559–665 ms，中位 624 ms | 214–336 ms，中位 280 ms |

命令首次资源与目录约 166–230 ms，运行时约 60–82 ms（其中 SQLite 47–63 ms、技能 12–18 ms），配置加载与投影约 14–16 ms，工作区绑定约 23–64 ms，旧线程归属检查约 8–24 ms。TUI 运行时就绪到首帧提交约 10–19 ms，三组均收到 `/exit` 并正常退出。进程加载、命令输出和退出阶段仍包含在命令完成时间中。开启 `RUST_LOG=info` 可查看分段计时，TUI 额外记录第一帧写入终端的 `tui_first_frame_submitted`；终端实际显示还受终端程序影响。
