# 蜂巢、蛹、舵机性能评分体系

## 目的

这套评分用于回答两个问题：一个版本的性能是否变好，以及下一次优化应该先做什么。它只衡量产品运行链路的速度、连续性、资源占用和稳定性，不衡量模型回答质量；模型质量继续由 WunderBench 单独评测。

三种形态各自有独立分数，不能把蜂巢、蛹、舵机的分数相加，也不能用一种形态的目标替代另一种形态的目标：

- **蜂巢**：云端 AI 工作台，重点是浏览器交互、长线程展示、流式连续性和并发服务质量。
- **蛹**：本地 AI 工作台，重点是原生启动、SQLite 读写、低延迟交互、离线可用和常驻资源。
- **舵机**：手工本地操作入口，重点是命令响应、终端输出、脚本化吞吐和长时间运行稳定性。

本文中的目标值和红线是首期可执行预算，适用于固定的标准评测配置。完成两轮真实基线后，可以调整预算，但必须保留旧版本报告，不能为了提高分数回填目标值。

## 统一评分方法

### 场景、指标和总分

每个场景得到 0–100 分，场景分数由该场景的指标加权得到；形态总分是场景分数的加权平均：

```text
场景分 = Σ(指标权重 × 指标分) / 100
形态分 = Σ(场景权重 × 场景分) / 100
```

所有权重均为百分比，四舍五入到 1 位小数。每个场景至少包含一个延迟或吞吐指标；涉及流式、渲染或存储的场景必须同时记录资源或正确性指标。

评分卡一行中列出多个指标时，默认在该场景内等权；如果某项是硬门禁或业务上更重要，报告可以显式写出指标权重，但必须在同一版本的前后对比中保持不变。正确性门禁不折算成分数，直接决定场景是否通过。

### 指标归一化

每项指标在评测前写明 `target`（达到目标得 100 分）和 `limit` 或 `floor`（到达红线得 0 分）。延迟、错误率、内存和 CPU 等“越低越好”的指标使用：

```text
score = clamp(100 × (limit - value) / (limit - target), 0, 100)
```

吞吐、成功率等“越高越好”的指标使用：

```text
score = clamp(100 × (value - floor) / (target - floor), 0, 100)
```

其中 `clamp` 将结果限制在 0–100。表格里的两个数依次表示 `target / limit` 或 `target / floor`。除非特别标注，延迟取 p95，吞吐取稳态值，资源取峰值或稳定态增量。

### 分数等级和回归判定

| 分数 | 含义 | 处理 |
| ---: | --- | --- |
| 90–100 | 充足 | 可以把优化精力转向最低分场景 |
| 80–89.9 | 健康 | 允许发布，继续观察趋势 |
| 70–79.9 | 需优化 | 进入下一轮性能迭代清单 |
| 60–69.9 | 风险 | 发布前必须说明原因并安排修复 |
| 0–59.9 | 不通过 | 阻止性能目标相关发布 |

相对上一版本还要看趋势：总分下降超过 3 分、任一场景下降超过 10 分，或现有《性能标准》定义的 p95、吞吐、内存回退阈值被触发，均标记为回退。优化优先级按下面的“损失贡献”排序：

```text
损失贡献 = 场景权重 × (100 - 场景分) / 100
```

每轮先处理损失贡献最高的三个场景，而不是只追逐总分中最容易增加的项目。

### 硬门禁

以下条件不参与平均分抵消，任一命中即为“不通过”，并在报告中单独列出：

- 崩溃、数据损坏、事件丢失、重复输出无法解释或跨线程串线。
- 流式内容丢字；断线恢复后无法补齐；取消后仍继续写入或占用线程。
- 关键 API 错误率超过 1%，或出现未记录的超时、无界队列增长、长时间阻塞。
- 同一固定负载下，内存持续增长且 15 分钟内未回落，或工作集超过该形态的红线。
- 场景所需的真实入口被绕开，例如用专用假数据函数代替真实 SQLite、WebSocket、Slint 或终端渲染路径。

## 评测配置和采样口径

### 固定负载

评测包应使用匿名、可重复生成的数据，不包含真实身份、密钥、业务名称或真实路径。所有形态的默认模型请求使用稳定 mock 或本地固定模型；真实线上模型另做体验报告，不混入系统性能分。

| 配置 | 蜂巢 | 蛹 | 舵机 |
| --- | --- | --- | --- |
| 长线程 | 500,000 条历史 item，窗口内 200 轮；正文、思考、工具事件按固定比例生成 | 127,400 个事件，覆盖冷开、重开和滚动 | 20,000 条终端可读事件，输出超过终端可视区 |
| 列表规模 | 1,000 个线程、10,000 个工作区文件 | 1,000 个线程、5,000 个本地文件 | 10,000 个线程、5,000 个本地文件 |
| 流式负载 | 30 秒、30 token/s、包含工具批次和结束事件 | 同上，经 NativeDesktop 有界通道 | 同上，经 CLI 输出与 flush 路径 |
| 稳定性窗口 | 10 个用户、5 条活动流、10 分钟 | 空闲 10 分钟，另测持续流 5 分钟 | 单线程 30 分钟，另测 5 个并行任务 |

### 采样规则

1. 启动场景使用全新进程，1 次预热后至少 5 次采样；交互和 API 场景至少 20 个样本才计算 p95。
2. 每次采样记录 OS、CPU/内存、浏览器或终端、Rust/Node 版本、数据库、编译 profile、代码来源和关键配置。
3. 蜂巢分为本机或局域网固定 RTT 的系统链路分和真实网络体验分；蛹与舵机分为 x64 开发基线和 Win7/32 位兼容基线，架构之间不互相比较。
4. 先运行不计分的预热，再采集；不得把编译、首次依赖安装、容器拉取或数据库初始化混入交互样本。
5. 原始 JSON/CSV 必须保留，报告只展示摘要。报告放在 `docs/性能基线/`，命名为 `YYYY-MM-DD-<形态>-性能评分.md`。

## 蜂巢评分卡（100 分）

蜂巢的首要指标是“用户可见内容是否及时出现并持续可用”。浏览器 Performance trace 要同时记录 LongTask、接口重复请求、WebSocket 重连、heap 和真实绘制时间。

| 编号 / 权重 | 场景与固定动作 | 主要指标（target / limit） | 硬门禁 |
| --- | --- | --- | --- |
| H1 / 8 | 冷启动到工作台可交互，无预置长线程 | TTI p95：1,200 / 2,000 ms | 页面无未捕获错误 |
| H2 / 7 | 登录后打开 1,000 线程目录 | 首个可操作线程 p95：600 / 1,200 ms；接口重复率 ≤ 2% / 5% | 列表不得全量渲染 |
| H3 / 12 | 打开 500,000 item 长线程 | click→首个正文 paint p95：800 / 1,500 ms | 只读真实快照/WS 入口 |
| H4 / 8 | 同一线程补水到窗口完整可读 | 完整窗口 p95：2,500 / 5,000 ms；响应压缩体积 ≤ 1 / 2 MB | 空态必须来自权威读取 |
| H5 / 14 | 30 秒流式输出，含工具批次 | 首个增量可见 p95：500 / 900 ms | 不丢字、不重复、不乱序 |
| H6 / 12 | 流式期间输入、选择文本、上下滚动 | 输入到绘制 p95：100 / 200 ms；帧 p95：33 / 50 ms | 输出期间不能阻塞输入 |
| H7 / 8 | 20,000 行轨迹上下滚动并回到原位置 | 滚动帧 p95：33 / 50 ms；>50 ms 长任务占比 ≤ 1% / 3% | 滚动位置无跳变 |
| H8 / 8 | 5,000 文件工作区浏览、读取、写入 | 文件列表 p95：500 / 1,000 ms；单次操作 p95：500 / 1,200 ms | 权限错误可见且不重试风暴 |
| H9 / 8 | 流式中点断 WebSocket，恢复并补水 | 恢复到可读 p95：1,500 / 3,000 ms | 事件完整性 100% |
| H10 / 10 | 10 用户、5 活动流、10 分钟 | 成功率：99.5% / 98%；接口 p95：500 / 1,000 ms | 无队列无界增长 |
| H11 / 5 | 空闲驻留 15 分钟 | heap 增长 ≤ 5% / 10% | 无崩溃、无持续增长 |

蜂巢发布分同时给出“交互分”（H1–H9）和“服务分”（H10–H11），两者均不得低于 70；任一硬门禁失败，总分直接标记不通过。

## 蛹评分卡（100 分）

蛹默认走 `frontend-slint/` 与 `wunder-desktop::NativeDesktop` 同进程入口。评测必须覆盖真实 SQLite、原生 StreamEvent、有界通道和 16–33 ms 增量合并；不得用 Electron、Tauri 或本机 HTTP bridge 代替默认路径。

| 编号 / 权重 | 场景与固定动作 | 主要指标（target / limit） | 硬门禁 |
| --- | --- | --- | --- |
| C1 / 8 | 全新进程冷启动到窗口首帧 | 首帧 p95：350 / 700 ms | 首帧前不启动重任务 |
| C2 / 8 | 冷启动到线程列表和输入可用 | 可交互 p95：1,200 / 2,000 ms | 无 panic、无 UI 线程阻塞 |
| C3 / 12 | 打开 127,400 事件长线程 | 首个正文 p95：300 / 600 ms；完整窗口 p95：1,500 / 3,000 ms | 历史不丢段、不复制全量列表 |
| C4 / 10 | SQLite 中 1,000 线程目录和最近线程查询 | 查询/投影 p95：150 / 300 ms | 查询有界、无全表重算 |
| C5 / 14 | 30 秒流式输出，经 NativeDesktop | 首个增量可见 p95：300 / 600 ms | 有界缓冲且不丢字 |
| C6 / 14 | 流式期间输入、复制、滚动 | 输入到 UI 响应 p95：100 / 200 ms；帧 p95：33 / 50 ms | UI 线程不做网络/重解析 |
| C7 / 8 | 在线程树切换 20 个线程并返回原线程 | 切换完成 p95：150 / 300 ms | 活动线程状态不串线 |
| C8 / 8 | 5,000 本地文件列表、读取、写入 | 列表 p95：500 / 1,000 ms；操作 p95：500 / 1,200 ms | 路径权限边界保持有效 |
| C9 / 6 | 无网络冷启动、查看历史、恢复连接 | 离线可用 p95：1,200 / 2,000 ms；恢复 p95：2,000 / 4,000 ms | 离线不阻塞本地历史 |
| C10 / 7 | 空闲驻留 10 分钟，另测持续流 5 分钟 | 空闲 CPU ≤ 1% / 2%；工作集增量 ≤ 10 / 20 MB | 无定时器泄漏、无崩溃 |
| C11 / 5 | 取消轮次并关闭窗口，检查 durable 状态 | 取消到持久化 p95：500 / 1,000 ms | 取消后不得继续写入 |

蛹发布分同时给出“交互分”（C1–C8）和“本地可靠性分”（C9–C11），任一分低于 70 或任一硬门禁失败即暂停性能相关发布。x86/Win7 只在相同场景矩阵下建立独立报告，不把低端硬件的绝对值直接与 x64 合并。

## 舵机评分卡（100 分）

舵机是终端驱动、脚本化、自动化入口。这里的“可见”定义为终端收到并 flush 的输出；命令本身的执行时间与模型网络时间分开记录，避免把外部服务波动算成 CLI 性能。

| 编号 / 权重 | 场景与固定动作 | 主要指标（target / limit） | 硬门禁 |
| --- | --- | --- | --- |
| D1 / 5 | 新进程执行帮助或版本命令 | 首行输出 p95：300 / 600 ms | 退出码正确、无多余日志 |
| D2 / 8 | 冷加载配置、SQLite 和线程运行时 | 命令就绪 p95：800 / 1,500 ms | 配置失败有明确错误 |
| D3 / 8 | 查询 10,000 个线程并分页输出 | 首页 p95：300 / 600 ms；后续页吞吐 ≥ 50 / 20 页/s | 不全量载入终端内存 |
| D4 / 10 | 打开 20,000 事件长线程 | 首屏 flush p95：1,000 / 2,000 ms | 输出有界、可取消 |
| D5 / 15 | 发送一条消息到首个运行事件 | 首事件 p95：500 / 1,000 ms | 不把“已受理”当“已执行” |
| D6 / 12 | 30 秒流式终端输出 | 事件到 flush p95：100 / 200 ms；CPU 峰值 ≤ 25% / 50% | 不丢字、不串线程 |
| D7 / 10 | 文件或命令工具调用一次完整链路 | CLI 自身额外开销 p95：200 / 400 ms | 工具错误和取消可见 |
| D8 / 10 | 5 个并行任务交错输出 | 调度额外延迟 p95：200 / 500 ms | 输出按任务隔离、无死锁 |
| D9 / 7 | 断网、重连、恢复待处理任务 | 恢复 p95：1,000 / 2,000 ms | 不重复执行、不永久排队 |
| D10 / 10 | 单线程运行 30 分钟 | 工作集增长 ≤ 10% / 20%；CPU 平均 ≤ 2% / 4% | 无未回收任务或句柄 |
| D11 / 5 | 退出前写完状态和审计 | 退出 flush p95：500 / 1,000 ms | 重启后状态完整 |

舵机发布分同时给出“命令体验分”（D1–D7）和“自动化稳定分”（D8–D11）；任一分低于 70，或并行任务出现串线、死锁、重复执行，均不通过。

## 运行和报告模板

仓库提供 `scripts/performance_score.py` 自动计算器。它不替代蜂巢、蛹、舵机各自的采集器；采集器只需要输出下面的 JSON，或等价的 CSV 行，评分脚本负责归一化、覆盖率、门禁、回退和报告生成。

先生成输入模板：

```powershell
python scripts/performance_score.py --shape 蜂巢 --template --output target/beehive-score-input.json
python scripts/performance_score.py --shape 蛹 --template --output target/desktop-score-input.json
python scripts/performance_score.py --shape 舵机 --template --output target/cli-score-input.json
```

填写采集结果后运行评分。`--require-complete` 会在有缺测场景或门禁时返回非零退出码，适合 CI；不加它可以先查看部分覆盖率：

```powershell
python scripts/performance_score.py --input target/beehive-score-input.json `
  --baseline target/previous/performance-score.json `
  --out-dir target/beehive-score --require-complete
```

CSV 也可以作为输入。每行填写 `scenario,metric,value`，或 `scenario,gate,passed`：

```csv
scenario,metric,value,gate,passed
H1,tti_p95_ms,1180,,
H1,,,no_uncaught_errors,true
```

输出目录包含 `performance-score.json`（供 CI/后续比较）和 `performance-score.md`（供评审归档）。部分运行不会虚构形态总分，只显示已测场景分数和覆盖率；完整覆盖后才发布 0–100 总分。退出码为 1 表示硬门禁失败、相对上一版本回退，或 `--require-complete` 下仍有缺测；退出码为 2 表示输入格式错误。

每次版本评测按以下顺序执行：

1. 生成固定负载，记录环境和代码来源。
2. 预热一次；按场景顺序执行，启动类场景使用全新进程。
3. 保存原始 JSON/CSV，计算指标分、场景分、形态总分和硬门禁结果。
4. 与上一份同配置报告比较，列出分数变化和损失贡献最高的三个场景。
5. 性能优化只有在前后数据、命令和报告路径齐全时，才能在 `docs/功能迭代.md` 写成“性能提升”。

首轮不需要等待所有场景的专用自动化脚本完成：先用已有入口建立可比较的子集。蜂巢从线程展示真实 Playwright/Performance trace、`/wunder/admin/throughput/*` 和 WS 恢复开始；蛹复用桌面启动首帧报告、NativeDesktop 流式链路和 SQLite 读路径；舵机先覆盖 `--help`、线程列表、长线程首屏和流式 flush。未采集的场景标记“待测”，不能按 100 分计入总分，也不能用估算值补齐。

报告至少包含：

```md
# YYYY-MM-DD <蜂巢|蛹|舵机> 性能评分

## 形态总分
- 总分：
- 交互/命令分：
- 服务/可靠性分：
- 硬门禁：通过 / 不通过
- 对比版本：

## 场景分数
| 场景 | 权重 | 本次 | 上次 | 变化 | 损失贡献 |
| --- | ---: | ---: | ---: | ---: | ---: |

## 环境与采样
- 环境、入口、负载、预热、重复次数：
- 命令或页面操作：
- 原始资料：

## 结论
- 判定：通过 / 回退 / 待复测 / 有意 tradeoff
- 优先处理：
```

## 与现有性能文档的关系

- [性能标准](性能标准.md) 继续作为采样、回退阈值、真实入口和报告存放的总规范。
- [性能基线目录](性能基线/README.md) 保存每次评分的前后对比和原始资料。
- 舰桥已有的性能采样、吞吐和 WunderBench 页面分别提供数据；WunderBench 的任务质量分不纳入本文三个形态的性能分。
- 蛹启动和长线程已有专项报告时，直接把其中同口径数据映射到 C1–C4，不重复造一套计时入口。

## 舰体容量专项评分

舰体是用户与智能体管理平台，存储初始化和后台维护成本需要独立验收。容量专项使用 `--shape server`，不改变已有工作台和舵机评分卡的权重。

| 场景 / 权重 | 固定负载与指标 | 目标 / 红线 | 硬门禁 |
| --- | --- | --- | --- |
| S1 / 50 | 空库与大库各重开存储 20 次；四张大表各 100 万行、历史线程 10 万条 | 存储就绪 p95 ≤ 2 s / 5 s；容量放大附加 p95 ≤ 100 ms / 500 ms | 全部索引 OID 保持；启动不发现历史线程；不重写长期记忆行 |
| S2 / 25 | 大库已有 schema、无请求与活动任务，空闲采样 15 分钟 | 舰体与 PostgreSQL CPU 平均各 ≤ 1% / 2% | 两容器持续运行，空闲窗口有效 |
| S3 / 25 | 百万 item 待重建线程，观察实际后台循环与维护计数 | 工作时间占比 ≤ 1% / 2% | 每批发现 ≤ 64 线程；待迁移线程轮转；游标重启续跑 |

S1 测量存储初始化，不能替代从进程创建到 HTTP 可用的整机启动指标。每次样本重建存储实例与连接池，保留原始耗时。首次升级所需的索引构建或数据迁移独立记录，不混入日常启动 p95。升级成功后持久化 schema 指纹，指纹未变且分区月份相同时跳过 DDL 和数据清洗；源文件或展示 schema 变化会自动触发升级校验。

S2 的 Docker CPU 以单核为口径，Linux 容器 100% 约为一核，不能除以宿主机核心数来压低结果。S3 以 `thread_view_maintenance` 两个快照之间的 `work_ms / elapsed_ms` 增量计算，它是工作时间预算，包含数据库和队列等待，不等于整个服务的 CPU 占用。活跃窗口边界可能落在一批处理中，因此评分红线为 2%，循环仍按每批实际工作时间的 99 倍休眠。正式 CPU 预算使用 release 部署；debug 容量回归只能证明算法和门禁，不能冒充产品 CPU 基线。
