# 聊天流式管线根治：后端提交链路执行书

## 任务定位

你是从智能体一，负责后端 ThreadLog 提交链路和 durable cursor 通知。目标是消除“状态已提交但 feeder 没被唤醒”以及“同一状态由多处写入”的根因。

不创建分支、不提交 git，不修改前端主逻辑和无关 Desktop/CLI 文件。不恢复异步文本块写入队列，不为了旧测试重新把 v2 ThreadLog 状态写入 `stream_events`。

## 工作范围

1. 审计所有 `accept_thread_turn`、`append_thread_item`、`commit_thread_item`、`update_thread_turn`、文本块提交入口。
2. 每个成功 durable commit 后发布该 session 的最新 `change_seq`；优先使用提交 receipt 中的 cursor，不能用旧缓存猜测。
3. 覆盖普通 turn、手动压缩、`/goal`、队列进入/更新/开始/完成/失败/取消、重试、子智能体和后台任务。
4. queue item 使用稳定 `item_id`，状态变更产生不可变 `item_upsert` 版本；不得通过最新 item 回填旧 change payload。
5. SQLite 与 PostgreSQL 的事务、revision、immutable payload 和终态批量更新保持一致。

## 执行方法

1. 先用 `rg` 列出所有 ThreadLog 写入口和所有 hub publish 入口，形成一一对应关系。
2. 检查每个写入口是否在成功提交之后、错误返回之前发布 cursor；失败提交不能发布虚假 cursor。
3. 检查复合操作的顺序：同一 session 的 turn、item、block、状态必须按提交顺序产生 change；不要在长时间等待期间持有数据库锁。
4. 对队列和子智能体路径确认 `turn_id`、`user_round`、`queue_id`、`item_id` 来自持久身份，不从 monitor 最新轮次推断。
5. 为并发、取消、失败、重试、交错模型轮次补最小必要测试；测试应查询 `thread_log_changes`，而不是只查询旧 `stream_events`。

## 必须满足的验收条件

- 任意成功 ThreadLog commit 都能唤醒同 session feeder。
- hub 只负责唤醒，不能被当作事实源；无订阅者的 session entry 可回收。
- change payload 是提交时快照，历史 replay 不读取当前 item/block。
- queue `queued → running → terminal` 使用同一个稳定 Item，状态和 revision 可重放。
- 文本 block 与对应 item 的身份和 offset 一致；没有孤儿 block、跨轮次串写或无界队列。
- `cargo check -p wunder-runtime` 与 PostgreSQL feature check 通过。
