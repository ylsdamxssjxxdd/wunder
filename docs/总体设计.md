# 总体设计

wunder（心舰）是一个**多形态的智能体工作台**：把目标交给智能体，它拆解任务、调用工具、交付结果。四个形态各有定位：蛹（desktop）是**本地 AI 工作台**（个人默认入口、主推应用），蜂巢（web）是**云端 AI 工作台**（随舰体提供，构建产物由 nginx 容器只读挂载对外，默认端口 18001），舵机（cli）是**手工本地操作入口**（终端驱动、脚本化），舰体（server）是**用户与智能体管理平台**（多租户、用户与单位、智能体应用构建发布、网关接入与调度，内置工具链、知识库与长期记忆）。舰桥（`web/`）是舰体自带的治理界面，随舰体挂载于 `/`，不另立进程。

## 分层与接入

- 代码分层：`wunder-core`（配置、鉴权、存储契约与记录类型、路径围栏、执行策略）→ `wunder-runtime`（引擎：orchestrator、线程运行时、工具、渠道、网关、互通；库名对外为 `wunder_server`）→ 舰体 / 蛹 / 舵机三种可执行形态。蜂巢由舰体提供、无独立进程；蛹与舵机不依赖舰体。
- 蛹默认前端 `frontend-slint/`（Rust + Slint），同进程原生直调引擎，不经本机 HTTP；Electron / Tauri 壳停止维护。
- 对外集成面：REST `/wunder/*`、六个 WebSocket 通道（chat / core / gateway / interlink / user_world / LAN）、MCP 端点 `/wunder/mcp`、外部工作流 SSE `/wunder/external/workflow*`、渠道 webhook。统一错误包络 `{ok:false, error:{code, message, hint, trace_id}}` 并回写 `x-trace-id`。
- 存储选型：舰体 PostgreSQL（日志大表按月分区、用量增量计数与水位对账）；蛹与舵机 SQLite。两者实现同一组分域存储契约（`wunder-core/src/storage_backend.rs`）。schema 采用幂等建表 + 列探测式增列，无版本化迁移脚本。
- 轮次口径：用户轮次 = 每条用户消息；模型轮次 = 引擎主循环一次模型调用（可含一批工具调用，工具调用不另计轮次，`orchestrator/execute.rs`）。

## 四个核心：多快好省

| 核心 | 含义 | 落点 |
| --- | --- | --- |
| **多** | 多平台，多形态 | 四形态共享 `wunder-core` / `wunder-runtime`；32 位 Win7、Ubuntu 18.04 与现代 Windows / Linux / Docker，网页版与本地版并存；模型、渠道与工作区按接入层扩展 |
| **快** | 启动快、秒开，响应不卡顿 | 蛹与舵机同进程直调引擎，不经本机 HTTP；线程与历史从本地 SQLite 直接恢复；流式事件按帧合并、投影增量下发；工具在并行白名单内并发（≤4） |
| **好** | 稳定性强，可 7×24 运行，智能程度高 | 有界队列 / 缓存 / 视图、会话锁、轮次上限、日配额、重试熔断与断线续传；目标态、子智能体、工具链、记忆、知识库与上下文压缩支撑复杂任务 |
| **省** | CPU 内存占用极低，上下文消耗极低，自带预制运行环境 | Rust 单进程 + 本地 SQLite，无浏览器运行时；补充包预制智能体运行环境，免自行搭建；工具结果裁剪、提示词冻结复用缓存、记忆索引单次注入、微压缩与历史压缩压低 token 消耗 |

多与好决定能力面，快与省约束实现方式：接入层保持薄、执行路径保持短，队列、缓存、视图与上下文一律有界。

## 能力分解

| 能力 | 设计目标 | 核心能力 | 当前边界 / 未收口项 |
| --- | --- | --- | --- |
| 目标 | 让智能体进入目标态并持续完成一项任务 | 单一 `goal` 工具驱动（`action=get|create|edit|pause|resume|complete|blocked`）；phase 仅 active / paused / blocked / complete；CAS-on-revision、轮次只增；默认目标轮上限 256、连续无进展 3 轮自动 block；入口含 REST `/wunder/chat/sessions/{id}/goal` 与 `/goal` 斜杠 | 无 token 预算、无冷却；armed 态不持久，重启 / resume 后需显式 `goal action=resume` 重新 arm；桌面端不开放选择（运行时按会话注入）；舰桥无 goal 界面 |
| 兼容性 | 让蛹与舵机在旧操作系统环境中可运行并被明确约束 | Windows 7 32 位（专用 `i686-win7-windows-gnu` Tier 3 目标 + build-std 离线工具链）、Ubuntu 18.04 x64/arm64 离线构建链与 sysroot；Slint 软件渲染不依赖 GPU；命令会话 winpty 与 GBK 解码；启动恢复扫描与自检 | 构建脚本仍残留 Tauri 死链（指向已不存在的目录，属工程缺口）；win7 互通节点不声明 `tool.exec`，旧设备能力面收窄 |
| 上下文压缩 | 在长会话中控制上下文规模并保留有效信息 | 三触发面 history / overflow / pre-sampling（history 阈值 0.9×max_context）；只信任 provider 观测 token；microcompaction 把旧的可复现观测压成 768B 预览（保留最近 5 组）；压缩窗口保护当前用户消息；预算再平衡 | 手动 `/compact` 已证实仅舵机入口，蜂巢 / 蛹等价入口未证实；该服务（LLM 上下文压缩）与 UI 分页读模型是两回事，文档不得混写 |
| 子智能体 | 在单一线程内派生子任务，由独立执行体完成并回传结果 | `子智能体控制` 11 种动作（spawn / batch_spawn / wait / interrupt / close / resume / report / send / status / list / history）；父轮引用编码 user_round+model_round；子会话用户消息隐藏、auto-wake；运行时侧 child_runs / mailbox / tree | 协作形态**只有子智能体**：蜂群编排（蜂群工具 / 蜂房 / 编排态 / team run / 蜂群包）已从引擎与协议层移除；TUI 提示、前端 i18n 标签与兼容垫片仍有残留，空目录待清理 |
| 定时任务 | 支持系统级周期执行与后台治理 | kind `at` / `every` / cron（5–7 字段 + 时区，支持自然语言）；目标为当前会话或 isolated 新会话；租约 + claim 循环 + 并发上限；退避阶梯 30s→1h，连续失败自动禁用；11 个用户面 API 与 `定时任务` 工具同源 | 舵机显式关闭 cron；舰桥无用户级定时任务面板（仅作为预设智能体模板页存在）；`cron.enabled=false` 时增改启用一律拒绝 |
| 渠道通信 | 多入口接入同一运行时能力 | 7 个 adapter：feishu、qqbot、weixin、wechat、wechat_mp、whatsapp_cloud、xmpp；长连接 supervisor 仅 feishu / qqbot / weixin / xmpp，其余 webhook-only；入站有界队列（512）+ 出站 outbox 退避 + 令牌桶限流；绑定按特异性打分路由；网关为接入注册表 + 定向 RPC + presence 的 Hub（`/wunder/gateway/ws`）；互通隧道含影子投影、命令台账、审批工单、审计与 L0–L3 风险分层 | Telegram / Discord / Slack / LINE / DingTalk **无 adapter**（仅 generic webhook 目录项）；xmpp 默认 feature 关闭时为占位 stub；云端与本地 L3 命令（`tool.exec` / `agent.spawn`）默认不在设备能力集，审批不可记忆 |
| 记忆 | 支持长会话与长期资料利用，但不污染线程核心认知 | 线程初始化时以索引注入一次并随 system prompt 冻结（后续不再改写）；片段三层 L0 标题 / L1 摘要 / L2 正文 + core / working / peripheral 分级与升级阈值；轮末自动提取候选；作用域 user_id + agent_id；知识库三型（词面 / 内置向量 / 外部 RAGFlow）按库动态注册 | 语义召回当前禁用（走 inventory 模式）；舰桥无长期记忆面板（`state.js` 死条目）；知识库与向量检索已实现，除此之外不再声称其他检索形态 |
| 多线程 | 在单进程内通过并发控制提升吞吐与资源利用 | 单用户可并发多任务线程，调度、锁与实时状态按线程隔离；引擎级会话队列（默认开启）与 `会话让出` 让位；会话锁 TTL 120s + 心跳；工具并行度 ≤4（并行取读锁、独占取写锁）；活跃会话上限、轮次上限（默认 1000）、日配额、重试熔断 | 关闭 `agent_queue.enabled` 会导致运行中再发消息被判「用户忙」且不进排队条（舰体启动告警）；blocking 分类配额与有界队列是硬上限，满即 busy |
| 多租户 | 支持舰体的组织、用户、租户与权限治理 | 单位树从 `config/org_units.json` 播种、最深 4 级；用户账户（Argon2 口令）与配额；不透明 token（非 JWT）+ 刷新族轮换、重放即整族吊销；admin 门 = api-key 或 Bearer+管理员，leader 仅对 `/wunder/admin/org_units|user_accounts` 按后代单位放行；presence 分列蜂巢 / 蛹 / 舵机；舰桥四组 19 面板 | 舰桥互通治理面板**不存在**（互通治理当前是后端 API only）；api_key 为明文比较；服务端日志保留期默认 0（永不清理）；沙箱 HTTP 服务本身无鉴权，靠网络边界兜底；蜂巢大数据量线程渲染方案「实现待执行」，R1/R2/R3 仍是未解瓶颈 |

## 执行链路（提交到回复）

```text
WS 入口（api/chat_ws.rs）
  → ThreadRuntime::submit_user_request（services/runtime/thread/）
  → ThreadLogCommitter::accept_turn（分配用户轮次，幂等，线程日志唯一写出口）
  → 入队或直接执行（agent_queue）
  → Orchestrator::stream → execute_request 主循环（orchestrator/execute.rs）
  → 模型调用（services/llm/）；工具编排 execute_tools.rs → services/tools/dispatch.rs
  → 最终回复落库；全程 EventEmitter 同步 commit 到 durable 再广播
```

实时侧约束：事件按帧合并、投影表分页（聊天页 12 / 轨迹页 80，响应预算 128KB / 192KB）、写队列有界（2048）、慢客户端水位断开前先发 `resume_recommended`。
