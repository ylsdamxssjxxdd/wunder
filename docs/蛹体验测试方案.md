# 蛹体验测试方案

本文是蛹后续性能测试与优化的统一口径。蛹是本地 AI 工作台，测试从用户的操作出发，优先定位原生后端、线程运行时和本地存储的瓶颈。每次优化使用同一负载、正确性检查和基线比较，避免只凭体感判断。

## 1. 测试边界

默认运行外部 Python 驱动和独立 Rust 测试探针，直接调用聊天页使用的 `wunder-desktop::NativeDesktop`，继续经过正式提交、执行、取消、排队、持久化和事件通道。测试代码不接入产品入口，不要求构建或启动最终蛹程序，不依赖 Slint、浏览器、桌面会话、bridge 或舰体。

模型接口使用测试进程内的本机受控 SSE 服务，仅替代外部模型服务：固定块内容、块数、间隔和结束位置，记录源端发出时间，拒绝意外重试。模型接口的 HTTP 与蛹的原生调用链是两件事。整个测试无需外网、账号或模型密钥。

这些指标回答“后端何时准备好数据、输出是否连续、状态是否正确”。界面首次绘制、输入响应、滚动帧率、选中复制、Markdown 展示另列为可选界面层测试，不能从后端耗时推断已通过。后续补充界面测试不改变默认命令的独立性。

## 2. 固定测试场景

| 编号 / 命令场景 | 用户关注 | 负载与计时边界 | 必须满足的正确性条件 | 当前覆盖 |
| --- | --- | --- | --- | --- |
| UX-01 `chat_open` | 大日志能快速打开、返回和翻页 | 100 用户轮次 × 每轮 100 模型动作；首屏、缓存返回、原生头信息、存储页、会话信息、变更游标、上一页，分别计时 | 首屏与分页内容/顺序准确；返回游标正确；权威日志哈希不变 | 已自动化，复用已有七项基准 |
| UX-02 `submit` | 发送后及时被接收 | 发送调用至返回、正式接收轮次身份、首个文本增量 | 单次提交只执行一次；接收身份存在；最终回复与落盘内容一致 | 已自动化；通过完整执行验证接收结果 |
| UX-03 `stream` / `slow_consumer` | 输出持续、不卡住、不丢字 | 固定多字节文本流；首字、到达模型接口、增量间隔、源端首块至收到首块、源端结束至正式完成；慢消费者每个增量暂停 20 ms | 原文逐字一致、无重排/重复；有多次增量与最终事件；聊天预览与权威正文分别一致；流缓冲不超过 128 | 已自动化；慢消费默认验证背压，可提高块数制造压力 |
| UX-04 `cancel_resume` | 停止及时，之后还能继续 | 收到真实增量后取消，至执行流结束与持久化终态；随后再提交完整一轮 | 取消落入终态；后续请求可完成；新回复完整 | 已自动化；模型等待/工具阻塞中的取消待补 |
| UX-05 `queue` | 排队、插话、调序、撤回可控 | 活动轮次保持未完成，同时提交 3 条；调序后撤下另两条，再插话并等待完整回复 | 队列恰好 3 条；调序准确；撤下保留原文且不执行；插话实际完成；最终队列清空 | 已自动化；多条实际派发顺序和不同动作边界待补 |
| UX-06 `switch` | 反复切换不串内容、不积累订阅 | 4 个预先有真实回复的线程，循环打开快照、订阅、核验 Reset、退订和关闭 | 会话身份与初始投影吻合；观察者正常释放 | 已自动化；100×100 的单次大日志由 UX-01 覆盖 |
| UX-07 `background` | 切换页面不影响后台任务 | 一个线程收到首块后保持执行，切换其他 3 个有历史线程，核验原线程仍运行再取消 | 快照归属正确；切换未取消后台线程；取消可收敛 | 已自动化；两个线程同时输出与故障隔离待补 |
| UX-08 `workspace` | 大目录可浏览、刷新不等全量展示 | 合成目录，连续取 3 页，每页 200 条，再刷新首页 | 总数、页长、顺序准确，分页无重复 | 已自动化；深目录、变更通知、权限失败待补 |
| UX-09 `startup` / `recovery` | 启动快，重启后聊天仍在 | 新目录启动至可列线程；正常退出独立进程后重启至打开已持久化回复 | 新环境无历史；重启后会话与原文一致 | 已自动化；进程强杀、磁盘满、损坏/迁移恢复待补 |
| UX-10 `soak` | 连续使用不越来越慢、内存不失控 | 4 个线程循环发送和切换，每轮间隔 1 秒；外部采集 CPU、RSS、私有内存、句柄/FD、线程数与 I/O | 每一轮内容与落盘准确；每次切换准确；采样不截断 | 已自动化；长时趋势需按长时配置运行 |

“模型动作”遵循仓库模型轮次定义：模型调用、工具调用或最终回复均算动作。100×100 基准不是 10000 条用户消息，也不是将执行过程当成聊天首屏一次性加载。夹具细节、七个独立读路径与分析方式见 [聊天打开基准](../scripts/desktop-bench/chat-open.md)。

## 3. 一条命令复测

要求 Python 3.8+、`psutil`，首次构建探针需要 Rust 工具链。使用仓库根目录执行：

```powershell
python -m pip install psutil
python scripts/desktop-bench/measure-experience.py --profile smoke --output target/desktop-experience/smoke-001
```

驱动自动构建 Release 探针，拒绝 Debug 测量。首次构建时间不计入场景耗时。每次传入新的输出目录，保留历史报告；不要覆盖或手工清理正在使用的测试目录。

```powershell
# 日常优化：完整场景，100×100 聊天夹具保持不变
python scripts/desktop-bench/measure-experience.py --profile daily --output target/desktop-experience/daily-001

# 同环境、同参数的前后比较，退化或不可比较均返回非零码
python scripts/desktop-bench/measure-experience.py --profile daily --baseline target/desktop-experience/daily-001/report.json --output target/desktop-experience/daily-002

# 修改提交/流式/取消路径后的定向复测
python scripts/desktop-bench/measure-experience.py --profile daily --cases submit,stream,slow_consumer,cancel_resume --output target/desktop-experience/stream-001

# 长时间资源趋势，默认 2 小时
python scripts/desktop-bench/measure-experience.py --profile soak --output target/desktop-experience/soak-001

# 压慢消费缓冲：1024 块、源端 1 ms，消费者每块暂停 20 ms
python scripts/desktop-bench/measure-experience.py --cases slow_consumer --chunks 1024 --interval-ms 1 --output target/desktop-experience/backpressure-001
```

可以通过 `--probe` / `--chat-probe` 指定已构建的独立 Release 测试探针，`--fixture` 复用已有合成聊天夹具。这两个探针不是最终蛹程序。外部探针应由调用者保证工具链与构建选项一致，报告保留二进制哈希；只提供二进制不能证明其实际编译参数。

| 配置 | 普通场景重复 / 预热 | 流块数 / 间隔 | 切换次数 | 目录文件数 | 持续运行 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `smoke` | 1 / 0 | 8 / 2 ms | 4 | 600 | 3 秒 |
| `daily` | 10 / 1 | 32 / 8 ms | 50 | 2000 | 60 秒 |
| `release` | 30 / 2 | 32 / 8 ms | 200 | 10000 | 5 分钟 |
| `soak` | 1 / 0，只运行持续场景 | 32 / 8 ms | 每轮 1 次 | 不浏览目录 | 2 小时 |

持续场景每次只运行一个时间窗口，不乘普通场景的重复次数。各配置的聊天打开负载始终是 100×100；首次打开以新进程定义，不声称操作系统文件缓存已清空。允许覆盖重复次数等参数，但覆盖后的配置只能与相同配置比较。

## 4. 结果与判定

每次输出：

- `report.md`：人可读结果、各指标单位和 P50/P95/最大值。
- `report.json`：工作负载、环境、源码状态、探针哈希、每次状态、资源计数、基线比较。
- `summary.csv`：便于按场景和指标绘图。
- `samples.jsonl`：完整的逐次指标与有界资源采样序列。
- `chat-open/`：复用大日志基准的详细报告与原始数据。
- `workers/`：本次独立的合成数据，不接触个人配置与用户聊天。100×100 聊天夹具默认在 `target/desktop-chat-open/experience-fixture-v1/` 生成一次并复用，保证前后日志哈希一致；`--fixture` 可以指定其他合成夹具。

耗时统一使用单调时钟；只有以 `_ms` 结尾的指标使用毫秒。队列容量、循环次数单独标注单位。预热不进入分位数，失败和超时不能记为零，也不能从总结果中消失。单次 smoke 只说明链路可运行，不能作为可靠 P95；同一运行内的相邻增量存在相关性，`delta_gap_ms` 的样本数不等于独立进程样本数。持续场景另汇总每轮间隔 P95 和最大值，避免长时间保存无限数量的逐增量数据。

基线比较要求环境、构建声明、负载、选中场景和夹具一致，旧基线必须无失败。二进制哈希和源码版本允许变化。默认当 P50/P95 同时超过 **20% 相对增幅与 5 ms 绝对增幅**时判为退化；这是降低开发机噪声的初始阈值，不是用户体验承诺，可用参数调整。源端输出总跨度与设定的持续时长仅作为负载证据，不参与速度退化门槛。正确性失败、进程非零退出、超时、资源采样缺失/截断直接失败。退出码：0 通过，1 场景失败/退化/基线不兼容，2 参数、依赖或构建等准备失败。

资源包含 CPU 和 I/O 增量、RSS 峰值/增量、Windows 私有内存（平台可用时）、句柄或 FD、线程数。模拟模型位于探针同一进程，因此这些计数包含测试服务自身的开销；它们适合同配置比较，不能直接当作产品进程的绝对预算。持续场景排除前 20% 的资源采样后计算变化斜率和起止差；短于 60 秒标明不足以判断长时趋势。内存增长可能来自新增历史、SQLite 缓存或泄漏，斜率本身不下泄漏结论。需配合固定工作集的重复切换、不同数据规模和堆/调用栈分析定位。

当前资源增长作为诊断项保留，没有凭空设定跨机器统一内存上限；需要在目标设备建立正常基线后增加专门预算门槛。不要用所有场景加权成一个总分掩盖局部退化。

## 5. 日常执行与优化闭环

1. 修改前建立对应配置基线，保存原始报告、源码版本与是否有未提交修改；关闭会影响结论的高负载任务。开发机有并行编译时注明，重新在安静环境确认。
2. 改动后先跑定向 smoke，校验正式调用、断言和进程清理；通过后运行 daily 与基线比较。发布前使用 release，并补一轮 soak。
3. 优先修复正确性与可恢复性，再追踪 P95、CPU、I/O、内存变化。按“读取/索引 → JSON 与投影 → 调度/锁 → 事件传递 → 持久化”拆解，结论需调用栈或阶段证据支持，不能直接相减不同进程场景当作阶段成本。
   外部体验探针还会读取正式运行时计数器，在 `samples[].check.diagnostics.blocking` 保存测量窗口内各后台操作的调用次数、排队和执行累计毫秒；排除启动准备阶段。此窗口包含正确性读取和并发后台工作，计数器以整数毫秒累计，因此这些数据用于定位重复操作和慢查询，不能相加当作单请求时长，或用 0 判断操作没有成本。
4. 需要调用栈时，大日志用已有 `--symbols --profile wpr` 或 Linux `perf` 诊断模式。诊断数据不与无 profiler 基线直接比较；新体验场景可对独立探针附加平台分析器。
5. 每次优化同时检查原始内容、取消终态、队列、游标和分页不退化。确认后归档到 `docs/性能基线/`，记录收益、存储/内存代价、噪声和仍未覆盖项。

目标平台分别维护基线：Win7 x86、Ubuntu 18.04 x64，以及日常开发平台。不得用开发机的毫秒数当作低配目标机通过证据。模型和平台异常、并发、工具阻塞、强杀恢复属于下一批固定脚本场景，应保持同样的合成数据与错误断言约束。

## 6. 下一批扩充顺序

1. 模型首块前取消、实际工具阻塞时取消、停止期间重复取消，核验锁与子进程释放。
2. 两个独立线程同时输出，一个失败时另一个继续；校验事件归属、调度隔离与落盘内容。
3. 队列实际派发顺序、插话执行边界、撤回与派发竞态、重复提交幂等性。
4. 写入中强杀后重启、磁盘满/只读/配置损坏/升级迁移，验证部分文本保留、任务终态与后续可继续使用。
5. 深目录、目录增删、权限与失效路径；最后再补独立可选的 Slint 输入/滚动/绘制测试。

这些条目属于方案内的待实现范围，不计入当前已通过的覆盖率。
