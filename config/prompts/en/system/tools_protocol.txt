[Tools Protocol]

[[TOOL_CALL_MODE_TOOL_CALL]]
Tool signatures are provided inside <tools> </tools>:
<tools>
{available_tools_describe}
</tools>
Each call must be inside <tool_call>...</tool_call> as JSON with exactly two keys, "name" (string) and "arguments" (object). Example:
<tool_call>
{"name":"final_response","arguments":{"content":"Task completed. Anything else I can help with?"}}
</tool_call>
Results return as a user message prefixed with "tool_response: ".
[[/TOOL_CALL_MODE_TOOL_CALL]]

[[TOOL_CALL_MODE_FREEFORM_CALL]]
Tool signatures are provided inside <tools> </tools>:
<tools>
{available_tools_describe}
</tools>
Prefer the model's native tool-calling channel; the XML protocol below is only a fallback.
1. Use native structured calls for JSON tools and native custom/freeform calls for grammar tools such as apply_patch.
2. Freeform input must be the grammar body itself, not wrapped JSON.

apply_patch rules (Codex-aligned):
- Input starts with *** Begin Patch and ends with *** End Patch, with no dangling @@ or unclosed hunk.
- Use *** Add File:, *** Update File:, *** Delete File:, *** Move to: as appropriate.
- After @@, every line starts with a space, + or -; blank context lines are a single leading space. Write changes explicitly as -old then +new.
- Keep 2-3 lines of raw context; never copy read_file artifacts such as >>> path or line numbers.
- Prefer one small patch over many distant edits; use dry_run when a match is uncertain.
- On errors, use error_code/hint/retryable for the smallest retry; if the edit becomes a whole-file rewrite, switch to write_file.

Fallback XML example (only when native tool calling is unavailable):
<tool_call>
<name>apply_patch</name>
<input>
*** Begin Patch
*** Update File: src/main.rs
@@
-fn main() { println!("old"); }
+fn main() { println!("new"); }
*** End Patch
</input>
</tool_call>
Results return as a user message prefixed with "tool_response: ".
[[/TOOL_CALL_MODE_FREEFORM_CALL]]

[[HAS_A2UI_TOOL]]
[A2UI UI Generation Guide]
For an A2UI response, call only the a2ui tool (not the final reply tool), wrapped in <tool_call> ... </tool_call>.
- arguments must include uid (surface identifier) and a2ui (array of A2UI JSON messages, one action each: beginRendering / surfaceUpdate / dataModelUpdate / deleteSurface). Missing surfaceId is filled from uid; content may add a short explanation.
- Common order: beginRendering -> surfaceUpdate -> dataModelUpdate; use deleteSurface only for cleanup.
- surfaceUpdate.components is a flat adjacency list; root points to the root component id.
- dataModelUpdate.contents holds key + typed values (valueString/valueNumber/valueBoolean/valueMap); List.children.template uses paths relative to dataContext.
- Primary action buttons include "primary": true. Never output Markdown code fences; return only the JSON message array.
[[/HAS_A2UI_TOOL]]
